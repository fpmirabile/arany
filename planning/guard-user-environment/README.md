# Guard user environment: user tools, command environment and command tools

## Metadata

- Status: `Ready` (Research and Plan gates passed; U4+ await overlay G1′ as a named dependency)
- Owner: harness maintainers
- Last updated: 2026-10-27
- Next action: implement U1, U2a and U2b (D4, no new authority) first; U3a follows independently; U4 → U5 → U6a → U6b open after the [gates](#gates) below.

## Outcome and scope

One capability: a guarded or host `Command` finds and uses the user's own command-line tools the way Codex CLI and Claude Code do, under Arany's guarantees. Concretely, after one-time human consent in the existing folder-trust/`/permissions` flow, a user-installed executable in a user-writable directory (`~/.local/bin`, `~/.cargo/bin`, a Homebrew prefix, a version-manager shim directory) runs inside the Guard with read+exec grants; the command environment is a user-owned, pinned, journaled record derived from the user's login environment with a core allow-list default; and a user-selected command tool can act as a **command wrapper** (a prefix program or a rewriting hook: filter, proxy, token saver, logger) applied before Policy and approval, so the approved argv is the executed argv. Before any of that, the model-facing Command contract and the Guard's pre-dispatch failure reporting stop misleading the model and the user, and the Guard's selection phase stops imposing a budget no peer has. This serves [building the harness](../../AGENTS.md#product-and-implementation-priorities) (Tools, permissions, durable Sessions) and the [Daily use first](../../NEXT_STEPS.md#daily-use-first) goal of running this repository's tests without another harness.

Included: D1 command wrappers, D2 command environment, D3 user program grants, D4 contract text, diagnosability and selection budget, on Linux and macOS. Excluded: network egress ([network proxy plan](../network-proxy/README.md)), the Workspace overlay and cache storage ([overlay plan](../command-workspace-overlay/README.md)), child/worker host authority (never granted), a login or interactive shell inside the Guard (never), and reading repository settings as configuration (never; [safe AI cage](../../AGENTS.md#non-negotiable-guarantees)).

### Owner decisions (2026-10-27)

- **D1 (command wrappers).** The repository names no wrapper product anywhere: no documentation example, no instruction-file guidance, no code or test fixture tied to one tool (PR #566 removes the wrapper commands from `agents/references/testing-details.md`). Command wrappers are a generic, first-class Arany feature for any user-installed command tool: discoverable in `/permissions`, no hand-written JSON, safe by default, and compatible with the wire shapes wrapper vendors already ship for peer harnesses ([design decision](#design-decision-first-class-command-tools-over-peer-wire-shapes)). Confirmed degradation applies to the separate Rewrite hook effect (missing, drifted, timed out, non-zero exit, malformed output → the original proposal continues with a journaled stage) and to a Prefix wrapper whose pin fails before intent normalization, Policy and approval; a prefix-wrapped command that has been dispatched keeps its own Failed, Limit, Cancelled or Uncertain outcome and is never rerun unwrapped.
- **D1 scope.** The rewrite scope follows what the peers actually allow, verified from source and documentation ([peer behavior](#peer-behavior-verified-from-source-and-documentation)), not an assumed "pinned-shell `-c` only" rule; the chosen scope and each divergence are in [Contract and scenarios](#contract-and-scenarios).
- **D2 (command environment source).** Follow Codex CLI and Claude Code: the user's login environment is the source. Arany's equivalent is a user-owned environment record captured from the Arany process environment by default and, on explicit human request, from the user's login shell run once on the host outside the sandbox; the record is pinned, digested, journaled and re-captured only on a human action. Secret handling is at least as safe as the peers: a core allow-list default plus the Codex secret-name exclusions applied unconditionally. Where a guarantee forbids the exact peer behavior the divergence is named in [Contract and scenarios](#contract-and-scenarios).
- **D3 (user programs in the Guard).** User-installed executables in user-writable directories, including version-manager shims and rustup proxies, are usable inside the Guard with read+exec-only grants, resolved directories and their dynamic dependencies (Homebrew prefix, interpreter shebangs, manager roots), with an honest statement of the exposure ([security model](#security-and-resource-model)).
- **D4 (contract, diagnosability, selection budget).** Ship the low-risk fixes first: model-facing Command contract text, refusal of a non-`-c` first argument for the pinned shell, named selection-boundary causes, the error variant in `development.log`, the Guard stage in `/agents`, accurate recovery text. The Guard's project-selection budget follows the peers: no peer has a separate setup cap, so selection runs inside the command's own timeout (default 120 s, maximum 600 s, the Claude Code Bash defaults Arany already uses) instead of an Arany-specific 5 s cap.

### Current Arany behavior

- **Guarded command environment and PATH.** [`guard.rs::runtime_path`](../../crates/arany/src/tools/guard.rs) builds `PATH` from each selected toolchain grant's `bin` followed by `/usr/bin:/bin`; nothing from the host environment enters. The payload environment is cleared and set to `PATH`, private `HOME`/`TMPDIR`, cache-view `CARGO_HOME`/`CARGO_TARGET_DIR`/`npm_config_cache`/`PIP_CACHE_DIR`, `ARANY_TOOL_*`, `NO_COLOR`, plus `CURL_SSL_BACKEND` and `SDKROOT` for Rust/SDK grants ([`guard.rs` environment block](../../crates/arany/src/tools/guard.rs), [Commands](../../docs/specs/tools.md#commands), [macOS environment](../../docs/specs/tools.md#macos-enforcement-and-compatibility)). Toolchain grants are mounted read-only on Linux ([`guard/linux.rs::runtime_mounts`](../../crates/arany/src/tools/guard/linux.rs)) and granted `file-read* file-map-executable process-exec (subpath …)` on macOS ([`guard/macos.rs`](../../crates/arany/src/tools/guard/macos.rs)); a non-toolchain grant is read-only. Both revalidate the grant's device/inode and executables through [`RuntimeGrant::verify_host`](../../crates/arany/src/tools/toolchains.rs) before dispatch.
- **Runtime discovery.** [`toolchains::discover`](../../crates/arany/src/tools/toolchains.rs) reads `~/.rustup/toolchains`, the nvm/fnm/Volta/asdf Node roots and `~/.pyenv/versions`, metadata only, numeric labels only; [`RuntimeKind`](../../crates/arany/src/tools/toolchains.rs) has eleven variants and [`MAX_RUNTIME_GRANTS`](../../docs/specs/limits.md#max_runtime_grants) caps selections at 11. Pins live in the account-root `workspace-permissions.json` (version 2, [`workspace.rs`](../../crates/arany/src/tools/workspace.rs)), bound by exact path and device/inode per folder ([folder trust](../../docs/specs/tools.md#folder-trust-and-approvals)).
- **Host commands.** [`tools.rs`](../../crates/arany/src/tools.rs) pins a `command_unguarded` program through `std::env::var("PATH")` of the Arany process at admission; [`unguarded::pin`](../../crates/arany/src/tools/unguarded.rs) refuses relative or Workspace-internal PATH entries, pins executable path/device/inode/SHA-256 and the PATH string, and `environment_digest` covers `HOME`, `TMPDIR`, `LANG`, `LC_ALL`, `TERM`. Dispatch uses a cleared environment with that PATH, real `HOME`, `TMPDIR`, `NO_COLOR`, `ARANY_TOOL_WORKSPACE`, `ARANY_UNGUARDED` and the three locale/terminal values when set ([primary host commands](../../docs/specs/tools.md#primary-host-commands)). Without a host pin, the same launcher falls back to `runtime_path`. Remembered prefixes exclude privilege tools, the closed wrapper/launcher list ([`unguarded.rs::WRAPPERS`](../../crates/arany/src/tools/unguarded.rs): `env`, `xargs`, `find`, `nice`, `timeout`, …), interpreters and generic `git`/`gh`/`rm`, and [`permissions/host.rs::eligible`](../../crates/arany/src/tools/permissions/host.rs) also refuses inline options and shell metacharacters in any token ([remembered host prefixes](../../docs/specs/tools.md#remembered-host-prefixes)); a shell-form host command (`sh -c SCRIPT`) is therefore never eligible. Remembered host rules are written by `/permissions` into the private [`RecordKind::UnguardedCommands`](../../crates/arany/src/tools/unguarded_rules.rs) record, not hand-edited.
- **Hooks are user-owned and only narrow.** Hooks and permission rules load from the State directory's private `permissions.json` ([`RecordKind::Permissions`](../../crates/arany/src/store/state.rs), [`tools.rs::load_permissions`](../../crates/arany/src/tools.rs)); repository content never supplies them. The hook schema copies the Claude Code `hooks` envelope ([`permissions/hooks.rs`](../../crates/arany/src/tools/permissions/hooks.rs): events, matcher, `type: "command"`, `command`, `args`, `timeout`). `PreToolUse` handlers run after the permission decision as journaled Guard `Command` effects; `updatedInput` narrows only reads, and for `command` "a changed argv has no provable order; the model must propose it as a new call" ([hook execution](../../docs/specs/tools.md#hook-execution), [`step/hooks.rs`](../../crates/arany/src/engine/run_loop/step/hooks.rs)). Unknown hook outcomes stop the Run without retry ([delegated Tools](../../docs/specs/tools.md#hook-execution)). A wrapper rewrite therefore cannot be a `PreToolUse` hook today; D1 needs a stage that runs before Policy and approval and inherits the same unknown-outcome rule.
- **Model-facing contract.** [`catalog.rs::COMMAND_CONTRACT`](../../crates/arany/src/tools/catalog.rs) says nothing about the cleared environment, the fixed `PATH`, or that login/interactive shell options are useless; it does say `command_unguarded` exists. The model emitted `sh -lc …` in the triggering dogfood, which made `/bin/sh` try `/etc/profile` under Seatbelt and, because [`guard.rs::prefix_shell_runtime_compat`](../../crates/arany/src/tools/guard.rs) prefixes only when `args[0] == "-c"`, silently skipped the documented page-size compatibility prefix ([macOS compatibility](../../docs/specs/tools.md#macos-enforcement-and-compatibility)).
- **Pre-dispatch failure reporting.** [`tools.rs::failure_stage`](../../crates/arany/src/tools.rs) maps every `ToolError` without its own label, including `Timeout`, `NotFound` and `Conflict` from the project [selection phase](../../crates/arany/src/tools/selection.rs), to `"execution"`; `unstarted_observation` then prints `Cause: execution` with the generic Guard-executable remedy. The same three variants also arise outside selection: [`guard.rs::spawn_before`/`capture`](../../crates/arany/src/tools/guard.rs), [`guard/linux.rs::receive_result`](../../crates/arany/src/tools/guard/linux.rs) and `discovery_work` emit `Timeout`, and [`fs.rs`](../../crates/arany/src/tools/fs.rs) emits `NotFound`/`Conflict` for typed file mutations, so the variant alone does not identify the stage. The selection boundary is [`fs::prepare_command`](../../crates/arany/src/tools/fs.rs)/`selected_command_changeset` (in process on macOS, through [`selection_phase::response`/`receive`](../../crates/arany/src/tools/guard/selection_phase.rs) on Linux). [`diagnostics::tool_failure`](../../crates/arany/src/diagnostics.rs) logs only `stage`, `check` and `detail`, so the variant is lost. The Guard worker serializes `BootstrapFailure::at(stage)` without a check for payload-stage errors ([`guard.rs`](../../crates/arany/src/tools/guard.rs)). The CLI sentence in [`presentation.rs`](../../crates/arany-cli/src/presentation.rs) says "Use /agents to inspect the Guard stage", but [`presentation/agents.rs`](../../crates/arany-cli/src/presentation/agents.rs) renders no stage field; the stage exists only in the observation text. Contract: [Guard failures before dispatch](../../docs/specs/tools.md#portable-skills) and [diagnostics](../../docs/specs/diagnostics.md).
- **Selection budget.** [`selection.rs`](../../crates/arany/src/tools/selection.rs) caps the project selection phase at `PHASE_TIME = 5 s` regardless of the command's own `runtime_ms` ([`DEFAULT_COMMAND_TIMEOUT_MS`](../../docs/specs/limits.md#default_command_timeout_ms) 120 000, [`MAX_COMMAND_TIMEOUT_MS`](../../docs/specs/limits.md#max_command_timeout_ms) 600 000, [`ToolLimits`](../../crates/arany/src/tools/types.rs)), alongside the byte and call caps (`CONTROL_BYTES`, `CONTROL_TOTAL_BYTES`, `CONTROL_FILES`, `RULES`, `COMMAND_CALLS`). `Selector::new` clamps every deadline to `now + PHASE_TIME`; [`tools.rs::reservation_overhead`](../../crates/arany/src/tools.rs) adds `PHASE_TIME` to the scheduling reservation; the Linux [`selection_phase::encode_deadline`](../../crates/arany/src/tools/guard/selection_phase.rs) clamps the transmitted deadline to `PHASE_TIME`. A large tree therefore fails with a selection timeout while the command had minutes of budget left.
- **Owners that stay.** [Enforcement failure causes](../../docs/specs/tools.md#enforcement-failure-causes) keep `guard_bootstrap`/`filesystem_denied`; [persistent build cache](../../docs/specs/tools.md#persistent-workspace-build-cache) keeps toolchain, SDK, cache and Cargo jobs; [session](../../docs/specs/session.md#workspace-admission-and-authority) keeps instruction files (repository `agents/` stays tool-neutral; no instruction text is needed for wrappers because the feature is configuration, not model guidance); [terminal](../../docs/specs/terminal.md#interactive-commands-and-completion) owns `/permissions`, consent pages and `/agents`.

## Design decision: first-class command tools over peer wire shapes

The owner asked why Arany should copy Claude Code's `PreToolUse`/`updatedInput` hook system instead of designing something better, given that adopting a wrapper, proxy, filter or user CLI must be easy: minimal setup, discoverable in `/permissions`, no hand-written JSON, safe by default. Options compared:

| Option | Adoption | Compatibility | Guarantees | Verdict |
|---|---|---|---|---|
| **A. Peer hook compatibility only** (a `commandRewrite` JSON object in `permissions.json`, Claude Code wire shape) | Hand-written JSON with an absolute path and a SHA-256; only tools that already speak a peer hook protocol | Existing wrappers work unchanged | Pin, Guard execution and journaling are possible, but the user computes digests by hand and nothing shows which tool is active | Rejected as the user-facing surface: it is the peers' weakest point |
| **B. A new Arany protocol** (own stdin/stdout schema, own discovery of "wrapper-capable" tools) | Every vendor must add an Arany mode; nothing discovers capability generically | No existing tool works until vendors ship support | Same as A | Rejected: a plugin model without adopters ([smell test](../PLANNING.md#smell-test)) |
| **C. First-class Command tools UX over the peer wire shapes, plus import** (chosen) | `/permissions` → Command tools lists executables from the directories the user already granted (D3), the user picks a tool and a role, Arany pins identity and digest, probes the tool in the Guard with a sample command and shows the rewrite preview before enabling; one keystroke imports `PreToolUse` command hooks from the user's own Claude Code settings | Hook-aware wrappers work through the `PreToolUse` JSON exchange they already implement; any plain CLI works as a prefix exactly as under `CLAUDE_CODE_SHELL_PREFIX` | Configuration is a user-owned private record written by `/permissions` (like remembered host rules), never repository content; execution is in the Guard under the hook grant; the rewritten argv is what Policy, approval and replay bind; confirmed failures degrade, unknown outcomes are Uncertain | Chosen |

Why C keeps every guarantee and is still the simplest: the wire shapes are borrowed, not designed (two argv/JSON constructors and one JSON parser that the hook code already has); the discovery, pin and probe reuse the D3 grant class, the hook executable identity checks and the hook Guard grant; the record reuses the `/permissions`-written private record pattern of [`unguarded_rules.rs`](../../crates/arany/src/tools/unguarded_rules.rs). The import reuses the existing hook parser because Arany's `hooks` schema already copies Claude Code's. No crate, daemon, trait, plugin loader or network. A "better" protocol would cost adoption without buying a guarantee; the guarantee gains (pinning, Guard execution, journaled rewritten argv, no hook-granted approval, Uncertain on unknown) come from the stage design, not from the wire shape.

Roles a selected command tool can have (one tool may have several):

- **Program** (D3): reachable on the Guard `PATH`; nothing else changes.
- **Prefix wrapper**: every shell-form proposal `sh -c SCRIPT` is dispatched as `<wrapper> [fixed args] SCRIPT` with the whole script as one argument, the Claude Code `CLAUDE_CODE_SHELL_PREFIX` contract (the wrapper re-evaluates `$1` with a shell). The wrapper becomes the program and is added to the closed wrapper set, so a prefix wrapper is never prefix-eligible for remembered host rules and cannot launder an arbitrary script through a short remembered prefix. A prefix wrapper is not a separate effect: the wrapped command is the command, so its Failed, Limit, Cancelled or Uncertain outcome is the command's outcome and is never followed by an automatic unwrapped rerun. Only a pin failure at intent normalization, before Policy and approval, degrades to the unwrapped proposal; a pin mismatch at dispatch refuses the approved intent with `ChangedInput` instead of altering it.
- **Rewrite hook**: before Policy, the tool receives the Claude Code `PreToolUse` input on stdin and may return `hookSpecificOutput.updatedInput.command`; the rewritten script becomes a new shell-form intent. Only the Claude Code shape is spoken: it is the canonical one every surveyed vendor implements first, and Arany's hook parser already understands it.

## Contract and scenarios

Owning contract: [Tools](../../docs/specs/tools.md) (folder trust, commands, host commands, hooks, Linux/macOS enforcement, limits); [Diagnostics](../../docs/specs/diagnostics.md) for the development log; [Terminal](../../docs/specs/terminal.md) for `/permissions`, consent and `/agents`; [Session](../../docs/specs/session.md) is unchanged. Exact sentence changes are listed per slice.

**Rewrite scope (D1 scope).** Peers rewrite the shell command string of their Bash-equivalent tool; Claude Code's `updatedInput` also reaches any other tool, OpenCode's plugin hook reaches any tool's args, and the surveyed wrappers rewrite only shell commands. Arany's scope: the wrapper stage applies to every primary `Command` and `command_unguarded` proposal. A shell-form proposal (`sh -c SCRIPT`) is presented as `tool_input.command = SCRIPT`; an explicit-argv proposal is presented as its shell-quoted command line (the peers have no explicit-argv tool, so this is the only faithful mapping) and, if rewritten, becomes a shell-form proposal with the same `cwd`. Child, worker and hook commands are never rewritten (peer: Claude Code hooks do run inside subagents; Arany diverges because children have no authority to add tools and the primary's receipts must stay the single provenance). Non-command Tools (Read, Edit, typed Git, MCP) are not in scope: Arany's typed file Tools already have `PreToolUse` read narrowing, and a rewrite that widened a path would break "hooks only narrow"; this divergence from Claude Code's any-tool `updatedInput` is recorded in the rewrite paragraph.

Named divergences from the peers, each recorded in the owning passage by its slice:

| Peer behavior | Guarantee | Arany divergence |
|---|---|---|
| Commands read most of the host, including credentials | Per-effect isolation: never widen disclosure | Only human-selected user program directories and manager roots are granted, read+exec, pinned by identity; `HOME`, `TMPDIR` and credentials stay out |
| Full environment inherited, secrets included by default | Per-effect isolation; security rule "minimum child environment" | Core allow-list default; `*KEY*`/`*SECRET*`/`*TOKEN*` names are refused even when selected; values are never journaled, only the record digest |
| Login shell (`-lc`) per command; rc files run under the sandbox | Per-effect isolation (rc files read the host home) and journal-first (an rc file is unjournaled behavior) | The login shell runs at most once, on the host, on an explicit human action, with cwd `$HOME`, and only its environment is captured; the pinned shell inside the Guard refuses anything but `-c SCRIPT` |
| Hooks run on the host with full user permissions; repository settings may add hooks after trust; `CLAUDE_CODE_SHELL_PREFIX` is an environment variable | Safe AI cage: repository content supplies no authority; hooks run in the Guard | Command tools are selected in `/permissions`, stored in a private user-owned record, pinned by executable identity and digest, and run in the Guard under the existing hook grant; a repository, an environment variable or model text cannot install one |
| `updatedInput` from a hook replaces the Bash command, then permissions are evaluated | Journal-first; approvals bind the exact executed argv | Same ordering (rewrite → Policy → approval → dispatch), with the original proposal, the tool identity and the rewritten argv journaled in the intent; strict replay never re-runs the tool |

## Chosen direction

Simplest sufficient solution after Ponytail: extend the existing seams instead of adding new ones. User programs are two new [`RuntimeKind`](../../crates/arany/src/tools/toolchains.rs) variants (`UserPrograms`, `ManagerShims`) that flow through discovery → consent → `workspace-permissions.json` pin → Linux read-only bind / macOS subpath grant → `runtime_path`, exactly as toolchains do. The command environment is one new private record (`command-environment.json`, [`RecordKind`](../../crates/arany/src/store/state.rs)) that replaces the two live `std::env` reads in [`tools.rs`](../../crates/arany/src/tools.rs) and [`unguarded.rs`](../../crates/arany/src/tools/unguarded.rs) and feeds user-program discovery. Command tools are one new private record (`command-tools.json`) written only by `/permissions`, following [`unguarded_rules.rs`](../../crates/arany/src/tools/unguarded_rules.rs); the wrapper stage reuses the hook executable identity checks, the hook Guard grant, the Claude Code stdin/stdout wire shape, the hook output parser and the existing bounds; only its position (before Policy), its accepted output (`updatedInput.command`) and the prefix argv constructor are new. The selection budget change deletes a constant's clamping role rather than adding anything. No new crate, daemon, trait or plugin model.

Record and wire shapes:

- `command-tools.json` (version 1): `tools[]` with `path` (absolute, inside a granted user program directory or shim directory), `device`, `inode`, `sha256`, `roles` (`prefix` | `rewrite`, non-empty), `args` (fixed arguments, exec form, ≤ 16 tokens), `timeout_s` (default 10, ≤ 600, the Claude Code default being 600 and the Codex snapshot bound 10), `source` (`selected` | `imported`), `probe` (the last preview: sample input digest, outcome, rewritten script or closed failure). At most 4 tools; at most one Prefix wrapper; Rewrite hooks run one at a time in record order and each sees the previous output, Arany's deterministic sequential composition (Claude Code runs matching hooks in parallel; the existing [hook divergence](../../docs/specs/tools.md#hook-execution) "Sequential configuration order, bounded matches" for journal-first ordering and deterministic replay applies unchanged). The record is read at Tool admission and digested into `RunStarted.tool_policy` beside `permissions_digest`.
- Rewrite stdin is the Claude Code `PreToolUse` input with `tool_name: "Bash"`, `tool_input.command` (the script, or the shell-quoted explicit argv), `cwd` and `session_id`; accepted stdout is exit 0 with `hookSpecificOutput.updatedInput.command` as a control-free string within the existing 4096-byte command bound; empty stdout or an identical command means "no rewrite"; everything else, including `permissionDecision`, `permissionDecisionReason` and `additionalContext`, is ignored for authority (the reason is shown in the Tool row as text). The rewritten call is `sh -c SCRIPT` with the same `cwd`.
- Prefix argv is `<tool path> <args…> SCRIPT` with the script as the final single argument, run in the Guard or on the host exactly where the original would run; for a host proposal the wrapper itself is pinned as the host executable and the script token keeps the host command's existing token bounds.
- `command-environment.json` (version 1): `source` (`process` | `login-shell`), `shell` (`path`, `sha256`, only for `login-shell`), `captured_at`, `path` entries, `names` (selected variables with values), `excluded` (names dropped by the secret patterns, names only) and `sha256` over the canonical bytes. The default record is derived from the process environment with the core set `PATH, SHELL, TMPDIR, TEMP, TMP, HOME, LANG, LC_ALL, LC_CTYPE, LOGNAME, USER`. Inside the Guard only `PATH` ordering, `LANG`, `LC_ALL`, `LC_CTYPE` and the manager home variables of selected shim grants are used; `HOME` and `TMPDIR` stay private scratch. Host commands use the record's `PATH` and names in place of today's live reads; `environment_digest` becomes the record digest plus `HOST_POLICY_VERSION`.
- Selection budget: `Selector` deadlines derive from the intent's `runtime_ms`; `PHASE_TIME` is deleted, `reservation_overhead` reserves the command runtime once (no separate selection term), and `selection_phase::encode_deadline` transmits the remaining command budget. `DISCOVERY_TIME` (reads) is unchanged.

Linux/macOS impact: policy is identical; mechanisms differ as today (bind mounts and Landlock exec on Linux, Seatbelt subpath grants on macOS). macOS needs the Homebrew prefix granted as a whole (`bin` links into `Cellar`, dylibs under `opt/*/lib`) and user binaries are not catalogue-checked system executables, so they form an explicit grant class without the root-owned/unentitled checks; the consent text says so. Linux grants `/home/linuxbrew/.linuxbrew` the same way. A command tool must live in a granted directory, so it is reachable in the Guard on whichever platform enforces the grant. Interpreter shebangs resolve to `/usr/bin` interpreters (already executable) or to a granted directory; a venv interpreter inside the Workspace stays a Workspace file and is not an exec grant. Native evidence per platform is required before claiming support ([exit criteria](#exit-criteria)).

Ownership changes: `toolchains.rs` owns user-program discovery and the closed shim table; `store/state.rs` owns the two new record kinds; `unguarded.rs` keeps host pinning but reads the environment record, and its wrapper set gains the configured prefix wrapper; a new `tools/command_tools.rs` owns the record, pin verification, probe and import parsing (one owner, in-process, no trait); `step/hooks.rs` owns the wrapper stage (its position is a new call site in `step/intent.rs` before Policy); `presentation/agents.rs` renders the typed Guard stage; `cli/attached/permissions.rs` gains the Command environment and Command tools pages. No seam crosses a process boundary that does not already exist; a rewrite is one more Guard `Command` effect. Hard-to-reverse choice: the wrapper stage is placed before Policy. The alternative (accept `updatedInput` for `command` from existing `PreToolUse` hooks after the decision) was rejected because it would make the approved argv differ from the executed one.

## Security and resource model

This plan triggers the [security pass](../../agents/security.md#security-pass-triggers): new capability behavior, new child-process path and filesystem access, new persistent-state formats, new configuration surface. Each implementing slice performs it for its actual change.

Assets: Workspace bytes, StateRoot and account records, the user's home directory contents and credentials, Provider-visible journal text. Trust boundaries: human consent and the private `workspace-permissions.json`/`command-environment.json`/`command-tools.json` records supply authority; repository content, model text, Tool output, a tool's output, the user's Claude Code settings file (data for an import proposal, never configuration) and the contents of granted directories supply none. Attacker-controlled inputs: the model's proposed argv and script (reaches the rewrite tool on stdin, inside the Guard), the bytes of granted directories (run inside the Guard), the login shell's rc files (run once on the host with the user's own authority, like opening a terminal), the tool's stdout (parsed under the existing hook bounds), the imported settings file (parsed by the existing fail-closed hook parser, proposals only).

Threat cases:

- **PATH hijack.** A same-user process plants a `cargo` in `~/.local/bin`. Inside the Guard it runs with the Guard's grants only; ordering puts toolchain bins first so a selected Rust toolchain wins over a user directory for the same name. Same-user host tampering is outside the threat model ([safe AI cage](../../AGENTS.md#non-negotiable-guarantees)); the consent text states that a granted directory runs whatever it currently holds. A directory under the Workspace is never a candidate (model-writable).
- **Shim code execution.** A shim executes manager logic that reads its manager root. Granting the root read-only and setting the manager home variable makes it work without `HOME`; the manager cannot write (no download, no `rustup update`), and a missing version fails closed offline. A shim that needs a writable root is unusable in the Guard and the consent row says so.
- **Secrets in the environment.** Names matching the closed `*KEY*`/`*SECRET*`/`*TOKEN*` patterns are refused at selection time and dropped at capture, unconditionally (stricter than both peers' defaults); values of selected names are shown only in `/permissions` after an explicit reveal and never enter the journal, `development.log` or Provider requests; the Guard receives only the listed subset. Host commands keep today's allowlist semantics with the record as the source. A user who selects `SSL_CERT_FILE` pointing at an ungranted host path gets a command that fails closed, not a widened grant.
- **TOCTOU on resolved binaries.** Directory pins bind device/inode, not file digests, like toolchain grants; a file replaced inside a granted directory between consent and dispatch runs. This is the accepted pin posture for runtime roots; host command executables keep their per-intent digest pin and re-verification at dispatch, and every command tool is digest-pinned in `command-tools.json` and verified before each invocation; a drifted tool is refused and marked "needs re-pin".
- **Wrapper rewriting approved argv.** The wrapper stage runs before Policy and approval; the human sees and approves the rewritten or prefixed argv; the intent digest covers it; `permissionDecision` from the tool is ignored; the rewritten script and the prefix program pass the same privilege-tool, wrapper and interpreter policies as a model proposal; a tool cannot change `cwd`. A rewritten proposal keeps `program = sh` and a prefix wrapper is in the closed wrapper set, so [`permissions/host.rs::eligible`](../../crates/arany/src/tools/permissions/host.rs) refuses both for remembered prefixes: a wrapped host command always needs a fresh human approval. Claude Code lets `Bash(<wrapper> …:*)` rules and a hook's `allow` auto-approve the rewritten command; Arany diverges here under its host-authority rules.
- **Import as a configuration vector.** The import reads one user-owned file, parses it with the fail-closed hook parser, and yields proposals that still require the pin-and-preview confirmation; a project `.claude/settings.json` is never read, so a repository cannot propose a tool.
- **Replay.** The journaled intent carries the final argv, the original argv digest, the tool identity and the environment record digest; strict replay re-executes nothing and rejects a digest mismatch. Neither record is read during replay.
- **Tool as an attack surface.** It receives model text on stdin (rewrite) or as an argument (prefix) inside the Guard (offline, private view, explicit environment, hook bounds), or on the host only for a human-approved host command. The rewrite is a separate pre-Policy effect, so its confirmed failure or hostile output degrades to the unrewritten proposal and its unknown outcome is Uncertain and stops the pending Tool call. The prefix wrapper is the command itself: a failure after dispatch may already have executed the payload, so it is recorded as the command's Failed, Limit, Cancelled or Uncertain outcome and never triggers an unwrapped rerun; only a pin failure at normalization, before Policy and approval, degrades, and a pin mismatch at dispatch refuses the approved intent.

Bounds: candidate directories ≤ 32 per discovery, PATH ≤ 16 KiB (existing `pin` bound), environment record ≤ 64 KiB and ≤ 64 selected names, capture output ≤ 64 KiB and 10 s, command tools ≤ 4 with ≤ 16 fixed arguments each and `timeout_s` ≤ 600, rewrite stdin/stdout under the existing hook caps, probe and import under the same caps and the 64 KiB config bound, selection under the command's `runtime_ms` (≤ [`MAX_COMMAND_TIMEOUT_MS`](../../docs/specs/limits.md#max_command_timeout_ms)) and the unchanged byte/call caps, selected runtime grants still within [`MAX_RUNTIME_GRANTS`](../../docs/specs/limits.md#max_runtime_grants) raised by the slice that adds the kinds (regenerated `limits.md`). Overflow refuses the candidate, capture, tool or rewrite; never truncates silently. Failure containment: a Guard failure before dispatch stays `guard_bootstrap`-class reporting with the new named causes. Rewrite and capture outcomes follow [Honest uncertainty](../../AGENTS.md#non-negotiable-guarantees) and the [hook contract](../../docs/specs/tools.md#hook-execution): a confirmed non-execution (unpinned, drifted or missing executable, refused before dispatch) or a completed failure with a receipt (non-zero exit, recorded `Limit` for timeout or overflow, malformed output) degrades to the unrewritten proposal or the unchanged record with a journaled stage; an unknown outcome (missing receipt, Guard or host process lost without a recorded exit) is journaled Uncertain, stops the pending Tool call or `/permissions` action, is reported as unknown and is never retried automatically. Prefix execution is not degraded: only a pin failure at normalization, before Policy and approval, falls back to the unwrapped proposal, a pin mismatch at dispatch refuses with `ChangedInput`; after dispatch the wrapped command's Failed, Limit, Cancelled or Uncertain outcome stands, with the host no-retry rule unchanged.

Explicit non-claims: a granted directory's contents are not reviewed or signed; a user program can read every granted path and the Workspace snapshot; the login shell capture executes the user's rc files on the host once per capture; `/permissions` reveals selected values to the terminal; the probe proves protocol compliance for one sample, not the tool's behavior on every script.

## Risks and mitigations

- Overlay plan reserves `guard/linux.rs`, `guard.rs`, `tools/process.rs` → U4+ open after G1′ and rebase on the overlay head; U1/U2a/U2b touch `guard.rs` only at `prefix_shell_runtime_compat`, the worker failure serialization and the selection deadline plumbing ([gates](#gates)).
- A typed Guard stage on the observation changes a journaled record → follow the `approval_cause` precedent (nullable fact); if a format version changes, ship migration and fixture in the same PR (global rule 5).
- A wrapper is not self-contained in the Guard (dylibs, config reads) → the probe shows the failure before the role is enabled; at run time a Rewrite hook's confirmed failure degrades with a journaled stage, while a prefix-wrapped command that fails after dispatch keeps that failure as its outcome (the Tool row names the wrapper so the user can disable it); native dogfood records the result in NEXT_STEPS.
- A prefix wrapper on macOS launches the SIP-protected system shell, which strips `DYLD_INSERT_LIBRARIES` → the compatibility export is placed inside the script argument, the mechanism already used for `/bin/sh -c`, so the wrapper's shell re-exports it for its children; a wrapper that does not run the script through a shell gets no compatibility claim, which the consent text states.
- Removing the selection cap lets a slow tree consume the command budget → the byte and call caps still bound work, the typed cause says where the time went, and the model can raise `timeout_ms` up to the maximum exactly as under Claude Code.
- Login-shell capture hangs or prints secrets → 10 s bound, 64 KiB cap, name filter before storage, values never logged.
- `MAX_RUNTIME_GRANTS` and the 128-entry trust record become tight with many directories → cap user program directories at 8 per folder; overflow asks the user to deselect.
- Codex-style PATH prepend logic is not copied → Arany's PATH is a pinned record, so there is no login-shell reordering to repair.

# Tool-step Event folding and lenient inspection

## Metadata

- Status: `Ready`
- Owner: harness maintainers
- Last updated: 2026-10-25

## Outcome and scope

One capability: a Tool step commits fewer Events without losing any committed fact, and a Session whose history fails strict validation can still be inspected. Concretely: (a) the permission verdict becomes a field of `ToolStarted`, so a step without hooks commits `GoalProviderCallReserved`, `ProviderCallRecorded`, `ToolStarted` and `ToolFinished` (four instead of five); (b) the Engine runs the reducer's `ToolStarted` validation before dispatching a step, so a would-be `InvalidHistory` on resume becomes a typed refusal with a reason at proposal time; (c) `arany show` falls back to a lenient per-Event projection with a visible notice when strict replay rejects a history, never for resume or continuation.

Responsibility served: journal-first durability at lower cost ([priority 1](../../AGENTS.md#product-and-implementation-priorities)); global rule 5 (one current format, migration with fixture, archive below the floor). Excluded, with the reason recorded in Research: folding `GoalProviderCallReserved` or the hook Events.

## Research

- Events of one primary Tool step in commit order: `GoalProviderCallReserved` ([run_loop.rs:437](../../crates/arany/src/engine/run_loop.rs)) → `ProviderCallRecorded` → `ToolStarted` ([step/intent.rs:422](../../crates/arany/src/engine/run_loop/step/intent.rs)) → zero or more `HookStarted`/`HookFinished` pairs for `PreToolUse` handlers ([step/hooks.rs:956,971](../../crates/arany/src/engine/run_loop/step/hooks.rs)) → `ToolPermissionDecided` ([step.rs:653](../../crates/arany/src/engine/run_loop/step.rs); the delegation-deadline refusal path appends it at [intent.rs:438](../../crates/arany/src/engine/run_loop/step/intent.rs)) → dispatch → `ToolFinished` ([intent.rs:460,598](../../crates/arany/src/engine/run_loop/step/intent.rs)) → `PostToolUse` hook pairs ([hooks.rs:1175,1240](../../crates/arany/src/engine/run_loop/step/hooks.rs)). Payloads: `ToolStarted { run_id, agent_run_id, intent: ToolIntentRecord, active_ceiling_ms }`, `ToolPermissionDecided { run_id, agent_run_id, verdict: PermissionVerdict }` where `PermissionVerdict { host, intent_digest, decision, mode, basis, source, .. }` ([tools/permissions.rs:81](../../crates/arany/src/tools/permissions.rs)) already correlates by intent digest ([events.rs:379-410](../../crates/arany/src/session/events.rs)).
- Versions and floors: `ToolStarted` floor 13 (current 14), `ToolPermissionDecided` floor 4 (current 7), `HookStarted` 3→4 (current 11), `HookFinished` 8→9 (current 17), `ToolFinished` 19→20 ([store/migrate.rs:322](../../crates/arany/src/store/migrate.rs) `EVENT_FLOOR`, [execution.md payload versions](../../docs/specs/execution.md#admission-persistence-and-recovery)). Migration steps are JSON `Value -> Value` per `(kind, source version)`; the machinery cannot merge two rows into one. Rule 5 and [execution.md Journal migration](../../docs/specs/execution.md#journal-migration) permit the other path: "history below a floor is archived" intact and replaced with a fresh store with a notice; `every_stored_version_above_its_floor_has_a_step_and_fixture` ([migrate/tests.rs:1795](../../crates/arany/src/store/migrate/tests.rs)) enforces step-plus-fixture for every version above a floor.
- Headroom and caps: `Action::ProviderCall.max_events()` reserves 7 + steering + previews ([engine/ledger.rs:202](../../crates/arany/src/engine/ledger.rs)); Events per Session lineage are capped at `MAX_SESSION_EVENTS = 10_000` ([store/replay.rs:11](../../crates/arany/src/store/replay.rs); [execution.md Persistence bounds](../../docs/specs/execution.md#persistence-bounds)), so today a hook-free Session holds roughly 2,000 Tool steps; folding raises that to about 2,500 without touching the cap.
- Why the reservation stays: `GoalProviderCallReserved.active_ceiling_ms` commits before the Provider call so that a crash charges the Goal ("a crash charges it", [events.rs:344](../../crates/arany/src/session/events.rs)); folding it into the post-call record would weaken the durable-Goals guarantee. Why hook Events stay: each hook handler is a Guard process, an effect with its own committed intent (`HookStarted`) under journal-first; and they are absent when no hooks are configured, so they cost nothing in the common case.
- Validation on append already runs the reducer: `Journal::append` validates each transition and the four `begin_write` callers reuse the cached admission ([overview §2](../../docs/architecture/system-overview.md#2-runtime-architecture); the gitignored `.lavish/architecture-maps-after.html` review, problem 3). The live/replay divergence the review found is in Engine decisions taken without an Event (editor delegation, G5). For Tool steps, `check_tool` ([run_loop.rs:1287](../../crates/arany/src/engine/run_loop.rs)) and `primary_lease_allows` ([step/permission.rs:364](../../crates/arany/src/engine/run_loop/step/permission.rs)) decide before the intent commits; the reducer's `ToolStarted` validation (`session/events/validate/tool.rs`, `reducer/tool/lifecycle.rs`) is a second implementation of overlapping predicates.
- `show` uses strict read-only replay ([overview §4](../../docs/architecture/system-overview.md#4-public-command-contract)); a rejected history yields a typed State/replay error and no transcript ([goals.md Current-format replay](../../docs/specs/goals.md#current-format-replay-and-exec)).
- Peers: Codex writes one `ResponseItem` per function call and output plus a few turn-level Events; its persistence policy skips every Begin/Delta/approval-request event as "transient, non-durable" ([rollout/src/policy.rs](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/policy.rs)); `reconstruct_rollout` tolerates unknown or partial items and never re-executes ([rollout_reconstruction.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/rollout_reconstruction.rs)). Claude Code records a message, a tool use and a tool result per call in a JSONL whose format "is internal to Claude Code and changes between versions" ([sessions](https://code.claude.com/docs/en/sessions)); interrupted tool calls are marked cut-off, not re-run. Goose stores messages in SQLite with a 17-step migration chain ([session_manager.rs](https://github.com/block/goose/blob/main/crates/goose/src/session/session_manager.rs)).

## Contract and scenarios

- Owning specs: [execution.md Committed Event stream](../../docs/specs/execution.md#committed-event-stream), [Admission, persistence and recovery](../../docs/specs/execution.md#admission-persistence-and-recovery) (payload versions, Event order), [Journal migration](../../docs/specs/execution.md#journal-migration) (floors, archive), [tools.md Permission modes, rules and hooks](../../docs/specs/tools.md#permission-modes-rules-and-hooks) (where the verdict is recorded), [goals.md Current-format replay and exec](../../docs/specs/goals.md#current-format-replay-and-exec) and [terminal.md](../../docs/specs/terminal.md) (`show` output), [serve.md](../../docs/specs/serve.md)/[acp.md](../../docs/specs/acp.md) (Event kinds exposed on the wire).
- Proposed contract (a): `ToolStarted` v15 carries `verdict: PermissionVerdict` and commits after `PreToolUse` hooks and the permission decision, immediately before dispatch; `ToolPermissionDecided` is removed from the vocabulary. Pre-hooks correlate to the pending intent by digest as today (`HookStarted` carries the intent digest), so journal-first holds for hook processes; the Tool effect still has a committed intent-plus-verdict before it runs; an approval wait that ends in process death leaves no `ToolStarted`, which replays as nothing pending (nothing executed) instead of today's Interrupted intent, and the model re-proposes on resume. A denied or not-dispatched step commits `ToolStarted { verdict: Deny | .. }` then `ToolFinished { not_dispatched }`, unchanged in count. The floor for `ToolStarted` rises to 15 and `ToolPermissionDecided` leaves `EVENT_FLOOR`; any store containing version ≤14 or the removed kind is below the floor and is archived with the notice.
- Proposed contract (b): before committing the folded `ToolStarted`, the Engine calls the reducer's `ToolStarted` validator on the candidate against the current committed view; a rejection becomes a `ProposalRefusalCause` with a bounded reason, never an append attempt. The validator is exported narrowly at the Session boundary (mirroring G5's `validate_request`). Replay still rejects the same forged histories.
- Proposed contract (c): `arany show` on a history that strict replay rejects prints the committed prefix projection up to the rejecting sequence, then a notice `History invalid at sequence N: <typed cause>; shown read-only, not resumable`, then a per-Event lenient listing (kind, sequence, decoded payload if it decodes, otherwise `undecodable`) for the remainder; exit status is nonzero; resume, fork, `exec --session` and compaction keep refusing. JSONL `show` adds `{"notice": ...}` lines with the same facts.
- Scenarios: hook-free Read step commits four Events and replays identically; `PreToolUse` deny commits `HookStarted`, `HookFinished`, `ToolStarted{Deny}`, `ToolFinished{not_dispatched}`; crash during an Ask prompt replays with no pending intent and the next Run re-proposes; a v14 store opens as archived with the notice and a fresh store; a forged `ToolStarted` with a verdict for another digest rejects; the Engine refuses a step the validator would reject with the same cause; `show` on an `InvalidHistory` store prints prefix, notice and lenient tail; serve/ACP clients see no `ToolPermissionDecided` kind in the schema export.
- Evidence owners: `session/reducer/tests.rs` and `session/events/tests.rs` (payload tables, order), `store/migrate/tests.rs` (floor, archive fixture `toolstarted-v14-archived.json`), `crates/arany/tests/engine_run/permissions.rs` and `hooks.rs`, `crates/arany-cli/tests/session_run/tools/replay.rs` and `serve/` fixtures (`fixtures/serve/schema.json`, `basic.jsonl`), `tests/session_run/exec_interrupt.rs` (Ask-wait death), new `show` lenient case beside `rewind.rs`.

## Chosen direction

- Simplest sufficient solution: add one field, delete one Event kind, move one append site; raise one floor and ship the archive fixture; export one validator; one fallback branch in `show`. No new Event kind, no cross-row migration machinery, no second runtime format.
- OS impact: none.
- Interface change: `session` exports `validate_tool_started(&SessionView, &ToolStarted) -> Result<(), ToolRefusal>`; `Event::ToolPermissionDecided` disappears from the public Event enum, the serve schema and ACP mapping. These are deliberate breaking changes under rule 5; there are no external consumers yet ([serve.md](../../docs/specs/serve.md) owns the schema version bump).

## Security and resource model

No trust input changes. The verdict's authority is unchanged (same `PermissionVerdict`, same basis/source provenance), only its container. Lenient `show` renders undecodable payloads as a fixed marker, never raw bytes, and keeps the existing control-character sanitization; it grants nothing (no resume). Archive-below-floor is the existing rule-5 path with its existing notice and bounds.

## Risks and mitigations

- Tooling that greps `ToolPermissionDecided` (presentation, ACP, telemetry) misses a site → the exhaustive `Event` match in `events.rs::kind()` and the serve schema snapshot fail to compile or differ; the slice lists every consumer by `grep -rn ToolPermissionDecided` at open time (presentation rows, `cli/acp/translate.rs`, telemetry span names).
- A hidden consumer relied on the verdict preceding dispatch as a separate row for the agent inspector timeline → the inspector reads the verdict from `ToolStarted` at the same position; pinned in `agent_inspector.rs`.
- Lenient `show` tempts callers into treating invalid histories as usable → nonzero exit, explicit notice, and resume/fork/exec unchanged; pinned.

## Vertical slices

1. **Fold the verdict into `ToolStarted`.** Move the `ToolStarted` append after hooks and permission; add `verdict`; delete `ToolPermissionDecided` and its reducer, validate, presentation, ACP and telemetry arms; `Action::ProviderCall.max_events()` drops by one; raise the floor to 15, add the archived-store fixture and the migration test rows; update serve schema and ACP fixtures. Specs: `execution.md` (stream order, versions, migration), `tools.md` (verdict recorded on `ToolStarted`), `serve.md`/`acp.md` (schema version). ≤600 (if the exhaustive consumer sweep exceeds it, split presentation/ACP/telemetry arms into 1b behind a temporary `_ =>` that 1b removes).
2. **Engine pre-validates through the reducer.** Export `validate_tool_started`; call it in `prepare_step_intent` before the append; map rejection to a typed refusal with reason; delete the duplicated predicates in `check_tool`/`primary_lease_allows` that the validator now owns (keep Engine-only liveness and budget gates). Specs: `execution.md` accepted outcomes (refusal causes), `tools.md` authority section (one validator). ≤500.
3. **Lenient `show`.** Fallback projection in the `show` path (`crates/arany-cli/src/main.rs::show`, `cli/record_formats.rs`), notice line and JSONL line, nonzero exit; replay entry returns the rejecting sequence and cause for the prefix (already typed). Specs: `goals.md` Current-format replay and `exec`, `terminal.md` `show` section. ≤400.

## Exit criteria

- Scripted evidence per slice: four-Event hook-free step, deny path, Ask-wait death, archive fixture, forged verdict rejection, Engine refusal parity with the validator, lenient `show` on an invalid store with nonzero exit; `show` byte-identical for valid stores before and after.
- Contract updates listed per slice; no `NEXT_STEPS` item is replaced by this plan (none exists for it). Delete this folder when slice 3 lands.

## Outcome and scope

One feature: the primary can request a supervised host command whenever the task needs host access, with explicit user authority, without first manufacturing a Guard failure. Commands otherwise default to the Guard. This serves ordinary single-agent work, host inspection and evaluation of team results; children remain isolated.

Owner decision, 2026-10-22, verbatim intent:

> I don't see much sense in blocking the PRIMARY agent 100%. The group of subagents should have this Guard, but the primary must be able to run things unguarded, especially simple things when you don't need a team (or when it's evaluating whether the team's work is worth it). We should rewrite the AGENTS.md rule and update this to how other harnesses do it.

The acceptance case is a request to locate Arany disk usage across the machine. An empty isolated Workspace is not evidence that host files do not exist. The primary should explain the access needed, request a bounded host `du`/`find` invocation and report its actual coverage, permission errors and truncation. This plan does not run that inspection.

The lead is dropping the host-read-access proposal on its unmerged branch; this feature replaces that approach to primary inspection and has no dependency on that branch. Do not add a second host-read grant or filesystem-browser Tool for this use case. `arany-storage` remains a separate feature; neither its plan nor sibling worktrees are edited here. Typed Git/PR workflows retain their own plans and approval constraints.

### Command admission and authority

Reuse the normalized command intent and host supervisor. Ordinary `command` selects the Guard; `command_unguarded` requires a justification. The Engine checks the actual primary actor, permission restrictions, Goal phase, cancellation and budgets before requesting authority. Model fields cannot select actor identity, approval provenance or trust. Host execution is never an automatic fallback from the Guard.

Keep cwd Workspace-relative, resolved beneath the admitted Workspace without following links, as [host preparation](../../crates/arany/src/tools/unguarded.rs) does today. Absolute host targets belong in argv. Every approval/rule binds the Run's Workspace identity and exact relative cwd; there is no user-wide host-rule scope or arbitrary external cwd in this feature. Host admission needs no Guard boot or image preparation. Resolve programs only through admitted absolute PATH entries: reject empty/relative entries and entries or resolved executable targets inside the Workspace, including resolved aliases. Pin the absolute executable path, filesystem identity and digest before approval and revalidate before dispatch. The same absolute-only PATH supplies the cleared environment. Shells must be explicitly pinned; no implicit login/startup loading or translation of Guard paths/variables into host targets.

The approval binds executable, argv, cwd/Workspace, execution class, environment policy and finite limits. Retain the allowlisted environment and empty stdin. Warn that the process runs as the user with reachable files/network, can execute repository configuration, alter Arany's own permissions/Store/journal, disclose private data to the Provider and change files without rewind. Add a highlighted warning when argv lexically names `.env` or `.env.*`, `.ssh`, `.aws`, `.gnupg`, the admitted StateRoot or fixed account root. Apply it to path components and literal embedded paths, including option values; sanitize display. This check neither expands shell syntax nor detects all aliases, derived paths or hidden access: it is a warning, not a security boundary.

Only a human approval or an admitted user-owned rule authorizes host execution. Deny/ask rules, hooks, plan restrictions and cancellation still narrow it. Generic commands remain potentially mutating and are refused in `plan`. A command's success, settings-file write, Tool output, MCP metadata/output, Skill text, child report or ACP client policy is never an approval action. Folder trust alone grants no host authority.

**State-write limit.** Before any rule-matched, non-human dispatch, refuse argv that lexically names the admitted StateRoot or account root, including their descendants, absolute literal occurrences in command strings/option values and relative path tokens normalized against cwd. Use bounded lexical matching without shell evaluation. Apply this refusal to all non-human cached host dispatch as well; there is no fallback to execute anyway. A fresh human request may still approve the displayed command. This catches direct `sed`/`tee`/`cp` targets; it cannot prevent computed paths, aliases or an approved program accessing state internally. Pin live settings and reject detected out-of-band changes until human re-admission through `/permissions`; a direct write supplies no approval or rule-creation receipt. Because the same user can forge both settings and history, this is not reliable attribution of all future state writes. Same-user journal/configuration tamper resistance is explicitly not claimed.

**Post-failure and hooks.** Keep explicit primary post-failure requests through the same host operation, without a failure prerequisite. In S1 remove machine-generated hook-origin exact re-run offers, `child_unguarded` inheritance and Stop/PreCompact continuations whose sole purpose was to offer an unguarded re-run. Keep bounded diagnostic hook feedback and immutable Ignored outcomes. Primary Stop failures no longer re-prompt solely for host escape; PreCompact no longer blocks solely for such an offer. Genuine hook Block/Stop outcomes, their existing eight-continuation cap, cancellation, uncertainty and compaction-stop semantics remain. A primary may independently propose a fresh host command from diagnostic context; its result never replaces a hook verdict. No child/hook output automatically triggers host execution.

### Approval scopes and prefix rules

- **Once:** the exact pending intent only; expiry, decline, dropped reply or cancellation dispatches nothing.
- **For this session:** only the identical command approved by a human earlier in the same live Session epoch: pinned executable path/identity/digest, identical argv, cwd/Workspace and environment policy, with no greater limits. The Engine creates and journals a fresh opaque epoch ID per attached process/Session binding or serve connection/Session binding before use, and pins it in each Run and approval. Session or Goal resume, reload, restart, reconnect and fork start a new epoch; normal subsequent turns may reuse the current one. The reducer validates same-epoch references to earlier human decisions and rejects cross-epoch/resume/fork references. History retains expired decisions without reviving them. Cap at 128 entries, with once still available when full. Revocation is journaled before further reuse. Mode restrictions below can always require a fresh human.
- **Remember prefix:** only an attached terminal approval or `/permissions` may create a rule, through S2's existing private admission, typed editing, atomic replacement and digest machinery. Serve supports once/session only; ACP and exec cannot create rules. Keep `typedPrefixes` closed to typed operations and add a separate closed host record binding executable path/identity/digest, literal token prefix, decision, environment-policy identity, Run Workspace path/device/inode and exact relative cwd. The prefix sequence includes the executable token. Model proposals require at least two tokens; only `/permissions` can explicitly create a one-token prefix, with the broader suffix warning. No rule can override the exclusions below. New rules apply next Run; saving approves the current action once. Never promote a file write or model-proposed rule into an admitted user decision.

**Closed remembrance exclusions.** Arany owns one versioned, table-tested literal set of first-token basenames, applied both to the requested spelling and resolved executable basename:

`env`, `xargs`, `find`, `nice`, `ionice`, `timeout`, `nohup`, `setsid`, `time`, `sudo`, `doas`, `su`, `runuser`, `chroot`, `busybox`, `toybox`, `awk`, `gawk`, `mawk`, `nawk`, `sed`, `sh`, `bash`, `dash`, `zsh`, `ksh`, `mksh`, `fish`, `csh`, `tcsh`, `python`, `python2`, `python3`, `pypy`, `pypy3`, `node`, `nodejs`, `deno`, `bun`, `perl`, `ruby`, `php`, `lua`, `luajit`, `tclsh`, `wish`, `pwsh`, `powershell`, `git`, `gh`, `rm`.

Also refuse any executable matching a declared shell/interpreter pin or the typed Git/gh pin, by resolved path, filesystem identity or digest; this catches declared versioned interpreters and renamed/hardlinked copies. Explicit script/interpreter forms, heredoc/herestring proposals and tokens containing shell control syntax are ineligible. These exclusions apply at rule creation, admission and dispatch, including `/permissions`, not merely to the model's suggestion. Shell/interpreter declarations come from trusted user/runtime admission, never model or repository metadata. Unknown renamed programs can still interpret data or execute other programs: this is a closed conservative policy, not complete executable classification. No wildcard/name heuristic silently expands the set. [Codex's pinned prefix guidance][codex-request] motivates banning broad scripting and `rm`; Arany deliberately also excludes wrappers and Git/gh to avoid remembered access to their broader effects. Once and exact-session approval remain available subject to other restrictions.

Match literal argv tokens without wildcard matching, basename aliasing, wrapper stripping, shell splitting or substitutions. A `du` prefix never authorizes `sh -c 'du ...'`. All eligible suffixes are expressly authorized host behavior, not OS confinement. Ordinary Bash deny/ask rules still narrow; ordinary Bash allows never become host preapprovals. Settings and live terminal modes compose restrictively: remembered host allows apply only in `default`/`dontAsk` and eligible `exec`; `auto` and `acceptEdits` require a fresh human for each host command, ignoring both prefix and session-cache preapproval, never substituting AI review. Explicit ask always needs a fresh human; `plan` refuses.

Share the existing 64 KiB settings and 128-rule ceiling and existing argument/string bounds; reject overflow as a whole. Keep the settings compare-and-replace lock and immutable Run snapshot. Failed save dispatches nothing; unconfirmed replacement is Uncertain and never retried. Rule revocation affects the next admitted Run; cancellation withdraws pending authority now. Replay validates committed provenance and never reads/writes current settings. These checks rely on intact state and do not attest it against an authorized same-user host process.

### Execution, recovery and rewind

Engine owns ordering: committed intent → committed verdict/approval scope → committed dispatch authorization → spawn → committed outcome. Reserve Store/Event tail and Goal action time before spawn. A post-authorization crash without proof that nothing started is Uncertain; recovery never executes the pending command. The reducer rejects a child host intent, missing/wrong-intent verdict, fabricated session/rule provenance, Guard receipt, cache publication or changeset integration attached to a host command.

**Decided 2026-10-22: preserve confirmed-stop classification** (existing [host executor](../../crates/arany/src/tools/unguarded.rs) and [Tools Execution contract](../../docs/specs/tools.md#unguarded-re-run-after-a-guard-failure)). Confirmed teardown after timeout/output overflow remains `Limit(timeout/output_ceiling)`; confirmed cancellation remains `Cancelled`; a known nonzero exit remains `Failed`. Possible partial host effects alone do not convert those observed outcomes to Uncertain. This feature does not broaden confirmed stops into Uncertain. Lost dispatch/outcome acknowledgement, unconfirmed leader/group termination or a separately evidenced unknown effect remains Uncertain and stops continuation without retries. Preserve existing Engine/Goal stop and resume semantics for Limit/Cancelled; a new inspection is a new intent, never an automatic retry of the stopped command. Execution owns outcome/recovery classification; Goals owns pause/resume and incomplete-evidence reporting.

Retain bounded head/tail output, totals, deadlines and process-group kill/reap. A confirmed stop proves neither rollback nor complete inventory; preserve possible-effect/non-rewindable markers and partial output. A group kill cannot contain deliberately detached descendants. The receipts and replay are meaningful only with intact journal state; no tamper-proof audit trail is claimed against a host command running as the user.

Host results carry `host/unguarded` in the model result, terminal, linear output, transcript, `exec` receipt/JSONL, `show`, Goal report, serve/ACP items and telemetry's existing effect counts. Runtime restrictions may explain failure but are not a Guard attestation. Host output is bounded untrusted data; summaries must not turn absent/truncated/inaccessible paths into a complete host inventory.

No host output is a changeset or checkpoint pre-image. Persist a possible non-rewindable effect marker before spawn, settle it from the receipt, and retain unknown markers on interrupted prefixes. Rewind previews and restored conversations retain a visible warning that host/external effects remain. Code rewind may restore eligible tracked changes only, with existing conflict checks; it must not claim to undo the host command. Invalidate prior file-success and worker-verification evidence after a possibly mutating host dispatch; re-read/reverify before integration or claiming completion. Reuse the Workspace writer lease and stale-base validation; no lock claims to serialize arbitrary host paths against other applications.

## Security and resource model

The [security pass](../../agents/security.md#security-pass-triggers) covers changed authorization, host processes, disclosure, durable records and client approval semantics. Assets include host files and credentials, the network, Workspace state, journal integrity and approval records. Model argv/justification, repository programs/configuration, child reports and output are attacker-controlled. Trusted user/process configuration is admitted before repository input; the harness accepts host grants only from the human channel or admitted user-owned rules, subject to the same-user tampering limitation below.

The host process can read or rewrite whatever that OS user can access, including credential files, private permission settings, Store and journal; clearing the environment is not credential or state isolation. Output filtering cannot guarantee secret removal. Journal consistency checks detect malformed history, not a same-user attacker who forges consistent records. No tamper-resistant approval provenance or audit trail is claimed against that process. Existing sensitive-output protections remain, but the prompt must disclose Provider egress. No new credential broker or automatic credential import is introduced. Typed Git authentication remains owned by its existing plan. Host execution is a deliberate exception to filesystem/network/CPU/memory confinement, not a fallback silently chosen when the Guard is unavailable.

Reuse [Tool limits](../../docs/specs/tools.md#limits-and-failure-behavior): 16 KiB serialized non-content arguments, 512-byte justification, finite Goal-pinned command timeout (120 seconds by default), bounded rendered output and the 1 GiB per-stream kill ceiling. Host approval waits reuse the existing immutable intent deadline; they do not charge active execution time. Admit one primary host command at a time per Run and no new work queue. Session approvals and persistent rules have the caps above; Event/Store/context budgets remain independent of aggregate Goal limits. Overflow refuses before dispatch where possible, or stops the process and records the honest outcome after dispatch. Child programs launched by an authorized host process are covered by its warning and supervision; they are not Arany subagents and do not receive agent grants.

Linux and macOS use existing process-group and no-follow identity primitives. Do not assume GNU `find`/`du` flags, a shell location or a service manager. Test host visibility and supervision with isolated synthetic fixture directories on each OS. No real account directories or credentials are required. Native kill/reap, filesystem identity and terminal checks belong in NEXT_STEPS when unavailable during implementation, and do not become support claims from synthetic CI.

## Risks and mitigations

- A broad approval runs hostile repository code or rewrites private Arany state → explicit warning, lexical refusal on non-human state-targeting requests and rejection of detected unadmitted writes; no claim of isolation, reliable same-user attribution or journal tamper resistance.
- Generic host commands bypass the protections of typed Git operations → the proposed Safe AI cage wording exposes this limitation; typed operations retain their own stronger path and approvals.
- A host edit makes a worker result or completion criterion stale → invalidate evidence and use existing conflict/digest checks before publication or completion.
- Approval caching creates invisible authority → exact session fingerprints, visible scopes, bounded lifetimes, revocation and journaled provenance; children receive none.
- Process termination is mistaken for rollback → confirmed stops retain Limit/Cancelled plus possible-effect markers; unknown execution/teardown remains Uncertain, with no retry. Whole-machine inventory reports incomplete coverage.

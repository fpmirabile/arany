# Git writes on macOS

Outline of a plan to offer the typed Git writes on macOS through a confined executor unit and a separate publisher unit. Resolve relative links from this directory.

## Metadata

- Status: `Draft`
- Owner: `fpmirabile`
- Last updated: `2026-10-27`

## Outcome and scope

On macOS the primary can run `git_commit`, `git_branch` creation and `git_switch` exactly as on Linux: Git runs on a neutralized private view in a unit whose Seatbelt profile cannot write the Workspace or `.git`, and only Arany's own code in a second unit publishes the validated result with a receipt. Serves harness priorities 1 (per-effect isolation, journal-first receipts) and 2 (Linux/macOS parity). Push and PR creation stay [human-approved host Git](../../docs/specs/tools.md#human-approved-host-git), unchanged. Linked worktrees, submodules and signing stay unsupported on both platforms.

## Research

Current contract and code (this worktree, `main` at `20b5dd02`):

- **Refusal today.** [Typed Git writes item 1](../../docs/specs/tools.md#typed-git-writes) refuses macOS because Seatbelt cannot further restrict a child of the already sandboxed Guard worker. The code gate is `git_writes_available()` returning `false` off Linux (`crates/arany/src/tools/guard.rs:51`), consumed at `crates/arany/src/tools/config.rs:364`; `spawn_confined_before` returns `ProtectionUnavailable` off Linux (`crates/arany/src/tools/git.rs:1125-1141`).
- **Linux shape.** `write::execute` (`crates/arany/src/tools/git/write.rs:177`) builds the view, runs Git through a Landlock/seccomp-confined child (`Io.writable`, `git.rs:1105-1112`) and then calls `publish` (`write.rs:1194`) in the same process, which holds locks and replaces refs/index/files under the [publication contract](../../docs/specs/tools.md#typed-git-writes) (items 4 and 8). One process both confines Git and publishes because Landlock domains attach per spawned thread.
- **macOS shape.** A unit installs its Seatbelt profile once in the helper (`unit::helper_main`, `crates/arany/src/tools/guard/macos/unit.rs:1249`; `install` dispatch at `macos.rs:433`). Git reads use `install_git` (`macos.rs:628-651`): `GIT_PROFILE` (`macos.rs:210`), exec of the pinned Git, `file-read*` of the Workspace, read/write only of the view under the unit root, no network, coalition emptied at teardown. `unit_root` (`macos.rs:465`) checks the Workspace identity but skips `storage::verify_storage`, so the view has no volume quota ([accepted trade-off](../../docs/specs/tools.md#typed-git-reads), line 722). A profile cannot be changed after install and a child always inherits its parent's sandbox (Apple DTS, [App Sandbox inheritance](https://developer.apple.com/forums/thread/706390): "A process is not allowed to change its sandbox"; a second profile set fails with `SYSCALL_SET_PROFILE`), so one unit cannot both run Git unwritably and publish. This is the premise in [NEXT_STEPS item 5](../../NEXT_STEPS.md#daily-use-first). [Chromium's Seatbelt design](https://raw.githubusercontent.com/chromium/chromium/main/sandbox/mac/seatbelt_sandbox_design.md) is background on deny-by-default profiles only; it does not carry this premise.
- **Existing IPC.** Units already exchange bounded, hashed, chunked frames with the controller (`read_frame`, `crates/arany/src/tools/guard/transfer.rs:700`, capped by `WORKER_DATA_BYTES`; `unit::execute`, `unit.rs:898`). The recovery record and lock-record reporting (`arany-locks-<intent>.json`, [item 8](../../docs/specs/tools.md#typed-git-writes)) already cover a Guard that dies mid-publication.
- **Bounds that carry over.** 4,096 new objects and [32 MiB](../../docs/specs/limits.md#max_snapshot_bytes) objects plus index, 2,048 switched files of at most [1 MiB](../../docs/specs/limits.md#max_file_bytes) and 32 MiB in total, 20 s Git runtime ([limits table](../../docs/specs/tools.md#limits-and-failure-behavior)).
- **Evidence owners.** Linux acceptance rows in the [Typed Git writes table](../../docs/specs/tools.md#typed-git-writes) (`tools::git::write::tests`, `guard_runs/git_writes.rs`); macOS profile text and install tests in `macos.rs` (`tests`, profile table at `macos.rs:1320-1340`); macOS CI lanes `macOS Tests (debug|release)` ([ci.yml](../../.github/workflows/ci.yml)). Hosted CI runs macOS, so synthetic evidence is available; real-device evidence stays in NEXT_STEPS.
- **Peers** (from the [Git writes research](../../docs/research/git-writes-2026-10.md), source-checked 2026-10-21, documentation level only): Claude Code's sandbox protects Git configuration and hooks but permits other Git metadata writes inside one sandbox ([sandboxing](https://code.claude.com/docs/en/sandboxing#protected-paths)); Codex CLI keeps `.git` recursively read-only under `workspace-write`, so Git writes there need different authority ([approvals](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)). Neither confines Git while publishing validated results, and neither is a pinned implementation audit. Arany diverges because journal-first receipts, neutralized configuration and isolated Git are guarantees; the divergence is already recorded in the spec and research. Peer macOS source: Codex `codex-rs/sandboxing/src/seatbelt.rs` (commit `aeb6b22c`) grants `file-write*` per writable root with `file-write-unlink` denials and excludes protected metadata names; its `seatbelt_fcntl_tests.rs` documents fcntls that mutate files through read-only descriptors, bypassing `file-write*` and `file-ioctl` (see the executor model below). The Chromium design page was fetched by the validation and does not document profile immutability.

Research gate result: facts above are code-, spec- or source-cited; the Chromium page no longer carries the premise (Apple DTS does) and the Codex source finding enters the security model.

## Contract and scenarios

- Owning spec: [Typed Git writes](../../docs/specs/tools.md#typed-git-writes) (item 1 availability, items 4 and 10, limits row) and [Typed Git reads](../../docs/specs/tools.md#typed-git-reads) (macOS trade-offs). The final slice rewrites item 1 and item 10 so macOS is supported and the trade-off paragraph names the write quota.
- Successful path: on macOS a human-approved `git_commit` (paths and staged), `git_branch` creation and `git_switch` return the same JSON and `publication` receipt as Linux; closed-store replay never re-executes.
- Rejection and failure: Git cannot create, truncate, link, chmod or rename anything in the Workspace or `.git` (executor profile and absent descriptors); Git cannot mutate Workspace or `.git` contents through a read-only descriptor (the fcntl paths Codex's `seatbelt_fcntl_tests.rs` names bypass `file-write*` and `file-ioctl`), so the executor profile denies them by syscall/fcntl and the macOS row equals the Linux "cannot write, truncate, link, chmod, retime or `ioctl`" row; drift of HEAD, refs, packed-refs or index between snapshot and publish publishes nothing; a held lock fails; an oversized view frame is `Limit`; a publisher that dies after its first effect is Uncertain and reports recorded locks; a missing profile, `file-write*` denial that cannot be attested or an unsupported macOS version leaves writes unavailable (fail closed, catalog omits them).
- Evidence owner: extend the table in the spec with macOS-capable rows (same tests where possible, `cfg` only where Landlock is the subject); native device check recorded in [NEXT_STEPS.md](../../NEXT_STEPS.md).

## Chosen direction

- **Simplest sufficient solution (Ponytail).** Reuse the unit supervisor, the existing Git view builder and the Linux publisher unchanged. Add two Seatbelt profile kinds (executor, publisher) beside `ProfileKind::Git`, run two units for one intent under the lifecycle of step 3a (bounded overlap during transfer, executor torn down before publication), and relay one opaque bounded frame between them. No new crate, trait or daemon.
  1. *Plan half* (executor unit): builds the view, runs Git, reads switch preimages; its profile allows Workspace `file-read*`, view `file-write*`, pinned Git exec and nothing else. The writable surface is exactly the unit's private view directory; the Workspace and `.git` carry `deny file-write*` by omission under `(deny default)`.
  2. *Descriptor closure.* Seatbelt checks at open, not at use, so a writable descriptor opened before the profile is installed would survive it. Before the Git child starts, the executor unit holds no descriptor that can mutate the Workspace or `.git`: lock files, the real `.git` directory handle used for snapshots is opened read-only, and all other inherited descriptors are closed (closed-set check in the unit, with a test that enumerates `/dev/fd`).
  3. *View exchange.* The executor emits one frame whose complete representation is: (a) new loose object files as `xx/yyyy…` name plus stored bytes, at most `MAX_OBJECTS` (4,096) entries (`write.rs:25,857-906`); (b) the new index bytes, with (a)+(b) together at most `MAX_SNAPSHOT_BYTES` (32 MiB), the bound `new_objects` already enforces; (c) for a switch, the replacement blobs, each at most `MAX_FILE_BYTES` and together at most 32 MiB (`read_blobs`, `write.rs:805-855`), plus the path/mode plan (at most 2,048 files); (d) the planned ref, HEAD and lock-holds lists, plus the name of every snapshot ref beside its digest, so ref names are budgeted separately from ref contents: at most `MAX_REF_ENTRIES` names, each bounded only by the admitted filesystem path (`write.rs:336-364` enforces entry count and `REF_BYTES` of content, not name length), budgeted at `MAX_PATH_BYTES` (4,096, `crates/arany/src/validate.rs:45`) per name, with a 32-byte digest per ref instead of content; (e) a SHA-256 digest of each snapshot input (HEAD, `packed-refs`, `shallow`, every loose ref, the index) instead of the snapshot bytes, because the publisher reads the real repository itself and compares digests; (f) the inspected `.git` device and inode (`Repository.identity`), which the publisher compares with its own `.git` handle before taking any lock, as `publish` does at `write.rs:1206-1209`, so an identical-byte replacement directory is refused as drift. Switch preimages are not transferred: the publisher re-reads them with `current_version` under its locks. A commit or branch frame is therefore at most 32 MiB of objects plus index; a switch frame at most 32 MiB of index plus 32 MiB of blobs, since a switch creates no objects. Encoding is binary with a 4-byte length per field and the codec's 4 bytes per 45 KiB chunk plus a 32-byte hash, so expansion is below 0.1%. The frame cap is a new named constant beside the Git write owner, derived as `2 * MAX_SNAPSHOT_BYTES` plus allowances computed from the actual admitted bounds: `MAX_REF_ENTRIES * (MAX_PATH_BYTES + 32)` for ref names and digests (about 16 MiB), 2,048 switch paths of at most `MAX_PATH_BYTES` (about 8 MiB), `MAX_OBJECTS` object names and fixed length prefixes, about 90 MiB in all; no new name-length refusal is introduced; every other use derives from it. It exceeds the shared 48 MiB `WORKER_DATA_BYTES` (`crates/arany/src/session/worker.rs:12`), so `read_frame` and the writer take the cap as a parameter and the worker handover keeps its own. Frame transfer and unit lifetimes are specified in the next step. No currently admissible Linux write may become `Limit`.
  3a. *Unit lifetimes and transfer order.* One Tool intent holds one admission that reserves **both** units up front (two unit envelopes counted against the shared Guard capacity for the whole effect; if both cannot be reserved the call waits or fails `Limit` exactly as one unit does today, so the publisher can never be starved after Git ran). Order: (1) executor and publisher units bootstrap; the publisher installs its profile and then idles holding no descriptor into the Workspace or `.git`; (2) the executor builds the view and runs Git under the shared action deadline (the publisher's time counts against the same deadline); (3) the executor streams the frame in codec chunks to the controller, which forwards each chunk to the publisher with at most one chunk in flight, so this is a bounded **overlap** of two live units (before sending, the controller verifies that no coalition member other than the executor helper itself exists, so no Git process or other descendant is alive; the helper cannot be absent while it streams) rather than controller buffering or disk spooling; the publisher accumulates the frame in memory within its existing 512 MiB envelope, which holds the roughly 90 MiB cap; (4) after the hash and length verify, the controller tears down the executor unit and waits until its coalition is entirely empty (helper included), then sends the publisher `GO`; the publisher takes no lock before `GO`, so no Git or executor unit exists while it publishes; (5) the publisher publishes and returns the receipt; the controller tears it down. The executor profile denies Unix-socket connect and process signalling beyond its own children, so it cannot reach the idle publisher. Cancellation before `GO` tears down both units and publishes nothing; after `GO` the existing publication semantics apply (finish, or Uncertain with recorded locks). A truncated, over-cap or hash-mismatched transfer fails the effect with nothing published. M1a carries tests for each of these plus teardown order asserting two distinct conditions (during transfer only the helper remains in the executor coalition; after executor teardown and before `GO` the coalition is empty) and both units gone after the receipt and capacity release on every exit.
  4. *Publish half* (publisher unit, "Guard worker"): its own profile allows Workspace write only under the admitted Workspace and `.git`, no process exec and no network. It re-validates what `publish` validates today: object-name grammar, entry and byte bounds, ref names, drift of every snapshot digest under the locks, and switch preimages. **It does not verify object contents.** `copy_objects` (`write.rs:1310`) copies the loose-object bytes Git wrote and Linux does the same; verifying would add a zlib inflater (no such dependency today, only `sha2`) and a new hostile-data parser with decompression-bomb bounds. Following Claude Code and Codex CLI, whose reviewed documentation describes no verification of the objects Git writes, macOS keeps the Linux behavior: opaque copy, bounded and name-checked. Residual risk (a compromised Git could write a malformed or misnamed object that a subsequent read rejects, never executes) is recorded as a non-claim in the spec and does not widen beyond Linux.
- **Refactor first.** M0 splits `write::execute` into plan and publish halves joined by the frame codec on Linux with byte-identical observations, so macOS adds only profiles and a relay.
- **Linux/macOS impact.** Linux behavior unchanged (M0 is a pure flow split). macOS gains writes on the same CLT-pinned Git ([availability](../../docs/specs/tools.md#typed-git-reads)). Necessary difference: two units instead of one process with Landlock. macOS native evidence beyond CI: real-device approval journey and a Seatbelt violation check, in NEXT_STEPS.
- **Alternatives.** (a) One unit with publication via the controller: the Engine already publishes primary typed file edits in process, but Git publication needs lock records, packed-refs handling and switch preimage checks that the Linux publisher owns; moving it into the Engine would need that amendment. (b) Executor writes directly to a Workspace-writable profile: rejected, a Git memory-corruption bug on hostile packs would reach `.git`. In-process publication in the Engine is also not available: [AGENTS.md per-effect isolation](../../AGENTS.md#non-negotiable-guarantees) names the in-process exceptions exhaustively and Git publication is not one, so it needs an AGENTS.md amendment, not a spec edit. (c) Host Git: not a fallback ([AGENTS.md](../../AGENTS.md#non-negotiable-guarantees)).

## Security and resource model

[Security pass](../../agents/security.md#security-pass-triggers) triggers: process execution, filesystem writes, untrusted repository content, native sandbox change.

- Trust boundaries: repository content and Git output are hostile; the executor is untrusted code on hostile data; the publisher is Arany code and trusts nothing from the frame. The controller relay is byte-transparent.
- Authorization unchanged: ask like commands in `request`/`auto edits`, review in `auto`, deny in `plan`, typed prefix rules per verb ([policy item 9](../../docs/specs/tools.md#typed-git-writes)). Offered to the primary only.
- View storage: the write executor does not use the unquotaed control root. A new `prepare_git_storage` (slice M0b, shared by reads and writes) creates exactly one fixed-capacity native volume through `prepare_storage_with_sizes` (`storage.rs:95`) sized `SCRATCH_BYTES`, the same envelope as the Linux `/scratch` tmpfs that already holds the view, so Linux-admissible writes fit; the view lives at `<volume>/git-view`, `install_git`'s write variant grants `file-write*` only beneath that volume, and `verify_storage`'s volume checks (`storage.rs:269-286`, no-follow, mode 0700, mount flags) run for it before Git starts. Teardown owner is the unit's existing root teardown that detaches its volumes. M0b gives macOS Git reads the same bounded volume and removes the documented no-quota trade-off. M0b evidence: view exhaustion on a read fails the effect without touching the control root, detach on every exit, bootstrap refusal. M1a2 evidence: Git filling the view gets `ENOSPC` and fails the effect while the control root and Workspace stay unchanged (a test asserts the profile grants no write path outside the volume), volume detach on every exit, and bootstrap refusal when the volume cannot be prepared.
- Bounds: the view frame is at most `2 * MAX_SNAPSHOT_BYTES` plus header allowances (one named constant, derived from its constituents as in the view-exchange step); the relay forwards one chunk at a time and the publisher holds the frame within its unit envelope; the Git view volume and its limit are owned by the View storage bullet above (M0b, reads and writes); 20 s Git runtime shared across both units; both units are reserved together for the effect, as in step 3a; overflow is `Limit` before publication.
- Failure containment: executor failure or timeout publishes nothing; publisher death after the first effect is Uncertain, never retried, locks reported as on Linux; teardown empties each unit's coalition.
- Unsupported required enforcement (no attestable profile, old macOS) fails closed to the current refusal.

## Risks and mitigations

- Inherited writable descriptor defeats the profile → explicit closure plus a native test that tries to write the Workspace through every descriptor visible to the child.
- Frame desynchronization or truncation between units → hashed chunked frames reuse the codec with a parameterized cap; the publisher refuses incomplete frames and over-bound entries. Object contents are not verified (see Chosen direction); this is Linux parity, not a new gap.
- Enforcement digest changes (profile texts feed `enforcement_digest()`, `macos.rs:248-270`, profile loop at 267) → verify that historical macOS receipts replay unchanged; add the migration/fixture only if a stored format actually changes.
- Executor and publisher overlap during transfer doubles peak unit capacity for the effect → both are reserved together up front and measured in M3; no second admission wait.
- Two-unit latency inside the 20 s budget → measure in the latency corpus; if over budget, raise via the limits owner, not by weakening checks.
- Read-only-descriptor mutation through fcntl bypasses `file-write*` → deny by syscall/fcntl in the executor profile, with a native test in M1a.
- Publisher bug on hostile frame data → optionally deny `file-write*` on `.git/config` and `.git/hooks` in the publisher grant (Claude Code's protected paths, Codex's protected metadata names); the publisher never writes them.

## Vertical slices

Estimates count added plus deleted lines; ceiling around 1,500 per slice ([slice delivery](../PLANNING.md#slice-delivery)).

1. **M0: split the Linux Git write flow into plan and publish halves (≈1,100).** Path: `write::execute` → `plan` returning a typed publication plan and `publish` consuming it through the parameterized frame codec and the derived frame cap; observations, receipts and tests byte-identical. Boundary evidence: a switch at the maximum admissible size (32 MiB index plus 32 MiB blobs), a commit at 4,096 objects plus index at the 32 MiB bound, and each one byte or entry over, admissible ref paths and switch paths longer than 1 KiB (up to `MAX_PATH_BYTES`) round-tripping with no new refusal, a replaced `.git` directory with identical bytes refused before any lock (the plan carries and compares the repository identity across the split), with the cap derived from its constituents and checked against them; existing `tools::git::write::tests` unchanged. 3. **M1a: macOS `git_branch` creation, executor and publisher core (≈1,200).** Executor and publisher profile kinds with the enforcement-digest update, descriptor closure (with the `/dev/fd` test), the read-only-descriptor fcntl denial with its native test, controller relay, two-unit reservation, the write view on the M0b volume, `GO` sequencing, cancellation before and after `GO`, truncation/over-cap/hash-mismatch tests, teardown-order assertions, per-verb macOS availability (only branch creation offered; commit and switch keep the existing denial), spec item 1/4 edits including the macOS divergence sentence beside item 4, and replay without re-execution. ## Owner decisions

Recorded as the plan's recommendations (peer-parity first):

1. **Relay topology: controller relay.** The frame must reach the controller for bounds and journaling, reuses `transfer.rs`, and a unit-to-unit socket would need a new authenticated channel. Peers have no equivalent.
2. **Git view volume: shared, in M0b, for reads and writes.** Removes a documented gap at small cost; the write executor needs the volume regardless.
3. **Staging: branch creation, then commit, then switch (M1a/M1a2, M1b, M2).** M1a and M1b ship in the same release train, since daily use is about commit, not branch creation; `git_switch` stays unavailable until M2. Peers expose all Git verbs at once through shell; staging only reduces review size.
4. **Divergence record: yes.** Arany's confined-executor-plus-publisher design, unlike Claude Code's single sandbox with protected paths or Codex's read-only `.git`, stays recorded in the spec as a guarantee-driven divergence; M1a adds the macOS sentence beside item 4.
5. **M1a size: split into M1a and M1a2** instead of a single owner-excepted slice of about 1,900 lines.

## Exit criteria

- Native/CI observations: macOS CI runs the profile tests, the descriptor-closure test and the commit/branch/switch journeys; Linux Git write tests pass unchanged after M0.
- Failure observations: Workspace and `.git` writes by the Git child denied; drift, held lock, oversize frame and publisher death behave as in the Linux rows.
- Unavailable here: real-device macOS approval journey and Seatbelt violation observation move to NEXT_STEPS native checklist.
- Contracts: [tools.md](../../docs/specs/tools.md#typed-git-writes) items 1, 4, 7, 10 and the macOS trade-off are updated in M1a–M2 (item 10 and the trade-off rewrite in M1a2); closeout per the [planning lifecycle](../README.md#lifecycle).

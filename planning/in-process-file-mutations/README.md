# In-process typed file mutations

## Metadata

- Status: `In progress`
- Owner: harness maintainers
- Last updated: 2026-10-25

## Outcome and scope

One capability: the typed File-family mutations (Write, Edit, MultiEdit, Mkdir, Delete, Move) and the primary's `ApplyChangeset` publication run in the Arany process under the admitted cap-std Workspace capability, with the same digest preconditions, fresh-inode replacement and journaled receipt they have today, and no native Guard unit. The Guard remains the only execution site for programs: Command, MCP, Skill scripts and Git. The harness responsibility served is Tool execution ([priority 1](../../AGENTS.md#product-and-implementation-priorities)) at the cost the [per-effect isolation](../../AGENTS.md#non-negotiable-guarantees) guarantee actually requires; the owner approved the guarantee rewording below (decision 4, Option B, 2026-10-25).

Included: the Linux and macOS dispatch change, the receipt and attestation shape for in-process effects, the reducer's site rule, deletion of the Linux file-worker profile and the macOS file profile with its per-mutation disk image, and the AGENTS.md, `tools.md` and overview edits. Excluded: commands (the [command Workspace overlay](../command-workspace-overlay/README.md) plan), worker (editor) private targets (decision 5, undecided), Skill loading (stays in the Guard: YAML parsing of repository-controlled text is exactly the untrusted-input case the Guard exists for).

## Research

- The mutation logic is already pure Rust over cap-std: [`fs::native`](../../crates/arany/src/tools/fs.rs) (line ≈1486) matches Delete/Move, Write, Mkdir, Edit/MultiEdit and `ApplyChangeset` and calls `replace`, `remove_or_move`, `apply_changeset`; [`replace_file`](../../crates/arany/src/tools/fs.rs) (≈1979) writes a `.arany-write-<uuid>` temporary with `create_new` and `FollowSymlinks::No`, `sync_all`, verifies the precondition closure, renames with `RENAME_NOREPLACE` for creation, then syncs the parent directory; a failed parent sync maps to `ToolError::Uncertain`. `open_directory`, `open_file`, `read_regular` and `identity` are the no-follow, no-mount-crossing primitives reads already use in process.
- Today that code runs inside a Guard helper: [`tools/dispatch.rs:15`](../../crates/arany/src/tools/dispatch.rs) `Family::File => fs::native(site.workspace, call, site.config)` is executed by the helper process launched for `Site::Guard` from [`ToolRuntime::execute`](../../crates/arany/src/tools.rs) (≈1445-1515); in-process reads take `Site::InProcess => self.run_read(..)` (≈1652) and attest `Attestation::InProcess { policy_digest, workspace_device, workspace_inode }` ([tools.rs:1741](../../crates/arany/src/tools.rs), [types.rs:1006](../../crates/arany/src/tools/types.rs)). Guard effects attest `Attestation::Guard(GuardReceipt { contract_version, intent_digest, enforcement_digest, limits })` ([types.rs:967](../../crates/arany/src/tools/types.rs)). The facts table sets the site per operation: `read_row` is InProcess for File and Skill reads, `write_row` is Guard ([catalog.rs:22-40](../../crates/arany/src/tools/catalog.rs)).
- The reducer validates the site per observation: an unguarded intent may carry only an Unguarded attestation, a non-approved verdict may carry none, and the lifecycle rules in [`reducer/tool/lifecycle.rs:80-100`](../../crates/arany/src/session/reducer/tool/lifecycle.rs) check attestation presence against disposition; `GuardReceipt::valid_for` binds intent and enforcement digests.
- Native file-worker machinery that exists only for these effects: the Linux "typed file worker" with its non-spawning seccomp layer ([tools.md §Private worker targets](../../docs/specs/tools.md#private-worker-targets-and-handover-transfer) line ≈640; [linux.rs](../../crates/arany/src/tools/guard/linux.rs) `private_file_worker_filter_*`), the macOS file profile with CPU expiry and the per-mutation disk image ([macos.rs](../../crates/arany/src/tools/guard/macos.rs) `native_file_profile_*`, [macos/unit.rs:3451](../../crates/arany/src/tools/guard/macos/unit.rs) calling `fs::native`, `hdiutil` in `storage.rs`/`unit.rs`), and the file-profile enforcement digest ([guard.rs](../../crates/arany/src/tools/guard.rs) `file_profile_digest_excludes_selected_process_runtimes`).
- Checkpoints are captured by the Engine before a mutation from committed before-versions ([step/checkpoint.rs](../../crates/arany/src/engine/run_loop/step/checkpoint.rs) `capture_checkpoint`), independent of the execution site; the Store owns pre-image durability ([overview §7](../../docs/architecture/system-overview.md#7-canonical-persistence)).
- Contract text today: [tools.md macOS section](../../docs/specs/tools.md#macos-enforcement-and-compatibility) line ≈1044 "Native file writes use digest or create preconditions, no-follow handles and a fresh inode plus atomic replacement, never in-place truncation of an aliased inode …", and the pre-GO rule at ≈1046 "Beginning the GO write makes a subsequent missing completion conservatively uncertain"; [overview §2 line 168](../../docs/architecture/system-overview.md#2-runtime-architecture) "List, Read, Search and Glob use the admitted directory capability in process … Mutations, typed Git reads, Skill loading and MCP stay behind the separate Guard."
- The latency corpus has a warm Read row only; "guarded Edit" rows were deferred ([latency.md](../../crates/arany-cli/tests/guard_runs/latency.md), NEXT_STEPS "Visible reliability").
- Peers: Claude Code's Edit is "exact string replacement" done by the CLI process; its sandbox applies to Bash ([tools reference](https://code.claude.com/docs/en/tools-reference), [sandboxing](https://code.claude.com/docs/en/sandboxing)). Codex applies patches in process through the `apply-patch` crate after approval; sandboxing covers shell commands ([codex-rs/apply-patch](https://github.com/openai/codex/tree/main/codex-rs/apply-patch), [approvals](https://learn.chatgpt.com/docs/agent-approvals-security)). OpenCode and Goose write files in process. No peer isolates its own typed writes from itself.

## Contract and scenarios

- Owning contracts: [AGENTS.md per-effect isolation](../../AGENTS.md#non-negotiable-guarantees) (owner-approved rewording, slice 1), [overview §1 item 10, §2, §6, §11](../../docs/architecture/system-overview.md), [tools.md In-process reads](../../docs/specs/tools.md#in-process-file-operations) (becomes "In-process file operations"), [Limits](../../docs/specs/tools.md#limits-and-failure-behavior), [Enforcement failure causes](../../docs/specs/tools.md#enforcement-failure-causes), [macOS](../../docs/specs/tools.md#macos-enforcement-and-compatibility) and [Linux](../../docs/specs/tools.md#linux-enforcement-and-compatibility) enforcement sections, [execution.md Committed Event stream](../../docs/specs/execution.md#committed-event-stream) (attestation per site).
- AGENTS.md sentence, current: "Mutations, processes, Skill scripts and MCP calls run in the Guard under pinned, typed grants and publish only through validated changesets with receipts, except for the primary-only host operations below. Ordinary reads retain the same admitted directory capabilities and bounds, in-process or in the Guard, and never widen disclosure." Approved replacement: "Processes, Skill scripts and MCP calls run in the Guard under pinned, typed grants and publish only through validated changesets with receipts, except for the primary-only host operations below. Typed file reads and mutations run in process under the same admitted directory capabilities and bounds, with digest preconditions and journaled receipts, and never widen disclosure." Every other guarantee sentence is unchanged: journal-first (intent before write, observation after; same Events), honest uncertainty (an in-process rename returns or the process dies; parent-sync failure stays Uncertain), durable Goals (same reservations), safe AI cage (the capability still refuses links, special files, protected names and mount crossing; repository content selects nothing).
- Proposed site contract: File-family mutations and `ApplyChangeset` have `Site::InProcess`; their observation attests `Attestation::InProcess { policy_digest, workspace_device, workspace_inode }` plus a new additive `receipt: Option<FileReceipt { intent_digest, before: Option<[u8;32]>, after: Option<[u8;32]>, executable: bool }>` (omitted for reads, so no payload version bump under the additive rule; the reducer requires it for mutation observations with disposition Succeeded). `GuardReceipt` stays for Guard sites. Preconditions, bounds and error texts are unchanged (`Conflict` on a stale digest or existing target, `Parent directory not found; create it with Mkdir first`, 1 MiB file and 64 KiB content caps).
- Journal-first, uncertainty, crash and cancellation for in-process writes: `ToolStarted` commits before any byte is written; the write runs on `spawn_blocking` with the intent's deadline; cancellation is checked before the temporary file is created and never after the rename begins (a rename is not interruptible; cancellation after it yields a Succeeded observation followed by the Run's Cancelled stop, as a Guard effect does today); a temporary-file write failure records attested `Failed` with the file unchanged; a rename failure after `create_new` records `Failed` (the target is unchanged, the temporary is removed); a parent-directory sync failure after the rename records `Uncertain` and stops the Run; process death between the rename and `ToolFinished` replays as an Interrupted intent, and the next Run's Read or digest precondition observes the actual file state (no re-execution). The in-process path has no pre-GO stage, so the `guard_bootstrap`/preparation enforcement causes never apply to File effects; the reducer rejects them for `Site::InProcess`.
- Scenarios: Write/Edit/MultiEdit/Mkdir/Delete/Move succeed in process on Linux and macOS with receipts and checkpoints identical to today's observable output; stale digest → `Conflict`; symlink target or hard link → rejection before any write; cancellation before the temporary → `Cancelled` with the file unchanged; injected parent-sync failure → `Uncertain` and Run stop; crash after rename → Interrupted intent, file present, resume does not retry; `ApplyChangeset` from a command receipt validates every precondition then publishes; a hostile Workspace path (protected name, `..`, absolute) is refused at decoding as today; replay of a pre-change history with `Attestation::Guard` on a File effect still validates (historical fact) while a new `Guard` attestation on a File effect is rejected (site rule).
- Evidence owners: `crates/arany/src/tools/fs.rs` tests (precondition, replacement and error tables), `crates/arany/src/tools/tests.rs` (site dispatch, attestation shape), `session/reducer/tests.rs` (site rule, receipt requirement), `crates/arany-cli/tests/session_run/tools.rs` and `tools/replay.rs` (end-to-end mutations, close/reopen, `show`), `crates/arany-cli/tests/guard_runs/rewind.rs` (checkpoints unchanged), `crates/arany/tests/engine_run/workspace_security.rs` (hostile paths, links), `guard_runs/latency.rs` (new Edit row), `tests/session_run/tools_macos.rs` (macOS parity through the same corpus).

## Chosen direction

- Simplest sufficient solution: add `ToolRuntime::run_file` beside `run_read` that calls the existing `fs::native` on `spawn_blocking` under the admitted Workspace capability and builds the in-process observation with the receipt; flip `write_row` to `Site::InProcess`; delete the helper-side `Family::File` arm, the Linux file-worker filter, the macOS file profile and the per-mutation disk-image lifecycle. No new trait, executor or configuration.
- Linux/macOS impact: both platforms use the same code path (cap-std and `rustix::fs::renameat_with` are already used on both). Linux loses one seccomp profile; macOS loses the file Seatbelt profile and the file-effect disk images (the command profile and its volumes stay). Native evidence: the existing Linux and macOS `session_run` tool corpora already cover each mutation; no new support claim.
- Interface change: `Site` assignment for six operations and `Attestation` gains an optional receipt; `tools::dispatch` helper loses one arm. Not a module boundary change (Tools still owns admission, dispatch and attestation).

## Security and resource model

Trust boundary: the effect is Arany's compiled code writing bytes the Engine validated, under a capability that denies symlink following, mount crossing and traversal; this is the same boundary reads use today. What is lost is a kernel boundary around Arany's own write code; what is kept is every precondition, bound, receipt and the journal. Attacker-controlled inputs (model-chosen path and content, repository symlinks and hard links, concurrent host edits) are handled by the unchanged `open_file`/`replace_file` checks and the digest precondition; the macOS "not a transaction against concurrent host edits" caveat stays. Bounds: 1 MiB file, 64 KiB content, 400 KiB arguments, one write at a time per Run (effects stay serial), deadline from the intent. The security pass for a changed enforcement site ([triggers](../../agents/security.md#security-pass-triggers)) runs in slice 1 with `workspace_security.rs` as evidence.

## Risks and mitigations

- A write blocks the Engine thread → `spawn_blocking` with the intent deadline; timeout records `Limit` only before the rename begins, `Uncertain` after.
- Removing the macOS disk-image path breaks command volumes that share code → slice 2 deletes only the file-profile branches; `storage.rs` command-volume functions stay and their tests pin them.
- Presentation or telemetry labels say "Guard" for file effects → the site label table ([tools.rs:1866](../../crates/arany/src/tools.rs)) and the ACP/serve projections are updated in slice 1; snapshot fixtures pin the new labels.

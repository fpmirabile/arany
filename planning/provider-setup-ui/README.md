## Outcome and scope

Configure the Providers used by an Arany team without hand-editing JSON: manage accounts and exact custom routes, explicitly check a route, assign primary/child/review/compaction chains, and maintain named roster presets from the attached CLI. This is one capability: user-owned Provider configuration through the terminal, feeding the existing admission and execution path.

The planned setup surface covers ChatGPT-plan access, Anthropic API access and Kimi/GLM custom profiles. Existing OpenAI API access remains available. This does not establish vendor compatibility, expand credential slots, add an adapter, change fallback predicates, or add per-agent recovery. A ChatGPT account, the saved Anthropic account and environment-backed custom routes can coexist within the current account model.

### Interaction and ownership

Use inline selectors in **Fullscreen and Classic**, plus **linear/screen-reader** equivalents, with the existing input-admission barrier, bounded fields and safe rendering. In every slice, long dialogs use the [paging-dialog contract](../../docs/specs/terminal.md#terminal-continuity-and-provisional-text): Up/Down and PageUp/PageDown traverse both directions, acceptance remains blocked until the final page has been shown, and resize restarts required review. Fullscreen preserves the disjoint history area and reading anchor; Classic grows only to content/screen height; linear mode pages the same complete intent. Lists open without inference or unrelated credential access. Opening a secret-bearing native account for inspection requires explicit selected-item access; a metadata row must not silently read every credential. Enter confirms the focused operation, Escape returns without publishing the current draft, and removal/cost confirmation starts on Cancel. Reuse secret input's masking/no-echo behavior. Preserve the conversation draft, caret and history position on return; an already committed account/save/check is not undone by closing the manager.

Keep draft editing and terminal geometry in `arany-cli`. The routing/roster owners validate and serialize their own records; `provider::custom` owns custom declarations, destination admission and probes. Expose small concrete typed edit operations, not raw paths/JSON or a new trait. StateRoot owns checked locking, replacement and receipts. Add a **new typed Provider-record write path beside `Record::replace_upgraded`** in [state.rs](../../crates/arany/src/store/state.rs), with a closed target set of ProviderProfiles, ProviderRouting and ProviderRoster and typed Replace/Remove edits. It takes an expected snapshot and validated bounded record, locks/rechecks and calls the existing private publish/remove primitives directly. Keep the three ordinary `Record::replace/remove` permissions read-only; do not flip their writable flags. `replace_upgraded` remains the migration bypass for user-authored records; UI writers never call it or pretend to migrate. Existing writable-record behavior need not change. Account storage and OAuth remain in `accounts/`; secrets never cross into presentation or Engine configuration. Engine receives the existing immutable admitted Provider bundle and owns Run/Goal accounting and route pinning.

Confirmed UI mutations use the attached Session’s existing `events` stream (materialize the Session before the first confirmed effect, without creating a Run or reading Workspace content). Add closed `ProviderSetupEditStarted`/`ProviderSetupEditFinished` v1 Session Events: operation ID, target kind/account identity, expected/non-secret resulting digest and known/unknown disposition, never record bodies or secrets. The Session reducer allows one pending idle edit, rejects mismatched results and blocks continuation after uncertainty; read-only replay never republishes. These new kinds need registry/current-format fixtures, not the prerequisite’s standalone check table. Pre-confirmation cancellation still creates no Session.

Order each save as bounded draft validation → normalized intent and expected record snapshot → private-root/authority admission → committed intent → locked re-read/validation → publication → committed result → visible success. A busy lock or changed snapshot refuses without overwriting the other editor. Hold publication locks only for local bounded work, never while waiting for user input, network or OS dialogs. Retain the credential owner's stronger lock lifetime around OS-store writes. Cancellation after dispatch must settle or report unknown, not pretend that the old record is still authoritative.

For diagnostics, call the prerequisite’s typed check interface and render its acknowledged `CheckView`. Its CheckId stream owns probe intent, results, evidence publication and recovery; the manager supplies only the explicit selection and cost consent, never a Session/Run requirement or a chat draft.

For an environment-backed custom route, listing shows `Credential: ARANY_PROVIDER_NAME — not checked`; listing/editing does not read the variable. After an explicit Check admits the exact destination, the checker reads only that named variable. Unset produces `Credential: ARANY_PROVIDER_NAME — not set` with guidance to export it in the launching shell and restart Arany; empty/invalid bytes produce `unavailable or invalid`, never an echoed value. The saved declaration remains editable and unverified. A destination refusal wins before credential inspection; a present variable alone is never “verified.” Re-check uses the same destination-first ordering.

Linux and macOS share these decisions and existing adapters. No new platform API, executable or dependency is proposed. Native Secret Service/Keychain, ACL, terminal and accessibility claims still require their existing native evidence owners.

## Security and resource model

The [security pass](../../agents/security.md#security-pass-triggers) is triggered by private-state writes, credential operations, user-controlled rendering and an interactive paid-check entry point. Assets are credentials, destination/evidence integrity, route records and pinned Run provenance. Authority comes only from the user's explicit local control action, bound to its normalized operation, expected snapshot and admitted directory/account identity. Provider responses, terminal labels and custom form values are untrusted data. No model or child receives management authority; existing Tool grants remain unchanged.

Use the existing private-directory capability and native enforcement for each effect, including Guard enforcement for new mutations and the selected-item credential helper for OS-store operations; no broad filesystem grant or Workspace Tool invocation may implement setup. Failure to attest required enforcement refuses the operation. Secret fields and token responses never enter events, drawing, scrollback, diagnostics or telemetry. Store only non-secret intent identifiers/digests and bounded outcomes. Check requests contain only fixed synthetic data, never the chat draft, history, instructions or Workspace content. Destination admission precedes selected-key lookup; consent and admission still precede any real Run disclosure.

| Bound | Enforcement / overflow |
|---|---|
| Editing | One open draft and one effect/check in flight per terminal; one record published per Save. A second operation refuses busy; no background retry queue. Draft serialization must fit its record before publication. |
| Records and names | Existing limits: role routing 16 KiB; custom/roster records 64 KiB each; custom profiles ≤32; roster profiles ≤32, presets ≤16. Reuse current parsers' name, URL, effort, depth and node bounds; reject whole invalid edits. |
| Routes and manifest | ≤3 routes per chain; ≤8 eligible/expanded roster profiles and ≤24 expanded slots; full manifest ≤16 KiB. Display paging may not hide an unreviewed destination from confirmation. |
| Checks | Existing custom bound: ≤15 calls, 180 seconds aggregate, no retries, 24-hour evidence; reuse request/reply/DNS limits and per-effort schema challenges. Cost confirmation is explicit; cancellation or journal failure prevents further dispatch. |
| Credentials and admission | Reuse eight-ChatGPT-account and one-native-slot limits, five-second routine helper and two-minute selected-item authorization bounds; roster admission remains sequential within 120 seconds. No enumeration of the OS password store or unrelated StateRoots. |
| Journal/storage | Existing Event and store ceilings apply to control/check facts; reserve space before dispatch. Full storage refuses new work. Replay validates outcomes without republishing configuration, recontacting Providers or re-running credential effects. |

Atomicity is per record, not across credentials, conformance evidence, Session defaults and routing. Cross-record work is separate acknowledged actions. Before changing/removing a custom declaration, durably invalidate its evidence; failure then leaves it unchecked, not falsely authorized. An uncertain record publication never triggers a compensating overwrite. Show repair guidance and require a fresh inspected state. Pinned submissions remain immutable; the next submission re-admits everything.

## Risks and mitigations

- **Scope grows into an account vault or general settings system:** retain current account cardinality, records, command responsibilities and concrete owners (D1, D2, D6).
- **A polished “Check” button hides a durability bypass:** S1 waits for both prerequisite slices and consumes their tested CLI/UI interface (D8).
- **Stored and usable look identical:** distinguish saved declaration, credential availability, exact check status and next-Run admission; show why a candidate is unavailable (D3, D4).
- **Multi-record edits look transactional:** save one record at a time, reject dangling local references and report completed versus unknown actions explicitly (D6, D8).
- **Vendor branding overstates support or billing:** use exact route/account labels and existing Kimi/GLM qualifications; never infer entitlement from key bytes (D2, D3, D7).

## Exit criteria

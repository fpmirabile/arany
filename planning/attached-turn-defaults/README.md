# Attached-turn Goal defaults

## Metadata

- Status: `Draft`
- Owner: Fernando Mirabile
- Last updated: `2026-10-22`

## Outcome and scope

New attached Goals get defaults appropriate for user-supervised interactive work, while saved limits, durable accounting and explicit recovery remain binding. This delivers the budget half of [Daily use first item 5](../../NEXT_STEPS.md#daily-use-first) (`NEXT_STEPS.md:22`).

The other half is the independent [large draft attachments](../large-draft-attachments/README.md) feature: either capability can ship without the other. Two plans follow [PLANNING.md:8](../PLANNING.md), rather than making a budget change depend on a composer redesign. This plan does not change the default budget of library callers or unsaved `exec`/`serve` clients.

## Contract and scenarios

- Owning spec and proposed change: [Goals](../../docs/specs/goals.md#lifecycle-budgets-and-recovery) distinguishes attached initial defaults from other clients. [Terminal settings](../../docs/specs/terminal.md#interactive-commands-and-completion) describes their selection, saved-value precedence and recovery. Proposed attached values are `max_provider_calls: None`, `max_tokens: None`, `max_active_ms: None`, `max_runs: 16`. They apply to new attached Goals, including explicit `/goal` creation and continuation; never to an existing Goal on resume.
- Success: a fresh attached session completes a scripted turn requiring more than 64 calls and another requiring more than 30 active minutes; every dispatch is charged and replay shows the same usage. `/settings` shows the effective defaults before submission. A saved finite budget still stops the next inadmissible action with the committed exhaustion receipt.
- Rejection/recovery: an unsafe settings record fails admission; malformed/unsupported settings retain the current conservative fallback and visible recovery, never obtain unlimited execution because parsing failed. Cancellation and crash preserve Interrupted/Uncertain facts. Resume preserves all old limits and charges; `/goal continue` explicitly creates and links a new budget. Headless clients without saved settings retain 64 calls/30 minutes/16 Runs/unlimited tokens.
- Evidence owners: [Goal corpus](../../crates/arany/tests/engine_run/goals.rs), [stop projection](../../crates/arany/src/session/stop.rs), [settings corpus](../../crates/arany-cli/src/cli/attached/controls.rs), [slash journeys](../../crates/arany-cli/tests/session_run/slash_completion.rs), [active terminal](../../crates/arany-cli/tests/session_run/active_terminal.rs), [exec adapter](../../crates/arany-cli/src/cli/exec.rs) and [serve conformance](../../crates/arany-cli/src/cli/serve). Native/live daily-use evidence belongs in [NEXT_STEPS](../../NEXT_STEPS.md), not a synthetic frequency claim.

## Chosen direction

- Simplest sufficient solution after Ponytail: reuse the supported nullable Goal dimensions. Change only the selection of an absent attached preference, rather than increasing arbitrary finite maxima or adding another scheduler/budget type. Keep `GoalBudget::default()` and finite validation unchanged. Preserve every valid saved budget, even one equal to the old defaults: the record does not prove whether its owner deliberately chose those numbers.
- Keep absence distinguishable from a valid saved value and an invalid record in the private settings loader. Attached absence selects the new values; `execution_limits` used by noninteractive clients keeps its existing default. Invalid attached records keep the old finite fallback. `/settings` explicitly saving unlimited values continues to affect the shared execution preferences, including `exec`/`serve`; show that scope in settings help. No versioned record shape changes or migrations are needed.
- Linux/macOS impact: identical policy and serialization on both. No new OS API, process, capability or dependency. Existing terminal and private-State adapters retain their native evidence requirements; this plan claims no new native support.
- Ownership: CLI selects the client default and converts private JSON into `GoalBudget`; Engine validates/pins it, GoalLedger reserves/settles usage, and the reducer verifies history ([system-overview.md:39–65](../../docs/architecture/system-overview.md#2-runtime-architecture)). The seam remains in-process. No preference type crosses into Engine policy. Journal acknowledgment still precedes dispatch, cancellation never refunds calls, and a lost acknowledgment never authorizes a retry.
- Alternative: a larger finite budget needs a new ceiling and a workload rationale. Choose it only if the owner requires a finite interactive cap and supplies the intended spend/time boundary; peer behavior and the available repo evidence do not establish a defensible percentile-derived number.

## Security and resource model

This triggers the security pass for changed execution/session policy and a newly default-unlimited LLM cost dimension ([agents/security.md:32–47](../../agents/security.md#security-pass-triggers)).

Assets are paid usage, private Session data, journal capacity and Workspace effects. The authority source is user-owned settings or the compiled attached policy; repository/model text cannot select a budget. The immutable normalized budget is committed in `GoalStarted` before any Provider call. Existing Policy, per-effect grants, Guard attestation and descendant authority remain unchanged; more allowed calls confer no additional file, process or network capability.

Calls, tokens and active time have no aggregate Goal ceiling under the proposed default; **there is no dollar-spend guarantee**. Runs remain capped at 16, Session lineage at 10,000 Events, and all request/response, storage, action-time, process and Tool bounds remain finite under [execution limits](../../docs/specs/execution.md#persistence-bounds) and [Goals](../../docs/specs/goals.md#lifecycle-budgets-and-recovery). Exhaustion of any remaining resource stops dependent work with durable disposition and reserved terminal headroom. Unknown effects stop continuation without automatic retry. Startup still admits private State and policy before Workspace input. No new sensitive data, retention policy or diagnostics payload is introduced.

Verification must cover absent versus corrupt versus valid settings, all saved finite dimensions, repeated calls across roles, crash/pause charges, no dispatch after exhaustion, and replay with zero Provider/effect calls. Security review records these non-claims and evidence in the implementation PR.

## Risks and mitigations

- Higher default paid usage → explicit unlimited display, existing cancellation/pause and selectable finite settings; owner approval of this policy is a Plan gate.
- Shared preference readers accidentally widen headless defaults → adapter-level tests for absent, finite and explicitly unlimited records through attached, `exec` and `serve`.
- Existing users retain the older ceiling → deliberate preservation, with `/settings` guidance; never guess intent from a value equal to an old default.
- Unknown exhaustion frequency → state it honestly. Optional owner measurement uses a declared sample of ordinary attached Goals and reports counts by exhausted dimension, calls and active time from canonical receipts, including interrupted/unknown cases separately. It is neither a prerequisite for synthetic delivery nor permission to export private prompts.

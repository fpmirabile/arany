# Attached TUI as a client of the channel Server

## Metadata

- Status: `Ready` (implementation gated as listed under Gates)
- Owner: harness maintainers
- Last updated: 2026-10-25

## Outcome and scope

One capability: the attached terminal drives Runs through the same channel Server that `serve --stdio` and ACP use, over an in-process channel pair, so that submission, committed Event delivery, approvals, steering, cancellation and settlement have one driver; `exec` follows on the same loop. Every terminal behavior stays byte-identical: Fullscreen and Classic rendering, linear output, keyboard access, secret echo, pickers, rewind, `/compact`, `/settings`, `/model`, setup, storage report, accessibility paths and the budget-refusal feedback. The harness responsibility served is the Engine/client boundary ([overview §2](../../docs/architecture/system-overview.md#2-runtime-architecture): "Its stdio adapter, ACP translator and in-process conformance adapter use the same loop"); the attached terminal is the one surface that still bypasses it.

Included: a provisional-display notification so the terminal keeps its streaming previews and Guard capacity hints through the Server; the attached Run driver and `exec` on the Server loop; deletion of the two bypassed driver paths. Excluded: Session-level operations that are not Run driving (rename, defaults, compaction, fork, setup, catalogs, storage) keep their direct Engine calls unless a serve method already exists; a daemon or second process (the [overview §14](../../docs/architecture/system-overview.md#14-explicitly-deferred) trigger "Second Client or detached execution" is unchanged).

## Contract and scenarios

- Owning contracts: [serve.md](../../docs/specs/serve.md) (new opt-in notification, in-process transport statement), [terminal.md](../../docs/specs/terminal.md) (unchanged behavior; evidence owners re-pointed), [goals.md Budget refusal feedback](../../docs/specs/goals.md#lifecycle-budgets-and-recovery) and [Current-format replay and exec](../../docs/specs/goals.md#current-format-replay-and-exec), [execution.md Committed Event stream](../../docs/specs/execution.md#committed-event-stream), [overview §2, §8](../../docs/architecture/system-overview.md).
- Proposed serve contract: a client that declares `capabilities.provisionalDisplay: true` at `initialize` receives `turn/display` notifications `{threadId, turnId, update}` carrying the bounded `DisplayUpdate` (preview text, commentary, Guard capacity hint) exactly as `RunHints` publishes them, coalesced by the Server's existing outbound follower and dropped, never queued, when the client lags; they are display-only, carry no authority, are never journaled and never reach replay or Provider context. The in-process transport is a documented transport beside stdio: the same `ClientMessage`/outbound channel pair with no framing.
- Attached driver contract: unchanged observable behavior. Submission goes through `turn/start` (text and image parts as today's `Message` input), committed facts arrive as serve notifications and are reduced into the terminal's local `SessionView` as the tap is today, approvals arrive as server requests rendered by the same `lines`, steering is `turn/steer`, cancellation `turn/interrupt`, settlement reloads the strict view through `receipt/get`; budget-refusal feedback uses `presentation::budget_refusal_feedback` once. Session operations outside a Run keep direct Engine calls.
- `exec` contract: unchanged receipts, exit codes, JSONL lines and signals ([terminal.md deterministic channels](../../docs/specs/terminal.md#entry-modes-and-channels)); driven through the same in-process client with provisional display disabled; its looser `budget_stop_goal` predicate is kept as a documented `exec` difference through one helper (B13's outcome), not a second driver.
- Scenarios: an attached Run with streaming preview, a Guard capacity wait, one approval and one steering note renders identically in Fullscreen, Classic and linear modes before and after (PTY/tmux snapshot corpora byte-identical); `Ctrl-C` cancels through `turn/interrupt` with the same notices; a lagging terminal drops previews but never loses committed rows; a Server fault while a Run is active surfaces as the existing fatal terminal boundary without inventing an outcome; `exec` JSONL is byte-identical; resume/fork/rewind unchanged; ACP and stdio serve unaffected (their fixtures unchanged).
- Evidence owners: `crates/arany-cli/tests/session_run/active_terminal*.rs`, `chat_mouse.rs`, `rewind.rs`, `exec_interrupt.rs`, `performance/`, `serve/` fixtures (`basic.jsonl`, `schema.json`), `tests/serve/in_process.rs`, `cli/attached/run/tests.rs` (after E8d–E8h), `cli/serve/tests.rs`.

## Chosen direction

- Simplest sufficient solution: reuse `serve_transport` with an in-process channel pair (the ACP and conformance pattern), add one opt-in notification for provisional display, and replace `drive_run`/`drive_loop`/`apply_tapped` with a client that maps serve notifications and server requests onto the existing presentation reducers and approval UI. No new protocol, process or trait; the Server grows one notification and one capability flag.
- OS impact: none.
- Interface change: `serve` gains `turn/display` and `capabilities.provisionalDisplay`; `cli/attached/run.rs` loses its direct `Engine::submit`/tap loop; `cli/exec.rs` loses its own submit/subscribe loop. The library is untouched. This is a binary-internal boundary change: the Server becomes the single owner of Run driving, which answers the [PLANNING.md](../PLANNING.md) seam questions as follows: ownership of in-flight submission state moves to `serve/server.rs` (already owns it for stdio); ordering is the Server's existing per-connection order; errors are the serve `Fault` model mapped to the terminal's typed classifications; cancellation is `turn/interrupt`; performance is bounded by the existing inbound/outbound capacities with the preview drop rule; the seam is in-process with two adapters today (stdio, ACP) and three after.

## Security and resource model

No trust boundary changes: the in-process client runs with the same authority as the Server it talks to; approvals keep their human channel through the terminal; the provisional notification carries display-only data already sanitized by the hints owner. Bounds: inbound/outbound channel capacities unchanged; previews coalesce and drop under backpressure (never block Journal appends, per the existing Server rule). No new persistent state.

## Risks and mitigations

- Latency of previews through an extra channel hop → the hop is an in-process `mpsc`; the latency corpus's terminal row (`history_latency`) is the gate, with the existing CI measurement step.
- Terminal-only approval affordances (remember rules, session approvals, unguarded warnings) not expressible through `{accept|decline|cancel}` → slice 1 extends the server request reply with the existing `ToolApprovals` decision vocabulary (already typed in the library) before the terminal switches; stdio clients keep the three-value subset.
- `run_configured` grows further → slice 1 splits the Server's submission task from its connection loop first (code-health finding 8), keeping each under the split signal.

# Guard toolchain defaults for daily development

## Metadata

- Status: `Ready`; owner decisions D1–D4 accepted; implementation has not started
- Owner: harness maintainers; priority: daily use, macOS first
- Last updated: 2026-10-26
- Delivery: **G1'a → G1'b**, then optional **G2'** after overlay S2b; one PR per slice ID

## Outcome and scope

Make the existing runtime-profile feature usable through ordinary folder trust on Linux and macOS. The owner observed the failure on **macOS**. Default proposals select existing installed toolchains and package caches; a user-owned per-Workspace numeric range can constrain the proposed version. Build commands receive a controller-detected positive Cargo jobs count on both platforms and can retain a validated private build cache after a confirmed timeout. Keep the ten-minute command ceiling, actual test counts and named test-IPC ignores.

The fix reuses existing discovery, `RuntimeGrant`, the shared chooser, native Apple profiles, optional read-only host caches and the two existing native backends. There is no intermediate policy compiler, sandbox DSL, new trust mode, package installer, manager discovery, repository hint parser or host fallback. The simplest sufficient solution after Ponytail is to change defaults at their current owner and repair the existing Build environment/cache path. Linux users receive the same defaults in G1'a; macOS repository acceptance is in G1'b, independently of overlay delivery.

[Command Workspace overlay](../command-workspace-overlay/README.md) owns Workspace visibility, Linux overlay/capture, private build-cache storage and CPU quota. This plan owns system/toolchain/package-cache selection and the command environment, including Cargo jobs. Local test IPC remains in [NEXT_STEPS](../../NEXT_STEPS.md#daily-use-first); network fetch access remains in the [network plan](../network-proxy/README.md). D5 is an overlay decision and is not changed here.

## Contract and scenarios

[Tools](../../docs/specs/tools.md) owns folder trust/runtime selection, command environment, cache publication and native enforcement. [Terminal](../../docs/specs/terminal.md#interactive-commands-and-completion) owns chooser and `/settings`; [Goals](../../docs/specs/goals.md#lifecycle-budgets-and-recovery) owns admitted settings/budgets; [Execution](../../docs/specs/execution.md#committed-event-stream) owns verdict/receipt ordering and replay. No current behavior changes in this planning PR. Each implementing slice replaces existing spec sentences/rows, including the affected Goal/Terminal settings text; Tools must not grow in lines or bytes.

1. **Consent on both OSes:** newest numeric installed runtime inside the user's range, or newest overall without a range, is proposed with exact paths and related caches. macOS Rust also proposes CLT and newest physical SDK. Read only is focused; explicit Trust admits the displayed identities once. Multiple versions remain selectable. New discovery does not alter a remembered grant outside consent.
2. **Range failure and migration:** a range with no installed match proposes no runtime of that kind and no dependent cache/Apple bundle, and explains which bounds excluded candidates without running code. Invalid/reversed/duplicate ranges refuse saving and keep the previous record. Migrating old trust adds no range and grants nothing new; saved exact pins remain intact. A new installation inside an existing range is not automatically trusted.
3. **Build jobs:** the controller snapshots available cores once at admission, pins the positive effective jobs value/digest and sets `CARGO_BUILD_JOBS` on both OSes. `/settings` can lower it within 1–cores. Changing settings during an active Run cannot change its jobs. Host sysctl remains denied inside the Guard; no model-supplied `-j` workaround is needed. Linux CPU quota is still owned by overlay S3.
4. **Confirmed Build timeout:** positive descendant cleanup permits one bounded capture/validation/publication of a private cache candidate; disposition remains `Limit` with cause `timeout`, no Workspace changeset publishes and the Run does not retry itself. A later separately requested command can reuse that cache. Cancellation, nonzero exit, default-class timeout, resource/output limits, missing post-GO outcome or uncertain cleanup retain the prior cache; no eligible partial cache is fabricated from a failure to observe completion.
5. **Repository proof:** extend the existing macOS owner to execute `cargo test --locked --offline -p arany --lib` in this repository's current copied Workspace using admitted Build settings, complete host registry data and the existing shim/CLT/SDK. Record actual passes/failures/ignored counts. If a cold run times out, record it honestly and prove a later explicit warm command makes progress; synthetic compilation or a timeout alone is not completed-test evidence. IPC-dependent ignores remain; unrestricted full-suite IPC is not delivered here.

## Chosen direction

### D1: use the existing shared chooser and profiles

Reuse `RuntimeKind`, `RuntimeManager`, `RuntimeGrant`, `Candidate`, `discover`, `discover_apple_runtimes`, `validate_selection`, `verify_host`/`verify_at`, `apple_compiler_executables` and cache destination helpers in [`toolchains.rs`](../../crates/arany/src/tools/toolchains.rs). Add a small private `default_profile_selection` there, called through existing `WorkspacePermissions::runtime_profile_choices`; keep `prepare_profile_selection`, `remember_profiles`/`selected_grants`, the attached `choose`/`toggle_profile`/`parse_linear_selection` flow, and native adapters. Selection proposals are UI data until explicit human Trust saves exact `runtime_grants`. Preserve explicit `--tools` precedence, individual deselection and read-only startup on discovery failure.

Adapters remain cfg-selected consumers of the same grants. The shared facts already have owners: `guard.rs::runtime_path` for PATH, `payload` for environment, `cache_exclusions` for archive exclusions, `toolchains.rs` for cache destinations and the Apple executable list. Do not move native enforcement operations into a new layer. Optional G2' only derives repeated system-root literals from `guard.rs::runtime_roots()` and places Linux root/loader-alias constants beside that existing owner. It must preserve exact read/map/metadata permissions: never turn `/bin` or `/usr/bin` listing/traversal into a subtree read, or widen a file-only profile to a spawning profile.

### D4: a private per-Workspace numeric range

Store **at most one inclusive From/Through range per Rust, Node or Python kind** in the existing private Workspace trust entry, keyed by its already pinned Workspace path/device/inode. Apple SDK has no range: always propose the newest admitted numeric physical SDK when the Rust bundle is proposed. AppleCompiler and cache kinds have no artificial version range. Use two numeric endpoint fields in the existing chooser (for example Rust From `1.88.0`, Through `1.98.9`); empty means no range. No general semver expression language, separate config file or repository parser.

Parse three checked nonnegative numeric components per endpoint, using the existing version-label byte ceiling. Bounds are inclusive and must be ordered. Compare candidate major/minor/patch numerically, ignoring the existing manager/host suffix only for numeric rank; Node's existing `v` prefix and two-component SDK versions use their known layouts (SDK missing patch compares as zero). Equal numeric versions use the existing deterministic label/path/token tie order. Candidate labels still describe manager directory names, not a verified binary version. Overflow/unrankable metadata is not an automatically proposed compiler. Keep display ordering separate from numeric max selection; e.g. 1.10.0 must outrank 1.9.0.

In initial consent or when the human opens `/permissions`, propose the newest admitted installed candidate inside that user range. With no range, propose newest installed overall. With an installed set but no in-range candidate, propose nothing for that kind and explain it; never fall back outside the range. Bundle only caches associated with an actually proposed runtime; Rust on macOS also requires the existing CLT compiler and newest SDK. A user can explicitly choose a different installed version in the chooser, but a bounded kind must stay inside its edited range before Trust; changing the range and exact selection is one explicit human save.

The range is a **proposal filter, not a future grant**. Saved roots remain exact immutable admission inputs until renewed human consent. A normal remembered startup only revalidates saved pins and does not discover/switch versions. Cancelling/Read only saves neither ranges nor proposed roots. Existing explicit narrower selections stay authoritative until the human accepts the newly displayed proposal. Model text, repository files, hooks and Tool output have no range-edit or trust-record mutation capability through Arany.

**Reject repository hint prefill**, including display-prefilling From/Through from Cargo `rust-version` or a rust-toolchain channel. This keeps the Tools sentence “discovery never executes a candidate or reads manager or project configuration” literally true, avoids a TOML/rustup resolver and removes a path by which an untrusted value could arrive prechecked at consent. Pure informational display after an explicit read would require another designed flow and is unnecessary for this owner decision; it is not part of this plan. A user may type their chosen broad range. This is an explicit Arany divergence from peers' environment/version-manager behavior, required by safe AI cage/pinned-grant authority, not a claim that peers ignore repository pins.

New domain data is limited to a validated numeric version/range in `toolchains.rs` and a bounded `runtime_ranges` map in the existing private trust entry. Ship its **version-2 → version-3 record migration and fixture** via the [existing record migration owner](../../crates/arany/src/store/migrate/record.rs); preserve all old exact grants and initialize an empty map. Reuse the 128-entry/64-KiB trust limits and reject excess/unsafe records without rewriting them. This owner refinement requires a stored-format change; the earlier “no schema change” conclusion no longer applies. There is still one current format at runtime and no extra trust store.

### D2: controller-owned Build jobs

Snapshot the controller's available positive logical core count once at native admission, outside the sandbox. Resolve the existing `/settings` preference (automatic means cores; a lower positive value is allowed) against that snapshot and pin it for the Run. Reject an unavailable/invalid core count for Build rather than obtain a different count in the payload or execute a host probe; unrelated file/read operations remain available. Validate `/settings` within 1–cores; on a later admission with fewer cores the effective value is narrowed to that snapshot without widening any other resource limit or rewriting the saved preference.

Keep the resolved jobs in the existing ToolRuntime/Guard Task settings path and append the actual value to the current `bind_runtime_grants` **`build-jobs=`** field; `payload` sets that exact pinned value for every Build command on **both Linux and macOS**; default-class commands receive no jobs override. Bind this value even when no Rust profile is selected, rather than taking the old empty-grants early return with an unbound environment value. Retain `CARGO_NET_OFFLINE`, the Rust marker and macOS Secure Transport/SDK/helper settings. Update `/settings` through the current bounded preferences owner with its migration/fixture; no second settings file or Event payload field is needed for a value already committed through the runtime digest. Strict replay never rereads current cores. This is Cargo compilation concurrency, not test-thread configuration or Linux aggregate CPU quota. The overlay plan keeps `cpu.max` and its separate CPU control/measurement; it no longer owns Cargo jobs.

### D3: validated cache after a confirmed Build timeout

Extend the existing success eligibility narrowly: a **primary guarded Build Command** with an attested `Limit` / `timeout` may collect and publish its private build cache **after positive descendant termination and cleanup**, under current cache quotas, transfer/capture deadlines, identity lease, no-follow/archive validation and Store atomic publication. Keep `MAX_COMMAND_TIMEOUT_MS = 600_000`; reserve only the existing bounded capture/cleanup/publication tail inside the action/Goal allowance. Do not extend execution past the command deadline or retry it. If that tail has no headroom, keep the prior cache and report the cache result honestly.

Use one narrow eligibility predicate for candidate production, host publication and observation validation. The change must reach Linux `send_cache_candidate`, macOS `unit.rs` capture eligibility, shared `publish_cache_candidate` and `ToolObservation::valid`/reducer evidence; changing only the publisher cannot work. Preserve all current success cases. No timeout exception for workers, MCP, preparation failures, cancellation, resource/output limits or Uncertain outcomes. A candidate that fails schema/type/path/size/identity checks does not replace the prior cache. Receipt disposition/cause stay `Limit(timeout)` even when `cache_update` is `published`; a cache-publication uncertainty stops continuation under the existing rule. Workspace changesets remain empty on timeout.

Security reasoning: this is **Cargo's own incremental state, not Workspace content**. A partial target directory is Cargo's normal crash state; a build process could already populate arbitrary cache bytes on a successful invocation, so timeout eligibility supplies no new read/write authority or path. Do not claim structural archive validation proves compiler artifacts trustworthy. Validate every entry and bound before Store publication, and keep state/credentials excluded. The accepted change deliberately allows timeout-produced incremental artifacts to influence a later guarded build; no agent can use them as permission or Workspace publication evidence.

### T5: keep the existing registry destinations

**Read-only registry binds mount beneath the cache view at the existing relative destinations; with a directory-backed cache those mountpoints are created in the private cache directory, never in the Workspace; archive exclusions retire with S2b.** `RuntimeGrant::mounted_path` remains the destination owner. Overlay S2a creates/validates the mountpoint directories in its bounded private cache and retains read-only nested binds; macOS keeps its existing volume links and archive exclusions. G1' changes no mount layout and adds no cache implementation.

## Security and resource model

**Named security pass: profile defaults, user-owned version ranges and timeout build-cache retention.** Assets: exact runtime/package data, Workspace source, private cache, StateRoot/account/credentials and journal. Trust boundaries: human chooser → admitted user-owned trust/settings → existing pinned grant/digest → native Guard → validated cache publication/unchanged Workspace publisher. Attacker inputs include manager labels, aliases/mounts, packages, build scripts, repository/model text and output. Only explicit human consent saves ranges and displayed root identities. A version range supplies no automatic authority to a later installation.

Retain existing no-follow identity/overlap checks, root/signature admission, bounded discovery, read-only runtime/cache grants, cleared environment, native sandbox/Ready/GO, descendant cleanup and replay. No general home/root/Developer/registry-parent mount; Cargo/npm/pip config and credential siblings stay absent. Default host-registry proposals widen disclosure to selected package names/sources/embedded URLs only after the existing exact-path warning and human Trust. Host caches remain data; their content is never loaded automatically into a Provider request. Unknown execution/cache outcomes remain Uncertain and stop continuation.

Bounds remain with their current owners: 64 candidates, 128 scanned manager entries, 11 selected runtime/cache roots, trust-record 128 entries/64 KiB, native Task/catalogue limits, Tool output/storage/process/memory/Goal limits. Add only three possible range entries per Workspace; endpoints reuse the current version-label byte bound and reject overflow/invalid ordering. Available controller cores bound jobs; it raises no process/memory/time/cache quota. Trust/settings format additions ship their migrations/fixtures; cache timeout changes observation validation semantics without changing its payload shape. Do not add a universal runtime-access value or a second native enforcement path.

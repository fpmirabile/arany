# Guard toolchain defaults for daily development

## Metadata

- Status: `Ready`; D1–D3 accepted, D4' defers ranges; implementation has not started
- Owner: harness maintainers; priority: daily use, macOS first
- Last updated: 2026-10-26
- Delivery: **G1'a → G1'b**, then optional **G1'c** (triggered user version range) and optional **G2'** after overlay S2b; one PR per slice ID

## Outcome and scope

Make the existing runtime-profile feature usable through ordinary folder trust on Linux and macOS. The owner observed the failure on **macOS**. Without an exact remembered pin, default proposals select the newest numeric installed toolchain per kind and its existing package caches. The exact pin saved by `remember_profiles` is the authoritative per-project choice; a user version range is deferred to optional G1'c. Build commands receive a controller-detected positive Cargo jobs count on both platforms and can retain a validated private build cache after a confirmed timeout. Keep the ten-minute command ceiling, actual test counts and named test-IPC ignores.

The fix reuses existing discovery, `RuntimeGrant`, the shared chooser, native Apple profiles, optional read-only host caches and the two existing native backends. There is no intermediate policy compiler, sandbox DSL, new trust mode, package installer, manager discovery, repository hint parser or host fallback. The simplest sufficient solution after Ponytail is to change defaults at their current owner and repair the existing Build environment/cache path. Linux users receive the same defaults in G1'a; macOS repository acceptance is in G1'b, independently of overlay delivery.

[Command Workspace overlay](../command-workspace-overlay/README.md) owns Workspace visibility, Linux overlay/capture, private build-cache storage and CPU quota. This plan owns system/toolchain/package-cache selection and the command environment, including Cargo jobs. Local test IPC remains in [NEXT_STEPS](../../NEXT_STEPS.md#daily-use-first); network fetch access remains in the [network plan](../network-proxy/README.md). D5 is an overlay decision and is not changed here.

## Contract and scenarios

[Tools](../../docs/specs/tools.md) owns folder trust/runtime selection, command environment, cache publication and native enforcement. [Terminal](../../docs/specs/terminal.md#interactive-commands-and-completion) owns chooser and `/settings`; [Goals](../../docs/specs/goals.md#lifecycle-budgets-and-recovery) owns admitted settings/budgets; [Execution](../../docs/specs/execution.md#committed-event-stream) owns typed intent/receipt ordering, stored defaults and replay. No implemented behavior changes in this planning PR. Each implementing slice replaces existing spec sentences/rows, including affected Goal/Terminal/Execution settings text; Tools must not grow in lines or bytes.

1. **Consent on both OSes:** with no exact remembered pin for a runtime kind, propose its newest numeric installed candidate and related caches. macOS Rust also proposes existing CLT and newest physical SDK. A saved exact pin wins, including during `/permissions`; stale pins remain marked/blocked until the human explicitly replaces/removes them, never refreshed into another version. Read only is focused, all paths/warnings remain visible, and only explicit Trust saves the selected identities. Manual selection in the existing chooser remains the project-specific choice. G1'a keeps trust record v2 unchanged.
2. **Optional range:** execute G1'c only after **a re-consent proposed a version the human changed by hand**. Inclusive per-Workspace/per-runtime From/Through bounds, empty-match guidance and v2→v3 RecordStep/fixture are described below. This optional slice does not gate the default/Build fix or Linux overlay work.
3. **Build jobs:** controller detection resolves a positive count at Goal resource admission. Preferences → admitted Goal settings/ledger → `intent.limits.build_jobs` → journal → identical receipt limits is the one path. The reducer requires positive jobs no greater than `max_processes`. `/settings` can lower the preference within 1–cores; admitted/resumed Goals do not reread host cores or change the pinned count. Selected-Rust Build commands on both OSes use that field for environment/digest; other runtimes do not receive a jobs environment override. CPU quota and test-thread counts remain separate.
4. **Confirmed Build timeout:** positive cleanup permits bounded capture/validation/publication of an eligible private cache. `cache_update: published` requires `Succeeded`, or `Limit/timeout` with Guard attestation, primary Build `Command` and an empty Workspace changeset. Preserve all other existing process/host/worker/attestation checks. Controller-synthesized Limits without a helper report keep `not_applicable`; no absent candidate upgrades them to `uncertain`. Unknown dispatched execution/publication still follows the existing Uncertain rule. The command is never retried automatically.
5. **Repository proof:** extend the existing macOS owner to execute `cargo test --locked --offline -p arany --lib` in this repository's copied Workspace using admitted Build settings, complete host registry data and existing shim/CLT/SDK. Record actual passed/failed/ignored counts. If a cold run times out, report it and prove progress on a later explicitly requested warm command; a timeout or synthetic compilation is not completed-test evidence. Local test IPC stays excluded.

## Chosen direction

### D1: use the existing shared chooser and profiles

Reuse `RuntimeKind`, `RuntimeManager`, `RuntimeGrant`, `Candidate`, `discover`, `discover_apple_runtimes`, `validate_selection`, `verify_host`/`verify_at`, `apple_compiler_executables` and cache destination helpers in [`toolchains.rs`](../../crates/arany/src/tools/toolchains.rs). Add a small private `default_profile_selection` there, called through existing `WorkspacePermissions::runtime_profile_choices`; keep `prepare_profile_selection`, `remember_profiles`/`selected_grants`, the attached `choose`/`toggle_profile`/`parse_linear_selection` flow, and native adapters. Selection proposals are UI data until explicit human Trust saves exact `runtime_grants`. Preserve explicit `--tools` precedence, individual deselection and read-only startup on discovery failure.

Adapters remain cfg-selected consumers of the same grants. The shared facts already have owners: `guard.rs::runtime_path` for PATH, `payload` for environment, `cache_exclusions` for archive exclusions, `toolchains.rs` for cache destinations and the Apple executable list. Do not move native enforcement operations into a new layer. Optional G2' only derives repeated system-root literals from `guard.rs::runtime_roots()` and places Linux root/loader-alias constants beside that existing owner. It must preserve exact read/map/metadata permissions: never turn `/bin` or `/usr/bin` listing/traversal into a subtree read, or widen a file-only profile to a spawning profile.

### D4': newest numeric defaults and exact-pin precedence in G1'a

G1'a ships **newest numeric installed version per kind when that kind has no exact remembered pin**. Existing `remember_profiles`/`Entry.runtime_grants` pins are the authoritative per-Workspace choice; ordinary startup revalidates them without discovery, and opening `/permissions` does not silently replace them. Newest is a proposal, never authority for an unreviewed installation. The human can choose a different exact version in the existing chooser; no From/Through fields, range map or trust-record version change ships here. Keep Read only initially focused, narrower deselection, explicit `--tools` precedence, current disclosure warnings and exact token/identity pinning.

Refactor the **existing `is_versioned_installation` scan** into the numeric-key owner, returning checked `(u64,u64,u64)` components; boolean installation admission derives from that same result. Reuse its Node `v` handling, label bound, leading-zero rejection and manager/host suffix validation. Do not copy the parsing walk into `default_profile_selection`. Keep numeric proposal ranking separate from lexicographic display order: 1.10.0 outranks 1.9.0, while labels/paths/tokens keep the current deterministic equal-key order. Handle overflow explicitly rather than wrapping or silently misordering. Likewise expose the numeric key from existing `valid_apple_sdk_version` validation (missing patch compares as zero); propose newest physical SDK for an unpinned SDK kind in the Rust bundle, preserving any saved exact SDK pin. AppleCompiler/cache kinds have no version selector. Candidate labels remain manager metadata, not verified binary versions.

The private `default_profile_selection` in `toolchains.rs` consumes already discovered candidates plus saved pins. `WorkspacePermissions::runtime_profile_choices` exposes those proposal checks through its existing options; only `remember_profiles` admits the final exact selection. Bundle caches only for an actually selected/proposed runtime; on macOS Rust includes the existing CLT compiler and one newest SDK. A missing prerequisite is shown without an install/fetch/alias/parent-root fallback. Preserve stale pinned roots as stale until explicit human action.

### G1'c: optional private per-Workspace range

**Trigger: a re-consent proposed a version the human changed by hand.** Until that is observed, this is a deferred design, not a requirement or format change for G1'a/G1'b. Keep the existing exact pin authoritative; the range only filters a new proposal when no exact choice is retained or the human explicitly requests a replacement.

If triggered, store **at most one inclusive From/Through range per Rust, Node or Python kind** in the existing private Workspace trust entry, keyed by pinned Workspace path/device/inode. Apple SDK remains newest without a range; AppleCompiler/cache kinds have none. Add two numeric endpoint fields to the existing attached chooser and a corresponding bounded linear-mode edit syntax (for example From `1.88.0`, Through `1.98.9`); clearing both removes the range. No general semver language, separate config file, manager discovery or second trust store.

Use G1'a's numeric parser/key, not another parser. Endpoints are checked numeric triples within the existing label byte bound, with ordered inclusive limits. Propose newest eligible installed candidate inside the range, newest overall without a range, and **nothing for that kind** when no installed candidate matches, with a clear explanation and no outside-range fallback. Show exact selected roots/cache disclosure before Trust; the human can edit/clear the range and exact choice in one save. A cancelled/Read only choice saves neither. A range never grants a later installation automatically or replaces a saved pin on prompt-free startup.

Add the bounded `runtime_ranges` map through the existing [RecordFormat/RecordStep owner](../../crates/arany/src/store/migrate/record.rs): **v2→v3**, current 3/floor 2, a RecordStep adding an empty map and a fixture preserving every old exact grant. Retain the 128-entry/64-KiB trust ceiling and at most three range entries; duplicate, reversed, overflowed or excessive input refuses saving without changing the prior record. One current format at runtime; no compatibility reader.

**Repository prefill remains rejected**, including Cargo `rust-version`, rust-toolchain channels and `.nvmrc`. Discovery never executes candidates or reads manager/project configuration; neither repository nor model text edits the private range or selects trust. This narrower authority model intentionally differs from peers' ordinary environment/version-manager activation. Only human chooser input and the user-owned record affect proposals, and only reviewed exact grants affect execution.

### D2/N2/N5: Build jobs follow the existing resource path

Snapshot the controller's available positive logical core count once at **Goal resource admission**, outside the sandbox. Resolve the `/settings` preference (automatic means cores; an explicit positive value can lower it) against that snapshot and the admitted Build process ceiling. The effective count is no greater than cores or `max_processes`; it raises no other resource bound. Validate `/settings` within 1–cores and show the effective narrowing if the process limit is lower. An unavailable/invalid count refuses Build admission without a payload/host probe; unrelated file/read operations remain available. Settings changes and resumed Runs do not recalculate an already admitted Goal's jobs; a new Goal takes a new snapshot.

Carry the resolved jobs as **`build_jobs` in the existing `intent.limits`** beside `memory_bytes` and `max_processes`, set from the Goal's admitted resource settings at [`engine/run_loop/step/intent.rs`](../../crates/arany/src/engine/run_loop/step/intent.rs). Validate it through the reducer as positive and at most `max_processes`, bind it to the admitted Goal's settings, and echo it unchanged in `GuardReceipt.limits`. Preferences → Goal resource settings/ledger → intent → journal → receipt is one typed path. The digest **binds** that field; it does not carry the value or replace journaled state. Strict replay explains the recorded value without reading current cores or settings.

The journaled limit exists for every Build command; **`payload` and the current `build-jobs=` digest field apply it only inside the existing selected-Rust branch**. Default-class commands and other selected runtimes receive no Cargo jobs environment override. Pass that same intent value into Task digest validation and `payload`; do not keep a second independently resolved jobs count in ToolRuntime. Retain selected-Rust offline mode/marker, macOS Secure Transport/SDK/helper and all resource limits. The Rust branch scope is deliberate; Linux's existing `/usr` bind can still expose distro Cargo, so do not justify it by claiming Cargo is universally absent without a profile.

The jobs `/settings` field belongs to the current preferences record: **UI preferences v6→v7 RecordStep and fixture**, not a new file. Goal resource settings and `ToolLimits` are also persisted: use [Execution's existing additive-default rule](../../docs/specs/execution.md#admission-persistence-and-recovery) with the historical effective jobs value **1**, omitted at that default, so old Event bytes, intent digests and receipt equality remain intact. New Goal admission records its resolved count; replay of an old Goal retains one rather than interpreting a missing field as current host cores. Pin these old-byte/default and non-default round-trip cases at the existing Event/migration/reducer owners. No legacy reader or digest-only side channel. This is compilation concurrency, not libtest threads or Linux CPU quota; overlay S3 owns its separate CPU control/measurement.

### D3/N4: validated cache after a confirmed Build timeout

Extend success eligibility narrowly: a **primary guarded Build Command** with an attested `Limit` / `timeout` may collect and publish its private build cache **after positive descendant termination and cleanup**, under existing quotas, transfer/capture deadlines, identity lease, archive validation and Store atomic publication. Keep `MAX_COMMAND_TIMEOUT_MS = 600_000`; the existing Linux unit lifetime already includes bounded cache-transfer tails beyond execution. Stay within the admitted action/Goal allowance; never extend command execution or retry it. If publication has no reserved headroom, keep the prior cache and report the cache result honestly.

The change must reach Linux `send_cache_candidate` (and its cfg-Linux call site), macOS `unit.rs` candidate capture and shared `publish_cache_candidate`.

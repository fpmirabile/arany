## Outcome and scope

One feature: a user-selected Rust environment can compile and execute Cargo tests inside the Guard with reusable private build artifacts and a bounded multicore Build profile. The acceptance workload is this repository's exact `cargo test -p arany --lib`, with honest exit status, resource observations, cache receipts and closed replay.

**Research found a blocker to claiming that workload passes:** ordinary library tests open TCP and named Unix sockets, which the current offline Guard denies. Toolchain/cache access and CPU allocation cannot resolve that incompatibility. This plan delivers the Cargo execution environment and measures the exact workload; it must not close item 6 as fully successful on a failed or filtered run. A requirement for a green full suite needs a separately approved local-test capability or test-boundary change before this plan can promise it. That second capability is not silently folded into the Build profile.

Reuse existing folder trust, exact runtime grants, cache transactions, command execution, settings and native adapters. Include selected-runtime environment defaults, explicit Build parallelism, admission/pinning, failure presentation and verification. Do not add a package installer, arbitrary cache-root chooser, new executor, daemon, crate or Cargo-specific authority parser.

[Item 8](../../NEXT_STEPS.md#daily-use-first) retains general all-core command defaults and opt-in external network/domain-proxy work. Here, only the explicitly requested Build class gains bounded parallelism; ordinary commands remain unchanged and egress remains denied. Local test IPC is distinct from domain-allowed outbound access: a proxy does not make a socket-creating test safe or functional. [Item 7](../../NEXT_STEPS.md#daily-use-first) retains snapshot/ignore/changeset enlargement. If the real workload hits those limits, record that dependency rather than enlarging them here.

### macOS path

macOS uses Seatbelt plus an owned launchd job/coalition and separate quota-backed project, scratch and cache volumes. It needs explicit, distinct selections for the physical CLT compiler root and a versioned SDK in addition to Rust and Cargo caches. Cargo receives `CURL_SSL_BACKEND=Secure-Transport` only with Rust, `SDKROOT` only with the selected SDK, and the existing exact-byte page-size compatibility library. Host CPU/sysctl discovery stays denied; the current contract recommends a positive Cargo jobs value. Shell strings are not rewritten into physical Workspace paths. See [tools.md:712](../../docs/specs/tools.md#macos-enforcement-and-compatibility) and [guard.rs:2074](../../crates/arany/src/tools/guard.rs).

The existing explicit native Rust gate builds and runs a standard-library-only fixture with `--jobs 1`; it does not prove this repository or registry-backed tests work: [tools_macos.rs:364](../../crates/arany-cli/tests/session_run/tools_macos.rs), [tools_macos.rs:1284](../../crates/arany-cli/tests/session_run/tools_macos.rs). Reuse this evidence owner. Unsupported or unverified enforcement must refuse; put unavailable native measurements in [NEXT_STEPS](../../NEXT_STEPS.md#beta-2-and-broader-release), without claiming macOS support from Linux or compilation alone.

### What belongs in folder trust, and what is durable

Folder trust owns the exact external Rust directory and each independent host-cache disclosure, plus macOS compiler/SDK selections. Its private record binds Workspace absolute path/device/inode and runtime kind/manager/version/path/device/inode; selections are token-based, not display positions. It does not infer trust from `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/config`, Skills, model text or a successful prior build. Discovery executes no candidates. [workspace.rs:128](../../crates/arany/src/tools/workspace.rs), [workspace.rs:381](../../crates/arany/src/tools/workspace.rs), [toolchains.rs:163](../../crates/arany/src/tools/toolchains.rs).

Resource maxima belong in existing user settings, then the durable Goal pin. A Goal's Build request narrows those values; it does not grant toolchains, caches, network or new executables. Keep the existing trust-record format unless a real additional selection requires a change.

Today runtime grants are serialized into Config and hashed into the Tool policy receipt, then bound into process enforcement. `RunStarted.tool_policy` pins policy; `ToolStarted` carries the normalized intent, limits and resource identity; permission decisions and native attestation gate dispatch. Directory pins are rechecked before use. This is directory identity pinning, not a recursive immutable hash of every toolchain/cache byte; same-user modification is not a claimed defense. [config.rs:262](../../crates/arany/src/tools/config.rs), [guard.rs:580](../../crates/arany/src/tools/guard.rs), [tools.rs:1030](../../crates/arany/src/tools.rs), [tools.md:17](../../docs/specs/tools.md#authority-and-effect-admission).

## Chosen direction

Ponytail choice: extend the existing selected-runtime environment and Build resource path. Preserve Engine policy, Store cache ownership and native Guard enforcement; no new module boundary or dependency is justified. Rust policy uses closed typed values and checked narrowing, not shell parsing or a generic environment map. CLI exposes choices; it does not construct platform policy.

1. For a Build command with a selected Rust runtime, provide `CARGO_NET_OFFLINE=true` and an explicit positive `CARGO_BUILD_JOBS` derived from the admitted Build parallelism. These are compatibility defaults, not security controls. Keep private Cargo home/target construction, real selected binaries, read-only external caches and existing compiler/SDK handling. A command may override a Cargo preference but cannot override the Guard. Do not expose rustup proxy/config parents or add automatic downloading. Preserve the actual compiler/version in measurement evidence.
2. Proposed user setting: Build parallelism default **4**, accepted range **1–16**, resolved downward against available controller CPU capacity and pinned to a positive concrete value. This finite initial policy needs owner acceptance; four is a conservative starting point, not a measured optimum. Linux enforces the resolved value as aggregate `cpu.max` quota, and attests the same value instead of the two hard-coded class constants. Default stays 25%. macOS uses the same Cargo jobs value while retaining its explicitly supervised CPU semantics; do not present that hint as an aggregate CPU cap. If the owner requires a hard multicore quota on macOS, refuse that requested capability until an enforcing adapter exists.
3. Bind the effective parallelism and platform semantics into Goal/intent/receipt validation and the enforcement digest. Resolve capacity before the immutable intent; never recompute a larger value after approval. CPU hotplug or a reduced parent quota may reduce performance, never silently enlarge authority. Thread/process/memory/wall/storage bounds still apply independently. Children receive at most the parent's effective value and retain their existing tool/lease restrictions.
4. Keep the existing cache transaction and failed-command retention rule. A separate successful `cargo test -p arany --lib --no-run` may seed compilation artifacts for measurement; its receipt is compilation evidence only. Never publish artifacts from a failed test merely to improve warm results.

Any new persisted field ships the registered migration step and fixture with its slice: private preferences, Goal settings and journal intent/receipt data as applicable. Translate old CPU semantics conservatively (existing Build means one-core Linux quota); do not retroactively grant four cores to old Goals or replay. Keep one current runtime format and preserve archive-floor behavior. The exact version numbers are assigned against the integration base, not guessed in this draft.

## Security and resource model

The security pass **is triggered** by changed filesystem/process environment, capability/resource settings, durable fields and cross-session cache use. Follow [agents/security.md:47](../../agents/security.md#security-pass-triggers).

- **Assets and boundaries:** host code/toolchains, dependency sources and private package names, Cargo credentials/config, Workspace files, private journals/cache archives, CPU/memory/storage and user processes. Boundaries are consent → private trust/settings → Engine intent/journal → native Guard → validated Store/cache or Workspace publication.
- **Attacker inputs:** repository instructions/manifests/configuration, build scripts/proc macros/tests, symlinks/mount replacements, model argv, cached executables and subprocess output. None selects trust. Selected cache content can contain private metadata or embedded credential URLs and can be emitted by the payload; consent must retain that disclosure warning. Cache isolation is not cache-content trust or reproducible-build attestation.
- **Authority and startup:** consent remains before account/session setup; metadata discovery is bounded and never executes candidate programs. Use the existing owner-only record and no-follow directory identities. No raw parent home mounts, credential helpers, inherited secrets, host terminal or StateRoot access. Normalized argv/cwd, exact runtime identities, effective resource values, deadline/use count and digest are fixed before the permission decision and GO.
- **Five guarantees:** journal-first ordering and reducer validation remain mandatory; unknown effects stop as Uncertain without retry; every effect stays in the Guard and only receipt-backed changesets publish; Goal budgets/pause/cancellation/recovery survive exits; repository/model/cache text supplies no authority and children/hooks/reviews only narrow. Strict replay performs no discovery, approvals, cache publication or process execution. The existing human-only escape hatch is not this feature's acceptance path.
- **Bounds:** retain every current bound above except the explicitly approved Build CPU value. No larger memory/cache/descriptor/output/snapshot cap is presumed. Parallelism remains finite even across the bounded native-unit pool. Overflow refuses or kills under the existing typed outcome; queues remain bounded FIFO, cache contention stays nonblocking busy and no automatic build retry is added.
- **Enforcement/non-claims:** Linux must attest quota, memory/swap/tasks, runtime mounts and descendant cleanup; macOS must attest Seatbelt, runtime selections, owned coalition, supervised thresholds and volume cleanup. Neither Cargo jobs nor a successful compiler exit proves isolation. No defense against privileged host modification, malicious same-user toolchain mutation, confidentiality of explicitly emitted cache data, arbitrary native tests or network-enabled builds is claimed.

## Risks and mitigations

- Full suite requires denied IPC → owner resolves the separate capability/test-boundary dependency; preserve the exact failing command and test counts. Do not broaden the offline profile or silently skip tests.
- More compiler jobs exceed 4 GiB, tmpfs memory or 64 descriptors → measure cold/seeded/warm cases and report the first limiting resource; keep limits enforced. A necessary limit/storage redesign reopens the plan rather than hiding a wider change in CPU tuning.
- Dependency inputs are incomplete or mutate on the host → exact read-only grants, identity checks and honest offline failure. User preparation is separate and does not authorize Arany to install or write host caches.
- Larger repository snapshots or test-generated source changes hit item 7 → retain refusal and identify that independent dependency. Private target artifacts do not bypass Workspace publication limits.
- macOS jobs/library discovery differs from Linux → explicit jobs, existing SDK/page-size support and native fixture evidence; unresolved libtest CPU discovery is a measured compatibility gap, not a sysctl allow rule.

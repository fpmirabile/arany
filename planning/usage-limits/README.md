## Outcome and scope

One capability: inspect the rate-limit facts actually reported by the selected Provider route, separately from Arany's token accounting. Move ChatGPT-plan inference from `https://api.openai.com/v1/responses` to `https://chatgpt.com/backend-api/codex/responses`, matching Codex CLI and Pi under OWNER DECISION D2 (2026-10-27). Carry that backend's account-window observations through committed attempts and the reduced view into `/usage`, then extend the same passive path to native API keys and admitted custom routes. This serves the harness's usage transparency responsibility; observations never control execution or grant authority.

The two [Terminal follow-ups](../../NEXT_STEPS.md#terminal-follow-ups) are one reporting feature. The backend switch includes request shape, account/session headers, bounded SSE, errors/limits, selected-account renewal and admission fingerprints for Runs, children, compaction and explicit checks. It does not add `/wham/usage`, `/api/codex/usage`, polling, WebSockets, imported harness tokens, a paid diagnostic probe, API-key fallback, quota estimates or automatic wait/resume. Existing `/status` plan summaries and `/usage` token totals retain their meanings. A backend-compatible credential is required: under OWNER DECISION D4 (2026-10-28) a fresh Arany sign-in uses the peers' public Codex OAuth client profile ([authentication profile](#authentication-profile-auth-gate)). Existing SIWC grants are never redirected to the backend or converted to that profile; they become disconnected and require a fresh verified sign-in.

The owner decisions below extend the scoped [freeze](../../NEXT_STEPS.md#frozen-areas) exception to the `UL0a`–`UL0d` storage identity, authentication profile, refresh and catalog, the `UL1a` backend flow and `UL1b` passive-window reporting, including their contracts and evidence. `UL2a`–`UL5` add rows to the existing `/usage` pager and touch no subscription route or new terminal view; they need no freeze lift. All other frozen work remains frozen.

## Research

### Saved-account backend activation

This implementation replaces the pre-token route refusal and covers `UL0b-fix`, `UL0c`, `UL0d` and `UL1a` using the existing account lock, pending-renewal marker, catalog decoder, Responses streaming decoder and journaled Provider lifecycle. Removed model-check and migration machinery is outside this implementation; admission uses current consent and the existing catalog cache. The shared Rust HTTP paths have no OS-specific implementation change.

A live catalog query on 2026-10-31 returned no visible models with Arany's release version and six with only `client_version` changed to the compiled Codex compatibility version. The pinned [Codex catalog](https://github.com/openai/codex/blob/eec8bde1e9a5fe0e6cbefa88ff587ad1a478c08a/codex-rs/models-manager/models.json) declares minimum client versions above Arany's unrelated semver. This supersedes the proposed static-catalog response to a confirmed filter: pin the catalog compatibility version beside the adapter, retain `originator: arany`, and keep the account-filtered server catalog. There is no version probing, automatic fallback or claim of support for all Codex features; empty and refused catalogs retain their existing handling.

The pinned peer sources below establish the catalog and inference destinations and account headers. [OIDC refresh validation](https://openid.net/specs/openid-connect-core-1_0.html#RefreshTokenResponse) permits an absent renewed nonce and requires a present nonce to match the original ID token. The planned replacement ID token remains optional; Arany verifies it when present with the selected subject and backend account. The original sign-in token remains the nonce/admission anchor even when a renewal omits identity; no new persisted field is needed. A refresh may retain its refresh token; this does not authorize a retry. The verified backend account crosses the CLI/Provider boundary as a required constructor input and stays out of persisted Events and diagnostics.

Security scope: assets are tokens, verified account identity and consented Workspace input. Issuer and backend HTTPS responses are untrusted bounded documents; compiled destinations, the selected account and current consent authorize egress. Renewal remains serialized and pending before exchange; uncertain replacement or a lost renewal reply, server failure or unavailable signing keys keeps use blocked without a repeated exchange. Catalog discloses only its token/account headers; journaled inference discloses only the admitted request, including inherited child and compaction requests. Existing deadlines, body/frame/output bounds, action/Goal budgets, no-redirect/no-proxy policy and the existing retry contracts remain unchanged. Production adds no processes, grants, dependencies, prompt authority or storage formats. This does not claim host isolation or remote usage caps.

Verification owners are the exchange/account/catalog corpora, subscription request/stream tables, Engine compaction coverage and the isolated offline HTTPS setup/turn journey. Success must include exact destination, account/session headers and request shape; rejection covers identity drift, malformed replacement identity, invalid lifetime, oversized/redirected/encoded replies and secret reflection. Reopened Events and strict replay must retain the accepted outcome without redispatch. Live model acceptance remains an owner-run check during this work.

### Corrections and delivery boundaries

The setup failures reported during this implementation require two explicit departures from the original research: the token lifetime follows the positive, representable expiry rule in the [ChatGPT contract](../../docs/specs/chatgpt.md#authorization-transaction), instead of the unsupported two-hour ceiling; uncertain refresh outcomes follow the [renewal contract](../../docs/specs/chatgpt.md#accounts-consent-and-storage), instead of Codex's transient server-error category. Neither changes stored identity, authorizes a repeated uncertain exchange or establishes live renewal support. The optional replacement identity and exact terminal error set follow the original plan.

Owner delivery exception (2026-10-31): at the owner's explicit request, publish the integrated changes in one PR without the 1,500-line ceiling or one-PR-per-slice split. This exception covers only `UL0b-fix`, `UL0c`, `UL0d` and `UL1a` in this delivery; every other slice retains the normal rules. `UL0b-fix` owns the sign-in lifetime, safe diagnostics and shared issuer fixture; `UL0c` owns renewal/revocation; `UL0d` owns catalog/setup and the reproduced archive-notice loss; `UL1a` owns inference. The startup correction restores existing notices rather than redesigning the UI.

## Chosen direction

# Guard egress proxy, web Tools and remote MCP

## Metadata

- Status: `Ready` (low priority; implementation after the items above it in `NEXT_STEPS`)
- Owner: harness maintainers
- Last updated: 2026-10-25

## Outcome and scope

One capability: a guarded process (Command, MCP server, Skill script) can reach an explicitly allow-listed set of domains through a Guard-side egress proxy, and nothing else; on that mechanism Arany then offers `web_fetch` and `web_search` Tools and remote MCP servers with OAuth. The harness responsibility served is Tool execution with a typed network grant ([per-effect isolation](../../AGENTS.md#non-negotiable-guarantees): "run in the Guard under pinned, typed grants"); the guarantee is unchanged, a network grant becomes one more pinned typed grant.

This plan absorbs the network half of the `NEXT_STEPS` "Development command environment" item ("opt-in network through a per-project domain allowlist behind a Guard proxy, like the Claude Code sandbox and Codex `network_access`") and the "Deferred network grants" follow-up (remote MCP/OAuth); both link here. Excluded: interactive and background jobs (they remain in "Deferred network grants"), Provider egress (already its own contract), and any ambient network for the payload.

## Contract and scenarios

- Owning contracts: [tools.md](../../docs/specs/tools.md) (new "Network grants and egress proxy" section; Permission rules; Local MCP → "Local and remote MCP"; Limits; Linux and macOS enforcement), [provider.md Configuration and egress](../../docs/specs/provider.md#configuration-and-egress) (shared destination policy owner), [execution.md Persistence bounds](../../docs/specs/execution.md#persistence-bounds) (observation bounds for web results), [credentials.md](../../docs/specs/credentials.md) (MCP OAuth token storage), [terminal.md](../../docs/specs/terminal.md) (`/permissions` domain rows, approval prompt), [goals.md](../../docs/specs/goals.md) (web Tool call accounting), `docs/tools.md` user guide.
- Proposed grant: `tools.json` gains `network: { allow: ["example.com", "*.pypi.org"], ... }` per folder grant (at most 64 patterns, exact host or one leading `*.` label, no IPs except numeric loopback, no ports other than 443 unless loopback); the grant is pinned into the enforcement digest and the Run's `RunStarted` like every other grant. A Command or MCP intent names the grant; the Guard starts a per-unit proxy listener in the parent (a Unix socket bind-mounted into the unit on Linux; a loopback port in the launchd unit's private domain on macOS) and sets `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY=` for the payload. The payload keeps its network namespace: the only route out is the proxy socket. The proxy accepts `CONNECT host:443` and plain `GET`/`POST` to allow-listed hosts only, resolves through the Provider destination policy, refuses redirects and non-allow-listed hosts with a bounded typed refusal that is recorded in the observation (`network_refusals: [{host, count}]`, capped), and never terminates TLS. Unlisted host at runtime: refused (no prompt mid-command); the observation's refusal list lets the model ask, and the user adds the domain through `/permissions` (remember rule `Network(domain:x)` in the Claude Code syntax) before the next command. Bounds per command: 64 connections, 32 MiB transferred each way, 120-second idle; overflow closes the connection and is counted.
- Proposed web Tools (slice 2): `web_fetch { url }` (exact URL, allow-listed host or an explicit per-call `ask` approval like `WebFetch(domain:x)` rules; GET only; 100,000-character bounded text extraction from HTML/Markdown/plain text; result through the ordinary 64 KiB excerpt plus the [spill file](../context-budgets/README.md) when it lands) and `web_search { query }` through one reviewed backend API declared in private configuration with its own credential reference (no scraping; at most 8 backend calls per Tool call and 200 per Session). Both run in the Guard through the proxy; results are untrusted data like any observation; they are primary-only operations by default and researcher-eligible by grant.
- Proposed remote MCP (slice 3): `tools.json` MCP entries gain `url` (HTTPS only) with `auth: oauth` ; discovery per RFC 9728 then 8414, PKCE, loopback callback as the ChatGPT flow does, tokens stored through the existing account-root keyring/private-file owner with a per-server slot; the MCP client runs in the Guard behind the proxy with the server's origin allow-listed implicitly; the same catalog, schema and framing bounds as local MCP.
- Scenarios: `npm install` against an allow-listed registry succeeds and the observation lists zero refusals; `curl evil.example` inside the same command is refused and recorded; a redirect to an unlisted host is refused; `web_fetch` of an allow-listed page returns bounded text; a 2 MiB page is cut with the marker; `web_search` beyond 8 backend calls records `Limit`; a remote MCP server with expired token refuses before any call with a typed reason and the user re-authorizes; proxy crash mid-command → the payload sees connection failures, the command observation records `proxy_unavailable`, disposition from the command's exit as usual; replay never contacts the network.
- Evidence owners: new `crates/arany-cli/tests/session_run/tools/network.rs` with a loopback fixture upstream (success, refusal, redirect, limits), `crates/arany/src/tools/guard/linux.rs` tests (socket mount, namespace attestation), `tests/session_run/tools_macos.rs` (proxy port in the unit), `tests/engine_run/workspace_security.rs` (no ambient egress; `NO_PROXY` empty), `tests/session_run/custom.rs` pattern for the search backend fixture, `accounts` corpora for MCP OAuth storage.

## Chosen direction

- Simplest sufficient solution: one proxy implementation in the library (`tools/network.rs`) built on the existing reqwest client and destination policy for upstream connections, speaking HTTP/1.1 `CONNECT` and absolute-form requests to the payload; no TLS interception, no DNS inside the unit, no per-protocol parsing. Web Tools are thin operations over the same proxy client. Remote MCP reuses the local MCP client with a streamable-HTTP transport behind the proxy.
- Linux/macOS: Linux bind-mounts the proxy Unix socket into the unit (bubblewrap `--bind` of one socket file) while the network namespace stays empty; macOS allows outbound to one loopback port from the command profile (`(allow network-outbound (remote ip "localhost:PORT"))`) and nothing else. Both fail closed if the proxy cannot start; native evidence through the existing Linux and macOS command corpora.
- Interface change: one new grant kind, three new ToolCall variants (`WebFetch`, `WebSearch`, and MCP entries with `url`), one new observation field. The facts table and all per-variant consumers gain arms (the known per-variant cost; B15's family split lands first).

## Security and resource model

New trust boundary: the proxy is a network reachability policy, not content inspection. Attacker-controlled inputs: everything the payload sends (hostnames, request bodies) and everything the upstream returns. Controls: allow-list matched on the exact host the payload names (no DNS rebinding through the payload, since it has no resolver; the proxy resolves under the Provider destination policy and pins the admitted address set per connection); redirects refused; no credentials injected or masked (the payload sees only what the user put in its environment, which is cleared today, so no credentials unless a grant adds one explicitly); bounded bytes, connections and idle time; the socket is created `0600` by the parent and removed with the unit. TLS is end-to-end payload↔upstream; the proxy cannot see or alter content, which also means it cannot filter exfiltration inside an allowed host, exactly as the peers document. Web Tool results and MCP responses are untrusted data for instruction, trust and approval decisions (safe AI cage unchanged). The security pass ([triggers](../../agents/security.md#security-pass-triggers): network, MCP, untrusted rendering, auth) runs in every slice; the dependency review covers any HTML-to-text crate before slice 2 (prefer a bounded in-tree extractor over a dependency).

## Risks and mitigations

- Allow-listed hosts become exfiltration channels (a package registry accepts uploads) → documented limitation, same as peers; the default allow-list is empty; the refusal list makes unlisted attempts visible.
- Build tools ignore proxy variables → documented per toolchain (`cargo` and `npm` honor them; `pip` honors them); no transparent redirection in beta.
- Search backend credentials → stored only as an `ARANY_PROVIDER_*`-style reference in private configuration, never in Events.

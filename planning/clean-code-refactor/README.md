# Clean-code refactor

Behavior-preserving clean-up of the hot orchestration code, the refusal idiom, the test-support hooks and the shared limits, delivered as small independently mergeable PRs that keep journal bytes, model-facing bytes and user-visible output byte-identical.

## Outcome and scope

One observable feature: after this plan every slice below has landed and the repository satisfies the exit criteria while every existing corpus passes unchanged. The harness responsibility served is [priority 3](../../AGENTS.md#product-and-implementation-priorities): keep the Engine, Store and binary cheap to change safely for the daily feature merge train.

In scope, in priority order:

1. Rule-level violations: refusals carried as `Err(EngineError::…)` inside the Run loop, and test-support hooks spliced into Store, Journal, Guard and Provider-retry code.
2. Shared limits: one owner per shared ceiling, no same-name/different-value constants, the four hand-rolled bounded sequence visitors.
3. The giant orchestration functions, split by flow into files with one reason to change.
4. Duplication (native adapters, reducer admission, binary cycle) and provider identity as raw strings.

Out of scope, with the reason:

- `engine/report.rs` sentences ("Goal completed.", "Worker {id}: settled and verified."): the report is journaled in `GoalFinished.report` ([engine.rs:1169–1180](../../crates/arany/src/engine.rs), [events.rs:285](../../crates/arany/src/session/events.rs)). Moving composition to the binary changes journal bytes and the Goal contract; it is a spec change, not a refactor.
- The Guard enforcement-digest prose ([linux.rs:60–70](../../crates/arany/src/tools/guard/linux.rs), [macos.rs:246–262](../../crates/arany/src/tools/guard/macos.rs)): the digest is pinned in `ToolStarted`. Its bytes stay; slice C4 only adds a consistency test that fails when a named constant drifts from the prose.
- `Result<_, String>` in the binary (128 functions, 191 `map_err(…to_owned)`): the CLI is a reporting boundary; typed causes already cross the Engine seam as `EngineError`/`RunStop`. Per [rust-clean-code](../../.agents/skills/rust-clean-code/references/design-and-errors.md#preserve-useful-errors) an erased error with context is adequate there.
- Public `EngineError` variants: serve exports them as the `$defs.Reason` vocabulary ([serve spec](../../docs/specs/serve.md), [rpc.rs:143](../../crates/arany-cli/src/protocol/rpc.rs)) and the Goals spec names `GoalBudgetExhausted` at the public resume interface. The enum stays; only the Run loop's internal use changes.
- `.clone()` density, `expect` in `cli/acp/translate.rs` (44 lock sites), `GoalView`/`RunConfig` field counts, `Reason`/`TerminalInput` variant counts: no concrete consequence demonstrated; revisit only when a slice touching that file shows one.
- Behavior corrections discovered on the way (one recorded below in [Risks](#risks-and-mitigations)) go to `NEXT_STEPS.md`, never into a slice of this plan.

## Chosen direction

Skills applied: [Ponytail](../../.agents/skills/ponytail/SKILL.md) (reuse existing enums and owners, delete copies, no new traits), [rust-clean-code](../../.agents/skills/rust-clean-code/SKILL.md) (closed enums over bool pairs, errors for failure only, extraction only where a name explains an operation), [clean-architecture-review](../../.agents/skills/clean-architecture-review/SKILL.md) (dependency direction, one owner per policy, cycles), [codebase-design](../../.agents/skills/codebase-design/SKILL.md) with [DEEPENING](../../.agents/skills/codebase-design/DEEPENING.md) and [DESIGN-IT-TWICE](../../.agents/skills/codebase-design/DESIGN-IT-TWICE.md) (seam placement and the two designs compared below), and [improve-codebase-architecture](../../.agents/skills/improve-codebase-architecture/SKILL.md) for weighting by churn.

### Refusal values in the Run loop (design it twice)

Constraint: the public `EngineError` stays; the per-site `StopCause` mapping stays exactly as it is today, including where it is inconsistent.

- Design A, nested result: `GoalLedger::reserve` and `reserve_active` return `Result<Admission<T>, EngineError>` with `pub(super) enum Admission<T> { Reserved(T), Exhausted }`; `ContextTooLarge` inside the loop becomes the existing `SizingRefusal::ContextFull`; `intent_observation` is deleted and its callers match `IntentResult` directly. Each consumer replaces `Err(EngineError::GoalBudgetExhausted) => X` with `Ok(Admission::Exhausted) => X`. Interface: one enum, one meaning, exhaustive matches.
- Design B, fold into `StopCause`: helpers return `Result<T, StopCause>` everywhere. Rejected: the ledger does not know which stop cause the site wants (today `ActiveTime` vs `Budget` is chosen per site), so B would either widen `StopCause` with an `Exhausted` placeholder or move site policy into the ledger, changing settlement precedence.

Design A is chosen: it is the smallest change that makes the refusal closed, keeps the ledger ignorant of stop policy and preserves every byte. The closed value also removes the overloaded uses in `hooks.rs` (cancellation and a missing hook run currently share `GoalBudgetExhausted`); the slice gives each its own `Admission`/`HookOutcome` variant while mapping to the identical downstream value.

### Test-support hooks (deepening the fault seam)

`fault::FaultPlan` is already the one internal seam for faults (in-process, local-substitutable). Deepen it instead of adding a port: every fault point becomes a plain function or method that always exists (`fault::checkpoint_stalled(session).await`, `fault::append_fails(..)`, `fault::retry_backoff(..)`) whose body is `cfg`-gated inside `fault.rs`, so the hot paths contain no `#[cfg]` blocks and no `let _ = param;` residue. The cfg-gated `receipt` parameter becomes a `LatencyReceipt` type that is a zero-sized unit outside `test-support`, so `invoke_attempt`/`invoke_bounded_with_preview` have one signature. The `run_start: bool, sealed_data: bool` pair becomes one closed `AdmissionKind { Operation, RunStart, SealedData }` that production uses for the run-start byte allowance and the test recorder reads unchanged. `account_path` keeps one override point (`test_support::account_root()`); the env fixture check moves beside it. One adapter, one seam: no trait.

### Shared limits and validators (leaf module)

The cycle root is generic primitives owned by `tools::types`/`tools::skills`. A leaf module `crates/arany/src/validate.rs` (no `crate::` imports) owns `valid_name`, `valid_relative`, `valid_revision`, `valid_digest`, `digest`, `parse_json_bounded`, a generic bounded sequence deserializer and the two path ceilings `MAX_PATH_BYTES = 4096`, `MAX_RELATIVE_PATH_BYTES = 512`. `tools::types` re-exports them, so the move lands without touching callers; a later mechanical slice migrates `use` paths and deletes the three private `MAX_PATH_BYTES` and the inline `4096` checks. This passes the deletion test: removing the module scatters the same checks over 65 sites. Other shared values get one owner at the module that already defines the policy (`session::MAX_USER_MESSAGE_BYTES` made `pub` for the CLI edge; `provider::NATIVE_CALL_DEADLINE`; `native_check::{TOTAL_DEADLINE, PROBE_OUTPUT_CAP}` made `pub(crate)`; `provider::catalog::MAX_MODELS` exported as `arany::MAX_CATALOG_MODELS`; `tools::WORKER_PREPARATION_MS = 120_000`). Same-name/different-value constants are renamed, never merged.

### Orchestration functions (split by flow, not by layer)

Each giant function is split into named phases that already exist as comment sections or local-variable clusters, moved into a sibling file owned by that flow: startup vs idle loop in `attached.rs`; admission vs drive vs finish in `submit_objective`; client message vs committed event vs worker completion in `run_configured`; checkpoint, review and dispatch in `step.rs`; ToolCall projection vs Run feedback vs exec rendering in `presentation.rs`. Splits are pure moves plus a struct for the locals they share; no logic change, no new trait.

### Linux/macOS impact

None. The Guard digest bytes and the macOS/Linux adapters are untouched except for naming one shared 120 s constant whose value they already use.

### Ownership or interface changes

Internal only: `GoalLedger::reserve*` return type, `Journal::admit*` take `AdmissionKind`, `fault` functions always present, `validate` leaf module, `cli::bounded_list`/`open_optional_state` move to a leaf `arany-cli/src/files.rs`. No public API rename; the two new public items (`arany::MAX_USER_MESSAGE_BYTES`, `arany::MAX_CATALOG_MODELS`) are additive.

No trust boundary, authorization, secret, bound or overflow behavior changes. Every limit keeps its value; the slices move ownership only. ## Risks and mitigations

- A slice changes a `StopCause` at one site while making refusals closed → the slice keeps a table of every old arm and its new arm; `engine_run::goals`/`routing`, `session/stop.rs` and `guard_runs` must pass unchanged; any arm whose mapping looks wrong is kept and noted in `NEXT_STEPS.md` (today `hooks.rs:625–637` reports a cancellation during a hook as `GoalBudgetExhausted`, which downstream becomes `ActiveTime`; whether that is intended is a behavior question outside this plan).
- Merge conflicts with feature PRs on `step.rs`, `presentation.rs`, `active.rs`, `run_loop.rs` → slices on those files are pure moves or mechanical arm rewrites, kept under ~400 changed lines, rebased the day they open, and sequenced after the in-progress feature slice that touches the same function (see [Parallelism](#parallelism-map)).
- A move changes `pub(super)` visibility and silently widens an interface → every moved item keeps the narrowest visibility that compiles; Clippy with `-D warnings` runs on every slice.
- A renamed constant hides a real duplicate → the consistency test in C4 asserts each shared value once; a second definition of the same value in a sibling module fails review by the grep in the exit criteria.
- The `validate` leaf module tempts new generic helpers → it accepts only functions with two or more callers in different top-level modules; everything else stays with its owner.

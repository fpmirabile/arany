# Custom protocol family: OpenAI Chat Completions

## Metadata

- Status: `In progress`
- Owner: harness maintainers
- Last updated: 2026-10-26

## Outcome and scope

One capability: a custom profile may declare `protocol: openai-chat-completions`, pass the same `provider check` conformance sequence as the two existing families, and then serve read-only primary, child and compaction calls through `custom:NAME`. This opens every endpoint that speaks only `POST /v1/chat/completions` (vLLM, llama.cpp server, LiteLLM and other gateways, Groq, Mistral, Together, DeepSeek's native API) without a vendor-specific adapter. The harness responsibility served is the Provider boundary ([priority 1](../../AGENTS.md#product-and-implementation-priorities)); the [custom-destination admission contract](../../docs/specs/provider.md#custom-destinations-and-routing) (admission before disclosure, durable provenance, exact conformance) is reused unchanged.

Excluded: Workspace Tools on custom routes (today every custom route is read-only, [setup.md](../../docs/setup.md#openai-compatible-and-anthropic-custom-routes); extending Tools to custom routes is a separate feature for all three families), streaming previews on this family, OpenRouter's broker profile, and any relaxation of the check gate (the owner's comparison recommended making the probe a diagnostic; that is a separate decision and not part of this plan).

## Research

- Existing families: `CustomProtocol { OpenaiResponses, AnthropicMessages }` and the serde-tagged `ProfileEntry` with per-family fields ([provider/custom.rs:40,105-150](../../crates/arany/src/provider/custom.rs)); a Responses entry needs `endpoint` ending in `/responses` and `outcome_encoding: json_schema`, a Messages entry needs `base_url`, `auth` and `outcome_encoding: native_tools` ([provider.md Custom destinations](../../docs/specs/provider.md#custom-destinations-and-routing)). Shared pieces: the bounded transport and DNS/address admission (`custom/destination.rs`, `custom/transport.rs`), the check journal and probe sequence (`custom/check.rs` `probe`, `probe_compaction`: streaming direct answer, one-child delegation, text compaction, one probe per declared effort, at most 15 calls in 180 seconds), the HMAC evidence fingerprint and the `CustomProvider::admit` re-resolution before any key read.
- Wire builders: the Responses body is built in `provider/openai/wire.rs` (functions, `allowed_tools`, `prompt_cache_key`, `include: reasoning.encrypted_content`); the shared Responses decoder is `provider/openai/responses.rs`; Messages in `provider/anthropic/wire.rs`. The semantic request/outcome types (`ProviderRequest`, `ProviderOutcome::{Answer, Delegate, Plan, Review, Tools}`, `Usage`, `ProviderWireProvenance`) are adapter-neutral ([provider.rs:951-967](../../crates/arany/src/provider.rs)).
- Setup: the attached custom-route form already selects a protocol by key (`b'1'`/`b'2'`, [cli/attached/setup.rs:1538-1568](../../crates/arany-cli/src/cli/attached/setup.rs)) and branches endpoint and auth prompts on it; `docs/setup.md` holds the DeepSeek/Kimi/GLM recipes.
- Record format: `provider-profiles.json` is a closed version-2 document with at most 32 profiles; an added family is an additive variant of the tagged enum and keeps version 2 (unknown `protocol` values already refuse, so old readers are not a concern under rule 5).
- Peers. Codex removed Chat Completions ("`wire_api = "chat"` is a config error", [model-provider-info/src/lib.rs](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs)) and reaches Ollama and LM Studio through their Responses endpoints (`utils/oss`). OpenCode selects the AI SDK package per provider and documents `@ai-sdk/openai-compatible` (Chat Completions) for custom providers ([providers](https://opencode.ai/docs/providers/)). Aider uses litellm, Chat Completions for every provider ([aider/coders/base_coder.py](https://github.com/Aider-AI/aider/blob/main/aider/coders/base_coder.py)). Goose ships its own providers with Chat Completions for OpenAI-compatible endpoints ([crates/goose-providers](https://github.com/block/goose/tree/main/crates/goose-providers)). Peer evidence is split; the family is justified by endpoints that offer only Chat Completions, not by parity with Codex.
- Chat Completions contract (OpenAI reference, read 2026-10-25): `POST {base}/chat/completions` with `model`, `messages[{role, content | tool_calls | tool_call_id}]`, optional `tools[{type:"function", function:{name, description, parameters, strict}}]`, `tool_choice` (`"none" | "auto" | "required" | {type:"function", function:{name}}`), `parallel_tool_calls`, `reasoning_effort`, `max_completion_tokens`, `stream`; the non-streaming reply carries `choices[0].message.{content, tool_calls[{id, function:{name, arguments}}]}`, `finish_reason: stop | tool_calls | length | content_filter`, `usage.{prompt_tokens, completion_tokens, total_tokens}` and a response `id` ([API reference](https://platform.openai.com/docs/api-reference/chat/create)). Delegation and the strict outcome encoding therefore map to one function tool exactly as on Responses; a `length` finish rejects as `max_tokens` does on Messages.

## Contract and scenarios

- Owning specs: [provider.md Custom destinations and routing](../../docs/specs/provider.md#custom-destinations-and-routing) (new entry shape, URL derivation, request headers, probe reuse), [Provider support summary](../../docs/specs/provider.md#provider-support-summary) (one row), [Structured outcomes](../../docs/specs/provider.md#structured-outcomes-and-tool-encoding) (encoding on this route), [execution.md JSON record migration](../../docs/specs/execution.md#json-record-migration) (document stays version 2), [credentials.md](../../docs/specs/credentials.md) (unchanged credential reference rule), [terminal.md](../../docs/specs/terminal.md) setup form, [setup.md](../../docs/setup.md) recipe.
- Proposed contract: a Chat entry requires `protocol: openai-chat-completions`, a canonical `base_url` (same validation as Messages; `/chat/completions` is appended, an already-suffixed base rejects), `auth: bearer`, `outcome_encoding: json_schema` (one strict function tool, as on Responses), the shared `model`, `credential_env`, `privacy`, `max_output_tokens`, `capability_evidence_version` and `efforts` fields; `efforts` map to `reasoning_effort` and must pass their probes. Requests are non-streaming JSON with `stream: false`, `parallel_tool_calls: false`, `store` omitted, honest `User-Agent`, Bearer only; replies require exactly one choice, `finish_reason: stop` for a plain answer or `tool_calls` with exactly one call for a structured outcome, a non-empty `id`, positive `usage` within the cap, and the exact requested model; `length`, `content_filter`, several calls, several choices, missing usage or model drift reject. Provenance records `ChatCompletionsStopStorageUnspecified` (new `ProviderWireProvenance` value; no retention claim). The check runs the same 15-call sequence; evidence binds the family like the others.
- Successful path: a llama.cpp server on loopback declared as `custom:local`; `provider check custom:local` passes; `exec --provider custom:local` answers a read-only question; a `team` policy delegates one child through the same route; compaction uses the route's text contract.
- Rejection/failure/recovery: an endpoint that returns two choices fails the check with a typed `response contract` reason and leaves no evidence; a `length` finish during a Run records a `ProviderCallRecorded` failure with the closed reason and the existing fail-and-drain recovery; an SSE reply to a `stream: false` request rejects at the media-type guard; a base URL with a query string refuses at load; a changed base URL invalidates evidence and the Run refuses before Workspace input.
- Evidence owners: `crates/arany/src/provider/custom/check.rs` tests and `provider/snapshots/` request bodies (new family rows), `crates/arany-cli/tests/session_run/custom.rs` (loopback fixture server speaking Chat Completions: success, two-choice rejection, `length`, missing usage), `tests/session_run/setup/` (form), `cli/record_formats.rs` tests (document parsing).

## Chosen direction

- Simplest sufficient solution: one new `ProfileEntry` variant, one body builder and one strict decoder in a new `provider/openai/chat.rs` reusing the Responses function-tool encoding and `Usage` types, one `Protocol::OpenaiChat { base_url }` branch in the custom adapter and transport, and the existing probe sequence unchanged. Non-streaming only: previews are optional on the trait (`invoke_with_preview` defaults to `invoke`), and streaming chunk reassembly would double the decoder for no contract gain on read-only routes.
- OS impact: none.
- Interface change: `ProviderWireProvenance` gains one value (additive, journaled; `ProviderCallRecorded` keeps its version under the additive rule only if the field is an enum extension accepted by the validator; otherwise bump the version with a fixture, decided at slice 1 open by the migration test). Not a module boundary change.

## Security and resource model

Same trust boundary as the two existing families: trusted private configuration, selected key only, no arbitrary headers, no redirects, DNS and address admission, HTTPS for domains, loopback exception, 512 KiB request bound, the shared HTTP client reply bound, no Workspace input until evidence is admitted. The decoder refuses credential reflection like the others. The security pass for a new wire family ([security triggers](../../agents/security.md#security-pass-triggers)) runs in slice 1 against the loopback fixture.

## Risks and mitigations

- Vendors deviate from the reference (missing `usage`, `finish_reason: "stop"` with tool calls) → strict rejection with a typed reason, visible in `provider check`; no fallback or repair, as on the other families; the research note records the exclusion.
- Read-only custom routes limit the feature's daily-use value → stated in scope; the Tools-on-custom-routes feature is tracked in `NEXT_STEPS` as deferred, not in this plan.
- Code growth in `provider/` → the builder/decoder is one file under 400 lines; no new transport, DNS or check code.

# MCP and runtime Skills: beta 1 foundation

Retrieved: 2026-10-04  
Status: primary-source research and implementation recommendations; no server launch, dependency installation, credential access or live inference

## Recommendation

Build one effect router for native Tools, commands and MCP. Skills supply optional instructions and bundled resources to that same loop; they are not executable plugins or a second permission system. Keep transport, protocol objects and filesystem paths out of the Provider semantic interface. The new user request activates the effectful gate in [security rules](../../agents/security.md#effectful-execution-gate): normalized intent, deterministic restrict-only Policy, digest-bound approval, separate enforcing Guard and effective-capability evidence must precede execution.

A useful first MCP increment is a real local stdio client: connect, discover, admit exact Tools, invoke them through the Engine, return results to the model, continue to a final answer, persist and replay, cancel and clean up. Do not deliver only an `mcp list` command or a successful JSON parser. Streamable HTTP is a distinct next adapter, not a stdio URL shortcut. If beta 1 promises remote MCP, implement its full admitted transport lane before calling that scope complete. Neither an SDK nor a process group is a sandbox.

## Current protocol facts

The current stable specification is **2026-07-28**, not the repository's historical 2025-11-25 baseline. Modern MCP carries version and client capabilities on every request; there is no initialization handshake. For dual-era stdio, probe `server/discover`: a discovery result or recognized modern version error selects modern behavior; another error or a bounded timeout permits legacy `initialize` fallback. Self-reported identity is not proof of provenance. [Versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover).

Legacy 2025-11-25 requires `initialize`, a supported response version/capabilities, then `notifications/initialized` before normal requests. Unknown returned versions should disconnect. Timeouts have an absolute maximum regardless of progress. [Legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle).

Both standard transports are real supported choices: stdio uses newline-delimited UTF-8 JSON-RPC on child stdin/stdout, with separate stderr. Modern Streamable HTTP posts each message to one endpoint and accepts JSON or request-scoped SSE; it removed protocol sessions and the standalone GET stream. Legacy HTTP has different session, GET/DELETE and resumability behavior. An implementation must not mix those eras. [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

Tools use paginated `tools/list` and `tools/call`. Definitions include input schemas and optional output schemas; results contain content, optional structured data and an error flag. Modern structured results may be any JSON value, not just objects. Tool names are server-local; annotations such as read-only or idempotent are untrusted. Modern `input_required` is not a completed result. [Modern Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Legacy Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

JSON Schema defaults to 2020-12. A client must handle unsupported dialects explicitly, never automatically fetch external `$ref` URLs, and bound expensive compositions and recursion. Modern request metadata and `resultType` are core protocol behavior, not cosmetic fields. [Base protocol and schema requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic).

Cancellation is not rollback: stdio sends `notifications/cancelled` for its in-flight ID; modern HTTP closes the response stream. Servers may already have completed or be unable to cancel. Late results must not be accepted as a new call. [Cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation).

## Concrete MCP ownership and lifecycle

These are proposed Arany decisions, not claims about existing support:

1. Trusted user configuration outside the Workspace identifies the server, transport, immutable executable/package provenance or exact endpoint, Tool allowlist, credential references, limits and effective grants. No workspace `.mcp.json`, arbitrary `npx`, lifecycle installer, shell startup, PATH search or inherited Provider token. Refuse changed executable/config digests before launch. Interpreter-based servers require reviewed interpreter and script/package inputs, not merely an approved executable path.
2. Guard admits local-server startup itself as an effect before untrusted code executes. It pins cwd, readable/writable roots, minimal environment, descriptors, network and descendants. Protocol startup receives no objective or Workspace payload. Process lifetime may be narrowed to one Run when necessary to revoke its pinned Workspace capabilities; document that security reason rather than claim the process is an MCP Session.
3. Advertise only implemented capabilities. Start with tools and ping; no sampling, user elicitation, host-root disclosure, task extensions, app rendering or server-triggered execution. Modern capability errors and legacy server requests receive bounded protocol handling, not an implicit grant. Supporting modern core `input_required` means recognizing and terminating unsupported interaction safely, never fabricating `complete` or automatically opening a URL.
4. Fetch single catalog pages under a finite page/count/byte budget. Namespace Tools by Arany's configured server ID, not `serverInfo.name`. Validate definitions and compile input/output validators before publication. Pin server/config, version, Tool name and schema digest in the Run's catalog. A list-change notification marks the snapshot stale; a newly advertised Tool or changed schema needs fresh admission and cannot widen a running grant.
5. The model proposes one semantic Tool call. Normalize its arguments once, validate the pinned schema, derive typed resources/data disclosure, reserve aggregate budget, obtain exact Policy/approval, commit the intended attempt, then submit to Guard. MCP receives only those arguments, never all conversation or credentials. Policy must name remote operation/tenant scope and permitted data; an endpoint allowlist alone cannot enforce the server's remote side effects.
6. Correlate exact request IDs and accept one terminal result. Reject malformed JSON-RPC, duplicate keys/results, unsolicited IDs, invalid structured output and forbidden content. Text/structured JSON can form a complete useful first content profile. Resource links remain inert; do not automatically fetch URLs, read local `file:` paths, download icons or run returned commands. Unsupported image/audio/blob content gets a typed result rejection, not silent loss or false success.
7. Return bounded normalized Tool results as untrusted Tool observations to the requesting AgentRun. They never become system instructions, Skill activation, Policy, credential selection or shell text. Record the execution disposition independently of whether the model can continue after a Tool error; child calls remain narrower and read-only by default.
8. On timeout/cancellation/disconnect, classify an attempted mutation as uncertain unless completion or rejection is actually known. Close stdin, escalate termination under a bounded grace, kill/reap the complete owned tree and release permits. A later fresh connection rechecks version, catalog and grants. No automatic replay of `tools/call`; an MCP recommendation to restart does not prove an effect is idempotent. Replay/resume never reconnects or re-executes history.

For HTTP, add exact normalized endpoint and DNS/address admission, ordinary TLS/name validation, no ambient proxy/redirect/decompression/retry, media-type and JSON/SSE bounds, and per-server credentials. Modern mirrored `Mcp-*`/schema-designated headers require the selected version's correct encoding/validation; reject a Tool whose header behavior cannot satisfy the disclosure grant. An old `Mcp-Session-Id` is not authentication. OAuth issuer/resource/audience/scopes and every metadata endpoint need separate authority; a remote response cannot authorize extra fetches or browser launches. stdio credentials may use an explicitly selected server-only environment reference; no whole-environment forwarding. [Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

## Dependencies: use a reviewed SDK, not its defaults as guarantees

The checked [Arany manifest](../../Cargo.toml) already has Tokio, Serde/JSON, Reqwest, URL, SHA-2, capability filesystem and Unix process facilities. Neither `rmcp`, a JSON Schema validator nor a YAML parser is presently installed; futures components and indexmap are transitive. Reuse the existing process/HTTP boundary where its ownership and limits fit; do not add a second generic execution framework.

The official published **rmcp 3.5.0** release declares Rust **1.88** and Apache-2.0. Its feature graph separates client, async read/write, subprocess, HTTP and OAuth support. Disable defaults: they enable server/macros and are unnecessary for a client. A stdio integration candidate is `client` plus a bounded transport owned by Arany, without automatic executable resolution or server/OAuth features. HTTP and validators add dependencies only after source/feature/license/advisory review. [Published crate](https://docs.rs/crate/rmcp/3.5.0), [Release manifest](https://raw.githubusercontent.com/modelcontextprotocol/rust-sdk/rmcp-v3.5.0/Cargo.toml), [Release feature graph](https://raw.githubusercontent.com/modelcontextprotocol/rust-sdk/rmcp-v3.5.0/crates/rmcp/Cargo.toml).

Two inspected defaults do not meet Arany's contract: `AsyncRwTransport::receive` appends `read_until` to a `Vec` without a frame ceiling; the HTTP transport enables session recovery and documents replaying ordinary POSTs after session expiration. SDK parse errors can include response previews. Own bounded framing, zero hidden call replay and compiled/redacted error conversion outside those defaults; avoid a maintained fork. [Release async transport](https://raw.githubusercontent.com/modelcontextprotocol/rust-sdk/rmcp-v3.5.0/crates/rmcp/src/transport/async_rw.rs), [Release HTTP transport](https://raw.githubusercontent.com/modelcontextprotocol/rust-sdk/rmcp-v3.5.0/crates/rmcp/src/transport/streamable_http_client.rs).

The SDK roadmap reports date-versioned conformance, while explicitly noting untested specification features. Upstream green tests are neither Arany's containment proof nor proof of every enabled SDK behavior. A handwritten legacy-only client can be a documented bounded profile, but must not masquerade as modern MCP or accept schemas it does not validate. Recommendation: prefer the reviewed published SDK plus narrow transport controls when supporting both eras; justify any restricted hand implementation with the exact advertised version/profile. [Official SDK roadmap](https://github.com/modelcontextprotocol/rust-sdk/blob/main/ROADMAP.md).

## Skills: a functional portable base

- Discover only explicitly admitted roots, with exact provenance/digests, no-follow handles and deterministic ordering. Workspace-root `.agents/skills` is guidance after Workspace admission, never trusted configuration. No Git/ancestor traversal, symlink following, implicit home scans or auto-installation is required. Duplicate names need source-qualified identity or an explicit rejection, not first-wins shadowing.
- Parse bounded portable YAML metadata; support actual scalar quoting/multiline descriptions rather than a misleading split-on-colon parser. Reject duplicate keys and malformed/oversized structures; unsupported host-specific behavioral fields remain inert with explicit compatibility feedback. A dedicated maintained YAML parser is a real new parsing dependency to review, not permission to add arbitrary packages.
- Advertise bounded name/description/source IDs; activate only a discovered identity, either through a semantic `skill.load` Tool or explicit `--skill NAME`/`/skill NAME [ARGS]`. Return the complete immutable body; do not execute code fences, `!` interpolation, variable-substitution commands or installers. Arguments remain bounded user data, not shell expansions.
- Read named references/assets lazily through the pinned Skill root, under normal file/Tool policy and context budgets. Execute a bundled script only through the existing command Tool and its interpreter/provenance grant; a Skill can be fully useful without inventing a script-specific backend. Frontmatter `allowed-tools`, `compatibility`, dependencies and natural language cannot grant roots, network, credentials, child creation or budgets.
- Pin activation digest/source in Run provenance and keep supplied instructions distinct from ordinary retrieved text. Resume/fork/compaction preserves historical provenance as data; a new Run revalidates current admitted Skills before use. Automatic activation relies on the catalog/model, not another classifier or keyword engine. Explicit activation remains available if the model omits it.

## Proposed bounds and evidence owners

The final implementation should define constants once and derive aggregate reservations; these are initial proposals, not permission to raise existing context/Event bounds:

| Boundary | Initial proposal | Overflow/failure |
|---|---|---|
| Configured servers / live local servers | 8 / 2; one outstanding Tool call per server | Reject admission before starting extra processes. |
| Catalog | 16 pages, 128 Tools/server, 256 overall; 256 KiB decoded metadata | Reject incomplete/cyclic catalogs; never call an omitted Tool. |
| Wire / JSON / schema | 256 KiB/frame, depth 32; 32 KiB/schema, 256 subschemas | Stop transport before unlimited allocation; reject unsupported/ref-expensive schemas. |
| Arguments / normalized result | 16 KiB / 32 KiB per call; 256 KiB result budget per Run | Whole-record rejection or explicitly typed truncation; no invisible prefix success. |
| Time / notifications | 10 s admission, 60 s call bounded by remaining Run time, 2 s cleanup; 64 notifications/call | Progress cannot renew absolute budget; flood fails closed. |
| Skill discovery / activation | 4 roots, 128 entries; 16 KiB catalog, 64 KiB body, 128 KiB reference, 256 KiB selected aggregate | Report limit before use; complete selected files or reject, not hidden partial instructions. |

Use the existing strict Provider fake for the semantic read/Tool/continuation/final-answer journey and exact request/count assertions. A private real stdio fixture proves wire negotiation, discovery, arguments, normal/error results, cancellation and killed/reaped descendants; it is not another Engine double. Reopen SQLite and compare deterministic `exec`/`show` channels and replay, including a crash after invocation but before result commitment: history must say interrupted/uncertain and execute nothing on resume.

Add hostile cases to the same owners: oversized unterminated line/stderr, duplicate/wrong IDs, notification flood, unsupported version, catalog/schema drift, external `$ref`, deep/recursive schemas, invalid structured result, control-text/credential canaries, stale approvals, cancelled replies and forbidden Skill paths/interpolation. The process fixture must exercise the actual Guard, not a `cfg(test)` unsandboxed route. Remote support needs its own compiled endpoint-admission, no-egress canary, TLS/SSRF and bounded SSE owner. Run focused synthetic checks during implementation; leave real accounts/services and native macOS to the final user-owned checklist without treating them as passing proof.

## Explicitly later

Package installation/update endpoints, arbitrary plugins, MCP Apps, task extensions, sampling, elicitation UI, automatic resource fetching/subscription, MCP-delivered Skills, interactive PTYs, background/detached jobs and recursive teams require their own named use and grants. They are not placeholders in this foundation. Remote OAuth is a separately implemented credential/destination lifecycle; a functional local stdio Tool client does not claim it. UI polish can wait, but clear execution/result/error/cancellation facts and trustworthy CLI admission cannot.

## First adapter and parsing dependencies

Follow-up recommendation, checked 2026-10-04: ship an explicitly named **MCP 2025-11-25 stdio Tools profile** first. Its implemented journey is `initialize` with that version and actual capabilities, require a supported reply, `notifications/initialized`, paginated `tools/list`, checked `tools/call`, correlated results, cancellation and bounded shutdown. Do not advertise 2026-07-28, Streamable HTTP, remote OAuth or other optional capabilities. This narrower adapter is functional, not a stub; the newer protocol discussion above is migration research. In this legacy profile `structuredContent` is an object, not the arbitrary JSON value allowed by the newer protocol. [Legacy lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [legacy Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

For schema validation, recommend the published `jsonschema = { version = "=0.56.0", default-features = false }`: its manifest declares Rust 1.85 and MIT, and disabling defaults removes HTTP/file resolution and optional TLS/IDNA support. Also call `.offline()` so an unregistered reference fails even if Cargo feature unification later enables a resolver. Choose the admitted draft explicitly, retain schema/meta-schema validation, compile once per pinned Tool digest, and use boolean/first-error validation instead of collecting an unbounded report. Do not bundle, dereference or register a network retriever. [Published manifest](https://docs.rs/crate/jsonschema/0.56.0/source/Cargo.toml), [offline and build API](https://docs.rs/jsonschema/0.56.0/jsonschema/struct.ValidationOptions.html).

Arany still owns resource admission: the proposed 32 KiB schema, depth 32, 256 subschemas, 16 KiB arguments and 32 KiB results are ceilings, not a proof of bounded validation work. Cap reference edges, array/object elements, composition branches and pattern bytes before compilation; reject unsupported dialects, unresolved/external references and work-amplifying graphs explicitly. Prefer the documented linear `PatternOptions::regex()` engine, with incompatible advanced patterns rejected rather than silently reinterpreted. The library documents draft-specific compliance gaps; use a real validator for admitted schemas and never claim arbitrary JSON Schema support from a small keyword checker. Validation remains synchronous: a Tokio timeout or dropping a blocking task cannot enforce a hard CPU deadline. Any hard wall-clock/memory guarantee needs a supervised, killable validation worker, or a separately evidenced deterministic admission restriction. [Validator capabilities and pattern options](https://docs.rs/jsonschema/0.56.0/jsonschema/).

For Skill frontmatter, recommend the published `yaml_serde = { version = "=0.10.7", default-features = false, features = ["std"] }`, the YAML Organization's maintained Serde parser fork; its manifest declares Rust 1.82 and MIT OR Apache-2.0. It handles scalar quoting and block descriptions without Arany inventing YAML semantics. Its deserializer has a depth limit of 128 and an alias-jump limit proportional to document events, not application-configurable work budgets. Therefore read at most 16 KiB of frontmatter into a slice, require one mapping/document, and use a bounded Serde visitor/seed for depth 8, 256 decoded nodes and 16 KiB cumulative scalar bytes, rejecting duplicate/non-string keys, unsupported tags and excessive alias expansion before building large values. Do not feed it an uncapped reader or mistake post-parse checks for allocation limits. Metadata cannot resolve includes, interpolate environment values, execute tags or grant authority; errors must not print raw source snippets. [Maintained published crate](https://docs.rs/crate/yaml_serde/0.10.7), [published manifest](https://docs.rs/crate/yaml_serde/0.10.7/source/Cargo.toml.orig), [published deserializer](https://docs.rs/crate/yaml_serde/0.10.7/source/src/de.rs).

These are dependency recommendations, not executed MSRV, license or security gates. No matching `jsonschema`, `yaml_serde` or `serde-saphyr` manifests were found by the read-only local Cargo source-cache check; nothing was installed. Resolve the selected graph with the repository's Rust-version policy, review transitive licenses and features, and retain the native Rust 1.88 build in the final verification handoff if its runner remains unavailable.

### Confirmed configuration and graph

The selected graph includes `jsonschema`, `jsonschema-regex`, `jsonschema-value` and `referencing` 0.56.0; `regex` 1.13.1 and `fancy-regex` 0.19.2; and `yaml_serde` 0.10.7 with `libyaml-rs` 0.3.0. No JSON Schema HTTP/file/async resolver, validator macro, Python or Ruby binding feature is enabled in this graph. All declared MSRVs in the inspected closure are at most 1.85; some packages omit an MSRV declaration. The root [manifest](../../Cargo.toml), [lockfile](../../Cargo.lock) and published [JSON Schema features](https://docs.rs/crate/jsonschema/0.56.0/source/Cargo.toml) are the version/feature owners, not this snapshot.

All manifest license expressions have a choice permitted by the current [license policy](../../deny.toml), including the conjunction requiring Unicode-3.0 and the less common MIT-0, Zlib and BSL-1.0 choices. The main parser/validator license texts were inspected; distribution still needs the applicable license texts and notices, not just allowed SPDX names. No license-policy expansion is indicated by this manifest pass. This does not replace `cargo-deny`, an advisory check or the distribution bundle's notice verification.

The top-level parser/validator and `libyaml-rs` declare `build = false`; the latter is Rust code transpiled from libyaml, not a bundled C build or dynamically loaded C parser. Transitive compilation still runs code: `unicode-general-category` 1.1.0 generates a table in Cargo's `OUT_DIR` from checked-in data; `ref-cast` 1.0.27 generates a private module and probes the selected `RUSTC`; `ref-cast-impl`, `strum_macros` and the already-used Serde derive path are procedural macros. The inspected new generation/probe paths do not fetch remote data or select arbitrary external source directories. `STRUM_DEBUG` can print generated tokens, so it is a build-log knob, not a runtime secret transport. Preserve the repository's build-input/feature controls. [Unicode table build](https://docs.rs/crate/unicode-general-category/1.1.0/source/build.rs), [reference-cast build](https://docs.rs/crate/ref-cast/1.0.27/source/build.rs), [Strum macro source](https://docs.rs/crate/strum_macros/0.28.0/source/src/lib.rs).

The exact JSON Schema builder chain is below; the constants remain Arany-owned, reviewed byte limits, not library defaults:

```rust
let validator = jsonschema::draft202012::options()
    .offline()
    .with_pattern_options(
        jsonschema::PatternOptions::regex()
            .size_limit(MAX_COMPILED_REGEX_BYTES)
            .dfa_size_limit(MAX_REGEX_DFA_CACHE_BYTES),
    )
    .build(&admitted_schema)?;
```

`offline()` installs `OfflineRetriever`, whose retrieval method always returns an error. `build()` retains meta-schema validation by default; the pattern limits are forwarded to `regex::RegexBuilder`. Their sizes are approximate per-pattern compilation/cache bounds, not aggregate validator memory or CPU budgets. Restrict pattern count and total pattern bytes separately. Matching panics are caught only with unwind panic behavior; aborts, allocation failure and synchronous runaway work still require process ownership to contain. No `unsafe` was found in the inspected JSON Schema compiler/reference/regex core source, but its transitive SIMD, allocation, reference-cast and hash/storage code means this is not an all-safe-Rust graph claim. [Pinned options implementation](https://github.com/Stranger6667/jsonschema/blob/1e244c994dd81a1feb7801556a813c6bf2d45dad/crates/jsonschema/src/options.rs), [offline retriever](https://github.com/Stranger6667/jsonschema/blob/1e244c994dd81a1feb7801556a813c6bf2d45dad/crates/jsonschema/src/retriever.rs), [regex implementation](https://github.com/Stranger6667/jsonschema/blob/1e244c994dd81a1feb7801556a813c6bf2d45dad/crates/jsonschema/src/regex.rs).

### Required integration controls

- **Parser ownership and bounds:** `yaml_serde::Loader` reads an entire reader without a cap and constructs a complete event vector before calling the Serde visitor. A bounded visitor limits decoded output and alias replay, not that earlier parser allocation. Use the pre-read frontmatter cap, pass a slice, and keep node/depth/scalar/duplicate-key admission; if the contract requires a hard memory/time boundary, parse in a supervised child with those actual limits and no credentials or inherited authority. Never describe `catch_unwind` as containment for memory unsafety or aborts. The wrapper uses raw-pointer unsafe code; `libyaml-rs` has manual allocation and assertion paths that intentionally double-panic to abort. That requires a dedicated unsafe-boundary review and hostile-input evidence before releasing an in-process hostile-input guarantee, but no exploitable memory defect was established by this read-only review. [Pinned loader](https://github.com/yaml/yaml-serde/blob/22a7009e918620b523ea06e54ca75275eabe8027/src/loader.rs), [parser wrapper](https://github.com/yaml/yaml-serde/blob/22a7009e918620b523ea06e54ca75275eabe8027/src/libyaml/parser.rs), [transpiled parser allocation/assertions](https://github.com/yaml/libyaml-rs/blob/66d8ae3d348b328ef2159e3dc0bc53f1deb4c3a2/src/lib.rs).
- **Tag contract:** typed string deserialization ignores scalar tags; `deserialize_any` exposes local `!Tag` values through `visit_enum`, but can ignore nonlocal explicit tags. A public Serde visitor therefore cannot prove rejection of every unsupported tag. Reject exposed local tags and document ignored global tags as inert metadata, or add a real event-level tag admission owner. Neither parser executes tags, resolves includes nor interpolates environment values. The earlier blanket tag-rejection recommendation needs this qualification; do not hand-write a raw-text YAML tag scanner or claim stronger rejection than the adapter can evidence. [Pinned tag/string deserialization](https://github.com/yaml/yaml-serde/blob/22a7009e918620b523ea06e54ca75275eabe8027/src/de.rs).
- **Validation work and privacy:** schema compilation, meta-schema checking and instance validation are synchronous; schema byte/depth bounds and linear regex do not bound all composition/reference work. A hard deadline needs killable ownership or evidenced deterministic work admission before invoking the library. Reject unsupported required schema semantics instead of silently claiming their enforcement. Library error strings may contain attacker-controlled URIs, schema/instance text or raw tags; return bounded typed reasons and do not forward their `Display`/`Debug` values into user output, logs or canonical error receipts. [Compiler and meta-schema call](https://github.com/Stranger6667/jsonschema/blob/1e244c994dd81a1feb7801556a813c6bf2d45dad/crates/jsonschema/src/compiler.rs), [validation error implementation](https://docs.rs/crate/jsonschema/0.56.0/source/src/error.rs).

No inspected source behavior requires replacing the selected published dependencies or keeping an Arany fork. The conditional blockers are uncapped reader admission, claiming pre-parser bounds from a visitor, running uncontained synchronous validation under a hard-deadline promise, raw dependency-error disclosure and an unevidenced all-tags-rejected claim. Their fixes are explicit admission/ownership/receipt contracts and focused synthetic evidence, not paid calls or a manual-test prerequisite.

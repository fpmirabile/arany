# macOS Guard crash recovery in other agent harnesses

Date: 2026-10-12. Status: research and proposed design assessment; not approval to change implementation or evidence of runtime conformance.

## Answer

The inspected harnesses do not establish an equivalent macOS recovery contract for Arany's combination of one-use launchd jobs, kernel resource coalitions and mounted fixed-capacity images. Their local cleanup mechanisms mostly execute inside the still-running owner. This makes them useful examples of ordinary lifecycle cleanup, but insufficient evidence that Arany should replace its persisted ownership and later reconciliation with `Drop`, signal handlers or process-group killing. See the source-specific comparison below.

**Assessment, not a demonstrated guarantee:** keeping bounded recovery inside the existing macOS Guard is reasonable while Arany retains disposable mounted storage and its descendant-containment contract. The important question is whether every interruption leaves enough validated ownership evidence for the next admission, without authorizing deletion or signaling from a filename, stale PID or stale disk number. The current [Tool contract](../specs/tools.md#macos-enforcement-and-compatibility), [unit recovery](../../crates/arany/src/tools/guard/macos/unit.rs) and [storage recovery](../../crates/arany/src/tools/guard/macos/storage.rs) explicitly address those concerns. Peer adoption alone cannot validate their race handling.

## What the source actually proves

### Codex

The local MCP launcher requests `ProcessMode::NewGroup`. Its process handle terminates locally on explicit shutdown or `Drop`; Unix termination uses SIGTERM followed by delayed SIGKILL. This requires the terminating owner to execute. The source itself acknowledges that an escaped descendant can retain stderr, which is why reader draining has a separate deadline. [Local MCP launcher](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/rmcp-client/src/stdio_server_launcher.rs).

Codex's shared group helper has a Linux `PR_SET_PDEATHSIG` implementation and a no-op on other platforms. macOS group signaling can fall back to individual current group members after permission denial. These functions demonstrate group cleanup, not persistent crash reconciliation or containment of descendants that leave the group. [Process-group helper](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/utils/pty/src/process_group.rs).

The shared command wrapper defaults to direct-child kill/reap on drop; it exposes parent-death setup only under Linux configuration. [Command lifecycle](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/utils/pty/src/child_command.rs). macOS sandbox creation generates arguments for `/usr/bin/sandbox-exec`; scratch lowering includes `/private/tmp` and `/private/var/tmp` access roots. This inspected path solves a different storage problem from Arany's hard-capacity images. [Seatbelt launcher](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/sandboxing/src/seatbelt.rs), [scratch lowering](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/sandboxing/src/seatbelt_scratch.rs).

There is a stronger platform-specific ownership example: Codex's Windows Job Object implementation enables `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; its MCP-specific constructor disables breakaway. This is an OS-managed lifetime mechanism and should not be mistaken for a macOS process-group guarantee. The local launcher also has fallbacks when Windows Job containment is unavailable. [Job Object implementation](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/utils/pty/src/win/job.rs), [launcher](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/rmcp-client/src/stdio_server_launcher.rs).

### Claude Code and sandbox-runtime

Claude Code documents Seatbelt on macOS, writable per-user temporary storage and shell-descendant restrictions. Its built-in file tools, MCP servers and hooks are outside that shell sandbox. This scope differs materially from Arany's guarded command/MCP profile. The documentation does not specify recovery of mounted images or launchd jobs following controller death. [Official sandbox contract](https://code.claude.com/docs/en/sandboxing).

The open library's cleanup registration calls reset on exit, SIGINT and SIGTERM, with additional synchronous deletion of resources still held by that process. Its own comment distinguishes these owned paths from scanning the temp directory or accepting configured paths. This supports retaining explicit ownership, but does not demonstrate a later process recovering earlier owners' resources. [Cleanup registration](https://github.com/anthropics/sandbox-runtime/blob/5507fb0e639c00f845554336ece62e27af5b1bb7/src/sandbox/sandbox-manager.ts#L222).

The macOS wrapper constructs a `sandbox-exec` argument array. The CLI forwards SIGINT/SIGTERM to the command and runs post-command cleanup on child exit. A subtle non-guarantee: closing `--control-fd` input deliberately leaves the command running under its last applied configuration. Only an unusable channel or read error before any update supplies the cited refusal/termination path. Control-channel EOF is therefore not an owner-death cleanup primitive in this CLI. [Wrapper](https://github.com/anthropics/sandbox-runtime/blob/5507fb0e639c00f845554336ece62e27af5b1bb7/src/sandbox/macos-sandbox-utils.ts), [CLI control and exit handling](https://github.com/anthropics/sandbox-runtime/blob/5507fb0e639c00f845554336ece62e27af5b1bb7/src/cli.ts#L379).

### OpenCode and Pi

OpenCode's shell service keeps its process handle inside an Effect scope, starts detached Unix commands, and requests three-second force-kill escalation. Separately, an initial and hourly cleanup scans matching output files and delegates retention. That is real persistent-file housekeeping, but file retention does not prove that a crashed owner's processes are dead or that mounted storage is safe to remove. OpenCode explicitly describes its permissions as user awareness rather than security isolation. [Shell lifecycle and retention](https://github.com/anomalyco/opencode/blob/bcf23b6775c79a429b1511b255d6d88ab0248d4a/packages/core/src/shell.ts), [security contract](https://github.com/anomalyco/opencode/blob/bcf23b6775c79a429b1511b255d6d88ab0248d4a/SECURITY.md).

Pi's local shell launches detached Unix children, records their PIDs in memory and kills on timeout/abort. Its Unix helper signals the group using a negative PID and falls back to the direct child. Interactive SIGTERM/SIGHUP handlers and an uncaught-exception handler call the tracked-child cleanup. This handles several orderly and catchable failure paths; it does not establish cleanup after killing Pi with SIGKILL. [Built-in shell](https://github.com/earendil-works/pi/blob/11f99114506ad2cc759cb389663edaf7546cbe8c/packages/coding-agent/src/core/tools/bash.ts), [PID tracking and kill helper](https://github.com/earendil-works/pi/blob/11f99114506ad2cc759cb389663edaf7546cbe8c/packages/coding-agent/src/utils/shell.ts#L163), [interactive shutdown](https://github.com/earendil-works/pi/blob/11f99114506ad2cc759cb389663edaf7546cbe8c/packages/coding-agent/src/modes/interactive/interactive-mode.ts#L4296).

## Implications for Arany

Apple specifies that SIGKILL cannot be caught or ignored. A Node exit/signal handler therefore cannot cover that failure; neither does Rust code that requires the killed process to execute. A later owner or a surviving independent owner must handle any remaining resources. [Apple signal semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/sigaction.2.html), [Node signal events](https://nodejs.org/api/process.html#signal-events).

Apple also specifies that advisory locks coordinate cooperating processes, that duplicate/forked descriptors reference the same lock, and that the last close releases it. Process exit frees descriptors. This supports a liveness lock only when unintended processes cannot retain it; it does not authenticate persisted cleanup targets. [Apple flock semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html), [Apple close semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/close.2.html).

Arany consequently has a different sequence to verify: exclusive recovery ownership; checked record and root identity; boot separation; exact job retirement and coalition termination; validated backing-image identity and current OS device/mount correspondence; then deletion only after mount absence. The implementation records root/boot before job launch and supervisor identity before payload/storage admission, limits scans and recovery time, leaves uncertain roots intact, and never replays the old Tool intent. These are source/contract observations, not a fresh native test result. [Contract](../specs/tools.md#macos-enforcement-and-compatibility), [unit ownership/recovery](../../crates/arany/src/tools/guard/macos/unit.rs), [storage ownership/recovery](../../crates/arany/src/tools/guard/macos/storage.rs), [boot/process/mount adapters](../../crates/arany/src/tools/guard/macos/ffi.rs).

**Proposed review priorities:** exercise crashes before and after each durable ownership publication, bootstrap and supervisor publication overlap, partial image attachment, recovery interrupted by cancellation/SIGKILL, two competing recoverers, controller lock inheritance, changed image/root identity, reused disk identifiers, and previous-boot records. These cases follow from Arany's effect ordering, not from a peer's popularity. Tests must demonstrate native cleanup and rejection of unrelated resources, including descendants that leave process groups. [Owning contract](../specs/tools.md#macos-enforcement-and-compatibility), [current unit flow](../../crates/arany/src/tools/guard/macos/unit.rs), [current storage flow](../../crates/arany/src/tools/guard/macos/storage.rs).

## Alternatives and limits

These are proposed choices for design discussion, not approved implementation work:

- **Keep bounded admission recovery:** uses the existing Guard boundary and durable records. It permits retained resources until the next admission, and ambiguous/older roots can still require manual inspection. This is the present contract. [Tool contract](../specs/tools.md#macos-enforcement-and-compatibility).
- **Add an independent persistent reaper:** could shorten the interval before cleanup while Arany is stopped, but adds a service lifecycle, authority, installation and its own crash recovery. It still needs the same ownership and mount-validation evidence. This is an architectural inference; none of the compared macOS flows establishes a drop-in equivalent.
- **Use ordinary host temp directories and process groups:** resembles the inspected peers' simpler local execution paths, but does not supply Arany's fixed filesystem capacities or current descendant-containment contract. Adopting it would require an explicit product/security contract decision, rather than a cleanup refactor. [Arany guarantees](../specs/tools.md#macos-enforcement-and-compatibility), [Codex scratch policy](https://github.com/openai/codex/blob/6c372fbef45f730b6d8aa727b0ec8332365588db/codex-rs/sandboxing/src/seatbelt_scratch.rs), [Pi group cleanup](https://github.com/earendil-works/pi/blob/11f99114506ad2cc759cb389663edaf7546cbe8c/packages/coding-agent/src/utils/shell.ts).

## Local design stress test

The following observations concern Arany revision [`bd98941`](https://github.com/fpmirabile/arany/commit/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b), before any resulting redesign. They are distinct from the peer comparison and do not imply approval to change a contract.

- **Demonstrated aggregate-bound mismatch:** admission counts unlocked retained roots and excludes live controllers, with no shared reservation around admission/root creation. Nine controllers can each admit images while the preceding controllers stay alive; if all crash, their eighteen 64-MiB images total 1.125 GiB. Thus the stated 1-GiB retained-image bound is not enforced across benign concurrent processes. This admission behavior predates the recovery PR. A shared admission lock alone is insufficient unless capacity also accounts for live reservations. [Pinned admission/counting implementation](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/unit.rs), [image capacities](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/storage.rs), [claimed bound](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/docs/specs/tools.md).
- **Demonstrated candidate starvation:** recovery takes the first eight unlocked candidates before validating their records. An arbitrary directory order can repeatedly select eight unrecoverable roots while skipping later valid roots. Selecting validated eligible candidates within the bounded scan is a proposed repair; unknown roots must still remain untouched. [Pinned recovery selection](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/unit.rs).
- **Native interruption evidence gap:** the controller-crash fixture finishes storage preparation and then writes an artificial pending marker. It proves recovery of completed mounts and escaped descendants, not death during an actual in-flight attachment. Recovery cancellation at bootout, coalition termination, inventory collection and detach is also not explicitly exercised. The fixture publishes the supervisor record through its test launcher; production supervisor publication needs its own crash-ordering evidence. [Pinned native fixtures](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/unit.rs).
- **Platform uncertainty, not a demonstrated unsafe deletion:** Apple's Disk Arbitration session release removes callbacks from queued requests without deleting those requests; mount execution retains requests across asynchronous completion. Caller death therefore is not a general cancellation barrier. These sources do not establish that an absent kernel image can appear after Arany's empty inventory snapshot: the relevant DiskImages attachment/inventory boundary remains undocumented in the inspected public sources. The installed Apple `hdiutil(1)` manual defines `-kernel` as helper-free attachment and `info` as the current attachment inventory; neither documents a pending-operation barrier. Negative inventory alone needs a justified native guarantee before its comment is treated as proof that an interrupted attach is settled. [Apple queue/session release](https://github.com/apple-oss-distributions/DiskArbitration/blob/main/diskarbitrationd/DAQueue.c#L755), [asynchronous mount execution](https://github.com/apple-oss-distributions/DiskArbitration/blob/main/diskarbitrationd/DARequest.c#L674), [Arany marker cleanup](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/storage.rs).
- **Deadline scope:** Tokio's timeout is cooperative; non-yielding synchronous work can exceed it. Arany's bounded directory/record inspection and final deletion are synchronous. The existing contract excludes hard-real-time and kernel-failure guarantees; recovery should share that explicit scope rather than be read as an interruptible syscall deadline. This is not a measured ordinary-host overrun. [Pinned recovery implementation](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/src/tools/guard/macos/unit.rs), [Tokio 1.53.2 timeout semantics](https://docs.rs/tokio/1.53.2/tokio/time/fn.timeout.html), [existing limit scope](https://github.com/fpmirabile/arany/blob/bd9894147dbb3d79b2250fe9e1ee057585dc5a1b/docs/specs/tools.md).

This is a targeted source comparison, not an exhaustive audit of these products, their hosted/container execution modes, dependency implementations or private desktop services. No fresh crash experiment or platform support claim follows from it. The [Tool acceptance scenarios](../specs/tools.md#acceptance-scenarios-and-evidence-owners) identify the authoritative native evidence owners.

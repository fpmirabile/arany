# Effect Guard platform base

**Date:** 2026-10-04  
**Status:** primary-source research and initial read-only host observations; current implementation/evidence belongs to [local tools](../tools.md)  
**Scope:** functional beta 1 native file tools, build/test commands and local stdio MCP, without a new UX requirement

## Conclusion

Implement one separately privileged same-binary Guard behind immutable typed effects and deterministic restrict-only Policy. Keep trusted native file operations inside that Guard; run command and local-MCP payloads in a separately restricted child. Linux can support useful build/test descendants with installed Bubblewrap plus a private delegated cgroup v2 subtree. Do not substitute approval text, command regexes, process groups, or a no-fork-only command subset for that base. No root installation or desktop-specific product contract is indicated by the inspected host.

The current [security contract](../../agents/security.md#effectful-execution-gate) still governs: requested, authorized and effectively enforced capabilities are different values; the Engine rejects missing required enforcement. Existing [protection research](./deterministic-harness-protection.md) provides the broader threat model, not evidence that these capabilities already exist.

## Source facts that determine the design

- Bubblewrap constructs a namespace environment; its policy is the caller's responsibility. Its empty mount view can expose only selected read-only/runtime and writable/staging objects. Mounting a D-Bus socket can recover host execution authority, and terminal access needs care. [Bubblewrap official README](https://github.com/containers/bubblewrap/blob/v0.13.0/README.md).
- Bubblewrap 0.13.0 accepts opened-object mounts, seccomp programs, explicit namespace setup and a setup barrier. Its implementation closes surplus descriptors, drops setup privileges and verifies disabled nested user namespaces. These facilities need a compiled policy and a trusted bootstrap; a version string or info record alone is not a complete attestation. [Reviewed version's source](https://github.com/containers/bubblewrap/blob/v0.13.0/bubblewrap.c).
- `openat2` supports root-relative lookup without symlinks, magic links or mount crossings; lookup races can reject rather than resolve an escape. [Linux `openat2(2)`](https://man7.org/linux/man-pages/man2/openat2.2.html).
- Hard links alias one inode. A writable live-Workspace bind can therefore change an outside-linked inode even though no outside pathname is visible. Replacing a directory entry with a new inode does not mutate other links to the replaced inode. [Linux `link(2)`](https://man7.org/linux/man-pages/man2/link.2.html), [Linux `rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html).
- Network namespaces isolate protocol stacks and abstract Unix sockets; omitting host pathname sockets and inherited sockets remains separately necessary. [Linux network namespaces](https://man7.org/linux/man-pages/man7/network_namespaces.7.html).
- seccomp is syscall filtering, not a complete sandbox; it cannot dereference argument pointers. Descendants inherit filters. [Kernel seccomp documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html).
- Landlock restrictions compose monotonically and inherit to new descendants. Runtime ABI discovery is mandatory for required rights; already-open file/socket capabilities need independent handling. TCP/UDP port rules do not identify an HTTPS origin or permitted payload. [Kernel Landlock documentation, August 2026](https://docs.kernel.org/userspace-api/landlock.html).
- cgroup v2 provides hierarchical process and memory limits, CPU bandwidth controls, and whole-tree `cgroup.kill`. Delegation and actual controller availability matter. `cpu.max` is bandwidth, not a total CPU-time budget. [Kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html).
- Ordinary resource limits are largely per-process; `RLIMIT_NPROC` counts a real UID's tasks and has privilege exceptions. They supplement, not replace, aggregate Run containment. [Linux `getrlimit(2)`](https://man7.org/linux/man-pages/man2/getrlimit.2.html).
- Namespace init death terminates the namespace's processes. This is a cleanup primitive, not aggregate resource admission. Use a verified namespace owner and cgroup-empty acknowledgement rather than assuming killing the command PID or its process group killed everything. [Linux PID namespaces](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html).

## Two implementable designs

| Design | What it enforces | Trade-off and use |
|---|---|---|
| Same-binary broker for closed operations | Guard accepts only typed bounded file-read/list/create/replace/edit intents against pinned directory handles; independently evaluates the policy and performs the exact operation. It never accepts a shell string or opaque executable as a file operation. | Small portable trusted surface for native tools. A separate process is not itself arbitrary-code containment: generic commands and MCP servers need their own OS restrictions. Trust separation is between credential/state owners, Guard and untrusted payload, not a claim of a different host UID. |
| Same-binary broker plus Bubblewrap command worker and delegated cgroup | Guard prepares the private filesystem, kernel isolation, finite cgroup limits, payload identity, immutable intent and bootstrap acknowledgement before launching arbitrary build/test descendants. Host credential/state roots and sockets remain absent. | Recommended Linux command/local-MCP adapter. Existing namespace constructor avoids new application FFI/unsafe; the policy, resource admission and attestation remain Arany's responsibility. No silent unsandboxed fallback. |

A direct Landlock-only launcher is not equivalent to the second design: it still needs descriptor scrubbing, private filesystem visibility, process-tree supervision and aggregate resources. A remote Linux worker/VM can later implement the same semantic contract, but it introduces additional provisioning and transport authority and is not needed to make progress on this host.

## Filesystem plan: useful writes without a live writable bind

Recommendations, not guarantees supplied by a third-party crate:

1. Admit and pin the caller's Workspace directory identity before project input. Admit StateRoot, account roots, Guard staging and runtime roots independently and reject overlap by opened identities, not string prefixes. Never give an untrusted worker those state/account handles, paths, sockets or parent descriptors.
2. Native reads/listing use bounded handle-relative traversal, no-follow semantics and regular-file checks. Linux should add `NO_XDEV` where the declared policy excludes nested mounts; existing `session/input.rs` rejects symlinks and multi-linked regular files but is not an effect runtime or mount-crossing enforcer.
3. Native writes create an exclusive fresh regular inode in a checked parent, write only bounded normalized bytes, flush as required by the declared durability contract, then replace/create by directory-relative rename. Never truncate an admitted inode in place. Bind exact expected prior content/identity or absence into the intent; a mismatch is a conflict, not permission to overwrite a different object. A multi-file application is not automatically atomic; journal partial/uncertain results precisely.
4. For commands that write source, copy a bounded admitted Workspace tree into a Guard-owned private writable staging filesystem: new regular inodes, bounded entry count/depth/bytes, no links, devices, FIFOs, sockets or nested mounts. Bind the opened staging object rather than reopening a model-supplied host pathname. Staging permits code generation, compilation and test fixtures, not merely read-only commands. After exit, treat every staged output as hostile and apply selected changes through the same typed native writer with prior digests. Do not copy generated symlinks/special files or execute generated objects from privileged host code.
5. A read-only Workspace plus bounded scratch is a valid *named alternative* for reads or tools supporting output-directory flags. It is not a substitute for general writable build/test work. Runtime/toolchain/cache mounts must also exclude keys and configuration carrying authority; do not mount the user's entire home or `.cargo` indiscriminately.

An opened directory can be moved by a separate host process. A handle pins its object, not an eternal pathname location. Define grants by admitted object identity and state clearly that arbitrary concurrent same-user host mutation, bind-mount replacement by a privileged actor, and kernel compromise are outside this base's isolation claim. Untrusted workers must not have operations that relocate host parents or widen mount visibility. Static hostile aliases remain rejected; exclusions are not an excuse for path-prefix checks.

## Command and local-MCP worker contract

Before untrusted code executes, require all of these:

- A trusted executable identity or explicit trusted interpreter policy, explicit argument vector, pinned working directory, bounded stdin, cleared environment and small allowlist. Repository executables and compiler/test descendants are untrusted payload under the same contained grant, never privileged host helpers. Do not interpolate model text into a shell.
- Empty mount namespace exposing only opened read-only runtime/toolchain inputs, admitted staging and finite tmpfs/scratch. No StateRoot, account storage, real user home, host `/proc`, cgroup control files, D-Bus, SSH agent, Docker socket, Wayland/X11 or credential-helper transport.
- Explicit user/mount/PID/network/IPC isolation, dropped capabilities, no-new-privileges, no controlling terminal, disabled and verified nested user namespaces, and an architecture-checked seccomp policy blocking escape primitives while allowing normal build/test process creation. Wrong architectures and unreviewed syscall ABI variants fail closed; do not rely on syscall-number filtering without ABI checks.
- A dedicated owned cgroup containing bootstrap and descendants before payload release, with finite `memory.max`, swap policy, `pids.max`, CPU bandwidth, wall deadline and output/artifact limits. Keep the supervisor outside the payload subtree. Prevent access to writable cgroup/migration handles. A namespace for cgroups is not resource delegation.
- A trusted bootstrap acknowledges the exact intent/policy digest and installed resource/isolation facts on a bounded control channel before release. Separate control provenance from attacker-written stdout/stderr; close control/root/setup handles before payload execution. Test failure of each setup stage. Attestation is about that prepared execution, not a reusable successful self-test.
- Drain stdout/stderr concurrently under aggregate byte ceilings and a complete deadline through EOF/reaping. Overflow, malformed protocol, timeout, cancellation, parent loss or leader exit with remaining descendants follows one cleanup path. Terminate the owned cgroup, wait for empty membership, reap owned children and dispose bounded staging; report uncertainty if completion cannot be proved.

MCP stdio is UTF-8 JSON-RPC framed one object per line; stderr is not protocol output and can contain ordinary diagnostics. [MCP transport specification, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports). Treat discovery descriptions, schemas, results, notifications and server requests as untrusted. Pin reviewed server executable/configuration digests and authorize startup separately: a local server may perform effects before its first tool call. Bind per-server/tool/operation requests to the same deterministic router. A long-lived server's OS authority is its lifetime profile; a claimed per-call restriction needs a narrower freshly spawned worker or a mediated broker, not merely a tool-name check. Do not let server requests for sampling/roots or unknown methods gain Provider or host authority.

The initial offline worker grants no external network or secrets. Network-dependent package installation, remote MCP and command-side authenticated access require separate typed destination **and content** grants plus an enforcing broker; opening port 443 or approving a host name does not implement those grants. Existing Provider transport remains separately credential-isolated and admitted; tool output entering Provider context still needs explicit bounded data-flow policy.

## Current Linux facts, checked read-only

Observed on 2026-10-04, starting at 07:36 UTC, with no cgroup changes, namespace payload execution, service startup, keyring access or secret inspection:

- Kernel `7.2.7-zen1-1-zen`; effective UID `1000`; active LSM list includes `landlock`. Presence does not prove its usable ABI or installed rules.
- Root-owned non-setuid `/usr/bin/bwrap` is `0.13.0`; `setpriv`, `prlimit`, `unshare`, `systemd-run` and `getfattr` are installed. `bwrap --help` exposes opened-object bind options, finite tmpfs size, seccomp input, barriers and strict nested-user-namespace disable/assert options. Trust still requires identity/version review, not PATH search.
- cgroup v2 is mounted. The root is not writable, but that is **not** evidence that user resource containment is unavailable.
- `/proc/self/cgroup` places this research process beneath the current user's service, an application scope and a terminal-tab scope. `user@1000.service` reports `Delegate=yes`, actual delegated controllers `cpu memory pids`, and `user.delegate="1"`; its subtree control and process-admission files are writable. The current application ancestor also reports delegation; the terminal leaf has writable memory/pid/CPU limits and `cgroup.kill`.
- These are **shared terminal/service-manager resources**, not Arany-owned payload groups. Never change their limits, move sibling processes or invoke their kill controls. Obtain a dedicated owned scope/service instead. Systemd 262 is installed; no native macOS runner was used.
- Existing dependencies already expose safe Rustix `openat2`, `memfd_create`, `setrlimit`, `prlimit` and process-management calls. They reduce implementation work, not the need for runtime enforcement tests. `Cargo.toml`, `src/session/input.rs`, `src/terminal/clipboard.rs` and `src/cli/credentials/keyring_helper.rs` were inspected; their current lifecycle patterns are not arbitrary-process sandbox proof.

Systemd specifies single-writer ownership of delegated subtrees and forbids direct mutation of arbitrary manager-owned groups, even when mode bits allow it. A transient user scope/service can request delegation; verify what the kernel actually supplies. Keep this acquisition adapter outside the general cgroup controller. [Systemd delegation contract](https://systemd.io/CGROUP_DELEGATION/). The existing launcher supports transient scopes/services and property requests; scope execution inherits its caller environment, and argument environment expansion must be disabled. [Systemd 262 launcher contract](https://github.com/systemd/systemd/blob/v262/man/systemd-run.xml).

Thus a useful fork-capable offline command/MCP profile has no demonstrated install/root blocker on this host. Dedicated acquisition, limits and cleanup are still an implementation/conformance gate; writable shared ancestors alone are not passing evidence. On another Linux without usable delegation, accept an explicitly supplied owned kernel cgroup capability or a narrowly supported manager adapter; otherwise fail that profile with `ProtectionUnavailable`. Do not silently replace it with per-UID `RLIMIT_NPROC` or promise that every Linux installation has the required kernel/service configuration.

### Transient-service candidate: attestation and complete cleanup

The selected implementation candidate is a same-binary Guard under a unique `systemd-run --user --pipe --wait` transient service, then Bubblewrap for the untrusted worker. This requires no Arany daemon. `--pipe` passes standard descriptors to the service; `--wait` observes service state and jobs, and the client reconnects on bus loss. Killing the client is not proof that its service stopped or its pipes reached EOF. [Systemd 262 implementation](https://github.com/systemd/systemd/blob/v262/src/run/run.c).

Proposed minimal lifecycle:

1. Generate the unit ID from Arany's cryptographic randomness, not Tool text. Invoke reviewed absolute launcher/bootstrap paths with `--no-ask-password`, `--quiet`, `--expand-environment=no` and an explicit safe description. Send intent and task data over the bounded private stdin protocol, not the unit command line, description, journal or environment. Clear the bootstrap's service-manager environment before any payload process; clearing only the launcher's environment does not specify the user manager's service environment.
2. Explicitly request `Type=exec`, `Restart=no`, finite `TimeoutStartSec`, `RuntimeMaxSec` and `TimeoutStopSec`, `KillMode=control-group`, `SendSIGKILL=yes`, `FinalKillSignal=SIGKILL`, `RuntimeRandomizedExtraSec=0`, `RemainAfterExit=no`, memory/swap/tasks limits and CPU quota. Runtime limits exclude activation, and shutdown has its own timeout. Keep the independent Arany complete deadline. [Systemd 262 service lifecycle](https://github.com/systemd/systemd/blob/v262/man/systemd.service.xml), [whole-group termination](https://github.com/systemd/systemd/blob/v262/man/systemd.kill.xml).
3. While the trusted bootstrap is held before payload release, obtain bounded exact `Id`, `InvocationID`, `ControlGroup`, `MainPID`, state and required property values; reject absent, changed or unexpected records. The fixed bootstrap reads its own kernel cgroup membership and actual finite memory/swap/pid/CPU controls, then acknowledges the intent digest and limits. Independently confirm its PID/group corresponds to the requested invocation. Verify the namespace/seccomp facts inside the restricted trusted worker before execution. Manager property requests alone are not effective-capability evidence. The D-Bus interface exposes these lifecycle properties and stop/kill operations. [Systemd 262 manager API](https://github.com/systemd/systemd/blob/v262/man/org.freedesktop.systemd1.xml).
4. Preserve explicit separation between the attestation protocol and tool stdout/stderr. A single-threaded fresh Guard may use existing safe Rustix descriptor/limit calls and standard process APIs, but must close setup capabilities and read no account state before payload execution. This avoids application `pre_exec`/fork FFI and accidental descriptor inheritance from the multithreaded Engine. No native isolation claim follows merely from avoiding application unsafe.
5. On cancellation/overflow/deadline, close the private control writer and request stop of only the retained exact unit. A bounded `systemctl --user stop` follows the configured group-kill ladder; immediate escalation can use the exact unit's all/cgroup kill operation. Check invocation ownership before signaling; never use a prefix pattern, shared ancestor or the user's terminal group. Launcher/stop-command status is only an acknowledgement. Require inactive/failed terminal state plus actual empty owned cgroup, bounded channel EOF and reaped direct children. If manager communication fails, use only an already admitted owned cgroup capability; report uncertain termination rather than kill guessed PIDs or start another copy. [Systemd 262 control CLI](https://github.com/systemd/systemd/blob/v262/man/systemctl.xml).
6. Do not let `--collect` discard the only ownership/result evidence before recording it. Retain the opened cgroup object and bounded receipt through cleanup, or use the manager's explicit invocation reference until observation completes. `ExitType=cgroup` can keep a unit active while descendants remain, but does not replace explicit teardown after a nominal command ends. A malicious program can close its output descriptors while still running; EOF alone is not a terminal receipt. Parent death needs private-control EOF handling plus the finite manager runtime backstop, with adversarial proof of both.

For this candidate, manager-applied limits need not imply `Delegate=yes`: delegation is needed when Arany itself manages a subtree. If selected, put the Guard supervisor in one leaf and the payload in another so a payload limit cannot kill the cleanup owner. Without that split, the Engine remains the external cleanup owner and the whole service's resource budget must include the Guard. Direct raw-cgroup control is simpler only when Arany already owns an explicitly delegated subtree; the current writable Konsole tree is not such an Arany capability. No source check proves the candidate until its real finite service/namespace/descendant/cancellation journey passes.

### Safe-Rust seccomp addition, researched 2026-10-04

The installed Rustix 1.1.5 and Nix 0.29.0 sources expose no safe filter installer. Nix's safe no-new-privileges setters require its `process` feature; Rustix's equivalent requires `thread`, neither currently enabled. Bubblewrap 0.13.0 sets no-new-privileges unconditionally and fails on error. Do not diagnose a missing bit by exact whitespace in `/proc/self/status`. [Bubblewrap setup source](https://github.com/containers/bubblewrap/blob/v0.13.0/bubblewrap.c#L2735-L2737).

Two viable implementation choices remain:

- No new crate: put a fresh same-binary bootstrap **inside** the service, create a filter memfd with existing safe Rustix APIs, serialize bounded classic-BPF fields explicitly, and inherit that FD into Bubblewrap's `--seccomp FD`. A memfd created in the Engine is not transferred automatically by `systemd-run --pipe`; its forwarded descriptors are only stdin/stdout/stderr. This route adds bootstrap/descriptor handoff work and a hand-written policy compiler, so it is not the smallest change to the present post-Bubblewrap helper.
- Recommended for the present helper: Linux-only `seccompiler = { version = "=0.5.0", default-features = false }`. Its safe `apply_filter(&program)` can run in the fresh helper after Bubblewrap setup, before Tokio/threads, `Ready`, native operations or untrusted execution. It installs on the calling thread; later fork/exec descendants inherit it. Installation failure is `ProtectionUnavailable`, never an optional fallback. [Published installer API](https://docs.rs/seccompiler/0.5.0/seccompiler/fn.apply_filter.html), [Linux inheritance contract](https://man7.org/linux/man-pages/man2/seccomp.2.html).

The published normalized manifest has `build = false`, no native library requirement, and only `libc` as a mandatory dependency; JSON/Serde features are unnecessary. Its license is `Apache-2.0 OR BSD-3-Clause`, and its supported Linux targets are little-endian x86-64, AArch64 and RISC-V64. Select an already permitted license and include the normal release notice. The standalone repository was archived in August 2026 because development moved to the Rust-VMM monorepo; pin the **published** crate, not a Git fork. [Published package manifest](https://docs.rs/crate/seccompiler/0.5.0/source/Cargo.toml), [target support](https://docs.rs/seccompiler/0.5.0/seccompiler/), [upstream move](https://github.com/rust-vmm/seccompiler).

Review points: the dependency contains internal FFI/unsafe around `prctl` and `seccomp`, but callers need no application unsafe. The filter memory is alive during the kernel copy; the installer converts its length to `u16`, so Arany must enforce a finite nonempty instruction ceiling before installing, including added instructions. Run the repository's ordinary lockfile, feature, license, source, advisory and build-input checks after admitting the dependency. This source review is not an advisory database clearance or an MSRV/native-runtime pass. [Pinned installer implementation](https://github.com/rust-vmm/seccompiler/blob/v0.5.0/src/lib.rs#L294-L360).

Concrete fixed-profile construction:

1. Use `nix::libc`'s existing re-export for native `SYS_*` and errno constants; no additional direct libc dependency or Nix process feature is needed. Build a constant-size `BTreeMap<i64, Vec<SeccompRule>>`, then `SeccompFilter::new(rules, SeccompAction::Allow, SeccompAction::Errno(EPERM as u32), native_arch)?.try_into()` into `BpfProgram`. An empty vector matches that syscall unconditionally; nonempty rule vectors are OR alternatives, with each rule's conditions ANDed. Never accept arbitrary policy JSON or raw BPF from Tool input. [Compiler API and rule semantics](https://github.com/rust-vmm/seccompiler/blob/v0.5.0/src/backend/filter.rs).
2. Deny the closed profile's escape primitives: `ptrace`, `process_vm_readv/writev`, `pidfd_getfd`, `bpf`, `perf_event_open`, `add_key/request_key/keyctl`, module/kexec operations, `unshare/setns`, and legacy/new mount operations (`mount`, `umount2`, `pivot_root`, `fsopen`, `fsconfig`, `fsmount`, `fspick`, `open_tree`, `move_mount`, `mount_setattr`). Include `open_by_handle_at`, `userfaultfd` and `io_uring_*` in the reviewed attack-surface reduction. Inspect target-specific constants rather than copying x86 numbers; unsupported/unreviewed target profiles fail closed.
3. Preserve ordinary `clone`/fork/thread creation. Deny namespace flags with one OR rule per `CLONE_NEW*` bit: `SeccompCondition::new(0, Dword, MaskedEq(bit), bit)` inside `SeccompRule::new`. Flags are argument zero for the reviewed 64-bit targets. Deny `clone3` separately with `Errno(ENOSYS)`, installed **first**, because its pointer argument cannot be inspected by classic seccomp. Glibc's current internal wrapper falls back to legacy clone specifically for ENOSYS, not arbitrary EPERM; confirm the actual compiler/test descendants remain usable. [Namespace flags UAPI](https://github.com/torvalds/linux/blob/v6.17/include/uapi/linux/sched.h), [Glibc 2.42 fallback](https://github.com/bminor/glibc/blob/glibc-2.42/sysdeps/unix/sysv/linux/clone-internal.c).
4. The compiler emits an audit-architecture check returning `KillProcess` on mismatch, but **does not reject x32**. For each x86-64 program prepend three public `sock_filter` instructions: `LD_W_ABS nr` (`code=0x20,k=0`), `JMP_JSET_K __X32_SYSCALL_BIT` (`code=0x45,k=0x40000000,jt=0,jf=1`), then `RET_K KILL_PROCESS` (`code=0x06`). Remaining jumps stay relative and valid. Bound the combined program and test both sides of the bit check, wrong architecture and negative syscall numbers. Require a reviewed kernel baseline or reject the historical pre-5.4 x32 alias range too. [Pinned architecture generator and public fields](https://github.com/rust-vmm/seccompiler/blob/v0.5.0/src/backend/bpf.rs), [ABI bypass warning](https://man7.org/linux/man-pages/man2/seccomp.2.html).

This default-allow profile is defense in depth against the listed primitives, **not** a complete syscall allowlist or a guarantee against future kernel APIs. Filesystem, network, descriptor and aggregate-resource enforcement remain independent mandatory barriers. Before releasing payload, the trusted helper should record successful fixed-filter installation, its profile digest, `Seccomp=2`, `NoNewPrivs=1`, and zero effective/permitted/inheritable/ambient capabilities. Compare kernel namespace object identities against the independently pinned parent identities, not just a PID of 1/2 or a launcher option list. A pre-existing `Seccomp=2` alone does not prove Arany's filter was installed.

Protect the trusted helper from contained payload memory access with the already enabled safe `rustix::process::set_dumpable_behavior(DumpableBehavior::NotDumpable)` before spawning payload. Blocking the `ptrace` syscall alone does not prevent `/proc/<guard-pid>/mem` file access, which uses a ptrace permission check internally. Do not confuse this with an exclusion claim for hostile host/root processes. [Rustix safe API](https://github.com/bytecodealliance/rustix/blob/v1.1.5/src/process/prctl.rs#L113-L131), [proc memory access](https://man7.org/linux/man-pages/man5/proc_pid_mem.5.html).

Required proof remains a real contained build/test with threads and descendants plus adversarial denied calls, wrong ABI, setup failure and child/exec inheritance, all with parent deadlines and no secret inputs. No filter was installed or OS payload executed by this research task.

## Portable boundary and completion evidence

Keep intent, Policy, journal and lifecycle independent of Linux types; hide namespace/cgroup details inside one platform implementation. Apple documents entitlement-based App Sandbox protection, but that fact does not prove dynamic per-Run arbitrary-tool containment or Linux-equivalent resource/tree guarantees for Arany. [Apple App Sandbox](https://developer.apple.com/documentation/security/app-sandbox) ([machine-readable primary content](https://developer.apple.com/tutorials/data/documentation/security/app-sandbox.json)). A macOS adapter and the same adversarial native corpus remain pending; compile success is not proof, and no automatic unprotected fallback is allowed. Portable typed builtins may be proven independently of an arbitrary-command profile.

The Linux base is complete only after a shipped-binary, private synthetic journey proves useful native create/edit/read, a real build/test with descendants, local MCP initialize/list/call, and strict replay alongside adversarial cases:

- denial before execution, policy intersection, stale/duplicate/mismatched intents and grants, child non-widening;
- outside/sibling/state/account canaries, traversal, every path component type, hard links, mount crossings, concurrent replacement and staged-output revalidation;
- TCP/UDP, host loopback, DNS, pathname/abstract Unix sockets, inherited descriptors and attempted credential access;
- `setsid`/double-fork descendants, limit exhaustion, output floods, idle and in-flight cancellation, supervisor death, cleanup with no survivors and truthful incomplete/uncertain journal prefixes;
- capability setup failure, absent controller/namespace/syscall support, forged stdout attestation, executable/version drift and bounded malformed MCP frames/server requests.

Do not report this research or installed tools as those results. No paid account call, real account mutation, package install, CI change or commit was performed.

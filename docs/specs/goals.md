# Goals

## Scope and delivery boundary

This contract owns durable task-level Goal identity, Run linkage, budget admission, initial Tool-plan timing, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics; [Tools](./tools.md) owns trusted grants and guarded effects; [Session rules](../../agents/session.md), [Engine rules](../../agents/engine.md) and [Store rules](../../agents/store.md) own their respective implementation boundaries.

Optional OTLP records one Goal execution-segment span for each admitted Run. Its child Run span carries only canonical IDs and committed Run facts. The Goal span carries its ID, committed Goal lifecycle and reservation markers, terminal status, known usage, unknown-usage flag and active-time totals. A continuation or explicit resume begins another segment span; trace context is not persisted. Telemetry never carries the objective, plan contract, report, Workspace paths, Tool payloads or Provider content. [Telemetry rules](../../agents/telemetry.md) own export bounds and privacy.

Every accepted task, including `exec`, has one durable Goal. There is no Run-without-Goal path. The Goal owns its pinned budget and resource settings across Runs, long Tool loops, delegation, review and in-Goal compaction. Budgeted execution reserves each actual Provider call and active action at its dispatch boundary. Active-Run Tool-history compaction includes the admitted objective, exact live instruction/include snapshots, current approved plan, typed Goal facts and selected acknowledged observations. Between-Run history compaction uses canonical Goal objective, plan, budget, resource settings, usage facts and history; it does not reconstruct discarded instruction/include contents, and the next Run supplies its newly admitted snapshots. Both request shapes fit the existing 256 KiB compaction input bound. Steering, pause UI, prospective contract revision, complete per-phase/worker context capsules, checkpoint artifacts and rewind remain follow-on Goal behavior and are not implied by this contract's resource changes.

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, admits the Goal lifecycle and the next bounded Run/action envelope with enough terminal-tail capacity, and acquires the OS-user Workspace identity lock for a write-capable Implementation Goal. Each later Provider call and guarded effect receives its own serialized Store/Event headroom admission; there is no up-front reservation proportional to an unlimited Goal budget. The lock is keyed by admitted `(device, inode)`, is shared across separate Session StateRoots and processes, and is not taken by read-only Goals. At most 4,096 identity lock files are retained; quota exhaustion rejects new writers before disclosure or effects. Store byte admission is conservative preflight, not a physical disk reservation.

The live Engine owns that Workspace lock for the entire nonterminal write-capable Goal, including the gaps between Runs when `finish_after_run` is false. Before awaiting the first `GoalStarted` or `GoalResumed` append acknowledgment, Engine takes ownership from provisional admission. If acknowledgment fails, it releases only after a serialized canonical Store view confirms there is no active Goal; an unavailable or active/interrupted view keeps the lease and reports that the user must inspect history before retrying or explicitly resuming. This also covers a dropped Run future after Store enqueue. It releases the lock after the terminal Goal receipt or when the Engine/process exits; explicit recovery reacquires it before Workspace content or Provider disclosure. A different Engine or StateRoot cannot write the same admitted Workspace while the Goal remains live.

`GoalStarted` pins a UUIDv7 identity, objective, Workspace identity, explicit `GoalBudget` and the validated resource settings used for that Goal. Changing saved preferences affects new Goals only; an explicit resume keeps the original pinned values. `GoalRunLinked` names each unique Run and phase before `MessageAccepted`. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged Goal start/resume/link appends and before `MessageAccepted`; a preaccept prefix creates no Run, Provider call or effect. Explicit recovery drops a trailing GoalRunLinked ID with no accepted message, so it consumes no Run budget and is never retried. If the Goal has no accepted Run yet, recovery must preserve the original objective. `GoalResumed` is an explicit user action after reviewing an interrupted Goal; it starts a new Run and never retries the old Provider call or Tool effect. Headless `exec` requires `--session-id` plus `--resume-goal GOAL_ID`; attached startup requires `--resume SESSION_ID --resume-goal GOAL_ID`, or an idle `/resume-goal` confirmation before the next message. The selected ID must match the interrupted Goal in that Session. An ordinary prompt never auto-resumes it. A crash after a first Tool request but before its plan record can resume only when the interrupted Run has no open or uncertain Tool observation; acknowledged read-only inspection history is retained, and the pending plan wait is cleared by `GoalResumed`. Reopening an unfinished Goal projects it as Interrupted. A closed Goal has exactly one terminal status: Completed, Failed or Cancelled, plus a bounded report. A crash or Store failure before that receipt leaves an interrupted prefix rather than a fabricated result.

Initial defaults are at most 64 Provider calls, 16 Runs and 30 minutes of active Goal time; the token dimension is unlimited by default. Settings may explicitly make the Provider-call or active-time dimension unlimited. Finite values remain bounded by the implementation maxima, while each request, Run, Tool, context, Event and native resource limit remains finite. A plan contract may request lower call, token or active-time limits and cannot widen the Goal's pinned settings. Known `ProviderCallRecorded` usage is preserved; missing usage remains unknown. With a finite token ceiling, unknown usage cannot count as zero or authorize another Provider call or effect.

Before each actual Provider dispatch, including primary, child, review and compaction calls, the Engine durably reserves one call after concurrency capacity is available. Store's serialized reducer rejects an over-budget reservation atomically, including racing children; queued calls are not charged. A started or cancelled call remains charged; an unobserved reservation remains uncertain and is not reported as definitely sent. Failure and cancellation never refund call or token usage.

Provider active time begins after Provider concurrency capacity is available. A Tool action's active interval begins only after human approval and shared Guard capacity are available; Engine reserves the bounded interval before Workspace snapshot/cache transfer or native setup, so preparation, payload execution and cleanup count. The interval must cover the unchanged immutable intent's full runtime plus bounded setup, cleanup and terminal work; GO is sent only if that runtime still fits the remaining reservation. Guard `Ready` is not dispatch. If preparation consumes the available interval, the Tool fails before GO and settles observed active time without an effect. Active time is settled using monotonic elapsed time at the acknowledged boundary. A wave of overlapping child calls charges wall time once, not the sum of their runtimes. Provider/Guard capacity waits, human approval waits and pauses are excluded; elapsed Engine acknowledgment/processing time is carried into the next active segment before pausing. If the process exits before settlement, replay retains the unobserved reservation as conservatively charged, uncertain time; explicit resume never restores it. Time while paused or waiting for capacity is not charged.

Tool dispatch preserves enough bounded terminal-tail capacity to record the Tool disposition and Run receipt.

With a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children. It observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage under a finite cap, fails before `ToolRequested`/`ToolStarted` or child admission. A matching Finish at the exact cap may complete if the success criterion is met. Unlimited call or active-time preferences remove only that Goal dimension's ceiling; they do not remove per-action, request, Run-count, Store, Tool or Guard bounds.

Goal report payloads are at most 8 KiB serialized; summary and each listed item are at most 2 KiB, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts. Cache publication and Tool failure/uncertainty facts are recorded before optional positive evidence so a full report cannot silently hide them. If lower-priority facts must be omitted to preserve the byte and item bounds, the report includes an omission notice. A successful Command retains its evidence when cache publication is rejected or fails whenever the report has room; an uncertain cache publication directs recovery to Session history rather than Workspace inspection. Engine truncates a longer model summary at a UTF-8 boundary based on its serialized JSON size, reserving room for those priority facts and the omission notice; it never fabricates successful evidence from a Provider summary. If storage fails before `GoalFinished`, replay leaves the Goal interrupted.

## Initial plan contract and success receipt

Before the first plan, the primary may use bounded Workspace `List`, `Read` and `Search`, an admitted Skill read, or configured bounded MCP catalog listing. These operations can inform the declared scope; MCP catalog listing reveals names only and is not an MCP tool invocation. Every other Tool—including `Command`, Workspace mutations and `McpCall`, even when its catalog advertises `readOnlyHint`—requires a strict `GoalPlanContract` before dispatch. The same actor may inspect in either `RootPlan` or `RootSynthesis`; delegation does not let the primary use an unplanned Tool in synthesis. A contract may be supplied with a prelude inspection, but it is validated, credential-checked and journaled before that call. Schema and Engine admission apply the same rule. A pure read-only task, or a task with no Tool call, can finish with its bounded canonical report and does not invent a writable scope or success criterion. The Goal success gate applies whenever a contract is present.

The contract contains a mission (at most 2,048 bytes), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes and resource at most 512), and at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes and tool at most 128), one typed success criterion, a bounded Goal budget, a `default` or `build` resource class and an optional command timeout. Resource requests are checked against the settings pinned at Goal start and do not widen executable, path, Skill, MCP or network grants. Plan approval latches the requested values; in-range Accept/Auto operation uses those values, while a request above the saved maximum produces a non-dispatched `Limit` receipt that names the requested timeout and pinned maximum and tells the user to lower the request or change `/settings`. The Goal keeps its pinned settings; approval never bypasses the configured maximum, and the existing Ask effect approval remains in force for admitted operations. The immutable Tool intent and Guard receipt carry the exact effective limits. A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the already admitted Skill grant and cannot grant or discover a Skill. The full serialized contract is limited to 8 KiB and receives the ordinary credential-reflection check before persistence, including native wire sibling fields. Missing or invalid contracts reject before non-prelude dispatch. Every requested operation must fit both the contract and the already admitted Tool grant. Research and Plan phase Runs remain limited to the bounded read-only prelude; only Implementation phase Runs can dispatch commands, MCP tool invocations or Workspace mutations. Command admission checks its configured command independently from the writable path scope; returned changeset paths are checked against the path scope. An internal changeset outside that scope is durably recorded as `Denied`, with no Guard receipt or dispatch, and replay rejects any successful or guarded out-of-scope integration. MCP scope identifies both server and tool.

Success criteria are one exact eligible Tool call with the latest matching successful attested receipt (and, for a command with file changes, its successful changeset integration receipt), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB. `tool_call_succeeded` applies to `Command`, `Write`, `Edit`, `Mkdir`, `Skill`, and `McpCall`; read-only `List`, `Read`, `Search`, and `McpList`, plus internal `ApplyChangeset`, cannot be success evidence. A generic successful Read is not sufficient; use a file criterion when verification depends on its contents. For file criteria, replay and live admission use the latest relevant verified read or mutation: a later failed, unattested or uncertain observation, changed digest, deletion or published changeset invalidates the earlier match until a fresh verification succeeds. This remains true across Goal Runs. An exact-content criterion is itself bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until the matching criterion is satisfied. Contract revision is prospective, requires the current mode's approval and a quiescent boundary, and cannot widen the pinned Tool grant; its complete interaction and checkpoint/rewind behavior belong to the follow-on Goal-completion slice.

## Current-format replay and `exec`

Goal Events are additive facts within the current SQLite schema 4 and Event payload version 4; there is no migration or compatibility reader. Saved display and execution preferences use the single strict version 3 `ui-preferences.json` record, limited to 1 KiB; invalid or unsupported records are refused without conversion or overwrite. Replay requires Goal linkage for every accepted task. Histories without required Goal linkage, with missing fields, invalid transitions or exceeded bounds reject intact; they are not upgraded, deleted or interpreted optimistically. Explicit user-confirmed history reset remains governed by the [terminal contract](./terminal.md#setup-and-account-choices).

`exec` creates a Goal for every invocation and keeps its existing text and JSONL channels and terminal exit behavior. JSONL preserves canonical sequence and Event scope while selecting all Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts for exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals; it never assigns a Run ID to a session-scoped Goal Event. A terminal report therefore appears in JSONL without changing its durable Event. On cancellation or crash, neither output channel implies a completion receipt if replay has no terminal Goal Event.

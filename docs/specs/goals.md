# Goals

## Scope and delivery boundary

This contract owns durable task-level Goal identity, Run linkage, budget admission, initial Tool-plan timing, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics; [Tools](./tools.md) owns trusted grants and guarded effects; [Session rules](../../agents/session.md), [Engine rules](../../agents/engine.md) and [Store rules](../../agents/store.md) own their respective implementation boundaries.

Optional OTLP records one Goal execution-segment span for each admitted Run. Its child Run span carries only canonical IDs and committed Run facts. The Goal span carries its ID, committed Goal lifecycle and reservation markers, terminal status, known usage, unknown-usage flag and active-time totals. A continuation or explicit resume begins another segment span; trace context is not persisted. Telemetry never carries the objective, plan contract, report, Workspace paths, Tool payloads or Provider content. [Telemetry rules](../../agents/telemetry.md) own export bounds and privacy.

Every accepted task, including `exec`, has one durable Goal. There is no Run-without-Goal path. The Goal owns its pinned budget and resource settings across Runs, long Tool loops, delegation, review and in-Goal compaction. Budgeted execution reserves each actual Provider call and active action at its dispatch boundary. Active-Run Tool-history compaction includes the admitted objective, exact live instruction/include snapshots, current approved plan, typed Goal facts and selected acknowledged observations. Between-Run history compaction uses canonical Goal objective, plan, budget, resource settings, usage facts and history; it does not reconstruct discarded instruction/include contents, and the next Run supplies its newly admitted snapshots. Both request shapes fit the existing 256 KiB compaction input bound. Goal lifecycle, atomic Provider-call and active-time reservations, the initial plan contract and typed success receipt, bounded reports, cross-StateRoot Workspace writer exclusion, Ctrl+C pause (any cancelled Goal stays Interrupted), coexistence with new prompts and `/goal resume` are delivered. Engine steering delivery, pause boundaries, the terminal steering composer and `/goal pause` are delivered; context reinjection, approved contract revision, checkpoint artifacts and rewind are follow-on Goal behavior, and this contract must not claim those interactions are available.

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, admits the Goal lifecycle and the next bounded Run/action envelope with enough terminal-tail capacity, and acquires the OS-user Workspace identity lock for a write-capable Implementation Goal. Each later Provider call and guarded effect receives its own serialized Store/Event headroom admission; there is no up-front reservation proportional to an unlimited Goal budget. The lock is keyed by admitted `(device, inode)`, is shared across separate Session StateRoots and processes, and is not taken by read-only Goals. At most 4,096 identity lock files are retained; quota exhaustion rejects new writers before disclosure or effects. Read-only Goals and Session history are unaffected. Recovery is manual: with no Arany process running for that OS user, remove the `guard/workspace-locks` directory beneath the account root (`~/Library/Application Support/dev.Arany.arany` on macOS, `~/.local/state/arany` on Linux); the next writer Goal recreates it. Store byte admission is conservative preflight, not a physical disk reservation.

A write-capable Implementation Goal holds the admitted Workspace OS lock only while a Run call is live, including autonomous continuations inside that call. Engine takes ownership from provisional admission before awaiting the first `GoalStarted`, `GoalResumed` or `GoalRunLinked` acknowledgment. The call's lease drops when the call returns, when its future is dropped, or after the terminal Goal receipt, so a paused (Interrupted) Goal holds no writer lock. While the Goal is paused, another Goal in this or another StateRoot may write the admitted Workspace. Explicit recovery reacquires the lock before Workspace content or Provider disclosure and fails with `WorkspaceBusy` while another writer holds it. A failed acknowledgment reports `GoalAdmissionUncertain` when the Goal is committed and otherwise returns the Store error.

`GoalStarted` pins a UUIDv7 identity, objective, Workspace identity, phase, explicit `GoalBudget` and the validated resource settings used for that Goal. Changing saved preferences affects new Goals only; an explicit resume keeps the original pinned values. Starting a Goal seals any unfinished predecessor as Interrupted, so at most one Goal is Running and a predecessor left Running by a crash is paused rather than blocking. `GoalRunLinked` names each unique Run and must repeat the pinned phase before `MessageAccepted`; an explicit resume keeps that phase and never takes one from the client. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged Goal start/resume/link appends and before `MessageAccepted`; a preaccept prefix creates no Run, Provider call or effect. Explicit recovery drops a trailing GoalRunLinked ID with no accepted message, so it consumes no Run budget and is never retried. If the Goal has no accepted Run yet, recovery must preserve the original objective; `--resume-goal ID PROMPT` for such a Goal accepts PROMPT only when it equals that objective (omitting PROMPT resumes it), and any other PROMPT is `GoalUnavailable`. `GoalResumed` is an explicit user action after reviewing an interrupted Goal; it starts a new Run and never retries the old Provider call or Tool effect. Autonomous continuations append no `GoalResumed`. Headless `exec` requires `--session-id` plus `--resume-goal GOAL_ID`; attached startup requires `--resume SESSION_ID --resume-goal GOAL_ID` and resumes at once when no prompt is given; idle chat resumes with `/goal resume`, which needs no further confirmation. An explicit resume whose paused Goal admits no next Run under the rule in Autonomous Goals durably closes it as Failed with its bounded report, returns `GoalBudgetExhausted` and records no `GoalResumed`; the Goal is then not resumable. The reducer accepts this close only for a paused Goal whose budget is exhausted and rejects it while a Run is admissible. A crash-left unfinished Run is sealed as interrupted before this check, so a Goal killed inside its only admitted Provider call closes the same way. The selected ID must be the most recent paused Goal in that Session (the latest Goal that is Running or Interrupted); older paused Goals are history and are not resumable. An ordinary prompt never auto-resumes it; while a Goal is paused, a prompt starts a new Goal. A crash after a first Tool request but before its plan record can resume only when the interrupted Run has no open or uncertain Tool observation; acknowledged read-only inspection history is retained, and the pending plan wait is cleared by `GoalResumed`. Reopening an unfinished Goal projects it as Interrupted; an explicit `GoalResumed` seals an unfinished Running predecessor the same way. A closed Goal has exactly one terminal status: Completed or Failed, plus a bounded report. Cancellation never closes a Goal; it stays Interrupted until explicit resume. A crash or Store failure before that receipt leaves an interrupted prefix rather than a fabricated result.

Initial defaults are at most 64 Provider calls, 16 Runs and 30 minutes of active Goal time; the token dimension is unlimited by default. Settings may explicitly make the Provider-call or active-time dimension unlimited. Finite values remain bounded by the implementation maxima, while each request, Run, Tool, context, Event and native resource limit remains finite. A plan contract may request lower call, token or active-time limits and cannot widen the Goal's pinned settings. Known `ProviderCallRecorded` usage is preserved; missing usage remains unknown. With a finite token ceiling, unknown usage cannot count as zero or authorize another Provider call or effect.

Before each actual Provider dispatch, including primary, child, review and compaction calls, Engine durably reserves one call after concurrency capacity is available. Store's serialized reducer rejects an over-budget reservation atomically, including racing children; queued calls are not charged. A started or cancelled call remains charged; an unobserved reservation remains uncertain and is not reported as definitely sent. Failure and cancellation never refund call or token usage. A call or token budget reached before the next dispatch settles the Run as Failed and finishes the Goal with its report, rather than returning an unrecorded error.

Provider active time begins after Provider concurrency capacity is available. A Tool action's active interval begins only after human approval and shared Guard capacity are available; Engine reserves the bounded interval before Workspace snapshot/cache transfer or native setup, so preparation, payload execution and cleanup count. The interval must cover the unchanged immutable intent's full runtime plus bounded setup, cleanup and terminal work; GO is sent only if that runtime still fits the remaining reservation. Guard `Ready` is not dispatch. If preparation consumes the available interval, the Tool fails before GO and settles observed active time without an effect. Each durable action reservation is capped at 31 minutes to cover the configured 600-second Build command, two bounded cache transfers, preparation, cleanup and Store tail; this is separate from a Goal's default 30-minute usage ceiling. Active time is settled using monotonic elapsed time at the acknowledged boundary. An acknowledged action that exceeds the remaining finite Goal time is recorded and closes the Run/Goal as failed; an unacknowledged result or Store write retains its reservation and uncertainty for explicit recovery. A wave of overlapping child calls charges wall time once, not the sum of their runtimes. Provider/Guard capacity waits, human approval waits and pauses are excluded; elapsed Engine acknowledgment/processing time is carried into the next active segment before pausing. If the process exits before settlement, replay retains the unobserved reservation as conservatively charged, uncertain time; explicit resume never restores it. Time while paused or waiting for capacity is not charged.

Tool dispatch preserves enough bounded terminal-tail capacity to record the Tool disposition and Run receipt.

With a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children. It observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage under a finite cap, fails before `ToolRequested`/`ToolStarted` or child admission. A matching Finish at the exact cap may complete if the success criterion is met; unknown usage does not block a Finish. Unlimited call or active-time preferences remove only that Goal dimension's ceiling; they do not remove per-action, request, Run-count, Store, Tool or Guard bounds.

Goal report payloads are at most 8 KiB serialized; summary and each listed item are at most 2 KiB, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts. Cache publication and Tool failure/uncertainty facts are recorded before optional positive evidence so a full report cannot silently hide them. If lower-priority facts must be omitted to preserve the byte and item bounds, the report includes an omission notice. A successful Command retains its evidence when cache publication is rejected or fails whenever the report has room; an uncertain cache publication directs recovery to Session history rather than Workspace inspection. Engine truncates a longer model summary at a UTF-8 boundary based on its serialized JSON size, reserving room for those priority facts and the omission notice; it never fabricates successful evidence from a Provider summary. If storage fails before `GoalFinished`, replay leaves the Goal interrupted. The report also states `cached_input_tokens`, the total cache-read input tokens across the Goal's Provider calls. Replay requires it to equal the Goal's accumulated cache-read total. It is information only and never changes budgets.

## Autonomous Goals

`GoalStarted` pins an `autonomous` flag. An autonomous Goal's Engine admits its next Run after each Run that ends without finishing the Goal, with no user input. The Run input is the pinned objective; earlier Runs' results and reports are ordinary Session history. Each iteration runs the normal Run admission, budget, linkage and effect rules. A resume with no new text (`GoalRequest::resume`, empty `RunRequest.objective`) also runs the pinned objective. Resume of an autonomous Goal continues this loop. A non-empty resume text is used as before.

A Run that Finishes without the plan's success criterion is a Run boundary while another Run is admissible within the pinned budget. Otherwise the same Finish fails the Run, and the Goal fails with its report. Plain prompts and other non-autonomous Goals keep the single-Run rule. Stop conditions:

- A Finished Run whose success criterion is satisfied, or whose Goal has no plan contract, completes the Goal.
- A Finished Run whose criterion is unsatisfied and whose Runs, Provider calls or known tokens admit no further Run fails the Run, and the Goal fails with its report. The Engine decides these dimensions when the Finish is recorded, so the next Run is never admitted. Active time is decided at settlement, below.
- A Failed Run fails the Goal, as for any Run.
- Cancellation stops the current Run and starts no further Run, for every Goal kind: one-Run prompts as well as autonomous Goals. A Run that already Finished keeps its committed outcome, which the call returns, including when cancellation arrives during the next Run's admission before `MessageAccepted`. The Goal records no terminal receipt and stays open, so reopening it projects it as Interrupted for explicit resume with its pinned objective.
- Any other failure to admit the next Run (Workspace identity or input, Provider selection, request validation, or a Store load or append) also keeps the committed Finished Run. The call returns `StoppedAfterRun` with that Run's outcome and the failure as its reason, so the answer is never lost. The Goal records no terminal receipt and stays open, so reopening it projects it as Interrupted for explicit resume.

Attached `/goal OBJECTIVE` starts an autonomous Goal, and `/goal resume` continues the most recent paused Goal even after newer Goals finished; `/goal` shows its read-only status and names a paused Goal that is not the shown one. Paused and new Goals coexist: a Goal's pause never refuses a plain prompt or `/goal OBJECTIVE`, and starting a Goal does not resume an older one. The [terminal spec](./terminal.md) owns those commands and their notices.

Active time for the next Run is judged when the Finished Run's active time settles, so time spent recording its terminal facts can exhaust the Goal. If that settlement leaves an unsatisfied planned Goal with no admissible next Run, the Finished Run stays committed and the Engine records the autonomous Goal as Failed with its bounded report in the same segment; the call returns `StoppedAfterRun` whose reason is `GoalBudgetExhausted`. "No admissible next Run" is one rule for every dimension: fewer Runs linked than `max_runs`, fewer Provider calls charged than `max_provider_calls`, less active time than `max_active_ms`, and, under a finite token ceiling, known usage with no unknown part and below that ceiling. Replay accepts a Failed receipt over a Finished Run only for an unsatisfied planned Goal that admits no next Run under that rule; a planless or satisfied Goal completes, and any other Failed receipt needs a Failed Run.

## Initial plan contract and success receipt

Before the first plan, the primary may use bounded Workspace `List`, `Read` and `Search`, typed Git status/diff/log reads, an admitted Skill read, or configured bounded MCP catalog listing. These operations can inform the declared scope; MCP catalog listing reveals names only and is not an MCP tool invocation. Every other Tool—including `Command`, Workspace mutations and `McpCall`, even when its catalog advertises `readOnlyHint`—requires a strict `GoalPlanContract` before dispatch. The same actor may inspect in either `RootPlan` or `RootSynthesis`; delegation does not let the primary use an unplanned Tool in synthesis. A contract may be supplied with a prelude inspection, but it is validated, credential-checked and journaled before that call. Schema and Engine admission apply the same rule. A pure read-only task, or a task with no Tool call, can finish with its bounded canonical report and does not invent a writable scope or success criterion. The Goal success gate applies whenever a contract is present.

The contract contains a mission (at most 2,048 bytes), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes and resource at most 512), and at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes and tool at most 128), one typed success criterion, a bounded Goal budget, a `default` or `build` resource class and an optional command timeout. Resource requests are checked against the settings pinned at Goal start and do not widen executable, path, Skill, MCP or network grants. Plan approval latches the requested values; in-range Accept/Auto operation uses those values, while a request above the saved maximum produces a non-dispatched `Limit` receipt that names the requested timeout and pinned maximum and tells the user to lower the request or change `/settings`. The Goal keeps its pinned settings; approval never bypasses the configured maximum, and the existing Ask effect approval remains in force for admitted operations. The immutable Tool intent and Guard receipt carry the exact effective limits. A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the already admitted Skill grant and cannot grant or discover a Skill. The full serialized contract is limited to 8 KiB and receives the ordinary credential-reflection check before persistence, including native wire sibling fields. Missing or invalid contracts reject before non-prelude dispatch. Every requested operation must fit both the contract and the already admitted Tool grant. Research and Plan phase Runs remain limited to the bounded read-only prelude; only Implementation phase Runs can dispatch commands, MCP tool invocations or Workspace mutations. Command admission checks its configured command independently from the writable path scope; returned changeset paths are checked against the path scope. An internal changeset outside that scope is durably recorded as `Denied`, with no Guard receipt or dispatch, and replay rejects any successful or guarded out-of-scope integration. MCP scope identifies both server and tool.

Success criteria are one exact eligible Tool call with the latest matching successful attested receipt (offered only when the catalog admits at least one such call; the schema never contains an empty `anyOf`) (and, for a command with file changes, its successful changeset integration receipt), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB. `tool_call_succeeded` applies to `Command`, `Write`, `Edit`, `Mkdir`, `Skill`, and `McpCall`; read-only `List`, `Read`, `Search`, and `McpList`, plus internal `ApplyChangeset`, cannot be success evidence. A generic successful Read is not sufficient; use a file criterion when verification depends on its contents. For file criteria, replay and live admission use the latest relevant verified read or mutation: a later failed, unattested or uncertain observation, changed digest, deletion or published changeset invalidates the earlier match until a fresh verification succeeds. This remains true across Goal Runs. An exact-content criterion is itself bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until the matching criterion is satisfied. Contract revision is prospective, requires the current mode's approval and a quiescent boundary, and cannot widen the pinned Tool grant; its complete interaction and checkpoint/rewind behavior belong to the follow-on Goal-completion slice.

## Current-format replay and `exec`

Goal Events are additive facts within the current SQLite schema 4 and Event payload version 6; there is no migration or compatibility reader. Saved display and execution preferences use the single strict version 3 `ui-preferences.json` record, limited to 1 KiB; invalid or unsupported records are refused without conversion or overwrite. Replay requires Goal linkage for every accepted task. Histories without required Goal linkage, with missing fields, invalid transitions or exceeded bounds reject intact; they are not upgraded, deleted or interpreted optimistically. Explicit user-confirmed history reset remains governed by the [terminal contract](./terminal.md#setup-and-account-choices).

`exec` creates a Goal for every invocation and keeps its existing text and JSONL channels and terminal exit behavior. A first SIGINT during `exec` cancels its active Run: the Run keeps its Cancelled receipt, the Goal stays open and is projected as Interrupted, and stderr names the resume command `arany exec --session-id SESSION --resume-goal GOAL`. A second SIGINT, SIGTERM or SIGHUP stops waiting after a bounded grace and reports the stop on stderr. A cancelled autonomous loop prints its committed answer before the pause line. A cancelled Run exits unsuccessfully, as before. In JSONL, the stderr reason is `error: Run cancelled`, `error: Run failed`, or `error: Goal paused before completion` for a finished Run whose Goal stays open, and the pause line follows. An exhausted explicit resume exits unsuccessfully with `error: Goal budget is exhausted` and no Run. `exec --goal OBJECTIVE` starts an autonomous Goal; its exit status follows the last Run, so success requires that Run to finish. When an autonomous loop stops after a committed Run for any `StoppedAfterRun` reason, `exec` prints that Run's committed answer, writes `error: Goal stopped after a committed Run: REASON` to stderr and exits unsuccessfully. JSONL preserves canonical sequence and Event scope while selecting all Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts for exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals; it never assigns a Run ID to a session-scoped Goal Event. A terminal report therefore appears in JSONL without changing its durable Event. On cancellation or crash, neither output channel implies a completion receipt if replay has no terminal Goal Event.

## Steering notes and pause

A user may send a steering note to a running Goal, and may pause it at its next boundary. This section fixes the durable fact, its Engine delivery and the pause semantics. The attached terminal composes notes and offers `/goal pause` as specified in the [terminal spec](./terminal.md#interactive-commands-and-completion); `exec` never requests steering.

- A note is the Run-scoped Goal fact `GoalSteeringNoteRecorded` (goal ID, Run ID, text) within the current payload version 6. Replay rejects an agent-scoped or unlinked instance.
- A Run accepts any number of notes. The per-Run bound is 8 KiB (`MAX_USER_MESSAGE_BYTES`) and charges each recorded note its text plus its history label (`MAX_STEERING_LABEL_BYTES`, 8 bytes, the largest `\n[N] ` label for up to 9999 notes), and the waiting note is charged the same way. Rendered labels and notes therefore stay within 8 KiB; the fixed history header is the only other bytes. Each note is non-empty after trimming and within that byte bound. An offer made while another note waits merges into it, separated by a blank line, so the Engine delivers one note; an offer that would exceed the bound is refused and the caller keeps its text.
- A note is accepted only when its Run is the latest and Active, its Goal is Running with that Run active, and the Run's primary AgentRun has an open planning or synthesis provider reservation not yet settled by `ProviderCallRecorded`. A Tool review reserves under the primary AgentRun too, so replay also rejects a note while a Tool observation is pending. Notes before that reservation, after its outcome, during a child reservation, after the Run ends (including after the primary AgentRun finishes), for another Goal or beyond a bound reject replay.
- The Engine takes the waiting note only inside that open reservation, journals it, then adds it to that call; a call that is cancelled before dispatch takes no note. Taking a note reserves its Run's quota. The caller's note waits until the next primary reservation of its submission, including the first primary call of a next autonomous Run; if the submission ends first, the caller keeps it as an ordinary retained draft.
- Every later primary planning or synthesis call of the same Run receives the Run's recorded notes in order, as user input data labelled `steering_notes`; the instruction that applies them is added only when notes are present. Notes never grant permissions, widen Tool authority or revise the plan contract. Child calls and Tool review never receive notes.
- Later Runs carry the notes in their history turn and compaction input under a labelled "Steering notes the user sent during this Run" block; the Engine reserves the bounded context bytes for them. Replay never re-delivers a note. A crash that leaves its Run interrupted keeps the note as history on that Run; an explicit resume starts a new Run with no notes.
- Pause is a sticky request on the caller's steering handle. The Engine turns it into the Run's cancellation only at a boundary: before each primary call, after a valid Tool or Delegate outcome before its plan contract, Tool dispatch or children, before synthesis, before the next autonomous Run, and before each child call or child Tool dispatch (in-flight child calls finish and are recorded). A pause recorded during Tool review or the approval wait stops the Run before dispatch. An in-flight Provider call is never aborted; a Finish it returns still commits. A requested Tool that has not dispatched never starts; its observation records that no operation was dispatched. A paused Run has the same receipts as Ctrl+C: its Run is Cancelled and its Goal Interrupted and resumable; a pause between autonomous Runs keeps the committed Finished Run and leaves the Goal Interrupted.

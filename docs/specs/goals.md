# Goals

## Scope and delivery boundary

This contract owns durable task-level Goal identity, Run linkage, budget admission, initial Tool-plan timing, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics; [Tools](./tools.md) owns trusted grants and guarded effects; [Session rules](../../agents/session.md), [Engine rules](../../agents/engine.md) and [Store rules](../../agents/store.md) own their respective implementation boundaries.

Optional OTLP records one Goal execution-segment span for each admitted Run. Its child Run span carries only canonical IDs and committed Run facts. The Goal span carries its ID, committed Goal lifecycle and reservation markers, terminal status, known usage, unknown-usage flag and active-time totals. A continuation or explicit resume begins another segment span; trace context is not persisted. Telemetry never carries the objective, plan contract, report, Workspace paths, Tool payloads or Provider content. [Telemetry rules](../../agents/telemetry.md) own export bounds and privacy.

Every accepted task, including `exec`, has one durable Goal. There is no Run-without-Goal path. Foundation delivers Goal lifecycle, atomic Provider-call and active-time reservations, the initial plan contract and typed success receipt, bounded reports, and cross-StateRoot Workspace writer exclusion. Steering and pause UI, context reinjection, approved contract revision, checkpoint artifacts and rewind are follow-on Goal behavior; the Foundation slice must not claim those interactions are available.

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, admits the bounded Event capacity for the remaining Goal budget and acquires the OS-user Workspace identity lock for a write-capable Implementation Goal. The lock is keyed by admitted `(device, inode)`, is shared across separate Session StateRoots and processes, and is not taken by read-only Goals. At most 4,096 identity lock files are retained; quota exhaustion rejects new writers before disclosure or effects. Store byte admission is conservative preflight, not a physical disk reservation.

The live Engine owns that Workspace lock for the entire nonterminal write-capable Goal, including the gaps between Runs when `finish_after_run` is false. Before awaiting the first `GoalStarted` or `GoalResumed` append acknowledgment, Engine takes ownership from provisional admission. If acknowledgment fails, it releases only after a serialized canonical Store view confirms there is no active Goal; an unavailable or active/interrupted view keeps the lease and reports that the user must inspect history before retrying or explicitly resuming. This also covers a dropped Run future after Store enqueue. It releases the lock after the terminal Goal receipt or when the Engine/process exits; explicit recovery reacquires it before Workspace content or Provider disclosure. A different Engine or StateRoot cannot write the same admitted Workspace while the Goal remains live.

`GoalStarted` pins a UUIDv7 identity, objective, Workspace identity and explicit `GoalBudget`. `GoalRunLinked` names each unique Run and phase before `MessageAccepted`. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged Goal start/resume/link appends and before `MessageAccepted`; a preaccept prefix creates no Run, Provider call or effect. Explicit recovery drops a trailing GoalRunLinked ID with no accepted message, so it consumes no Run budget and is never retried. If the Goal has no accepted Run yet, recovery must preserve the original objective. `GoalResumed` is an explicit user action after reviewing an interrupted Goal; it starts a new Run and never retries the old Provider call or Tool effect. Headless `exec` requires `--session-id` plus `--resume-goal GOAL_ID`; attached startup requires `--resume SESSION_ID --resume-goal GOAL_ID`, or an idle `/resume-goal` confirmation before the next message. The selected ID must match the interrupted Goal in that Session. An ordinary prompt never auto-resumes it. A crash after a first Tool request but before its plan record can resume only when the interrupted Run has no open or uncertain Tool observation; acknowledged read-only inspection history is retained, and the pending plan wait is cleared by `GoalResumed`. Reopening an unfinished Goal projects it as Interrupted. A closed Goal has exactly one terminal status: Completed, Failed or Cancelled, plus a bounded report. A crash or Store failure before that receipt leaves an interrupted prefix rather than a fabricated result.

Initial finite defaults are at most 64 Provider calls, 16 Runs and 30 minutes of active Goal time. Each dispatched Run reserves no more than five minutes of that total. A Plan contract may request lower limits and an optional token ceiling; it cannot widen the pinned Goal budget. A caller may explicitly choose an unlimited token dimension. Known `ProviderCallRecorded` usage is preserved; missing usage remains unknown. With a token ceiling, unknown usage cannot count as zero or authorize another Provider call or effect. Before each Run dispatch, Engine durably reserves its finite active-time segment. At an acknowledged boundary it settles the reservation with monotonic elapsed time. Plan-contract append acknowledgment latency stays within the narrowed active interval. If the process exits before settlement, replay retains the reservation as conservatively charged, uncertain time; explicit resume never restores it. Time outside a dispatched Run is not charged.

Before every actual Provider dispatch charged to a Goal, including primary, child, Tool review and an in-Goal compaction call, Engine durably reserves one call. Store's serialized reducer rejects an over-budget reservation atomically, including racing child callers. Queued children do not consume a call until concurrency capacity is available. A started or cancelled call remains charged; an unobserved reservation remains uncertain and is not reported as definitely sent. Failure and cancellation never refund call or token usage. Tool dispatch preserves the bounded terminal-tail budget needed to record the Tool disposition and Run receipt.

With a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children. It observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage under a finite cap, fails before `ToolRequested`/`ToolStarted` or child admission. A matching Finish at the exact cap may complete if the success criterion is met.

Goal report payloads are at most 8 KiB serialized; summary and each listed item are at most 2 KiB, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts. It truncates a longer model summary at a UTF-8 boundary and includes an unresolved notice; it never fabricates successful evidence from a Provider summary. If storage fails before `GoalFinished`, replay leaves the Goal interrupted.

## Initial plan contract and success receipt

Before the first plan, the primary may use bounded Workspace `List`, `Read` and `Search`, an admitted Skill read, or configured bounded MCP catalog listing. These operations can inform the declared scope; MCP catalog listing reveals names only and is not an MCP tool invocation. Every other Tool—including `Command`, Workspace mutations and `McpCall`, even when its catalog advertises `readOnlyHint`—requires a strict `GoalPlanContract` before dispatch. The same actor may inspect in either `RootPlan` or `RootSynthesis`; delegation does not let the primary use an unplanned Tool in synthesis. A contract may be supplied with a prelude inspection, but it is validated, credential-checked and journaled before that call. Schema and Engine admission apply the same rule. A pure read-only task, or a task with no Tool call, can finish with its bounded canonical report and does not invent a writable scope or success criterion. The Goal success gate applies whenever a contract is present.

The contract contains a mission (at most 2,048 bytes), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes and resource at most 512), and at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes and tool at most 128), one typed success criterion and a bounded Goal budget. A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the already admitted Skill grant and cannot grant or discover a Skill. The full serialized contract is limited to 8 KiB and receives the ordinary credential-reflection check before persistence, including native wire sibling fields. Missing or invalid contracts reject before non-prelude dispatch. Every requested operation must fit both the contract and the already admitted Tool grant. Research and Plan phase Runs remain limited to the bounded read-only prelude; only Implementation phase Runs can dispatch commands, MCP tool invocations or Workspace mutations. Command admission checks its configured command independently from the writable path scope; returned changeset paths are checked against the path scope. MCP scope identifies both server and tool.

Success criteria are one exact eligible Tool call with the latest matching successful attested receipt (and, for a command with file changes, its successful changeset integration receipt), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB. `tool_call_succeeded` applies to `Command`, `Write`, `Edit`, `Mkdir`, `Skill`, and `McpCall`; read-only `List`, `Read`, `Search`, and `McpList`, plus internal `ApplyChangeset`, cannot be success evidence. A generic successful Read is not sufficient; use a file criterion when verification depends on its contents. For file criteria, replay and live admission use the latest relevant verified read or mutation: a later failed, unattested or uncertain observation, changed digest, deletion or published changeset invalidates the earlier match until a fresh verification succeeds. This remains true across Goal Runs. An exact-content criterion is itself bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until the matching criterion is satisfied. Plan changes are not available in Foundation; approved prospective revision and its mode interaction are owned by the follow-on Goal behavior.

## Current-format replay and `exec`

Goal Events are additive facts within the current SQLite schema 4 and Event payload version 3; there is no migration or compatibility reader. Replay requires Goal linkage for every accepted task. Histories without required Goal linkage, with missing fields, invalid transitions or exceeded bounds reject intact; they are not upgraded, deleted or interpreted optimistically. Explicit user-confirmed history reset remains governed by the [terminal contract](./terminal.md#setup-and-account-choices).

`exec` creates a Goal for every invocation and keeps its existing text and JSONL channels and terminal exit behavior. JSONL preserves canonical sequence and Event scope while selecting all Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts for exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals; it never assigns a Run ID to a session-scoped Goal Event. A terminal report therefore appears in JSONL without changing its durable Event. On cancellation or crash, neither output channel implies a completion receipt if replay has no terminal Goal Event.

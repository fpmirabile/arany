# Goals

## Scope and delivery boundary

This contract owns durable Goal identity, Run linkage, budget admission, optional plan recording, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics, [Tools](./tools.md) owns grants and guarded effects, [Session](./session.md) owns the conversation boundary and [telemetry](./telemetry.md) owns Goal segment telemetry. Editing constraints: [security rules](../../agents/security.md). Native evidence gaps are tracked in [NEXT_STEPS.md](../../NEXT_STEPS.md#beta-2-and-broader-release).

Every accepted task, including `exec`, has one durable Goal; no Run exists without a Goal. The Goal owns its pinned budget and resource settings across Runs, Tool loops, delegation, review and in-Goal compaction. Budgeted execution reserves each Provider call and active action at its dispatch boundary.

Active-Run Tool-history compaction includes the admitted objective, the exact live instruction and include snapshots, the current approved plan, typed Goal facts and selected acknowledged observations. Between-Run compaction uses the canonical objective, plan, budget, resource settings, usage facts and history; it does not reconstruct discarded instruction or include contents, and the next Run supplies fresh snapshots. Both fit the [generated compaction input limit](./limits.md#max_compaction_input_bytes).

Guarded code rewind, replay and evidence invalidation follow the [rewind contract](./tools.md#checkpoints-and-rewind). Context reinjection and approved contract revision are not available.

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, and admits the Goal lifecycle and the next bounded Run or action envelope with enough terminal-tail capacity. A write-capable Implementation Goal also acquires the OS-user Workspace identity lock. Each later Provider call and guarded effect gets its own serialized Store and Event headroom admission; nothing is reserved up front in proportion to an unlimited Goal budget. Store byte admission is a conservative preflight, not a disk reservation.

The Workspace lock is keyed by admitted `(device, inode)` and shared across Session StateRoots and processes; read-only Goals do not take it. At most the [generated Workspace lock-file quota](./limits.md#max_workspace_lock_files) is retained. At the quota, new writers are rejected before disclosure or effects; read-only Goals and Session history are unaffected. Recovery is manual: with no Arany process running for that OS user, remove `guard/workspace-locks` beneath the account root (`~/Library/Application Support/dev.Arany.arany` on macOS, `~/.local/state/arany` on Linux); the next writer recreates it.

A writer holds the lock only while a Run call is live, including autonomous continuations inside that call. Engine owns the lease from provisional admission, before awaiting the first `GoalStarted`, `GoalResumed` or `GoalRunLinked` acknowledgment. The lease drops when the call returns, when its future is dropped or after the terminal receipt, so a paused Goal holds no lock. Explicit recovery reacquires it before Workspace or Provider disclosure and fails with `WorkspaceBusy` while another writer holds it. A failed acknowledgment reports `GoalAdmissionUncertain` when the Goal is committed and otherwise returns the Store error.

- `GoalStarted` pins a UUIDv7 identity, objective, admitted include paths, Workspace identity, phase, explicit `GoalBudget`, validated resource settings and `continues` (the source of a [continuation](#budget-continuation), or null). Saved-preference changes affect only new Goals. Settings changes, continuation Runs and explicit resume never recalculate an admitted Goal. Starting a Goal seals any unfinished predecessor as Interrupted, so at most one Goal is Running; a crash-left predecessor is paused, not blocking.
- Goal admission snapshots the controller's positive available logical core count once. Automatic Build CPU cores and jobs each use that count; separate explicit positive preferences may lower either, and `max_processes` caps jobs only. If cores are unavailable, zero or unrepresentable, or a preference exceeds cores, the affected setting is null and Build plans are refused without a payload or host probe; ordinary operations remain available. Each Build command inherits positive `intent.limits.build_cpu_cores` and `intent.limits.build_jobs` through the ledger, and reducer validation binds both to the admitted settings. [Tools](./tools.md#limits-and-failure-behavior) owns Linux quota enforcement and the macOS supervised-threshold difference.
- `GoalRunLinked` names each unique Run and repeats the pinned phase before `MessageAccepted`; explicit resume keeps the stored phase, never a client-supplied one. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged start, resume and link appends and before `MessageAccepted`; such a pre-accept prefix creates no Run, Provider call or effect.
- Resume is explicit. `GoalResumed` follows the user's review of an interrupted Goal and starts a new Run; it never retries the old Provider call or Tool effect. Autonomous continuations append no `GoalResumed`. Recovery drops a trailing `GoalRunLinked` with no accepted message; it consumes no Run budget and is never retried. If no Run was accepted, `--resume-goal ID PROMPT` accepts PROMPT only when it equals the preserved objective, omitting PROMPT resumes it, and any other PROMPT is `GoalUnavailable`. Headless `exec` resumes with `--session-id` and `--resume-goal GOAL_ID`; attached startup uses `--resume SESSION_ID --resume-goal GOAL_ID` and resumes at once without a prompt; idle chat uses `/goal resume` without confirmation. Only the Session's most recent Running or Interrupted Goal is resumable; older paused Goals are history. A prompt never auto-resumes; while a Goal is paused, a prompt starts a new Goal.
- If a paused Goal admits no next Run under [Autonomous Goals](#autonomous-goals), explicit resume closes it Failed with its bounded report, returns `GoalBudgetExhausted` and records no `GoalResumed`; the Goal is then not resumable. The reducer accepts this close only for a paused, budget-exhausted Goal. A crash-left unfinished Run is sealed as interrupted before this check. After a crash between a `plan_recorded` Provider call and its contract Event, resume is allowed only when the interrupted Run has no open or [Uncertain](./execution.md#effect-outcomes) Tool observation; `GoalResumed` clears the pending plan wait and keeps acknowledged read-only history.
- Reopening an unfinished Goal projects it as Interrupted; explicit `GoalResumed` seals an unfinished Running predecessor the same way. A closed Goal has exactly one terminal status, Completed or Failed, with a bounded report. Cancellation never closes a Goal; it stays Interrupted until explicit resume. A Run [stopped by a hook](./execution.md#accepted-outcomes) also leaves its Goal open: resume is explicit and subject to budget and uncertainty admission, and an autonomous Goal never continues after it. A crash or Store failure before the receipt leaves an interrupted prefix, never a fabricated result.

New Goals in attached chat, `exec` and `serve` default to unlimited Provider calls, tokens and active time, with at most [the generated Goal Run limit](./limits.md#max_goal_runs) Runs. This follows Claude Code's [unlimited interactive turns](https://code.claude.com/docs/en/cli-reference#cli-flags), Codex's [default-disabled rollout token budget](https://github.com/openai/codex/blob/342ed69a174c206c1de52a59491b131e0753cfa5/codex-rs/features/src/lib.rs#L1975-L1980) and OpenCode's [optional step limit](https://opencode.ai/docs/agents/#max-steps), including headless execution. There is no aggregate dollar-spend guarantee. Settings may select finite limits and show unlimited dimensions as unlimited; pause, cancellation, usage accounting and pinned-budget resume apply either way. Finite Provider-call and active-time values are bounded by the [generated Goal maxima](./limits.md#max_goal_provider_calls) and [active-time maximum](./limits.md#max_goal_active_ms). An unlimited dimension removes only that Goal ceiling; per-action, request, Run-count, context, Event, Store, Tool, Guard and native bounds stay finite. A plan contract may lower call, token or active-time limits and never widens the pinned settings. Replay checks a contract's active-time limit against settled Runs only; the Engine also counts the live Run's in-memory time. Known `ProviderCallRecorded` usage is preserved and missing usage stays unknown. Under a finite token ceiling, unknown usage never counts as zero and never authorizes another Provider call or effect.

The Store-action margin is 5,000 ms<!-- unrelated-bound: Goal Store-action margin -->.

Goal exhaustion projects onto the latest accepted Run when `GoalFinished.exhausted` is true, or when an interrupted Run's committed counts prove the budget spent, subject to [accepted-outcome precedence](./execution.md#accepted-outcomes). Projection ignores a trailing unaccepted Run link and uses the committed refusal dimension when present, otherwise settled facts. The effective finite limit at refusal is chosen in this order: tokens when known usage reaches the ceiling or usage is unknown; calls when charged calls reach the ceiling; active time when remaining time is within the Store-action margin; otherwise Runs.

Before each Provider dispatch (primary, child, review or compaction), once concurrency capacity is available, Engine durably reserves one call. Store's serialized reducer atomically rejects an over-budget reservation, including from racing children; queued calls are not charged. A started or cancelled call stays charged, and an unobserved reservation is [Uncertain](./execution.md#effect-outcomes), never reported as definitely sent. Failure and cancellation never refund call or token usage. Reaching a call or token budget before the next dispatch settles the Run as Failed and finishes the Goal with its report, never an unrecorded error. Compaction calls use the Session compaction output bound and charge reported input, output and cache usage to this ledger; the larger summary allowance grants no extra budget.

Provider active time begins once Provider concurrency capacity is available. A Tool action's interval begins only after human approval and shared Guard capacity are available. Engine reserves the bounded interval before Workspace snapshot, cache transfer and native setup, so preparation, pre-GO checkpoint capture, payload execution and cleanup all count. The interval covers the immutable intent's full runtime plus bounded setup, cleanup and terminal work; GO is sent only if that runtime still fits the remaining reservation. Guard `Ready` is not dispatch. If preparation consumes the interval, the Tool fails before GO and settles its observed time without an effect. Active time settles on monotonic elapsed time at the acknowledged boundary. An acknowledged action that exceeds the remaining finite Goal time is recorded and fails the Run and Goal. Overlapping child calls charge wall time once. Provider and Guard capacity waits, approval waits and pauses are excluded; Engine processing time before a pause carries into the next active segment. [Execution](./execution.md#researcher-children) owns the delegation segment and pending child Ask withdrawal.

Per-action reservations and settlements live in Engine memory. The journal records active time per Run and persists refused quantities in the [budget refusal snapshot](#budget-refusal-feedback). `RunStarted` pins `active_deadline_ms`, the Goal's remaining effective active time at Run start (null when unlimited). `RunFinished` records the Run's settled `active_ms`, which replay adds to the Goal. Each action-start Event (`GoalProviderCallReserved`, `GoalCompactionCallReserved`, `ToolProposed`, `ToolStarted`, `ToolActiveTimeReserved` and every lifecycle `HookStarted`) records `active_ceiling_ms`: the Run's settled time plus that action's reservation, which also covers a reviewed Tool's later review call. A between-Run Goal compaction reserves at most its 120-second<!-- unrelated-bound: Engine compaction call deadline --> call plus the Store tail within the remaining Goal time, records that as its ceiling and journals its settled time in `ContextCompacted.active_ms`, which replay charges to the Goal.

If the process exits before settlement, replay charges the latest ceiling, capped by the Run's deadline and any later plan contract, as conservative uncertain time. A crash thus charges only the open action, not the rest of the Run's deadline, so explicit resume continues while time remains; resume never restores that charge. A multi-call step commits all intents, then commits `ToolActiveTimeReserved` for each primary call before its hooks, review or dispatch. That refresh uses the Run's consumed time plus the call's action and hook bound; a later call's shorter intent ceiling never replaces the executing action's bound, and earlier calls stay charged after a crash. Researcher Tools are covered by their delegation reservation.

A primary Tool batch reserves Event and observation capacity for every call before its first intent (`Action::ToolStep { calls }`). Each call keeps its `Action::Tool` terminal, integration, Supervisor and review headroom, and admission keeps drain headroom for every editor holding a lease. Researchers keep their `Action::Child` admission. A review call spends the Tool admission and is not admitted again. Admission adds `chain_len - 1` switch slots and three same-route retry facts per call of its role, including child waves and review calls, as [execution](./execution.md#researcher-children) bounds them. `Action::max_events_for` includes these and terminal headroom under the [Session Event cap](./execution.md#persistence-bounds). Tool dispatch keeps enough terminal-tail capacity to record the Tool disposition and Run receipt.

Provider roles, all selected [roster candidates](./provider.md#named-roster-presets) and fallback attempts share this ledger; profile count creates no separate budget. Explicit roster-bound recovery follows the [same-selection rule](./session.md#roster-recovery-and-compaction). A committed `ProviderFallbackUsed` or `ProviderRetryScheduled` charges one more call while keeping the open step reservation and its active-time ceiling; a retry's wait counts as active time. Failed-call usage stays unknown, so a finite token budget refuses a replacement attempt; unlimited tokens do not make failed calls free. The final successful attempt contributes only its reported usage and cache counters. After protected usage and cache-uncertainty facts, and before optional positive evidence, the Goal report keeps at most eight retry (role, attempt, cause, delay) and fallback (role, from, to) notices with a warning that failed calls may have consumed usage; further notices produce the ordinary omission marker. A post-Goal manual compaction never amends a closed Goal's usage or receipt. [Provider selection](./provider.md#per-role-selection-and-fallback) and [switch replay](./execution.md#admission-persistence-and-recovery) own other routing rules.

Under a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children, and observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage, fails before `ToolRequested`, `ToolStarted` or child admission. An answer at the exact cap may complete if the success criterion is met; unknown usage does not block an answer. When a finite Provider-call budget leaves exactly one charged call and the primary plans or synthesizes with no active child, that last call is answer-only: the request keeps its Tool list for cache stability, disables Tools (`tool_choice: none` or the Messages equivalent) and carries a fixed `harness_final_call` data block asking for the budget-reached status, the work done, what remains and the next step. This follows OpenCode's [last-step answer](https://github.com/anomalyco/opencode/blob/b6c43a524265496086fc0fdd83180bfa47d4d22e/packages/core/src/session/runner/llm.ts#L225-L244). It is the last call inside the budget, not an extra one: the answer commits normally, a planless Goal completes, and the report adds the unresolved fact `Provider-call budget reached; the final call was answer-only.`, derived from committed counts. Token and active-time ceilings keep no wrap-up call.

Goal reports are bounded by the [generated Goal report limit](./limits.md#max_goal_report_bytes); the summary and each listed item are at most 2 KiB<!-- unrelated-bound: Goal report item cap -->, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts, and never fabricates success evidence from a Provider summary. Skipped checkpoint capture, pruning notices, cache publication and Tool failure or uncertainty facts precede optional positive evidence, so a full report cannot hide them; omitted lower-priority facts produce an omission notice. A successful Command keeps its evidence when cache publication is rejected or fails, if room remains; an uncertain cache publication directs recovery to Session history, not Workspace inspection. A longer model summary is truncated at a UTF-8 boundary, leaving room for priority facts and the omission notice. If storage fails before `GoalFinished`, replay leaves the Goal interrupted. The report states `cached_input_tokens`, the total cache-read input tokens across the Goal's Provider calls; replay requires it to equal the accumulated total. It is informational and never changes budgets.

### Budget refusal feedback

`GoalFinished.budget_refusal` is required and nullable. Every budget-caused closure, including an out-of-budget resume or failed next-Run admission that closes an existing Goal, carries a non-null `BudgetRefusal`; other closures carry null, as do closures recorded before the field existed, whose refused quantities are unavailable. The record never changes charges or grants a continuation. Exhaustion allows no extra Provider call, retry, fallback or compaction to explain it. A committed answer stays intact; cancellation, hook stops and unknown effects keep [Execution precedence](./execution.md#accepted-outcomes). A Provider failure on the final allowed attempt stays a Provider failure unless a separate budget boundary stops the Run. A delegation-only deadline or a recoverable Tool timeout or runtime refusal is not Goal exhaustion.

The closed record contains `dimension` (`tokens`, `calls`, `active_time`, `runs`), `cause` (`exhausted`, `unknown_usage`, `insufficient_headroom`), `action` (`provider`, `tool`, `delegation`, `compaction`, `run`, `resume`), required nullable `run_id` and `agent_run_id`, unsigned `used` and finite `limit`, independently nullable `requested` and `required_minimum`, `token_usage_unknown`, and `charge_basis` (`observed`, `conservative`). The charge basis is `conservative` exactly when recovered or in-flight token usage is unknown or the Goal carries uncertain or unsettled active time, and `observed` otherwise. IDs belong to the Goal and actor; Run and resume admission have null IDs. Counts use units, tokens use known charged tokens with explicit unknown usage, and active time uses milliseconds. The serialized record is bounded by the [generated budget-refusal limit](./limits.md#max_budget_refusal_bytes) and contains no paths, arguments or free text. `requested` is unclamped and present only when captured at admission; unknown next-call token demand gets no invented reservation. The minimum active admission is carried processing time plus the [Store-action margin](#lifecycle-budgets-and-recovery) plus one millisecond of useful headroom; a zero-duration Tool pause or delegation boundary needs only carried processing plus one millisecond. Reaching that margin below the ceiling is insufficient headroom, not exhaustion.

Engine captures the refusal under serialized ledger admission and carries it through Run settlement without refund or double charge. `GoalFinished` follows the Run's terminal facts in reserved terminal capacity. `used` is usage at refusal, labelled separately from final settled usage. Reducer validation checks the pinned effective finite limit, actor membership, cause, arithmetic, unknown and conservative qualifications and the final committed usage bound; snapshot active usage cannot exceed final settlement. Strict replay reads these facts without dispatch. Before Goal admission or a terminal acknowledgment, only a bounded local admission or infrastructure diagnostic may describe available values; a refused idle compaction without a Goal closure also uses it. If a failed terminal append is proved absent, its refusal details are labelled uncommitted; if it may have committed, `GoalAdmissionUncertain` requires inspecting Session history without claiming absence. A failed or lost acknowledgment never authorizes a fabricated receipt; reopening exposes the committed prefix and conservative recovery facts, with missing refusal detail marked unavailable. A budget-failed Run without a Goal receipt keeps its stop semantics and shows only proved committed counters, excluding unaccepted links.

`exec`, `show`, serve, ACP and attached autonomous Goals share one committed Goal/Run status projection; attached chat shortens a plain Goal's stop as [Terminal](./terminal.md#interactive-commands-and-completion) defines. It names the actual dimension, pinned limit, used-at-refusal, known requested and minimum quantities, unknown tokens, Store margin and conservative charges. The report keeps at most eight recent failed, denied, conflicted or limited Tool facts across primary and children, newest first, with actor and compiled Tool labels, available exit and limit codes, bounded admitted excerpts and an omission count. Unknown and blocking facts precede optional Tool detail. Denial summaries use compiled labels, never raw hook or client reasons or permission rules; excerpts use shared control and bidi escaping within the 2 KiB<!-- unrelated-bound: Goal report item cap --> item and generated Goal report bounds. Overflow drops optional details, never the terminal cause. This follows [Codex's typed failed/declined items](https://developers.openai.com/codex/app-server#approvals) and [Claude's specific Tool failures](https://code.claude.com/docs/en/hooks#posttoolusefailure) under Arany's durable budget. Reports are Arany status, never assistant `MessageCommitted` text; JSONL stays canonical Events.

The shared `budget_refusal_feedback` lookup requires a committed refusal record. After an exhausted resume, `exec` falls back to its looser admission-refusal predicate and formats the selected budget-stopped Run's committed facts. Committed output receipts format their exact Run, so another Run in the same Goal cannot supply its answer or stop text.

## Worker accounting and verification

Each [editor](./execution.md#worker-journal-protocol) requires Implementation, a committed plan and a write-capable parent; its lease and catalog intersect parent, plan and definition. The Goal's Workspace writer lock covers editor work and primary verification, and editor work uses the shared [call and active-time accounting](#lifecycle-budgets-and-recovery).

Goal and editor criteria are distinct. Satisfying the Goal criterion does not waive the [worker journal protocol's](./execution.md#worker-journal-protocol) verification requirements; that protocol also owns worker stops, cancellation and retained effects.

Goal receipts derive changes from observations, including child effects; the bounded [editor path/digest report](./session.md#worker-replay) keeps landed effects after completion, cancellation or pause. A command criterion requires a successful command and, when it produces changes, its successful Workspace publication. An unfinished editor intent gets the same recovery refusal as an unfinished primary effect, and no private cleanup or containment record waives it.

## Autonomous Goals

`GoalStarted` pins an `autonomous` flag. After each Run that ends without finishing the Goal, an autonomous Goal's Engine admits the next Run with no user input. Its input is the pinned objective; earlier results and reports are ordinary Session history. Each iteration follows the normal Run admission, budget, linkage and effect rules. A resume with no new text (`GoalRequest::resume`, empty `RunRequest.objective`) runs the pinned objective, and resuming an autonomous Goal continues the loop; non-empty resume text is used as given. Plain prompts and non-autonomous Goals keep the single-Run rule.

A Run that Finishes without the plan's success criterion is a Run boundary while another Run is admissible within the pinned Run, Provider call and known-token budgets; otherwise it fails the Run and the Goal with its report. Active-time exhaustion is handled at settlement, below. Stop conditions:

- A Finished Run that satisfies the criterion, or whose Goal has no plan contract, completes the Goal.
- A Finished Run with an unsatisfied criterion whose Runs, Provider calls or known tokens admit no further Run fails the Run and the Goal with its report. The Engine decides these dimensions when the answer is recorded, so no next Run is admitted. Active time is decided at settlement, below.
- A Failed Run fails the Goal.
- Cancellation stops the current Run and starts no further Run, for every Goal kind. An already Finished Run keeps its committed outcome, which the call returns, even when cancellation arrives during the next Run's admission before `MessageAccepted`. The Goal records no receipt and stays open, projected as Interrupted for explicit resume with its pinned objective.
- Any other next-Run admission failure (Workspace identity or input, Provider selection, request validation, Store load or append) also keeps the committed Finished Run: the result carries its outcome with the failure as stop reason, so the answer is never lost. The Goal stays open.

The live stop equals the replayed projection of the same turn.

Active time for the next Run is judged when the Finished Run settles `active_ms` in `RunFinished`, so recording its terminal facts can exhaust the Goal. If settlement leaves an unsatisfied planned Goal with no admissible next Run, the Finished Run stays committed and the Engine records the Goal Failed with its bounded report in the same segment; the result carries that Run with stop `GoalExhausted`. One rule defines an admissible next Run for every dimension: fewer linked Runs than `max_runs`, fewer charged Provider calls than `max_provider_calls`, less active time than `max_active_ms` and, under a finite token ceiling, fully known usage below that ceiling. Replay accepts a Failed receipt over a Finished Run only for an unsatisfied planned Goal with no admissible next Run; a planless or satisfied Goal completes, and any other Failed receipt needs a Failed Run.

Attached `/goal OBJECTIVE` starts an autonomous Goal, and `/goal resume` continues the most recent paused Goal even after newer Goals finished; `/goal` shows its read-only status and names a paused Goal that is not the shown one. Paused and new Goals coexist: a pause never refuses a plain prompt or `/goal OBJECTIVE`, and starting a Goal does not resume an older one. The [terminal spec](./terminal.md) owns those commands and their notices.

### Budget continuation

Budget exhaustion is terminal; an exhausted Goal is never reopened. `/goal continue` and `exec --session-id SESSION --continue-goal GOAL` start a new Goal in the same Session, seeded from the most recent budget-exhausted Goal that no later Goal continues.

`GoalFinished.exhausted` is true when the Engine closed the Goal because its budget ran out: a Run stopped by the budget, an unsatisfied planned Goal with no admissible next Run, or an out-of-budget resume. Replay requires the flag in the last two cases and accepts it only on a Failed Goal that admits no next Run or whose remaining active time is within the [Store-action margin](#lifecycle-budgets-and-recovery). Replay verifies only that arithmetic, so the flag is a necessary condition; a forged flag can at most allow a user-initiated fresh-budget continuation. A Provider failure on the last allowed call is not a budget stop. A Goal whose last Run left a Tool without a known outcome is not continuable, nor is a Goal that failed for any other reason, even with an exhausted budget.

The new Goal keeps the source's objective, phase and autonomous flag, takes a fresh budget and resource settings from current saved settings (`exec`: the defaults), starts with no Runs, lease or reservation, and journals `GoalStarted.continues` naming the source. The source's plan contract, results and report are ordinary Session history, so the first Run records its own contract. Replay rejects a `continues` that is not the latest unclaimed budget-exhausted Goal in the Session, or whose objective, admitted include list, phase or mode differs. With no eligible source, a source other than that Goal, or request text, the Engine returns `GoalNotContinuable` ("no exhausted Goal is available to continue") with no Event, Run or Provider call. A paused out-of-budget Goal first needs `/goal resume`, which closes it Failed.

`GoalStarted.include_paths` is required and nullable. New Goals record their complete list: at most 16 relative UTF-8 paths of at most 512 bytes<!-- unrelated-bound: Goal include path bytes --> each, with the control, traversal and protected-name exclusions of Tool paths. A null list means the inputs are unknown. Continuation, resume and every later Run of an existing Goal reuse the recorded list, including an empty one, never replacement request paths; continuation never parses the stored objective for `@` mentions. A continuation request's nonempty include list must equal the recorded list or admission fails. Each path is read under the current admitted Workspace capability and input bounds; recorded paths confer no authority. An unknown list refuses continuation or an existing Goal's next Run with `GoalIncludesUnavailable` and guidance to start a new Goal with explicit inputs, without a Provider call or new Event.

## Rewind and Goal recovery

A restored Workspace rewind leaves a paused Goal paused and charges or refunds no call, token, Run or active time. It invalidates file success evidence for changed paths and effect or command criteria that may depend on them, so fresh verification is required; a later initial plan cannot reuse a pre-rewind read of a changed path. Worker verification of overlapping leased paths is invalidated across historical Runs. The bounded rewind fact enters later resume context and the Goal report. An open or [Uncertain](./execution.md#effect-outcomes) rewind after the Goal's last Run blocks `GoalResumed` and budget continuation, also after reopen. A fresh Goal may inspect the Workspace, but that does not clear the earlier Goal's uncertainty. Fork never copies Goal budgets. [Session replay](./session.md#rewind-planning-and-replay) owns checkpoint chains and sealing; [Tools](./tools.md#checkpoints-and-rewind) owns code restore.

## Initial plan contract and success receipt

Primary host dispatch clears earlier file-success and worker-verification evidence before spawn; a later read or verification must re-establish current state. Host stops keep their [effect outcome](./execution.md#effect-outcomes) under the Goal pause and resume rules. Reports keep possible non-rewindable host effects and incomplete inventory coverage. [Tools](./tools.md#primary-host-commands) owns authority and supervision.

Planning is optional and offered only to autonomous Goals (`/goal`, `exec --goal`) and under an explicit `team` policy; plain chat and `auto` or `single` Goals get neither the `arany_plan` function nor plan guidance, so they cannot delegate editors. The primary may call `arany_plan` with a `GoalPlanContract` when a long autonomous Goal or an exact success criterion benefits from a recorded plan. It takes one Provider step: Engine validation precedes `GoalPlanContractRecorded`, and the next request gets a correlated result naming the recorded path, command, Skill and MCP scope. Invalid or replacement plans follow the [proposal refusal continuation](./execution.md#accepted-outcomes); a recorded contract cannot be replaced. The Tool never grants authority. Without a recorded plan, every call permitted by the Goal phase and pinned grant proceeds through the permission mode, hooks, Supervisor and Guard. Goal budgets are Engine-enforced from `GoalStarted`, independent of model-declared arithmetic. Planning is optional as in Claude Code TodoWrite and Codex update_plan; Arany diverges by binding a recorded plan's scope and success gate, so model text can only narrow authority.

The contract contains a mission (at most 2,048 bytes<!-- unrelated-bound: plan contract mission bytes -->), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes<!-- unrelated-bound: plan contract path bytes --> each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes, resource at most 512), at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes, tool at most 128), one typed success criterion, a bounded Goal budget, a `default` or `build` resource class and an optional command timeout. The full serialized contract is limited to 8 KiB<!-- unrelated-bound: serialized plan contract --> and passes the ordinary credential-reflection check before persistence, including native wire sibling fields.

Resource requests resolve against settings pinned at Goal start and never widen executable, path, Skill, MCP or network grants. A command may request Build and a timeout without a plan; a recorded plan caps both fields, with null timeout binding the pinned default. Effect approval latches the exact effective limits whether requested by a plan or a call; it never bypasses the configured maximum or changes the Goal's pinned settings. The [command resource and timeout contract](./tools.md#commands) owns resolution and refusal; the immutable Tool intent and Guard receipt carry the effective limits.

A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the admitted Skill grant and cannot grant or discover a Skill. MCP scope identifies both server and tool. With a recorded contract, every requested operation must fit both its scope and the admitted Tool grant; [accepted outcomes](./execution.md#accepted-outcomes) owns Goal-phase restrictions. Command admission checks the configured command independently of the writable path scope, and returned changeset paths are checked against the path scope. An internal changeset outside that scope is recorded as `Denied` with no Guard receipt or dispatch, and replay rejects any successful or guarded out-of-scope integration.

[Command Prefix wrappers](./tools.md#hook-execution) preserve the pre-prefix call for plan scope and exact-call success; completion still requires the final wrapped receipt and any required changeset integration.

A success criterion is one exact eligible Tool call with the latest matching successful attested receipt (offered only when the catalog admits such a call), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB<!-- unrelated-bound: success criterion file content -->. `tool_call_succeeded` applies to `Command`, `CommandUnguarded` (an attested host run authorized under the [host-command contract](./tools.md#primary-host-commands), which the report marks unguarded), `Write`, `Edit`, `MultiEdit`, `Mkdir`, `Skill` and `McpCall`. Read-only `List`, `Read`, `Search` and `McpList`, and internal `ApplyChangeset`, are never success evidence; a generic successful Read is not sufficient. A command with file changes also needs its successful changeset integration receipt. File criteria use the latest relevant verified read or mutation, in replay and live admission: a later failed, unattested or uncertain observation, a changed digest, a deletion or a published changeset invalidates an earlier match across Goal Runs until a fresh verification succeeds. An exact-content criterion is bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until its criterion is satisfied.

## Current-format replay and `exec`

Goal Events are additive facts in the current internal format ([execution](./execution.md#admission-persistence-and-recovery)); journals at another version are [archived](./execution.md#incompatible-history), never read by a compatibility reader. Saved display and execution preferences use the [tolerant](./execution.md#incompatible-records) `ui-preferences.json` record, limited to 1 KiB<!-- unrelated-bound: UI preferences record cap -->, which stores only the keys `/settings` changed from the binary defaults; every other key, including each Goal budget field, follows the running binary's default at read time and is resolved into the Goal snapshot at admission. A record at another version is [archived](./execution.md#incompatible-records) at startup. Invalid records are never converted or overwritten: attached chat, task submission and `/settings` run on defaults until `/settings` saves a replacement, while `exec` and `serve` refuse them. Replay requires Goal linkage for every accepted task. Histories with missing linkage or fields, invalid transitions or exceeded bounds are rejected intact, never upgraded, deleted or interpreted optimistically, and are ineligible for resume, fork, `exec --session-id` and compaction. The [terminal contract](./terminal.md#setup-and-account-choices) owns explicit user-confirmed history reset, and the [terminal spec](./terminal.md#entry-modes-and-channels) owns `show`.

`exec` creates a Goal for every invocation, receives its typed settlement through the [in-process Server connection](./serve.md#scope-and-related-contracts) and reopens committed history before projecting its exact Run and Goal. The [terminal contract](./terminal.md#entry-modes-and-channels) owns its deterministic output and signals.

- A first SIGINT cancels the active Run: the Run keeps its Cancelled receipt, the Goal stays open as Interrupted, and stderr names `arany exec --session-id SESSION --resume-goal GOAL`, plus `--profile PRESET` for a roster-bound Run. A second SIGINT, SIGTERM or SIGHUP stops waiting after a bounded grace and reports the stop on stderr. A cancelled autonomous loop prints its committed answer before the pause line. SIGINT and SIGTERM leave the Goal resumable and exit with status 1.
- In JSONL, the stderr reason is `error: Run cancelled`, `error: Run failed`, `error: Run stopped by hook[: REASON]` (REASON escaped; the Goal stays open and the pause line follows) or, for a finished Run whose Goal stays open, `error: Goal paused before completion` followed by the pause line.
- An exhausted explicit resume exits unsuccessfully with `error: Goal budget is exhausted` and no Run.
- `exec --goal OBJECTIVE` starts an autonomous Goal and takes no prompt or `--resume-goal`. `exec --session-id SESSION --continue-goal GOAL` starts a [continuation](#budget-continuation) with the default budget and is exclusive with a prompt, `--goal` and `--resume-goal`. Exit status follows the last Run, so success requires that Run to finish.
- When an autonomous loop stops after a committed Run, `exec` prints that Run's answer, writes `error: Goal stopped after a committed Run: REASON` to stderr and exits unsuccessfully. REASON is the failure that refused the next Run, otherwise the projected stop: `Goal budget is exhausted`, `Tool effect completion is uncertain` when the next Run committed an effect with no known outcome, or `Run interrupted without a terminal receipt; check Session history` when it stopped before any such effect. A pause that SIGINT requested between Runs prints only its pause line. A Run that cannot settle exits unsuccessfully with its projected stop and no answer.
- JSONL keeps canonical sequence and Event scope. It selects the Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts of exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals and never assigns a Run ID to a session-scoped Goal Event. After cancellation or a crash, neither channel implies a completion receipt unless replay has a terminal Goal Event.

## Steering notes and pause

A user may send a steering note to a running Goal and pause it at its next boundary. The attached terminal composes notes and offers `/goal pause` ([terminal spec](./terminal.md#interactive-commands-and-completion)); `exec` never steers. In the [serve protocol](./serve.md), `turn/steer` and `goal/pause` use the same handle and `goal/resume` is the explicit resume above.

Child messaging follows [Claude Code's teammate transcript messaging](../research/next-step-decision-register.md#d-10--terminal-contract). The pinned Codex source shows parent-owned children as view-only, so universal Codex live-child input is not claimed. Arany delivers notes at the next committed boundary to keep its journal-first guarantee.

- A primary note is the Run-scoped `GoalSteeringNoteRecorded` (goal ID, Run ID, text); a child note is `AgentSteeringNoteRecorded` (goal ID, Run ID, AgentRun ID, text). Replay rejects a missing, wrong or unlinked scope.
- A Run accepts any number of notes within its [generated per-Run bound](./limits.md#max_steering_note_bytes). Primary and child notes share it, counting recorded and waiting text, merge separators and history labels: 8 bytes per primary label and 24 bytes per child label (`MAX_CHILD_STEERING_LABEL_BYTES`, covering `\n[child N / K] `). Fixed history headers fit the additional 256-byte context reserve. Each note is non-empty after trimming. An offer made while another note for the same target waits merges into it after a blank line; different targets never merge. An offer that would exceed the bound is refused and the caller keeps its text.
- A primary note is accepted only when its Run is the latest and Active, its Goal is Running with that Run active, and the primary AgentRun has an open planning or synthesis Provider reservation not yet settled by `ProviderCallRecorded`. A Tool review reserves under the primary AgentRun, so replay rejects a note while a Tool observation is pending. Replay also rejects notes before that reservation, after its outcome, during a child reservation, after the Run ends, for another Goal or beyond a bound.
- The Engine takes the waiting primary note only inside that open reservation, journals it, then adds it to that call; a call cancelled before dispatch takes no note. Taking a note reserves its quota. Otherwise the note waits for the next primary reservation of its submission, including the first primary call of a next autonomous Run; if the submission ends first, the caller keeps it as a retained draft.
- Every later primary planning or synthesis call of the same Run receives the Run's primary notes in order, as user input data labelled `steering_notes`. Notes never grant permissions, widen Tool authority or revise the plan contract. Primary notes never reach children, child notes reach only their exact actor, and Tool review never receives notes.
- An Active child of the attached, latest Active Run accepts a text-only offer while its Goal is Running. The target binds Session, Run and AgentRun identity; ordinals and model text confer no authority. At most eight children are registered and eight child offers wait, beside the primary offer; a ninth concurrently active child is refused with its own notice. Expired entries stay withdrawable and consume pending capacity until withdrawn. No child note crosses a Run boundary, revives a child, creates an extra call or moves to a sibling or the primary.
- The Engine takes a child note only after that actor's own ChildWork reservation commits, while it is active with no pending own Tool observation; unrelated primary or sibling Tools do not disqualify it. The note Event commits before the request can dispatch. An in-flight call is never interrupted to deliver a note, and a child may finish its final call without another boundary. Taking a note charges quota atomically, including on append failure; an ambiguous append is never retried or reoffered. Commitment acknowledges recording, not remote receipt. On settlement, pause or failure the caller keeps unacknowledged text and reports non-delivery when withdrawal succeeds, otherwise an unknown outcome until validated history confirms it. Replay accepts a child note only from its committed `AgentSteeringNoteRecorded`, for a latest Active Run, a Running Goal, an Active child with an open ChildWork reservation, no worker or hook stop, no pending own Tool observation and room in the Run's allowance. It stores the text in that child's history, rebuilds it from the journal alone and never re-delivers or re-offers it.
- Later ChildWork requests keep earlier notes at their original continuation boundary: after stop-hook feedback or the latest Tool step, or in the request head before any continuation. Route and retry attempts reuse the recorded request. Notes cannot change catalogs, grants, leases, approvals, plans or budgets.
- Later Runs carry notes in their history turn and compaction input under labelled primary and `[child N / K]` historical blocks, and the Engine reserves the bounded context bytes for them. Replay never re-delivers a note. A crash that leaves its Run interrupted keeps the note as history on that Run; explicit resume starts a new Run with no notes.
- Pause is a sticky request on the caller's steering handle. The Engine turns it into the Run's cancellation only at a boundary: before each primary call; after a valid Tool or Delegate outcome, before its plan contract, Tool dispatch or children; before synthesis; before the next autonomous Run; and before each child call or child Tool dispatch. In-flight child calls finish and are recorded. A pause during Tool review or the approval wait stops the Run before dispatch. An in-flight Provider call is never aborted, and its answer still commits. A requested Tool that has not dispatched never starts; its observation records that nothing was dispatched. A paused Run has the same receipts as Ctrl+C: Run Cancelled, Goal Interrupted and resumable. A pause between autonomous Runs keeps the committed Finished Run and leaves the Goal Interrupted.

# Goals

## Scope and delivery boundary

This contract owns durable task-level Goal identity, Run linkage, budget admission, initial Tool-plan timing, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics; [Tools](./tools.md) owns trusted grants and guarded effects; [Session rules](../../agents/session.md), [Engine rules](../../agents/engine.md) and [Store rules](../../agents/store.md) own their respective implementation boundaries.

Optional OTLP records one Goal execution-segment span for each admitted Run. Its child Run span carries only canonical IDs and committed Run facts. The Goal span carries its ID, committed Goal lifecycle and reservation markers, terminal status, known usage, unknown-usage flag and active-time totals. A continuation or explicit resume begins another segment span; trace context is not persisted. Telemetry never carries the objective, plan contract, report, Workspace paths, Tool payloads or Provider content. [Telemetry rules](../../agents/telemetry.md) own export bounds and privacy.

Every accepted task, including `exec`, has one durable Goal. There is no Run-without-Goal path. Foundation delivers Goal lifecycle, atomic Provider-call and active-time reservations, the initial plan contract and typed success receipt, bounded reports, and cross-StateRoot Workspace writer exclusion. Ctrl+C pause (any cancelled Goal stays Interrupted), coexistence with new prompts and `/goal resume` are delivered. Steering UI, context reinjection, approved contract revision, checkpoint artifacts and rewind are follow-on Goal behavior; this slice must not claim those interactions are available.

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, admits the bounded Event capacity for the remaining Goal budget and acquires the OS-user Workspace identity lock for a write-capable Implementation Goal. The lock is keyed by admitted `(device, inode)`, is shared across separate Session StateRoots and processes, and is not taken by read-only Goals. At most 4,096 identity lock files are retained; quota exhaustion rejects new writers before disclosure or effects. Read-only Goals and Session history are unaffected. Recovery is manual: with no Arany process running for that OS user, remove the `guard/workspace-locks` directory beneath the account root (`~/Library/Application Support/dev.Arany.arany` on macOS, `~/.local/state/arany` on Linux); the next writer Goal recreates it. Store byte admission is conservative preflight, not a physical disk reservation.

A write-capable Implementation Goal holds the admitted Workspace OS lock only while a Run call is live, including autonomous continuations inside that call. Engine takes ownership from provisional admission before awaiting the first `GoalStarted`, `GoalResumed` or `GoalRunLinked` acknowledgment. The call's lease drops when the call returns, when its future is dropped, or after the terminal Goal receipt, so a paused (Interrupted) Goal holds no writer lock. While the Goal is paused, another Goal in this or another StateRoot may write the admitted Workspace. Explicit recovery reacquires the lock before Workspace content or Provider disclosure and fails with `WorkspaceBusy` while another writer holds it. A failed acknowledgment reports `GoalAdmissionUncertain` when the Goal is committed and otherwise returns the Store error.

`GoalStarted` pins a UUIDv7 identity, objective, Workspace identity, phase and explicit `GoalBudget`. Starting a Goal seals any unfinished predecessor as Interrupted, so at most one Goal is Running and a predecessor left Running by a crash is paused rather than blocking. `GoalRunLinked` names each unique Run and must repeat the pinned phase before `MessageAccepted`; an explicit resume keeps that phase and never takes one from the client. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged Goal start/resume/link appends and before `MessageAccepted`; a preaccept prefix creates no Run, Provider call or effect. Explicit recovery drops a trailing GoalRunLinked ID with no accepted message, so it consumes no Run budget and is never retried. If the Goal has no accepted Run yet, recovery must preserve the original objective; `--resume-goal ID PROMPT` for such a Goal accepts PROMPT only when it equals that objective (omitting PROMPT resumes it), and any other PROMPT is `GoalUnavailable`. `GoalResumed` is an explicit user action after reviewing an interrupted Goal; it starts a new Run and never retries the old Provider call or Tool effect. Autonomous continuations append no `GoalResumed`. Headless `exec` requires `--session-id` plus `--resume-goal GOAL_ID`; attached startup requires `--resume SESSION_ID --resume-goal GOAL_ID` and resumes at once when no prompt is given; idle chat resumes with `/goal resume`, which needs no further confirmation. The selected ID must be the most recent paused Goal in that Session (the latest Goal that is Running or Interrupted); older paused Goals are history and are not resumable. An ordinary prompt never auto-resumes it; while a Goal is paused, a prompt starts a new Goal. A crash after a first Tool request but before its plan record can resume only when the interrupted Run has no open or uncertain Tool observation; acknowledged read-only inspection history is retained, and the pending plan wait is cleared by `GoalResumed`. Reopening an unfinished Goal projects it as Interrupted; an explicit `GoalResumed` seals an unfinished Running predecessor the same way. A closed Goal has exactly one terminal status: Completed or Failed, plus a bounded report. Cancellation never closes a Goal; it stays Interrupted until explicit resume. A crash or Store failure before that receipt leaves an interrupted prefix rather than a fabricated result.

Initial finite defaults are at most 64 Provider calls, 16 Runs and 30 minutes of active Goal time. Each dispatched Run reserves no more than five minutes of that total. A Plan contract may request lower limits and an optional token ceiling; it cannot widen the pinned Goal budget. A caller may explicitly choose an unlimited token dimension. Known `ProviderCallRecorded` usage is preserved; missing usage remains unknown. With a token ceiling, unknown usage cannot count as zero or authorize another Provider call or effect. Before each Run dispatch, Engine durably reserves its finite active-time segment. At an acknowledged boundary it settles the reservation with monotonic elapsed time. Plan-contract append acknowledgment latency stays within the narrowed active interval. If the process exits before settlement, replay retains the reservation as conservatively charged, uncertain time; explicit resume never restores it. Likewise, an unobserved Provider-call reservation stays charged and makes token usage unknown when explicit resume settles the interrupted prefix. Time outside a dispatched Run is not charged.

Before every actual Provider dispatch charged to a Goal, including primary, child and Tool review calls, Engine durably reserves one call. Context compaction runs between Runs and is not charged to a Goal. Store's serialized reducer rejects an over-budget reservation atomically, including racing child callers. Queued children do not consume a call until concurrency capacity is available. A started or cancelled call remains charged; an unobserved reservation remains uncertain and is not reported as definitely sent. Failure and cancellation never refund call or token usage. A call or token budget reached before the next dispatch settles the Run as Failed and finishes the Goal with its report, rather than returning an unrecorded error. Tool dispatch preserves the bounded terminal-tail budget needed to record the Tool disposition and Run receipt.

With a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children. It observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage under a finite cap, fails before `ToolRequested`/`ToolStarted` or child admission. A matching Finish at the exact cap may complete if the success criterion is met; unknown usage does not block a Finish.

Goal report payloads are at most 8 KiB serialized; summary and each listed item are at most 2 KiB, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts. Cache publication and Tool failure/uncertainty facts are recorded before optional positive evidence so a full report cannot silently hide them. If lower-priority facts must be omitted to preserve the byte and item bounds, the report includes an omission notice. A successful Command retains its evidence when cache publication is rejected or fails whenever the report has room; an uncertain cache publication directs recovery to Session history rather than Workspace inspection. Engine truncates a longer model summary at a UTF-8 boundary based on its serialized JSON size, reserving room for those priority facts and the omission notice; it never fabricates successful evidence from a Provider summary. If storage fails before `GoalFinished`, replay leaves the Goal interrupted.

## Autonomous Goals

`GoalStarted` pins an `autonomous` flag. An autonomous Goal's Engine admits its next Run after each Run that ends without finishing the Goal, with no user input. The Run input is the pinned objective; earlier Runs' results and reports are ordinary Session history. Each iteration runs the normal Run admission, budget, linkage and effect rules. A resume with no new text (`GoalRequest::resume`, empty `RunRequest.objective`) also runs the pinned objective. Resume of an autonomous Goal continues this loop. A non-empty resume text is used as before.

A Run that Finishes without the plan's success criterion is a Run boundary while another Run is admissible within the pinned budget. Otherwise the same Finish fails the Run, and the Goal fails with its report. Plain prompts and other non-autonomous Goals keep the single-Run rule. Stop conditions:

- A Finished Run whose success criterion is satisfied, or whose Goal has no plan contract, completes the Goal.
- A Finished Run whose criterion is unsatisfied and whose Runs, Provider calls or known tokens admit no further Run fails the Run, and the Goal fails with its report. The Engine decides these dimensions when the Finish is recorded, so the next Run is never admitted. Active time is decided at settlement, below.
- A Failed Run fails the Goal, as for any Run.
- Cancellation stops the current Run and starts no further Run, for every Goal kind: one-Run prompts as well as autonomous Goals. A Run that already Finished keeps its committed outcome, which the call returns, including when cancellation arrives during the next Run's admission before `MessageAccepted`. The Goal records no terminal receipt and stays open, so reopening it projects it as Interrupted for explicit resume with its pinned objective.
- Any other failure to admit the next Run (Workspace identity or input, Provider selection, request validation, or a Store load or append) also keeps the committed Finished Run. The call returns `StoppedAfterRun` with that Run's outcome and the failure as its reason, so the answer is never lost. The Goal records no terminal receipt and stays open, so reopening it projects it as Interrupted for explicit resume.

Attached `/goal OBJECTIVE` starts an autonomous Goal, and `/goal resume` continues the most recent paused Goal even after newer Goals finished; `/goal` shows its read-only status and names a paused Goal that is not the shown one. Paused and new Goals coexist: a Goal's pause never refuses a plain prompt or `/goal OBJECTIVE`, and starting a Goal does not resume an older one. The [terminal spec](./terminal.md) owns those commands and their notices.

Active time for the next Run is judged when the Finished Run's active time settles, so time spent recording its terminal facts can exhaust the Goal. If that settlement leaves an unsatisfied planned Goal with no admissible next Run, the Finished Run stays committed and the Engine records the autonomous Goal as Failed with its bounded report in the same segment; the call returns `StoppedAfterRun` whose reason is `GoalBudgetExhausted`. "No admissible next Run" is one rule for every dimension: fewer Runs linked than `max_runs`, fewer Provider calls charged than `max_provider_calls`, less active time than `max_active_ms`, and, under a finite token ceiling, known usage with no unknown part and below that ceiling. Replay accepts a Failed receipt over a Finished Run only for an unsatisfied planned Goal that admits no next Run under that rule; a planless or satisfied Goal completes, and any other Failed receipt needs a Failed Run.

## Initial plan contract and success receipt

Before the first plan, the primary may use bounded Workspace `List`, `Read` and `Search`, an admitted Skill read, or configured bounded MCP catalog listing. These operations can inform the declared scope; MCP catalog listing reveals names only and is not an MCP tool invocation. Every other Tool—including `Command`, Workspace mutations and `McpCall`, even when its catalog advertises `readOnlyHint`—requires a strict `GoalPlanContract` before dispatch. The same actor may inspect in either `RootPlan` or `RootSynthesis`; delegation does not let the primary use an unplanned Tool in synthesis. A contract may be supplied with a prelude inspection, but it is validated, credential-checked and journaled before that call. Schema and Engine admission apply the same rule. A pure read-only task, or a task with no Tool call, can finish with its bounded canonical report and does not invent a writable scope or success criterion. The Goal success gate applies whenever a contract is present.

The contract contains a mission (at most 2,048 bytes), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes and resource at most 512), and at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes and tool at most 128), one typed success criterion and a bounded Goal budget. A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the already admitted Skill grant and cannot grant or discover a Skill. The full serialized contract is limited to 8 KiB and receives the ordinary credential-reflection check before persistence, including native wire sibling fields. Missing or invalid contracts reject before non-prelude dispatch. Every requested operation must fit both the contract and the already admitted Tool grant. Research and Plan phase Runs remain limited to the bounded read-only prelude; only Implementation phase Runs can dispatch commands, MCP tool invocations or Workspace mutations. Command admission checks its configured command independently from the writable path scope; returned changeset paths are checked against the path scope. An internal changeset outside that scope is durably recorded as `Denied`, with no Guard receipt or dispatch, and replay rejects any successful or guarded out-of-scope integration. MCP scope identifies both server and tool.

Success criteria are one exact eligible Tool call with the latest matching successful attested receipt (offered only when the catalog admits at least one such call; the schema never contains an empty `anyOf`) (and, for a command with file changes, its successful changeset integration receipt), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB. `tool_call_succeeded` applies to `Command`, `Write`, `Edit`, `Mkdir`, `Skill`, and `McpCall`; read-only `List`, `Read`, `Search`, and `McpList`, plus internal `ApplyChangeset`, cannot be success evidence. A generic successful Read is not sufficient; use a file criterion when verification depends on its contents. For file criteria, replay and live admission use the latest relevant verified read or mutation: a later failed, unattested or uncertain observation, changed digest, deletion or published changeset invalidates the earlier match until a fresh verification succeeds. This remains true across Goal Runs. An exact-content criterion is itself bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until the matching criterion is satisfied. Plan changes are not available in Foundation; approved prospective revision and its mode interaction are owned by the follow-on Goal behavior.

## Current-format replay and `exec`

Goal Events are additive facts within the current SQLite schema 4 and Event payload version 3; there is no migration or compatibility reader. Replay requires Goal linkage for every accepted task. Histories without required Goal linkage, with missing fields, invalid transitions or exceeded bounds reject intact; they are not upgraded, deleted or interpreted optimistically. Explicit user-confirmed history reset remains governed by the [terminal contract](./terminal.md#setup-and-account-choices).

`exec` creates a Goal for every invocation and keeps its existing text and JSONL channels and terminal exit behavior. A first SIGINT during `exec` cancels its active Run: the Run keeps its Cancelled receipt, the Goal stays open and is projected as Interrupted, and stderr names the resume command `arany exec --session-id SESSION --resume-goal GOAL`. A second SIGINT, SIGTERM or SIGHUP stops waiting after a bounded grace and reports the stop on stderr. A cancelled autonomous loop prints its committed answer before the pause line. A cancelled Run exits unsuccessfully, as before. `exec --goal OBJECTIVE` starts an autonomous Goal; its exit status follows the last Run, so success requires that Run to finish. When an autonomous loop stops after a committed Run for any `StoppedAfterRun` reason, `exec` prints that Run's committed answer, writes `error: Goal stopped after a committed Run: REASON` to stderr and exits unsuccessfully. JSONL preserves canonical sequence and Event scope while selecting all Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts for exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals; it never assigns a Run ID to a session-scoped Goal Event. A terminal report therefore appears in JSONL without changing its durable Event. On cancellation or crash, neither output channel implies a completion receipt if replay has no terminal Goal Event.

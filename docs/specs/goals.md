# Goals

## Scope and delivery boundary

This contract owns durable Goal identity, Run linkage, budget admission, optional plan recording, completion reports and explicit interruption recovery. [Execution](./execution/README.md) owns Run and Provider-call semantics, [Tools](./tools/README.md) grants and guarded effects, [Session](./session.md) the conversation boundary and [telemetry](./telemetry.md) Goal segment telemetry. Editing constraints: [security rules](../../agents/security.md). Native evidence gaps: [NEXT_STEPS.md](../../NEXT_STEPS.md#beta-2-and-broader-release).

Every accepted task, `exec` included, has one durable Goal; no Run exists without one. The Goal owns its pinned budget and resource settings across Runs, Tool loops, delegation, review and in-Goal compaction.

Compaction inside a Goal keeps the objective, current instructions and includes, the approved plan, typed Goal facts and selected observations; between-Run compaction keeps the canonical objective, plan, budget, settings, usage facts and history, and the next Run supplies fresh instruction and include snapshots. Both fit the [generated compaction input limit](./limits.md#max_compaction_input_bytes).

Guarded code rewind, replay and evidence invalidation follow the [rewind contract](./tools/changesets-and-checkpoints.md#checkpoints-and-rewind). Context reinjection and approved contract revision are not available.

## Lifecycle, budgets and recovery

Nothing from the Workspace is read or disclosed to a Provider before the request, Workspace identity, Session locks, Goal and next Run are admitted. Each Provider call and guarded effect is admitted against Store and Event headroom as it happens; nothing is reserved up front for an unlimited budget.

A write-capable Implementation Goal holds the OS-user Workspace lock, shared across StateRoots and processes, only while a Run call is live, so a paused Goal holds none; read-only Goals never take it. Another writer fails with `WorkspaceBusy`. At most the [generated Workspace lock-file quota](./limits.md#max_workspace_lock_files) is retained; at the quota new writers are rejected before disclosure or effects. Recovery is manual: with no Arany process running for that OS user, remove `guard/workspace-locks` beneath the account root (`~/Library/Application Support/dev.Arany.arany` on macOS, `~/.local/state/arany` on Linux). A failed start acknowledgment reports `GoalAdmissionUncertain` when the Goal is committed, otherwise the Store error.

- `GoalStarted` pins a UUIDv7 identity, objective, admitted include paths, Workspace identity, phase, explicit `GoalBudget`, validated resource settings and `continues` (the source of a [continuation](#budget-continuation), or null). Later setting changes affect only new Goals; continuation Runs and explicit resume never recalculate an admitted Goal. Starting a Goal seals any unfinished predecessor as Interrupted, so at most one Goal is Running.
- Goal admission snapshots the available logical core count once for Build CPU cores and jobs; explicit positive preferences may lower either, and `max_processes` caps jobs only. If cores are unknown, or a preference exceeds them, that setting is null and Build plans are refused without running anything; ordinary operations remain available. Each Build command carries `intent.limits.build_cpu_cores` and `intent.limits.build_jobs`, which replay binds to the admitted settings. [Tools](./tools/limits-and-failures.md#limits-and-failure-behavior) owns enforcement.
- `GoalRunLinked` names each unique Run and repeats the pinned phase before `MessageAccepted`; resume keeps the stored phase, never a client-supplied one. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Cancellation before `MessageAccepted` creates no Run, Provider call or effect.
- Resume is explicit: `GoalResumed` follows the user's review of an interrupted Goal and starts a new Run, never retrying the old Provider call or Tool effect; autonomous continuations append no `GoalResumed`. A trailing `GoalRunLinked` with no accepted message is dropped without consuming Run budget. If no Run was accepted, `--resume-goal ID PROMPT` accepts PROMPT only when it equals the preserved objective, omitting PROMPT resumes it, and any other PROMPT is `GoalUnavailable`. Headless `exec` resumes with `--session-id` and `--resume-goal GOAL_ID`; attached startup uses `--resume SESSION_ID --resume-goal GOAL_ID` and resumes at once; idle chat uses `/goal resume` without confirmation. Only the Session's most recent Running or Interrupted Goal is resumable; older paused Goals are history. A prompt never auto-resumes; while a Goal is paused, a prompt starts a new Goal.
- If a paused Goal admits no next Run under [Autonomous Goals](#autonomous-goals), explicit resume closes it Failed with its report, returns `GoalBudgetExhausted` and records no `GoalResumed`. After a crash between a `plan_recorded` Provider call and its contract Event, resume is allowed only when the interrupted Run has no open or [Uncertain](./execution/events-and-outcomes.md#effect-outcomes) Tool observation.
- An unfinished Goal reopens as Interrupted. A closed Goal has exactly one terminal status, Completed or Failed, with a bounded report. Cancellation never closes a Goal; it stays Interrupted until explicit resume. A Run [stopped by a hook](./execution/events-and-outcomes.md#accepted-outcomes) also leaves its Goal open for explicit resume, and an autonomous Goal never continues after it. A crash or Store failure before the receipt leaves an interrupted prefix, never a fabricated result.

New Goals in attached chat, `exec` and `serve` default to unlimited Provider calls, tokens and active time, with at most [the generated Goal Run limit](./limits.md#max_goal_runs) Runs; there is no aggregate dollar-spend guarantee. Settings may select finite limits, bounded by the [generated Goal maxima](./limits.md#max_goal_provider_calls) and [active-time maximum](./limits.md#max_goal_active_ms). An unlimited dimension removes only that Goal ceiling; per-action, request, Run-count, context, Event, Store, Tool, Guard and native bounds stay finite. A plan contract may lower call, token or active-time limits and never widens the pinned settings. Missing usage stays unknown; under a finite token ceiling, unknown usage never counts as zero and never authorizes another Provider call or effect.

The Store-action margin is 5,000 ms<!-- unrelated-bound: Goal Store-action margin -->.

Goal exhaustion projects onto the latest accepted Run when `GoalFinished.exhausted` is true, or when an interrupted Run's committed counts prove the budget spent, subject to [accepted-outcome precedence](./execution/events-and-outcomes.md#accepted-outcomes). The limit reported is, in order: tokens when known usage reaches the ceiling or usage is unknown; calls when charged calls reach the ceiling; active time when remaining time is within the Store-action margin; otherwise Runs.

Every Provider call (primary, child, review or compaction) is durably reserved before dispatch, and an over-budget reservation is refused, even between racing children; queued calls are not charged. A started or cancelled call stays charged, an unobserved one is [Uncertain](./execution/events-and-outcomes.md#effect-outcomes), and failure and cancellation never refund call or token usage. Reaching a call or token budget before the next dispatch fails the Run and finishes the Goal with its report. Compaction calls charge reported usage to the same ledger.

Active time counts Provider calls once capacity is available and Tool actions after approval and Guard capacity, including preparation, checkpoint capture, execution and cleanup; an action starts only if its full runtime fits the remaining time, and preparation that consumes it fails the Tool without an effect. An acknowledged action exceeding the remaining finite time is recorded and fails the Run and Goal. Overlapping child calls charge wall time once. Capacity and approval waits and pauses are excluded. [Execution](./execution/collaboration.md#researcher-children) owns the delegation segment.

`RunStarted` pins `active_deadline_ms`, the Goal's remaining active time (null when unlimited), and `RunFinished` records the Run's settled `active_ms`, which replay adds to the Goal. Each action-start Event (`GoalProviderCallReserved`, `GoalCompactionCallReserved`, `ToolProposed`, `ToolStarted`, `ToolActiveTimeReserved` and every lifecycle `HookStarted`) records `active_ceiling_ms`. A between-Run Goal compaction reserves at most its 120-second<!-- unrelated-bound: Engine compaction call deadline --> call and journals its time in `ContextCompacted.active_ms`. If the process exits before settlement, replay charges the latest ceiling as conservative uncertain time, only for the open action, so explicit resume continues while time remains; resume never restores that charge.

Event and observation capacity for every call in a Tool batch, its review, fallback switches and retries is reserved before the batch starts, within the [Session Event cap](./execution/persistence.md#persistence-bounds), so terminal facts always fit.

Provider roles, all selected [roster candidates](./provider/selection.md#named-roster-presets) and fallback attempts share this ledger; explicit roster-bound recovery follows the [same-selection rule](./session.md#roster-recovery-and-compaction). A committed `ProviderFallbackUsed` or `ProviderRetryScheduled` charges one more call, and a retry's wait counts as active time. Failed-call usage stays unknown, so a finite token budget refuses a replacement attempt, and unlimited tokens do not make failed calls free. The Goal report keeps at most eight retry (role, attempt, cause, delay) and fallback (role, from, to) notices, warning that failed calls may have consumed usage, then an omission marker. A post-Goal manual compaction never amends a closed Goal's usage or receipt. [Provider selection](./provider/selection.md#per-role-selection-and-fallback) and [switch replay](./execution/admission-and-recovery.md#admission-persistence-and-recovery) own other routing rules.

Under a finite token ceiling, at most one Provider call runs at a time. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage, fails before `ToolRequested`, `ToolStarted` or child admission; an answer at the cap may complete if the success criterion is met. When a finite Provider-call budget leaves exactly one call and the primary has no active child, that last call is answer-only: Tools are disabled (`tool_choice: none` or the Messages equivalent) and a fixed `harness_final_call` data block asks for the budget-reached status, the work done, what remains and the next step. The answer commits normally, a planless Goal completes, and the report adds `Provider-call budget reached; the final call was answer-only.` Token and active-time ceilings keep no wrap-up call.

Goal reports are bounded by the [generated Goal report limit](./limits.md#max_goal_report_bytes); the summary and each item are at most 2 KiB<!-- unrelated-bound: Goal report item cap -->, with at most 32 changes, evidence items and unresolved items. Changes, evidence and unresolved facts come only from committed, attested Tool outcomes and terminal Run facts, never a Provider summary. Skipped checkpoint capture, pruning, cache publication and Tool failure or uncertainty facts come before optional positive evidence, so a full report cannot hide them; omitted facts produce an omission notice. An uncertain cache publication directs recovery to Session history. If storage fails before `GoalFinished`, replay leaves the Goal interrupted. The report states `cached_input_tokens`, total cache-read input tokens across the Goal's calls, informational only.

### Budget refusal feedback

`GoalFinished.budget_refusal` is required and nullable: non-null `BudgetRefusal` on every budget-caused closure, including an out-of-budget resume or failed next-Run admission, otherwise null. The record never changes charges or grants a continuation, and exhaustion allows no extra Provider call, retry, fallback or compaction to explain it. A committed answer stays intact; cancellation, hook stops and unknown effects keep [Execution precedence](./execution/events-and-outcomes.md#accepted-outcomes). A Provider failure on the final allowed attempt is not a budget stop unless a separate budget boundary stops the Run, and a delegation-only deadline or recoverable Tool timeout is not Goal exhaustion.

The closed record contains `dimension` (`tokens`, `calls`, `active_time`, `runs`), `cause` (`exhausted`, `unknown_usage`, `insufficient_headroom`), `action` (`provider`, `tool`, `delegation`, `compaction`, `run`, `resume`), required nullable `run_id` and `agent_run_id` (null for Run and resume admission), unsigned `used` (usage at refusal) and finite `limit`, independently nullable `requested` and `required_minimum`, `token_usage_unknown`, and `charge_basis` (`observed`, `conservative`). The basis is `conservative` exactly when token usage is unknown or the Goal carries uncertain or unsettled active time. Counts use units, tokens known charged tokens, and active time milliseconds. The record is bounded by the [generated budget-refusal limit](./limits.md#max_budget_refusal_bytes) and contains no paths, arguments or free text. `requested` is present only when known. The minimum active admission is carried processing time plus the [Store-action margin](#lifecycle-budgets-and-recovery) plus one millisecond, or just processing plus one millisecond at a zero-duration Tool pause or delegation boundary; reaching the margin below the ceiling is insufficient headroom, not exhaustion. Replay validates the record against the pinned limit, actor and committed usage.

Before a Goal is admitted or closed, and for a refused idle compaction, only a local diagnostic may describe the refusal. If a terminal append failed and is proved absent, its details are labelled uncommitted; if it may have committed, `GoalAdmissionUncertain` points to Session history. A lost acknowledgment never produces a fabricated receipt; reopening shows the committed prefix with missing refusal detail marked unavailable.

`exec`, `show`, serve, ACP and attached autonomous Goals share one committed Goal/Run status; attached chat shortens a plain Goal's stop as [Terminal](./terminal/commands.md#interactive-commands-and-completion) defines. It names the actual dimension, pinned limit, used-at-refusal, known requested and minimum quantities, unknown tokens, Store margin and conservative charges. The report keeps at most eight recent failed, denied, conflicted or limited Tool facts across primary and children, newest first, with actor and Tool labels, exit and limit codes, bounded excerpts and an omission count. Denial summaries use compiled labels, never raw hook or client reasons or permission rules; excerpts are escaped within the 2 KiB<!-- unrelated-bound: Goal report item cap --> item and report bounds. Overflow drops optional details, never the terminal cause. Reports are Arany status, never assistant `MessageCommitted` text; JSONL stays canonical Events. Output for a Run only ever uses that Run's committed facts.

## Worker accounting and verification

Each [editor](./execution/events-and-outcomes.md#worker-journal-protocol) requires Implementation, a committed plan and a write-capable parent; its lease and catalog intersect parent, plan and definition. Editor work shares the Goal's Workspace lock and [call and active-time accounting](#lifecycle-budgets-and-recovery).

Satisfying the Goal criterion does not waive the [worker journal protocol's](./execution/events-and-outcomes.md#worker-journal-protocol) verification requirements; that protocol owns worker stops, cancellation and retained effects.

Goal receipts include child effects; the bounded [editor path/digest report](./session.md#worker-replay) keeps landed effects after completion, cancellation or pause. A command criterion requires a successful command and, when it produces changes, its successful Workspace publication. An unfinished editor intent blocks recovery like an unfinished primary effect.

## Autonomous Goals

`GoalStarted` pins an `autonomous` flag. After each Run that ends without finishing the Goal, an autonomous Goal admits the next Run with the pinned objective and no user input, under normal admission and budgets; earlier results are ordinary Session history. Resuming with no new text runs the pinned objective and continues the loop; non-empty resume text is used as given. Plain prompts and non-autonomous Goals run one Run.

A next Run is admissible while linked Runs are below `max_runs`, charged Provider calls below `max_provider_calls`, active time below `max_active_ms` and, under a finite token ceiling, usage is fully known and below it. Active time is judged when the finished Run settles. Stop conditions:

- A Finished Run that satisfies the criterion, or whose Goal has no plan contract, completes the Goal.
- A Finished Run with an unsatisfied criterion continues while a next Run is admissible; otherwise the Goal fails with its report, keeping the Run committed, and the result carries stop `GoalExhausted`.
- A Failed Run fails the Goal.
- Cancellation stops the current Run and starts no further Run. An already Finished Run keeps its committed outcome, which the call returns. The Goal stays open, Interrupted, for explicit resume.
- Any other next-Run admission failure keeps the committed Finished Run: the result carries its outcome with the failure as stop reason, and the Goal stays open.

The live stop equals the replayed projection of the same turn.

Attached `/goal OBJECTIVE` starts an autonomous Goal, and `/goal resume` continues the most recent paused Goal even after newer Goals finished; `/goal` shows its read-only status. Paused and new Goals coexist: a pause never refuses a plain prompt or `/goal OBJECTIVE`, and starting a Goal does not resume an older one. The [terminal spec](./terminal/README.md) owns those commands and their notices.

### Budget continuation

Budget exhaustion is terminal; an exhausted Goal is never reopened. `/goal continue` and `exec --session-id SESSION --continue-goal GOAL` start a new Goal in the same Session from the most recent budget-exhausted Goal that no later Goal continues.

`GoalFinished.exhausted` is true when the Goal closed because its budget ran out: a Run stopped by the budget, an unsatisfied planned Goal with no admissible next Run, or an out-of-budget resume. Replay checks only the budget arithmetic, so a forged flag can at most allow a user-initiated fresh-budget continuation. A Goal whose last Run left a Tool without a known outcome, or that failed for any other reason, is not continuable.

The new Goal keeps the source's objective, phase and autonomous flag, takes a fresh budget and resource settings from current saved settings (`exec`: the defaults), starts with no Runs, and journals `GoalStarted.continues` naming the source; the source's plan, results and report are ordinary history. Replay rejects a `continues` that is not the latest unclaimed exhausted Goal or whose objective, include list, phase or mode differs. With no eligible source, another source, or request text, the Engine returns `GoalNotContinuable` ("no exhausted Goal is available to continue") with no Event, Run or Provider call. A paused out-of-budget Goal first needs `/goal resume`, which closes it Failed.

`GoalStarted.include_paths` is required and nullable: at most 16 relative UTF-8 paths of at most 512 bytes<!-- unrelated-bound: Goal include path bytes --> each, with Tool path exclusions; null means unknown. Every later Run, resume and continuation reuses the recorded list, never new request paths or `@` mentions parsed from the objective; a continuation request's nonempty list must equal it. Paths are read under current Workspace admission and confer no authority. An unknown list refuses continuation or a next Run with `GoalIncludesUnavailable` and guidance to start a new Goal with explicit inputs, without a Provider call or Event.

## Rewind and Goal recovery

A restored Workspace rewind leaves a paused Goal paused and charges or refunds no budget. It invalidates file success evidence and criteria that may depend on changed paths, including worker verification of overlapping leased paths, so fresh verification is required. The rewind fact enters later resume context and the Goal report. An open or [Uncertain](./execution/events-and-outcomes.md#effect-outcomes) rewind after the Goal's last Run blocks `GoalResumed` and budget continuation, also after reopen; a fresh Goal does not clear it. Fork never copies Goal budgets. [Session replay](./session.md#rewind-planning-and-replay) owns checkpoint chains; [Tools](./tools/changesets-and-checkpoints.md#checkpoints-and-rewind) owns code restore.

## Initial plan contract and success receipt

A primary host command clears earlier file-success and worker-verification evidence; host stops keep their [effect outcome](./execution/events-and-outcomes.md#effect-outcomes), and reports keep possible non-rewindable host effects. [Tools](./tools/host-commands.md#primary-host-commands) owns authority.

Planning is offered only to autonomous Goals (`/goal`, `exec --goal`) and under an explicit `team` policy; plain chat and `auto` or `single` Goals get neither the `arany_plan` function nor plan guidance, so they cannot delegate editors. The primary may call `arany_plan` with a `GoalPlanContract`; validation precedes `GoalPlanContractRecorded`, and the next request gets a result naming the recorded path, command, Skill and MCP scope. Invalid or replacement plans follow the [proposal refusal continuation](./execution/events-and-outcomes.md#accepted-outcomes); a recorded contract cannot be replaced. The plan never grants authority: without one, calls proceed through the permission mode, hooks, Supervisor and Guard; with one, its scope and success gate can only narrow. Goal budgets are enforced from `GoalStarted`, independent of model-declared arithmetic.

The contract contains a mission (at most 2,048 bytes<!-- unrelated-bound: plan contract mission bytes -->), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes<!-- unrelated-bound: plan contract path bytes --> each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes, resource at most 512), at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes, tool at most 128), one typed success criterion, a bounded Goal budget, a `default` or `build` resource class and an optional command timeout. The serialized contract is limited to 8 KiB<!-- unrelated-bound: serialized plan contract --> and must pass the credential-reflection check.

Resource requests resolve against settings pinned at Goal start and never widen executable, path, Skill, MCP or network grants. A command may request Build and a timeout without a plan; a recorded plan caps both, a null timeout meaning the pinned default. Approval fixes the exact effective limits, never beyond the configured maximum. The [command resource and timeout contract](./tools/commands-and-cache.md#commands) owns resolution and refusal.

A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the admitted Skill grant and cannot grant or discover a Skill; MCP scope names server and tool. With a recorded contract, every operation must fit both its scope and the admitted Tool grant; [accepted outcomes](./execution/events-and-outcomes.md#accepted-outcomes) owns Goal-phase restrictions. A command's changes outside the path scope are recorded as `Denied` and never published.

[Command Prefix wrappers](./tools/hooks.md#hook-execution) keep the unwrapped call for plan scope and exact-call success; completion still requires the wrapped receipt.

A success criterion is one exact eligible Tool call with a matching successful attested receipt (offered only when the catalog admits it), an exact Workspace file digest, or exact Workspace file content of at most 8 KiB<!-- unrelated-bound: success criterion file content -->. `tool_call_succeeded` applies to `Command`, `CommandUnguarded` (an attested host run under the [host-command contract](./tools/host-commands.md#primary-host-commands), marked unguarded), `Write`, `Edit`, `MultiEdit`, `Mkdir`, `Skill` and `McpCall`. Read-only `List`, `Read`, `Search` and `McpList`, and internal `ApplyChangeset`, are never success evidence. A command with file changes also needs its integration receipt. File criteria use the latest verified read or mutation: a later failed, unattested or uncertain observation, a changed digest, a deletion or a published changeset invalidates an earlier match until a fresh verification succeeds. An exact-content criterion never writes a file. A Goal with a Tool plan cannot complete until its criterion is satisfied.

## Current-format replay and `exec`

Goal Events use the current journal format; journals at another version are [archived](./execution/persistence.md#incompatible-history). Saved display and execution preferences use the [tolerant](./execution/persistence.md#incompatible-records) `ui-preferences.json` record, limited to 1 KiB<!-- unrelated-bound: UI preferences record cap -->, storing only keys `/settings` changed from the binary defaults; other keys, Goal budget fields included, follow the running binary's defaults and are fixed into the Goal at admission. A record at another version is [archived](./execution/persistence.md#incompatible-records). Invalid records are never converted or overwritten: attached chat, task submission and `/settings` run on defaults until `/settings` saves a replacement, while `exec` and `serve` refuse them. Histories with missing linkage or fields, invalid transitions or exceeded bounds are rejected intact and are ineligible for resume, fork, `exec --session-id` and compaction. The [terminal contract](./terminal/setup-and-accounts.md#setup-and-account-choices) owns user-confirmed history reset, and the [terminal spec](./terminal/entry-and-modes.md#entry-modes-and-channels) owns `show`.

`exec` creates a Goal for every invocation through the [in-process Server connection](./serve.md#scope-and-related-contracts) and reports only committed history. The [terminal contract](./terminal/entry-and-modes.md#entry-modes-and-channels) owns its output and signals.

- A first SIGINT cancels the active Run: the Goal stays open as Interrupted, and stderr names `arany exec --session-id SESSION --resume-goal GOAL`, plus `--profile PRESET` for a roster-bound Run. A second SIGINT, SIGTERM or SIGHUP stops waiting after a bounded grace. A cancelled autonomous loop prints its committed answer before the pause line. SIGINT and SIGTERM leave the Goal resumable and exit with status 1.
- In JSONL, the stderr reason is `error: Run cancelled`, `error: Run failed`, `error: Run stopped by hook[: REASON]` (REASON escaped; the pause line follows) or, for a finished Run whose Goal stays open, `error: Goal paused before completion` followed by the pause line.
- An exhausted explicit resume exits unsuccessfully with `error: Goal budget is exhausted` and no Run.
- `exec --goal OBJECTIVE` starts an autonomous Goal and takes no prompt or `--resume-goal`. `exec --session-id SESSION --continue-goal GOAL` starts a [continuation](#budget-continuation) with the default budget and is exclusive with a prompt, `--goal` and `--resume-goal`. Exit status follows the last Run.
- When an autonomous loop stops after a committed Run, `exec` prints that Run's answer, writes `error: Goal stopped after a committed Run: REASON` to stderr and exits unsuccessfully. REASON is the failure that refused the next Run, otherwise `Goal budget is exhausted`, `Tool effect completion is uncertain` or `Run interrupted without a terminal receipt; check Session history`. A pause requested between Runs prints only its pause line. A Run that cannot settle exits unsuccessfully with no answer.
- JSONL emits the Events of the latest Run, the `GoalStarted`, `GoalResumed` and `GoalFinished` facts of its Goal, and `SessionStarted` only for a new Session, never earlier Runs or unrelated Goals. Neither channel implies a completion receipt without a committed terminal Goal Event.

## Steering notes and pause

A user may send a steering note to a running Goal and pause it at its next boundary. The attached terminal composes notes and offers `/goal pause` ([terminal spec](./terminal/commands.md#interactive-commands-and-completion)); `exec` never steers. In the [serve protocol](./serve.md), `turn/steer`, `goal/pause` and `goal/resume` do the same. Notes are delivered only at the next committed boundary.

- A primary note is the Run-scoped `GoalSteeringNoteRecorded` (goal ID, Run ID, text); a child note is `AgentSteeringNoteRecorded` (goal ID, Run ID, AgentRun ID, text).
- A Run accepts any number of notes within its [generated per-Run bound](./limits.md#max_steering_note_bytes), shared by primary and child notes and counting labels: 8 bytes per primary label and 24 bytes per child label (`MAX_CHILD_STEERING_LABEL_BYTES`, covering `\n[child N / K] `), plus a 256-byte context reserve for headers. Each note is non-empty after trimming. Notes waiting for the same target merge after a blank line. An offer that would exceed the bound is refused and the caller keeps its text.
- A waiting primary note joins the next primary planning or synthesis call of its submission, including the first call of a next autonomous Run, and every later such call of that Run, as user input data labelled `steering_notes`. If the submission ends first, the caller keeps it as a draft.
- A child note targets one Active child of the latest Active Run by Session, Run and AgentRun identity; ordinals and model text confer no authority. At most eight children and eight waiting child notes are tracked beside the primary. It joins that child's next call only; an in-flight call is never interrupted, and a child may finish without receiving it. If the child settles, pauses or fails first, the caller keeps the text and reports non-delivery, or an unknown outcome until history confirms it.
- Notes are recording only: they never grant permissions, widen Tool authority, revise the plan or change catalogs, grants, leases, approvals or budgets. Primary notes never reach children, child notes reach only their target, and Tool review never receives notes. No note crosses a Run boundary.
- Later Runs see notes in history under labelled primary and `[child N / K]` blocks. Replay never re-delivers a note; a crash keeps it as history, and resume starts with no notes.
- Pause takes effect only at a boundary: before each primary or child call, after a Tool or Delegate outcome before dispatch, before synthesis and before the next autonomous Run. An in-flight Provider call is never aborted and its answer still commits; a requested Tool that has not dispatched never starts. A paused Run has the same receipts as Ctrl+C: Run Cancelled, Goal Interrupted and resumable. A pause between autonomous Runs keeps the committed Finished Run.

# Goals

## Scope and delivery boundary

This contract owns durable task-level Goal identity, Run linkage, budget admission, optional Tool-plan recording, completion reports and explicit interruption recovery. [Execution](./execution.md) owns Run and Provider-call semantics; [Tools](./tools.md) owns trusted grants and guarded effects; [Session](./session.md) owns the conversation boundary.

Goal segment telemetry is specified in [telemetry](./telemetry.md).

Every accepted task, including `exec`, has one durable Goal. There is no Run-without-Goal path. The Goal owns its pinned budget and resource settings across Runs, long Tool loops, delegation, review and in-Goal compaction. Budgeted execution reserves each actual Provider call and active action at its dispatch boundary. Active-Run Tool-history compaction includes the admitted objective, exact live instruction and include snapshots, the current approved plan, typed Goal facts and selected acknowledged observations. Between-Run compaction uses the canonical objective, plan, budget, resource settings, usage facts and history; it does not reconstruct discarded instruction or include contents, and the next Run supplies its newly admitted snapshots. Both request shapes fit the [generated compaction input limit](./limits.md#max_compaction_input_bytes).

Delivered: Goal lifecycle, atomic Provider-call reservations, Run-level active-time settlement with crash ceilings, the optional plan contract and typed success receipt, bounded reports, cross-StateRoot Workspace writer exclusion, Ctrl+C pause (any cancelled Goal stays Interrupted), coexistence with new prompts, `/goal resume`, Engine steering delivery, pause boundaries, the terminal steering composer and `/goal pause`. Guarded code rewind, replay and evidence invalidation follow the [rewind contract](./tools.md#checkpoints-and-rewind). Context reinjection and approved contract revision remain unavailable.

Editing constraints: [security rules](../../agents/security.md).

## Lifecycle, budgets and recovery

Before Workspace content is read or disclosed to a Provider, Engine validates the request, resolves Workspace identity, acquires Session and lineage locks, admits the Goal lifecycle and the next bounded Run or action envelope with enough terminal-tail capacity (each call in the envelope also covers its route switches and three same-route retry facts, as [execution](./execution.md#researcher-children) bounds them), and acquires the OS-user Workspace identity lock for a write-capable Implementation Goal. Each later Provider call and guarded effect receives its own serialized Store and Event headroom admission; there is no up-front reservation proportional to an unlimited Goal budget. The lock is keyed by admitted `(device, inode)`, shared across separate Session StateRoots and processes, and not taken by read-only Goals. At most the [generated Workspace lock-file quota](./limits.md#max_workspace_lock_files) is retained; quota exhaustion rejects new writers before disclosure or effects. Read-only Goals and Session history are unaffected. Recovery is manual: with no Arany process running for that OS user, remove the `guard/workspace-locks` directory beneath the account root (`~/Library/Application Support/dev.Arany.arany` on macOS, `~/.local/state/arany` on Linux); the next writer Goal recreates it. Store byte admission is conservative preflight, not a physical disk reservation.

A write-capable Implementation Goal holds the admitted Workspace lock only while a Run call is live, including autonomous continuations inside that call. Engine takes ownership from provisional admission before awaiting the first `GoalStarted`, `GoalResumed` or `GoalRunLinked` acknowledgment. The lease drops when the call returns, when its future is dropped, or after the terminal receipt, so a paused (Interrupted) Goal holds no writer lock. Explicit recovery reacquires the lock before Workspace content or Provider disclosure and fails with `WorkspaceBusy` while another writer holds it. A failed acknowledgment reports `GoalAdmissionUncertain` when the Goal is committed and otherwise returns the Store error.

- `GoalStarted` pins a UUIDv7 identity, objective, admitted include paths, Workspace identity, phase, explicit `GoalBudget`, the validated resource settings and `continues`, the source Goal of a [continuation](#budget-continuation) or null. Saved-preference changes affect new Goals only, and an explicit resume keeps the pinned values. New Goal admission snapshots the controller's positive available logical core count once; automatic Build jobs use cores, an explicit positive preference may lower it, and the process ceiling narrows the result. Unavailable, zero, unrepresentable cores or a preference above cores records null jobs and refuses Build plans without a payload/host probe; ordinary operations remain available. Each Build command inherits this positive `intent.limits.build_jobs`, at most `max_processes`, through the ledger; reducer validation binds it to the admitted settings. Settings, continuation Runs and explicit resume never recalculate an admitted Goal; a new Goal takes a fresh snapshot. Starting a Goal seals any unfinished predecessor as Interrupted, so at most one Goal is Running; a crash-left predecessor is paused rather than blocking.
- `GoalRunLinked` names each unique Run and repeats the pinned phase before `MessageAccepted`; an explicit resume keeps the stored phase and never takes one from the client. Replay rejects an unlinked message, duplicate IDs, Workspace drift, out-of-order transitions, a second active Run and budget overruns. Sticky cancellation is checked after acknowledged Goal start, resume and link appends and before `MessageAccepted`; a preaccept prefix creates no Run, Provider call or effect.
- Resume is explicit. `GoalResumed` follows a user's review of an interrupted Goal, starts a new Run and never retries the old Provider call or Tool effect; autonomous continuations append none. Recovery drops a trailing `GoalRunLinked` ID with no accepted message, so it consumes no Run budget and is never retried. If no Run was accepted, `--resume-goal ID PROMPT` accepts PROMPT only when it equals the preserved objective, omitting PROMPT resumes it, and any other PROMPT is `GoalUnavailable`. Headless `exec` uses `--session-id` with `--resume-goal GOAL_ID`; attached startup uses `--resume SESSION_ID --resume-goal GOAL_ID` and resumes at once without a prompt; idle chat uses `/goal resume` with no confirmation. Only the most recent Goal in the Session that is Running or Interrupted is resumable; older paused Goals are history. An ordinary prompt never auto-resumes, and while a Goal is paused a prompt starts a new Goal.
- An explicit resume whose paused Goal admits no next Run under [Autonomous Goals](#autonomous-goals) durably closes it as Failed with its bounded report, returns `GoalBudgetExhausted` and records no `GoalResumed`; the Goal is then not resumable. The reducer accepts this close only for a paused Goal whose budget is exhausted and rejects it while a Run is admissible. A crash-left unfinished Run is sealed as interrupted before this check. A crash after a `plan_recorded` Provider call but before its contract Event resumes only when the interrupted Run has no open or uncertain Tool observation; `GoalResumed` clears the pending plan wait and acknowledged read-only history is kept.
- Reopening an unfinished Goal projects it as Interrupted; an explicit `GoalResumed` seals an unfinished Running predecessor the same way. A closed Goal has exactly one terminal status, Completed or Failed, with a bounded report. Cancellation never closes a Goal, which stays Interrupted until explicit resume. A Run [stopped by a hook](./execution.md#accepted-outcomes) leaves its Goal open the same way: resume is explicit, subject to the existing budget and uncertainty admission, and an autonomous Goal never continues after it. A crash or Store failure before the receipt leaves an interrupted prefix rather than a fabricated result.

New Goals across attached chat, `exec` and `serve` default to unlimited aggregate Provider calls, tokens and active time, with at most [the generated Goal Run limit](./limits.md#max_goal_runs). This follows Claude Code's [unlimited interactive turns](https://code.claude.com/docs/en/cli-reference#cli-flags), Codex's [default-disabled rollout token budget](https://github.com/openai/codex/blob/342ed69a174c206c1de52a59491b131e0753cfa5/codex-rs/features/src/lib.rs#L1975-L1980) and OpenCode's [optional step limit](https://opencode.ai/docs/agents/#max-steps), including headless execution. There is no aggregate dollar-spend guarantee. Settings may select finite limits; pause, cancellation, durable usage accounting and pinned-budget resume still apply. Finite Provider-call and active-time values remain bounded by the [generated Goal maxima](./limits.md#max_goal_provider_calls) and [active-time maximum](./limits.md#max_goal_active_ms), and each request, Run, Tool, context, Event and native resource limit stays finite. A plan contract may request lower call, token or active-time limits and cannot widen the Goal's pinned settings. Replay checks a contract's active-time limit against settled Runs only; the Engine also counts the live Run's in-memory time before recording it. Known `ProviderCallRecorded` usage is preserved; missing usage stays unknown. With a finite token ceiling, unknown usage cannot count as zero or authorize another Provider call or effect.

The Store-action margin is 5,000 ms.

Goal exhaustion projects onto the latest accepted Run when `GoalFinished.exhausted` is true, or when an interrupted Run's committed counts prove the budget spent, subject to [accepted-outcome precedence](./execution.md#accepted-outcomes). Projection excludes a trailing unaccepted Run link and uses the committed refusal dimension when available; otherwise it uses settled facts. At refusal, select the effective finite limit in this order: tokens when known usage reaches the ceiling or usage is unknown, then calls when charged calls reach the ceiling, then active time when the remaining time is within the [Store-action margin](#lifecycle-budgets-and-recovery), otherwise Runs.

Before each actual Provider dispatch, including primary, child, review and compaction calls, Engine durably reserves one call once concurrency capacity is available. Store's serialized reducer rejects an over-budget reservation atomically, including racing children; queued calls are not charged. A started or cancelled call remains charged, and an unobserved reservation remains uncertain and is not reported as definitely sent. Failure and cancellation never refund call or token usage. A call or token budget reached before the next dispatch settles the Run as Failed and finishes the Goal with its report, rather than returning an unrecorded error.

Compaction calls use the Session compaction output bound and charge reported input, output and cache usage through this same ledger; the larger summary allowance does not grant additional Goal budget.

Provider active time begins once Provider concurrency capacity is available. A Tool action's active interval begins only after human approval and shared Guard capacity are available. Engine reserves the bounded interval before Workspace snapshot or cache transfer and native setup, so preparation, pre-GO checkpoint capture, payload execution and cleanup all count. The interval covers the unchanged immutable intent's full runtime plus bounded setup, cleanup and terminal work, and GO is sent only if that runtime still fits the remaining reservation. Guard `Ready` is not dispatch. If preparation consumes the interval, the Tool fails before GO and settles its observed time without an effect. Active time settles on monotonic elapsed time at the acknowledged boundary. An acknowledged action that exceeds the remaining finite Goal time is recorded and closes the Run and Goal as failed. Overlapping child calls charge wall time once. Provider and Guard capacity waits, approval waits and pauses are excluded; elapsed Engine processing time carries into the next active segment before a pause.

Per-action reservations and settlements live in Engine memory; the journal records active time at Run granularity and persists terminal refused quantities in the [budget refusal snapshot](#budget-refusal-feedback). `RunStarted` pins `active_deadline_ms`, the Goal's remaining effective active time when the Run starts (null for an unlimited dimension), and `RunFinished` records the Run's settled `active_ms`, which replay adds to the Goal. Each action-start Event (`GoalProviderCallReserved`, `GoalCompactionCallReserved`, `ToolProposed`, `ToolStarted`, `ToolActiveTimeReserved` and every lifecycle `HookStarted`) records `active_ceiling_ms`: the Run's settled time plus that action's reservation, which also covers a reviewed Tool that still follows its review call. A between-Run Goal compaction reserves at most its 120-second call plus the Store tail within the remaining Goal time, records that bound as its ceiling and journals its settled time in `ContextCompacted.active_ms`, which replay charges to the Goal. If the process exits before settlement, replay charges the latest ceiling, capped by the Run's deadline and by any plan contract recorded since, as conservatively charged, uncertain time: a crash charges the action that was open, not the rest of the Run's deadline, so explicit resume continues while time remains. A multi-call step commits its intents first, then commits `ToolActiveTimeReserved` for each primary call before its hooks, review or dispatch. This refresh uses the Run's already consumed time plus that call's action and hook bound; a later call's shorter initial intent ceiling cannot replace the currently executing action's bound, and earlier calls remain charged after a crash. Researcher Tools remain covered by their delegation reservation. Explicit resume never restores that charge. A primary Tool batch reserves Event and observation capacity for every call before its first intent, through `Action::ToolStep { calls }`; each call retains its `Action::Tool` terminal, integration, Supervisor and review headroom. Admission also retains the drain headroom for every editor holding a lease. Researchers retain their research `Action::Child` admission. A review call spends the Tool admission and is not admitted again. Admission adds `chain_len - 1` switch slots and three same-route retry facts per call of its actual role, including child waves and review calls. `Action::max_events_for` includes these bounds and terminal headroom under the [Session Event cap](./execution.md#persistence-bounds).

Provider roles, all selected [roster candidates](./provider.md#named-roster-presets) and fallback attempts share this same ledger; profile count creates no separate budget. Explicit roster-bound recovery follows the [same-selection rule](./session.md#roster-recovery-and-compaction). A committed `ProviderFallbackUsed` or `ProviderRetryScheduled` charges one additional call while preserving the open step reservation and its active-time ceiling; a retry's wait counts as active time. Failed-call usage stays unknown, so a finite token budget refuses a replacement attempt; unlimited tokens do not imply free failed calls. The final successful attempt contributes only its reported usage and cache counters. After protected usage and cache uncertainty facts, the Goal report retains at most eight retry (role, attempt, cause, delay) and fallback (role, from, to) notices with the warning that failed calls may have consumed usage before optional positive evidence; additional notices produce the ordinary omission marker. A post-Goal manual compaction does not amend an already closed Goal's usage or receipt. [Provider selection](./provider.md#per-role-selection-and-fallback) and [switch replay](./execution.md#admission-persistence-and-recovery) own the other routing rules.

Tool dispatch preserves enough bounded terminal-tail capacity to record the Tool disposition and Run receipt.

With a finite token ceiling, Engine admits at most one concurrent Provider call, including queued Team children, and observes each result before filling another slot. A Tool or Delegate outcome at the exact known-token cap, or with unknown usage under a finite cap, fails before `ToolRequested`, `ToolStarted` or child admission. A matching answer at the exact cap may complete if the success criterion is met; unknown usage does not block an answer. Unlimited call or active-time preferences remove only that Goal dimension's ceiling; they do not remove per-action, request, Run-count, Store, Tool or Guard bounds.

Goal report payloads are bounded by the [generated Goal report limit](./limits.md#max_goal_report_bytes); the summary and each listed item are at most 2 KiB, with at most 32 changes, evidence items and unresolved items. Engine derives changes, evidence and unresolved facts from committed, attested Tool outcomes and terminal Run facts. Skipped checkpoint capture and pruning notices, cache publication and Tool failure or uncertainty facts are recorded before optional positive evidence, so a full report cannot hide them. If lower-priority facts must be omitted to keep the byte and item bounds, the report includes an omission notice. A successful Command keeps its evidence when cache publication is rejected or fails, whenever the report has room; an uncertain cache publication directs recovery to Session history rather than Workspace inspection. Engine truncates a longer model summary at a UTF-8 boundary, reserving room for the priority facts and the omission notice, and never fabricates successful evidence from a Provider summary. If storage fails before `GoalFinished`, replay leaves the Goal interrupted. The report also states `cached_input_tokens`, the total cache-read input tokens across the Goal's Provider calls. Replay requires it to equal the Goal's accumulated cache-read total. It is information only and never changes budgets.

### Budget refusal feedback

Every newly recorded budget-caused Goal closure has a required nullable `GoalFinished.budget_refusal` containing a non-null `BudgetRefusal`; other closures carry null. This includes an explicit out-of-budget resume or failed next-Run admission that closes an existing Goal. Version-7 migration supplies null: historical refused quantities remain unavailable. The record never changes charges or grants a continuation. Exhaustion allows no extra Provider call, retry, fallback or compaction to explain it. An already committed answer remains intact; cancellation, hook stops and unknown effects retain [Execution precedence](./execution.md#accepted-outcomes). A failed Provider call on its final allowed attempt remains a Provider failure unless a separate budget boundary actually stops the Run. A delegation-only deadline or recoverable Tool timeout/runtime refusal is not Goal exhaustion.

The closed record contains `dimension` (`tokens`, `calls`, `active_time`, `runs`), `cause` (`exhausted`, `unknown_usage`, `insufficient_headroom`), `action` (`provider`, `tool`, `delegation`, `compaction`, `run`, `resume`), required nullable `run_id` and `agent_run_id`, unsigned `used` and finite `limit`, independently nullable `requested` and `required_minimum`, `token_usage_unknown`, and `charge_basis` (`observed`, `conservative`). IDs belong to the Goal and actor; Run/resume admission has null IDs. Counts use units, tokens use known charged tokens with explicit unknown usage, and active time uses milliseconds. The serialized record is bounded by the [generated budget-refusal limit](./limits.md#max_budget_refusal_bytes) and contains no paths, arguments or free text. The requested amount is unclamped and present only when captured at admission. Unknown next-call token demand has no invented token reservation. The minimum active admission includes carried processing time, the [Store-action margin](#lifecycle-budgets-and-recovery) and one millisecond of useful headroom (a zero-duration Tool pause or delegation boundary requires only carried processing plus one millisecond); reaching that margin below the ceiling is insufficient headroom, not elapsed exhaustion.

Engine captures refusal under serialized ledger admission and carries it through Run settlement without refund or double charge. `GoalFinished` follows the Run's terminal facts, using reserved terminal capacity. `used` is usage at refusal, separately labelled from final settled usage after terminal-tail work. Reducer validation checks the pinned effective finite limit, actor membership, cause and arithmetic, unknown/conservative qualifications and the final committed usage bound. A refusal snapshot's active usage cannot exceed valid final settlement. Strict replay reads these facts without dispatch. Before any Goal admission or a terminal acknowledgment, only a bounded local admission/infrastructure diagnostic may describe available values. If a failed terminal append is proved absent, its refusal details are labelled uncommitted; if commitment is possible, the existing `GoalAdmissionUncertain` diagnostic requires inspecting Session history without claiming the refusal is absent. A refused idle compaction without a Goal closure uses that local diagnostic. A failed or lost acknowledgment never authorizes a fabricated durable receipt; reopening exposes the committed prefix and any conservative recovery facts, with missing refusal detail explicitly unavailable. A budget-failed Run without a Goal receipt keeps its existing stop semantics and can display only proved committed counters, excluding unaccepted links.

The local Arany status uses one committed Goal/Run projection across attached output, `exec`, `show`, serve and ACP. It names the actual dimension, pinned limit, used-at-refusal, known requested/minimum quantities, unknown tokens, Store margin and conservative charges. The report retains at most eight recent failed, denied, conflicted or limited Tool facts across primary and children, newest first, with actor and compiled Tool labels, available exit/limit codes, bounded admitted excerpts and an omission count. Unknown/blocking facts precede optional Tool detail. Denial summaries use compiled labels without raw hook/client reasons or permission rules; excerpts use shared control/bidi escaping within the existing 2 KiB item and generated Goal report bounds. Overflow drops optional details, never the terminal cause. This follows [Codex's typed failed/declined items](https://developers.openai.com/codex/app-server#approvals) and [Claude's specific Tool failures](https://code.claude.com/docs/en/hooks#posttoolusefailure), under Arany's durable-budget constraint. Reports are Arany status, never assistant `MessageCommitted` text; JSONL stays canonical Events. Linux and macOS share this policy.

The shared `budget_refusal_feedback` lookup requires a committed refusal record. `exec` retains its looser admission-refusal predicate as an explicit fallback after an exhausted resume, and formats the selected budget-stopped Run's committed facts. Committed output receipts format their exact Run so another Run in the same Goal cannot supply its answer or stop text.

## Worker accounting and verification

Each [editor](./execution.md#worker-journal-protocol) requires Implementation, a committed plan and a write-capable parent. Its lease/catalog intersect parent, plan and definition. The Goal's Workspace writer lock covers editor work and primary verification. Shared [call and active-time accounting](#lifecycle-budgets-and-recovery) applies to editor work.

The Goal and editor criteria are distinct. Satisfying the Goal criterion does not waive the [worker journal protocol's verification requirements](./execution.md#worker-journal-protocol). That protocol also owns the rules for worker stops, cancellation and retained effects.

Goal receipts derive changes from observations, including the child's effects. An unfinished editor intent is subject to the same recovery refusal as an unfinished primary effect. No private cleanup or containment record can waive that refusal.

Evidence owners: [Engine team corpus](../../crates/arany/tests/engine_run/team.rs), [native live-editor journeys](../../crates/arany-cli/tests/guard_runs/worker.rs), [shared team scenarios](../../crates/arany/src/test_support/worker_teams.rs), [live replay](../../crates/arany/src/session/reducer/worker/workspace_tests.rs), [Engine parent-grant refusal](../../crates/arany/tests/engine_run/shared_editors.rs), and shared `assert_action_bounds`.

## Autonomous Goals

`GoalStarted` pins an `autonomous` flag. An autonomous Goal's Engine admits its next Run after each Run that ends without finishing the Goal, with no user input. The Run input is the pinned objective; earlier Runs' results and reports are ordinary Session history. Each iteration runs the normal Run admission, budget, linkage and effect rules. A resume with no new text (`GoalRequest::resume`, empty `RunRequest.objective`) also runs the pinned objective, and a resume of an autonomous Goal continues this loop. A non-empty resume text is used as before.

A Run that Finishes without the plan's success criterion is a Run boundary while another Run is admissible within the pinned budget. Otherwise the same answer fails the Run, and the Goal fails with its report. Plain prompts and other non-autonomous Goals keep the single-Run rule. Stop conditions:

- A Finished Run whose success criterion is satisfied, or whose Goal has no plan contract, completes the Goal.
- A Finished Run whose criterion is unsatisfied, and whose Runs, Provider calls or known tokens admit no further Run, fails the Run and the Goal with its report. The Engine decides these dimensions when the answer is recorded, so the next Run is never admitted. Active time is decided at settlement, below.
- A Failed Run fails the Goal, as for any Run.
- Cancellation stops the current Run and starts no further Run, for every Goal kind. A Run that already Finished keeps its committed outcome, which the call returns, including when cancellation arrives during the next Run's admission before `MessageAccepted`. The Goal records no terminal receipt and stays open, so reopening it projects it as Interrupted for explicit resume with its pinned objective.
- Any other failure to admit the next Run (Workspace identity or input, Provider selection, request validation, or a Store load or append) also keeps the committed Finished Run. The submission's result carries that Run's outcome with the failure as its stop reason, so the answer is never lost. The Goal stays open, as above.

Attached `/goal OBJECTIVE` starts an autonomous Goal, and `/goal resume` continues the most recent paused Goal even after newer Goals finished; `/goal` shows its read-only status and names a paused Goal that is not the shown one. Paused and new Goals coexist: a pause never refuses a plain prompt or `/goal OBJECTIVE`, and starting a Goal does not resume an older one. The [terminal spec](./terminal.md) owns those commands and their notices.

Active time for the next Run is judged when the Finished Run settles its active time in `RunFinished`, so time spent recording its terminal facts can exhaust the Goal. If that settlement leaves an unsatisfied planned Goal with no admissible next Run, the Finished Run stays committed and the Engine records the autonomous Goal as Failed with its bounded report in the same segment. The submission's result carries that Run with stop `GoalExhausted`. "No admissible next Run" is one rule for every dimension: fewer Runs linked than `max_runs`, fewer Provider calls charged than `max_provider_calls`, less active time than `max_active_ms`, and, under a finite token ceiling, known usage with no unknown part and below that ceiling. Replay accepts a Failed receipt over a Finished Run only for an unsatisfied planned Goal that admits no next Run under this rule; a planless or satisfied Goal completes, and any other Failed receipt needs a Failed Run.

### Budget continuation

Budget exhaustion is terminal and an exhausted Goal is never reopened. `/goal continue` and `exec --session-id SESSION --continue-goal GOAL` start a new Goal in the same Session, seeded from the most recent Goal closed by budget exhaustion that no later Goal continues. Closed by budget exhaustion is journaled: `GoalFinished.exhausted` is true when the Engine closed the Goal because its budget ran out (a Run stopped by the budget, an unsatisfied planned Goal with no admissible next Run, or an out-of-budget resume). Replay accepts `exhausted` only on a Failed Goal that admits no next Run or whose remaining active time is within the [Store-action margin](#lifecycle-budgets-and-recovery) of its limit, and requires it when an unsatisfied planned Goal has no admissible next Run and on an out-of-budget resume; it verifies only that budget arithmetic, so the flag is a necessary condition and a forged one can at most allow a user-initiated fresh-budget continuation. A Provider failure on the last allowed call is not a budget stop. A Goal whose last Run left a Tool without a known outcome is not continuable, and a Goal that failed for any other reason is a failure and not continuable even at an exhausted budget. The new Goal keeps the source's objective, phase and autonomous flag, takes a fresh budget and resource settings from the current saved settings (`exec`: the defaults), starts with no Runs, lease or reservation, and journals `GoalStarted.continues` naming the source. Continuation never parses the stored objective for `@` mentions. Both attached and headless continuation reuse the original Goal's recorded admitted include paths, including an empty list, across every subsequent Run. Resuming or advancing any existing Goal also uses its recorded list, never replacement request paths. Each path is read under the current admitted Workspace capability and existing input bounds; recorded paths confer no authority. A continuation request’s nonempty include list must equal the recorded list or admission fails. `GoalStarted.include_paths` is required nullable: new Goals record their complete list (at most 16 relative UTF-8 paths of at most 512 bytes each, using the same control, traversal and protected-name exclusions as Tool paths); migrated Goals with an unknown list record null. An unknown list refuses continuation or an existing Goal's next Run with `GoalIncludesUnavailable` and guidance to start a new Goal with explicit inputs, without a Provider call or new Event. The source's plan contract, results and report are ordinary Session history, so the first Run records its own contract. Replay rejects a `continues` that is not the latest unclaimed Goal closed by budget exhaustion in the Session or whose objective, admitted include list, phase or mode differs. With no eligible source, or a source that is not that Goal, the Engine returns `GoalNotContinuable` ("no exhausted Goal is available to continue") with no Event, Run or Provider call. A paused Goal that is out of budget first needs `/goal resume`, which closes it Failed.

## Rewind and Goal recovery

A restored Workspace rewind leaves a paused Goal paused and charges or refunds no call, token, Run or active time. It invalidates file success evidence for changed paths and effect/command criteria that may depend on them; fresh verification is required. A later initial plan cannot reuse a pre-rewind read for a changed path. Worker verification for overlapping leased paths is invalidated across historical Runs. The bounded rewind history fact enters subsequent resume context and the Goal report. An open or Uncertain rewind after the Goal's last Run blocks GoalResumed and budget continuation, including after reopen; it is never retried. A fresh Goal may inspect the Workspace, but this does not clear the earlier Goal's uncertainty. Fork inheritance never copies Goal budgets. [Session replay](./session.md#rewind-planning-and-replay) owns checkpoint chains and sealing. Runtime code restore follows [Tools](./tools.md#checkpoints-and-rewind).

## Initial plan contract and success receipt

Primary host dispatch clears prior file-success and worker-verification evidence before spawn; a later read or verification must establish current state. A confirmed timeout/output stop remains Limit and confirmed cancellation remains Cancelled, preserving the existing Goal pause/resume contract. Unknown dispatch or teardown remains Uncertain and never retries itself. Reports retain possible non-rewindable host effects and incomplete inventory coverage. [Tools](./tools.md#primary-host-commands) owns authority and supervision.

Planning is optional. The primary may call `arany_plan` with a `GoalPlanContract` when a long autonomous Goal or an exact success criterion benefits from a recorded plan. It occupies one Provider step: Engine validation precedes `GoalPlanContractRecorded`, and the next request receives a correlated result naming the recorded path, command, Skill and MCP scope. Invalid or replacement plans follow the [proposal refusal continuation](./execution.md#accepted-outcomes). The Tool never grants authority. Without a recorded plan, every call permitted by the Goal phase and pinned grant proceeds through the permission mode, hooks, Supervisor and Guard. Goal budgets remain Engine-enforced from `GoalStarted`, independently of model-declared arithmetic. Like Claude Code TodoWrite and Codex update_plan, planning is optional; Arany deliberately diverges by binding a recorded plan's scope and success gate so model text can only narrow authority.

The contract contains a mission (at most 2,048 bytes), at most 64 sorted non-overlapping Workspace-relative paths (512 bytes each), at most eight sorted command names (64 bytes each), a `skills` list of at most 64 sorted exact `{name, resource}` bindings (Skill name at most 64 bytes, resource at most 512), at most 64 sorted MCP `{server, tool}` bindings (server at most 64 bytes, tool at most 128), one typed success criterion, a bounded Goal budget, a `default` or `build` resource class and an optional command timeout. The full serialized contract is limited to 8 KiB and receives the ordinary credential-reflection check before persistence, including native wire sibling fields. Resource requests are checked against the settings pinned at Goal start and never widen executable, path, Skill, MCP or network grants. Plan approval latches the requested values. In-range Accept or Auto operation uses them, while a request above the saved maximum produces a non-dispatched `Limit` receipt that names the requested timeout and pinned maximum and tells the user to lower the request or change `/settings`. The Goal keeps its pinned settings, and approval never bypasses the configured maximum; the Ask effect approval stays in force for admitted operations. The immutable Tool intent and Guard receipt carry the exact effective limits. A null Skill resource binds only `SKILL.md`; another resource must be named exactly. Skill bindings intersect the admitted Skill grant and cannot grant or discover a Skill. When a contract is recorded, every requested operation must fit both its scope and the admitted Tool grant. [Accepted outcomes](./execution.md#accepted-outcomes) owns Goal-phase restrictions. Command admission checks its configured command independently from the writable path scope, and returned changeset paths are checked against the path scope. An internal changeset outside that scope is durably recorded as `Denied`, with no Guard receipt or dispatch, and replay rejects any successful or guarded out-of-scope integration. MCP scope identifies both server and tool.

Success criteria are one exact eligible Tool call with the latest matching successful attested receipt (offered only when the catalog admits such a call), an exact Workspace file digest, or bounded exact Workspace file content of at most 8 KiB. `tool_call_succeeded` applies to `Command`, `CommandUnguarded` (an attested host run authorized under the [host-command contract](./tools.md#primary-host-commands), which the report marks unguarded), `Write`, `Edit`, `MultiEdit`, `Mkdir`, `Skill` and `McpCall`. Read-only `List`, `Read`, `Search` and `McpList`, plus internal `ApplyChangeset`, cannot be success evidence, and a generic successful Read is not sufficient. For a command with file changes, the successful changeset integration receipt is also required. For file criteria, replay and live admission use the latest relevant verified read or mutation: a later failed, unattested or uncertain observation, a changed digest, a deletion or a published changeset invalidates an earlier match until a fresh verification succeeds, across Goal Runs. An exact-content criterion is bounded plan data; it neither writes a file nor invents unknown bytes. A Goal with a Tool plan cannot complete successfully until its criterion is satisfied. A recorded contract cannot be replaced.

## Current-format replay and `exec`

Goal Events are additive facts within the current internal format ([execution](./execution.md#admission-persistence-and-recovery)); older journals reach the reducer only through the [journal migration](./execution.md#journal-migration), never a compatibility reader. Saved display and execution preferences use the single strict version 4 `ui-preferences.json` record, limited to 1 KiB; a version 3 record reaches the decoder only through the [record migration](./execution.md#json-record-migration), and invalid or unsupported records are never converted or overwritten: attached chat, task submission and `/settings` run on defaults until `/settings` saves a replacement, while `exec` and `serve` refuse them. Replay requires Goal linkage for every accepted task. Histories without required linkage, with missing fields, invalid transitions or exceeded bounds reject intact; they are not upgraded, deleted or interpreted optimistically. Explicit user-confirmed history reset remains governed by the [terminal contract](./terminal.md#setup-and-account-choices).

`exec` receives its typed settlement through the [in-process Server connection](./serve.md#scope-and-related-contracts) and reopens committed history before projecting its exact Run and Goal. Budget-stop feedback uses that receipt's Run; the looser exhausted-resume fallback [above](#lifecycle-budgets-and-recovery) remains distinct. The [terminal contract](./terminal.md#entry-modes-and-channels) owns its deterministic output and signals.

Invalid history remains ineligible for resume, fork, `exec --session-id`, and compaction. The `show` projection and output contract are owned by the [terminal spec](./terminal.md#entry-modes-and-channels).

`exec` creates a Goal for every invocation and keeps its text and JSONL channels and its terminal exit behavior. A first SIGINT during `exec` cancels its active Run: the Run keeps its Cancelled receipt, the Goal stays open and is projected as Interrupted, and stderr names the resume command `arany exec --session-id SESSION --resume-goal GOAL`. For a roster-bound Run that hint includes its explicit `--profile PRESET` selector. A second SIGINT, SIGTERM or SIGHUP stops waiting after a bounded grace and reports the stop on stderr. A cancelled autonomous loop prints its committed answer before the pause line. A cancelled Run exits unsuccessfully. In JSONL, the stderr reason is `error: Run cancelled`, `error: Run failed`, `error: Run stopped by hook[: REASON]` (REASON escaped; the Goal stays open and the pause line follows), or `error: Goal paused before completion` for a finished Run whose Goal stays open, and the pause line follows. An exhausted explicit resume exits unsuccessfully with `error: Goal budget is exhausted` and no Run. `exec --goal OBJECTIVE` starts an autonomous Goal and `exec --session-id SESSION --continue-goal GOAL` starts a [continuation](#budget-continuation) with the default budget (exclusive with a prompt, `--goal` and `--resume-goal`); its exit status follows the last Run, so success requires that Run to finish. When an autonomous loop stops after a committed Run, `exec` prints that Run's committed answer, writes `error: Goal stopped after a committed Run: REASON` to stderr and exits unsuccessfully. REASON is the failure that refused the next Run, otherwise the projected stop: `Goal budget is exhausted`, `Tool effect completion is uncertain` when the next Run committed an effect with no known outcome, or `Run interrupted without a terminal receipt; check Session history` when it stopped before any such effect. A pause that SIGINT requested between Runs keeps only its pause line. A Run that cannot settle exits unsuccessfully with its projected stop and no answer. JSONL preserves canonical sequence and Event scope. It selects the Events scoped to the latest Run, the session-scoped `GoalStarted`, `GoalResumed` and `GoalFinished` facts for exactly the Goal linked to that Run, and `SessionStarted` only for a newly created Session. It excludes earlier Runs and unrelated Goals and never assigns a Run ID to a session-scoped Goal Event. On cancellation or crash, neither output channel implies a completion receipt if replay has no terminal Goal Event.

## Steering notes and pause

A user may send a steering note to a running Goal, and may pause it at its next boundary. The attached terminal composes notes and offers `/goal pause` as specified in the [terminal spec](./terminal.md#interactive-commands-and-completion); `exec` never requests steering. The [serve protocol](./serve.md) is a second caller: `turn/steer` and `goal/pause` use the same handle, and `goal/resume` is the explicit resume above.

Child messaging follows [Claude Code's teammate transcript messaging](../research/next-step-decision-register.md#d-10--terminal-contract). The pinned Codex source verifies parent-owned children as view-only, so this decision does not claim universal Codex live-child input. Arany's committed next-boundary delivery preserves its journal-first guarantee.

- A primary note is the Run-scoped Goal fact `GoalSteeringNoteRecorded` (goal ID, Run ID, text). A child note is `AgentSteeringNoteRecorded` (goal ID, Run ID, AgentRun ID, text). Replay rejects a missing, wrong or unlinked scope.
- A Run accepts any number of notes within its [generated per-Run bound](./limits.md#max_steering_note_bytes). Primary and child notes share this allowance, including recorded and waiting text, merge separators and every history label: 8 bytes for a primary label and 24 bytes for a child label (`MAX_CHILD_STEERING_LABEL_BYTES`, covering `\n[child N / K] `). Rendered labels and notes stay within the generated per-Run bound; fixed history headers fit the additional 256-byte context reserve. Each note is non-empty after trimming. An offer made while another note for the same target waits merges into it, separated by a blank line. Different targets never merge. An offer that would exceed the bound is refused, and the caller keeps its text.
- A primary note is accepted only when its Run is the latest and Active, its Goal is Running with that Run active, and the Run's primary AgentRun has an open planning or synthesis provider reservation not yet settled by `ProviderCallRecorded`. A Tool review reserves under the primary AgentRun too, so replay rejects a note while a Tool observation is pending. Notes before that reservation, after its outcome, during a child reservation, after the Run ends, for another Goal or beyond a bound reject replay.
- The Engine takes the waiting primary note only inside that open reservation, journals it, then adds it to that call; a call cancelled before dispatch takes no note. Taking a note reserves its Run's quota. The caller's note waits for the next primary reservation of its submission, including the first primary call of a next autonomous Run. If the submission ends first, the caller keeps it as an ordinary retained draft.
- Every later primary planning or synthesis call of the same Run receives the Run's recorded primary notes in order, as user input data labelled `steering_notes`. Notes never grant permissions, widen Tool authority or revise the plan contract. Primary notes never reach children. Child notes reach only their exact actor, and Tool review never receives notes.
- An attached, latest Active Run's Active child accepts a text-only offer while its Goal is Running. The target binds Session, Run and AgentRun identity; ordinals and model text confer no authority. At most eight children are registered and eight child offers wait, in addition to the primary offer; a ninth concurrently active child is refused with its own notice. Expired entries remain withdrawable and consume pending capacity until withdrawn. No child note crosses a Run boundary, revives a child, creates an additional call or moves to a sibling or the primary.
- The Engine takes a child note only after that actor's own ChildWork reservation commits, while it is still active and has no pending Tool observation. Unrelated primary or sibling Tools do not disqualify it. The note Event commits before the request can dispatch. An in-flight call is never interrupted to deliver a note; a child may finish its final call without another boundary. Taking a note charges quota atomically, including on append failure; an ambiguous append is never automatically retried or reoffered. Commitment acknowledges recording, not remote receipt. On settlement, pause or failure the caller retains unacknowledged text and reports non-delivery when withdrawal succeeds, otherwise unknown outcome until validated history confirms it. Replay accepts a child note only from its committed `AgentSteeringNoteRecorded` for a latest Active Run, a Running Goal, an Active child with an open ChildWork reservation, no worker or hook stop, no pending own Tool observation and room in the Run's allowance; it stores the text in that child's history, rebuilds it from the journal alone, and never re-delivers or re-offers it.
- Subsequent ChildWork requests preserve earlier notes at their original continuation boundary, after stop-hook feedback or the latest Tool step, or in the request head before any continuation. Existing route and retry attempts reuse the already-recorded request. Notes cannot change catalogs, grants, leases, approvals, plans or budgets.
- Later Runs carry the notes in their history turn and compaction input under labelled primary and `[child N / K]` historical child-note blocks, and the Engine reserves the bounded context bytes for them. Replay never re-delivers a note. A crash that leaves its Run interrupted keeps the note as history on that Run; an explicit resume starts a new Run with no notes.
- Pause is a sticky request on the caller's steering handle. The Engine turns it into the Run's cancellation only at a boundary: before each primary call; after a valid Tool or Delegate outcome, before its plan contract, Tool dispatch or children; before synthesis; before the next autonomous Run; and before each child call or child Tool dispatch. In-flight child calls finish and are recorded. A pause recorded during Tool review or the approval wait stops the Run before dispatch. An in-flight Provider call is never aborted, and an answer it returns still commits. A requested Tool that has not dispatched never starts; its observation records that no operation was dispatched. A paused Run has the same receipts as Ctrl+C: its Run is Cancelled and its Goal Interrupted and resumable. A pause between autonomous Runs keeps the committed Finished Run and leaves the Goal Interrupted.

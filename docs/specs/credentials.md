# Saved credentials

## Scope and related contracts

This contract owns saved-account scope, protected storage, selected-item startup authorization, replacement and recovery. Behavior is shared across OSes; native storage mechanisms and support evidence can differ, and outstanding native account and stalled-store checks stay in [next steps](../../NEXT_STEPS.md#beta-2-and-broader-release). Provider admission belongs to the [Provider contract](./provider.md); OAuth, verified identity, consent and token renewal to the [ChatGPT contract](./chatgpt.md). [Folder trust](./tools.md#folder-trust-and-approvals) owns consent ordering; the [terminal contract](./terminal.md#setup-and-account-choices) owns account choices, interactive cancellation and account-inspection display. Editing constraints: [security rules](../../agents/security.md).

Session State keeps Tool output outside the Workspace in private `0700` directories; output files and the per-Run `writer.lock` are `0600`. The [output spill contract](./tools.md#limits-and-failure-behavior) owns layout and retention.

## Account scope and identity

A saved Provider Account belongs to one effective OS user across that user's Sessions and StateRoots, never the whole machine. Account metadata and its replacement lock live under the effective user's passwd home, independently of `HOME`, XDG variables and Session `--state-dir`: `.local/state/arany` on Linux and `Library/Application Support/dev.Arany.arany` on macOS. Keyring items stay in that user's OS credential store. Account readers use only this root; they never inspect or move records from environment-selected Session roots. Session-root configuration has its own contract.

Admission walks each path component through a no-follow directory handle and never canonicalizes a supplied path or redirects an account to an environment-selected home. Private account and Session directories need physical paths with no symlinked ancestor, so macOS `/tmp` and `/var` aliases reject (native fixtures use `/private/tmp`); root-owned sticky temporary ancestors are admissible. New components are created `0700`; existing leaves need the current owner and private permissions. Opening creates no records or locks. New state and temporary files use exclusive creation in user-private directories with least permissions. Predictable shared temporary paths, links, non-regular objects, unexpected owners or ACLs and state inside an untrusted Workspace reject. Private leaves, including State records, open nonblocking before their type check, so a FIFO fails admission instead of blocking.

Debug builds alone accept `ARANY_TEST_ACCOUNT_ROOT`: an absolute path with explicit `HOME` and XDG settings beneath a non-root fixture parent; Store admission rejects an environment-selected state root outside that parent. The macOS Keychain fixture likewise accepts `ARANY_TEST_KEYCHAIN_ROOT` only in debug builds, selecting a fixed file inside an admitted private root. Optimized builds reject both before any OS-store access.

Native API-account records validate, on read and write, the exact OpenAI or Anthropic Provider, UUIDv7 identity, bounded printable key, and either a reviewed model and effort or a bounded model ID with explicit effort. Each record carries an explicit nullable workspace scope; a non-null scope must be a validated Anthropic API workspace. Unsupported versions, missing fields, invalid scope and cross-Provider scope reject. Saved scope is never reconstructed from environment variables.

A Session stores the saved account UUID, never its credential. Native Run and catalog use first resolve that UUID and Provider against the current protected record, so a replaced account is unavailable to an older Session. Environment-backed access never falls through to saved credentials, and saved access never falls through to environment credentials. A saved model and effort is not compatibility evidence: Run admission and strict request and outcome validation still apply, without a mandatory synthetic check.

Custom routes read only their selected `ARANY_PROVIDER_*` environment reference after destination and evidence admission; saved accounts never supply them. Kimi Code console keys use `ARANY_PROVIDER_KIMI_CODE_KEY`, distinct from Kimi platform keys (`ARANY_PROVIDER_KIMI_API_KEY`) and native Anthropic credentials. The GLM candidate uses only `ARANY_PROVIDER_GLM_STANDARD_KEY`, holding a newly issued Standard key whose console classification and standard billing the owner confirms; opaque key bytes cannot establish that. Compatible and Coding Plan keys are excluded. These keys create no saved account or OAuth flow. A missing selected key, a 401, a redirect or model drift never selects another key, vendor, billing route or native account. The [custom destination contract](./provider.md#custom-destinations-and-routing) owns authentication headers and scope.

Roster admission reuses the current selected-account loaders. Several models or efforts on one admitted identity are supported; any unsupported combination of saved native or ChatGPT accounts, including an unused candidate, refuses before Workspace content. There is no roster credential-slot enumeration or account-store expansion; adding one needs a separate security and account change. Environment-backed native and saved sources keep their own admission rules. [Provider presets](./provider.md#named-roster-presets) own route composition and candidate ordering.

## Metadata-only storage inspection

The explicit local storage report may admit the fixed account root through private-directory admission without opening history, account payloads, selected credentials, the account lock or the OS keyring. It may stat private regular files, including secret-containing ones, only into aggregate sizes and counts; record names and contents are never shown. It authorizes no model read, account selection, credential access, repair or creation, and an explicit Session root never changes account-root resolution. Missing roots stay absent; malformed account or history payloads do not prevent metadata inspection. Reports never enter model input, Events, logs, telemetry or MCP. The [storage inventory contract](./tools.md#local-storage-inventory) owns coverage, bounds, unsafe-object refusal and deduplication.

## Backend selection and startup

Setup prefers the OS keyring. An unavailable, unpinned store may offer a separately warned, explicitly selected private-file backend; a locked store reports a locked error. The checked backend marker pins keyring storage without a key, or file storage with the account. Read, write or authorization failure on a pinned keyring never downgrades storage.

Bare startup first reuses the last explicit saved-source preference, selecting Provider, account and model metadata without loading credentials; disconnected ChatGPT metadata cannot restore access. Without a preference, checked record presence determines the available saved routes before either payload is read. When API and ChatGPT records coexist, the billing-route choice is explicit. Cancellation reads neither payload and creates no Session. An invalid selected record never falls back to the other route. A native keyring item without a current backend marker is not a configured account and is never loaded, even when a ChatGPT index exists; explicit native setup admits it, and inspection without the marker probes backend availability but returns no account.

On Linux, Secret Service admission accepts one bounded `unix:path=` or `unix:abstract=` address with an optional exact GUID, or the bounded absolute `XDG_RUNTIME_DIR`. With both absent, the client connects directly to `/run/user/<uid>/bus` without autolaunch.

### Selected-item authorization

After folder consent and account choice, attached startup authorizes only the selected keyring-backed Arany item, before Provider catalog, preflight or chat input. The fixed service and validated slot exclude enumeration, whole-store unlock and ACL changes. The status-only operation checks native UUID and Provider identity, or the selected ChatGPT slot, and returns no credential. Unconfigured, environment-backed, custom and private-file selections skip OS-store access.

Native-account discovery without a remembered preference uses the same cancellable interactive wait for its bounded account read, then discards the key before chat, with no second authorization or credential cache. Neither path refreshes tokens, starts sign-in, grants Run authority or calls a Provider. The selected account is revalidated after authorization and its credentials reloaded at use.

Interactive startup access has a supervised two-minute human-interaction deadline. Cancellation kills and reaps the helper and restores the terminal. Denial, missing or invalid items, identity replacement and timeout give safe startup feedback and submit no initial or resumed objective, with no Provider call, sign-in, automatic retry or fallback. Routine reads, writes and deletion keep five-second deadlines, after which the helper is killed and reaped. On macOS the OS owns per-item permission persistence; Allow Once may prompt again on later access.

The keyring helper is a short-lived copy of the same binary with a fixed service, bounded private pipes, a cleared environment and `/` as its working directory. Startup authorization validates the identity inside the helper. Test builds require an absolute `ARANY_TEST_EXE`, which shipped binaries ignore; synthetic input comes through a private file, not a parent pipe.

## Storage, replacement and recovery

An incompatible or malformed saved account or model preference never prevents opening the attached CLI. Arany shows recovery guidance and keeps access unconfigured until the user selects valid access; it never switches billing routes, loads another credential or submits an initial objective automatically. A recoverable failure during initial `--setup` returns to the composer; terminal failure and shutdown keep their normal exit behavior. Headless commands reject with attached-setup guidance.

Setup offers an explicit local reset for invalid selected-route data, Back focused. Confirmed reset discards only that route's checked account records, its ChatGPT registration when applicable, and saved model choices; conversations, folder trust and other-route accounts stay. The bounded records are snapshotted before confirmation and rechecked under the account lock; a concurrent change refuses reset. Cancellation writes nothing. Unsafe or over-limit filesystem objects cannot be reset through this flow. Invalid saved model choices can be reset separately, keeping all accounts. A confirmed reset is a completed local effect even if setup is later cancelled.

Reset never interprets an unsupported format, migrates records, enumerates the password store or revokes remote access; it explains that old password-store entries may remain and that reset is local. New setup follows ordinary storage consent and verified sign-in.

A partial storage failure is [Uncertain](./execution.md#effect-outcomes) and claims no rollback. During setup, once a removal or write has completed, any later preference, account-index, registration or keyring failure, including an ordinary storage error, keeps that uncertainty and blocks setup continuation. Failed directory synchronization after a record rename or unlink is likewise uncertain, in reset, native save and ChatGPT index or registration publication.

The private-file backend is plaintext at rest beneath a checked, user-owned `0700` root. Each fixed record and pending replacement is bounded, no-follow, single-link, owner-checked and `0600`. On macOS, opened private roots, files and locks reject extended ACL allow entries, and ancestors reject ACL mutation grants; unreadable or unknown ACLs fail closed, deny-only entries are admissible, and more than 128 entries fail closed. Atomic rename with file and directory synchronization prevents a partially written final record; a crash may leave one bounded pending file. Permission modes and ACL checks do not encrypt credentials, exclude same-UID or privileged processes or securely erase old disk contents.

Native Keychain access selects the exact user-domain Keychain, service and slot without changing the default, search list or item permissions. Replacement first reads the selected item; only item-not-found permits insertion. Locked or denied access keeps the pinned backend and never becomes a new item or plaintext fallback.

Native API accounts use schema 3 with explicit nullable effort and Anthropic workspace fields. Their Provider is the closed `{kind, custom_name}` record: native kinds require a null custom name, and custom and ChatGPT kinds reject. The enclosing backend marker uses schema 2. The account file, ChatGPT index and registration records are read through the [record migration](./execution.md#json-record-migration), which defines supported versions; a registered step only reshapes non-secret fields forward, preserves UUID, key, workspace, model, effort and backend, and never changes or prints a secret. Keyring reads and selected-item authorization apply the same bounded migration in memory and never rewrite an OS-store item; private-file upgrades use the locked atomic record migration, and an interrupted upgrade stays recoverable and never selects another credential. Explicit replacement writes only the current schema. ChatGPT registration carries its nullable issued client ID; index state flags, nullable token and selection, and bounded model checks are explicit. Unsupported records are preserved unchanged; only the explicit reset deletes them. Setup and replacement still require current identity, backend and consent admission. Native replacement pins the inspected account and credential digest before entry or catalog work and rechecks it under the account lock; any change, including a same-backend one, refuses replacement.

Once an OS-store write or deletion helper is dispatched, disappearance, a wait or pipe failure, timeout, an unrecognized exit or an invalid acknowledgment is [Uncertain](./execution.md#effect-outcomes), including on a first-time save. A valid locked-store response is a confirmed refusal; failure to launch is unavailable before dispatch. Read failures keep their read-only disposition. The backend stays pinned, and killing the helper is no rollback. ChatGPT logout deletes only its validated token slot, never the native API item. Uncertain deletion keeps account use blocked and warns the user. After a recognized terminal refresh-token error, the account is disconnected and its model evidence cleared before deletion is attempted; failed cleanup never re-enables use and stays visible.

The account-replacement lock is held in the same blocking task as the OS credential-store write, so cancelling the awaiting interface cannot release it early.

Explicit native-account removal snapshots the account record, model preferences and selected keyring credential identity together under the account lock before confirmation, then rechecks all three under the lock; a stale snapshot refuses. It removes the account marker and model preferences before deleting only the unchanged pinned keyring slot, so uncertain deletion leaves the credential unconfigured. A crash may leave an orphaned keyring item, which is never loaded without its marker. Malformed records use the checked reset path, which never decodes them or deletes a credential based on an untrusted record. ChatGPT removal in setup is local only, as the [ChatGPT contract](./chatgpt.md#logout) defines.

Native setup runs lookup, choice, catalog, journal, then save and settlement, and confirms before removal or reset publication. Secret key and workspace-ID entry restore echo on cancellation. Save and removal settle the journal disposition before reporting a publication failure.

### Remote MCP tokens

`arany mcp login <server>` saves one OAuth grant per configured [remote MCP server](./tools.md#remote-mcp-and-oauth) in `mcp-oauth.json` in the account root: at most four servers, each with its URL, issued client ID, token and optional revocation endpoints, access token, optional refresh token and optional expiry, in a record of at most 64 KiB<!-- unrelated-bound: MCP OAuth record --> published by synced rename under the version-1 [record migration](./execution.md#json-record-migration). The grant is an unencrypted private file in the `0700` account root with no keyring slot, so any process of the same user can read it; login says so before printing the authorization URL. Keys and tokens never enter Events, logs, telemetry or Tool observations, and a grant is sent only to the exact URL it was issued for. Unknown fields, non-HTTPS endpoints and oversized or non-printable tokens reject the whole record; an unreadable record means no token. Logout deletes the entry, and the file with its last entry, even when remote revocation is unconfirmed. Login, logout and renewal change the record only under the account replacement lock, re-reading it inside the lock, so no writer loses another's entry. Each grant carries `renewal` (`ready`, `renewing`, `rejected`); the [renewal rules](./tools.md#remote-mcp-and-oauth) say how an unknown refresh outcome blocks reuse.

## Limits and record admission

Native API-account records, their backend marker and private-file records are each at most 1 KiB<!-- unrelated-bound: native account metadata records -->, in a `0700` leaf directory; a pending file is reused under the lock and published by synced rename. A ChatGPT registration record is 256 bytes, carries one stable UUIDv4 host ID and a nullable issued client ID, and never holds a token. `chatgpt-accounts.json` is at most 384 KiB and holds at most eight accounts sharing one host ID and at most 64 expiring check records; keyring entries hold metadata only, while private-file entries hold the plaintext token pair. `account-credentials.lock` is a zero-byte file beneath the account root. The ChatGPT helper slot admits a versioned, consent-bound token record of at most 64 KiB<!-- unrelated-bound: ChatGPT helper token record -->. Invalid or oversized records reject without partial admission.

Credentials pass to and from OS-store helpers only through bounded private pipes, never arguments or the process environment. Keys and tokens never enter Events, logs, telemetry or drawing calls. Errors are redacted and never expose platform error text or secret records. Availability probes return no secret, and a successful read-only probe does not prove later writes will succeed.

Linux targets Secret Service without a KDE or GNOME requirement. OS-store protection does not mean every backend encrypts at rest or restricts an unlocked item to Arany; the [dependency source evidence](../security/beta-dependency-inventory.md#build-time-and-native-authority) records the observed Linux boundary. The Linux keyring consent warning states that another same-user application may read an unlocked item; it claims no Arany-only secrecy and offers no silent plaintext fallback. Native availability, replacement, unlock and failure behavior, private-file ACL admission and per-item authorization need platform evidence before a support claim.

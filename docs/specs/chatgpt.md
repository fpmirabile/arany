# ChatGPT-plan access

## Scope

This contract owns the official ChatGPT-plan OAuth route: registration and sign-in, verified identity, plan consent, renewal, logout, and the account's catalog, checks and Runs with their local-only output bound. The route never falls back to API-key billing and never uses a private route; it must never import another harness's tokens. Storage limits belong to the [credential contract](./credentials.md), inference admission to the [Provider contract](./provider.md) and the accepted-outcome rules to the [execution contract](./execution.md#accepted-outcomes). Live sign-in and paid Runs stay in [next steps](../../NEXT_STEPS.md). The weaker output bound is accepted in [D-18](../research/next-step-decision-register.md#d-18--explicitly-accepted-chatgpt-plan-route-is-beta-scope). Editing constraints: [security rules](../../agents/security.md).

## Authorization transaction

- Each attempt binds a fresh `state`, nonce and PKCE verifier to a canonical `127.0.0.1` callback URI; the registration's host ID is rendered as `urn:uuid:`. First registration requires a bounded issued client ID in the callback. Returning authorization uses the selected registration's client and host ID, omits `agent_name_hint` and any ID-token hint, and rejects a different callback client ID.
- The one-shot listener starts only after the current `RiskPrompt` acknowledgment, on one ephemeral `127.0.0.1` port. It accepts eight connections at most, within a two-minute aggregate and a five-second per-connection deadline. Invalid requests get an inert rejection and do not consume the attempt. The accepted request is one HTTP/1.1 GET on the exact path and `Host`, with no `Origin` or body headers, capped at 8 KiB and 32 headers. Responses never reflect a code or token.
- The browser launcher accepts only the compiled authorization origin and refuses any token hint in process arguments.
- Redeem the code once with the exact issued client, redirect, verifier and resource at the compiled token endpoint. A bounded `invalid_grant` marks that one code unusable and is never retried. A first registration may restart with the callback's issued client ID and host ID, with fresh state, nonce and PKCE.
- The ID token verifies against the bounded, identity-encoded JWKS from the compiled issuer endpoint. The validator accepts RS256 only. Signature, issuer, audience, nonce, lifetime and a nonempty subject must hold, and the token response must carry the direct-use, resource-invocation and offline-access scopes. The audience is exactly the issued client, as a string or a one-element array. A present `azp` must equal that client. Rejection reports only a typed category (format, signing key, signature, claim binding or time), never a token, claim, callback or response body.
- A returning attempt also requires the signed subject to match its selected account before replacement. The callback client ID and token response are never account authority, and a browser callback alone is not verified sign-in.

- State, nonce and PKCE come only from the OS-backed `getrandom` source. An alternate entropy source, or a compiler or backend switch that could substitute one, needs separate provenance review.
- The issued client ID is persisted under the default-user account lock before the code is redeemed, so a competing registration cannot replace it silently.

## Accounts, consent and storage

- After risk consent, attached new-account setup offers Back or Resume for a retained issued client, Back focused. Cancelling preserves the registration and all saved accounts; it is not deletion or revocation. Returning accounts skip this choice.
- The prompt's warnings and pagination follow the [terminal setup contract](./terminal.md#setup-and-account-choices). The Linux keyring warning follows the [credential contract](./credentials.md#limits-and-record-admission). The file warning states that owner-only modes neither encrypt tokens nor exclude same-user processes. The receipt binds backend, warning version and exact text digest to client, subject and host; changing any one requires fresh consent.
- A verified sign-in without all required plan permissions keeps only token-free identity metadata with an explicit permission-disabled marker, persisted under the account lock before any old keyring item is removed. Setup offers `Enable plan`, which alone uses `prompt=consent` with the same client, host, subject and backend. `force_reconsent` is not admitted. A disabled account loads no token and runs nothing.
- Refresh uses the registration's issued client and rotating refresh token with `grant_type=refresh_token` and the fixed resource, omits scope, requires renewed direct-use permission and a distinct replacement pair, and returns a new in-memory credential. Absolute access expiry is the request-start time plus bounded `expires_in`, with delay allowance; a relative lifetime cannot survive restart. `earliest_refresh_at` is opaque and never schedules refresh. Active use refreshes ahead of local expiry ([official guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).
- Near-expiry refresh is serialized across processes under the account lock. A durable renewal-pending marker is written before egress. An `Unavailable` exchange clears it and keeps old credentials; a lost response after server-side rotation can still leave the next refresh unusable. Only a recognized terminal refresh error disconnects the account, clears model evidence and the private-file token, and asks the helper to delete the pinned keyring token; uncertain keyring deletion keeps use blocked. Other failures leave the marker and block loads until verified reauthorization. An invalid client requires registration repair, not token deletion.
- Keyring tokens use a SHA-256-derived slot separate from native API slots; the private index holds no keyring token. A user-accepted private-file token stays in the checked index, never SQLite. Save holds the account lock across keyring write and index publication, and replacing a keyring token first persists a pending marker. Token load and use require the current exact consent receipt. [Record limits](./credentials.md#limits-and-record-admission) apply.
- Reauthorization requires the original UUID and issued client under the lock, preserves UUID and backend, clears the pending marker and model evidence, and rejects host, subject or backend drift. A new account's save clears the registration's pending client ID only after the verified account is saved.
- Attached setup can save a verified new account, switch to a saved UUID (pinning account-only Session defaults until a catalog or explicit choice) or reauthorize the selected one. Cancelling leaves the old selection unchanged.
- ChatGPT setup converts authorization, account and catalog failures through the shared setup error owner while retaining exact feedback and the existing recoverable, uncertain and shutdown outcomes.
- Attached account actions follow the [Terminal setup contract](./terminal.md#setup-and-account-choices). Reconnect reads only validated selected-account metadata and starts a fresh returning attempt without reading the old token. Cancelling before save changes neither credentials nor defaults.
- Opening a Session or `/provider chatgpt` reads the selected account ID from the OS-user index only. It loads no token, contacts no keyring and refreshes nothing. Catalog, check and Run paths reopen the consent-matched token, serialize near-expiry refresh and reject pending, disconnected or invalid renewal before any Provider request or Workspace disclosure. An attached caller passes its pinned UUID, and a different selection is rejected under the lock before token retrieval or renewal. Registration open rejects a host mismatch with the account index before any browser attempt. Exact check publication revalidates its account, registration and consent snapshot; no lock spans the inference sequence.

- Refresh failures other than a recognized terminal error keep the stored credential: transport, rate-limit, server, malformed and unknown responses change nothing. Malformed saved metadata gets its own recovery diagnostic and never relaxes signed identity checks or contacts the token store.

## Logout

`provider logout chatgpt` signs out only the selected account under the account lock. It marks sign-out pending and removes model evidence before touching the token or network. Revocation uses the compiled issuer's bounded OpenID configuration and a same-origin HTTPS revocation endpoint with no query or fragment. Only an empty HTTP `200` confirms it; transport and 5xx failures get two backoff-and-jitter retries within 30 seconds. The account is then disconnected and its token removed or its pinned keyring item deleted. A failed remote step still disconnects locally and warns in ChatGPT Settings; uncertain deletion keeps use blocked. Logout does not securely erase backups or stop same-user processes.

Provider setup removes a chosen ChatGPT account locally only. It confirms the full account ID and exact account-index snapshot, clears that account's local token and evidence under the account lock, and leaves remote access unchanged. Use `provider logout chatgpt` when remote revocation is intended.

If local keyring deletion is uncertain, the account stays disconnected and blocked. Setup ends the current lifecycle with an uncertainty notice; retry or inspection requires a fresh setup lifecycle.

## Catalog, checks and Runs

- `provider models chatgpt` reads only the selected verified account's token at the compiled `/v1/models` route. It sends no Workspace input and uses neither `OPENAI_API_KEY` nor `--saved-account` or `--state-dir`. It lists every `visibility: "list"` row in server order with bounded slug and display name. An optional numeric `context_window` within 32,768–2,000,000 tokens is kept as the row's window; any other value is absent, and a non-numeric or duplicate field is an invalid catalog. Model listings and successful check output show this window in human token units with at most one decimal and no trailing `.0` (for example `272k tokens`, `32.8k tokens` or `1M tokens`), or `unknown` when absent. Visibility grants no Run or effort capability. One 20-second read, no retry; replies over 1 MiB, compressed or redirected replies, duplicate or oversized rows and token reflection fail as an invalid catalog. A non-success status reports only its numeric code and fixed advice, without reading the body.
- `provider check chatgpt MODEL --effort LEVEL --accept-cost` is explicitly plan-consuming. It uses the selected OS-user account root and that root's `events.sqlite3`, even when the root also holds conversation history, and returns the shared acknowledged `CheckView` to callers. The [standalone check lifecycle](./execution.md#standalone-provider-checks) commits Start before clearing the tuple's old evidence through the checked account writer, acknowledges clearing before catalog access, and acknowledges each catalog/probe intent before egress and its result before continuation. One catalog read and the same three synthetic probes remain bounded by the existing aggregate deadline, narrowed by the lifecycle deadline with local settlement time reserved. No lock spans the network sequence except the root check lease; concurrent checks refuse busy. It never falls back to an API key and accepts neither `--saved-account` nor `--state-dir`.
- After all probes pass, the checker revalidates the exact selected account, credentials, registration host and consent under the account lock, then commits the digest of the proposed model-check record before JSON publication. The locked writer revalidates again, requires the same latest pending publication, writes and rereads the record, and only then acknowledges terminal journal success. This is not a cross-store transaction: a crash or lost acknowledgment between file publication and terminal success leaves optional evidence unusable. Recovery never repairs the account index, completes publication or retries a call. A new attempt suppresses earlier evidence even when physical clearing fails. CLI success and admitted failure report CheckId and the [shared durable disposition](./provider.md#commands), including `unconfirmed` after a lost final acknowledgment. Cancellation and probe-deadline refusals report their stop cause separately from journal failures; a stopped response wait still records unknown outcome and usage before returning.
- Optional checks expire after 24 hours and bind account UUID, signed registration, exact consent receipt, model, effort, protocol/check version and the retained ID token; rotating access/refresh tokens do not key the fingerprint. Readers also require the latest target attempt to replay successfully with matching CheckId, fingerprint, contract and exact record digest. An absent or null `context_window_tokens` means no window; an out-of-range saved value is damaged saved state. A new sign-in clears checks; token rotation keeps them. Incomplete or failed diagnostics remove only optional evidence and cached windows, leaving ordinary account-consent admission independent. The [schema-1 → 2 migration](./execution.md#json-record-migration) clears unproved old checks without changing credentials or consent.

- After normal renewal, Run admission attempts one authenticated catalog read with a five-second deadline and no retry, then revalidates account identity and consent under the lock before Workspace input. The shorter admission deadline leaves the 20-second catalog deadline for model listings and checks unchanged. The selected window is journaled in `RunStarted.config.context_window_tokens` without a separate plan-consuming check or inference call.
- A successful catalog read supplies the exact selected slug's admitted window. An absent row or absent or out-of-range window means no window and the default [context ceiling](./session.md#context-and-compaction); a saved check never overrides current authenticated metadata. Only a failed read, including the admission deadline, uses the currently valid same-account, same-slug check with the greatest recorded check time across effort levels, or no window if none is valid. Check identity bindings and the 24-hour validity interval apply, including rejection of future-dated and expired checks; an unavailable catalog alone never stops admission.
- Like Codex's live-model fetch with cached-catalog fallback, cached metadata only resizes bounded budgets and grants no model, effort or account authority. Inherited team children and automatic Goal continuations reuse the admitted provider. Explicitly configured role routes admit their own providers; setup and model-picker reads remain separate from Run admission. Replayed evidence grants a Session no authority.
- Run function selection follows the [Provider text-answer contract](./provider.md#structured-outcomes-and-tool-encoding). Requests are the [Provider](./provider.md) ChatGPT-route shape: `store: false`, `stream: true`, an array `input` of required local history, no `previous_response_id` and no remote `max_output_tokens`, as the [official preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) requires.
- Compaction follows the [plain-text Provider contract](./provider.md#structured-outcomes-and-tool-encoding), without response schemas or Tool selection. Its byte guidance and local-only accounting remain as defined below.
- Streams accept LF, CRLF and CR line endings across chunks. Only `response.completed` succeeds, with positive labelled usage within the [Run limits](#run-limits) and the [Provider-owned framing bounds, including the separate event and completed-response ceilings](./provider.md#streaming-and-provisional-text), before the [stream-idle deadline and call ceiling](#run-limits). `response.failed`, `response.incomplete`, malformed, encoded or interrupted streams, missing usage and local overflow publish no partial outcome or summary. One bounded SSE parser serves the route regardless of absent or misleading media labels. Optional event labels must agree with JSON types. A matching created or completed identity plus complete indexed item events may supply empty terminal output; populated terminal output must agree. Deltas never supply accepted results. Native and catalog media admission remains unchanged; no JSON or HTML fallback is implied.
- A failed or error event may retain only a nonempty machine-readable code of at most 128 safe ASCII bytes from its documented location, after token-reflection rejection. Malformed or unsafe codes stay generic. Only recognized temporary usage-unavailable codes map to unavailable.
- A non-200 response retains its optional numeric plan observation and only its numeric status, plus what [Provider reliability](./provider.md#usage-provenance-and-reliability) reads from a 429 or 5xx (the `Retry-After` and quota classification): 4xx maps to rejected, 5xx to unavailable, others to invalid response. Check output shows the status with fixed advice; 401, 403 and 503 receive distinct advice, while 429, other 5xx and unknown statuses stay cautious and infer no plan limit. No check failure saves evidence or retries, and no failure switches billing or erases a stored token on one 401.
- Passive [plan-limit metadata](./provider.md#passive-plan-limit-observations) is collected only from already authorized `POST /v1/responses` responses, including non-success status headers and recognized events if supplied on this SSE route. Availability on the official direct-use route remains unverified. No `/wham/usage`, `/api/codex/usage`, private endpoint, polling, WebSocket transport, new account integration or API-key fallback is admitted. A 429 or usage-limit reason alone establishes no percentage, balance or reset. [Terminal freshness labels](./terminal.md#reported-usage) distinguish these account-level observations from Session token totals.
- Observed Runs preserve only closed reasons: account access, usage limit, rate limit, temporary usage or service unavailability, stream protocol, selected response contract, structured outcome contract or local output acceptance. Canonical Events hold no raw status, code, upstream text, body or request ID. A reason does not establish credential invalidity, exact quota, retry time or billing. Run calls retry the same route only as [Provider reliability](./provider.md#usage-provenance-and-reliability) defines. There is no automatic model or encoding fallback, or billing switch.
- Run and compaction Events pin an opaque admission fingerprint, account UUID, closed category and local-only output bound. Its `account_consent` HMAC uses a domain separate from optional checks and binds model, effort, verified client, subject, host, account UUID, exact storage consent and versions. Missing categories, unknown values or unknown fields fail closed.
- Setup, after verified save, selects a low-effort default from the account catalog: visible `gpt-5.6-luna` if present, otherwise the first visible row with prices reported as unknown. It asks no model, effort or cost questions.

- Changing the request or decoder, effort mapping, consent or output-bound semantics bumps the account-admission contract version. Checker versions do not affect it. An admission-version change regenerates Run fingerprints from the current consented account without invalidating its storage-consent receipt; fresh consent follows only the [receipt-matching contract](#accounts-consent-and-storage). A model-check version change invalidates optional checks and their cached-window fallback, without making checks mandatory for Runs.

### Run limits

Primary and private editor calls declare 32,768 visible output tokens; researcher calls request 4,096. The shared [execution contract](./execution.md#accepted-outcomes) owns the child caps and route narrowing.

| Limit | Value | Overflow |
|---|---|---|
| Local output cap | The request's [role-specific cap](./execution.md#accepted-outcomes) applied to visible output: `usage.output_tokens` minus `usage.output_tokens_details.reasoning_tokens`. Absent or null details count every output token. ChatGPT compaction keeps its separate 4,096 visible-token cap. Because its request cannot carry an output cap, the prompt targets three quarters of the [Session-owned summary byte bound](./session.md#context-and-compaction), noting that a non-ASCII character takes up to 4 bytes; local summary acceptance enforces that shared bound. | `local_output_limit`, no retry. Reasoning above the total, or details without an unsigned 32-bit count, is a response-contract failure. |
| Reported output total | At most 1,000,000 tokens, reasoning included; journaled and charged unchanged | Response-contract failure |
| Stream idle | 300 seconds waiting for the response headers and between received SSE events. Only a framed event restarts it; comments and partial frames do not. | Before the status check: a send timeout, never retried. After it: a stream cut, retried and charged under [Provider reliability](./provider.md#usage-provenance-and-reliability). |
| Call ceiling | 600 seconds per call, also ending at the remaining action and Goal active time | With no decoded outcome, a cut at the ceiling is a stream cut, retried and charged under [Provider reliability](./provider.md#usage-provenance-and-reliability) when a retry fits the remaining action and Goal time; otherwise the call times out with unknown usage, which is charged |
| Compaction | The Engine's 120-second [compaction deadline](./execution.md#accepted-outcomes) | Compaction times out |

Peer behavior (openai/codex d571eaf1): Codex's Responses request carries no `max_output_tokens`, and Codex applies no client-side output cap; it only reports `reasoning_output_tokens`. Its `stream_idle_timeout_ms` defaults to 300,000 ms with a per-provider override and restarts on each SSE event; an expiry is a stream error, and the request has no total timeout. Arany copies the idle value and per-event restart, and treats a cut at its ceiling like an idle cut. It keeps a visible-output cap and adds the call ceiling, because every Provider call needs explicit bounds and a trickling stream must not run forever. The ceiling equals the native API routes' deadline, so action reservations, wave planning and Goal active time already account for it, and it spans two idle windows. No idle override is offered: Arany has no per-provider configuration surface. Replay sees only the recorded total, so it cannot re-verify the visible share.

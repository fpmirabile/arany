# ChatGPT-plan access

## Scope

This contract owns the official ChatGPT-plan OAuth route: registration and sign-in, verified identity, plan consent, renewal, logout, and the account's catalog and Runs with their local-only output bound. The route never falls back to API-key billing, never uses a private route and never imports another harness's tokens. Storage limits belong to the [credential contract](./credentials.md), inference admission to the [Provider contract](./provider.md) and accepted outcomes to the [execution contract](./execution.md#accepted-outcomes). [D-18](../research/next-step-decision-register.md#d-18--explicitly-accepted-chatgpt-plan-route-is-beta-scope) accepts the weaker output bound. Live sign-in, native keyring use and paid Runs stay in [next steps](../../NEXT_STEPS.md#beta-2-and-broader-release). Editing constraints: [security rules](../../agents/security.md).

## Authorization transaction

- Each attempt binds a fresh `state`, nonce and PKCE verifier to a canonical `127.0.0.1` callback URI. They come only from the OS-backed `getrandom` source; another entropy source, or a build switch that could substitute one, needs separate provenance review.
- The account-root registration record atomically stores one stable UUIDv4 host ID before the first authorization request; it holds no code, token or consent receipt and authorizes no catalog use or Run. The host ID is rendered as `urn:uuid:`. First registration requires a bounded issued client ID in the callback; it is persisted under the default-user account lock before code redemption, so a competing registration cannot replace it silently. Reopening reconciles a crash after account publication, so another new account can register with the same host ID. Returning authorization never claims the pending client slot; it uses the selected registration's client and host ID, omits `agent_name_hint` and any ID-token hint, and rejects a different callback client ID.
- The one-shot listener starts only after the current `RiskPrompt` acknowledgment, on one ephemeral `127.0.0.1` port. It accepts at most eight connections, within a two-minute aggregate and a five-second per-connection deadline. Invalid requests get an inert rejection and do not consume the attempt. The accepted request is one HTTP/1.1 GET on the exact path and `Host`, with no `Origin` or body headers, capped at 8 KiB<!-- unrelated-bound: OAuth callback request headers --> and 32 headers. Responses never reflect a code or token.
- The browser launcher accepts only the compiled authorization origin and refuses a token hint in process arguments.
- The code is redeemed once at the compiled token endpoint with the exact issued client, redirect, verifier and resource. A bounded `invalid_grant` marks that code unusable and is never retried. A first registration may restart with the callback's issued client and host ID and fresh state, nonce and PKCE.
- The ID token verifies against the bounded, identity-encoded JWKS from the compiled issuer, RS256 only. Signature, issuer, audience, nonce, lifetime and a nonempty subject must hold, and the token response must carry the direct-use, resource-invocation and offline-access scopes. The audience is exactly the issued client, as a string or a one-element array; a present `azp` must equal it. Rejection reports only a typed category (format, signing key, signature, claim binding or time), never a token, claim, callback or body.
- A returning attempt also requires the signed subject to match the selected account before replacement. The callback client ID and token response are never account authority; a browser callback alone is not verified sign-in.

## Accounts, consent and storage

- After risk consent, new-account setup with a retained issued client offers Back or Resume, Back focused; Resume starts a fresh PKCE attempt with that client. Cancelling preserves the registration and all saved accounts; it is not deletion or revocation. Returning accounts skip this choice.
- Prompt warnings and pagination follow the [terminal setup contract](./terminal.md#setup-and-account-choices); the Linux keyring warning follows the [credential contract](./credentials.md#limits-and-record-admission). The file warning states that owner-only modes neither encrypt tokens nor exclude same-user processes. The consent receipt binds backend, warning version and exact text digest to client, subject and host; changing any one requires fresh consent.
- Missing plan permission never bypasses signature, issuer, audience, nonce, lifetime or returning-subject validation. A verified sign-in without all required plan permissions keeps only token-free identity metadata with an explicit permission-disabled marker, persisted under the account lock before any old keyring item is removed. Setup offers `Enable plan`, which alone uses `prompt=consent` with the same client, host, subject and backend. `force_reconsent` is not admitted. A disabled account loads no token and runs nothing.
- Refresh uses the registration's issued client and rotating refresh token with `grant_type=refresh_token` and the fixed resource, omits scope, requires renewed direct-use permission and a distinct replacement pair, and returns a new in-memory credential. Absolute access expiry is the request-start time plus bounded `expires_in`, with delay allowance; a relative lifetime cannot survive restart. `earliest_refresh_at` is opaque and never schedules refresh. Active use refreshes ahead of local expiry ([official guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).
- Near-expiry refresh is serialized across processes under the account lock, and a durable renewal-pending marker is written before egress. An `Unavailable` exchange clears the marker and keeps the old credentials; a lost response after server-side rotation can still make the next refresh unusable. Only a recognized terminal refresh error disconnects the account: it clears the private-file token, then asks the helper to delete the pinned keyring token; uncertain deletion keeps use blocked. Other failures (transport, rate limit, server, malformed, unknown) keep the stored credential, leave the marker and block loads until verified reauthorization. An invalid client requires registration repair, not token deletion.
- New keyring accounts use a per-account slot: `chatgpt-` plus the base64url SHA-256 of the client ID and account UUID, recorded as non-secret `keyring_slot` and separate from native API slots. Accounts never share a slot. A helper token record carries its exact slot; a read requires it to match both the addressed slot and the index entry. Deletion, logout and uncertain cleanup use the entry's recorded slot.
- An account created before per-account slots keeps its client-derived slot for life. Its token record upgrades in memory without rewriting the OS-store item; the next refresh or reauthorization replaces it at the same slot under the pending marker, preserving startup authorization, load and renewal behavior.
- Within one host and storage, account identity is the client ID, subject and account ID triple. Account IDs currently stay null: verified sign-in matches the entry with the same client and subject and a null account ID, or creates a new account. Duplicate triples or slots reject the index; the same subject under different clients stays distinct. Verified account-ID support remains unimplemented ([plan](../../planning/usage-limits/README.md)): once enabled, sign-in must match the exact triple without adopting a null or different account ID, and reauthorization must refuse with the registration-conflict category if another entry already holds that ID. Reauthorization binds to the selected UUID and changes nothing on refusal; the user removes one conflicting account.
- The private index holds no keyring token. A user-accepted private-file token stays in the checked index, never SQLite. Save holds the account lock across keyring write and index publication; an uncertain new-account write never publishes a selection, though an orphan keyring item may remain. Replacing a keyring token first persists a pending marker. Reopen rejects backend or consent drift, a missing selected keyring item and a token subject or host mismatch. Token load and use require the current exact consent receipt. [Record limits](./credentials.md#limits-and-record-admission) apply.
- Reauthorization requires the original UUID and issued client under the lock, preserves UUID and backend, clears the pending marker, and rejects host, subject or backend drift. Saving a new account clears the registration's pending client ID only after the verified account is saved.
- Attached setup can save a verified new account, switch to a saved UUID (pinning account-only Session defaults until a catalog read or explicit choice) or reauthorize the selected one. Reconnect reads only validated selected-account metadata and starts a fresh returning attempt without reading the old token. Cancelling before save changes neither credentials, defaults nor the selection. Catalog defaults keep catalog order; account drift and empty catalogs reject.
- A locked keyring refuses private-file fallback; an unavailable or timed-out probe permits the explicit storage choice. Malformed saved metadata gets its own recovery diagnostic and never relaxes signed identity checks or contacts the token store.
- Opening a Session or `/provider chatgpt` reads the selected account ID from the OS-user index only: no token, keyring or refresh. Catalog and Run paths reopen the consent-matched token, serialize near-expiry refresh and reject pending, disconnected or invalid renewal before any Provider request or Workspace disclosure. An attached caller passes its pinned UUID; a different selection is rejected under the lock before token retrieval or renewal. Registration open rejects a host mismatch with the account index before any browser attempt. No lock spans an inference call.

## Logout

`provider logout chatgpt` signs out only the selected account under the account lock. It marks sign-out pending before touching the token or network. Revocation uses the compiled issuer's bounded OpenID configuration and a same-origin HTTPS revocation endpoint with no query or fragment. Only an empty HTTP `200` confirms it; transport and 5xx failures get two backoff-and-jitter retries within 30 seconds<!-- unrelated-bound: ChatGPT revocation retry deadline -->. The account is then disconnected, keeping identity and registration for reconnect, and its token removed or its pinned keyring item deleted. A failed remote step still disconnects locally and warns in ChatGPT Settings. An in-flight Provider request is not cancelled. Logout does not securely erase backups or stop same-user processes.

Setup's removal of a ChatGPT account is local only. It confirms the full account ID and exact account-index snapshot, clears that account's local token under the account lock, and leaves remote access unchanged; `provider logout chatgpt` is the remote sign-out.

[Uncertain](./execution.md#effect-outcomes) keyring deletion, on logout, removal or terminal refresh, keeps the account disconnected and blocked. Setup then ends the current lifecycle with an uncertainty notice; retry or inspection needs a fresh setup lifecycle.

## Catalog and Runs

- `provider models chatgpt` reads only the selected verified account's token at the compiled `/v1/models` route. It sends no Workspace input and uses neither `OPENAI_API_KEY`, `--saved-account` nor `--state-dir`. It lists every `visibility: "list"` row in server order with bounded slug and display name. An optional numeric `context_window` within 32,768–2,000,000 tokens is the row's window; any other value is absent, and a non-numeric or duplicate field is an invalid catalog. Listings show the window in human token units with at most one decimal and no trailing `.0` (`272k tokens`, `32.8k tokens`, `1M tokens`), or `unknown`. Visibility grants no Run or effort capability. One 20-second read, no retry; replies over 1 MiB<!-- unrelated-bound: subscription model catalog response -->, compressed or redirected replies, duplicate or oversized rows and token reflection are an invalid catalog. A non-success status reports only its numeric code and fixed advice, without reading the body.
- Arany sends no plan-consuming request the user did not ask for: there is no model check, like Codex, which admits a listed model without a probe. Each Run's strict decoder validates the real response. An account index at another [record version](./execution.md#incompatible-records) is archived intact; nothing converts its credentials or consent.
- Setup selects a low-effort default from the account catalog after verified save, without inference: visible `gpt-5.6-luna` if present, otherwise the first visible row with prices reported as unknown. It asks no model, effort or cost questions. Catalog cancellation or failure after a new, switched or replaced account leaves account-only defaults with a visible retry notice; failed reuse of the current account keeps Session defaults.

Run admission:

- After normal renewal, Run admission makes one authenticated catalog read with a five-second deadline and no retry, then revalidates account identity and consent under the lock before Workspace input. `RunStarted.config.context_window_tokens` journals the selected window without a plan-consuming check or inference call.
- A successful read supplies the selected slug's admitted window. An absent row or window, an out-of-range value or a failed read, including the admission deadline, means no window and the default [context ceiling](./session.md#context-and-compaction). An unavailable catalog alone never stops admission.
- Like Codex's live-model fetch, catalog metadata only resizes bounded budgets and grants no model, effort or account authority. Inherited team children and automatic Goal continuations reuse the admitted provider; explicitly configured role routes admit their own. Setup and model-picker reads stay separate from Run admission. Replayed provenance grants a Session no authority.

Requests and streams:

- Function selection and parallel Tool calls follow the [Provider Tool encoding](./provider.md#structured-outcomes-and-tool-encoding); compaction follows its plain-text contract. The Session UUIDv7 is the `prompt_cache_key` on Run and compaction requests. Requests send `store: false`, `stream: true` and an array `input` of required local history, with no `previous_response_id` and no remote `max_output_tokens`, as the [official preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) requires.
- One bounded SSE parser serves the route after its status, destination, encoding and length guards, whatever the media label; non-SSE JSON or HTML has no fallback. It accepts LF, CRLF and CR line endings across chunks. Optional event labels must agree with JSON types. Only `response.completed` succeeds, with positive labelled usage within the [Run limits](#run-limits) and the [Provider framing bounds](./provider.md#streaming-and-provisional-text). `response.failed`, `response.incomplete`, malformed, encoded or interrupted streams, missing usage and local overflow publish no partial outcome or summary. A matching created or completed identity plus complete, contiguously indexed item events may supply empty terminal output; populated terminal output must agree. Deltas never supply accepted results.
- A failed or error event may keep only a nonempty machine-readable code of at most 128 safe ASCII bytes from its documented location, after token-reflection rejection; other codes stay generic. Only recognized temporary usage-unavailable codes map to unavailable.
- A non-200 response keeps only its numeric status, its optional plan observation, and what [Provider reliability](./provider.md#usage-provenance-and-reliability) reads from a 429 or 5xx. 4xx maps to rejected, 5xx to unavailable, others to invalid response. 429, other 5xx and unknown statuses infer no plan limit, and no failure switches billing or erases a stored token on one 401.
- [Plan-limit observations](./provider.md#passive-plan-limit-observations) come only from already authorized `POST /v1/responses` responses, including non-success headers and recognized events. Their availability on the official route is unverified. No `/wham/usage`, `/api/codex/usage`, private endpoint, polling, WebSocket transport or new account integration is admitted. A 429 or usage-limit reason alone establishes no percentage, balance or reset. [Terminal freshness labels](./terminal.md#reported-usage) distinguish these account-level observations from Session token totals.
- Runs keep only closed failure reasons: account access, usage limit, rate limit, temporary usage or service unavailability, stream protocol, response contract, structured outcome contract or local output acceptance. Events hold no raw status, code, upstream text, body or request ID. A reason does not establish credential invalidity, exact quota, retry time or billing. Retries follow [Provider reliability](./provider.md#usage-provenance-and-reliability); there is no model, encoding or billing fallback.
- Run and compaction Events pin an opaque admission fingerprint, account UUID, closed category and local-only output bound. Its `account_consent` HMAC binds the compiled endpoint, model, effort, verified client, subject, host, account UUID and exact storage consent. Missing categories, unknown values or unknown fields fail closed. Provenance grants no current account authority.

### Run limits

Primary and private editor calls declare 32,768 visible output tokens; researcher calls request 4,096. The [execution contract](./execution.md#accepted-outcomes) owns child caps and route narrowing.

| Limit | Value | Overflow |
|---|---|---|
| Local output cap | The request's [role-specific cap](./execution.md#accepted-outcomes) applied to visible output: `usage.output_tokens` minus `usage.output_tokens_details.reasoning_tokens`. Absent or null details count every output token. Compaction keeps a separate 4,096 visible-token cap; because the request cannot carry it, the prompt targets three quarters of the [Session summary byte bound](./session.md#context-and-compaction), noting that a non-ASCII character takes up to 4 bytes, and local acceptance enforces that bound. | `local_output_limit`, no retry. Reasoning above the total, or details without an unsigned 32-bit count, is a response-contract failure. |
| Reported output total | At most 1,000,000 tokens, reasoning included; journaled and charged unchanged | Response-contract failure |
| Stream idle | 300 seconds waiting for response headers and between SSE events. Only a framed event restarts it; comments and partial frames do not. | Before the status check: a send timeout, never retried. After it: a stream cut, retried and charged under [Provider reliability](./provider.md#usage-provenance-and-reliability). |
| Call ceiling | 600 seconds<!-- unrelated-bound: ChatGPT Provider call deadline --> per call, also ending at the remaining action and Goal active time | Without a decoded outcome, a stream cut, retried and charged when a retry fits the remaining action and Goal time; otherwise a timeout with unknown usage, which is charged |
| Compaction | The Engine's 120-second<!-- unrelated-bound: Engine compaction call deadline --> [compaction deadline](./execution.md#accepted-outcomes) | Compaction times out |

Peer behavior (openai/codex d571eaf1): Codex sends no `max_output_tokens`, applies no client-side output cap, defaults `stream_idle_timeout_ms` to 300,000 ms with a per-event restart, and has no total timeout. Arany copies the idle value and restart, but keeps a visible-output cap and adds the call ceiling because every Provider call needs explicit bounds and a trickling stream must not run forever. The ceiling equals the native API deadline, so action reservations, wave planning and Goal active time already cover it. Arany has no per-provider idle override because it has no per-provider configuration surface. Replay sees only the recorded total, so it cannot re-verify the visible share.

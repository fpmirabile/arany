# ChatGPT-plan access

## Scope

This contract owns the official ChatGPT-plan OAuth route: registration and sign-in, verified identity, plan consent, renewal, logout, and the account's catalog, checks and Runs with their local-only output bound. The route never falls back to API-key billing and never uses a private route; it must never import another harness's tokens. Storage limits belong to the [credential contract](./credentials.md), inference admission to the [Provider contract](./provider.md) and the accepted-outcome rules to the [execution contract](./execution.md#accepted-outcomes). Live sign-in and paid Runs stay in [next steps](../../NEXT_STEPS.md). The weaker output bound is accepted in [D-18](../research/next-step-decision-register.md#d-18--explicitly-accepted-chatgpt-plan-route-is-beta-scope). Editing constraints: [security rules](../../agents/security.md).

## Authorization transaction

- Each attempt binds a fresh `state`, nonce and PKCE verifier to a canonical `127.0.0.1` callback URI; the registration's host ID is rendered as `urn:uuid:`. First registration requires a bounded issued client ID in the callback. Returning authorization uses the selected registration's client and host ID, omits `agent_name_hint` and any ID-token hint, and rejects a different callback client ID.
- The one-shot listener starts only after the current `RiskPrompt` acknowledgment, on one ephemeral `127.0.0.1` port. It accepts eight connections at most, within a two-minute aggregate and a five-second per-connection deadline. Invalid requests get an inert rejection and do not consume the attempt. The accepted request is one HTTP/1.1 GET on the exact path and `Host`, with no `Origin` or body headers, capped at 8 KiB and 32 headers. Responses never reflect a code or token.
- The browser launcher accepts only the compiled authorization origin and refuses any token hint in process arguments.
- Redeem the code once with the exact issued client, redirect, verifier and resource at the compiled token endpoint. A bounded `invalid_grant` marks that one code unusable and is never retried. A first registration may restart with the callback's issued client ID and host ID, with fresh state, nonce and PKCE.
- The ID token verifies against the bounded, identity-encoded JWKS from the compiled issuer endpoint. The validator accepts RS256 only. Signature, issuer, audience, nonce, lifetime and a nonempty subject must hold, and the token response must carry the direct-use, resource-invocation and offline-access scopes. The audience is exactly the issued client, as a string or a one-element array. A present `azp` must equal that client. Rejection reports only a typed category (format, signing key, signature, claim binding or time), never a token, claim, callback or response body.
- A returning attempt also requires the signed subject to match its selected account before replacement. The callback client ID and token response are never account authority, and a browser callback alone is not verified sign-in.

- State, nonce and PKCE come only from the OS-backed `getrandom` source. An alternate entropy source, or a compiler or backend switch that could substitute one, needs separate provenance review.
- The issued client ID is persisted under the default-user account lock before the code is redeemed, so a competing registration cannot replace it silently.

## Accounts, consent and storage

- After risk consent, attached new-account setup offers Back or Resume for a retained issued client, Back focused. Cancelling preserves the registration and all saved accounts; it is not deletion or revocation. Returning accounts skip this choice.
- The prompt's warnings and pagination follow the [terminal setup contract](./terminal.md#setup-and-account-choices). The Linux keyring warning follows the [credential contract](./credentials.md#limits-and-record-admission). The file warning states that owner-only modes neither encrypt tokens nor exclude same-user processes. The receipt binds backend, warning version and exact text digest to client, subject and host; changing any one requires fresh consent.
- A verified sign-in without all required plan permissions keeps only token-free identity metadata with an explicit permission-disabled marker, persisted under the account lock before any old keyring item is removed. Setup offers `Enable plan`, which alone uses `prompt=consent` with the same client, host, subject and backend. `force_reconsent` is not admitted. A disabled account loads no token and runs nothing.
- Refresh uses the registration's issued client and rotating refresh token with `grant_type=refresh_token` and the fixed resource, omits scope, requires renewed direct-use permission and a distinct replacement pair, and returns a new in-memory credential. Absolute access expiry is the request-start time plus bounded `expires_in`, with delay allowance; a relative lifetime cannot survive restart. `earliest_refresh_at` is opaque and never schedules refresh. Active use refreshes ahead of local expiry ([official guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).
- Near-expiry refresh is serialized across processes under the account lock. A durable renewal-pending marker is written before egress. An `Unavailable` exchange clears it and keeps old credentials; a lost response after server-side rotation can still leave the next refresh unusable. Only a recognized terminal refresh error disconnects the account, clears model evidence and the private-file token, and asks the helper to delete the pinned keyring token; uncertain keyring deletion keeps use blocked. Other failures leave the marker and block loads until verified reauthorization. An invalid client requires registration repair, not token deletion.
- Keyring tokens use a SHA-256-derived slot separate from native API slots; the private index holds no keyring token. A user-accepted private-file token stays in the checked index, never SQLite. Save holds the account lock across keyring write and index publication, and replacing a keyring token first persists a pending marker. Token load and use require the current exact consent receipt. [Record limits](./credentials.md#limits-and-record-admission) apply.
- Reauthorization requires the original UUID and issued client under the lock, preserves UUID and backend, clears the pending marker and model evidence, and rejects host, subject or backend drift. A new account's save clears the registration's pending client ID only after the verified account is saved.
- Attached setup can save a verified new account, switch to a saved UUID (pinning account-only Session defaults until a catalog or explicit choice) or reauthorize the selected one. Cancelling leaves the old selection unchanged.
- With a connected selection, `/setup` and `--setup` offer `Use saved`, `Reconnect` and `Connect new`. A disconnected selection offers `Reconnect` or `Connect new`, plus `Use saved` when another connected account exists. Reconnect reads only validated selected-account metadata and starts a fresh returning attempt without reading the old token. Cancelling before save changes neither credentials nor defaults.
- Opening a Session or `/provider chatgpt` reads the selected account ID from the OS-user index only. It loads no token, contacts no keyring and refreshes nothing. Catalog, check and Run paths reopen the consent-matched token, serialize near-expiry refresh and reject pending, disconnected or invalid renewal before any Provider request or Workspace disclosure. An attached caller passes its pinned UUID, and a different selection is rejected under the lock before token retrieval or renewal. Registration open rejects a host mismatch with the account index before any browser attempt. Exact check publication revalidates its account, registration and consent snapshot; no lock spans the inference sequence.

- Refresh failures other than a recognized terminal error keep the stored credential: transport, rate-limit, server, malformed and unknown responses change nothing. Malformed saved metadata gets its own recovery diagnostic and never relaxes signed identity checks or contacts the token store.

## Logout

`provider logout chatgpt` signs out only the selected account under the account lock. It marks sign-out pending and removes model evidence before touching the token or network. Revocation uses the compiled issuer's bounded OpenID configuration and a same-origin HTTPS revocation endpoint with no query or fragment. Only an empty HTTP `200` confirms it; transport and 5xx failures get two backoff-and-jitter retries within 30 seconds. The account is then disconnected and its token removed or its pinned keyring item deleted. A failed remote step still disconnects locally and warns in ChatGPT Settings; uncertain deletion keeps use blocked. Logout does not securely erase backups or stop same-user processes.

## Catalog, checks and Runs

- `provider models chatgpt` reads only the selected verified account's token at the compiled `/v1/models` route. It sends no Workspace input and uses neither `OPENAI_API_KEY` nor `--saved-account` or `--state-dir`. It lists every `visibility: "list"` row in server order with bounded slug and display name. Visibility grants no Run or effort capability. One 20-second read, no retry; replies over 1 MiB, compressed or redirected replies, duplicate or oversized rows and token reflection fail as an invalid catalog. A non-success status reports only its numeric code and fixed advice, without reading the body.
- `provider check chatgpt MODEL --effort LEVEL --accept-cost` is explicitly plan-consuming. It clears the account's prior tuple evidence, verifies visibility, then runs the three synthetic calls, token cap and aggregate deadline of [Provider checks](./provider.md#commands). Only completed strict outcomes publish a check, valid for the same period and bound to account UUID, signed registration, exact consent receipt, model, effort, protocol and check version, and the retained ID token; rotating access and refresh tokens do not key it. A new sign-in clears the account's checks; token rotation keeps them. It never falls back to an API key and accepts neither `--saved-account` nor `--state-dir`.
- Run admission revalidates account identity and consent under the lock after normal renewal, before Workspace input. It needs no check record and makes no hidden catalog or inference call. Replayed evidence grants a Session no authority.
- Requests are the [Provider](./provider.md) ChatGPT-route shape: `store: false`, `stream: true`, an array `input` of required local history, no `previous_response_id` and no remote `max_output_tokens`, as the [official preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) requires.
- Streams accept LF, CRLF and CR line endings across chunks. Only `response.completed` succeeds, with positive labelled usage no greater than the local output cap, within the shared 1 MiB framing bound ([Provider](./provider.md#streaming-and-provisional-text)) and the [call deadline](./execution.md#accepted-outcomes). `response.failed`, `response.incomplete`, malformed, encoded or interrupted streams, missing usage and local overflow publish no partial outcome or summary. One bounded SSE parser serves the route regardless of absent or misleading media labels. Optional event labels must agree with JSON types. A matching created or completed identity plus complete indexed item events may supply empty terminal output; populated terminal output must agree. Deltas never supply accepted results. Native and catalog media admission remains unchanged; no JSON or HTML fallback is implied.
- A failed or error event may retain only a nonempty machine-readable code of at most 128 safe ASCII bytes from its documented location, after token-reflection rejection. Malformed or unsafe codes stay generic. Only recognized temporary usage-unavailable codes map to unavailable.
- A non-200 response retains only its numeric status: 4xx maps to rejected, 5xx to unavailable, others to invalid response. Check output shows the status with fixed advice; 401, 403 and 503 receive distinct advice, while 429, other 5xx and unknown statuses stay cautious and infer no plan limit. No failure saves evidence, retries, switches billing or erases a stored token on one 401.
- Observed Runs preserve only closed reasons: account access, usage limit, temporary usage or service unavailability, stream protocol, selected response contract, structured outcome contract or local output acceptance. Canonical Events hold no raw status, code, upstream text, body or request ID. A reason does not establish credential invalidity, exact quota, retry time or billing. There is no automatic retry, model or encoding fallback, or billing switch.
- Run and compaction Events pin an opaque admission fingerprint, account UUID, closed category and local-only output bound. Its `account_consent` HMAC uses a domain separate from optional checks and binds model, effort, verified client, subject, host, account UUID, exact storage consent and versions. Missing categories, unknown values or unknown fields fail closed.
- Setup, after verified save, selects a low-effort default from the account catalog: visible `gpt-5.6-luna` if present, otherwise the first visible row with prices reported as unknown. It asks no model, effort or cost questions.

- Changing the request or decoder, effort mapping, consent or output-bound semantics bumps the account-admission contract version. Checker versions do not affect it.

## Acceptance scenarios and evidence owners

Tests: [`src/cli/chatgpt/account/tests.rs::private_file_accounts_reopen_and_reject_cross_account_drift`](../../src/cli/chatgpt/account/tests.rs); [`tests/session_run/setup/offline_https/chatgpt.rs::release_private_file_chatgpt_checked_direct_and_team_turns`](../../tests/session_run/setup/offline_https/chatgpt.rs); [`src/provider/openai/subscription/tests.rs::only_a_complete_bounded_terminal_event_yields_an_outcome`](../../src/provider/openai/subscription/tests.rs).

| Scenario | Required outcome |
|---|---|
| Authorization transaction | One attempt binds state, nonce and PKCE to one exact callback. Invalid, stalled or wrong-path requests get inert rejections, and no code or token is reflected. |
| Identity and subject | Only RS256 tokens with exact audience, `azp` and signed subject return credentials. A returning sign-in with another subject cannot replace the account. |
| Checked turn | Setup completes without inference. An explicit diagnostic publishes evidence, and two account-bound direct Runs plus one team child replay under the local-only bound. |
| Subscription stream and outcome | Only `response.completed` with bounded usage and a valid strict outcome succeeds. Failed, incomplete, malformed or interrupted streams publish no partial outcome. |
| Renewal, logout and uncertain storage | Pending renewal or sign-out markers block use until verified reauthorization. Uncertain deletion stays blocked and visible. |

Offline proof establishes no live browser, live account, native keyring setup or paid Run.

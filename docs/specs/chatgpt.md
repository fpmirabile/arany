# ChatGPT-plan access

## Scope

This contract owns the ChatGPT-plan OAuth route through the public Codex client: sign-in, verified identity and account, plan consent, renewal, logout, and the account's catalog and Runs with their local-only output bound, an accepted weaker trade-off. The route never falls back to API-key billing, never uses a private route and never imports another harness's tokens. Storage limits belong to the [credential contract](./credentials.md), inference admission to the [Provider contract](./provider/README.md) and accepted outcomes to the [execution contract](./execution/events-and-outcomes.md#accepted-outcomes). Live checks stay in [next steps](../../NEXT_STEPS.md#beta-2-and-broader-release). Editing constraints: [security rules](../../agents/security.md).

## Authorization transaction

- Each attempt binds fresh `state`, nonce and PKCE `S256` from OS randomness to `http://127.0.0.1:1455/auth/callback`, using port `1457` only when `1455` is busy; other bind failures refuse with the busy-port category before opening the browser.
- Authorization uses `https://auth.openai.com/oauth/authorize`, compiled client `app_EMoamEEZ73f0CkXaXp7hrann`, scopes `openid profile email offline_access`, and `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, `originator=arany`, with no `resource` or host hint. Callbacks require `code` and exact `state`, ignoring other parameters.
- The account-root host record stores one stable UUIDv4 before authorization; it holds no code, token or consent and grants no authority.
- The one-shot listener starts only after the current `RiskPrompt` acknowledgment and accepts at most eight connections within a two-minute aggregate and a five-second per-connection deadline. Invalid requests get an inert rejection without consuming the attempt. The accepted request is one HTTP/1.1 GET on the exact path and `Host`, with no `Origin` or body headers, capped at 8 KiB<!-- unrelated-bound: OAuth callback request headers --> and 32 headers. Responses never reflect a code or token, and the browser is opened only on the compiled authorization origin.
- The code is redeemed once at `https://auth.openai.com/oauth/token` as a form POST of only `grant_type=authorization_code`, compiled `client_id`, `code`, exact `redirect_uri` and `code_verifier`. The reply requires `id_token`, `access_token`, `refresh_token` and bounded numeric `expires_in`; optional `scope` is only bounds-checked. `invalid_grant` marks the code unusable, never retried.
- The ID token must verify (RS256, issuer JWKS) on signature, issuer, audience (exactly the compiled client; a present `azp` must equal it), nonce, lifetime and a nonempty subject. The `chatgpt_account_id` claim under `https://api.openai.com/auth` must be nonempty and at most 128 safe-ASCII bytes; it identifies the backend account and never enters Events, logs or display. Rejection reports only a typed category (format, signing key, signature, claim binding, account claim or time), never a token, claim, callback or body.
- A returning attempt requires the signed subject and account ID to match the selected account. Access-token contents and a browser callback alone are never account authority or verified sign-in.

## Accounts, consent and storage

- After risk consent, new-account setup opens the browser directly; cancelling preserves all saved accounts.
- Prompt warnings follow the [terminal setup contract](./terminal/setup-and-accounts.md#setup-and-account-choices) and the Linux keyring warning the [credential contract](./credentials.md#limits-and-record-admission). The file warning states that owner-only modes neither encrypt tokens nor exclude same-user processes; the warning names the Codex backend. Consent binds backend, warning version and exact text to client, subject, account ID and host; changing any one requires fresh consent.
- A missing verified account claim refuses sign-in without saving anything. Backend plan-access refusals are per-call reasons, never stored permission state.
- Access expiry is stored as an absolute time, so it survives restart.
- Near-expiry refresh is serialized across processes. An `Unavailable` exchange keeps the old credentials. Only a recognized terminal refresh error disconnects the account and deletes its token; uncertain deletion keeps use blocked. Other failures (transport, rate limit, server, malformed, unknown) keep the stored credential and block loads until verified reauthorization. An invalid client requires registration repair, not token deletion.
- Keyring accounts each get their own slot, `chatgpt-` plus the base64url SHA-256 of the client ID and account UUID, recorded as non-secret `keyring_slot`, separate from native API slots; a token is read only from the slot its index entry records.
- Account identity is the triple of client ID, subject and account ID within one host and storage; verified sign-in matches only the exact triple, and duplicate triples or slots reject the index. Reauthorization binds to the selected UUID, preserves UUID and backend, rejects client, host, subject, account-ID or backend drift, and refuses with the registration-conflict category, changing nothing, if another entry holds that triple.
- Private-file tokens live in the checked index, never SQLite. An uncertain new-account write never publishes a selection, though an orphan keyring item may remain. Reopen rejects backend or consent drift, a missing selected keyring item and a subject or host mismatch. Token use requires the current exact consent. [Record limits](./credentials.md#limits-and-record-admission) apply.
- Attached setup can save a verified new account, switch to a saved UUID (pinning account-only Session defaults until a catalog read or explicit choice) or reauthorize the selected one without reading the old token. Cancelling before save changes no credentials, defaults or selection. Catalog defaults keep catalog order; account drift and empty catalogs reject.
- A locked keyring refuses private-file fallback; an unavailable or timed-out probe permits the explicit storage choice. Malformed saved metadata gets its own recovery diagnostic and never relaxes identity checks.
- Opening a Session or `/provider chatgpt` reads only the selected account ID, with no token, keyring or refresh. Catalog and Run paths reject pending, disconnected or invalid renewal, or a selection other than the attached caller's pinned UUID, before any Provider request or Workspace disclosure.

## Logout

`provider logout chatgpt` signs out only the selected account. Revocation uses the compiled issuer's OpenID configuration and a same-origin HTTPS endpoint; only an empty HTTP `200` confirms it, and transport and 5xx failures get two backoff-and-jitter retries within 30 seconds<!-- unrelated-bound: ChatGPT revocation retry deadline -->. The account is then disconnected, keeping identity and registration for reconnect, and its token deleted. A failed remote step still disconnects locally and warns in ChatGPT Settings. An in-flight Provider request is not cancelled, and logout does not securely erase backups or stop same-user processes.

Setup's removal of a ChatGPT account is local only: it confirms the full account ID, clears the local token and forgets the identity, leaving remote access unchanged. Removing the selection chooses a remaining usable entry, otherwise the first retained entry; an empty index has no selection.

[Uncertain](./execution/events-and-outcomes.md#effect-outcomes) keyring deletion, on logout, removal or terminal refresh, keeps the account disconnected and blocked; setup ends with an uncertainty notice, and retry needs a fresh setup.

## Catalog and Runs

Until the [backend route](../../planning/usage-limits/README.md) is admitted, renewal, catalog and Runs refuse before token load or Workspace disclosure with the closed `backend route not admitted` reason and advice to update Arany. Setup saves the verified account with account-only defaults and reports that refusal; the rules below do not bypass the gate.

- `provider models chatgpt` reads only the selected account's token at the compiled `/v1/models` route, sending no Workspace input and using neither `OPENAI_API_KEY`, `--saved-account` nor `--state-dir`. It lists every `visibility: "list"` row in server order with bounded slug and display name. An optional numeric `context_window` within 32,768–2,000,000 tokens is the row's window; any other value is absent, and a non-numeric or duplicate field is an invalid catalog. Listings show the window with at most one decimal and no trailing `.0` (`272k tokens`, `32.8k tokens`, `1M tokens`), or `unknown`. Visibility grants no Run or effort capability. One 20-second read, no retry; replies over 1 MiB<!-- unrelated-bound: subscription model catalog response -->, compressed or redirected replies, duplicate or oversized rows and token reflection are an invalid catalog. A non-success status reports only its numeric code and fixed advice.
- Arany sends no plan-consuming request the user did not ask for: a listed model is admitted without a probe, and each Run's strict decoder validates the real response. A refused account index is [archived intact](./execution/persistence.md#incompatible-records); nothing converts its credentials or consent.
- After verified save, setup selects a low-effort default without inference: visible `gpt-5.6-luna` if present, otherwise the first visible row with prices reported as unknown, asking no model, effort or cost questions. Catalog cancellation or failure after a new, switched or replaced account leaves account-only defaults with a visible retry notice; failed reuse of the current account keeps Session defaults.

Run admission:

- Run admission revalidates account identity and consent before Workspace input and takes the selected slug's window from the [catalog window cache](./provider/selection.md#per-role-selection-and-fallback), journaled as `RunStarted.config.context_window_tokens`, without a catalog read, plan-consuming check or inference call.
- Every successful startup, setup or `/model` catalog read refreshes that cache. A missing or out-of-range window means the default [context ceiling](./session.md#context-and-compaction); an unavailable catalog never stops admission.
- Catalog metadata only resizes bounded budgets and grants no model, effort or account authority. Team children and Goal continuations reuse the admitted provider; explicitly configured role routes admit their own. Replayed provenance grants no authority.

Requests and streams:

- Tool calls follow the [Provider Tool encoding](./provider/encoding-and-streaming.md#structured-outcomes-and-tool-encoding); compaction follows its plain-text contract. The Session UUIDv7 is the `prompt_cache_key`. As the [official preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) requires, requests send `store: false`, `stream: true` and an array `input` of local history, with no `previous_response_id` and no remote `max_output_tokens`.
- The route accepts only a bounded SSE stream, whatever the media label; non-SSE JSON or HTML has no fallback. Only `response.completed` succeeds, with positive labelled usage within the [Run limits](#run-limits) and the [Provider framing bounds](./provider/encoding-and-streaming.md#streaming-and-provisional-text). `response.failed`, `response.incomplete`, malformed or interrupted streams, missing usage and local overflow publish no partial outcome or summary. Deltas never supply accepted results.
- A failed event keeps only a machine-readable code of at most 128 safe ASCII bytes; recognized temporary usage-unavailable codes map to unavailable.
- A non-200 response keeps only its numeric status, its optional plan observation, and what [Provider reliability](./provider/routing-and-usage.md#usage-provenance-and-reliability) reads. 4xx maps to rejected, 5xx to unavailable, others to invalid response. 429, other 5xx and unknown statuses infer no plan limit, and no failure switches billing or erases a stored token on one 401.
- [Plan-limit observations](./provider/routing-and-usage.md#passive-plan-limit-observations) come only from already authorized `POST /v1/responses` responses; their availability on the official route is unverified. No `/wham/usage`, `/api/codex/usage`, private endpoint, polling, WebSocket transport or new account integration is used. A 429 or usage-limit reason alone establishes no percentage, balance or reset. [Terminal freshness labels](./terminal/conversation.md#reported-usage) distinguish these account-level observations from Session token totals.
- Runs keep only closed failure reasons: account access, usage limit, rate limit, temporary usage or service unavailability, stream protocol, response contract, structured outcome contract or local output acceptance. Events hold no raw status, code, upstream text, body or request ID, and a reason establishes no credential invalidity, exact quota, retry time or billing. Retries follow [Provider reliability](./provider/routing-and-usage.md#usage-provenance-and-reliability), with no model, encoding or billing fallback.
- Run and compaction Events pin an opaque admission fingerprint, account UUID, closed category and local-only output bound; its `account_consent` HMAC binds endpoint, model, effort, client, subject, host, account UUID and storage consent. Unknown values or fields fail closed, and provenance grants no current authority.

### Run limits

Primary and editor calls declare 32,768 visible output tokens; researcher calls request 4,096. The [execution contract](./execution/events-and-outcomes.md#accepted-outcomes) owns child caps and route narrowing. The call ceiling equals the native API deadline, so existing action and Goal reservations cover it.

| Limit | Value | Overflow |
|---|---|---|
| Local output cap | The request's [role-specific cap](./execution/events-and-outcomes.md#accepted-outcomes) applied to visible output: `usage.output_tokens` minus `usage.output_tokens_details.reasoning_tokens`; absent or null details count every output token. Replay sees only the recorded total. Compaction keeps a separate 4,096 visible-token cap enforced locally through the [Session summary byte bound](./session.md#context-and-compaction). | `local_output_limit`, no retry. Reasoning above the total, or details without an unsigned 32-bit count, is a response-contract failure. |
| Reported output total | At most 1,000,000 tokens, reasoning included; journaled and charged unchanged | Response-contract failure |
| Stream idle | 300 seconds waiting for response headers and between SSE events; only a complete event restarts it | Before the status check: a send timeout, never retried. After it: a stream cut, retried and charged under [Provider reliability](./provider/routing-and-usage.md#usage-provenance-and-reliability). |
| Call ceiling | 600 seconds<!-- unrelated-bound: ChatGPT Provider call deadline --> per call, also ending at the remaining action and Goal active time | Without a decoded outcome, a stream cut, retried and charged when a retry fits the remaining time; otherwise a timeout with unknown usage, which is charged |
| Compaction | The Engine's 120-second<!-- unrelated-bound: Engine compaction call deadline --> [compaction deadline](./execution/events-and-outcomes.md#accepted-outcomes) | Compaction times out |

# Tools: authority, trust and approvals

## Authority and effect admission

`ToolGrant`, owned by Tools, is the access a caller supplies for one submission: none, the admitted private `tools.json` configuration, or the trusted Workspace grant. The Engine consumes it when admitting a submission.

Each mutation, process, Skill script and MCP call requires typed effects, deterministic restrict-only Policy and effective-capability attestation. Programs run in the separate Guard. [In-process file operations](./file-operations.md#in-process-file-operations) publish under the same admitted directory capability with their own execution-site attestation. Hooks, prompts, command regexes, classifiers and approval UI are not enforcement boundaries.

An effect is normalized once into an immutable typed intent naming actor, Run, Tool, resources, operations, destinations, descendant behavior, use count and finite action limits. Policy, approval, journal and Guard share its digest; names, prefixes, hostnames, remembered approvals and summaries never define authority. Primary and child Tool effects pass one deterministic Policy route. [Provider egress](../provider/routing-and-usage.md#configuration-and-egress) has its own admission; [execution](../execution/collaboration.md#collaboration) owns child grants.

Tool intent preflight and replay share one Session-owned reducer validator; [execution](../execution/events-and-outcomes.md#accepted-outcomes) owns its refusal causes and feedback. Preflight is read-only and grants no authority. The Engine keeps live catalog, grant, liveness and budget admission; final permission provenance, hooks and host requirements still apply at the folded start.

Effective capabilities must equal or narrow the authorized set. Unsupported enforcement dimensions, missing capabilities, failed attestation, and authentication, authorization, signature, policy or schema failures reject. Descendants keep or lose authority; there is no approval-free unsandboxed fallback, and only [Guard mode](./host-commands.md#guard-mode-and-extra-reads) `auto` without a sandbox or `off` routes commands to approved host execution. Privileged code never follows or executes a filesystem object created by a less-privileged agent or sandbox without fresh no-follow, handle-relative validation. A process starts from a trusted executable identity without ambient PATH search, with validated arguments, a pinned working directory, an allowlisted cleared environment and closed inherited descriptors and sockets. Scripts need an admitted interpreter policy. Process-tree supervision, cancellation, reaping and release of permits, transactions and temporary resources follow the native profiles and the [failure contract](./limits-and-failures.md#limits-and-failure-behavior).

## Folder trust and approvals

Every attached startup asks whether to trust the opened folder, including when no account is configured, unless that exact folder has remembered trust. Consent precedes saved-account lookup, catalog or credential access and Session discovery or creation, for new, resumed and forked entry. The flow is the same on every OS and independent of Provider flags or `--tools`; `/permissions` revisits it.

The consent screen shows the full folder path and vertical Read only / Trust choices, Read only focused. With explicit `--tools`, the first choice reads Use explicit config and keeps that private configuration when trust is skipped; neither choice expands roots or capabilities. The screen proposes metadata-only runtime and cache selections; toggling one switches to Trust. Discovery runs for initial consent or when `/permissions` opens, and a discovery failure shows a notice without aborting startup. Remembered startup revalidates only saved pins, so an unrelated over-limit manager cannot block prompt-free chat. Enter confirms, Escape dismisses without a decision and Ctrl+C exits without saving. `/permissions` first asks whether to manage folder trust or [typed Git rules](./git.md#typed-prefix-rules); folder trust rediscovers candidates, keeps exact pins and permits explicit changes. Checking a toolchain unchecks other selections of its runtime kind; linear `trust` with two of one kind asks again, and `trust N` and `use config` also work. A selection that cannot be saved reports an error and keeps the previous permissions, so startup continues read only. Consent warns that prior versions of files changed by Arany are saved unencrypted in private StateRoot storage.

Choosing read only, using explicit configuration without trust, or dismissing remembers nothing. Unavailable, malformed or unsafe trust metadata stops startup before account or Session access with a message naming the record and the failed check. A `workspace-permissions.json` its strict decoder refuses is [archived intact at startup](../execution/persistence.md#incompatible-records), so every folder asks for trust again. A non-private record or state directory offers Retry or Exit and is never archived or modified. Trust is user-owned, shared by conversations, and pinned to the exact absolute path, device and inode in private OS-user state, never in Session facts; a replaced directory needs trust again, and replay never supplies authority. Remembered grants apply only to native Providers on platforms that admit Tools; custom Providers stay read-only. Explicit private `--tools` configuration takes precedence over remembered trust and keeps its narrower roots and capabilities.

The private `workspace-permissions.json` in the fixed OS-user account root holds at most 128 entries and 64 KiB<!-- unrelated-bound: workspace trust record cap --> and is replaced atomically, owner-only. Trust generates a Tool grant for `workspace_paths: ["."]`, typed writes, discovered project Skills and a pinned resolved system `sh`, while each Run resolves Git from `PATH` ([typed Git reads](./git.md#typed-git-reads)); the entry also keeps the folder's [Git hooks](./git.md#git-hooks) answer. Optional runtime selections bind exact path, profile kind and directory device/inode to the folder entry. MCP needs explicit private configuration. Standard secret, link and mount exclusions and finite snapshots apply; `target`, `node_modules`, `.venv` and `venv` are omitted from root discovery and snapshots. Commands use the offline Guard, never the host terminal, the whole home directory, package-manager configuration or credentials.

Discovery reads bounded directory entries and executable metadata under `~/.rustup/toolchains`, the per-version Node roots of nvm, fnm, Volta and asdf, and `~/.pyenv/versions`. It never executes a candidate or reads manager or project configuration. It reads the existing command environment without creating or changing State: an absent record uses an in-memory preview, while invalid or unsafe existing state reports discovery failure. Candidates need a numeric `major.minor.patch` directory label; aliases such as `stable` and `nightly` are excluded, and the label is the manager's directory name, not a verified binary version. Python candidates need a version-specific regular executable, or a `python`/`python3` alias to one in the same `bin`; other symlinks reject. Without an exact saved pin, consent proposes the newest numeric Rust, Node and Python, breaking ties by display order; saved pins, even stale ones, win. A saved toolchain grant for a recreated root is a new candidate.

**PATH directories.** Each Run grants, without a question, every directory of the pinned command environment's `PATH`, read-only and executable, in `PATH` order. This covers absolute entries wherever they are (in the home directory, under `/opt`, in a Homebrew prefix or at a system path), counted once at their first position. Only the first [`MAX_DISCOVERY_PATH_ENTRIES`](../limits.md#max_discovery_path_entries) distinct entries count; later ones are left out and startup says so. A `PATH` over 16 KiB<!-- unrelated-bound: user program discovery PATH cap --> refuses. An entry is skipped when it has a protected path component (`.git`, `.env*`, `.aws`, `.ssh`, `.gnupg`, `.npmrc`, `.pypirc`), overlaps the Workspace, the StateRoot or the account root, collides with a fixed Linux Guard mount, cannot be opened as a directory without following links, or (on macOS) lies under a platform root (`/System`, `/bin`, `/sbin`, `/usr/bin`, `/usr/sbin`, `/usr/libexec`, `/Library/Apple`), whose binaries can carry entitlements: only `/bin` and `/usr/bin` programs run there, each through the per-program unentitled [system catalogue](./native-guard.md#macos-enforcement-and-compatibility), and the rest stay out. Contents are not reviewed: a directory runs whatever it holds, and a user-writable Homebrew prefix is granted whole, except that protected names beneath it stay hidden. A Homebrew-prefix entry stays its own search entry while the whole prefix mounts read-only for its libraries, pinned at its physical location. This exposes the user's own programs, but Arany grants only the `PATH` directories, not the home directory.

**System link targets.** A program in a granted `PATH` directory, `/usr/bin` or `/bin` that is a link resolving to an executable regular file outside every grant and runtime root brings the file's directory along, read-only and executable but not on `PATH`, when that directory is at least two levels deep, it and every ancestor are root-owned and not group- or world-writable, it is outside `$HOME`, `/home`, `/Users`, `/root` and `/private/var/root`, and it passes the checks above. Examples are `/usr/local/bin/node -> /opt/node/bin/node` and Debian alternatives into `/opt`. Links are resolved once per Run, in sorted name order per directory, scanning at most [`MAX_LINK_SCAN_ENTRIES`](../limits.md#max_link_scan_entries) directory entries and granting at most [`MAX_LINK_TARGET_GRANTS`](../limits.md#max_link_target_grants) directories; later targets stay ungranted. Each grant is pinned by device and inode like other runtime grants. Only that directory is granted: a link into a package tree, such as npm's `lib/node_modules/npm/bin`, still lacks its sibling files.

**Manager shims.** Version-manager shim directories come from a closed table with their manager root and home variable. Consent proposes them, metadata only, in environment order; saved selections keep their saved order. Homebrew documents `opt/rustup/bin`, whose proxies are bash wrappers; because SIP-protected bash strips the [page-size interposer](./native-guard.md#macos-enforcement-and-compatibility), Arany pins rustup's multicall `libexec/bin` instead. When `<prefix>/etc/rustup/settings.toml` exists, it also sets the same `RUSTUP_OVERRIDE_UNIX_FALLBACK_SETTINGS` the wrappers export. A manager root is pinned by path and device/inode with its shim directory and rechecked with it; a replaced or missing root rejects. Several managers may be selected, deduplicated by path and device/inode. A `workspace-permissions.json` that still saves `PATH` directories as selections is refused and [archived](../execution/persistence.md#incompatible-records), so the folder asks for trust again.

Selected roots mount read-only. Their `bin` joins `PATH`, followed by selected shim directories and then the granted `PATH` directories, before the fixed system path `/usr/bin:/bin`; a selected manager root sets only its manager's home variable. Label, path and device/inode bind policy and candidate tokens; Run/Guard admission and Ready/GO recheck them and reject drift before dispatch. A saved root that no longer verifies stays pinned: commands and MCP reject with `ChangedInput`, while file and Skill Tools keep working. A runtime, user-program or cache grant overlapping the Workspace, the StateRoot or a fixed Guard runtime root rejects. Profile numbers use kind order (Rust, Node, Python, Cargo archive/source/index caches, npm cache, pip HTTP/wheel caches, Apple compiler, Apple SDK), then descending lexicographic version label, then ascending absolute path and token. Saved selections match by token, never by display position.

On macOS, Rust also proposes the Command Line Tools compiler and the newest numeric physical SDK, keeping exact saved pins. The compiler profile is the fixed physical `/Library/Developer/CommandLineTools/usr` root. Admission requires root-owned, non-group/world-writable directories, a root-owned `cc` link to `clang`, and root-owned, single-link, executable, non-set-ID, non-group/world-writable `clang` and `ld`. The native signature check must show both executables are unentitled; an unknown result is not checked at discovery, and the Guard refuses the grant at bootstrap with `ProtectionUnavailable`. Only `cc`, `clang` and `ld` receive process-exec permission. SDK profiles are exact physical `MacOSX<version>.sdk` directories under `/Library/Developer/CommandLineTools/SDKs`; versions have two or three canonical numeric components, each in the range 0–65535 with a nonzero major component, and a total length at most 32 bytes. The SDK directory and its required contents must be root-owned and not group/world-writable. Compiler and SDK grants bind kind, manager, exact path and directory device/inode; the SDK also binds its version. Each is deselectable and counts toward the [selected runtime grant ceiling](./limits-and-failures.md#limits-and-failure-behavior).

Optional host caches are separate read-only grants: Cargo's exact `registry/cache`, `registry/src` and `registry/index`; npm's exact `_cacache`; pip's exact `http-v2` or `wheels` under `~/.cache/pip` (Linux) or `~/Library/Caches/pip` (macOS). Existing caches are proposed only with their runtime, only human Trust saves them, and no parent cache mounts. Consent warns that caches may disclose private package names, source, registry metadata or credential URLs, which commands and MCP can emit into journaled output that later Provider requests carry; Arany never auto-loads them. Configuration, credential files, environment values and parent directories stay unavailable. A selected read-only host subtree takes precedence for that Run: Arany neither archives it nor restores private bytes over it, and keeps earlier Arany-owned entries at that subtree when publishing other cache changes. Disabling the opt-in restores the private writable view and those entries. Cache data supplies no authority.

Shift+Tab cycles **Auto edits → Request approvals → Auto approval → Auto edits**, keeping the draft and caret. The mode shows beside the composer and follows the selected Provider's native capability; selecting a supported native Provider after trusting an unconfigured conversation restores the remembered mode. Inside the sandbox nothing asks in any mode: guarded commands, local MCP calls and the integration of a guarded command's validated changeset run without a question; deny and ask rules (path-scoped `Edit` rules match each changeset path), protected paths, hooks and plan still narrow them. A remote MCP call leaves the Guard, so it still asks a human, or the review in Auto approval, unless a user allow rule covers it. Auto edits allows typed edits and asks for Git writes and host work; Request approvals asks for every other effect. Reads and Skill or catalog discovery need the pinned grant but no per-action question. In Auto approval, user rules resolve first (deny, ask, then the user's allow, typed and remembered host prefixes), and only an action outside the sandbox that no rule decided goes to the selected AI review, which may approve it within the pinned grant and can add model usage. <a id="auto-approved-workspace-edits"></a>A typed file edit (write, edit, multiedit, delete, move, mkdir) or a command or editor changeset publication inside the Workspace runs with no review and verdict source `mode`, unless a written path is protected; deny and ask rules, hooks and plan still apply first, and a user allow rule still approves a protected-path write. Protected paths are the configuration and instruction paths agents and tools read: the directories `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn` and `.claude`, plus the `.agents` directory, at any depth; and the files `.gitconfig`, `.gitmodules`, shell startup files (`.bashrc`, `.bash_profile`, `.bash_login`, `.bash_aliases`, `.bash_logout`, `.zshrc`, `.zprofile`, `.zshenv`, `.zlogin`, `.zlogout`, `.profile`, `.envrc`), package-manager and build configuration (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnp.cjs`, `.pnp.loader.mjs`, `.pnpmfile.cjs`, `bunfig.toml`, `.bunfig.toml`, `.bazelrc`, `.bazelversion`, `.bazeliskrc`, `gradle-wrapper.properties`, `maven-wrapper.properties`), hook and tool configuration (`.pre-commit-config.yaml`, `lefthook.yml`, `lefthook.yaml`, `.lefthook.yml`, `.lefthook.yaml`, `.devcontainer.json`, `.ripgreprc`, `pyrightconfig.json`, `.mcp.json`, `.claude.json`) and the instruction files `AGENTS.md`, `AGENTS.override.md` and `CLAUDE.md`. A write to a protected path still goes to the review. Ask-rule matches, a push or PR to any destination other than the folder's [pinned repository](./git.md#human-approved-host-git), and new [extra read directories](./host-commands.md#guard-mode-and-extra-reads) always need a human. Uncertainty, invalid output, failure, an exhausted review budget, or switching out of Auto during review asks the user; without a human channel the action is refused.

A human approval shows the exact proposed action; [terminal approval](../terminal/commands.md#interactive-commands-and-completion) owns layout, focus, labels and linear replies. All pages must be reviewed before accepting. Approval is one-use and never expands the grant. Primary ordinary, hook Ask and unguarded prompts have no wall-clock expiry while their human channel and Run are live. Escape and Ctrl+C cancel the Run; explicit No declines the proposal. Pause, cancellation and channel or turn shutdown withdraw pending work. Losing a delegated Ask's local approval inbox or reply sender cancels the Run; an explicitly delivered unavailable reply from a live channel differs from channel shutdown. A missing, invalid or undelivered reply while the Run is live records unavailable approval, never human decline. A late allow still revalidates the admitted directory, any explicit file-content precondition, executable bytes, grant/enforcement digests and worker revision before dispatch; no pin is refreshed. Ordinary reads pin no file content. Permission settings stay the Run snapshot: editing the rules file during a wait affects later admission, not the pending decision.

A child Ask stays pending while its human channel and Run are live. Its shared delegation and finite Goal active-time allowance pause during an idle human wait and keep running during overlapping sibling Provider, effect, preparation and cleanup work. Exhaustion withdraws the ask before dispatch with the delegation or Goal cause, never as human decline; cancellation and pause win over an accept, and dispatch rechecks the allowance. The non-dispatched observation stores `approval_cause` as `cancelled`, `paused`, `channel_unavailable`, `declined` or, on older observations only, `child_timeout`; active-time withdrawal uses the typed limit and Run stop causes instead, and other observations carry `null`. Presentation and replay use typed causes, never output text, and replay never restores a live request. The shared [denial delivery rules](./permissions.md#permission-modes-rules-and-hooks) apply. Cancellation, pause, hook stop, [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) effects and exhausted or unavailable continuation still stop; completed effects are not rolled back.

AI reviews have a 20-second ceiling, a 256-token output cap, no Tools, project instructions, history or includes, and canonical Provider-call usage. A review sees only the user's own prompts in this Session (accepted messages and steering notes, newest kept within 32 KiB<!-- unrelated-bound: AI review user prompt cap -->, older ones replaced by one marker) and the exact action, without the model's justification or proposed prefix, and decides whether the action is within what the user asked for. It never sees model text, Tool output, repository content, hook output, plans, Goal facts or child reports; children are reviewed against the same prompts, never their model-written objective. They share the primary call budget while preserving final continuation; review text never becomes an assistant answer. Each accepted review is pinned to its pending Tool in the projection; ownership is never inferred from adjacent review calls, so an approval-mode change cannot duplicate an integration review. Headless `--tools` uses its explicit private upfront grant without an interactive approval channel.

Workspace input resolves one component at a time beneath the pinned directory handle with no-follow semantics. Symlinks, special files, absolute paths, empty components, `.` and `..` reject. Candidates open nonblocking before the regular-file check, and the validated handle is used instead of reopening by path.

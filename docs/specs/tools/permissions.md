# Tools: permission modes and rules

## Permission modes, rules and hooks

Permission settings apply to primary and researcher Tool steps. Optional `permissions.json` is a user settings record beside `tools.json` in the admitted StateRoot, outside the Workspace, admitted like `provider-routing.json`. Malformed JSON, unknown fields, group/world-readable or symlinked files and oversized settings reject Tool admission with a Configuration error before Provider usage or any Tool intent. Missing settings keep the interactive and headless approval behavior and terminal mode cycle unchanged. Repository, Skill, model and hook text never select trust. Settings are data, not executable configuration or a grant; hook commands run only as [Hook execution](./hooks.md#hook-execution) defines.

Tool admission snapshots the settings once and pins the SHA-256 of their bytes in `RunStarted.tool_policy.permissions_digest` (`null` when absent); editing the file never changes an admitted Run. Present settings select the mode and approval path below, also headless: a required human approval without a channel denies, and AI review may use the admitted review Provider.

Every configured step journals its permission verdict in `ToolStarted` before dispatch or its denied observation; `verdict` is required and nullable, null only for unconfigured pinned-grant steps. A step needing a pre-hook, AI review or human approval first commits `ToolProposed` with the immutable intent ([ordering](../execution/events-and-outcomes.md#committed-event-stream)). The verdict binds the exact intent digest, effective decision, pinned settings mode, rule/mode/grant basis, final approval, approval source (`rule`, `mode`, `pinned_grant`, `human`, `ai_review`, `unavailable_approval`, `session_approval`, `hook`, `typed_prefix_rule` or `host_prefix_rule`), the narrowest `hook_restriction` (`null` when none) and the number of `hooks` that ran. Replay rejects missing, duplicate or mismatched verdicts, any effect after a denial, and an AI preapproval without a recorded review, and never reads settings, reruns a review or dispatches. [Execution](../execution/admission-and-recovery.md#admission-persistence-and-recovery) owns payload versions.

In a Run without settings, only a primary or [sandbox-less editor](./editors.md#editor-tool-steps) [host command](./host-commands.md#primary-host-commands), a primary [typed Git write](./git.md#typed-git-writes) or a primary [`gh_pr_list` / `gh_pr_view` read](./git.md#host-pull-request-listing) records a verdict, with `mode: null`. Host commands and typed Git writes then use basis `mode` or `pinned_grant` and source `mode`, `pinned_grant`, `human`, `ai_review` or `unavailable_approval`; a `gh_pr_list` or `gh_pr_view` approval needs a `human` answer to an `ask`, or is denied as `unavailable_approval`.

The same settings restrict children, which cannot select their own settings or expand their read-only spawn grant. Explicit asks go to the human. Auto reviews of researcher MCP discovery see the child's exact intent and the Goal objective, within the [shared delegation active-time allowance](./trust-and-approvals.md#folder-trust-and-approvals) and budget. Tool steps after primary synthesis skip review: required approval goes to a human or denies without a channel. Rules never bypass the Goal plan, deterministic Policy, pinned grant or Guard. Denials use labels such as `permission_rule_denied`, `permission_mode_denied`, `hook_denied`, `user_declined` or `channel_unavailable`, never hook prose, rule text or undisclosed paths. A committed denial reaches its requesting actor once as a Tool result. Every new proposal gets a fresh permission check; a refusal never retries the effect.

### Modes and approval decisions

The terminal cycles **Auto edits → Request approvals → Auto approval** ([folder trust](./trust-and-approvals.md#folder-trust-and-approvals)), which map to `acceptEdits`, `default` and `auto` below. In every mode, nothing asks inside the sandbox: guarded commands, local MCP calls and the integration of a guarded command's validated changeset run without a question, still narrowed by deny and ask rules (path-scoped `Edit` rules match each changeset path), protected paths, hooks and plan. A remote MCP call leaves the Guard, so it asks unless a user allow rule covers it. Reads and Skill or catalog discovery need the pinned grant but no per-action question. In `auto`, user rules resolve first (deny, ask, then the user's allow, typed and remembered host prefixes); only an action outside the sandbox that no rule decided goes to the selected AI review, which may approve it within the pinned grant and can add model usage. Ask-rule matches, a push or PR to any destination other than the folder's [pinned repository](./git.md#human-approved-host-git), and new [extra read directories](./host-commands.md#guard-mode-and-extra-reads) always need a human. Review uncertainty, invalid output, failure, an exhausted review budget, or switching out of Auto during review asks the user; without a human channel the action is refused.

The [serve approval transport](../serve.md#server-requests) is another human client of the same channel, with negotiated live-session scope for eligible primary host commands. The [ACP adapter](../acp.md#tool-updates-and-permissions) permits ordinary one-use client verdicts, including user-configured client policy. ACP v1 cannot attest a human gesture, so unresolved host-command asks and hook Asks there dispatch nothing, send no permission request and journal `unavailable_approval`; AI review, mode changes and client capabilities cannot resolve them. Host-prefix preapproval follows [Remembered host prefixes](./host-commands.md#remembered-host-prefixes); client policy and `allow_always` supply no host authority.

The five spellings are case-sensitive; aliases and bypass modes reject. An omitted `defaultMode` parses as `default` and does not change Arany's interactive default.

| Mode | Arany behavior |
|---|---|
| `default` | `Request`: outside the sandbox, absent a matching allow, a fresh one-use human approval for each effect needing approval. Remembered Tool use cannot renew an immutable intent. |
| `acceptEdits` | `AutoEdits`: typed mutations and sandboxed work proceed; Git writes and host work ask unless a user allow, typed or remembered host prefix rule matches. |
| `plan` | Deny mutations and command/MCP processes, even with allow rules. Permit admitted typed reads, Skill reads and typed Git reads; arbitrary argv and MCP metadata cannot prove a read-only effect. |
| `auto` | `Auto`: user rules first, then AI review as above; typed edits and changeset publication inside the Workspace run unreviewed unless they touch a [protected path](./trust-and-approvals.md#auto-approved-workspace-edits). Budgets, failure-to-human fallback and cancellation stay mandatory. |
| `dontAsk` | An unresolved `Ask`, including a hook `ask`, becomes `Deny` (the hook `ask` is still recorded); otherwise admitted no-question calls and matching allows proceed. An explicit ask rule denies. |

Settings and the live terminal mode are independent restrictions: a call asks if either asks, human Request takes precedence over AI review or edit preapproval, and neither widens a settings Ask or Deny.

Each decision is `Allow`, `Deny` or `Ask`: an approval disposition within the pinned grant, never authority. Invalid or oversized calls deny. An explicit ask rule selects a human even under `auto` or `acceptEdits`. Every call still needs deterministic Policy admission, guarded calls Guard attestation, and executed host commands record an `UnguardedReceipt` ([Primary host commands](./host-commands.md#primary-host-commands)). Restrictions combine as `Deny > Ask > Allow`. A hook's `allow` is ignored because it is program output; only a human or the Auto review resolves an Ask. Children keep the intersection with parent authority. `command_unguarded` is never pre-approved by an ordinary allow rule or a mode, only by its [session or host-prefix authority](./host-commands.md#primary-host-commands), a human or, in `auto`, the AI review; `plan` denies it.

**Allow rules:** a matching allow rule pre-approves an action that would otherwise ask, without a human prompt or AI review, in every mode but `plan` and `dontAsk`'s denials. It never bypasses the Guard, Policy or pinned grant, and deny and ask keep precedence. Ordinary allow rules never cover host work (host commands use remembered host prefixes, host Git uses typed rules), so even `Bash(*)` cannot approve anything outside the sandbox.

**Typed Git prefix rules** ([owner](./git.md#typed-prefix-rules)). A matching typed `allow` rule skips the prompt and the review in every mode but `plan`; the verdict records `typed_prefix_rule`. A typed allow for `git push` or `gh pr create` approves any destination; without one, only Auto approval reviews a push or PR, and only to the folder's pinned repository. Deny and ask rules in either list win over any allow, and a typed rule never overrides an ordinary Read, Edit, path or tool-name restriction. Rules are user-owned; repository content never adds or widens one.

### Permission rules

Permission rules use this envelope:

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(git diff *)", "Read(./crates/arany/src/**)"],
    "deny": ["Read(./private/**)"],
    "ask": ["Edit(./crates/arany/src/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "/reviewed/check", "timeout": 30}]
      }
    ]
  }
}
```

Every envelope and permissions field shown is optional, defaulting to empty lists/maps. Unknown or duplicate fields, wrong types, unsupported names and malformed rules reject the whole document. A rule is a bare Tool or `Tool(specifier)`; inner parentheses are literal. Lists evaluate in deny, ask, allow order regardless of specificity or input order, and no exception within a list undoes a match.

| Rule Tool | Typed Arany operations |
|---|---|
| `Bash` | `command`; the subject is its admitted logical program identifier and argv, not an inferred executable basename. |
| `Read` | `list`, `read`, `search`, `glob`; deny and ask also cover `git_status`, `git_diff` and `git_log` paths, Skill files inside the Workspace, and [Git writes](./git.md#typed-git-writes): commit paths and potentially covered descendants, plus every staged or whole-repository commit and every switch, whose paths are unknown before dispatch. A deny also covers typed mutations and changeset paths, so a read denial cannot be written through. |
| `Edit` | `mkdir`, `write`, `edit`, `multiedit`, `delete`, `move`, `apply_changeset`; deny and ask also cover the same [Git writes](./git.md#typed-git-writes) as `Read`. |
| `MultiEdit` | `multiedit`, with the same Edit-family path rules and read-denial protection. |
| `Write`, `Glob` | Bare `write`, and bare `list` and `glob`; path specifiers reject in favor of `Edit` and `Read`. |
| `Grep`, `Skill` | `search` path and admitted `skill` name. Skill wildcards match names, not authority or resource discovery. |
| `mcp__<server>__<tool>` | `mcp_call`, matched against separate server and tool fields; the Tool segment supports `*`. `mcp__<server>` also covers that server's catalog listing and all calls; `mcp__*` covers all servers for deny/ask. |
| `Network(domain:x)` | Not a call matcher: a host pattern that extends or restricts a configured [network grant](./commands-and-cache.md#network-grants-and-egress-proxy). Allow adds the domain; deny and ask remove it. The domain uses the grant grammar; `Network` alone, other specifiers and invalid patterns reject. |
| Exact Arany catalog name | That operation only, including `git_status`, `git_diff`, `git_log`, `mcp_list` and `mcp_call`. Native MCP operation names accept bare rules only. |

Bare Tool-name `*` globs are supported for deny and ask against rule Tool and native operation names; a non-MCP glob matching no known operation rejects. MCP allow rules require a literal server; generic allow name-globs reject. Server patterns are at most 64 bytes of lowercase ASCII letters, digits, `_`, `-` and `*`; Tool patterns are at most 128 bytes within the complete-rule ceiling. MCP allows compare parsed server and Tool fields separately. Deny/ask also test the complete rule-name glob against the call or catalog subject, including `__` descendants, so a rule can restrict a whole server; ambiguous server names containing `__` or ending in `_` may be over-restricted but never pre-approved. Matching discovers no servers. A changeset allow requires every path to match the same rule; deny/ask requires any path. Separate allows cannot assemble authority for an otherwise unmatched batch.

In Bash patterns, `*` spans spaces and exact patterns stay exact. A sole trailing ` *` also matches the bare command but keeps its word boundary; trailing `:*` is equivalent; `Bash(*)` equals bare `Bash`. Other characters are literal.

Only unambiguous argv words of ASCII letters/digits and `_./:@+=,%~-` are joined with spaces for specifier matching. Empty, quoted, whitespace-bearing or shell/control-bearing arguments are opaque: an opaque command never matches a specifier allow and matches every applicable specifier deny/ask, while a bare Tool rule still covers it. Deny/ask also check every word-boundary suffix of the joined argv, so `timeout 30 rm x`, `nice rm x`, `xargs rm x` and `env FOO=1 rm x` cannot hide an `rm *` restriction, even when the word is ordinary data. Allows match only the complete argv projection. Arany does not split shell strings, expand variables or infer commands from scripts, and text matching proves nothing about an executable's effects, disclosure or read-only behavior.

File patterns use [gitignore wildcards](https://git-scm.com/docs/gitignore#_pattern_format): `*` and `?` stay within a segment; whole-segment `**` crosses zero or more directories; alphanumeric classes/ranges, class negation and backslash-escaped literals are supported. Bare filenames match at any depth. `/path`, `./path` and multi-segment relative patterns anchor at the admitted Workspace capability, so settings placement cannot change path authority. Unanchored `crates/arany/src/**` matches only root `src` for allow and a `src` directory at any depth for deny/ask; an explicit `**/src/**` matches at any depth for every list. Deny/ask patterns compile case-insensitively; allow patterns stay case-sensitive. Deny/ask reject non-ASCII pattern literals, and any non-ASCII subject path, including changeset and Git paths, matches an applicable restrictive path rule, closing NFC/NFD and Unicode case aliases by over-restricting. Allow literals keep exact Unicode spelling. The matcher never touches the filesystem; filesystem aliases stay under the no-follow grant and Guard.

Paths are Workspace-relative. `//` absolute and `~/` home anchors, traversal, empty components, trailing directory-only slashes, non-segment `**`, unsupported classes, dangling escapes, leading comments and gitignore `!` exceptions reject; restrict-only sources cannot remove prior restrictions. No-follow admission and exclusions still apply. Rules match proposed typed paths and filter results.

A commit path can publish its whole subtree, so Read/Edit deny and ask rules also apply when a commit path overlaps the rule's literal directory prefix in either direction. The prefix ends before the first segment with a wildcard, class or escape; patterns that can start at any depth have an empty prefix and restrict every commit path. Staged and whole-repository commits match every applicable restrictive path rule.

`list`, `search` and `glob` results, `git_status` and `git_diff` rows and patch sections, and `git_log` commits omit every path for which the same operation would match a deny or ask rule that the call itself did not match. An approved `search` of an asked directory therefore shows its rows while a broader call hides them, and an approver never sees paths the call did not name. While any restrictive path rule applies, a broader call drops every non-ASCII path. A covered directory covers its subtree, and Search never opens a covered file. Filtering, Git output included, precedes ordering, row and byte fitting, `limit`, `offset`, `next_offset` and `truncated`, so pages count only visible rows. Every patch section starts hidden; only a `diff --git a/P b/P` or combined `diff --cc P` header, or a staged `* Unmerged path P` line, naming a visible unquoted path reveals it, so conflict sections, unrecognized or quoted headers and a line cut by the capture limit fail closed. A collapsed untracked directory row such as `dir/` names only that directory and is hidden when a rule covers it. Git paths quoted because they contain control characters, `"` or `\` (`core.quotePath=false`) stay hidden. A filtered `git_log` reads changed paths (`--name-only` without rename detection, so a move reports both sides; merges against their first parent) for at most 1,000 commits, keeps commits changing a visible path, then applies `max_count`; a commit without path evidence is dropped and an exhausted scan sets `truncated`. Subjects of kept commits show even when they also change covered paths. Git failures follow the [typed Git disclosure policy](./git.md#typed-git-reads). Git's [capture bound](./limits-and-failures.md#limits-and-failure-behavior) still counts covered output, so a capture overflow keeps `truncated` true. A Workspace Skill file is also a file read: a `skill` call takes the stricter of its own decision and a `read` of that path, and a Skill whose `SKILL.md` is covered is omitted from the catalog, so its description is never previewed. A denied Skill file is never opened. Rules are not an OS path filter: explicit includes, interpreter I/O and subprocess filesystem access stay bounded by the grant and Guard.

### Permission limits

[Hook execution](./hooks.md#hook-execution) owns hook bounds. The whole settings document is at most [64 KiB](../limits.md#max_config_bytes), with the JSON ceiling of 4096 nodes and 32 levels<!-- unrelated-bound: permission JSON nesting depth -->. There are at most 128 permission rules across the allow, deny and ask lists and `typedPrefixes`, each complete ordinary rule at most 1024 UTF-8 bytes; controls reject. Tool calls keep the serialized argument ceiling of [Tool context](./limits-and-failures.md#limits-and-failure-behavior), checked before typed validation. Overflow rejects without partial configuration, retry or fallback; errors name the constraint without echoing rule text.

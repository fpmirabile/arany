# Tools: Git

## Typed Git reads

The Engine runs the user's own Git natively on the Workspace repository, outside the Guard, only through typed operations with fixed arguments and a minimal cage; the user's settings, credential helpers and LFS apply, and each result is journaled with its own `Git` attestation.

1. **Availability.** Each Run resolves `git` from the launching user's `PATH`, skipping relative entries and those inside the Workspace or `StateRoot/editors`, and pins its canonical path and SHA-256 in `RunStarted.config.tool_policy.git`. A candidate is a regular, executable, non-set-ID, non-group/other-writable file of at most [32 MiB](../limits.md#max_snapshot_bytes); the macOS `/usr/bin/git` shim counts only when its developer directory holds Git, so the installer dialog never opens. A different Git than the previous Run's is simply used; folder trust is not renewed. The pin is rehashed before every invocation; a changed Git fails that operation with `The Git pinned for this Run changed on disk` and runs nothing. Without a Git the catalog reports `unavailable`, offers no Git operation and never emulates Git, and editors use Arany's own copy. Git needs a `.git` (directory or gitfile) at the Workspace root, named explicitly through `GIT_DIR` and `GIT_WORK_TREE`, so linked worktrees and submodule checkouts work and no parent repository is discovered.
2. **Operations.** `git_status {path}`, `git_diff {path, base, head, staged}` and `git_log {path, revision, max_count}`. `path` is a Workspace-relative literal pathspec (`.` is the whole repository). `git_diff` compares the working tree with the index, the staged index with `base` (HEAD when null), the working tree with `base`, or two endpoint trees with Git's two-dot semantics; `head` requires `base` and excludes `staged`. A revision is `HEAD`, a ref name or a hex commit name with at most four `~N`/`^N` steps, at most 128 bytes; `git_log.revision` also accepts one `base..head` range of two nonempty valid revisions (at most 258 bytes). Open endpoints, three-dot ranges, revision sets, `:`, `@{` and options reject; ambiguous refs and missing endpoints fail before dependent reads. `max_count` is 1 through 50. Endpoints resolve once to commit OIDs; at most four invocations share the action deadline. `git_status` returns `{"branch":{"oid","head"},"entries":[{"path","state"}],"truncated"}`, `git_diff` `{"files":[{"path","added","deleted"}],"patch","truncated"}` and `git_log` `{"commits":[{"oid","parents","author","time","subject"}],"truncated"}`; endpoint diffs and ranges add `comparison` with both endpoint names and captured OIDs. A failure returns `{"failed"}`, with diagnostics under the disclosure policy below.
3. **Exclusions.** The components `.git`, `.aws`, `.ssh`, `.gnupg`, `.env`, `.env.*`, `.npmrc` and `.pypirc` are excluded ASCII-case-insensitively, history included, through `:(icase)` pathspecs and row and stderr filters. Renames are not detected and submodules are ignored. The user's and the repository's settings (line endings, file modes, excludes) shape results as in terminal Git.
4. **Cage.** The environment is cleared except the user's `HOME`, the filtered `PATH`, `XDG_CONFIG_HOME`, `SSH_AUTH_SOCK`, `GH_CONFIG_DIR` and `GH_HOST` when set, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`. Command-line settings win over every configuration file: `core.hooksPath=/dev/null` unless the user accepted the folder's [hooks](#git-hooks), `core.fsmonitor=false`, `core.pager=cat`, `core.editor=false` and `core.quotePath=false`; every invocation but a push adds `protocol.allow=never` and `GIT_NO_LAZY_FETCH=1`, so reads and local writes reach no network (configuration, not OS enforcement). Diffs and logs add `--no-ext-diff` and `--no-textconv`; reads add `--no-optional-locks`, though `git diff` may still refresh index stat data as in a terminal.
5. **Configuration admission.** Before each operation Arany refuses, without running it, when any file Git reads lies inside the Workspace outside `.git` or inside `StateRoot/editors` (covering `include.path` and `includeIf`), or an executable value names a program there. The executable keys are `filter.*.clean|smudge|process`, `diff.*.command|textconv`, `diff.external`, `merge.*.driver`, `core.sshCommand|askPass|gitProxy`, `credential.helper` and `credential.*.helper`, `gpg.program` and `gpg.*.program`, `sequence.editor`, `pager.*`, `remote.*.uploadpack|receivepack` and aliases starting with `!`. The refusal names the key or file: `Git configuration … would run a program inside this folder; Arany did not run Git`. Configuration outside the folder is the user's and runs as is (LFS filters, credential helpers, signing). Residual risk: only path-shaped words are checked, so a system program reading a Workspace file (`filter.x.clean = make clean` reading the Makefile) or a path built from `$VAR` is not caught; such values come only from the user's own configuration.
6. **Policy and disclosure.** Reads need the pinned grant and no approval in any mode. They are in the Goal prelude with plan-contract `path` scope, are never success criteria and are never offered to children. Bounds follow [limits](./limits-and-failures.md#limits-and-failure-behavior); [branch comparison](#branch-discovery) has its own ancestry scan bound. A nonzero exit is Failed and the Run may continue. Path reads suppress stderr, because diagnostics cannot be filtered by path. History and changes reach the Provider and journal as untrusted data. Residual risk: secret-path exclusions are filters, not sandbox enforcement.
7. **Ignore selection.** After capture, returned paths pass the shared bounded Git-ignore selector within the shorter of the two-second discovery window and the action deadline, reading root and nested `.gitignore` controls under the [ignore-control admission](./changesets-and-checkpoints.md#command-input-selection) and [discovery limits](./file-operations.md#typed-read-discovery). A missing control means no rules at that level; a malformed, unsafe, unavailable or over-budget one fails the whole read. Ignored paths stay hidden even when tracked or named. Filtering precedes fitting: rows are omitted, a diff section stays only when its recognized path is visible (unrecognized or quoted headers stay hidden), and a log commit needs visible changed-path evidence. A subject visible through another path is untrusted data, not a redaction guarantee. Expiry returns `Limit(timeout)`, an over-budget control `Limit(resource)`, and invalid or unsafe controls (`Path`, `FilesystemDenied`) `Denied`. Strict replay never loads current controls or reruns Git.
8. **Receipts.** A completed operation records a `Git` attestation: intent digest, pinned Git SHA-256, exit code and, for writes, HEAD (ref name or `detached`), its commit and the target ref before and after, read through Git. Replay rejects a `Git` receipt whose SHA-256 differs from the Run's pin.

### Branch discovery

`git_branch {name:null, start_point:null, scope, base, max_count}` reads local and remote-tracking tips through the primary-only Git grant on Linux and macOS, plan mode included. `scope` is `local` (null default), `remote` or `all`; `max_count` is 1–256 (256 when null). A null `base` omits comparison; an explicit base uses the read revision grammar and must resolve to a commit. Invalid inputs reject before execution. Creation follows the [write contract](#typed-git-writes) and requires these three fields null.

The JSON result has `branches`, nullable `comparison_base: {revision, oid}`, `history_complete`, `truncated` and `timed_out`. Rows are sorted by full ref name; invalid UTF-8 becomes U+FFFD and `name` is capped at 1 KiB<!-- unrelated-bound: displayed Git ref name --> on a UTF-8 boundary, `name_truncated` marking clipped or lossy names (which also set `truncated:true`). A displayed name is never an exact ref identity; a lossy local name reports `upstream_status:unsupported`. Rows carry `kind: local|remote|non-commit`, tip `oid`, `current`, nullable `symbolic_target` (same cap, with `symbolic_target_truncated`), nullable `subject`, `subject_withheld`, nullable `upstream`, `upstream_status`, nullable `ahead`/`behind`, `counts_withheld` and `counts_capped`. Non-commit refs, including annotated tags in branch namespaces, stay rows with their object OID, null subject and withheld counts; remote symbolic aliases keep their target without subject or counts. Detached or unborn HEAD still enumerates; an empty repository without a base succeeds with no rows.

The base resolves once to a commit OID. Each row compares the base with its captured tip as `ahead` and `behind`, exact up to 1,000 commits; a lookahead commit withholds both with `counts_capped:true`, never a partial count. Subject and count work share a one-second per-row deadline; reaching it leaves unobserved fields null and withheld, marks requested counts capped and moves on. Any cap sets `truncated:true`. Counts describe whole-history ancestry, not permitted-file changes. Null counts mean no comparison, an alias or non-commit row, or `counts_withheld`.

Tip subjects are at most 256 characters and need visible-path evidence from that exact commit. Mandatory secret-path exclusions filter evidence and diagnostics without disabling enrichment; unresolved restrictive user Read path rules suppress subject and count enrichment and mark them withheld. A protected-only tip, or a parentless tip in a shallow view, has a null subject with `subject_withheld:true`. Filters run before persistence and model continuation.

Remote-tracking refs are local, possibly stale observations; nothing is fetched. Shallow repositories return `history_complete:false`. Missing objects or an unresolved base fail explicitly. Captured OIDs ignore concurrent ref updates, but the result is not an atomic snapshot. Enumeration stays within the [shared read limits](./limits-and-failures.md#limits-and-failure-behavior) and the action ceiling. Reaching the work deadline returns completed rows with `truncated:true` and `timed_out:true`; a deadline during enumeration or base resolution returns an empty truncated listing (`comparison_base` null if unresolved), never an empty successful inspection. Only complete rows fit the result budget; overflow sets `truncated:true`, never partial rows or invented counts. A failed cleanup stops the action without a partial result, and a missing receipt is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes). Replay uses committed rows, flags and OIDs without running Git or rereading configuration.

Upstream associations come from Git (`%(upstream)` and `%(upstream:track)`), so user and repository branch configuration apply. `upstream_status` is:

- `present`: the branch has an upstream whose ref exists;
- `gone`: the configured upstream ref is missing, with its name retained;
- `unavailable`: the branch has no upstream;
- `unsupported`: the branch name is not valid UTF-8, so no exact association is claimed; `upstream` is null;
- `not_applicable`: a remote row has no branch upstream.

### Range history and endpoint diff

A `base..head` log lists commits reachable from head and not from base. An endpoint diff compares the two trees directly, so it includes tree changes a three-dot diff would omit. Identical endpoints give an empty successful result. Both pin the resolved OIDs and apply the ordinary exclusions, Read rules and replay rules.

### Typed prefix rules

`permissions.json` may carry `permissions.typedPrefixes`, an optional list (default empty) of `{"prefix": [...], "decision": "allow"|"ask"|"deny", "workspace": null | {"path","device","inode"}}`; every field is required and unknown or duplicate fields reject. `prefix` is exactly one of `["git","commit"]`, `["git","branch"]`, `["git","switch"]`, `["git","push"]`, `["gh","pr","create"]`, `["gh","pr","list"]` or `["gh","pr","view"]`; partial verbs, extra tokens, flags, globs, shell strings, aliases, wrappers and executable paths reject. Matching uses the validated typed operation, never argv: `git_commit`, `git_branch` with a `name` and `git_switch` map to their verbs, and branch listing is a read matching none. `push` and `pr create` match `git_push` and `gh_pr_create`; an `allow` approves any destination (only Auto approval's review is limited to the folder's [pinned repository](#human-approved-host-git)), so `/permissions` labels them `host; allow covers every destination`. `pr list` and `pr view` match `gh_pr_list` and `gh_pr_view` under the [host-read exception](#human-approved-host-git). `workspace: null` is user-wide within this state directory; an object binds the folder's exact absolute path, device and inode, so a moved or replaced folder inherits nothing. Paths are at most 4096 bytes<!-- unrelated-bound: host approval Workspace path -->, canonical, control-free, with a nonzero inode.

Typed rules and [host-prefix records](./host-commands.md#remembered-host-prefixes) share the 128-rule and [64 KiB](../limits.md#max_config_bytes) limits and the single `deny > ask > allow` order with ordinary rules, so a typed allow never overrides an ordinary deny or ask. The folder filter applies once at Run admission; the pinned digest covers the whole file, and settings never reload during a Run. A read without a Workspace identity ignores folder-scoped allows but applies folder-scoped deny and ask rules. Replay admits typed-rule verdicts only for the primary with pinned settings in every mode but `plan`, plus the first-use `mode: null` human verdict.

The only writers are the `/permissions` typed settings edit (only while no Run is active) and the remember choice below. Each save atomically applies one insert, decision change or removal to the private file, only if the file (or its absence) and the folder identity are unchanged since load or Run admission; other settings keep their values. A stale view, busy lock, replaced folder or overflow refuses with a fresh-load notice, without retry or truncation. A failure after the replacement reports `save not confirmed`, since it may have taken effect. `/permissions` may create a missing file with `defaultMode: "default"`, warning that this activates default policy for other Tools; the remember choice never creates it.

When a human approves a primary local Git write no rule or hook decided, the dialog offers `Yes, and allow git commit in this folder from the next Run` (or `git branch` or `git switch`). The human verdict (source `human`) commits before the rule is appended; a failed save denies the pending call, and a save whose final directory sync fails after the rename is an [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) `rule save not confirmed` outcome that dispatches nothing. The [host-prefix save](./host-commands.md#remembered-host-prefixes) uses the same writer. The rule applies from the next admission, so another matching call in the same Run still asks. Replay never saves. The choice needs `permissions.json` to have pinned the Run, and is never offered for children, branch listing, hook asks, explicit ask rules, serve or ACP clients, or an `exec` Run without a human.

## Human-approved host Git

The primary may request `git_push {remote, branch}`, `gh_pr_create {repository, base, head, title, body, draft}`, `gh_pr_list {repository, state, base, head, limit}` or `gh_pr_view {repository, number}`, run outside the Guard under the owner-approved exception in [AGENTS.md](../../../AGENTS.md) with the typed Git catalog, immutable intent, permission verdict, action reservation and committed observation.

Authority is closed:

- `git_push` and `gh_pr_create`, under the `deny > ask > allow` order: a matching user-owned typed allow rule approves them in every mode but `plan`; otherwise Auto approval reviews one to the folder's pinned repository, `plan` and `dontAsk` deny, and every other case (default, acceptEdits, Auto to another destination) asks a fresh one-use human approval. No ordinary rule, mode or review of another destination replaces that.
- The repository is pinned only from user-owned state: the folder's trust entry keeps the push URL a human named with the attached push approval's `Yes, and treat this destination as this folder's repository`, never `.git/config`, remote names or other repository content. A later such answer replaces it; removing the folder's trust forgets it. Each Run pins it in `RunStarted.tool_policy.git.repository`. A push matches when its effective destination after the user's rewrites equals the pin byte for byte, at admission and at dispatch; a PR matches the pin's host exactly and its owner and repository ASCII-case-insensitively. A repository-local rewrite can only make a push differ, sending it to a human.
- `gh_pr_list` and `gh_pr_view` ask a human in every mode that asks; only a matching user-owned [typed prefix](#typed-prefix-rules) allow rule may pre-approve them, and without a human channel or such a rule they refuse before dispatch.
- Repository content, ordinary rules, hooks, upfront grants and child authority never authorize any of them, nor AI review beyond the above. Children neither receive these operations nor inherit their approvals.
- All four are journaled as the separate `host` execution class, never Guard-attested; terminal, transcript, exec/show, Provider observations and Goal reports mark them `host`.

Writes keep the whole-Workspace Git/write grant and writer lock. PR operations need an explicit native `gh` Program pin in the user-owned `commands` list, never chosen by PATH or repository files, its SHA-256 verified before each spawn. The catalog offers push and PR creation to a write-enabled Run, PR operations only with that pin; availability is not authorization.

### Host pull request inspection

`gh_pr_view {repository, number}` is a primary-only read of one PR in an explicit admitted `host/owner/repository` (the [PR-listing repository bounds](#host-pull-request-listing) apply; number 1–2,147,483,647; the gh authentication host must match). It runs two fixed reads, `gh pr view` for scalar fields and one `gh api graphql` query with adapter-generated variables. The returned URL and number must match: scheme, host, route and number exactly, owner and repository ASCII-case-insensitively, as [GitHub documents for repository identity](https://docs.github.com/en/rest/repos/repos#get-a-repository). It fetches the latest 50 issue comments and 50 reviews and at most 100 check/status contexts on the head, and never paginates, accepts a caller query, follows a returned URL or mutates a PR.

Approval follows `gh_pr_list`, with the `gh pr view` rule. Both subprocesses share one deadline narrowed by the Goal allowance and the [PR-listing runtime and capture bounds](#host-pull-request-listing). The query body is capped at 8 KiB<!-- unrelated-bound: PR inspection query body cap -->; at most 200 discussion/check rows are kept; body, comment and review text are clipped to 8 KiB<!-- unrelated-bound: PR inspection text field cap --> each, other strings per the [PR-listing text bounds](#host-pull-request-listing). Truncation is explicit and the pinned result budget wins, keeping the newest comments and reviews and the first checks; if the fixed PR fields still do not fit, the result is a local budget failure with no PR data and the exit-zero host receipt. GraphQL errors fail even when gh exits successfully. Null or missing status stays unknown; empty checks means none reported. A head OID that changed between the two observations sets `stale: true` and keeps both heads, so old description and current checks never pose as one snapshot. Failure text is inspection-specific; the result is data, never instruction or authority. Confirmed auth/API/parse failures are Failed; a dispatched process without confirmed completion and cleanup is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes). Replay uses only the committed observation.

### Host pull request listing

`gh_pr_list` is a primary-only remote read: `gh pr list` for the explicit admitted `host/owner/repository` with a fixed JSON field set, state `open` (default), `closed`, `merged` or `all`, optional exact base/head names and a limit of 1–50 (default 30). The repository is at most 256 bytes and base/head at most 128 bytes, control-free and validated before argv construction. The user-owned gh authentication host must match the repository host. There is no local repository discovery, arbitrary API request, browser, pagination, mutation or URL following.

A matching typed allow rule may pre-approve it in any mode, including Plan, Auto and headless/ACP, subordinate to deny and ask. The approval names host execution, the exact repository and filters, and private PR disclosure to the current Provider; saving a rule that allows this read, including changing an ask or deny rule, repeats that disclosure and requires explicit confirmation.

Stdout is capped at 256 KiB, stderr at 4 KiB<!-- unrelated-bound: host PR listing stderr capture --> and runtime at 20 seconds, narrowed by the Goal allowance. At most 50 rows are kept; title is clipped to 256 bytes and other strings to 2 KiB<!-- unrelated-bound: host PR string projection -->, with truncation fields. A result at the limit reports `possibly_more: true`; no total is inferred. Empty output is a successful empty list. Invalid or oversized JSON and confirmed API/auth failures are Failed. An interrupted dispatch without captured completion is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) even after confirmed local cleanup, which does not establish the remote outcome. Replay uses the committed result without a process, network request or credential read.

**Intent and approval.** Failure to pin host source data refuses before approval or dispatch with `Host source data is unavailable; no operation was dispatched`; hook denials keep precedence. Push accepts one literal credential-free `https://host/path` or `ssh://git@host/path` URL and an existing local branch; remote aliases, userinfo, ports, query strings, fragments, local/file/ext transports, symlinked or ambiguous ref routing refuse. Its intent pins the local source object ID, the `OID:refs/heads/branch` refspec and the effective destination: the URL Git pushes to after the user's rewrites (the longest matching `url.*.pushInsteadOf`, else `insteadOf` through `git ls-remote --get-url`), shown in the approval as `Pushes to:`. Both are resolved again at dispatch; a change dispatches nothing. There is no force, deletion, follow-tags or recursive submodule push. PR creation pins `host/owner/repository`, base, head, title, body and draft; its local head OID detects local drift before dispatch but does not bind the remote PR commit, so the approval says the PR uses the remote head branch at creation and never shows the local OID as its source. Push and PR creation need separate one-use approvals showing the whole normalized destination and payload; PR body lines are escaped and indented beneath `Body:` so they cannot impersonate approval fields. Missing, dropped, denied or cancelled approval dispatches nothing. ACP's channel without human-only attestation refuses; a human-capable serve channel may approve. Write prompts offer once/deny only. A committed `ToolStarted` verdict with source `human` precedes launch; replay rejects an AI approval of a host write outside Auto or to any destination but the Run's pinned repository, and any Guard or unguarded receipt for that intent.

**Execution and credentials.** Push runs `git push --porcelain --no-follow-tags --recurse-submodules=no -- URL REFSPEC` in the Workspace repository after [configuration admission](#typed-git-reads), caged but with network, so the user's credential helpers, SSH agent and `core.sshCommand` apply as in a terminal. gh runs from its pinned path in the Workspace with the user's own gh configuration (`GH_CONFIG_DIR`, `GH_HOST` and `XDG_CONFIG_HOME` pass through) and `GH_PROMPT_DISABLED`, `GH_PAGER=cat` and `GH_NO_UPDATE_NOTIFIER` set; fixed arguments and an explicit repository keep it from implicitly pushing, forking, paginating or selecting another repository. Arany never reads, copies or re-injects credentials, and their values never appear in intents, catalog, Provider context, journal, diagnostics or result text. User credential helpers are user-authorized host code. Only the Git and gh binaries are hash-pinned; `ssh`, `git-remote-https`, their libraries and user-selected helpers are trusted host components.

**Bounds and outcomes.** The Host Git row in [Limits and failure behavior](./limits-and-failures.md#limits-and-failure-behavior) defines payload and runtime bounds; stdout and stderr use the Typed Git reads capture caps there, overflow terminating the process group. Malformed or control-bearing write data refuses (body newlines are allowed). After approval one monotonic deadline covers preparation and execution; a preparation timeout refuses before dispatch, and the cleanup allowance is separate. Human waiting follows the [shared approval contract](./trust-and-approvals.md#folder-trust-and-approvals), consumes neither Goal active time nor the host runtime allowance, and cannot invalidate the approved intent. Cancellation and the deadline are rechecked immediately before spawn. Raw process output is always discarded, to prevent credential disclosure. Outcomes:

- A confirmed zero exit with confirmed group teardown records a host receipt and fixed completion text.
- A confirmed exit 1 with exactly one Git porcelain rejection for the pinned refspec, `(non-fast-forward)` or `(fetch first)`, is Failed with fixed “remote reported no ref update” text; HTTPS may still have uploaded a pack.
- For PR listing or inspection, a confirmed nonzero exit, invalid JSON or capture overflow is Failed with fixed bounded text.
- Timeout, cancellation after launch, lost acknowledgement or unconfirmed teardown is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes), as are write authentication errors and gh's PR-already-exists diagnostics, which do not prove no remote effect.
- A crash after the committed approval without an outcome stays unresolved on replay.

Rewind marks host effects with a receipt, an Uncertain outcome or an approval without outcome as non-rewindable; nothing undoes, completes or rolls back a push or PR.

Host execution has no Guard filesystem, network, CPU, memory or process-count isolation, remote transfer or storage bound, DNS isolation, or containment of descendants escaping the process group; human approval and time/output bounds are its controls.

## Typed Git writes

Typed Git writes let the primary commit, create branches and switch through the [typed Git read](#typed-git-reads) runner, cage, configuration admission and receipts. [Human-approved host Git](#human-approved-host-git) owns push and PR creation; [typed prefix rules](#typed-prefix-rules) remember approval for the three local verbs.

1. **Availability.** Writes need the Run's Git pin, the whole-Workspace grant and `write: true`; otherwise only reads are listed, with a `git_branch` schema fixing `name` and `start_point` to null so plan mode can list branches. Writes are primary-only, never offered to researchers or editors, never Goal success criteria, and admitted by a plan contract only with `.` scope.
2. **Operations.** `git_commit {message, paths, staged}` commits to the current local branch either distinct literal Workspace-relative `paths` (`.` for every change), staged with `git add --all` and committed with Git's `--only` semantics while protected components stay uncommitted, or, with `staged: true` and empty `paths`, the index exactly as staged. The message is non-blank UTF-8 with no controls but newline and tab. `git_branch` with `name: null` is the [branch discovery read](#branch-discovery); creation requires `scope`, `base` and `max_count` null and runs `git branch --no-track` at `start_point` (HEAD when null). `git_switch {branch}` runs `git switch --no-guess` to an existing local branch; the current branch returns `switched: false` without running Git. There is no amend, force, delete, detach, merge, remote or raw-argument escape. The user's identity, signing, LFS filters and, only when accepted, hooks apply; without an identity, Git's own error is a Failed result.
3. **Refusals.** A commit needs HEAD on a local branch, and a switch refuses from a detached HEAD, whose commits could become unreachable. Everything else is Git's decision: switching over local changes or untracked files, empty commits, unmerged entries and merges or rebases in progress fail as in a terminal.
4. **Results.** A commit returns `{"commit","branch"}`, a creation `{"branch","oid"}` and a switch `{"branch","switched"}`; failures return `{"failed"}` with filtered diagnostics. A write run with hooks off while the folder has hooks adds `hooks_not_run`, telling the user to accept them in `/permissions`.
5. **Outcomes and locks.** One Git write, push included, is in flight per Workspace. A Git process killed, timed out, cancelled or otherwise not finishing cleanly mid-write is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) and never retried; reopen and replay neither complete nor roll it back. The Uncertain observation leads with the typed `StaleGitLocks` report when `.git` holds `*.lock` files (top level or under `refs`, at most 4,096 entries<!-- unrelated-bound: stale Git lock scan --> scanned), naming them and saying to remove them once no git process runs; Arany never deletes them. Goal resume repeats the report before refusing to resume past the unsettled write. [Rewind](./changesets-and-checkpoints.md#checkpoints-and-rewind) does not undo Git writes.
6. **Policy.** Writes run on the host outside the sandbox: Request and Auto edits ask a human, Auto approval reviews them and `plan` denies them. A matching ordinary (`git_commit`, `git_branch`, `git_switch`) or typed allow rule pre-approves them in every mode but `plan` and is required in `dontAsk`; the [typed-allow mode mapping](./permissions.md#modes-and-approval-decisions) owns the rest, and accepted hooks narrow it per the [hooks rule](#git-hooks). Commit paths, `.` and ancestors included, cannot bypass restrictive rules on their descendants. The [limits table](./limits-and-failures.md#limits-and-failure-behavior) owns every bound; a result budget below its minimum records `Limit` before any effect.

### Git hooks

Repository hooks run only when the user accepts them for the folder.

- **Detection** finds the active hooks directory as Git does: the user's `core.hooksPath` (husky, lefthook), else `.git/hooks`. Hooks are its regular executable files named after Git hooks, `*.sample` excluded; the pre-commit framework's generated hooks are labeled. A digest covers every regular file there (at most 64 files of at most 1 MiB<!-- unrelated-bound: Git hook file bytes -->), pinning helpers such as husky's `h` too.
- **Asking.** The attached terminal asks after folder trust whenever hooks exist and no saved answer covers exactly this digest, so a new or edited hook asks again; `/permissions` → Git hooks asks at any time. The answer and digest are saved in the folder's trust entry (`git_hooks`). The warning says hooks run on the host with the user's authority, outside the sandbox, and often call other model-editable files (package scripts, lint or pre-commit configuration), so pinning the hook files protects only partly.
- **No** keeps `core.hooksPath=/dev/null` for Arany's own invocations only; the user's configuration and terminal Git are untouched.
- **Yes** pins the digest per Run in `RunStarted.config.tool_policy.git.hooks`. Each write detects the hooks again and runs them only while they match; a changed hook does not run, and the result says to accept the hooks again. A write running hooks gets the command runtime ceiling instead of the Git runtime bound. Internal worktree operations never run hooks.
- **Approval.** While hooks are accepted, a Git write to the trusted folder's repository is approved only by a human approval at that moment, an admitted user-owned allow rule or, in Auto approval, the AI review, which judges the write and therefore its hooks; replay rejects any other source. With no human reachable (`exec`, serve without an approval channel), the catalog offers only the write verbs a user-owned allow rule covers, keeps branch creation read-only otherwise, and adds `Commits, branch creation and switches are left to the user; leave changes in the working tree`.
- **Terminal-only consent.** Only the attached terminal asks. `exec`, serve and ACP use the answer saved for a trusted folder, configured Runs included; with none, hooks stay off and the write result carries the notice. ACP never asks through `session/request_permission`, because a client may answer by policy and ACP client policy never authorizes host execution.

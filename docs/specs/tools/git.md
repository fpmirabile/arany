# Tools: Git

## Typed Git reads

Typed Git runs natively: the Engine starts the user's own Git on the Workspace repository, outside the Guard, through typed operations only. It applies the user's settings, credential helpers and LFS; the model never gets free Git, every invocation has fixed arguments and a minimal cage, and each result is journaled with its own `Git` attestation.

1. **Availability.** Each Run resolves `git` from the launching user's `PATH` and pins its canonical path and SHA-256 in `RunStarted.config.tool_policy.git`. `PATH` entries that are relative or inside the Workspace or `StateRoot/editors` are skipped, and a candidate must be a regular, executable, non-set-ID, non-group/other-writable file of at most [32 MiB](../limits.md#max_snapshot_bytes); on macOS the `/usr/bin/git` shim counts only when its developer directory holds Git, so it never opens the installer dialog. Folder trust is never renewed for a new Git: a Run that pins a different Git than the previous one simply uses it. Before every invocation the pinned file is hashed again; a Git that changed during the Run fails that operation with `The Git pinned for this Run changed on disk` and runs nothing. Without a Git, the catalog reports `unavailable`, no Git operation is offered, Git is never emulated and editors use Arany's own copy. Git needs a `.git` (directory or gitfile) at the Workspace root; `GIT_DIR` and `GIT_WORK_TREE` name it explicitly, so linked worktrees and submodule checkouts work and no parent repository is discovered.
2. **Operations.** `git_status {path}`, `git_diff {path, base, head, staged}` and `git_log {path, revision, max_count}`. `path` is a Workspace-relative literal pathspec (`.` is the whole repository). `git_diff` compares the working tree with the index, the staged index with `base` (HEAD when null), the working tree with `base`, or two endpoint trees with Git's two-dot semantics; `head` requires `base` and excludes `staged`. A revision is `HEAD`, a ref name or a hex commit name with at most four `~N`/`^N` steps, at most 128 bytes. `git_log.revision` also accepts one `base..head` range of two nonempty, independently valid revisions (whole range at most 258 bytes). Open endpoints, three-dot ranges, revision sets, `:`, `@{` and options reject. A revision matching ambiguous refs fails before dependent reads. `max_count` is 1 through 50. Endpoints resolve once to commit OIDs; at most four invocations share the action deadline. Results are JSON: `git_status` returns `{"branch":{"oid","head"},"entries":[{"path","state"}],"truncated"}`, `git_diff` returns `{"files":[{"path","added","deleted"}],"patch","truncated"}` and `git_log` returns `{"commits":[{"oid","parents","author","time","subject"}],"truncated"}`; endpoint diffs and ranges add `comparison` with both original endpoint names and captured OIDs. A failure returns `{"failed"}`; diagnostics follow the disclosure policy below.
3. **Exclusions.** The components `.git`, `.aws`, `.ssh`, `.gnupg`, `.env`, `.env.*`, `.npmrc` and `.pypirc` are excluded ASCII-case-insensitively, including from history, through `:(icase)` pathspecs and row and stderr filters. Renames are not detected and submodules are ignored. Results follow the user's and the repository's own settings (line endings, file modes, excludes), as the user's terminal Git shows them.
4. **Cage.** Every invocation runs with a cleared environment holding only the user's `HOME`, the filtered `PATH`, `XDG_CONFIG_HOME`, `SSH_AUTH_SOCK`, `GH_CONFIG_DIR` and `GH_HOST` when set, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`, and with command-line settings that win over every configuration file: `core.hooksPath=/dev/null` unless the user accepted the folder's hooks ([hooks](#git-hooks)), `core.fsmonitor=false`, `core.pager=cat`, `core.editor=false` and `core.quotePath=false`. Every invocation except a push also sets `protocol.allow=never` and `GIT_NO_LAZY_FETCH=1`, so reads and local writes reach no network; this is configuration, not OS enforcement. Diffs and logs add `--no-ext-diff` and `--no-textconv`; reads add `--no-optional-locks`, although `git diff`, like in a terminal, may still refresh index stat data. Each process runs in its own process group, which is stopped before the result is recorded.
5. **Configuration admission.** Before each operation Arany lists the effective configuration with `git config --list --show-origin` and refuses, without running the operation, when any file Git reads lies inside the Workspace outside `.git`, or inside `StateRoot/editors` (this covers `include.path` and `includeIf`), or when an executable value names a program there. The executable keys are `filter.*.clean|smudge|process`, `diff.*.command|textconv`, `diff.external`, `merge.*.driver`, `core.sshCommand|askPass|gitProxy`, `credential.helper` and `credential.*.helper`, `gpg.program` and `gpg.*.program`, `sequence.editor`, `pager.*`, `remote.*.uploadpack|receivepack` and aliases starting with `!`. The refusal names the key or file: `Git configuration … would run a program inside this folder; Arany did not run Git`. Configuration outside the folder is the user's and runs as is (LFS filters, credential helpers, signing). Residual risk: only path-shaped words in executable values are checked, so a value that runs a system program which then reads a Workspace file is not caught, such as `filter.x.clean = make clean` reading the Makefile, nor are paths built from `$VAR`; these values come from the user's own configuration, never from the repository.
6. **Policy and disclosure.** Git reads need the pinned grant and no approval in any mode. They are in the Goal prelude with plan-contract `path` scope, are never success criteria and are never offered to children. Bounds follow [limits](./limits-and-failures.md#limits-and-failure-behavior); [branch comparison](#branch-discovery) has a separate ancestry scan bound. A nonzero exit is Failed and the Run may continue. Stderr is suppressed for path reads, because arbitrary diagnostics cannot be filtered by path. History and changes reach the Provider and journal as untrusted data. Residual risk: secret-path exclusions are filters, not sandbox enforcement.
7. **Ignore selection.** Returned paths also pass the shared bounded Git-ignore selector, after Git capture, within the shorter of the two-second discovery window and the action deadline. It reads root and nested `.gitignore` controls under the shared [ignore-control admission](./changesets-and-checkpoints.md#command-input-selection) and [discovery limits](./file-operations.md#typed-read-discovery). A missing control means no rules at that level; a malformed, unsafe, unavailable or over-budget control fails the whole read. Ignored paths stay hidden even when tracked or named explicitly. Filtering precedes result fitting: rows are omitted, a diff section stays only when its recognized path is visible (unrecognized or quoted headers stay hidden), and a log commit needs visible changed-path evidence. A subject visible through another path is untrusted data, not a redaction guarantee. Expiry returns `Limit(timeout)`, an over-budget control `Limit(resource)`, and invalid or unsafe controls (`Path`, `FilesystemDenied`) `Denied`. Strict replay never loads current ignore controls or reruns Git.
8. **Receipts.** A completed Git operation records a `Git` attestation: the intent digest, the pinned Git's SHA-256, the exit code and, for writes, HEAD (ref name or `detached`), its commit and the target ref before and after, read through Git. Replay rejects a `Git` receipt whose SHA-256 differs from the Run's pin. A Git process that does not finish cleanly during a write is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) and never retried.

### Branch discovery

`git_branch {name:null, start_point:null, scope, base, max_count}` reads local and remote-tracking tips through the same primary-only Git grant on Linux and macOS, including plan mode. `scope` is `local` (default when null), `remote` or `all`. `max_count` is 1–256 (256 when null). A null `base` omits comparison; an explicit base uses the read revision grammar and must resolve to a commit. Invalid inputs reject before execution. Creation follows the [write contract](#typed-git-writes) and requires these three fields null.

The JSON result has `branches`, nullable `comparison_base: {revision, oid}`, `history_complete`, `truncated` and `timed_out`. Rows are sorted by full ref name; invalid UTF-8 becomes U+FFFD and `name` is capped at 1 KiB<!-- unrelated-bound: displayed Git ref name --> on a UTF-8 boundary, with `name_truncated` marking clipped or lossy names (clipped or lossy names also set `truncated:true`). A displayed name is never an exact ref identity; a lossy local name reports `upstream_status:unsupported`. Rows carry `kind: local|remote|non-commit`, tip `oid`, `current`, nullable `symbolic_target` (same cap, with `symbolic_target_truncated`), nullable `subject`, `subject_withheld`, nullable `upstream`, `upstream_status`, nullable `ahead`/`behind`, `counts_withheld` and `counts_capped`. Non-commit refs, including annotated tags in branch namespaces, stay rows with their object OID, null subject and withheld counts. Remote symbolic aliases keep their target but have no subject or counts. Detached or unborn HEAD does not prevent enumeration; an empty repository without a base succeeds with no rows.

The base resolves once to a commit OID. Each comparison runs fixed `rev-list --left-right --max-count=1001 base_oid...tip_oid` against the captured tip: left is `behind`, right is `ahead`. Up to 1,000 commits give exact counts; a lookahead commit withholds both with `counts_capped:true`, never a partial count. Subject and count work share a one-second per-row deadline, since the output cap does not bound merge-base traversal; reaching it leaves unobserved fields null and withheld, marks requested counts capped and moves on. Any cap sets `truncated:true`. Counts describe whole-history ancestry, not permitted-file changes. Null counts mean no comparison was requested, an alias or non-commit row, or `counts_withheld`.

Tip subjects are at most 256 characters and need visible-path evidence from that exact commit. Mandatory secret-path exclusions always filter evidence and diagnostics but do not disable enrichment; unresolved restrictive user Read path rules suppress subject and count enrichment and mark those fields withheld. A protected-only tip, or a parentless tip in a shallow view, has a null subject with `subject_withheld:true`. Filters run before persistence and model continuation.

Remote-tracking refs are local, possibly stale observations; nothing is fetched. Shallow repositories return `history_complete:false`. Missing objects or an unresolved base fail explicitly. Captured OIDs do not change with concurrent ref updates, but the result is not an atomic snapshot. One sorted `for-each-ref` enumerates the selected namespaces within the [shared read limits](./limits-and-failures.md#limits-and-failure-behavior); rows are enriched sequentially, with at most one subject and one comparison invocation each plus one base resolution per action. All invocations share the action ceiling, with one second reserved for teardown and delivery. Reaching the work deadline returns completed rows with `truncated:true` and `timed_out:true`; a deadline during enumeration or base resolution returns an empty truncated listing, with `comparison_base` null if unresolved. A timeout is never an empty successful inspection. Only complete rows fit the result budget: overflow sets `truncated:true`, never partial rows or invented counts. Only confirmed cleanup permits another row or a partial result; a failed or expired child reap stops the action, and a missing receipt is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes). Replay uses committed rows, flags and OIDs without running Git or rereading configuration.

Upstream associations come from Git itself (`%(upstream)` and `%(upstream:track)`), so the user's and the repository's branch configuration apply. `upstream_status` is:

- `present`: the branch has an upstream whose ref exists;
- `gone`: the configured upstream ref is missing, with its name retained;
- `unavailable`: the branch has no upstream;
- `unsupported`: the branch name is not valid UTF-8, so no exact association is claimed; `upstream` is null;
- `not_applicable`: a remote row has no branch upstream.

### Range history and endpoint diff

A `base..head` log lists commits reachable from head and not from base. An endpoint diff compares the two trees directly (two-dot), so it includes tree changes a three-dot diff would omit. Identical endpoints give an empty successful result. Ambiguous branch/tag names and missing endpoints fail before dependent reads. Both results pin the resolved OIDs and apply the ordinary exclusions, Read rules and replay rules.

### Typed prefix rules

`permissions.json` may carry `permissions.typedPrefixes`, an optional list (default empty) of `{"prefix": [...], "decision": "allow"|"ask"|"deny", "workspace": null | {"path","device","inode"}}`; every field is required and unknown or duplicate fields reject. `prefix` is exactly one of `["git","commit"]`, `["git","branch"]`, `["git","switch"]`, `["git","push"]`, `["gh","pr","create"]`, `["gh","pr","list"]` or `["gh","pr","view"]`; partial verbs, extra tokens, flags, globs, shell strings, aliases, wrappers and executable paths reject. Matching uses the validated typed operation, never argv: `git_commit`, `git_branch` with a `name` and `git_switch` map to their verbs, and branch listing is a read that matches none. `push` and `pr create` match `git_push` and `gh_pr_create`; an `allow` approves any destination, while only Auto approval's review is limited to the folder's [pinned repository](#human-approved-host-git), so `/permissions` labels them `host; allow covers every destination`. `pr list` and `pr view` match `gh_pr_list` and `gh_pr_view` under the [host-read exception](#human-approved-host-git). `workspace: null` is user-wide within this state directory; an object binds the folder's exact absolute path, device and inode, so a moved or replaced folder inherits nothing. Paths are at most 4096 bytes<!-- unrelated-bound: host approval Workspace path -->, canonical, control-free, with a nonzero inode.

Typed rules and [host-prefix records](./host-commands.md#remembered-host-prefixes) share the 128-rule and [64 KiB](../limits.md#max_config_bytes) limits with ordinary rules and the single `deny > ask > allow` order, so a typed allow never overrides an ordinary deny or ask. The folder filter applies once at Run admission; the pinned digest still covers the whole file, and settings never reload during a Run. A configuration read without a Workspace identity ignores folder-scoped allows but still applies folder-scoped deny and ask rules. Replay admits typed-rule verdicts only for the primary with pinned settings in every mode but `plan`, plus the first-use `mode: null` human verdict.

The only writers are the `/permissions` typed settings edit (only while no Run is active) and the remember choice below. Under the account replacement lock the writer rereads and validates the whole file, compares the SHA-256 the user saw (absence included), revalidates the folder identity captured at load or Run admission, applies one insert, decision change or removal, validates and atomically replaces the private file; other settings keep their values. A stale view, busy lock, replaced folder or overflow refuses with a fresh-load notice, without retry or truncation. A failure after the replacement may already have taken effect and reports `save not confirmed`. `/permissions` may create a missing file with `defaultMode: "default"`, warning that this activates default policy for other Tools; the remember choice never creates the file.

When a human approves a primary local Git write that no rule or hook decided, the dialog offers `Yes, and allow git commit in this folder from the next Run` (or `git branch` or `git switch`). The human verdict (source `human`) commits before the rule is appended. A failed save denies the pending call. A save whose final directory sync fails after the rename may be in effect, so it is an [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) `rule save not confirmed` outcome that dispatches nothing. The [host-prefix save](./host-commands.md#remembered-host-prefixes) uses the same writer. The Run keeps its pinned rules, so another matching call in the same Run still asks; the rule applies from the next admission. Replay never saves. The choice is offered only when `permissions.json` already pinned the Run, and never for children, branch listing, hook asks, explicit ask rules, serve or ACP clients, or an `exec` Run without a human.

## Human-approved host Git

The primary may request `git_push {remote, branch}`, `gh_pr_create {repository, base, head, title, body, draft}`, `gh_pr_list {repository, state, base, head, limit}` or `gh_pr_view {repository, number}`. These run outside the Guard under the owner-approved exception in [AGENTS.md](../../../AGENTS.md). They reuse the typed Git catalog, immutable intent, permission verdict, action reservation and committed observation.

Authority is closed:

- `git_push` and `gh_pr_create` follow the order of other host work: a matching user-owned typed allow rule approves them in every mode but `plan`; otherwise Auto approval reviews a push or PR to the folder's pinned repository, and every other case asks a fresh one-use human approval (`dontAsk` denies). No ordinary rule, mode or review of any other destination replaces that.
- The repository is pinned only from user-owned state: the folder's trust entry keeps the push URL a human named with the attached push approval's `Yes, and treat this destination as this folder's repository`, never from `.git/config`, remote names or other repository content; a later such answer replaces it and removing the folder's trust forgets it. Each Run pins it in `RunStarted.tool_policy.git.repository`. A push matches when its effective destination after the user's rewrites equals the pinned URL byte for byte, at admission and again at dispatch; a PR matches the pinned URL's host exactly and its owner and repository ASCII-case-insensitively. A repository-local rewrite can only make a push differ from the pin, which sends it to a human.
- `gh_pr_list` and `gh_pr_view` ask a human in every mode that asks. Only a matching user-owned [typed prefix](#typed-prefix-rules) allow rule may pre-approve them. Without a human channel or such a rule they are refused before dispatch.
- Repository content, ordinary rules, hooks, upfront grants and child authority never authorize any of them, and AI review only as above. Children neither receive these operations nor inherit their approvals.
- A push runs through the [typed Git runner](#typed-git-reads), and gh runs from its pin, both with the user's own configuration and credentials, as below.
- All four are journaled as the separate `host` execution class, are never Guard-attested, and terminal, transcript, exec/show, Provider observations and Goal reports mark them `host`.

Writes keep the whole-Workspace Git/write grant and writer lock. PR operations need an explicit native `gh` Program pin in the user-owned `commands` list; neither PATH nor repository files choose it, and its SHA-256 is verified before each spawn. The catalog offers push and PR creation to a write-enabled Run, and PR operations only with that pin; availability is not authorization.

### Host pull request inspection

`gh_pr_view {repository, number}` is a primary-only read of one PR in an explicit admitted `host/owner/repository` (the [PR-listing repository bounds](#host-pull-request-listing) apply; number 1–2,147,483,647; the gh authentication host must match). It runs fixed `gh pr view NUMBER --repo HOST/OWNER/REPO --json ...` scalar fields, then one fixed `gh api graphql --hostname HOST --method POST --input -` with adapter-generated variables. The returned URL and number must match: scheme, host, route and number exactly, owner and repository ASCII-case-insensitively, as [GitHub documents for repository identity](https://docs.github.com/en/rest/repos/repos#get-a-repository). It fetches the latest 50 issue comments and 50 reviews and at most 100 check/status contexts on the head, and never paginates, accepts a caller query, follows a returned URL or mutates a PR.

Approval follows `gh_pr_list`, with the `gh pr view` rule. Both subprocesses share one deadline narrowed by the Goal allowance and the [PR-listing runtime and capture bounds](#host-pull-request-listing). The query body is capped at 8 KiB<!-- unrelated-bound: PR inspection query body cap -->, and at most 200 discussion/check rows are kept. Body, comment and review text are clipped to 8 KiB<!-- unrelated-bound: PR inspection text field cap --> each; other strings follow the [PR-listing text bounds](#host-pull-request-listing). Truncation is explicit, and the pinned result budget wins: trimming keeps the newest comments and reviews and the first checks. If the fixed PR fields still do not fit, the result is a local budget failure with no PR data and the exit-zero host receipt, not a malformed response. GraphQL errors fail even when gh exits successfully. Null or missing status stays unknown; empty checks means none reported. A head OID that changed between the two observations sets `stale: true` and keeps both heads, so old description and current checks never pose as one snapshot. Failure text is inspection-specific. The result is data, not instruction or authority. Confirmed auth/API/parse failures are Failed; a dispatched process without confirmed completion and cleanup is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes). Replay uses only the committed observation.

### Host pull request listing

`gh_pr_list` is a primary-only remote read: `gh pr list` for the explicit admitted `host/owner/repository` with a fixed JSON field set, state `open` (default), `closed`, `merged` or `all`, optional exact base/head names and a limit of 1–50 (default 30). The repository is at most 256 bytes and base/head at most 128 bytes, control-free and validated before argv construction. The user-owned gh authentication host must match the repository host. No local repository discovery, arbitrary API request, browser, pagination, mutation or URL following is available.

A matching typed allow rule may pre-approve the read in any mode, including Plan, Auto and headless/ACP, subordinate to deny and ask. The approval names host execution, the exact repository and filters, and private PR disclosure to the current Provider. Saving a rule that allows this read, including changing an ask or deny rule, repeats that disclosure and requires explicit confirmation.

The command runs through the pinned private gh copy and the host supervisor. Stdout is capped at 256 KiB, stderr at 4 KiB<!-- unrelated-bound: host PR listing stderr capture --> and runtime at 20 seconds, narrowed by the Goal allowance. At most 50 rows are kept; title is clipped to 256 bytes and other strings to 2 KiB<!-- unrelated-bound: host PR string projection -->, with truncation fields. A result at the limit reports `possibly_more: true`; no total is inferred. Empty output is a successful empty list. Invalid or oversized JSON and confirmed API/auth failures are Failed. An interrupted dispatch without captured completion is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes) even after confirmed local cleanup, which does not establish the remote outcome. Replay uses the committed result without a process, network request or credential read.

**Intent and approval.** Failure to pin host source data refuses before approval or dispatch with `Host source data is unavailable; no operation was dispatched`; hook denials keep precedence. Push accepts one literal credential-free `https://host/path` or `ssh://git@host/path` URL and an existing local branch; remote aliases, userinfo, ports, query strings, fragments, local/file/ext transports, symlinked or ambiguous ref routing refuse. Its intent pins the local source object ID, the `OID:refs/heads/branch` refspec and the effective destination: the URL Git pushes to after the user's rewrites (the longest matching `url.*.pushInsteadOf`, else `insteadOf` through `git ls-remote --get-url`), which the approval shows as `Pushes to:`. At dispatch both are resolved again; a changed source or destination dispatches nothing. There is no force, deletion, follow-tags or recursive submodule push. PR creation pins `host/owner/repository`, base, head, title, body and draft. Its local head OID detects local drift before dispatch but does not bind the remote PR commit: the approval says the PR uses the remote head branch at creation and never shows the local OID as its source. Push and PR creation need separate one-use approvals showing the whole normalized destination and payload; PR body lines are escaped and indented beneath `Body:` so they cannot impersonate approval fields. Rule precedence stays deny > ask > allow; without a typed allow, a push or PR asks a human in default and acceptEdits and in Auto unless its destination is the pinned repository, and plan and dontAsk deny. Missing, dropped, denied or cancelled approval dispatches nothing. ACP's channel without human-only attestation refuses; a human-capable serve channel may approve. Write prompts offer once/deny only. A committed `ToolStarted` verdict with source `human` precedes launch; replay rejects an AI approval of a host write outside Auto or to any destination other than the Run's pinned repository, and any Guard or unguarded receipt for that intent.

**Execution and credentials.** Push runs `git push --porcelain --no-follow-tags --recurse-submodules=no -- URL REFSPEC` in the Workspace repository after [configuration admission](#typed-git-reads), with the cage but network allowed, so the user's credential helpers, SSH agent and `core.sshCommand` apply as in a terminal. gh runs from its pinned path in the Workspace with the user's own gh configuration (`GH_CONFIG_DIR`, `GH_HOST` and `XDG_CONFIG_HOME` pass through) and `GH_PROMPT_DISABLED`, `GH_PAGER=cat` and `GH_NO_UPDATE_NOTIFIER` set; it receives fixed arguments and an explicit repository, so it cannot implicitly push, fork, paginate or select another repository. Arany never reads, copies or re-injects credentials, and credential values never appear in intents, catalog, Provider context, journal, diagnostics or result text. User credential helpers are user-authorized host code. Only the Git and gh binaries are hash-pinned: `ssh`, `git-remote-https`, their libraries and user-selected helpers are trusted host components.

**Bounds and outcomes.** The Host Git row in [Limits and failure behavior](./limits-and-failures.md#limits-and-failure-behavior) defines payload and runtime bounds; stdout and stderr use the Typed Git reads capture caps there, and overflow terminates the process group. Malformed or control-bearing write data refuses (body newlines are allowed). One Git write is in flight per Workspace. After approval, one monotonic deadline covers preparation and execution; a preparation timeout refuses before dispatch, and the cleanup allowance is separate. Human waiting follows the [shared approval contract](./trust-and-approvals.md#folder-trust-and-approvals), consumes neither Goal active time nor the host runtime allowance, and cannot invalidate the approved intent. Cancellation and the deadline are rechecked immediately before spawn. Raw process output is always discarded, to prevent credential disclosure. Outcomes:

- A confirmed zero exit with confirmed group teardown records a host receipt and fixed completion text.
- A confirmed exit 1 with exactly one Git porcelain rejection for the pinned refspec, `(non-fast-forward)` or `(fetch first)`, is Failed with fixed “remote reported no ref update” text. This does not mean nothing was uploaded: HTTPS can upload a pack before rejection.
- For PR listing or inspection, a confirmed nonzero exit, invalid JSON or capture overflow is Failed with fixed bounded text.
- Timeout, cancellation after launch, lost acknowledgement or unconfirmed teardown is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes). So are write authentication errors and gh's PR-already-exists diagnostics, which do not prove the absence of a remote effect.
- A crash after the committed approval without an outcome stays unresolved on replay.

Rewind marks host effects with a receipt, an Uncertain outcome or an approval without outcome as non-rewindable; nothing undoes, completes or rolls back a push or PR.

Host execution has no Guard filesystem, network, CPU, memory or process-count isolation, remote transfer or storage bound, DNS isolation, or containment of descendants escaping the process group; human approval and time/output bounds are its controls.

## Typed Git writes

Typed Git writes let the primary commit, create branches and switch, with the [typed Git read](#typed-git-reads) runner, cage and configuration admission. [Human-approved host Git](#human-approved-host-git) owns push and PR creation; [typed prefix rules](#typed-prefix-rules) remember approval for the three local verbs.

1. **Availability.** Writes need the Run's Git pin, the whole-Workspace grant and `write: true`. Otherwise only reads are listed, with a `git_branch` schema fixing `name` and `start_point` to null, so plan mode can still list branches. Writes are primary-only, never offered to researchers or editors, never Goal success criteria, and admitted by a plan contract only with `.` scope.
2. **Operations.** `git_commit {message, paths, staged}` commits to the current local branch either distinct literal Workspace-relative `paths` (`.` for every change), staged with `git add --all` and committed with Git's `--only` semantics while protected components stay uncommitted; or, with `staged: true` and empty `paths`, the index exactly as staged. The message is non-blank UTF-8 with no controls except newline and tab. `git_branch` with `name: null` is the [branch discovery read](#branch-discovery); creation requires `scope`, `base` and `max_count` null and runs `git branch --no-track` at `start_point` (HEAD when null). `git_switch {branch}` runs `git switch --no-guess` to an existing local branch; the current branch returns `switched: false` without running Git. There is no amend, force, delete, detach, merge, remote or raw-argument escape. The user's configuration applies: identity, signing, LFS filters and, only when accepted, hooks. Without an identity, Git's own error is a Failed result.
3. **Refusals.** A commit needs HEAD on a local branch, and a switch refuses from a detached HEAD, whose commits could become unreachable. Everything else is Git's own decision: switching over local changes or untracked files, empty commits, unmerged entries and merges or rebases in progress fail as they do in a terminal.
4. **Results and receipts.** A commit returns `{"commit","branch"}`, a creation `{"branch","oid"}` and a switch `{"branch","switched"}`. Failures return `{"failed"}` with filtered diagnostics. The `Git` receipt records HEAD and the target ref before and after the operation, read through Git, and the operation's exit status. A write that ran with hooks off while the folder has hooks adds `hooks_not_run`, telling the user to accept them in `/permissions`.
5. **Outcomes and locks.** One Git write is in flight per Workspace. A Git process that is killed, times out or is cancelled mid-write is [Uncertain](../execution/events-and-outcomes.md#effect-outcomes); reopen and replay neither complete nor roll it back. The Uncertain observation leads with the typed `StaleGitLocks` report when `.git` holds `*.lock` files (at the top level or under `refs`, at most 4,096 entries<!-- unrelated-bound: stale Git lock scan --> scanned), naming them and saying to remove them once no git process runs; Arany never deletes them. Goal resume repeats the report before refusing to resume past the unsettled write. [Rewind](./changesets-and-checkpoints.md#checkpoints-and-rewind) does not undo Git writes.
6. **Policy.** Writes run on the host outside the sandbox: Request and Auto edits ask a human, Auto approval reviews them and `plan` denies them. A matching ordinary (`git_commit`, `git_branch`, `git_switch`) or typed allow rule pre-approves them in every mode but `plan` and is required in `dontAsk`, and the [typed-allow mode mapping](./permissions.md#modes-and-approval-decisions) owns the rest. With accepted hooks the [hooks rule](#git-hooks) narrows this further. Commit paths, including `.` and ancestors, cannot bypass restrictive rules on their descendants. The [limits table](./limits-and-failures.md#limits-and-failure-behavior) owns every bound; a result budget below its minimum records `Limit` before any effect.

### Git hooks

Repository hooks run only when the user accepts them for the folder.

- **Detection** finds the active hooks directory the way Git does: the user's `core.hooksPath` (husky, lefthook), else `.git/hooks`. Hooks are its regular executable files named after Git hooks, `*.sample` excluded; the pre-commit framework's generated hooks are labeled as such. A digest covers every regular file in that directory (at most 64 files of at most 1 MiB<!-- unrelated-bound: Git hook file bytes -->), so helpers such as husky's `h` are pinned too.
- **Asking.** The attached terminal asks after folder trust whenever hooks exist and no saved answer covers exactly this digest, so a new or edited hook asks again; `/permissions` → Git hooks asks at any time. The answer is saved, digest included, in the folder's trust entry (`git_hooks`). The warning says that hooks run on the host with the user's authority, outside the sandbox, and that they often call other model-editable files (package scripts, lint or pre-commit configuration), so pinning the hook files protects only partly.
- **No** keeps `core.hooksPath=/dev/null` for Arany's own invocations only; the user's configuration and terminal Git are untouched.
- **Yes** pins the digest per Run in `RunStarted.config.tool_policy.git.hooks`. Each write detects the hooks again and runs them only while they match; a changed hook does not run, and the result says to accept the hooks again. A write that runs hooks gets the command runtime ceiling instead of the Git runtime bound. Internal worktree operations never run hooks.
- **Approval.** While hooks are accepted, a Git write to the trusted folder's repository is approved by a human approval at that moment, an admitted user-owned allow rule or, in Auto approval, the AI review, which judges the write and therefore the hooks it runs; replay rejects any other approval source. With no human reachable (`exec`, serve without an approval channel), the catalog offers only the write verbs a user-owned allow rule covers, keeps branch creation read-only otherwise, and adds `Commits, branch creation and switches are left to the user; leave changes in the working tree`.
- **Terminal-only consent.** Only the attached terminal asks. `exec`, serve and ACP use the answer saved for a trusted folder, also for configured Runs; with none, hooks stay off and the write result carries the notice. ACP never asks through `session/request_permission`, because a client may answer by policy and ACP client policy never authorizes host execution.

# Provider

## Scope and related contracts

This contract owns Provider selection and pinning, native and custom admission, outcome and Tool encoding, egress, usage provenance and provisional display. Accepted outcomes and deadlines belong to the [execution contract](./execution.md#accepted-outcomes), saved-account storage to the [credential contract](./credentials.md), ChatGPT-plan OAuth and its output bound to the [ChatGPT contract](./chatgpt.md), and plan contracts to the [goals contract](./goals.md#initial-plan-contract-and-success-receipt). The ChatGPT-plan trade-off is recorded in [D-18](../research/next-step-decision-register.md#d-18--explicitly-accepted-chatgpt-plan-route-is-beta-scope). Editing constraints: [security rules](../../agents/security.md).

- Each role has an explicitly selected profile, model, reasoning profile, privacy profile, outcome encoding and call limits pinned before Workspace input and `RunStarted`, including every configured fallback. A Session changes its defaults only between Runs. Unconfigured roles inherit the primary route; [role routing](#per-role-selection-and-fallback) defines the bounded chains and journal representation.
- Provider is the substitutable semantic inference interface. Requests and responses carry Arany semantics, never wire objects or a generic parameter bag.
- A primary Goal call may carry a bounded typed `GoalContextFacts` projection. It is context, not a grant or budget override; children never receive it.
- `Provider::compact` is a separate semantic call, not a synthetic AgentRun. It receives bounded accepted outcomes and an optional prior summary, never Workspace instructions or includes. API-key and custom routes enforce the output cap remotely; the ChatGPT-plan route records a local-only cap. The summary is untrusted data, portable only with its provenance.
- Rollout is staged: native OpenAI and Anthropic first; exact custom profiles after data-free conformance; OpenRouter stays deferred behind its route and privacy gate; Z.AI stays unadmitted until an exact profile passes a strict outcome contract.
- Selection is deterministic from admitted user configuration. There is no model-selected destination, hidden discovery call or preliminary model check inside a Run. Fallback is disabled unless explicitly configured as described below.

The primary Delegate envelope accepts optional nullable `agent`, selecting one admitted researcher definition for its `children` objectives. A child object keeps required `objective` and nullable `profile`; an editor additionally carries the closed `editor` assignment from the [worker protocol](./execution.md#worker-journal-protocol), repeats its mission as `objective`, and requires null `profile`. Its definition/digest come from the admitted catalog. The editor envelope requires `commands`: a sorted array of zero to eight unique admitted command names, each at most 64 bytes; missing, duplicate, unknown or extra names refuse admission. Both native function encodings share this envelope. The schema offers editor assignments whenever an admitted editor definition exists, so it stays constant within a Run; the Engine refuses an editor Delegate before a committed Goal plan, failing the Run before any capture or child call. Assignments offer foreground/background mode, bounded wave numbers and nullable current-Run supersession; nullable `resumes` accepts an exact historical child ID under the [fresh-assignment semantics](./session.md#worker-identity-and-explicit-reassignment). Editor calls use a compiled private-view prompt, Single policy and the restricted catalog, with text answers and no Delegate. [Execution](./execution.md#agent-definitions) owns its strict selection and authority intersection. Definition bodies stay in labelled untrusted user guidance; no new system role or Provider destination is introduced.

## Per-role selection and fallback

`Providers { primary, child, review, compaction }` binds primary planning/synthesis, researcher or reasoning children, AI Tool review and summary calls. A child receives the same narrowing of instructions, Tools, authority and Goal facts regardless of its Provider. Each route retains its own immutable identity, account or custom conformance provenance, effort, output-token bound and call limits. Pinned role deadlines are positive and at most 20 minutes; compiled routes retain their narrower limits. The role-specific output caps still apply, and concurrent children fit both the primary and every admitted child route's concurrency ceiling.

Peer mapping: [OpenCode's per-agent `model`](https://opencode.ai/docs/agents/#model) supplies model overrides and primary inheritance. [Claude Code, “Fallback model chains”](https://code.claude.com/docs/en/model-config#fallback-model-chains) supplies ordered server-availability fallback, a visible switch, actor-local continuation for this turn and a three-model ceiling. Authentication, billing, rate-limit, request-size and transport errors never switch. Arany admits and pins all destinations before disclosure, journals switches before dispatch, and rejects duplicates, oversized chains and unadmittable entries instead of silently removing them. These durability and exact-admission constraints are the R3-7 divergence. Content refusals never select another model.

Both `exec` and attached Run/compaction admission read only the optional private StateRoot record `provider-routing.json`, at most 16 KiB. Version 1 is a closed object with a required `providers` object containing all four role names. Each value is null or an ordered array of one initial route and at most two fallbacks. Each route has exactly `provider`, `model`, `effort` and `account_id`; the nullable fields are explicit. Provider/model names use existing exact selection rules. Native effort resolves through the ordinary model defaults; ChatGPT requires explicit effort and the selected account UUID. Unknown fields or versions, empty or oversized chains, duplicate admitted identities and malformed selections refuse admission. No Workspace file, instruction or model output selects these values.

```json
{
  "version": 1,
  "providers": {
    "primary": null,
    "child": [
      {"provider": "anthropic", "model": "claude-sonnet-5", "effort": "high", "account_id": null}
    ],
    "review": null,
    "compaction": null
  }
}
```

The primary remains the CLI/Session selection. A non-null primary chain must begin with that exact resolved selection; later entries are its fallbacks. A null role inherits the entire pinned primary chain. An absent record means one primary route and no fallback for every role. Every configured entry is admitted through the existing native credential/account, ChatGPT consent or exact-custom destination/conformance gate before Workspace input, including routes that will not be called. An admission failure names the configured profile/model and refuses the Run; it never selects another entry. Exact-custom primary/child routes remain incompatible with a Tool-enabled Run. Review and compaction receive no Tools or images and retain their ordinary strict-text conformance; custom primary/child routes refuse image-bearing objectives.

Fallback walks the pinned chain only when the HTTP status check rejects a response with 5xx (including 529), before body admission, and only after the call's [same-route retries](#usage-provenance-and-reliability) are spent or cannot fit. Native and custom adapters emit a typed pre-admission server failure at that check; ChatGPT keeps its numeric 5xx status and bounded `Retry-After` in a typed remote server failure. Native/custom call records preserve their existing unavailable disposition and failure-reason bytes. A send-time transport failure, any error after a successful status check (including stream overload, hidden reasoning, Tool-input JSON, pre-answer JSON or a body-read failure), local request rejection, content refusal, semantic/stream validation error, output limit, cancellation or deadline never switches. Visible preview text is an additional guard, not the admission-stage test. Only the attached primary exposes previews.

Before any switch fact or replacement charge, requests carrying Tool steps or opaque assistant turns must retain the same adapter and account. OpenAI API keys and ChatGPT subscriptions are different accounts even though their opaque turns use the same adapter tag. Tool-enabled Run admission refuses any primary or child chain mixing adapters or accounts, before dispatch; role overrides themselves may use different adapters. The replacement retains the entire semantic request and correlated observations without translation or truncation. It neither re-dispatches a Tool nor continues an uncertain effect. A successful fallback remains selected for that actor and role for this Run; each new Run starts at chain[0].

Claude Code excludes compaction fallbacks with smaller context windows. The only admitted window metadata is the ChatGPT catalog `context_window`, saved with the exact model check; it sizes the primary [context ceiling](./session.md#context-and-compaction) from the smallest window across the primary chain and never selects or filters a route. Arany sends the same complete, bounded compaction source to each configured destination, never truncates it to fit and never launches another compaction to make fallback possible. A target's request-size rejection ends that call without a switch. This explicit rule diverges from Claude Code's window-based filtering; selecting a compaction chain does not certify equal window sizes.

Each switch fits the existing action deadline and fresh Store/call-budget admission. Per-attempt adapter deadlines and output caps can only narrow it. The [execution contract](./execution.md#admission-persistence-and-recovery) owns switch facts and replay, and [Goals](./goals.md#lifecycle-budgets-and-recovery) owns charging unknown failed-call usage. A Run retains at most 64 switch facts; reaching the bound, or a refused Event or storage admission for the switch, stops fallback and records the call's failure. When the latest Run has explicit role provenance, Session compaction requires its admitted chain to match that Run's pinned compaction identities; it cannot introduce a new destination after the Run. Runs with the canonical inherited representation retain ordinary single-route between-Run compaction selection, and cannot introduce a fallback chain after the Run.

## Named roster presets

Decision O1 (product): item 9 covers named presets and eligible assignment selection only. Exhausted routes retain failed-child, sibling-drain and failed-Run behavior. Judge-only adapters and durable per-agent pause/retry/switch remain separate proposed D work; writable workers and leases remain outside this contract.

Decision O2 (product): `--profile PRESET` explicitly selects a private preset in attached mode or `exec`. There is no implicit preset, persistent preset default or new picker. Supplied Provider, model and effort flags must individually match its normalized primary tuple. A selected roster conflicts with any present `provider-routing.json`; choose one routing source. Without the flag the roster record is never opened and ordinary selection remains available.

The user maintains read-only-to-the-harness `provider-roster.json` beneath the admitted StateRoot outside the Workspace. Version 1 is a closed object with required `version`, `profiles` and `presets`. Each profile has exactly `name` and `routes`; routes use the exact four-field [role-route form](#per-role-selection-and-fallback). Each preset has exactly `name`, `providers` and `child_profiles`. Its four required Provider-role fields contain profile names, with explicit null permitted for child, review and compaction to inherit the entire primary chain. Primary is required and non-null. The nonempty, ordered child allowlist must include the resolved child default. Unknown or duplicate object fields, duplicate names/routes/eligibility, missing references, malformed values and unsupported versions reject the whole record. Native efforts normalize before duplicate detection or selection comparison.

Decision O3 (Provider/security): the primary selects only eligible names in the pinned preset for each direct child assignment. `Delegate.children` contains closed objects with required `objective` and required nullable `profile`; strings, missing fields and additional fields reject. Null selects the pinned child default, which may inherit the primary chain. Outside roster mode only null is legal. No raw model/account/endpoint, another preset, fifth role or judge capability is introduced.

```json
{"outcome":{"type":"delegate","children":[{"objective":"Inspect replay invariants","profile":"inspect"},{"objective":"Check output bounds","profile":null}],"agent":null}}
```

`RunInput.assignment_profiles` carries the eligible names for primary planning and synthesis, and is empty for children, review and compaction. Both structured text and native functions use the same assignment schema: its profile enum is the frozen eligible names plus null. Primary native function schemas stay fixed through the Run while phase restrictions still apply. Compiled guidance explains null/default selection. Validate the entire delegation before its first spawn; an unknown, ineligible, malformed or over-bound final assignment fails the plan with zero child dispatch and no repair call. Never infer a profile from objective text.

Each child binds the resolved profile through acknowledged `AgentSpawned` before reservation or dispatch. Calls and switches look up role plus actor and that immutable reference, even when two profiles share an initial identity and differ only in fallbacks. Successful fallback stays with that actor/role; a sibling starts at index zero. Review and compaction retain their fixed role chains. Assignment selection cannot alter definitions, instructions, authority, Tools, budgets, privacy requirements or destinations beyond those already admitted. Existing HTTP-status-only fallback predicates and fail-and-drain recovery remain unchanged.

Roster account selection follows [decision O4](./credentials.md#account-scope-and-identity), retaining current selected-account loaders and refusal of unsupported unused identities. Roster primary selection uses ordinary exact `select_provider` admission; ordinary headless native selection keeps its environment-only behavior. A manifest supplies neither credential authority nor account/plan consent.

Before credentials or Workspace-content loading, show a complete escaped manifest: preset, four role references, eligible children, every initial/fallback model and effort, and billing class (`native API`, `ChatGPT plan`, or `exact custom; unknown pricing`). ChatGPT rows disclose that the local output cap does not cap remote plan consumption. Headless manifests go only to stderr, including JSONL mode; attached submissions use existing safe notices. An unrepresentable complete manifest rejects instead of hiding routes.

Structurally validate the entire bounded record, then resolve only profiles reachable from the selected preset. Admit them in profile-name order and chain order, sequentially under one cancellable 120-second deadline; identical normalized selections share admitted adapters. Admit every eligible alternative and fallback even when unused. No inference, discovery, recheck, retry queue or billing fallback occurs. Existing credential, consent, exact-custom evidence and destination checks remain mandatory. Both entry paths complete startup roster admission before opening writable history or the Engine; attached startup does so after folder consent. Failure names the safe profile/route and refuses before journal creation, Workspace input or a Run; pre-existing Session/default facts need not be rolled back. Cancellation drops remaining admission and starts no Run; existing account-write uncertainty remains authoritative.

All agent candidates, including unused eligible profiles, obey image and native Tool capability checks. A Tool-enabled chain retains one adapter/account; role overrides may differ. Review and compaction stay Tool/image-free. Eligibility never changes the parent grant, child read-only/Single policy, instructions or shared Goal ledger. Admission pins an immutable semantic snapshot for all autonomous Runs of one submission; independent submissions re-read and re-admit, and process selection survives new/clear. A conflicting idle selection is refused at next-Run admission with guidance to use the preset tuple or invoke without the selector.

## Native models and accounts

- Effort is model-specific, resolved before Workspace input, sent explicitly on every Run and compaction request, and pinned in `RunStarted`. An omitted next-Run choice resolves to the reviewed model default. An unreviewed model needs an explicit closed effort and claims no compatibility. Malformed IDs and unsupported reviewed combinations fail before credential or Workspace input.
- A native credential is one immutable value: Provider, bounded key and optional Anthropic API workspace. Only an environment-backed Anthropic selection reads `ANTHROPIC_WORKSPACE_ID`; other Providers and key-only accounts never inherit it. A `wrkspc_` identifier is validated before requests, sent on every catalog, Run, compaction and conformance request, and bound to native evidence. Neither a workspace header nor catalog visibility grants another destination, capability or plan permission.
- `exec` and explicit native selections use only their named API-key environment variable. Bare attached mode can use one saved API account chosen through `/setup` or `--setup`; with none it stays unconfigured and rejects objectives locally before Workspace input. A Session's saved default pins the account UUID; Run and catalog admission must match that UUID and Provider before the key is released, so a replaced account never becomes an older Session's credential. Native adapters carry the UUID into `RunStarted`; environment-backed and custom adapters carry none.
- ChatGPT-plan OAuth is a separate consented route that never falls back to API-key billing. Anthropic remains API-key only unless Anthropic grants Arany prior approval.
- The OpenAI Responses adapter admits exactly `gpt-5.4`, `gpt-5.6-luna`, `gpt-6-astra`, `gpt-6.1-sol` and `gpt-6-luna` with `OPENAI_API_KEY`, sending the resolved value as `reasoning.effort`. Effort sets come from the model pages for [GPT-5.4](https://developers.openai.com/api/docs/models/gpt-5.4), [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol) and [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna). Astra defaults to `medium`; the others match their pages.
- The Anthropic Messages adapter admits exactly `claude-sonnet-5`, `claude-fable-5-1`, `claude-opus-5-5` and `claude-sonnet-5-5` with `ANTHROPIC_API_KEY`, sending the resolved value as `output_config.effort` per the [effort guide](https://platform.claude.com/docs/en/build-with-claude/effort). Opus 5.5 defaults to `medium`; the others to `high`. Requests use the compiled `/v1/messages` route with `anthropic-version: 2023-06-01`.
- Offline fixtures establish neither live support nor an account-level zero-data-retention claim.
- Attached native choices need no synthetic check; each Run still validates credential identity, workspace, bounded model and effort, and the strict actual response. Native setup selects a low-effort default from the account's catalog without model, effort or cost questions, preferring visible `gpt-5.6-luna` for OpenAI or `claude-sonnet-5-5` then `claude-sonnet-5` for Anthropic, otherwise the first visible row with unknown pricing disclosed. This is an economical preference, not a compatibility claim. `/model` selects model and effort atomically; selecting is staging, never credential or compatibility authority.

An explicit unknown effort is admitted without a compatibility claim and runs one call at a time.

## Structured outcomes and Tool encoding

- Run answers are plain assistant text, matching Codex CLI and Claude Code. One completed function call is the step's outcome; earlier assistant text is progress commentary. Without a function call, the final assistant message is the answer and ends the turn. There is no Finish function or model-authored summary/result split. Multiple, unknown or incomplete calls, malformed text parts and invalid typed arguments reject without repair or an alternate encoding. The Engine retains the [refusal and completion rules](./execution.md#accepted-outcomes).
- OpenAI API requests offer a constant list of strict native functions for catalog-available operations, the optional primary `arany_plan`, and `arany_delegate` when collaboration permits children. Each call restricts the list by phase with `tool_choice: {"type":"allowed_tools","mode":"auto","tools":[{"type":"function","name":"arany_…"}]}`. ChatGPT uses its phase-dependent list with `tool_choice: "auto"`; [P3](../../NEXT_STEPS.md#message-native-provider-request-owner-run-live-probes) concerns only the constant-list cache optimization. Both disable parallel Tool calls. This single-call divergence preserves one journaled outcome per step. Local decoding admits only the offered subset. Read-only routes offer only phase-allowed delegation.
- Native and custom Anthropic Messages Runs offer non-strict catalog Tools and phase-allowed Delegate, with `tool_choice: {"type":"auto","disable_parallel_tool_use":true}` and no `output_config.format`. A `tool_use` stop carries exactly one offered call, with earlier text as commentary; `end_turn` carries the plain text answer and no call. `max_tokens`, `refusal` and every other stop reason fail closed. A replayed Delegate `tool_use` is followed by a fixed `tool_result` before the child results, as on the OpenAI routes. A request with no offered function omits `tools`, `tool_choice` and `parallel_tool_calls` on every route. Compaction and Tool review retain strict structured JSON encodings; review returns the closed verdict object (`verdict: approve | ask`), decoded as a typed verdict, never as answer text.
- Researchers receive only read-only operations, without planning or delegation. At zero remaining Tool calls every route retains its Tool list, sends Tool choice `none` and accepts text only. The Engine independently refuses exhausted calls. Anthropic retains Tool and system cache markers, omitting the tail marker; changing Tool choice may invalidate the messages cache. Exact custom profiles continue to reject Tool context before HTTP.
- Ordinary non-autonomous turns without a recorded plan omit the `goal` budget block. Autonomous Goals and recorded plans carry their bounded budget context. Engine enforcement never depends on prompt visibility. A recorded plan remains binding scope and success policy, unlike advisory peer plans; [Goals](./goals.md#initial-plan-contract-and-success-receipt) owns that divergence.
- Typed Run input renders as closed system text, labelled untrusted user data, and each Tool step as the exact replayed assistant turn followed by correlated results that do not repeat the call. Responses replays raw output items, including encrypted reasoning with `store: false`; the ChatGPT route also drops item IDs. Replayed turns are in-memory and never journaled; a lost Run is interrupted, not resumed.
- Generated Tool branches and command, Skill and MCP names are restricted to bounded catalog availability. Catalog data never replaces pinned router or Guard authorization.

Anthropic thinking blocks are opaque: they replay unchanged within a Run, are never interpreted, and are dropped from kept turns when compaction rewrites history.

An opaque in-memory assistant turn is bounded to eight bytes per requested output token plus 64 KiB of framing and ciphertext overhead, capped at the 1 MiB response ceiling; exceeding this bound fails the call with `InvalidOutcome`.

## Prompt caching

- Anthropic follows the peer explicit-breakpoint layout for active Tool loops: `cache_control: {"type":"ephemeral"}` on the last Tool definition, the last system text block, and the final content block of the conversation tail. Single-call requests without Tools and compaction requests mark only the system block; their changing data tails are not reused, so a tail breakpoint would pay the 1.25× cache-write charge without a subsequent read. A spent researcher's final call retains Tool and system markers but omits the tail marker. Markers are added to the outgoing request, never stored in replayed turns or accumulated over previous messages. This uses at most three of Anthropic's [four documented breakpoints](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); the default five-minute TTL applies. No top-level automatic cache marker or extended TTL is requested.
- OpenAI API and ChatGPT Run and compaction calls all send the Session UUID as a stable `prompt_cache_key`, matching Codex CLI's conversation-ID key. The UUIDv7 carries a creation timestamp and lets the Provider link the turns of one Session, as with the peer. It adds no prompt, Workspace or credential text to the key. Calls keep `store: false` and existing encrypted-reasoning replay. Only the OpenAI API route uses the constant function list and `allowed_tools`; ChatGPT uses auto selection with a phase-dependent list, accepting one synthesis-switch cache miss; P3 measures constant-list compatibility only. No retention override is requested. Exact custom Responses profiles share the API request shape and require current conformance evidence.
- A cache key or breakpoint requests reuse; it guarantees neither a cache hit nor remote retention or live compatibility. Actual cache-read counts flow through the [usage record](#usage-provenance-and-reliability) into the [Goal report](./goals.md#lifecycle-budgets-and-recovery). Anthropic remains offline-tested, unvalidated live until [probe P1](../../NEXT_STEPS.md#message-native-provider-request-owner-run-live-probes).

Changing the decoder, prompts, request encoding, effort mapping, output cap or validation semantics bumps the native and exact-custom check contract versions in the same change; a package version alone does not.

Native adapters validate attachment count, aggregate bytes and objective or history origin before building a request body or egress.

ChildWork requests may contain only notes recorded for that exact child, rendered as ordinary user data at their actual continuation boundary with the shared `steering_notes` block. ReadOnly, Researcher and Editor work roles admit them; ToolReview and invalid role/phase combinations reject them, including nested Tool-step and stop-feedback notes. Earlier request prefixes remain unchanged on later continuations and route/retry attempts. Primary notes do not enter child requests. Guidance cannot widen the child's grant, catalog, lease, plan or budget; [Goals](./goals.md#steering-notes-and-pause) owns admission and delivery semantics.

## Configuration and egress

- An explicit CLI profile and model override trusted Session or user-configuration defaults. There is no compiled model default, Workspace-defined profile or implicit discovery.
- A Provider receives only the current objective, selected bounded Session context, instruction and include snapshots, and the Engine-produced child results the phase requires. Only credentials of the explicitly configured role routes and fallbacks are read. Credentials never enter CLI arguments, Events, output, fixtures, telemetry or error bodies. Attached `/model` follows the [terminal contract](./terminal.md#interactive-commands-and-completion).
- Every Provider HTTP client requests identity encoding, rejects any non-identity `Content-Encoding` before reading the body, and bounds declared and accumulated bytes to 1 MiB per response. Compressed Provider replies are unsupported.
- HTTPS is required outside numeric loopback. Destinations are pinned, with no redirects or ambient proxies; route or model drift, changed addresses, metadata, link-local and multicast destinations, and credential reflection reject. Receipts say `custom verified` and never relabel a service as native OpenAI or Anthropic.
- Operating-system TLS trust uses Reqwest's platform verifier with chain and server-name checks intact. Certificate and revocation connections the operating system makes during trust evaluation are not Provider destinations and never carry content, files or credentials.
- Each adapter owns authentication, request encoding, error mapping, usage, privacy and parsing. Endpoint authorization is not content authorization: omitted-input canaries prove withheld data never reaches a payload.

Provider HTTP clients follow no redirects, use no ambient proxy or cookies, and disable automatic protocol retries. Any future network grant must bind the typed operation, audience, method, destination, redirect policy, payload schema, data class and limits. A destination allowlist never authorizes arbitrary upload or proves data-loss prevention.

## Custom destinations and routing

Decision: reuse one Messages adapter with an explicit base URL and selected key, following [Pi at its reviewed commit](https://github.com/earendil-works/pi/blob/cae9fd28a2d3d515c83ea495093e3768cc8efab6/packages/ai/src/api/anthropic-messages.ts#L1104-L1108). Arany adds admission before disclosure, durable custom provenance and exact strict compaction conformance to preserve its guarantees. A vendor compatibility label cannot replace those checks.

- Native endpoints come from compiled, reviewed profiles. A custom profile lives in trusted user configuration outside the Workspace and names a closed protocol family, exact endpoint and base path, exact model, credential reference, outcome encoding and capability-evidence version. It never accepts arbitrary headers, shell credential commands, redirects, ambient proxies or cross-profile credential reuse.
- The loader reads only `provider-profiles.json` from the private state root, through the [record migration](./execution.md#json-record-migration). The closed version-2 document has at most 32 uniquely named profiles. A Responses entry requires `protocol: openai-responses`, an exact canonical `/responses` `endpoint` and `outcome_encoding: json_schema`; it rejects `base_url` and `auth`. A Messages entry requires `protocol: anthropic-messages`, a canonical `base_url`, `outcome_encoding: native_tools` and `auth: bearer | x-api-key`; it rejects `endpoint` and arbitrary headers. Unknown and duplicate fields refuse. The registered version-1 migration changes only the document version for valid existing Responses profiles; it cannot authorize a version-1 Messages entry.
- Both variants require an exact bounded model ID, an `ARANY_PROVIDER_*` credential reference, `privacy: user_authorized`, `max_output_tokens: 4096`, `capability_evidence_version: 2` and a canonically ordered unique `efforts` list from `none|low|medium|high|xhigh|max`. An empty list sends no effort field, including no native Claude default. Explicit Messages efforts map directly to `output_config.effort` and must pass their individual probes. Custom profiles never use the native model resolver.
- For Messages, validate the base before removing at most one terminal slash, then append `/v1/messages` without discarding a nonempty base path. Base and derived URL each have a 512-byte limit and 256-byte path limit. Reject already-suffixed Messages bases, credentials, queries, fragments, percent encoding, dot segments, doubled path slashes and noncanonical hosts or ports. Numeric loopback may use HTTP or HTTPS; domains require HTTPS and admitted public DNS. A credential reference cannot span origins.
- Messages requests send exactly the selected Bearer or `x-api-key` credential, `anthropic-version: 2023-06-01`, JSON content type, identity encoding and the compiled `User-Agent: arany/<version>`. Responses retains Bearer authentication and the same honest User-Agent. Native environment/saved keys and Anthropic workspace scope are never read or forwarded. The shared Messages adapter preserves opaque thinking/signatures and paired delegation results, and locally rejects multiple calls even if a vendor ignores parallel-call suppression. It sends no thinking budget. Workspace Tool context and images remain refused before HTTP.
- `arany provider check custom:NAME --state-dir STATE` (also accepting bare `NAME`) can incur charges. It clears prior evidence, runs streaming direct-answer and one-child probes, strict compaction and, for each declared effort, a streaming answer plus strict compaction, without Workspace input, retries or alternate encodings. Compaction probes constrain the summary to a fresh 128-bit random nonce in the JSON schema only, absent from every prompt, and require the decoded summary to match it exactly. Ignoring the schema and returning plausible summary JSON fails. The check makes at most 15 calls within one 180-second aggregate deadline, and evidence lasts 24 hours. Its fingerprint binds package/contract/document versions, name, protocol, normalized base (empty for Responses), derived endpoint, model, credential reference, encoding, auth, privacy, cap and efforts; DNS addresses are compared separately. Earlier check contracts cannot authorize either protocol. A failed compaction schema probe leaves no admission; JSON repair, tool-selection substitutes and skipped compaction are forbidden. See the [setup recipe](../setup.md#anthropic-compatible-custom-routes); Kimi platform is conditional on its exact check; Kimi Code remains explicitly unavailable pending endpoint-specific strict-compaction evidence, as do DeepSeek candidates. GLM Standard-key candidates also remain unavailable pending Messages-specific provider-enforced schema evidence; Compatible and Coding Plan keys are excluded from that recipe.
- Profile documents keep the [record byte bound](./execution.md#persistence-bounds), 65,536 JSON nodes and depth 32. Names and credential references are at most 64 bytes, model IDs 128 and keys 512. Custom DNS admits at most eight addresses within five seconds; connection time is at most ten seconds and each call 120 seconds, including vendor queues. Requests are at most 512 KiB; replies follow the [Provider HTTP client bound](#configuration-and-egress) and SSE the [shared framing limits](#streaming-and-provisional-text), plus at most 16 Messages content blocks. Compaction output is capped at 1,024 tokens. Overflow or invalid required usage rejects without partial acceptance; absent optional cache counters stay unknown.
- `CustomProvider::admit` re-reads the exact profile, re-resolves every address, compares fresh evidence and only then reads the selected key; `custom:NAME` Runs use it before Workspace input, and `RunStarted` pins the exact admitted endpoint and evidence fingerprint. The Engine rejects a `custom:` Provider without that provenance before Workspace input; replay treats it as historical evidence, never fresh authorization. Custom calls require positive labelled usage within the cap; their unproven concurrency ceiling is one.
- Domain DNS answers admit IPv6 only from reviewed allocated ranges; unallocated and reserved ranges fail closed. The allowlist is refreshed against the [IANA global-unicast allocations](https://www.iana.org/assignments/ipv6-unicast-address-assignments) and the [special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry) when a range is needed. Numeric loopback is a separate explicit exception.
- A future built-in OpenRouter profile is a broker: it pins one reviewed upstream endpoint, requires parameter support, disables fallback, denies data collection, requires ZDR, disables response caching, and records broker and upstream provenance.

Check evidence is an HMAC: it authenticates evidence but does not encrypt history or process memory. Checked library constructors require exact evidence and pin concurrency at one; ordinary constructors and product Runs do not. The declared effort list is part of the evidence fingerprint, and a change to the compiled strict contract invalidates old evidence independently of the configuration version.

## Usage, provenance and reliability

- A failure before a decoded outcome retries the same route, in every role including manual, automatic and in-Run compaction, single-route or chained: a send that fails before any response (the request may already have been delivered), HTTP 429, HTTP 5xx at status admission, or a body or stream that ends early (including a ChatGPT stream cut at its [idle window or call ceiling](./chatgpt.md#run-limits)). A semantic call has at most three retries across all its routes, with gaps of 2, 4 and 8 s (exponential from 2 s, at most 10 s each) or a longer delta-seconds `Retry-After` on a 429 or 5xx. Each wait must end before the remaining action deadline, which already lies inside the Goal's active time; a `Retry-After` that cannot fit is never waited out, so the call fails at once (a 5xx can still switch). A send timeout, cancellation, other 4xx, malformed stream or body, contract and content failures, and a primary call with committed display text never retry. A clean end is a cut only after at least one well-formed event. A 429 records the closed `rate_limited` reason. Only a bounded 429 body (at most 16 KiB, read only to classify) whose error code or type names an exhausted quota, credit balance, plan, or organization or project spending or usage limit (`insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded`, `usage_limit_reached`, `usage_not_included`) records `usage_limit`; such a call is terminal and never retries. Every adapter, ChatGPT included, keeps the bounded delta-seconds `Retry-After` of a 429 or 5xx. A temporary-usage stream event keeps its unavailable class and never retries. Each retry commits its fact and passes fresh call-budget and Store admission before the wait; it is charged as a call with unknown usage, so a finite token budget refuses it. A pause or cancellation during the wait ends the call before any further reservation or dispatch, and both are checked again just before the re-dispatch. The provisional preview is cleared and the retry is shown as `Reconnecting… n/3`; `show`, `exec` receipts and the Goal report list every retry. Only after same-route retries does a configured fallback chain switch; visible preview text still blocks the switch. Peer mapping: Codex retries 429, 5xx, transport errors and compaction streams (four request and five stream retries), honors `Retry-After`, never retries the same exhausted quota, credit and spending codes (openai/codex 102fc57e), and shows `Reconnecting... n/max`; OpenCode backs off from 2 s capped at 10 s and retries only before output; Pi and Goose default to three. Arany takes the lowest peer count. It also journals and charges every attempt, which no peer does, for durable Goals and strict replay: a send failure after delivery can double remote usage, and that cost is charged, never hidden. A Provider call is not a Workspace effect, so no effect repeats.
- Calls across all roles, retries and explicitly configured fallbacks share the Goal budget and per-action limits. A lost response may already have consumed tokens; unconfigured broker fallback stays disabled.
- Each semantic step commits one bounded `ProviderCallRecorded` fact before its AgentRun terminal Event; a failed attempt that switches is recorded by `ProviderFallbackUsed` before its replacement dispatch. Cache-read and cache-creation counts are subsets of the reported input total. Responses `usage.input_tokens_details.cached_tokens` supplies cache reads on OpenAI and ChatGPT; absent details remain unknown. Anthropic `usage.cache_read_input_tokens` and `usage.cache_creation_input_tokens` supply reads and writes beside uncached `input_tokens`, and their checked sum is the input total. Messages may instead report cache writes as `usage.cache_creation` with required `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`; their checked sum supplies the creation total. If both representations are present, the totals must agree and are counted once. Absent optional cache counters stay unknown. Counters must be unsigned 32-bit integers, the input total must fit the reporting ceiling, and cache subsets cannot exceed it; malformed, overflowing or inconsistent usage rejects without retry. Streaming preserves these counters from the final usage envelope (including Anthropic message-start usage merged with message-delta usage). Phase and local disposition are canonical; the response ID and reported usage appear only when a bounded response arrived. A timed-out or cancelled call reports unknown usage and does not prove absence of remote billing. Responses `completed` with a local `store: false` request and Messages `end_turn` are distinct wire provenance; neither is a remote retention or ZDR guarantee.
- API-key adapters reject exact selected-key reflection in bounded raw bytes and in decoded outcome, response-ID or compaction fields, including JSON-escaped echoes. This is not general secret detection.
- Persist only the bounded adapter, endpoint profile, requested and resolved model, request ID, broker and upstream identity, finish reason, usage provenance, privacy controls and capability-evidence version. Raw response bodies and uncontrolled headers are never persisted.
- A catalog lists availability, not compatibility; only reviewed manifests, adapter fixtures and opt-in live probes support capability claims.

## Streaming and provisional text

- A preview is a bounded candidate, never an accepted outcome, reasoning channel, Tool argument or authority. Only public assistant text is extracted. Assistant text streams as the answer candidate (a `final_answer` item followed by a function call is a response-contract failure: the item is announced as the end of the turn and may already be journaled as the answer, so honoring a call after it would contradict a committed outcome, while Codex tolerates it. Journal-first keeps exactly one committed outcome per step); text that may still become commentary (all Anthropic text, ChatGPT text outside an explicit `final_answer` item) is shown but journaled only at the completion boundary, as an Answer chunk if it is the answer and as Commentary if a call follows. If a function call follows in the same response, the candidate is withdrawn and the text becomes commentary at the completion boundary; commentary-phase text is held until then. A candidate above the display limit stops streaming and leaves the committed answer to the Engine, which refuses it as `answer_invalid` like every other route.
- Known selected credentials are checked before text is exposed or recorded. A suffix that could complete a credential is retained, and cancellation never flushes it.
- The one-slot `ResponsePreview` observer holds the latest bounded snapshot; complete response, model, usage and outcome checks still decide acceptance. Only attached primary invocations expose a preview; configured fallback chains also use a bounded private observer as an additional visible-output guard; HTTP status admission decides eligibility.
- Shared framing admits at most 1 MiB and 8,192 events, requires duplicate-free event JSON within 262,144 nodes and depth 64 (a `response.created` event echoes the request, including the Tool catalog); an opaque assistant turn uses the same node and depth bounds within its own byte cap, requires label and type agreement, and never silently switches media or response encoding. Native and custom streaming use strict SSE media admission; ChatGPT uses its [admitted SSE policy](./chatgpt.md#catalog-checks-and-runs).
- Custom checks prove streaming for the default and each declared effort before Workspace-bearing use. Live streaming compatibility remains open evidence.

Cancellation drops any buffered streaming tail instead of flushing it.

## Commands

- `arany provider check openai|anthropic MODEL --effort LEVEL --accept-cost` is an optional, potentially billable diagnostic, not Run authorization. It uses the named environment source or explicit `--saved-account`, confirms catalog visibility, then makes at most three synthetic streaming direct, delegate and compaction calls. Each is capped at 1,024 remote tokens under one 180-second aggregate deadline, with no retries and no Workspace data. It clears the tuple's prior evidence first and publishes a 24-hour HMAC bound to the exact key, Provider, workspace, source or account, model, effort and versions, only after strict success. Native routes carry no window metadata. Anthropic's `max_input_tokens` is deferred: native evidence has no slot for it without a SQLite schema change, which would force a history reset. The check proves neither universal compatibility nor credential authority.
- `arany provider check custom:NAME --state-dir STATE` checks a user-authorized custom route; bare `NAME` also works. The [custom conformance contract](#custom-destinations-and-routing) owns cost, probes, bounds and evidence. Only a successful exact check permits `--provider custom:NAME --model EXACT`; a candidate recipe alone grants nothing.
- `arany provider models PROFILE` reads only the selected native credential and no Workspace data. The default source is the Provider's environment key; `--saved-account` selects the current OS-stored API account and rejects a Provider mismatch. The result is complete or fails closed at 1 MiB per page, 16 pages or 4,096 unique models. The response needs one `application/json` media type before body reading and uses no proxy, redirect, retry or decompression. Native rows distinguish reviewed effort metadata from availability-only rows; unknown rows are selectable with an explicit effort and no mandatory probe. A custom profile lists its configured model and declared efforts without reading its credential.

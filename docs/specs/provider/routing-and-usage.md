# Provider: configuration, routing and usage

## Configuration and egress

- An explicit CLI profile and model override trusted Session or user-configuration defaults. There is no compiled model default, Workspace-defined profile or implicit discovery. Attached `/model` follows the [terminal contract](../terminal/commands.md#interactive-commands-and-completion).
- A Provider receives only the current objective, selected bounded Session context, instruction and include snapshots, and the child results the phase needs. Only the credentials of configured role routes and fallbacks are read, and credentials never enter CLI arguments, Events, output, fixtures, telemetry or error bodies. Endpoint authorization is not content authorization.
- Provider HTTP requests ask for identity encoding, reject a non-identity `Content-Encoding` before reading the body, and bound non-streamed bodies to 1 MiB<!-- unrelated-bound: Provider HTTP response body --> per response; SSE uses the [framing bounds](./encoding-and-streaming.md#streaming-and-provisional-text). They follow no redirects, use no ambient proxy or cookies, make no automatic protocol retries and keep at most one idle connection per host for 60 seconds.
- HTTPS is required outside numeric loopback, which may use explicit HTTP. Destinations are pinned; route or model drift, changed addresses, metadata, link-local and multicast destinations, credential reuse across origins and credential reflection reject. TLS uses the operating system's trust store with chain and server-name checks; certificate and revocation fetches the OS makes are not Provider destinations and carry no content, files or credentials.
- Receipts use exact support language: `ChatGPT plan`; `custom` for a user-declared route; `broker constrained` after a future OpenRouter gate. A receipt never relabels a service as native OpenAI or Anthropic.

A future network grant must bind the typed operation, audience, method, destination, redirect policy, payload schema, data class and limits; a destination allowlist never authorizes arbitrary upload or proves data-loss prevention.

## Custom destinations and routing

Every custom route is admitted before disclosure, pinned with durable provenance and has every response strictly validated; a vendor compatibility label never replaces this. Custom primary and child routes receive the same Workspace Tools, grants, Policy and Guard as native routes.

- Native endpoints are compiled. A custom profile lives in trusted user configuration outside the Workspace and names a closed protocol family, exact endpoint or base URL, exact model and credential reference. It never accepts arbitrary headers, shell credential commands, repository profiles, raw key arguments, redirects, ambient proxies, automatic model discovery, a generic compatibility plugin or cross-profile credential reuse.
- Profiles are read only from `provider-profiles.json` in the private state root, a [strict record](../execution/persistence.md#incompatible-records) validated whole. `{profiles}` holds at most 32 uniquely named profiles, and each credential reference binds one origin. Every entry has `name`, `protocol`, `url`, `model`, `credential_env` and `efforts`. Responses (`protocol: openai-responses`) takes an exact canonical `/responses` `url`; Messages (`anthropic-messages`) a canonical base `url` and required `auth: bearer | x-api-key`; Chat Completions (`openai-chat-completions`) a canonical base `url`. Only Messages carries `auth`; the others send a Bearer token. The encoding follows the protocol (JSON schema for Responses and Chat Completions, native Tools for Messages) and the output cap is 4,096 tokens, so neither is stored. Unknown, duplicate and header fields refuse.
- Every entry requires an exact bounded model ID, an `ARANY_PROVIDER_*` credential reference and a canonically ordered unique `efforts` list from `none|low|medium|high|xhigh|max`. An empty list sends no effort field, not even a native Claude default. Messages efforts map to `output_config.effort` and Chat Completions efforts to `reasoning_effort`. Custom profiles never use the native model resolver.
- For Messages and Chat Completions, at most one terminal slash is removed from the validated base before `/v1/messages` or `/chat/completions` is appended, keeping a nonempty base path. Base and derived URL each have a 512-byte<!-- unrelated-bound: custom endpoint URL bytes --> limit and 256-byte path limit. Bases already ending in their protocol suffix, credentials, queries, fragments, percent encoding, dot segments, doubled path slashes and noncanonical hosts or ports reject. Numeric loopback may use HTTP or HTTPS; domains need HTTPS and admitted public DNS, where IPv6 answers are admitted only from reviewed allocated ranges ([IANA global-unicast allocations](https://www.iana.org/assignments/ipv6-unicast-address-assignments), [special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry)) and any other range fails closed.
- Messages requests send exactly the selected Bearer or `x-api-key` credential, `anthropic-version: 2023-06-01`, JSON content type, identity encoding and `User-Agent: arany/<version>`; Responses and Chat Completions send Bearer authentication and the same User-Agent. Native keys and Anthropic workspace scope are never read or forwarded. Messages routes keep opaque thinking, signatures and paired delegation results, reject several calls even if a vendor ignores parallel-call suppression, and send no thinking budget. Images refuse before HTTP on every custom route.
- Chat Completions replays assistant turns in the `messages` wire family; compaction is a system and user text exchange. A successful reply needs a `Content-Type` media type of `application/json` (case-insensitive, parameters ignored), or fails as `InvalidOutcome`. It has no preview. Wire provenance follows the [execution contract](../execution/admission-and-recovery.md#admission-persistence-and-recovery).
- Profile documents keep the [record byte bound](../execution/persistence.md#persistence-bounds), 65,536 JSON nodes and depth 32. Names and credential references are at most 64 bytes, model IDs 128 and keys 512. Custom DNS admits at most eight addresses within five seconds; connection takes at most ten seconds and each call 120 seconds<!-- unrelated-bound: custom Provider call deadline -->, vendor queues included. Requests are bounded by [the generated Provider request limit](../limits.md#max_provider_request_bytes); replies follow the [Provider HTTP client bound](#configuration-and-egress), SSE the [framing limits](./encoding-and-streaming.md#streaming-and-provisional-text), and Messages at most 16 content blocks. Custom compaction is limited by the 4,096-token profile cap and [the generated compaction token limit](../limits.md#max_compaction_output_tokens). Overflow or invalid required usage rejects without partial acceptance; absent optional cache counters stay unknown.
- Each Run re-reads the exact profile, resolves and pins every address, and only then reads the key, before Workspace input; `RunStarted` pins the endpoint and a digest of the declaration, and a `custom:` Provider without that provenance is refused. Requests connect only to the pinned addresses and refuse a destination change. Replay treats provenance as history, never authorization. Custom calls need positive labelled usage within the cap and run one call at a time.
- Arany never sends a paid request the user did not ask for, so there is no conformance pre-check; the strict decoder validates every real response. The first failure fails the Run, never silently retried, with an actionable notice and its closed reason: `response_contract` when model, completed message or usage do not match, `outcome_contract` for a malformed outcome or Tool call, `outcome_decode` when nothing decodes to a complete outcome. Every reply, Tool arguments included, must fit the profile's `max_output_tokens`, so a large Write needs smaller Edits.
- Attached setup writes profile declarations only as confirmed edits against the previously inspected bytes, validating the whole record first; uncertain publication is reported unknown and never retried or compensated. The environment reference stays metadata until a Run admits the destination.
- A future built-in OpenRouter profile is a broker: it pins one reviewed upstream endpoint, requires parameter support, disables fallback, denies data collection, requires ZDR, disables response caching, and records broker and upstream provenance.

DeepSeek API, Kimi platform and Code, and GLM Standard candidates follow their [setup recipes](../../setup.md#openai-compatible-and-anthropic-custom-routes); a recipe grants nothing and claims no live support.

## Usage, provenance and reliability

MCP arguments, selected-credential reflection checks and Guard dispatch share the strict Tool argument parser: one object, at most 8 KiB<!-- unrelated-bound: strict Tool JSON parser -->, depth 32 and 4,096 nodes, no duplicate decoded keys. Invalid JSON rejects before Tool persistence; a parse failure never proves credential absence.

- A failure before a decoded outcome retries the same route in every role (manual, automatic and in-Run compaction included): a send that fails before any response (it may already have been delivered), a non-terminal HTTP 429, HTTP 5xx at status admission, or a body or stream that ends early, including a ChatGPT cut at its [idle window or call ceiling](../chatgpt.md#run-limits). A clean end counts as a cut only after at least one well-formed event.
- A semantic call has at most three retries across all its routes, waiting 2, 4 and 8 s (at most 10 s each) or a longer delta-seconds `Retry-After` on a 429 or 5xx. Each wait must end before the remaining action deadline, inside the Goal's active time; a `Retry-After` that cannot fit fails the call at once (a 5xx can still switch).
- Never retried: a send timeout, cancellation, other 4xx, a malformed stream or body, contract and content failures, a temporary-usage stream event (kept as unavailable), and a primary call with committed display text. The [primary outcome correction](./encoding-and-streaming.md#structured-outcomes-and-tool-encoding) is a separate call.
- A 429 records the closed `rate_limited` reason. A 429 body (read only to classify, at most 16 KiB<!-- unrelated-bound: Provider rate refusal body -->) whose error code or type names an exhausted quota, credit, plan, or spending or usage limit (`insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded`, `usage_limit_reached`, `usage_not_included`) records `usage_limit` and is terminal.
- Each retry commits its fact and passes fresh call-budget and Store admission before the wait. It is charged as a call with unknown usage, so a finite token budget refuses it; a send failure after delivery can double remote usage, which is charged, never hidden. Pause, cancellation or a lost retry acknowledgment ends the call before any further dispatch. The preview clears and the retry shows as `Reconnecting… n/3`; `show`, `exec` receipts and the Goal report list every retry. A Provider call is not a Workspace effect, so no effect repeats.
- Calls across all roles, retries and fallbacks share the Goal budget and per-action limits. A lost response may already have consumed tokens. Unconfigured broker fallback stays off.
- Each semantic step commits one bounded `ProviderCallRecorded` fact before its AgentRun terminal Event; a switched attempt is recorded by `ProviderFallbackUsed` before its replacement dispatch. Phase and local disposition are canonical; the response ID and reported usage appear only when a bounded response arrived; a timed-out or cancelled call reports unknown usage and does not prove absence of remote billing. Responses `completed` with a local `store: false` request and Messages `end_turn` are distinct wire provenance; neither guarantees remote retention or ZDR.
- Cache-read and cache-creation counts are subsets of the reported input total. On Responses routes `usage.input_tokens_details.cached_tokens` supplies reads and `usage.input_tokens_details.cache_write_tokens` creation. Anthropic `usage.cache_read_input_tokens` and `usage.cache_creation_input_tokens` supply reads and writes beside uncached `input_tokens`, their checked sum being the input total; writes may instead come as `usage.cache_creation` with required `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`, and if both forms appear their totals must agree and count once. Absent counters stay unknown and explicit zero is zero. Counters are unsigned 32-bit, the input total fits the reporting ceiling and cache subsets cannot exceed it; malformed, overflowing or inconsistent usage rejects without retry. Streaming takes the final usage envelope, merging Anthropic message-start and message-delta usage.
- API-key routes reject exact selected-key reflection in raw bytes and in decoded outcome, response-ID or compaction fields, including JSON-escaped echoes; this is not general secret detection.
- Persist only the bounded adapter, endpoint profile, requested and resolved model, request ID, broker and upstream identity, finish reason, usage provenance and privacy controls; never raw response bodies or uncontrolled headers.
- A catalog lists availability, not compatibility; only reviewed manifests, adapter fixtures and opt-in live Runs support capability claims.

Provider diagnostics are inert bounded records without response content; they never change acceptance, retry, output or failure reasons. The [diagnostics contract](../diagnostics.md#privacy) owns privacy and retention.

### Passive plan-limit observations

Authorized ChatGPT inference responses may supply optional plan windows, which the [ChatGPT route](../chatgpt.md#catalog-and-runs) does not guarantee. Arany reads only `x-codex-{primary,secondary}-{used-percent,window-minutes,reset-at}` headers and `codex.rate_limits` events whose `rate_limits.primary/secondary` objects hold `used_percent`, `window_minutes` and `reset_at`; an event's `metered_limit_name` and `limit_name`, when present, must each be exactly `codex`, and other meters are ignored and never stored. Only the default meter and percent used are kept.

Each attempt keeps at most two final windows and one closed unavailable reason, at most 4 KiB<!-- unrelated-bound: passive Provider rate-limit sample --> serialized. Headers admit at most 32 recognized values, each at most 128 bytes and 4 KiB<!-- unrelated-bound: passive Provider rate-limit header aggregate --> in aggregate. Duplicate names, malformed fields and overflow make that sample unavailable; aggregate overflow invalidates both header windows. Percentages must be finite within 0–100, durations positive `u32` minutes, and timestamps Unix seconds from zero to 253,402,300,799. Missing percentage, duration and reset are independently unknown; nothing is clamped or inferred. Each kept window and unavailable reason records its receipt time and closed source. A valid event replaces its slot's whole header window, never borrowing fields.

Header observations survive body failure, timeout, cancellation and dropped calls. Selected-token reflection in any response header is a transport rejection (`InvalidOutcome`), including on 429 and 5xx; stream reflection, framing and required-usage rejection stay authoritative. Otherwise the metadata changes no outcome, retry, fallback, cancellation, budget or permission decision. A sample is kept only with the attempt's [committed fact](../execution/admission-and-recovery.md#admission-persistence-and-recovery). Observations persist no raw headers, account identifiers, plan or meter names, URLs, bodies or upstream text, never enter prompts, compaction input or telemetry content, and inspecting them adds no request or credential access.

Native OpenAI Responses and Anthropic Messages calls, including previews, children, review and compaction, collect passive API rate facts from headers only, kept through status failures, body loss, stream cuts, cancellation and deadlines and attributed to the actual route of each attempt. Between-Run and in-Run compaction keep role-labelled observations, failed or cancelled calls included. Only committed samples enter the report; append failure or lost acknowledgment stops continuation, and cancellation before headers supplies no sample.

OpenAI recognizes only the `x-ratelimit-{limit,remaining,reset}-{requests,tokens,project-tokens}` family, independently of `Retry-After`. Counts are unsigned `u64`, zero included; missing limit, remaining and reset are independently unknown. Resets use ordered, unique `d`, `h`, `m`, `s`, `ms` components, fractional seconds to millisecond precision, rounded up to whole Unix seconds; signs, exponents, finer precision, malformed components and overflow are unavailable. Counters are throughput facts, never percentages or a plan balance.

Anthropic recognizes only the [`anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-{limit,remaining,reset}` and `anthropic-priority-{input-tokens,output-tokens}-{limit,remaining,reset}` families](https://platform.claude.com/docs/en/api/rate-limits#response-headers), keeping standard, input, output and priority dimensions separate. Generic tokens reflect the most restrictive current limit, never a sum, and remaining counts may be rounded. Resets need a valid RFC3339 date, time and offset with at most 9 fractional digits, rounded up to whole seconds; leap seconds, invalid dates and overflow are unavailable. API workspace IDs and foreign or fast-mode quotas are ignored, and collection adds no polling or priority request policy.

The optional `api` payload has a closed dialect and unique dimension rows, bounded by [the API row ceiling](../limits.md#max_api_limit_rows) and the bounds above; API and plan payloads never coexist. Each row keeps its header source, receipt time, independent numeric fields and a closed unavailable reason; an invalid row has no numeric fields. Aggregate header overflow invalidates the API sample. The first valid sample pins its family for the attempt. API headers give one whole snapshot; plan events keep whole-window replacement. An absent `api` payload is omitted. The reflection, retention, settlement, privacy and passivity rules above apply.

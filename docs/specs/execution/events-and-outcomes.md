# Execution: events, worker journals and outcomes

## Committed Event stream

A hook-free single-call Tool step without approval or review commits `GoalProviderCallReserved`, `ProviderCallRecorded`, `ToolStarted` and `ToolFinished`. `ToolStarted` carries the final permission verdict (null only for unconfigured pinned-grant steps). Before a pre-hook, AI review or human approval, a conditional `ToolProposed` commits the complete immutable intent and active-time ceiling; hooks and reviews correlate to it, and the folded start advances the same Tool. A denial still commits a folded start and a not-dispatched finish. A proposal without a start is not an unknown effect: explicit resume may re-propose it when every hook outcome is known and non-stopping. A started Tool without a known outcome, or an unfinished or [Uncertain](#effect-outcomes) hook, blocks continuation.

The durable proposal serves pending-intent validation, exact review ownership and crash-budget guarantees, within the per-step and Session bounds below.

`Journal::append` feeds clients, telemetry and diagnostics only after commit, through a 256-envelope broadcast ring per subscriber. Lag yields `Resync { missed }`, and the subscriber recovers from the committed view without blocking execution. Subscriber failure or lag cannot change a Run outcome or grant authority. Provisional Provider previews stay outside this stream.

An envelope's `created_at_ms` is Unix wall time in milliseconds, sampled inside the transaction before reducer validation, insertion and commit. Timestamp differences are journal intervals, not monotonic elapsed time. A held or lost result acknowledgement cannot complete a monotonic success sample, and negative wall-clock intervals stay separate from monotonic durations.

A primary or researcher Tool step holds 1 through [`MAX_STEP_TOOL_CALLS`](../limits.md#max_step_tool_calls) calls in model order; editors keep one call per step. The complete proposal, arguments, phase, lease, plan scope and context fit are validated before any intent commits. A multi-call step commits every intent as `ToolProposed` in model order before the first dispatch; each folded `ToolStarted` commits after that call's hooks and approval. Admitted in-process reads dispatch concurrently under the [shared file-operation capacity](../tools/file-operations.md#in-process-file-operations); other calls wait until every read observation commits, then dispatch one at a time in model order. In a primary step with two or more calls, `ToolActiveTimeReserved` commits the [Goal action ceiling](../goals.md#lifecycle-budgets-and-recovery) before each precommitted intent is processed; it names the intent digest, occurs at most once per intent and grants no authority. Overlapping read reservations and starts cannot lower the recorded recovery ceiling. A single-call step keeps its ceiling on `ToolStarted`. Each call keeps its own verdict, intent and `ToolFinished`, correlated by intent digest. Read finishes commit in completion order; the next Provider request carries observations in model order. Replay accepts observations in any order for the step's pending intents and rejects duplicate or unmatched results. Every observation and hook settles before the next Provider call. Command integration and hook replacements stay attached to their source call. A stop prevents later dispatch: dispatched calls settle and the remaining intents receive non-dispatched observations. A read reaching Limit while a sibling approval is pending withdraws that approval; a late acceptance cannot dispatch it. Concurrent reads keep their own deadlines and share elapsed Goal wall time instead of charging overlap repeatedly. A crash after a partial intent prefix leaves those intents interrupted and never executes them.

Workspace file mutations attest in process with an intent-bound FileReceipt on success; historical Guard observations keep their recorded execution site. [File operations](../tools/file-operations.md#in-process-file-operations) owns validation, publication, deadline and uncertainty rules.

## Worker journal protocol

Every EditOnly AgentRun uses the same `execute_step` and `before_dispatch` as the primary and researchers. Before its `AgentSpawned` commits, the Engine creates the editor's private workspace under `StateRoot/editors/<session>/<assignment>`.

When the Run pins a Git and the Workspace root holds `.git`, the workspace is a linked Git worktree named `arany-<assignment>` in that directory, created after [configuration admission](../tools/git.md#typed-git-reads): the base is `git stash create`, or HEAD when the tree is clean, checked out with `git worktree add --detach` with hooks off and LFS content left as pointers, after a free-space check against [`GUARD_DISK_RESERVE_BYTES`](../limits.md#guard_disk_reserve_bytes) for the base tree. Protected tracked files are removed from the checkout, unchanged files keep their Workspace modification times, and untracked non-ignored files (`git ls-files --others --exclude-standard`) are copied in and recorded in `base`. Arany always names the worktree's Git directory explicitly and never follows the tree's `.git` file, which editor commands can rewrite. Integration lists tracked changes with `git diff --raw` against the base, reading each base version from Git (at most [`MAX_FILE_BYTES`](../limits.md#max_file_bytes)), and untracked files with `git ls-files --others --exclude-standard` against the copied record; the rules below then apply unchanged. Cleanup runs `git worktree remove --force`, falling back to deleting the tree and Arany's own `.git/worktrees/arany-*` record; there is no repository-wide prune. A `resumes` assignment renames the directory and repoints Git's record at it. An unborn HEAD, or no Git, uses the copy below.

Otherwise the workspace is the [command input selection](../tools/changesets-and-checkpoints.md#disposable-copy-selection) of the Workspace (ignored, dependency and protected inputs excluded; inputs of any size included; modification times kept), each file cloned copy-on-write (APFS `clonefile`, Linux `FICLONE` on btrfs or XFS) or streamed as a byte copy where the volume cannot clone, plus a sorted `base` record of every populated file's digest. A byte copy never takes the volume below [`GUARD_DISK_RESERVE_BYTES`](../limits.md#guard_disk_reserve_bytes) free; reaching it, or any other creation failure, fails the Run closed before the spawn with the cause, and an editor never works unisolated. Platform difference: on ext4 and other filesystems without reflinks every editor pays a full copy of the selected project in time and disk. The editor's Tool intents carry `target: editor_workspace {assignment_id, device, inode}`: typed reads and mutations run in process on that tree under the usual preconditions and receipts, without checkpoints, and its commands run directly in it ([Editor Tool steps](../tools/editors.md#editor-tool-steps)). Its effects are never Workspace facts: rewind planning, Goal and verification evidence, preconditions and reports ignore them.

After the editor's answer passes the criterion gate and SubagentStop, the Engine integrates once. A streaming comparison of the tree against `base` yields the project changes; ignored, dependency and protected outputs never integrate. A new one is discarded with the tree, but one whose path exists in the Workspace records `integration_conflict` naming it, so excluded work is never reported as `no_change`. No change gives `no_change`. More files than the Goal-pinned "Editor changes: files" ([default](../limits.md#default_editor_change_files)), more after-bytes than "Editor changes: size" ([default](../limits.md#default_editor_change_bytes)), a change record above the [Tool argument ceiling](../limits.md#max_tool_argument_bytes), or a changed or deleted file above [`MAX_FILE_BYTES`](../limits.md#max_file_bytes) records `changes_too_large`, and an unsafe entry `tool_failed`, with nothing written; a change outside the editor's lease or inside a sibling lease records `integration_conflict` with nothing written. Every refusal's `AgentFinished` carries a bounded Engine note in `summary` and `result` (at most [`MAX_EDITOR_CHANGE_REPORT_BYTES`](../limits.md#max_editor_change_report_bytes)) naming the cause and the offending paths, which the primary reads in the worker history; it is the only failed `AgentFinished` with these fields. Otherwise one internal `ApplyChangeset {source: editor_workspace {files}}` Tool commits under the editor's identity with `target: workspace`, after its answer and before `AgentFinished`, at most once. Its files carry paths and before/after digests only (no content). It runs through the ordinary hooks, permission review, checkpoint gate (one pre-image per changed file) and in-process publisher: every base digest must still hold in the Workspace or the whole integration is a `Conflict` naming the paths, with nothing written; after bytes come from the tree and must match their digests. A partial or lost publication is [Uncertain](#effect-outcomes) and never retried. A refused or conflicted editor fails with nothing integrated, keeping its workspace; the primary splits or replaces the task.

Arany editors cannot observe each other's or the primary's work in progress, and their changes land as one validated, checkpointed changeset. Editors never receive host authority; their capabilities are the intersection of parent, plan, definition and leased assignment, with `unguarded: denied`.

The workspace is deleted after a successful or empty integration. Before each Run the Engine keeps only workspaces of unintegrated editors whose Goal is running or interrupted and deletes the rest, including incomplete or unknown ones; a `resumes` assignment adopts its source's kept workspace instead of cloning, whose `base` still names the original versions.

An editor requires a write-capable parent, the Implementation phase, an admitted matching definition and a committed Goal plan. Invalid input is refused before spawn or child disclosure. Foreground and background modes share admission; command lists and criteria must fit the parent, plan and definition grants. No editor can invoke Git, MCP, Skills, network, host commands or nested delegation. Per-Tool, context, turn, call, token, active-time and Store bounds stay in force.

`RunStarted.config.worker_policy` is required nullable; its bounded parent grant, concurrency, turns and model Tool ceiling are admission pins, with no data allowance.

`ProviderCallRecorded.delegation` keeps its required nullable bounded typed assignments and ordinal/wave matching. `AgentSpawned.assignment` is required nullable, present exactly with `ChildGrant::EditOnly`: the request, effective grant, parent policy digest and required nullable permission digest. Spawn atomically acquires the lease and validates lineage, concurrency and overlapping assignments against committed facts.

Writable leases name 1–64 sorted relative files or subtrees of at most 512 ASCII bytes and depth 16. Traversal, backslashes, protected components, controls and non-ASCII writable paths reject. Ancestor/descendant and ASCII case-folded aliases conflict. A typed mutation by any actor overlapping another actor's live lease is refused before intent commit. A lease authorizes only its owning editor, never a sibling or the primary. Primary commands and MCP require lease quiescence. Editor commands publish nothing; the integration must fit the owning lease and avoid every sibling lease, and one out-of-lease path refuses it without changing the Workspace. Leases have no TTL and never cross Runs.

Editor Tool steps run under the child's identity with its verdicts, delegated hooks, cancellation, delegation deadline and shared accounting. Successful typed file operations have receipts bound to the editor's workspace. Editor commands use the same platform Guard and exclusive cache-identity lease as primary commands, directly in the editor's workspace; busy refuses without waiting. Only the integration enters the shared checkpoint gate; [checkpoints](../tools/changesets-and-checkpoints.md#checkpoints-and-rewind) and [rewind planning](../session.md#rewind-planning-and-replay) include it and no edit made in the workspace. Known non-dispatch carries no checkpoint. Mkdir keeps ordinary directory semantics and cannot be a standalone assignment criterion.

`AgentFinished.worker` is required nullable and present exactly for editors, with closed `disposition` and `cause`. Ready and no-change require an observed answer and current committed Tool evidence in the editor's workspace for the criterion; ready requires a successful integration and no-change requires none. `integration_conflict` follows a conflicted integration or a lease refusal and `changes_too_large` an overflow; neither integrated anything. A known Tool failure, invalid answer, hook stop, turn or budget limit, or cancellation keeps its own cause. A known pre-dispatch denial follows the shared permission feedback rules; a model, definition, hook or child report cannot supply approval.

The editor's answer passes the criterion gate before SubagentStop. An unmet criterion keeps the closed `criterion_not_met_in_view` reason and allows at most three bounded corrective continuations within remaining turns, Tools, call, token, time and Event capacity. A continuation is a fresh model decision, never an effect retry. A blocked stop hook keeps the existing feedback, turn and budget precedence.

`WorkerLeaseReleased` contains only the assignment ID and the exact causal `AgentFinished` sequence. Release requires that editor's committed terminal outcome, settled known Tools and no earlier release; it fabricates no integration. `WorkerVerificationRecorded` follows release and pins the criterion digest plus at most eight increasing primary Workspace observation sequences; replay derives the result independently. Child evidence, the answer and release cannot pass verification, and later Workspace mutations invalidate a passing one. A failed editor requires an explicit replacement decision, never fabricated verification.

`WorkerStopObserved` records the first cancellation, pause or budget boundary before further team dispatch. New spawns, calls, Tools and verification reject after it, while in-flight observations and terminal and release facts drain. Cancellation and pause integrate nothing and keep the editor's workspace. Process death leaves interrupted intents and the last receipted Workspace state. An [Uncertain](#effect-outcomes) Workspace effect stops the whole Run without lease release or continuation.

## Accepted outcomes

A validated `arany_plan` call records disposition `plan_recorded`, zero requested effects, null delegation and no failure or refusal. Only a Tool-enabled primary in RootPlan or RootSynthesis without an existing contract may record it, and the function is offered only to autonomous Goals and explicit `team` policy ([Goals](../goals.md#initial-plan-contract-and-success-receipt)). The next contract Event precedes any new action, and continuation requires that contract to be committed. Plan calls consume the ordinary Goal call and usage budget.

A journaled `stopped` result from any successful [hook event](../tools/hooks.md#hook-execution) in an active Run ends the Run and its primary AgentRun as `stopped_by_hook`, distinct from success, failure and cancellation. A hook running with a child's identity (SubagentStop or a delegated Tool hook) also ends that child as `stopped_by_hook`, drains the other children (they end Cancelled) and prevents synthesis. No further Provider reservation, Tool, spawn or hook starts in that Run; already reserved child calls drain and are recorded. No assistant Message commits, and completed effects remain. The displayed optional reason comes from the committed hook result within the [Hook execution](../tools/hooks.md#hook-execution) reason bound; terminal, `exec` and `serve` adapters escape it and show it as user feedback, never model input. Diagnostics and telemetry use the closed disposition without the reason. The [Goal](../goals.md#lifecycle-budgets-and-recovery) stays open. Strict replay validates the facts without executing the hook.

Every step produces exactly one phase-allowed text answer, Delegate, optional primary plan or enabled Tool proposal within the [per-step bounds](#committed-event-stream). An accepted answer ends the turn and commits once as `MessageCommitted.text`; earlier text is commentary. `AgentFinished.summary` is the answer's first nonempty line, truncated at a UTF-8 boundary to 2 KiB<!-- unrelated-bound: derived child summary bytes -->, and `AgentFinished.result` keeps the answer; replay rejects a summary that differs from this derivation. A primary planning or synthesis call may carry the Run's accepted steering notes as user input; child calls carry only their own actor-bound notes, Tool review receives none, and pause applies only at the [Goal boundaries](../goals.md#steering-notes-and-pause). There is no fixed per-Run Tool-effect or model-step ceiling: each action requires bounded Event, Store, request, context and terminal-tail admission, and the Goal's call, Run and active-time budgets bound the task. The primary's last call under a finite Provider-call budget offers only an answer, as [Goals](../goals.md#lifecycle-budgets-and-recovery) defines; its committed answer finishes the Run normally.

Primary Tool calls need no plan: Tool schemas carry no per-Tool plan fields, and the plan is a separate primary function. Research and Plan Goal phases keep their prelude-only catalog: Workspace List/Read/Search, typed Git reads, admitted Skill reads and configured bounded MCP catalog listing. Implementation calls stay subject to the pinned grant and effect admission. A recorded [Goal plan](../goals.md#initial-plan-contract-and-success-receipt) further narrows scope and binds success; the Goal contract owns scope and replay rules. Children receive Single policy; a researcher receives only the read-only research catalog, its own observations and answer. Its MCP calls, writes, commands and plan contracts are invalid before dispatch; one read outside the plan contract is journaled Denied without dispatch, while an out-of-scope batch is refused in full before any intent. Unknown operations and malformed wire responses reject without an alternate encoding; decoded primary proposals follow the refusal continuation below.

A decoded primary proposal refused by Engine validation in RootPlan or RootSynthesis records `failure_reason: proposal_refused` with required nullable `refusal { operation, cause }` on the same `ProviderCallRecorded`, paired only with `Rejected`. The operation is the compiled `arany_` function name (including `arany_plan`), `answer` or `delegate`, never arguments. Closed causes are `invalid_arguments`, `invalid_path`, `digest_unknown` ([Engine-filled preconditions](../tools/file-operations.md#engine-filled-preconditions)), `phase`, `plan_invalid`, `plan_budget_outside_goal`, `plan_budget_spent`, `plan_scope_excludes_call`, `plan_outside_grant`, `argument_bytes`, `lease_overlap`, `not_offered`, `answer_invalid`, `delegate_invalid`, `editor_definition`, `editor_digest`, `editor_commands`, `editor_turns`, `editor_lease`, `editor_criterion`, `editor_resume` and `editor_grant`. The refusal commits before another Provider reservation, and the primary loop continues without a Tool intent, Guard dispatch or receipt. One invalid call refuses the whole batch before any intent, and feedback names its zero-based index. Exceeding the [per-step call cap](#committed-event-stream) or duplicating call IDs refuses with `invalid_arguments`, and feedback names the cap.

The turn continues after refused Tool proposals, under Arany's journal and resource cap. For a refused typed Tool proposal, the next request pairs the original assistant turn and each call ID with one native error result derived from the committed refusal: closed cause, fixed remediation, `dispatched: false` and `effect: none`, at most 2 KiB<!-- unrelated-bound: typed Tool refusal result --> plus framing. Invalid paths get the canonical Workspace-relative path requirements, never an echo of argument text. The error turn counts toward continuation capacity and may enter whole-step compaction; no intent, observation or receipt is fabricated. Other refused primary proposals get one `last_answer_refused` note as trailing user data in the `worker_coordination` channel after Tool steps and stop feedback, keeping the earlier request prefix: operation, closed cause and fixed remediation, never model-authored values. A Tool refusal during a worker wave records `worker_tool_refused` without a cause. Ledger read and editor-grant construction errors are Engine errors, never refusal causes. Explicit Team planning that answers instead of delegating uses this path.

Three consecutive primary refusals with the same `(operation, cause)` end the Run with `refusal_limit`; a different pair or a non-refused call breaks the streak. Eight total primary refusals also stop the Run. Each retry reserves and spends a normal Provider call under the Goal budget; cancellation and pause keep their boundaries. A crash after the refusal commit keeps it, and a resumed Session shows it as nothing dispatched within the history bounds.

Before publishing a prepared Tool step, the Engine preflights each candidate read-only against the committed Session through the reducer's validator: the proposal before hooks or approval, and the folded start with its final verdict before dispatch. Phase, plan scope and lease checks have one Session-owned implementation shared with proposal refusal and strict replay. Invalid payloads map to `invalid_arguments`, invalid transitions to `phase`, out-of-plan calls to `plan_scope_excludes_call` and lease conflicts to `lease_overlap`. A rejected candidate is never appended or dispatched; instead `ToolPreflightRefused` commits its intent digest and typed `{cause, reason}` under the same Run and actor, where the reason is one of the validator's fixed sentences (unknown reasons and mismatched pairs reject). A verdict already produced by hooks, review or approval is carried as diagnostic evidence without granting dispatch or remembered authority. At most one refusal is admitted per AgentRun. In a concurrent read step, known completions settle first. The refusal closes the actor's unstarted proposals and prevents another Provider call, hook or Tool start for it; it creates no observation, receipt or effect, and cannot settle a started effect or hook with an unknown outcome. A final-start rejection releases its approval or review active-time reservation. Rejection after an accepted proposal stops the Run with `proposal_refused`. The AgentRun projection, historical output and later failure feedback keep the typed cause. Cancellation, hook-stop, uncertainty and budget precedence is unchanged.

A researcher batch above the [Tool step cap](../limits.md#max_step_tool_calls) commits the same `rejected` / `proposal_refused` record with `InvalidArguments` before continuation, starts no Tool and keeps usage. Its next request has one cap-aware non-dispatched result per call ID. The refusal ceilings apply independently to each researcher AgentRun; a refusal consumes a normal turn and Goal call but no Tool-call allowance. Exhausted refusal, turn, context or time bounds end the child. Other invalid researcher outcomes stay fatal. Editors keep single-call validation without a refusal continuation.

`RunFinished.failure` is required nullable and present exactly with `Failed`: `provider_call`, `proposal_refused`, `budget_exhausted` (the Goal budget refused the next action), `tool_stopped` (a terminal dropped Tool step, a Guard failure after GO or without proof of non-dispatch, or an unusable Command result), `definition_invalid`, `plan_admission`, `tool_context_full`, `workers_unverified`, `criterion_unmet` or `refusal_limit`. A known recoverable primary Tool denial or failure, including a Guard failure whose observation proves nothing was dispatched, is delivered once as its correlated result and does not by itself produce `tool_stopped`; the effect is never retried, and the next call is a fresh model decision; a following Provider failure or refused continuation keeps its own cause. Strict replay rejects missing fields, unknown causes and invalid disposition pairings. [Terminal](../terminal/conversation.md#conversation-progress-and-history) owns failure copy and [diagnostics](../diagnostics.md) owns private records.

The primary Run settles once, by one precedence:

1. An [Uncertain](#effect-outcomes) primary Tool observation or hook outcome, or the stopping step's uncertain build-cache publication, journals no terminal Event and is reported unknown. A Run that cannot settle because a reservation, another agent or a primary Tool is still open also journals nothing; the submission returns it as reopened history projects it (`uncertain` only with an open or unknown effect, budget exhaustion when its counts prove it, otherwise interrupted).
2. Cancellation or pause ends the Run `cancelled`, including during a lifecycle hook.
3. A settled hook stop ends it `stopped_by_hook`.
4. Exhausted active time, or a call or token budget that refused the next action, ends it `budget_exhausted` and records the Goal exhausted once its budget is spent; this outranks `tool_context_full`, `tool_stopped` and `plan_admission`.
5. The stopping step's own cause.

An accepted answer that passed its Stop hooks still finishes when active time runs out after it.

The [Provider encoding contract](../provider/encoding-and-streaming.md#structured-outcomes-and-tool-encoding) owns automatic Tool selection, plain-text answers and structured compaction and review. Responses text parts join in order without inserted or repaired bytes. Explicit commentary may precede the final answer or Tool proposal; refusal, malformed content, unknown phases, ambiguous finals, late commentary and contradictory error or incomplete markers reject. A missing or null phase is valid only for an unambiguous final message or text preceding a call. The ChatGPT route's SSE parsing and item reconstruction belong to the [ChatGPT contract](../chatgpt.md#catalog-and-runs); only complete matching items reconcile, and failure publishes no partial answer.

All adapters reject reported input above the shared input ceiling. Provider-enforced routes reject reported output above the exact request cap; the ChatGPT route caps visible output, so its recorded total (including reasoning) is bounded only by the 1,000,000-token reporting ceiling, live and in replay ([ChatGPT limits](../chatgpt.md#run-limits)). Accepted outcomes also fit the serialized terminal payload bound, including JSON escaping. Native OpenAI may keep unknown usage; custom and ChatGPT outcomes require positive labeled usage. Native API-key and custom output caps are remote request controls; ChatGPT has a local acceptance cap and cannot guarantee remote generation or plan consumption. A Tool review uses Single policy without Tools, history, includes or project instructions, its own 256-token cap, a 20-second ceiling and the aggregate 32-call headroom ([approvals](../tools/trust-and-approvals.md#folder-trust-and-approvals)); uncertainty or failure asks a human and never grants a broader permission.

The selected Provider declares the primary output-token cap and call deadline; the Run pins the cap. Native OpenAI, Anthropic API and ChatGPT-plan routes declare 32,768 output tokens and exact custom routes 4,096 (ChatGPT counts only visible output; see [Run limits](../chatgpt.md#run-limits)); replay rejects a pinned cap outside 1 to 32,768. Editor calls request 32,768 tokens, narrowed by route binding; researcher calls request 4,096. Native OpenAI, Anthropic and ChatGPT-plan calls have a 600-second<!-- unrelated-bound: native Provider call deadline --> deadline (ChatGPT also has a [stream-idle deadline](../chatgpt.md#run-limits)); custom calls have 120 seconds<!-- unrelated-bound: custom Provider call deadline -->. Each call also ends at the remaining Goal active time. A Tool review reserves 20 seconds plus Store overhead, compaction keeps its 120-second<!-- unrelated-bound: Engine compaction call deadline --> deadline, a tool-free delegation reserves one deadline per wave of concurrent children (at most 20 minutes), and a researcher delegation reserves 20 minutes. The useful answer stays at the 32 KiB<!-- unrelated-bound: assistant and child result cap --> assistant or result bound; the extra output headroom covers Tool-call arguments and reasoning, and context budgeting reserves no output tokens. Arany keeps a finite declared cap for [explicit resource bounds](../../../AGENTS.md#global-rules).

Malformed, non-object or duplicate-key MCP arguments, and selected-credential reflections including nested escaped arguments, reject before persistence. A Provider failure stays the call's outcome even when an earlier Tool denial could otherwise continue. Same-route retries follow [Provider reliability](../provider/routing-and-usage.md#usage-provenance-and-reliability); no route has an encoding fallback, and only an explicitly configured, admitted [Provider fallback chain](../provider/selection.md#per-role-selection-and-fallback) switches destinations. A lost response can still consume remote usage.

### Effect outcomes

Every dispatched effect (Tool, hook, host operation, Provider setup edit or rewind) settles as one of:

- **Limit**: a bound (deadline, capacity, size or budget) stopped it before any effect, or with a known partial result and no publication; for example a command timeout keeps bounded partial output and publishes no changeset.
- **Cancelled**: cancellation stopped it before any effect, or with confirmed teardown.
- **Failed**: it completed with a confirmed failure (nonzero exit, refused request, API, auth or parse failure).
- **Uncertain**: its outcome is unknown after dispatch: a lost acknowledgement or receipt, unconfirmed teardown, interrupted publication, process death after GO or unconfirmed durability.

Uncertain stops its continuation: no further Provider call, Tool or hook starts for that work, the Run journals no terminal outcome and is reported unknown, and Goal resume is blocked until the user acts. Confirmed Limit and Cancelled outcomes keep their recorded meaning and imply no rollback.

No effect is retried automatically. A continuation after a failure is a fresh model decision with fresh intents and preconditions; only Provider calls have bounded same-route retries and fallback, which never redispatch an observed Tool. Tool attempts and results are untrusted historical facts: strict replay, resume, fork, rewind planning, compaction and archiving never execute a historical intent, complete or roll back an effect, or restore a permission. A fresh task may inspect current files and propose a newly authorized edit.

A command-generated `ApplyChangeset` correlates to its exact preceding command receipt; one that exceeds the active Goal path scope records a no-Guard denial, and replay rejects a successful out-of-scope integration. Pre-dispatch Guard failure follows the [Tool failure rules](../tools/limits-and-failures.md#limits-and-failure-behavior); once the GO write begins, missing completion is Uncertain.

# Execution: events, worker journals and outcomes

## Committed Event stream

A hook-free single-call Tool step without approval or review commits `GoalProviderCallReserved`, `ProviderCallRecorded`, `ToolStarted` and `ToolFinished`; `ToolStarted` carries the final permission verdict (null only for unconfigured pinned-grant steps). Before a pre-hook, AI review or human approval, `ToolProposed` commits the complete immutable intent and active-time ceiling; hooks and reviews correlate to it, and `ToolStarted` then advances the same Tool. A denial still commits a start and a not-dispatched finish. A proposal without a start is not an unknown effect: explicit resume may re-propose it when every hook outcome is known and non-stopping. A started Tool without a known outcome, or an unfinished or [Uncertain](#effect-outcomes) hook, blocks continuation.

Clients, telemetry and diagnostics see Events only after commit, through a 256-envelope buffer per subscriber; a lagging subscriber gets `Resync { missed }` and recovers from the committed view without slowing execution. Subscribers cannot change a Run outcome or grant authority. Provisional Provider previews stay outside this stream. An envelope's `created_at_ms` is Unix wall time in milliseconds at commit; differences between timestamps are journal intervals, not monotonic elapsed time.

A primary or researcher Tool step holds 1 through [`MAX_STEP_TOOL_CALLS`](../limits.md#max_step_tool_calls) calls in model order; editors keep one call per step. The whole batch is validated before any intent commits, then every intent commits as `ToolProposed` in model order before the first dispatch. Admitted in-process reads run concurrently under the [shared file-operation capacity](../tools/file-operations.md#in-process-file-operations); other calls wait for them, then run one at a time in model order. In a primary step with two or more calls, `ToolActiveTimeReserved` records each intent's [Goal action ceiling](../goals.md#lifecycle-budgets-and-recovery) before it is processed; a single-call step keeps its ceiling on `ToolStarted`. Each call keeps its own verdict, intent and `ToolFinished`, correlated by intent digest; the next Provider request carries observations in model order, and replay rejects duplicate or unmatched results. Every observation and hook settles before the next Provider call. A stop prevents later dispatch: dispatched calls settle and the remaining intents receive non-dispatched observations. A read reaching Limit while a sibling approval is pending withdraws that approval. Concurrent reads keep their own deadlines and share elapsed Goal time instead of charging overlap repeatedly. A crash after a partial intent prefix leaves those intents interrupted and never executes them.

Workspace file mutations attest in process with an intent-bound FileReceipt on success; [File operations](../tools/file-operations.md#in-process-file-operations) owns validation, publication, deadline and uncertainty rules.

## Worker journal protocol

Before its `AgentSpawned` commits, each EditOnly child gets a private workspace under `StateRoot/editors/<session>/<assignment>`; it runs the same step loop as the primary and researchers.

When the Run pins a Git and the Workspace root holds `.git`, the workspace is a linked Git worktree named `arany-<assignment>`, based on the current tree including uncommitted tracked changes, created with hooks off and LFS content left as pointers, after a free-space check against [`GUARD_DISK_RESERVE_BYTES`](../limits.md#guard_disk_reserve_bytes). Protected tracked files are removed, unchanged files keep their Workspace modification times, and untracked non-ignored files are copied in. Arany never follows the worktree's `.git` file, which editor commands can rewrite. Integration reads each base version from Git (at most [`MAX_FILE_BYTES`](../limits.md#max_file_bytes)) and then applies the rules below unchanged. Cleanup removes the worktree and only Arany's own `.git/worktrees/arany-*` record, never pruning the repository. An unborn HEAD, or no Git, uses the copy below.

Otherwise the workspace is a copy-on-write clone (byte copy where the volume cannot clone) of the [command input selection](../tools/changesets-and-checkpoints.md#disposable-copy-selection): ignored, dependency and protected inputs excluded, inputs of any size included, modification times kept. A copy never takes the volume below [`GUARD_DISK_RESERVE_BYTES`](../limits.md#guard_disk_reserve_bytes) free; reaching it, or any other creation failure, fails the Run before the spawn with the cause, so an editor never works unisolated. Platform difference: on ext4 and other filesystems without reflinks every editor pays a full copy of the selected project in time and disk. The editor's Tool intents carry `target: editor_workspace {assignment_id, device, inode}` and run there without checkpoints ([Editor Tool steps](../tools/editors.md#editor-tool-steps)). Its effects are never Workspace facts: rewind planning, Goal and verification evidence, preconditions and reports ignore them.

After the editor's answer passes the criterion gate and SubagentStop, the Engine integrates once, comparing the tree with its recorded base:

- No change gives `no_change`. Ignored, dependency and protected outputs never integrate; one whose path exists in the Workspace records `integration_conflict` naming it, so excluded work is never reported as `no_change`.
- More files than the Goal-pinned "Editor changes: files" ([default](../limits.md#default_editor_change_files)), more after-bytes than "Editor changes: size" ([default](../limits.md#default_editor_change_bytes)), a change record above the [Tool argument ceiling](../limits.md#max_tool_argument_bytes), or a changed or deleted file above [`MAX_FILE_BYTES`](../limits.md#max_file_bytes) records `changes_too_large`; an unsafe entry records `tool_failed`; a change outside the editor's lease or inside a sibling lease records `integration_conflict`. Each writes nothing, and its `AgentFinished` carries a bounded Engine note in `summary` and `result` (at most [`MAX_EDITOR_CHANGE_REPORT_BYTES`](../limits.md#max_editor_change_report_bytes)) naming the cause and offending paths, the only failed `AgentFinished` with these fields.
- Otherwise one internal `ApplyChangeset {source: editor_workspace {files}}` Tool commits at most once under the editor's identity with `target: workspace`, before `AgentFinished`; its files carry paths and before/after digests only. It runs through the ordinary hooks, permission review, checkpoint gate (one pre-image per changed file) and publisher: if any base file changed in the Workspace, the whole integration is a `Conflict` naming the paths, with nothing written. A partial or lost publication is [Uncertain](#effect-outcomes) and never retried.

A refused or conflicted editor fails with nothing integrated and keeps its workspace; the primary splits or replaces the task. Editors cannot observe each other's or the primary's work in progress, and never receive host authority: their capabilities are the intersection of parent, plan, definition and leased assignment, with `unguarded: denied`.

The workspace is deleted after a successful or empty integration. Before each Run, the Engine keeps only workspaces of unintegrated editors whose Goal is running or interrupted and deletes the rest; a `resumes` assignment adopts its source's kept workspace, whose base still names the original versions.

An editor requires a write-capable parent, the Implementation phase, an admitted matching definition and a committed Goal plan; invalid input is refused before spawn or child disclosure. Command lists and criteria must fit the parent, plan and definition grants. No editor can invoke Git, MCP, Skills, network, host commands or nested delegation. Per-Tool, context, turn, call, token, active-time and Store bounds stay in force.

`RunStarted.config.worker_policy` is required nullable: the bounded parent grant, concurrency, turns and model Tool ceiling. `ProviderCallRecorded.delegation` keeps its required nullable typed assignments with ordinal and wave numbers. `AgentSpawned.assignment` is required nullable, present exactly with `ChildGrant::EditOnly`: the request, effective grant, parent policy digest and required nullable permission digest. Spawn acquires the lease atomically.

Writable leases name 1–64 sorted relative files or subtrees of at most 512 ASCII bytes and depth 16. Traversal, backslashes, protected components, controls and non-ASCII writable paths reject; ancestor/descendant and ASCII case-folded aliases conflict. A typed mutation by any actor overlapping another actor's live lease is refused before intent commit: a lease authorizes only its owning editor. Primary commands and MCP require lease quiescence. The integration must fit the owning lease and avoid every sibling lease; one out-of-lease path refuses it without changing the Workspace. Leases have no TTL and never cross Runs.

Editor Tool steps run under the child's identity with its verdicts, delegated hooks, cancellation, delegation deadline and shared accounting. Editor commands use the same platform Guard and exclusive cache lease as primary commands; busy refuses without waiting. Only the integration is checkpointed and visible to [checkpoints](../tools/changesets-and-checkpoints.md#checkpoints-and-rewind) and [rewind planning](../session.md#rewind-planning-and-replay). Mkdir cannot be a standalone assignment criterion.

`AgentFinished.worker` is required nullable and present exactly for editors, with closed `disposition` and `cause`. Ready and no-change require an observed answer and committed Tool evidence in the editor's workspace for the criterion; ready requires a successful integration and no-change none. `integration_conflict` and `changes_too_large` integrated nothing. A known Tool failure, invalid answer, hook stop, turn or budget limit, or cancellation keeps its own cause. A model, definition, hook or child report cannot supply approval.

An unmet criterion keeps the closed `criterion_not_met_in_view` reason and allows at most three bounded corrective continuations within remaining turns, Tools, calls, tokens, time and Event capacity; each is a fresh model decision, never an effect retry.

`WorkerLeaseReleased` contains only the assignment ID and the causal `AgentFinished` sequence; release requires that editor's terminal outcome and settled Tools. `WorkerVerificationRecorded` follows release and pins the criterion digest plus at most eight increasing primary Workspace observation sequences; replay derives the result independently. Child evidence, the answer and release cannot pass verification, and later Workspace mutations invalidate a passing one. A failed editor requires an explicit replacement decision.

`WorkerStopObserved` records the first cancellation, pause or budget boundary; new spawns, calls, Tools and verification reject after it while in-flight work drains. Cancellation and pause integrate nothing and keep the editor's workspace. Process death leaves interrupted intents and the last receipted Workspace state. An [Uncertain](#effect-outcomes) Workspace effect stops the whole Run without lease release or continuation.

## Accepted outcomes

A validated `arany_plan` call records disposition `plan_recorded`, zero requested effects, null delegation and no failure or refusal. Only a Tool-enabled primary in RootPlan or RootSynthesis without an existing contract may record it, and the function is offered only to autonomous Goals and explicit `team` policy ([Goals](../goals.md#initial-plan-contract-and-success-receipt)). No new action starts until the contract commits. Plan calls consume the ordinary Goal call and usage budget.

A `stopped` result from any successful [hook event](../tools/hooks.md#hook-execution) in an active Run ends the Run and its primary AgentRun as `stopped_by_hook`, distinct from success, failure and cancellation. A hook running with a child's identity (SubagentStop or a delegated Tool hook) also ends that child as `stopped_by_hook`, cancels the other children and prevents synthesis. Nothing new starts in that Run; already reserved child calls drain and are recorded. No assistant Message commits, and completed effects remain. The optional reason, within the hook reason bound, is escaped and shown as user feedback, never model input; diagnostics and telemetry omit it. The [Goal](../goals.md#lifecycle-budgets-and-recovery) stays open. Replay validates the facts without executing the hook.

Every step produces exactly one phase-allowed text answer, Delegate, optional primary plan or enabled Tool proposal within the [per-step bounds](#committed-event-stream). An accepted answer ends the turn and commits once as `MessageCommitted.text`; earlier text is commentary. `AgentFinished.summary` is the answer's first nonempty line, truncated at a UTF-8 boundary to 2 KiB<!-- unrelated-bound: derived child summary bytes -->, and `AgentFinished.result` keeps the answer. A primary planning or synthesis call may carry the Run's accepted steering notes; child calls carry only their own notes, Tool review none, and pause applies only at the [Goal boundaries](../goals.md#steering-notes-and-pause). There is no fixed per-Run Tool-effect or model-step ceiling: each action needs Event, Store, request and context admission, and the Goal's call, Run and active-time budgets bound the task. The primary's last call under a finite Provider-call budget offers only an answer, which finishes the Run normally.

Primary Tool calls need no plan; the plan is a separate primary function. Research and Plan Goal phases offer only Workspace List/Read/Search, typed Git reads, admitted Skill reads and configured MCP catalog listing; Implementation calls stay subject to the pinned grant and effect admission. A recorded [Goal plan](../goals.md#initial-plan-contract-and-success-receipt) further narrows scope and binds success. Children receive Single policy; a researcher receives only the read-only research catalog, its own observations and answer. Its MCP calls, writes, commands and plan contracts are invalid before dispatch; one read outside the plan contract is journaled Denied without dispatch, while an out-of-scope batch is refused in full. Unknown operations and malformed wire responses reject without an alternate encoding.

A decoded primary proposal refused by Engine validation in RootPlan or RootSynthesis records `failure_reason: proposal_refused` with required nullable `refusal { operation, cause }` on its `ProviderCallRecorded`, paired only with `Rejected`. The operation is the compiled `arany_` function name (including `arany_plan`), `answer` or `delegate`, never arguments. Closed causes are `invalid_arguments`, `invalid_path`, `digest_unknown` ([Engine-filled preconditions](../tools/file-operations.md#engine-filled-preconditions)), `phase`, `plan_invalid`, `plan_budget_outside_goal`, `plan_budget_spent`, `plan_scope_excludes_call`, `plan_outside_grant`, `argument_bytes`, `lease_overlap`, `not_offered`, `answer_invalid`, `delegate_invalid`, `editor_definition`, `editor_digest`, `editor_commands`, `editor_turns`, `editor_lease`, `editor_criterion`, `editor_resume` and `editor_grant`. Nothing is dispatched and the primary loop continues. One invalid call refuses the whole batch, and feedback names its zero-based index. Exceeding the [per-step call cap](#committed-event-stream) or duplicating call IDs refuses with `invalid_arguments`, naming the cap.

For a refused typed Tool proposal, the next request pairs each call ID with one native error result: closed cause, fixed remediation, `dispatched: false` and `effect: none`, at most 2 KiB<!-- unrelated-bound: typed Tool refusal result --> plus framing. Invalid paths get the Workspace-relative path requirements, never an echo of argument text. Other refused primary proposals, including explicit Team planning that answers instead of delegating, get one `last_answer_refused` note in the `worker_coordination` channel: operation, closed cause and fixed remediation, never model-authored values. A Tool refusal during a worker wave records `worker_tool_refused` without a cause.

Three consecutive primary refusals with the same `(operation, cause)` end the Run with `refusal_limit`; a different pair or a non-refused call breaks the streak. Eight total primary refusals also stop the Run. Each retry spends a normal Provider call under the Goal budget. A resumed Session shows a committed refusal as nothing dispatched.

Each Tool candidate is checked against the committed Session before hooks or approval and again with its final verdict before dispatch, by the same checks replay uses: invalid payloads map to `invalid_arguments`, invalid transitions to `phase`, out-of-plan calls to `plan_scope_excludes_call` and lease conflicts to `lease_overlap`. A rejected candidate is never dispatched; `ToolPreflightRefused` records its intent digest and typed `{cause, reason}`, the reason being one of fixed sentences. An earlier hook, review or approval verdict is kept as evidence without granting dispatch. At most one such refusal is admitted per AgentRun; it closes the actor's unstarted proposals and stops its further calls, hooks and Tools, creating no observation, receipt or effect. Rejection after an accepted proposal stops the Run with `proposal_refused`. Cancellation, hook-stop, uncertainty and budget precedence is unchanged.

A researcher batch above the [Tool step cap](../limits.md#max_step_tool_calls) records the same `rejected` / `proposal_refused` record with `InvalidArguments`, starts no Tool and keeps usage; its next request has one cap-aware non-dispatched result per call ID. The refusal ceilings apply to each researcher AgentRun separately; a refusal consumes a turn and Goal call but no Tool-call allowance. Other invalid researcher outcomes stay fatal. Editors keep single-call validation without a refusal continuation.

`RunFinished.failure` is required nullable and present exactly with `Failed`: `provider_call`, `proposal_refused`, `budget_exhausted` (the Goal budget refused the next action), `tool_stopped` (a terminal dropped Tool step, a Guard failure after GO or without proof of non-dispatch, or an unusable Command result), `definition_invalid`, `plan_admission`, `tool_context_full`, `workers_unverified`, `criterion_unmet` or `refusal_limit`. A known recoverable primary Tool denial or failure, including a Guard failure that proves nothing was dispatched, is delivered once as its result and does not by itself produce `tool_stopped`; the next call is a fresh model decision. [Terminal](../terminal/conversation.md#conversation-progress-and-history) owns failure copy and [diagnostics](../diagnostics.md) owns private records.

The primary Run settles once, by one precedence:

1. An [Uncertain](#effect-outcomes) primary Tool observation or hook outcome, or the stopping step's uncertain build-cache publication, journals no terminal Event and is reported unknown. A Run that cannot settle because a reservation, another agent or a primary Tool is still open also journals nothing; it is reported as reopened history projects it (`uncertain` only with an open or unknown effect, budget exhaustion when its counts prove it, otherwise interrupted).
2. Cancellation or pause ends the Run `cancelled`, including during a lifecycle hook.
3. A settled hook stop ends it `stopped_by_hook`.
4. Exhausted active time, or a call or token budget that refused the next action, ends it `budget_exhausted` and records the Goal exhausted once its budget is spent; this outranks `tool_context_full`, `tool_stopped` and `plan_admission`.
5. The stopping step's own cause.

An accepted answer that passed its Stop hooks still finishes when active time runs out after it.

The [Provider encoding contract](../provider/encoding-and-streaming.md#structured-outcomes-and-tool-encoding) owns Tool selection, plain-text answers and structured compaction and review. Responses text parts join in order without inserted or repaired bytes. Explicit commentary may precede the final answer or Tool proposal; refusal, malformed content, unknown phases, ambiguous finals, late commentary and contradictory error or incomplete markers reject. A missing or null phase is valid only for an unambiguous final message or text preceding a call. The ChatGPT route's SSE parsing belongs to the [ChatGPT contract](../chatgpt.md#catalog-and-runs); failure publishes no partial answer.

All adapters reject reported input above the shared input ceiling. Provider-enforced routes reject reported output above the exact request cap; the ChatGPT route caps visible output, so its recorded total (including reasoning) is bounded only by the 1,000,000-token reporting ceiling ([ChatGPT limits](../chatgpt.md#run-limits)). Native OpenAI may keep unknown usage; custom and ChatGPT outcomes require positive labeled usage. Native API-key and custom output caps are remote request controls; the ChatGPT cap is local and cannot bound remote generation or plan consumption. A Tool review ([approvals](../tools/trust-and-approvals.md#folder-trust-and-approvals)) uses Single policy within the aggregate 32-call headroom; uncertainty or failure asks a human and never grants a broader permission.

The Run pins the selected Provider's primary output-token cap. Native OpenAI, Anthropic API and ChatGPT-plan routes declare 32,768 output tokens and exact custom routes 4,096 (ChatGPT counts only visible output; see [Run limits](../chatgpt.md#run-limits)); replay rejects a pinned cap outside 1 to 32,768. Editor calls request 32,768 tokens, narrowed by route binding; researcher calls request 4,096. Native OpenAI, Anthropic and ChatGPT-plan calls have a 600-second<!-- unrelated-bound: native Provider call deadline --> deadline (ChatGPT also has a [stream-idle deadline](../chatgpt.md#run-limits)); custom calls have 120 seconds<!-- unrelated-bound: custom Provider call deadline -->. Each call also ends at the remaining Goal active time. A Tool review reserves 20 seconds plus Store overhead, compaction keeps its 120-second<!-- unrelated-bound: Engine compaction call deadline --> deadline, a tool-free delegation reserves one deadline per wave of concurrent children (at most 20 minutes), and a researcher delegation reserves 20 minutes. The useful answer stays at the 32 KiB<!-- unrelated-bound: assistant and child result cap --> assistant or result bound; the extra output headroom covers Tool-call arguments and reasoning.

Malformed, non-object or duplicate-key MCP arguments, and responses reflecting the selected credential, reject before persistence. A Provider failure stays the call's outcome even when an earlier Tool denial could otherwise continue. Same-route retries follow [Provider reliability](../provider/routing-and-usage.md#usage-provenance-and-reliability); only an explicitly configured [Provider fallback chain](../provider/selection.md#per-role-selection-and-fallback) switches destinations. A lost response can still consume remote usage.

### Effect outcomes

Every dispatched effect (Tool, hook, host operation, Provider setup edit or rewind) settles as one of:

- **Limit**: a bound (deadline, capacity, size or budget) stopped it before any effect, or with a known partial result and no publication; for example a command timeout keeps bounded partial output and publishes no changeset.
- **Cancelled**: cancellation stopped it before any effect, or with confirmed teardown.
- **Failed**: it completed with a confirmed failure (nonzero exit, refused request, API, auth or parse failure).
- **Uncertain**: its outcome is unknown after dispatch: a lost acknowledgement or receipt, unconfirmed teardown, interrupted publication, process death after GO or unconfirmed durability.

Uncertain stops its continuation: no further Provider call, Tool or hook starts for that work, the Run journals no terminal outcome and is reported unknown, and Goal resume is blocked until the user acts. Confirmed Limit and Cancelled outcomes imply no rollback.

No effect is retried automatically. A continuation after a failure is a fresh model decision with fresh intents and preconditions; only Provider calls have bounded same-route retries and fallback, which never redispatch an observed Tool. Tool attempts and results are untrusted historical facts: replay, resume, fork, rewind planning, compaction and archiving never execute a historical intent, complete or roll back an effect, or restore a permission.

A command-generated `ApplyChangeset` correlates to its exact command receipt; one that exceeds the active Goal path scope is denied. Pre-dispatch Guard failure follows the [Tool failure rules](../tools/limits-and-failures.md#limits-and-failure-behavior); once the GO write begins, missing completion is Uncertain.

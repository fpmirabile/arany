# Local coding tools

This contract owns Tool grants, guarded effects, runtime Skills and local MCP. [Terminal](./terminal.md) owns completion, settings and consent presentation; [execution](./execution.md) owns Run coordination and capacity admission. Editing constraints: [security rules](../../agents/security.md).

Arany can continue a primary AgentRun through file operations, commands, portable Skills and local stdio MCP tools. This is an explicit, offline local foundation, not unrestricted host shell access. Every attached startup asks whether you trust the opened folder before account selection or setup, including when no account is configured, unless that exact folder already has remembered trust. This consent flow is the same across operating systems and independent of Provider flags or `--tools`. `/permissions` revisits the choice. Without explicit private Tool configuration, untrusted folders remain read-only. Explicit process selections and headless Runs can opt into reviewed configuration with `--tools`; this flag adds no paid compatibility check.

Folder consent and native Tool capability are independent. On platforms without an implemented enforcer, attached chat remains available without Tools even after trust is remembered. `/permissions` uses the same consent choices; Shift+Tab reports the native restriction without enabling authority. Explicit `--tools` rejects unavailable protection. Trust alone never supplies missing OS protection: only the explicitly approved [primary host commands](#primary-host-commands) and [typed host](#human-approved-host-git) exceptions run outside the Guard, and [in-process file operations](#in-process-file-operations) run only once native protection admits Tools.

The complete harness requires equivalent granted file operations, commands, Skills and local MCP across supported operating systems, with the same permission, isolation, cancellation and durable-result contract. Typed Git reads follow their [per-platform availability](#typed-git-reads). Resource guarantees differ explicitly by native profile as defined below. [Next steps](../../NEXT_STEPS.md#beta-2-and-broader-release) records unperformed native, platform, live and human checks; implemented code alone does not establish platform support.

Native adapters use [automatic Tool selection and plain text answers](./provider.md#structured-outcomes-and-tool-encoding), translating one semantic proposal at a time. Exact custom profiles reject `--tools` because their data-free conformance covers read-only turns. Compatibility with a real selected model requires live evidence.

The generated function and outcome schemas offer file reads and search and only catalog-enabled mutations, commands, Skills, MCP operations, typed Git reads and, with `write`, [typed Git writes](#typed-git-writes). Command, Skill and MCP-server identifiers are constrained to configured names. An unparsable or oversized catalog offers only read-only file operations and the primary's optional plan function. This restriction guides generation; catalog text supplies no execution authority, and the pinned router and Guard independently admit every proposal.

The optional `arany_plan` function records Engine-owned Goal state; it is separate from guarded effect Tools. [Goals](./goals.md#initial-plan-contract-and-success-receipt) owns plan admission, scope, success and replay rules.

## Authority and effect admission

`ToolGrant` is owned by Tools and describes the access a caller supplies for one submission: no grant, the admitted private `tools.json` configuration, or the trusted Workspace grant. The Engine consumes that value when admitting a submission; its variants, validation and authority are unchanged by the ownership boundary. Existing Engine and crate-root import paths remain available.

Each mutation, process, Skill script and MCP call requires typed effects, deterministic restrict-only Policy and effective-capability attestation. Programs run in the separate Guard; typed Workspace file mutations publish in process under the admitted directory capability. Hooks, prompts, command regexes, classifiers and approval UI are not enforcement boundaries. [In-process file operations](#in-process-file-operations) use the same admitted scope and their own execution-site attestation.

An effect is normalized once into an immutable typed intent identifying actor, Run, Tool, resources, operations, destinations, descendant behavior, use count and finite action limits. Policy, approval, journal and Guard share its digest; names, prefixes, hostnames, remembered approvals and summaries never define authority. Tool effects from primary and child AgentRuns pass one deterministic Policy route. [Provider egress](./provider.md#configuration-and-egress) has its own admission under the Provider contract. The [execution contract](./execution.md#collaboration) owns child grants.

Tool intent preflight and replay use one Session-owned reducer validator; the [execution contract](./execution.md#accepted-outcomes) owns its refusal causes and bounded feedback. The Engine retains live catalog, grant, liveness and budget admission. Preflight is read-only and grants no authority; final permission provenance, hooks and host requirements remain mandatory at the folded start.

Execution requires effective capabilities equal to or narrower than the authorized set. Unsupported enforcement dimensions, missing capabilities, failed attestations and authentication, authorization, signature, policy or schema failures reject. Descendants retain or lose authority; there is no automatic unsandboxed fallback. Privileged code never follows or executes filesystem objects created by a less-privileged agent or sandbox without fresh no-follow, handle-relative validation. A process starts from a trusted executable identity without ambient PATH search, with explicit validated arguments, a pinned working directory, an allowlisted cleared environment and closed inherited descriptors and sockets. Scripts require an admitted interpreter policy. Process-tree supervision, cancellation, reaping and release of permits, transactions and temporary resources follow the native profiles and [failure contract](#limits-and-failure-behavior).

## Folder trust and approvals

The consent screen shows the full folder path and vertical Read only / Trust choices, Read only focused. With explicit `--tools`, the first choice instead says Use explicit config and keeps that private configuration when trust is skipped; neither choice expands roots or capabilities. The screen proposes metadata-only runtime/cache selections; toggling one switches to Trust. A discovery failure shows a notice and never aborts startup. Discovery runs for initial consent or when `/permissions` opens; remembered startup revalidates only saved pins, so an unrelated over-limit manager cannot block prompt-free chat. Enter confirms; Escape dismisses without a decision; Ctrl+C exits without saving one. `/permissions` first asks whether to manage folder trust or [typed Git rules](#typed-prefix-rules); folder trust rediscovers candidates, retains exact pins, and permits explicit changes. Checking a toolchain unchecks other selections of its runtime kind; linear `trust` with two of one kind asks again, and `trust N` and `use config` also work. A selection that cannot be saved reports an error and keeps the previous permissions, so startup continues read only. Consent warns that prior versions of files changed by Arany are saved unencrypted in private StateRoot storage. Consent precedes saved-account lookup, catalog or credential access, and Session discovery or creation, for new, resumed and forked entry. Choosing read only, using explicit configuration without trust, or dismissing remembers nothing. Unavailable, malformed or unsafe trust metadata stops startup before account or Session access with a message naming the record and the failed check. An unsupported-version or malformed `workspace-permissions.json` offers Retry, Reset folder trust or Exit, mirroring [history recovery](./terminal.md#acceptance-scenarios-and-evidence-owners); a reset deletes only that record after an explicit confirmation and refuses when the record changed meanwhile. A non-private record or state directory is reported and never reset or modified. Trust is user-owned, shared by conversations, and pinned to the exact absolute path and directory identity; replacing the directory requires trust again, and replay never supplies authority. Remembered grants apply only to native Providers on platforms that admit Tools; custom Providers stay read-only. Explicit private `--tools` configuration takes precedence over remembered trust and keeps its narrower roots and capabilities.

A private `workspace-permissions.json` in the fixed OS-user account root stores at most 128 entries and 64 KiB using owner-only atomic replacement. Versions below its [migration floor](./execution.md#json-record-migration) reject without changing the record, and only the consented reset above removes it. Trust generates a version-1 Tool grant for `workspace_paths: ["."]`, typed writes, discovered project Skills and a pinned resolved system `sh` on Linux and macOS, plus a pinned system Git for [typed Git reads](#typed-git-reads) when one is available. Optional runtime selections bind each exact path, profile kind and directory device/inode to that folder entry. MCP requires explicit private configuration. Standard secret, link and mount exclusions and finite snapshots still apply; `target`, `node_modules`, `.venv` and `venv` are omitted from root discovery and snapshots. Commands use the existing offline Guard, never the host terminal, the whole home directory, package-manager configuration or credentials.

Discovery reads bounded directory entries and executable metadata under `~/.rustup/toolchains`, the per-version Node roots of nvm, fnm, Volta and asdf, and `~/.pyenv/versions`. It never executes a candidate or reads manager or project configuration. Candidates need a numeric `major.minor.patch` directory label; aliases such as `stable` and `nightly` are excluded, and the label is the manager's directory name, not a verified binary version. Python candidates need a version-specific regular executable, or a `python`/`python3` alias to one in the same `bin`; other symlink traversal is rejected. Without an exact saved pin, propose the newest numeric Rust, Node and Python, breaking ties by display order. Saved pins, including stale ones, win. Selected roots mount read-only; their `bin` joins `PATH`. Label, path and device/inode bind policy and candidate tokens; Run/Guard admission and Ready/GO recheck them, rejecting drift before dispatch. Discovery and consent profile numbers use kind order (Rust, Node, Python, Cargo archive/source/index caches, npm cache, pip HTTP/wheel caches, Apple compiler, Apple SDK), then descending lexicographic version label, then ascending absolute path and token. Saved selections retain their pinned grants and are matched by token, never by display position.

macOS Rust also proposes the existing Command Line Tools compiler and newest numeric physical SDK, retaining exact saved pins. The compiler profile is the fixed physical `/Library/Developer/CommandLineTools/usr` root; admission requires root-owned, non-group/world-writable directories, a root-owned `cc` link to `clang`, and root-owned, single-link, executable, non-set-ID and not group/world-writable `clang` and `ld` files. The native signature check must establish that both executables are unentitled; an unknown result is not checked at discovery and the Guard refuses the grant at bootstrap with `ProtectionUnavailable`. Only the selected `cc`, `clang` and `ld` executable paths receive process-exec permission. SDK profiles are exact physical directories named `MacOSX<version>.sdk` under `/Library/Developer/CommandLineTools/SDKs`; versions have two or three canonical numeric components, each in the range 0–65535 with a nonzero major component, and a total length at most 32 bytes. The selected directory and its required SDK contents must be root-owned and not group/world-writable. Compiler and SDK grants each bind their kind, manager, exact path and directory device/inode; the SDK also binds its version. Each is individually deselectable and counts toward the [selected runtime grant ceiling](#limits-and-failure-behavior).

Optional host caches are distinct read-only grants: Cargo's exact `registry/cache`, `registry/src` and `registry/index`; npm's exact `_cacache`; and pip's exact `http-v2` or `wheels` under `~/.cache/pip` (Linux) or `~/Library/Caches/pip` (macOS). Existing caches are proposed only with their runtime; only human Trust saves grants. No parent cache mounts. Consent warns that caches may disclose private package names, source, registry metadata or credential URLs: commands/MCP can emit data into bounded journaled output for later Provider requests. Arany never auto-loads it. Configuration, credential files, environment values and parent directories stay unavailable. A selected read-only host subtree takes precedence for that Run: Arany neither reads it into its private archive nor restores private bytes over it, and it retains earlier Arany-owned entries at that exact subtree when publishing other cache changes. Disabling the opt-in restores the private writable view and those entries. Cache data supplies no authority.

Shift+Tab cycles **Auto edits → Request approvals → Auto approval → Auto edits**, preserving the draft and caret. The current mode appears beside the composer and follows the selected Provider's native capability. Selecting a supported native Provider after trusting an unconfigured conversation restores the remembered mode. Auto edits allows typed edits and asks for commands, MCP calls and Git writes; Request approvals asks for every effect. Reads and Skill or catalog discovery still need the pinned grant but no per-action question. Auto approval uses the selected AI to review the exact proposed action against the current user request and resolves an Ask within the pinned grant, which can add model usage. Uncertainty, invalid output, failure or an exhausted review budget asks the user, as does switching out of Auto while review runs.

A human approval shows the exact proposed action; [terminal approval](./terminal.md#interactive-commands-and-completion) owns layout, focus, labels and linear replies. All pages must be reviewed before accepting. Approval is one-use and never expands the grant. Primary ordinary, hook Ask and unguarded prompts have no wall-clock expiry while their human channel and Run remain live, following [Claude Code ordinary permission waits](https://code.claude.com/docs/en/remote-control#limitations) and [Codex one-shot approval waits](https://github.com/openai/codex/blob/61f34c35af77777db4d77d0ea2aeb8547a6b4523/codex-rs/core/src/session/mod.rs#L2988-L3119). Escape and Ctrl+C cancel the Run; explicit No declines the proposal. Pause, cancellation and actual channel or turn shutdown withdraw pending work. Loss of a delegated Ask's local approval inbox or reply sender cancels the Run; an explicitly delivered unavailable reply from a live channel is distinct from channel shutdown. A missing, invalid or undelivered reply while the Run remains live records unavailable approval, never human decline. A late allow still validates the admitted directory, any explicit file-content precondition, executable bytes, grant/enforcement digests and worker revision before dispatch; no pin is refreshed. Ordinary reads do not pin file content. Permission settings remain the Run snapshot: editing the rules file during a wait applies to later admission, not the pending decision. A child Ask remains pending while its human channel and Run remain live. Its shared delegation and finite Goal active-time allowance pauses during an idle human wait and continues during overlapping sibling Provider, effect, preparation and cleanup work. Exhaustion withdraws the ask before dispatch with the delegation or Goal cause, never as human decline; cancellation and pause win over an accept, and dispatch rechecks the allowance. The non-dispatched observation stores `approval_cause` as `cancelled`, `paused`, `channel_unavailable`, `declined` or, for existing observations, `child_timeout`; active-time withdrawal uses the typed limit and Run stop causes instead. Other observations and histories without the fact carry `null`. Presentation and replay use typed causes, never infer them from output text. Replay never restores a live request. The shared [denial delivery and continuation rules](#permission-modes-rules-and-hooks) apply. Cancellation, pause, hook stop, Uncertain effects, and exhausted or unavailable continuation still stop; completed effects are not rolled back. AI reviews have a 20-second ceiling, a 256-token output cap, no Tools or project instructions, history or includes, and canonical Provider-call usage. They share the primary call budget, preserving final continuation; review text never becomes an assistant answer. Headless `--tools` uses its explicit private upfront grant without an interactive approval channel.

Workspace input resolves one component at a time beneath the pinned directory handle with no-follow semantics. Symlinks, special files, absolute paths, empty components, `.` and `..` reject. Candidates open nonblocking before the regular-file check, and the validated handle is used instead of reopening by path. Folder trust pins the exact path, device and inode in private OS-user state, never in Session facts. A saved toolchain grant for a recreated root is a new candidate.

Each accepted AI review is pinned to its pending Tool in the projection. Ownership is never inferred from adjacent review calls, so an approval-mode change cannot duplicate an integration review.

## Permission modes, rules and hooks

The shared Engine `before_dispatch` evaluates `arany::permissions::PermissionConfig` for primary and researcher Tool steps. Optional `permissions.json` is an authenticated user settings record beside `tools.json` in the admitted StateRoot, outside the Workspace. It uses the same private regular-file, ownership, no-follow and bounded-read admission as `provider-routing.json`; an unsafe or invalid present file rejects Tool admission. Missing settings preserve the existing interactive and headless approval behavior. Repository, Skill, model and hook text never select trust. Parsed settings are immutable data, not executable configuration or a grant. Hook commands run only as [Hook execution](#hook-execution) defines.

Tool admission snapshots the settings once and pins the SHA-256 of the complete settings bytes in `RunStarted.tool_policy.permissions_digest` (`null` when absent). Editing the file does not change an admitted Run. Present settings select the mode and approval path below, including in headless Runs: a required human approval without a channel denies; AI review can use the admitted review Provider. The terminal's existing mode cycle is unchanged when settings are absent.

Every configured step commits its permission verdict in `ToolStarted`, after preparation and approval and before dispatch or its denied observation. The `verdict` field is required nullable: only existing unconfigured pinned-grant steps carry null. A pre-hook, AI review or human approval first commits `ToolProposed` with the immutable intent and crash-charge ceiling; a hook-free single-call step needing none of these commits no proposal. Multi-call proposal ordering follows the [execution contract](./execution.md#committed-event-stream). The proposal advances in place when `ToolStarted` commits, retaining its hook and review evidence. The verdict binds the exact intent digest, effective decision, pinned settings mode, rule/mode/grant basis, final approval and approval source (`rule`, `mode`, `pinned_grant`, `human`, `ai_review`, `unavailable_approval`, `session_approval`, `hook`, `typed_prefix_rule` or `host_prefix_rule`), the narrowest hook restriction (`hook_restriction`, `null` when none) and the number of hooks that ran (`hooks`). The reducer rejects missing, duplicate, wrong-intent or post-observation verdicts and any effect after a denied verdict. An AI preapproval requires a recorded review of that pending Tool. Strict replay consumes these facts without reading settings, rerunning a review or dispatching an effect. The [execution version table](./execution.md#admission-persistence-and-recovery) owns current payload versions; only a [primary host command](#primary-host-commands), primary [typed Git write](#typed-git-writes) or primary [`gh_pr_list` / `gh_pr_view` read](#host-pull-request-listing) without settings at Run start may omit the settings mode. These calls commit a verdict with `mode: null`; the reducer rejects an omitted mode for other calls and for children. Unconfigured primary host commands and typed Git writes use basis `mode` or `pinned_grant` and source `mode`, `pinned_grant`, `human`, `ai_review` or `unavailable_approval`; the reducer rejects hook restrictions and rule, hook, session-scope, typed or host-prefix sources, and rejects unconfigured host or typed-write starts that carry no verdict.

An unconfigured primary `gh_pr_list` or `gh_pr_view` approval requires decision `ask` and source `human`; an `unavailable_approval` denial remains valid. Approval from `mode`, `pinned_grant` or `ai_review` is rejected. A `typed_prefix_rule` approval requires pinned settings and cannot authorize an unconfigured read.

The same settings restrict children; a child cannot select its own settings or expand its read-only spawn grant. Explicit asks go to the human adapter; auto reviews of researcher MCP discovery use the admitted review Provider with the child's exact intent and the Goal objective, within the [shared delegation active-time allowance](#folder-trust-and-approvals) and budget. Tool steps after primary synthesis retain their existing non-review path: required approval goes to a human or denies without a channel, preserving the delegation's reserved synthesis and continuation headroom. Rules never bypass the Goal plan, deterministic Policy, pinned grant or Guard. Denial results use compiled labels such as `permission_rule_denied`, `permission_mode_denied`, `hook_denied`, `user_declined` or `channel_unavailable`; they never copy hook prose, rule text or undisclosed paths. A committed denial reaches its requesting actor once as a correlated Tool result; continuation remains subject to that actor's existing limits. Every new proposal receives a fresh permission check; refusal never retries the effect.

### Modes and approval decisions

The [serve approval transport](./serve.md#server-requests) is another human client of the same approval channel, with negotiated live-session scope for eligible primary host commands. The [ACP adapter](./acp.md#tool-updates-and-permissions) permits ordinary one-use client verdicts, including user-configured client policy. ACP v1 cannot attest a human gesture, so its approval channel disables human-only requests: unresolved host-command asks and hook Asks dispatch nothing, send no permission request and journal source `unavailable_approval`. Host-prefix preapproval follows [Remembered host prefixes](#remembered-host-prefixes); ordinary client policy and `allow_always` supply no host authority. AI review, mode changes and client capabilities cannot resolve those requests.

The peer contract is [Claude Code permission modes](https://code.claude.com/docs/en/permissions#permission-modes). The five accepted spellings are case-sensitive; aliases and bypass modes reject. The parser's omitted `defaultMode` is `default`; it does not change Arany's existing interactive default.

| Mode | Peer behavior | Arany mapping and narrowing |
|---|---|---|
| `default` | Prompt on first Tool use. | Existing `Request`: absent a matching allow, a fresh one-use human approval for each effect needing approval. Remembering Tool use cannot renew an immutable intent. |
| `acceptEdits` | Accept file edits and common filesystem commands in working directories. | Existing `AutoEdits`: typed mutations, including changeset integration; commands, MCP calls and Git writes still ask because process behavior is not a typed edit. |
| `plan` | Explore without source edits; read-only shell commands are available. | Deny mutations and generic command/MCP processes, even with allow rules. Permit admitted typed reads, Skill reads and typed Git reads. Arbitrary argv and MCP metadata cannot prove a read-only effect. |
| `auto` | Classify actions before running without routine prompts; broad execution allows are dropped. | Preserve existing `Auto` AI review for approval-needing calls. Add review for typed Git processes and MCP discovery; every `spawns_process` call and MCP operation requires review. Matching allows never skip it. Existing budgets, uncertainty-to-human fallback and cancellation remain mandatory. |
| `dontAsk` | Deny actions that would prompt; pre-approved actions remain available. | Convert an unresolved `Ask` to `Deny`; permit otherwise admitted no-question calls and matching allow rules. An explicit ask rule still denies. |

Settings and the live terminal mode are independent restrictions: a call asks if either asks, human Request takes precedence over AI review or edit preapproval, and neither can widen a settings Ask or Deny. [Claude Code treats `defaultMode` as the starting mode that Shift+Tab overrides](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in); Arany combines both to preserve its only-narrow guarantee.

`decision(call)` returns only `Allow`, `Deny` or `Ask`. These are approval dispositions within the pinned grant, never executable authority. Invalid or oversized calls deny. `approval_mode(call)` selects human `Request` for an explicit ask rule even under `auto` or `acceptEdits`; only an otherwise unresolved `auto` decision selects AI review. A caller must still journal the exact intent and verdict and obtain deterministic Policy admission before dispatch. Guarded calls additionally require Guard attestation; executed host commands record an `UnguardedReceipt` under [Primary host commands](#primary-host-commands). `Decision::narrow` combines independent restrictions with `Deny > Ask > Allow`; an allow from a hook or review cannot erase an earlier denial or question. A hook's `allow` is ignored because it is runtime program output, unlike a static allow rule from user configuration; only a human or the Auto review resolves an Ask. Children retain the intersection with parent authority. There is no bypass or implicit unguarded execution: `command_unguarded` is never pre-approved by an ordinary allow rule, a mode or AI review; only its separate [session or host-prefix authority](#primary-host-commands) can pre-approve it. `plan` denies it.

**Owner-accepted peer behavior — 2026-10-17:** in `default`, a matching allow rule pre-approves commands and MCP calls without a human prompt or AI review, subject to live terminal restrictions, as in [Claude Code permissions](https://code.claude.com/docs/en/permissions#permission-rule-syntax). This is an explicit user-configured approval, not a bypass of the Guard, deterministic Policy or the pinned grant. Deny and ask retain precedence. `acceptEdits` keeps human approval for commands and MCP calls even with an allow rule; its existing typed-edit approval is unchanged.

[Claude Code drops broad execution allows on entering auto mode](https://code.claude.com/docs/en/permission-modes#how-auto-mode-evaluates-actions), including blanket command rules and wildcarded interpreters. Arany enforces the stricter behavior directly during decision evaluation: `auto` ignores allow rules for processes, MCP operations and calls that already need approval, including bare `Bash`/`command`, `Bash(*)`, `Bash(python*)`, `Bash(python *)`, `:*` equivalents, bare `mcp_call` and whole-server MCP rules. Existing AI review for commands, MCP calls and typed mutations remains mandatory. With settings present, Arany also reviews typed Git processes and MCP discovery; the existing Auto mode without settings keeps its previous scope. Explicit ask rules still select a human and deny rules still block.

**Typed Git prefix rules.** A matching typed `allow` rule skips the approval prompt in Request approvals and Auto edits, as Claude Code allow rules do; the verdict records `typed_prefix_rule`. Settings `default` and `dontAsk` honor it; `acceptEdits` and `auto` ignore local-write allows and ask, live Auto approval keeps its AI review, and `plan` denies writes. Deny and ask rules, in either list, always win over any allow, and a typed rule never overrides an ordinary Read, Edit, path or tool-name restriction. Rules are user-owned configuration: repository content never adds or widens one. See [Typed prefix rules](#typed-prefix-rules).

### Permission rules

The envelope copies [Claude Code settings](https://code.claude.com/docs/en/settings) and [rule syntax](https://code.claude.com/docs/en/permissions#permission-rule-syntax):

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(git diff *)", "Read(./crates/arany/src/**)"],
    "deny": ["Read(./private/**)"],
    "ask": ["Edit(./crates/arany/src/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "/reviewed/check", "timeout": 30}]
      }
    ]
  }
}
```

All fields shown at the envelope and permissions levels are optional with empty lists/maps as defaults. Unknown or duplicate fields, wrong types, unsupported names and malformed rules reject the entire document; no invalid rule is silently skipped. A rule is a bare Tool or `Tool(specifier)`; inner parentheses are literal. Lists are evaluated in deny, ask, allow order, regardless of specificity or input ordering. Within each list there are no exceptions that undo a match.

| Peer Tool | Typed Arany operations |
|---|---|
| `Bash` | `command`; the subject uses its admitted logical program identifier and argv, not an inferred executable basename. |
| `Read` | `list`, `read`, `search`, `glob`; deny and ask also cover `git_status`, `git_diff` and `git_log` paths, Skill files inside the Workspace, and [Git writes](#typed-git-writes): commit paths and potentially covered descendants, and every staged or whole-repository commit and every switch, whose paths are unknown before dispatch. A deny also covers typed mutations and changeset paths to prevent writing through a read denial. |
| `Edit` | `mkdir`, `write`, `edit`, `multiedit`, `delete`, `move`, `apply_changeset`; deny and ask also cover the same [Git writes](#typed-git-writes) as `Read`. |
| `MultiEdit` | `multiedit`; the same Edit-family path rules and read-denial protection apply. |
| `Write`, `Glob` | Bare `write`, and bare `list` and `glob`, respectively; path specifiers reject in favor of `Edit` and `Read`. |
| `Grep`, `Skill` | `search` path and admitted `skill` name respectively. Skill wildcards match names, not authority or resource discovery. |
| `mcp__<server>__<tool>` | `mcp_call` matched against separate server and tool fields; the Tool segment supports `*`. `mcp__<server>` also covers that server's catalog listing and all calls; `mcp__*` covers all servers for deny/ask. |
| Exact Arany catalog name | That operation only, including `git_status`, `git_diff`, `git_log`, `mcp_list` and `mcp_call`. Native MCP operation names accept bare rules only. |

Bare Tool-name `*` globs are supported for deny and ask against peer and native operation names. A non-MCP glob that matches no known operation rejects, preventing silent no-op restrictions. MCP allow rules require a literal server; generic allow name-globs reject. Server patterns are at most 64 bytes and use lowercase ASCII letters, digits, `_`, `-` and `*`; Tool patterns are at most 128 bytes within the complete-rule ceiling. MCP allows compare the parsed server and Tool fields separately. Deny/ask also test the complete peer-name glob against the call or catalog subject, including `__` descendants so the rule can restrict a whole server. This conservatively covers ambiguous server names containing `__` or ending in `_`; an ambiguous spelling may restrict more calls, but never pre-approve them. Tool names supply no authority and matching discovers no servers. A changeset allow requires every path to match the same rule; deny/ask requires any path. Separate allows cannot assemble authority for an otherwise unmatched batch.

Bash patterns follow the peer's [wildcard examples](https://code.claude.com/docs/en/permissions#wildcard-patterns): `*` spans spaces; exact patterns stay exact. A sole trailing ` *` also matches the bare command but keeps its word boundary; trailing `:*` is equivalent. `Bash(*)` equals bare `Bash`. Other characters are literal.

Arany-specific command narrowing: only unambiguous argv words composed of ASCII letters/digits and `_./:@+=,%~-` are joined with spaces for specifier matching. Empty, quoted, whitespace-bearing or shell/control-bearing arguments are opaque. An opaque command cannot match a specifier allow and conservatively matches every applicable specifier deny/ask. A bare Tool rule still covers it. For deny/ask only, the pattern also checks every word-boundary suffix of the joined argv, so `timeout 30 rm x`, `nice rm x`, `xargs rm x` and `env FOO=1 rm x` cannot hide an `rm *` restriction. This is a conservative narrowing: even a word used as ordinary data may trigger a restriction. Allows match only the complete argv projection. Arany does not split shell strings, expand variables or infer commands from scripts as the peer does. This avoids shell parsing becoming an authority boundary; all execution remains under the pinned command grant and Guard. Text matching does not prove an executable's effects, filesystem disclosure or read-only behavior.

File patterns use the peer's [Read/Edit matching depths](https://code.claude.com/docs/en/permissions#read-and-edit) and [gitignore wildcards](https://git-scm.com/docs/gitignore#_pattern_format): `*` and `?` stay within a segment; whole-segment `**` crosses zero or more directories; alphanumeric classes/ranges, class negation and backslash-escaped literals are supported. Bare filenames match at any depth. `/path` and `./path` anchor at the admitted Workspace; multi-segment relative patterns anchor there too. This is an explicit peer divergence for `/path`: Claude Code anchors it at the settings source, while Arany uses its admitted directory capability to prevent settings placement from changing path authority. Unanchored `crates/arany/src/**` matches only root `src` for allow, and a `src` directory at any depth for deny/ask. An explicit `**/src/**` matches at any depth for every list. Deny/ask path patterns compile case-insensitively on Linux and macOS; allow patterns remain case-sensitive. Deny/ask reject non-ASCII pattern literals. Any non-ASCII subject path conservatively matches an applicable restrictive path rule, including changeset and Git paths, closing NFC/NFD and Unicode case aliases without normalization dependencies. This deliberately over-restricts unrelated Unicode paths. Allow literals retain exact Unicode spelling and cannot normalize into a wider match. There is no filesystem access or symlink following; actual filesystem aliases remain outside this matcher, under the separate no-follow grant and Guard, and [result filtering](#permission-rules) applies the same matcher to each result path.

The admitted path vocabulary is Workspace-relative. This slice rejects `//` absolute and `~/` home anchors, traversal, empty components, trailing directory-only slashes, non-segment `**`, unsupported classes and dangling escapes rather than guessing filesystem identities or settings-source roots. Leading comments and gitignore `!` exceptions also reject: restrict-only sources cannot remove prior restrictions. The existing no-follow admission and exclusions still apply. Rules match proposed typed paths, and they also filter results.

A commit path can publish its entire subtree. Read/Edit deny and ask rules therefore also apply when a commit path overlaps the rule's literal directory prefix in either direction. The prefix ends before the first segment containing a wildcard, class or escape; patterns that can start at any depth have an empty prefix and restrict every commit path. This deliberately over-restricts uncertain wildcard suffixes without filesystem access or expanding an allow rule. Staged and whole-repository commits conservatively match every applicable restrictive path rule.

Result filtering follows the peer's [best-effort application of `Read` rules to Grep and Glob](https://code.claude.com/docs/en/permissions#read-and-edit) and its directory listings that leave out the names a rule matches. `list`, `search` and `glob` results, `git_status` and `git_diff` rows and patch sections, and `git_log` commits omit every path for which the same operation on that path would match a deny or ask rule that the call itself did not match. A rule that matched the call either denied it or was approved for it, so an approved `search` of an asked directory shows its rows while a broader call hides them: an approver never saw paths the call did not name. The matcher is unchanged, including case folding and the conservative non-ASCII match, so while any restrictive path rule applies, a broader call's results drop every non-ASCII path. A covered directory covers its whole subtree, so Workspace walks prune it before opening it and Search never opens a covered file; a private worker filters its in-memory image the same way. Filtering precedes ordering, row and byte fitting, `limit`, `offset`, `next_offset` and `truncated`, so pages and truncation count only visible rows. The Engine sends the restrictive patterns to the Guard in its task, where Git output is filtered before fitting. Every patch section starts hidden and only a `diff --git a/P b/P` or combined `diff --cc P` header, or a staged `* Unmerged path P` line, naming a visible unquoted path reveals it, so conflict sections, unrecognized or quoted headers and a line cut by the capture limit fail closed. A collapsed untracked directory row such as `dir/` names only that directory and is hidden when a rule covers it. The view config sets `core.quotePath=false`, so Git quotes only names with control characters, `"` or `\`, and those stay hidden. A filtered `git_log` reads changed paths (`--name-only` without rename detection, so a move reports both sides, and merges against their first parent) for at most 1,000 commits, keeps only commits that change a visible path, then applies `max_count`; a commit with no path evidence is dropped, and an exhausted scan sets `truncated`. Subjects of kept commits are shown even when they also change covered paths. Git failures follow the [typed Git disclosure policy](#typed-git-reads). Git's own [capture bound](#limits-and-failure-behavior) still counts covered output, so a capture overflow keeps `truncated` true. A Skill file inside the Workspace is also a file read: a `skill` call takes the stricter of its own decision and a `read` of that file's Workspace path, and a Skill whose `SKILL.md` a restriction covers is omitted from the catalog, so its description is never previewed. The verdict is journaled before dispatch, so a denied Skill file is never opened; the read path checks the pinned grant and file digests. Rules do not filter explicit includes, interpreter I/O or subprocess filesystem access; that disclosure remains bounded by the independent grant and Guard, and this config API is not an OS path filter.

### Hook execution

The envelope and nested groups copy the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#configuration) and [command fields](https://code.claude.com/docs/en/hooks#command-hook-fields). Accepted events are exactly `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop` and `PreCompact`. Groups contain a `hooks` array of command handlers, an optional matcher, and no other fields. Handlers accept `type: "command"`, a nonempty `command`, optional `args` and an optional integer `timeout` in seconds. Omitted `args` retains shell-form text; a present array, including `[]`, retains exec form. Nothing is interpolated or resolved; all five events execute at the Engine sites below.

Matchers absent, empty or `*` select every occurrence. The peer's exact-name/`|`/`,` alternatives are copied; other patterns use an unanchored regex. Arany narrows regexes to the bounded finite-automaton syntax: JavaScript lookaround/backreferences and oversized compiled patterns reject. Tool events must use `matches_tool` so invalid or ambiguous calls cannot evade a hook; other events use `matches` on their event-specific subject. Tool matching uses canonical peer names above, including actual `mcp__<server>__<tool>` call subjects and `mcp__<server>` catalog subjects; `SubagentStop` matches agent type and `PreCompact` matches the trigger (`manual`/`auto`). `Stop` accepts only match-all: a filtering matcher rejects instead of the peer's silent ignore. An MCP server name containing `__` produces a blocking Tool-subject error rather than an ambiguous canonical name; native MCP rules still compare typed fields. A present `null` is invalid, not an omitted field. Empty handler groups, other events/types, async handlers and extra execution options reject.

**Recorded owner decision — 2026-10-17:** hook commands run inside the Guard like every process, under pinned interpreter/executable identities, an explicit environment and typed grants. Arany copies Claude Code's hook protocol: events, matchers, JSON on stdin, event-specific exit-2 blocking, `permissionDecision` `allow|deny|ask` and timeouts. The peer divergence is execution authority: [Claude Code command hooks run with full user permissions](https://code.claude.com/docs/en/hooks#security-considerations); Arany requires Guard isolation because of its [Per-effect isolation security guarantee](../../AGENTS.md#non-negotiable-guarantees). Descendants cannot gain authority, and repository or hook output cannot select trust.

An ignored hook failure remains `Ignored`, with bounded diagnostic feedback. It never creates a host-command offer or an escape-only Stop/PreCompact continuation. A primary may independently request a fresh [host command](#primary-host-commands); its result cannot replace the recorded hook verdict.

**Delegated Tools.** Like Claude Code, researcher and editor Tool calls trigger the same configured PreToolUse and PostToolUse hooks as primary Tools. Hook intents and Events retain the child's `agent_run_id`; admission reserves their complete bounded tail, and execution stays within the shared delegation active-time allowance. Denial and feedback apply to that child's Tool. Delegated calls are never rewritten. Unknown hook outcomes stop the Run without retry, and completed Workspace publication remains recorded if a post hook stops the Run.

**`PreToolUse` command hooks.** After the permission decision and the live terminal restriction, and only while the decision is not `Deny`, a Tool step runs its matched handlers one at a time in configuration order. Each handler is a journaled `Command` effect with the Guard's offline, private-Workspace-view, explicit-environment grant of any model command: `HookStarted` commits the immutable hook intent, the exact-stdin digest and the pending proposal's digest; the Guard runs it; `HookFinished` commits the Guard observation (receipt included) and the parsed result; then the verdict follows. Shell form runs the pinned `sh` as `sh -c <command>`; exec form runs `command` as a pinned program name with `args`. A program that is not pinned, a matcher error or more matched handlers than the limit below denies the pending Tool before any hook starts, with reason `hook program is not pinned`, `hook configuration blocks this Tool` or `hook limit`. Handlers after a denial do not run. Internal Engine preparation calls over snapshot-pinned input (agent definition parsing) are never model Tools: no hook sees or narrows them, and they widen nothing.

The hook receives one JSON object on stdin (closed field set): `session_id`, `cwd` (always `/workspace`, the Guard view, never a host path), `permission_mode`, `hook_event_name`, `tool_name` (the peer name), `tool_input` (the typed call) and `tool_use_id`. Exit codes and output follow the peer: exit 0 with empty or non-JSON stdout adds nothing; exit 0 with a JSON object may carry `hookSpecificOutput` (`hookEventName` must be `PreToolUse`) with `permissionDecision` and `permissionDecisionReason`, the legacy top-level `decision: "block"` with `reason`, or `continue: false` with `stopReason` (stops the Run before dispatch, taking precedence over `decision: "block"`); exit 2 denies and its stderr is the reason; any other exit is a non-blocking failure. Unknown fields are ignored, and stdout is never interpreted as instructions. Hook output is evidence and a reason string only: reasons are control-stripped and truncated to the reason limit below. Model and history projections use `hook_denied` and exclude the reason text, including for older committed observations and compaction summaries.

A Guarded Command that is not a hook reads an empty stdin (immediate EOF), like the unguarded executor.

The verdict records `hook_restriction` (`null`, `ask` or `deny`) and `hooks` (handlers that ran). The reducer requires every started hook to be finished before the verdict, `hooks` to equal the journaled count, `null` only when no hook restricted or stopped, `ask` only when the fold is `Ask`, and `deny` only for a `Deny` fold, a stopped hook or a denial before any hook ran. A `Deny` hook verdict has basis and source `hook`; a hook `Ask` over an `Allow` has basis `hook` and is resolved by the human, never by AI review. Unknown outcomes stop continuation: a hook whose observation is `Uncertain`, cancelled or unattested is recorded and blocks resume like an uncertain Tool.

Hooks have at most 64 groups and 128 handlers across all events. Matchers and match subjects are at most 1024 bytes and control-free. Subject overflow, controls or an invalid Tool call return an error, not a non-match; callers must block the pending action on this error and cannot skip the hook. Commands are at most 4096 bytes; tab/newline are permitted as inert command text, other controls reject. Exec form has at most 64 arguments of 4096 bytes each, without NUL, within the aggregate document limit. Hook timeout is 1–600 seconds, default 600; the finite maximum is an Arany narrowing. Each regex has a 128 KiB compiled-size ceiling, a 32 KiB DFA cache and 32 nesting levels. All overflow rejects, with no truncation, partial config, retry or fallback. Errors identify the list/index or hook constraint without echoing command/rule text.

Hook limits: at most 8 matched handlers per occurrence; stdin at most 32 KiB, including the complete `tool_input`: a matched `PreToolUse` or `PostToolUse` set that cannot receive the whole call, such as a valid Write, Edit or MultiEdit carrying more than about 32 KiB of content, denies the Tool before any handler or effect (`hook input exceeds its limit`, zero handlers), never truncating or hashing `tool_input`, bypassing the hook or retrying unhooked; the complete Guard task of every matched handler must encode within the Guard task ceiling before any hook starts, else the Tool is denied (`hook input exceeds the Guard task limit`) with no `HookStarted`; a 32 KiB result with each stdout/stderr capture capped at 16 KiB minus 128 bytes (overflow fails closed); runtime at most the handler `timeout` and the remaining Goal active time, never less than 1 s (the Goal ledger refuses a start that does not fit); reasons control-stripped and truncated at a UTF-8 boundary to at most 1 KiB; admission of a Tool step reserves two Events and one observation per matched handler, and the Tool's authorization lifetime and active-time ceiling grow by the handlers' worst case, clamped to the remaining Goal active time (unbounded Goals keep the full worst case). Hook time is Goal active time. Descendants are reaped by the Guard on timeout.

**`PostToolUse` command hooks.** After a primary or delegated Tool completes with a `Succeeded` observation, its matched `PostToolUse` handlers run one at a time with the same Guard grant, bounds and `HookStarted`/`HookFinished` pair as `PreToolUse` (`HookStarted` requires that committed observation, the Tool's digest and directly follows the Tool's latest journaled step: a Command's hooks run after its changeset integration commits, so the hook sees the published tree (a worker command's hook instead runs after its private seal and sees the host Workspace, never the private view), and no Provider call, compaction or other Tool may sit between the Tool and its hooks). In a concurrent in-process read step, sibling read and admission Events may intervene: read post-hooks run serially in observation completion order after that step's admissions and dispatched reads settle, before any non-read call or Provider reservation. Each source has one contiguous set of distinct handlers in configuration order. Each deferred hook still binds its source digest in the current step; another step cannot reopen it. The hook cannot undo the effect, and its Workspace changes are discarded like any hook's. Failed, denied, uncertain and internal Engine calls run no `PostToolUse` hook. Stdin adds `tool_response` to the `PreToolUse` field set: the observation's model-facing projection, replaced by `{"truncated": true, "text": <prefix>}` when the input would exceed the stdin limit, with the prefix halved (down to empty) until every matched handler's Guard task fits, so on macOS a hook can receive less than 32 KiB. Exit 2 (stderr) and `decision: "block"` with `reason` become feedback; `hookSpecificOutput` (`hookEventName` must be `PostToolUse`) with `additionalContext` becomes feedback too; any other exit is a non-blocking failure, and a timeout or output overflow becomes the feedback `hook limit reached`. Feedback strings use the reason bound below. On exit 0, `continue: false` takes precedence over feedback and records `stopped` with optional `stopReason`; remaining handlers do not run. Its terminal behavior belongs to [Run outcomes](./execution.md#accepted-outcomes). `updatedToolOutput` and other fields are ignored: hook output never replaces an attested observation. An `Uncertain`, cancelled or unattributed unattested hook stops the Run after the Tool effect without retry; the typed pre-dispatch bootstrap exception above stays `Ignored`, the observation stays committed and the next Provider call does not start.

PostToolUse feedback is stored only in the journaled `HookFinished` result (a `feedback` result with a `lines` list); the reducer requires the recorded result to equal the deterministic parse of the hook's observation for its event. The model-facing Tool result gains a `hook_feedback` list of lines `hook feedback: <text>` (at most 4 KiB in total, later lines dropped), derived from the live results and, after resume or in history, from the journaled ones, so the same prompt bytes result. A step that matches either Tool hook set reserves twice that room (JSON escaping) in the context budget, and `PostToolUse` handler time extends the active-time ceiling but not the Tool's authorization lifetime. Because a `PostToolUse` handler cannot be refused after the effect, a Tool whose `PostToolUse` handlers are unpinned, over the matched-handler limit, unable to encode their Guard task or stdin even with an empty truncated response is denied before dispatch with the `PreToolUse` reasons.

**`updatedInput` narrowing.** `updatedInput` must be a complete, valid Tool call (the shape of `tool_input`); anything else denies. A replacement narrows only when it is: a `read` of the same path whose offset and end lie inside the original window; a `glob` with the same normalized pattern, an equal or lower limit and an equal or subtree path; a `list`, `git_status`, `git_diff` or `git_log` whose path equals the original or lies beneath it by whole path segments (a root original admits any path), with the Git reads keeping every other field; or a `search` keeping its query, `regex`, `include` and `case_sensitive` after default normalization, whose page lies inside the original row window (`offset` through `offset + limit`) for the same path, or whose path lies beneath the original's with no include, both offsets zero and a limit no larger (a subtree renumbers its rows, and an include would match relative to the new path). Parent paths, `..`, case or symlink variants, a larger window or glob limit, a changed query, glob pattern, matching mode, include or case and every `command`, MCP, Skill, `write`, `edit`, `multiedit`, `mkdir`, `apply_changeset` or internal call never narrow (a changed argv or content has no provable order; the model must propose it as a new call). The replacement must also be at least as restrictive as the original under the pinned rules and be within the pinned grant. `HookFinished` journals every valid-shaped update outside an `ask` decision (which keeps the original input) as a `narrowed` result carrying the call, but only the verdict's `narrowed` flag records that the Engine accepted it. An update identical to the current call is a no-op (the call proceeds as is and the hook restricts nothing, so idempotent clamping hooks work). An update refused by `narrows`, the pinned rules or grant, or the per-step limit denies with the matching reason and a false flag. `ask` together with `updatedInput` keeps the ask on the original input (the update is dropped, the human decides). On an accepted narrowing the original Tool is `Denied` with basis `hook`, the verdict flag set and the model-facing line `Hook narrowed this Tool to: <tool_name>`; it does not answer the request, and the next Tool of that step must be exactly the replacement (a new `ToolStarted` intent), so a later step requesting the same call is an ordinary request. `PreToolUse` hooks run again for the replacement; at most one narrowing per step, so a second one denies (`hook narrowing limit`). The model receives one Tool result for the request, built from the replacement's observation; the original's denial line arrives as a separate `hook_narrowing` data block. Internal Engine calls and delegated research are never narrowed. Step admission reserves the replacement's Events and observations.

**`Stop` and `SubagentStop`.** A primary answer runs `Stop` before `AgentFinished`. A researcher or editor answer runs `SubagentStop`, matched against its definition name (or the explicit role fallback `researcher` / `editor` if no definition is loaded), before the child's `AgentFinished`. Both receive `stop_hook_active` and `last_assistant_message`, truncated at a UTF-8 boundary to fit the stdin and Guard task ceilings of the Hook limits. Exit 2 or `decision: "block"` records `blocked` with a bounded reason. On exit 0, `continue: false` takes precedence over `decision: "block"`, journals `stopped` with optional `stopReason` and skips remaining handlers; [Run outcomes](./execution.md#accepted-outcomes) owns terminal settlement. On a block, the accepted assistant turn and a user-data block labelled `stop_hook_feedback` are appended to the next request; the next primary call uses ordinary Goal Provider-call admission; exhaustion ends the turn with the existing budget outcome. A child re-prompt stays inside its original delegation deadline and turn ceiling; a stopped editor retains its landed Workspace effects and releases its lease through the [editor lifecycle](#editor-tool-steps). **Continuation cap:** at most eight blocked continuations are admitted per actor in a Run, counting every blocked Stop whatever Tool calls sit between them (they never reset the cap or `stop_hook_active`), so their feedback stays within 8 KiB (eight reasons at the Hook limits' reason bound); after the cap a valid answer completes without another Stop invocation. Internal Tool calls never trigger hooks.

**`PreCompact`.** Before an active-Run compaction reservation or an idle Session compaction, matching handlers receive `trigger` (`manual` or `auto`) and empty `custom_instructions`. A block skips the compaction and makes no compaction Provider reservation; `continue: false` stops an active Run before the compaction reservation, or stops only the compaction when idle. Cancellation during an active-Run hook with a known outcome cancels the Run before any compaction reservation; an unknown hook outcome leaves the Run interrupted with an uncertain stop under [Run outcome precedence](./execution.md#accepted-outcomes). A manual `/compact` that a hook blocked fails with `CompactionBlockedByHook`, distinct from an empty input. If retained context still exceeds its limit, the existing context failure applies. Each trigger/call-index occurrence runs once; a retry at the same call count reuses the recorded outcome (a recorded block still blocks, a recorded pass proceeds) and never reruns the hook. Idle compaction re-admits the current private configured or remembered folder grant only if its digest and the permissions digest match the Run's pins; changed or unavailable admission fails closed. Between Runs of an open Goal, hook start reserves a durable active-time ceiling and completion settles elapsed time; outside an open Goal the handler keeps its finite timeout and Guard limits.

Lifecycle hooks use the same pinned programs, Guard, sequential execution, Hook limits, fail-closed Limit and uncertainty handling as Tool hooks. An invalid program records the offending handler's own call as a denied intent that was never dispatched; matched-handler overflow uses the first handler configured for the event and stdin that cannot fit the Guard task uses the first matched handler. Each selected call carries the reason as output and the result is `Blocked` with that reason, before any process runs. A SubagentStop shares its delegation, so admission reserves the actor's researcher or editor settlement tail rather than the primary's; a cut-off or cancelled SubagentStop ends that child (cancelled when the user cancelled, otherwise failed under that child's C1-fatal or C2-local failure policy) without declaring the Goal budget exhausted; the editor's closed failure cause follows the [worker outcome contract](./execution.md#worker-journal-protocol). An unknown outcome stops the Run as `Uncertain`. Replay binds Stop subjects to `(agent_run_id, provider call index)` and PreCompact subjects to `(trigger, provider call count)`. A Stop occurrence immediately follows its accepted Finished call; a blocked Stop forbids successful Agent completion until a new primary/child call is recorded. Each continuation re-renders the answer turn, which counts toward the Tool context and its compaction trigger, and a context without room for it refuses with `ContextTooLarge` before any hook journals. Open or Uncertain hooks block continuation and resume; strict replay consumes recorded facts without executing hooks.

### Supervisor adapter

The Engine owns the bounded Supervisor evaluation state and calls one pure, deterministic evaluator over committed reducer facts. The RunLoop applies a closed decision to journal a verdict or continue without one; the reducer only projects recorded verdicts and validates their shape and placement. Tool-enabled Runs pin `config.supervisor = {evaluator: 1, window: 32, floors, candidates, digest}` in `RunStarted`; Runs without Tools pin null. The field is required. The SHA-256 digest binds the domain `arany.supervisor.policy.v1`, evaluator, window and both closed threshold structs. There is no configuration file, model call, clock, I/O, network, Guard task or journal subscriber. Repository text, model output and hooks cannot select thresholds. Shadow mode is always on in production and never changes permissions, catalogs, approvals, continuation, integration, Run outcomes or model input.

A boundary follows every model `ToolFinished`, including editor Workspace effects and known denials/failures. A primary command carrying a nonempty validated changeset uses `command_capture`; invalid/deferred Provider results and blocked Stop/SubagentStop use `stall`. Internal definition parsing and changeset integration are excluded. Serialized worker-capture/handover sites remain bounded vocabulary; current live histories reject their source transitions.

Each actor has an independent last-32-boundary window in its Run (at most nine actors). The oldest step is evicted whole on the 33rd boundary; a new Run starts empty. All feature counts saturate at 65,535; ratios use saturating integer arithmetic, floor division and a denominator of at least one. Keys are SHA-256 over domain `arany.supervisor.call.v1` and canonical typed calls; Write/Edit content fields are replaced by SHA-256. Intent, actor and Run IDs, expiry and target revision are excluded. Outcome equality binds disposition, closed enforcement cause, exit class (zero/nonzero/unknown) and SHA-256 of the model-facing result without its call or target. No prose is parsed to invent denial classes. Policy/plan/grant/lease/permission/hook denials count as refusals; closed `filesystem_denied` enforcement counts as a path-admission rejection. Ordinary nonzero exits do not count as probing.

| Signal | Features | Notice floor | Would-narrow candidate |
|---|---|---|---|
| Loop | Identical `(call, outcome)` suffix; same-call non-success suffix; greatest whole suffix cycle repetitions for lengths 2, 3 and 4 (shortest length wins ties); maximum per-path returns to a prior after-digest following a different digest; stall boundaries since the last succeeded observation | identical 3; failing 2; cycle 3; oscillation 1; stalled 2 | identical 4; failing 3; length-2 cycle 3, other cycles 5; oscillation 2; stalled 3 |
| Probing | Refusal suffix; refusals in window; distinct refused call keys; closed path-admission rejections | streak 2 or alias 1 | streak 3, or distinct 3 with window 4, or alias 2 |
| Disproportion | Files, deleted files, ceil(decoded before+after bytes / 1024), declared roots (minimum 1), nullable base KiB (currently null), files/root, deleted/files permille, nullable changed/base permille (currently null) | files 16, or deletion 250 permille with files/root 4 | files/root 8 with files 32; deletion 500 permille with deleted 8; growth 4000 permille with changed 64 KiB |

Loop and probing signals are evaluated at `tool_outcome`, `command_capture` and `stall` boundaries only, and are journaled only when the subject is itself in the signal's evidence, so one crossing yields one verdict rather than a notice at each later boundary; disproportion is evaluated at every capture. A candidate hit has level `would_narrow`, otherwise a floor hit has level `notice`; both meet the minimum journaled notice level. Candidate responses are loop `pause`, probing `revoke`, disproportion `require_approval`; notices have null response. These are calibration candidates only. Disproportion uses validated command changeset facts and declared lease/plan roots; base/growth features are null without a base. Live editors supply no private capture or handover boundaries. Each signal retains at most eight increasing subject sequences as evidence. Edit equality retains only hashed path/after-digest pairs, at most the existing 2,048-file capture bound per step and 589,824 pairs per Run (36 MiB of pair data), never contents. Eviction removes the oldest step and its pairs together. Per-boundary work is bounded by the 32-step window and those existing finite capture bounds; no work or allocation grows with Session history. The evaluator has no fallible external operation; an implementation panic fails the coordinator through its existing failure boundary.

The RunLoop commits a nonempty `SupervisorVerdictRecorded` as its own Engine decision immediately after its subject, before hooks, integration, stop facts or any other continuation. A failed or unknown verdict append stops continuation; it never permits an uncommitted verdict to be treated as recorded. Its closed payload carries `subject_sequence`, `site`, `evaluator: 1`, `mode: shadow`, one to three signal entries (`signal`, `level`, nullable `would_response`, fixed feature struct and evidence) and `capped`. It contains only integers, booleans, enums and sequences. The [execution contract](./execution.md#persistence-bounds) owns the 2 KiB payload and 256-verdict Run cap. Evaluation continues after the cap without journaling. No verdict enters compiled context, compaction input, Provider input or diagnostics. [Serve](./serve.md#notifications-and-items) forwards this canonical, privacy-reduced verdict, including features and evidence that contain counts, sequences and closed enums, never paths or content. [Terminal](./terminal.md#conversation-progress-and-history) and [telemetry](./telemetry.md#spans) own their further-reduced fixed-vocabulary projections; the calibration corpus below owns its separate privacy contract.

Replay accepts recorded decisions without reevaluating the Supervisor or executing any historical Provider, Tool, hook or Guard action or reading configuration. It validates the closed payload, supported evaluator and pinned Supervisor, Run and actor scope, eligible adjacent subject and site, evidence shape, verdict cap and cap marker. Malformed, duplicate or misplaced verdicts reject. A well-formed, correctly placed forged verdict is accepted even when the evaluator would produce different features, level, response or evidence, or no verdict at all. Replay does not infer a missing verdict from the evaluator. An interrupted prefix ending immediately after a subject remains valid; later recovery starts fresh windows in a new Run. A different feature definition requires a new evaluator version under the current-format rule; threshold changes stay pinned data. Replay does not prove evaluator provenance, and the journal is not tamper evidence. No recorded verdict grants execution authority.

`arany show --output supervisor-corpus SESSION_ID` exports a local calibration corpus after strict read-only replay. It takes the existing Session lock nonblockingly for the entire read, refuses an active operation or an absent/unsafe lock, and neither creates lock files nor changes journal bytes. It opens no Workspace, reads no credentials or runtime configuration, and performs no Provider, Tool, hook or Guard call. Fork references and inherited history undergo the same strict validation as ordinary replay; records describe the selected Session's direct evaluation boundaries. Interrupted closed prefixes are valid. Invalid history emits no corpus.

The stdout format is JSONL, one header followed by one record for every evaluation boundary, including negatives and boundaries after the journal's verdict cap. The header has `format: "arany.supervisor.corpus.v1"`, `evaluator: 1`, `session_ordinal: 1`, `runs` and `goals`. Each Run entry contains its one-based `run_ordinal`, closed `outcome` and nullable `policy` with its pinned evaluator, window, floors and candidates; the policy digest is omitted. Run outcomes are `completed|failed|cancelled|stopped_by_hook|interrupted`; unfinished prefixes use `interrupted`. Goal entries contain a one-based `goal_ordinal`, `run_ordinals` and `outcome: completed|failed|interrupted|budget_exhausted`. A budget-exhausted Goal remains distinguishable from another failure.

Each record contains `run_ordinal`, the journal's zero-based `actor_ordinal`, closed `role`, `site`, nullable catalog `operation`, nullable `disposition_class` and closed enforcement `cause_class`, `features: {loop, probing, disproportion}`, nullable `journaled_level`, `salted_call_key`, `salted_outcome_key`, one-based `relative_step`, and `labels`. The feature structs are exactly those defined above, recomputed over the same actor window; disproportion is null outside capture sites. Operation, disposition and cause describe Tool observations and are null at other sites. `relative_step` counts all boundaries in that Run in journal order. `journaled_level` is the greatest level in the matching committed verdict, or null when no verdict was committed (negative, capped or interrupted prefix); it is not a fabricated verdict. Labels are booleans `pause_or_cancel`, `steering` and `goal_failed`, set when the corresponding committed cancellation, steering note or failed Goal follows within three subsequent evaluation boundaries of the same Run (including immediately after the subject). The journal does not distinguish a user pause from Ctrl+C, so the combined cancellation label makes no such inference; crash interruption is not a cancellation label.

Corpus privacy is an allowlist: only the fields above are serialized, with no objectives, paths, argv, file content, model text, UUIDs, timestamps, account data, raw hashes or policy digests. Call and outcome equality keys are HMAC-SHA-256 of the evaluator's normalized keys, with separate corpus domains and a fresh cryptographically random 32-byte secret salt per export. The salt is never exported or persisted. Equal keys remain equal within one export, but a new export changes every key while keeping other fields stable. Row ordering, ordinals and feature patterns stay observable across exports; only equality keys are unlinkable. Feature patterns and outcomes can still identify similar trajectories; the corpus is privacy-reduced, not an anonymity guarantee. No export is uploaded; owner labels are added offline to a copy, and threshold sweeps use the feature columns without re-execution.

An export holds at most 10,000 records and emits at most 8 MiB, including its header and newlines. The [lineage replay cap](./execution.md#persistence-bounds) also applies before corpus collection. Record or byte overflow refuses the whole export with record and serialized-byte counts, never truncation or partial stdout; replay-limit refusal uses the existing history-limit error. Corpus buffers, ordinal metadata and label tracking are bounded by those Event/record limits, the fixed record schema and a four-boundary label window. Random-source failure fails closed. The corpus grants no enforcement authority; calibrated enforcement and owner overrides remain separate work.

Peer mechanisms: [OpenHands](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py) supplies ID-free action/observation equality, four identical steps, failure streaks and alternating cycles; [Gemini CLI](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts) supplies hashed calls and short cycles; [Goose](https://github.com/aaif-goose/goose/blob/main/crates/goose/src/agents/agent.rs) places repetition checks in the pre-dispatch inspector seam; [Claude Code hooks](https://code.claude.com/docs/en/hooks) supply the restrict-only adapter shape. Arany diverges by journaling shadow candidates before enforcement, using bounded per-actor windows and excluding LLM judges. Engine ownership follows the recorded Engine-side gate shape of Claude Code hooks and Codex approval policy; replay accepts the recorded decision. Enforcement, durable pause/revoke and human-only overrides require later calibrated owner approval; this adapter applies none of them.

Evidence owners: [pure signal corpus](../../crates/arany/src/supervisor/tests.rs), [reducer corpus](../../crates/arany/src/session/reducer/tests.rs), [Event corpus](../../crates/arany/src/session/events/tests.rs), [Engine Goal corpus](../../crates/arany/tests/engine_run/goals.rs), [Goal recovery corpus](../../crates/arany/tests/engine_run/recovery.rs), [corpus show journey](../../crates/arany-cli/tests/session_run/supervisor.rs), [export-bound corpus](../../crates/arany/src/supervisor/corpus.rs) and shared `assert_action_bounds`. They own signal thresholds/cycles/oscillation/saturation, accepted recorded/forged verdicts, malformed/duplicate/misplaced rejection, capped/interrupted prefixes, commit-before-continuation, closed decoding and unchanged model observations and accepted output with an all-off test pin. The [Execution scenarios](./execution.md#acceptance-scenarios-and-evidence-owners) assign those requirements. The evaluator is platform-independent; native journeys establish platform support separately.

## Private grants

Put an owner-only `tools.json` beside the admitted Session database, outside the Workspace. Its directory must be private (`0700`) and the file must be regular, single-link, no-follow, current-user-owned and `0600`. `--state-dir` selects this Session and configuration root; it does not move your saved account. Permissions are not encryption or protection from another process running as the same user.

A minimal file-only configuration is:

```json
{
  "version": 1,
  "workspace_paths": ["src", "Cargo.toml", "Cargo.lock"],
  "write": true,
  "commands": [],
  "skills": [],
  "mcp": []
}
```

Use exact, nonoverlapping relative files or directories. The singleton `["."]` selects the whole project under the same exclusions and bounds; mixing `"."` with other roots rejects. List, search and command working directories accept `"."` or an empty path for the project root; mutations still require a named relative path. Absolute paths, traversal, links, mount crossings and special files are not admitted. StateRoot and the fixed account root must not overlap the Workspace or configured runtime resources. `.git`, `.env`/`.env.*`, `.aws`, `.ssh`, `.gnupg`, `.npmrc` and `.pypirc` path components are excluded. Repository history is reachable only through [typed Git reads](#typed-git-reads). This is not a universal secret detector: review the files you select. Tool observations can be sent to the selected Provider and persisted in the private, unencrypted journal.

The Linux profile exposes the system `/usr` tree read-only as its runtime. Workspace, StateRoot and account roots must not overlap it, since a private file inside a runtime mount stays visible to a same-user payload. This authorizes no home or unselected cache mount.

The offline profiles deny network, named Unix socket creation, connect, bind, listen and destination-bearing sends; a network namespace alone would leave pathname sockets in visible runtime trees reachable. Anonymous pipes and anonymous socket pairs stay usable: Linux pairs cannot rebind or send to named destinations, and macOS denies pair writes, so payloads cannot depend on socket wakeups. `sendmsg`/`sendmmsg` descriptor passing is unsupported. This is not a network-capable test profile.

JSON has a closed versioned schema: all six listed top-level fields are required, the optional `git` field pins [typed Git reads](#typed-git-reads), the optional `git_identity` `{name, email}` is the [commit identity](#typed-git-writes), and optional `child_unguarded` accepts only `denied`; children never receive [host authority](#primary-host-commands); unknown and duplicate fields reject. Private configuration has no interpolation, automatic installation or hidden executable lookup. Project Skill discovery stays within its selected Workspace roots. Where commands are supported, folder trust pins the resolved system shell rather than looking up arbitrary commands on PATH. Configuration is pinned for a Run; editing it does not cancel an admitted Run. Changed pinned executable or resource contents reject dispatch rather than being silently trusted.

## Enforcement failure causes

`ToolFinished` and `HookFinished` record an optional closed `enforcement_cause` separately from the disposition and untrusted output. `filesystem_denied` means the typed file boundary or command snapshot capture explicitly rejected a protected path component or set-ID entry metadata. It requires an execution attestation and a `denied` disposition. `guard_bootstrap` means the trusted controller observed a typed Guard bootstrap error at the RuntimeMounts, Capabilities or Handshake sandbox-setup stage before GO dispatch: it requires `failed`, no execution attestation and a Guard-site intent. This known pre-dispatch failure permits continuation; it never converts an unknown dispatched outcome into a retryable failure. Ordinary errno, diagnostics and program output cannot set either cause. Resource limits, cancellation, uncertainty and successes cannot claim a cause.

A runtime mount-topology refusal reported as a typed bootstrap failure before Ready and GO on Linux or macOS is `guard_bootstrap`: the next model request may receive that failed, unattested observation. This continuation grants no authority and dispatches no retry; the primary may independently request a fresh host command. Once GO begins, a missing completion remains uncertain and cannot use this exception.

Shared file readers and resolvers retain their existing errors, so unsupported Git layouts, ordinary path validation, non-regular or multiply linked files, unsupported changeset type conversions and opaque filesystem errors remain unclassified. Classification changes no grant or approval, and never retries anything.
The cause carries no path, filename, contents or native diagnostic text. Its size is fixed by the enum, within the existing observation and context budgets; protected names discovered while scanning a command snapshot never enter the cause or its diagnostic. The model result adds one short diagnostic field only when a cause exists: `Guard enforcement: protected path or set-ID entry refused`. Terminal Tool summaries show the same diagnostic. Bootstrap failures instead show `Guard enforcement: bootstrap failed before dispatch`. Results without a cause retain their model-facing projection. JSONL and strict replay retain the typed field under the [current payload versions](./execution.md#admission-persistence-and-recovery); previous versions reject without rewriting stored data.

| Platform | Reliable attribution in this profile | Reports no cause |
|---|---|---|
| Linux | Protected-path and set-ID entry refusals inside command snapshot capture; typed pre-dispatch controller bootstrap failures | Unclassified Bubblewrap startup failures, namespace-hidden paths, read-only mounts and seccomp-returned errno have no trusted per-operation denial channel. The current seccomp profile returns `EPERM` (and `ENOSYS` for `clone3`), rather than notification records; Arany uses no Landlock/audit attribution channel. A blocked socket/connect, `EACCES`, `EPERM`, `EROFS`, missing file or signal alone cannot establish Guard causation. |
| macOS | Post-run command snapshot refusals in the supervisor; a typed pre-launch controller bootstrap failure reports `guard_bootstrap` | Seatbelt violations are not collected through a trusted, invocation-correlated report channel. Program errno, stderr, exit status and unrelated system sandbox reports cannot establish attribution. |

`null` means no attributable cause, not permission or proof that enforcement was uninvolved. No network or process cause is claimed without a trusted evidence source. This applies equally to commands and local MCP servers; `isError`, server-provided cause fields and text remain ordinary program data. Skill loading is data-only; Skill scripts use ordinary guarded commands and the same classification.

This mirrors the separate sandbox diagnostic attached to results by Claude Code's [sandbox runtime `annotateStderrWithSandboxFailures`](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/sandbox-manager.ts), which uses invocation-correlated violations, and Codex CLI's [distinct `SandboxErr::Denied` result](https://github.com/openai/codex/blob/main/codex-rs/core/src/exec.rs). Arany does not copy Codex's `is_likely_sandbox_denied` output heuristic: hostile program output must never attest enforcement. The peers' escalation flows inform [primary host commands](#primary-host-commands); failure evidence supplies no authority.

In-process File effects have no Guard preparation or pre-GO stage; `guard_bootstrap` is invalid for their enforcement profile.

## Primary host commands

`command` remains guarded. The primary may request `command_unguarded` with a bounded justification before or after a Guard failure. This follows Codex's explicit `require_escalated` request; Arany deliberately retains human authorization, journal-first execution, no automatic fallback or retry, and primary-only authority. Host access needs no Guard image preparation. Guard admission retains the platform availability and trusted-helper checks; unavailable protection removes guarded commands from the catalog while host requests remain available. Every guarded dispatch rechecks availability and refuses before spawning on failure. Children, workers and hook outputs never receive host authority. A failed hook remains Ignored; diagnostic feedback remains bounded, but no automatic host proposal or escape-only Stop/PreCompact continuation is produced. Genuine Block/Stop outcomes and the eight-continuation cap remain.

**Admission.** Program, explicit argv and Workspace-relative cwd form a fresh immutable intent. Absolute targets belong in argv; cwd is opened beneath the admitted Workspace without following links. Programs resolve only through absolute PATH entries outside the canonical Workspace, including resolved aliases. An absolute program request must canonicalize to the same executable as the basename lookup through those entries; it cannot bypass PATH admission. The absolute executable, filesystem identity, digest, Workspace, environment policy and permission snapshot are pinned before approval and rechecked before dispatch. Native executable admission has the existing 32 MiB program bound; scripts require invocation through an explicitly pinned interpreter. The closed interpreter-name set is `awk`, `gawk`, `mawk`, `nawk`, `sed`, `sh`, `bash`, `dash`, `zsh`, `ksh`, `mksh`, `fish`, `csh`, `tcsh`, `python`, `python2`, `python3`, `pypy`, `pypy3`, `node`, `nodejs`, `deno`, `bun`, `perl`, `ruby`, `php`, `lua`, `luajit`, `tclsh`, `wish`, `pwsh` and `powershell`, plus the BusyBox and ToyBox multipurpose launchers; requested and resolved names require an explicit interpreter pin. A resolved interpreter without a matching `tools.json` command marked `interpreter: true` receives a distinct admission refusal, rather than an executable-resolution error. Wrapper arguments that name or resolve to these interpreters require their own matching executable and digest through the pinned PATH; a wrapper pin cannot admit a nested interpreter. These checks repeat before dispatch. There is no numeric-suffix heuristic. Trusted explicit interpreter declarations also identify versioned executables. Guard-only paths and variables are refused without translation. Model text cannot select actor identity, trust or approval provenance.

**Privilege tools.** Version 1 of the closed first-token policy prohibits `sudo`, `sudoedit`, `doas`, `su`, `pkexec`, `run0`, `runuser`, `chroot`, `systemd-run`, `machinectl`, `pfexec`, `ksu`, `dzdo` and `authopen`, checking requested and resolved basenames. `osascript` is refused when any argument contains “with administrator privileges” (ASCII case-insensitive). The wrapper/launcher set is closed and table-tested: `env`, `xargs`, `find`, `nice`, `ionice`, `timeout`, `nohup`, `setsid`, `time`, `busybox`, `toybox`, `stdbuf`, `chrt`, `taskset`, `flock`, `command`, `exec`, `strace`, `ltrace`, `nsenter`, `unshare`, `setpriv`, `script`, `watch`, `eatmydata`, `runcon`, `capsh`, `firejail` and `bwrap`; `chroot` is already prohibited outright. Wrapper argv naming a privilege-tool basename refuses, including nested launchers. `env -S` and `--split-string` forms refuse outright. During live admission and dispatch, path-like wrapper arguments and attached option values are canonicalized relative to the requested cwd and checked for a prohibited target basename or the filesystem identity of a privilege tool found through admitted PATH. These filesystem observations are not repeated during replay. Refusal precedes any approval offer and is rechecked before dispatch. No mode, reply or cached grant overrides it. The durable result says “Arany cannot run privilege-escalation commands. Please run this command by hand:” and carries the exact argv and Workspace-relative cwd as bounded JSON-quoted data. The primary must explicitly hand off to the user and never evade refusal through wrappers, shells or children. This is command admission, not confinement of arbitrary subprocesses. Shell/interpreter and wrapper argv text is conservatively tokenized on whitespace, quotes, shell metacharacters (`;`, `&`, `|`, parentheses, backticks, `$`, redirection and `=`); any privilege-tool token basename refuses. Common inline options (`-c`, `-e`, `-Command`, `--eval`, `--execute` and related forms) trigger this check even for other executable names. This scans literal strings without evaluation, including nested inline commands and quoted data; false positives are deliberate. An inline program remains opaque beyond this lexical check. File script contents, obfuscation, configuration and other payloads remain uninspected; the check is not a security boundary and cannot prove what a program will execute.

**Authority.** Attached human choices are once, identical-command approval for this live Session, an eligible proposed host prefix, and deny. Each Run pins an opaque Engine-generated epoch. Session grants are journaled with the approving verdict; reuse commits a new verdict referencing the earlier human intent in that epoch. Identity, digest, argv, cwd/Workspace, environment and settings must match, with no greater limits. At most 128 grants are reusable per epoch; once remains available when full. Session approval is offered only where reuse is eligible: rule-based asks, hook restrictions and literal StateRoot/account-root targets offer once only. Resume, restart, reconnect, fork, opening rewind, and `/permissions` end reuse. Failed permission readmission leaves host authority denied until successful explicit readmission; the attached session shows a recoverable notice and retains an already saved folder-trust change. Fresh binding/epoch creation on attachment, restart and reconnection is Engine-enforced: the epoch is journaled in Runs and verdicts, without a separate attach/resume binding Event. The reducer validates recorded epoch changes, resume/fork boundaries and exact prior-human references; it cannot independently detect a restart that incorrectly reused the same epoch. The live terminal mode is also an Engine restriction, not a journaled mode fact; replay validates the recorded settings mode and verdict, without reconstructing terminal mode changes. Explicit ask/deny and hooks narrow authority. Generic host commands are potentially mutating and refused in plan mode. `default`/`dontAsk` may reuse eligible session grants; `auto` and `acceptEdits` always need a fresh human, never AI review. Exec and ACP follow H1 through [Remembered host prefixes](#remembered-host-prefixes); unresolved host-command asks refuse immediately with a durable explanation. This follows [Codex headless policy](https://github.com/openai/codex/blob/61f34c35af77777db4d77d0ea2aeb8547a6b4523/codex-rs/exec/src/lib.rs#L586-L601) and [Claude preapproval](https://code.claude.com/docs/en/headless#auto-approve-tools). No human-attestation protocol or bypass mode exists. Serve offers once and negotiated exact-session scope only; unsupported scopes refuse rather than downgrading to once. These surfaces cannot create rules. Typed push/create always require a fresh human; typed PR reads retain their separate typed-rule authority.

Inactive `unguarded-commands.json` is archived byte-for-byte under `archive/inactive-host-commands/unguarded-commands.json`, with a bounded approval notice naming the archive and requiring fresh authority. Private-file admission and size bounds apply even to malformed contents. The existing private archive primitives serialize replacement and sync StateRoot before preparing the archive, so the archive directory is durably reachable before a pending identity/digest record is published or the source moves. After moving the source and syncing both directories, a separate manifest is written and synced while the pending marker remains. Only then is the marker removed as the final operation; this cleanup is deliberately unsynced, so a crash may restore the marker and conservatively require explicit recovery without losing the archive. Any unconfirmed archive remains blocked across reopen without retry or automatic completion; its pending marker requires explicit recovery. A recreated source beside an archive is a conflict, never overwritten or deleted. Unconfirmed and conflicting archives have distinct admission errors naming this directory. Recovery is manual: stop Arany, preserve the source and archive intact, and restore a verified backup or obtain operator assistance. Never remove a pending marker to assume completion or overwrite conflicting copies. No entry is converted into authority, and no exact-rule reader or writer participates in dispatch.

**Review and disclosure.** Review shows the pinned program, every argument, real cwd and model justification as escaped data. The approval prompt explicitly says that shell/interpreter inline programs are opaque beyond the lexical privilege-tool check, file scripts and obfuscation remain uninspected, and children have no controlling terminal for terminal privilege prompts. It explains that the process runs as the user, reaches files/network, can execute repository configuration, modify Arany permissions/Store/journal and disclose private data to the Provider. Lexical `.env`/`.env.*`, `.ssh`, `.aws`, `.gnupg`, StateRoot and account-root paths add a prominent sensitive-path warning. Non-human cached dispatch refuses literal StateRoot/account-root targets, including embedded absolute paths and relative tokens normalized against cwd. Saving a human-approved typed Git rule advances the Engine settings pin only to the exact bytes written from the expected prior digest; it never clears an existing settings-change lockout. Live permission settings are compared with the admitted digest before any host approval offer and again before dispatch. Detected out-of-band changes refuse with a settings-change explanation until human re-admission through `/permissions`; a typed-rule save also makes later host requests in the same immutable Run refuse before offering approval. Settings drift during an approval still refuses dispatch. These lexical checks do not detect computed paths or all aliases. Same-user state/journal tampering is neither prevented nor reliably detectable. Executables are invoked by path after digest/identity validation, and spawn re-resolves cwd after its directory check. Wrapper-argument target checks also race replacement before the wrapper opens the path. Same-user replacement in these TOCTOU windows is not prevented; pins are admission evidence, not execution isolation.

**Execution.** Intent, verdict/scope and dispatch authority commit before spawn. Existing Store tail, Goal action-time reservation and Workspace writer lease remain. The supervisor uses explicit argv, empty stdin and a cleared allowlisted environment with the admitted absolute PATH, real HOME, TMPDIR, LANG/LC_ALL/TERM when set, NO_COLOR, ARANY_TOOL_WORKSPACE and ARANY_UNGUARDED. A trusted internal Arany launcher creates a new OS session with `setsid` before replacing itself with the command; failure executes no payload. The command has no inherited controlling terminal or terminal-scoped privilege ticket. Existing finite command timeout, rendered output bound and 1 GiB per-stream kill ceiling remain. Timeout/output overflow with confirmed teardown stays Limit; confirmed cancellation stays Cancelled; known nonzero exit stays Failed. Lost acknowledgement or unconfirmed leader/group termination is Uncertain and stops continuation without retry. Process-group supervision does not contain deliberately detached descendants or confine host filesystem/network/CPU/memory access.

**Receipts and recovery.** Spawned host commands produce only an UnguardedReceipt, never a Guard receipt, changeset or cache publication. Approval without a terminal outcome is a possible non-rewindable effect; recovery never redispatches. Host dispatch invalidates earlier file-success and worker-verification evidence. Existing model, terminal, transcript, show, exec, Goal, serve/ACP and telemetry projections mark host/unguarded effects, retain partial output and do not claim complete inventory, rollback or rewind. Replay validates committed authority, exact references and bounds without reading settings or executing anything. [Execution](./execution.md#admission-persistence-and-recovery) owns migrations and [Session](./session.md#rewind-planning-and-replay) owns rewind.

## Commands

Native Tool decoding strips leading `./` segments and removes one trailing `/` for directory arguments (`list`, `search`, `glob` and command `cwd`), following Claude Code/Codex path-spelling parity. File arguments retain a trailing `/` and fail validation. This lexical normalization happens before argument validation, permission subjects, intent hashing and Guard pins; it performs no filesystem lookup, traversal collapse or home expansion. Absolute `/` remains absolute and is never normalized into the admitted root. The resulting Tool path must be canonical and Workspace-relative: at most 512 UTF-8 bytes, normal components separated by single `/`, with no absolute, traversal, `.` component, trailing separator, backslash, control character or excluded private component. Directory arguments also accept `.` or the empty string for the admitted root. Thus `docs/specs`, `docs/specs/` and `./docs/specs` select the same directory; doubled trailing separators remain invalid. Command argv has at most 64 NUL-free strings of at most 4,096 bytes each, within the aggregate [argument ceiling](#limits-and-failure-behavior). Semantic refusals use the [correlated argument feedback](./execution.md#accepted-outcomes), so a spelling error grants no access and can be corrected within the normal Goal budget. Permission subjects, proposed targets and Guard pins keep the same normalized path.

Command project copies exclude `.git`; the command description points to typed Git reads when they are cataloged. Following the Run's pinned catalog, a nonzero command exit whose kept stderr contains `not a git repository` receives a fixed hint in the model result's `hint` field when `git_status`, `git_diff` and `git_log` are available; the hint is derived deterministically from the recorded observation and omitted if adding it would put the complete model result above the [per-call result ceiling](#limits-and-failure-behavior).

Each `commands` entry declares a reviewed executable and its SHA-256, whether it is an interpreter, and any additional pinned input files:

```json
{
  "name": "bash",
  "executable": "/usr/bin/bash",
  "sha256": "REPLACE_WITH_THE_64_CHARACTER_LOWERCASE_SHA256",
  "interpreter": true,
  "inputs": []
}
```

The placeholder above is deliberately invalid. Resolve a system executable's real path and calculate its digest yourself, for example with `readlink -f /usr/bin/bash` and `sha256sum /usr/bin/bash` on Linux, or `shasum -a 256 /bin/sh` on macOS. Arany requires a no-follow, regular, single-link native executable: ELF on Linux or Mach-O on macOS. A symlink must be replaced with its resolved executable path. The optional `git` pin differs: it must lie under `/usr`, be root-owned, non-set-ID and not group- or world-writable, may have several hard links (distributions hard-link `git-core`), and runs in place from the read-only `/usr` mount rather than from a `/programs` copy, since its shared libraries load live from `/usr`. Updating an executable requires reviewing and changing its pin.

Additional inputs use `{"path":"/absolute/reviewed/file","destination":"relative/name","sha256":"<digest>"}`. They appear read-only under `/inputs/PROGRAM_ID/relative/name`. Executables are copied to `/programs/PROGRAM_ID`, except checked immutable macOS system programs, which retain their original paths. Paths and digests are checked again for each fresh invocation. Descriptions and the `interpreter` declaration do not prove that arbitrary arguments or a script are safe; allowing a shell or interpreter authorizes its behavior inside the same OS-enforced boundary, including descendants using the admitted native runtime.

## Persistent Workspace build cache

Commands receive an explicit argument array, a relative working directory, a cleared environment, private `HOME`, temporary and Cargo directories, no terminal input and bounded lossy UTF-8 output. With the build cache enabled, `CARGO_HOME`, `CARGO_TARGET_DIR`, `npm_config_cache` and `PIP_CACHE_DIR` point into the admitted cache view (`/cache` on Linux, the cache volume on macOS); otherwise they point into private scratch. Toolchain subtrees are executable across their whole tree, so `bin` entries that symlink into `lib` run on both platforms; selected `bin` paths augment the fixed system `PATH` in grant order, and a selected host cache replaces only its corresponding nested cache path. Each snapshot is a fresh writable copy of selected project paths, including prior typed edits and integrated changes; empty directories and executable bits survive without set-ID bits.

Selected Rust commands receive `CARGO_ENCODED_RUSTFLAGS=--cfg\x1farany_guard` (separator byte `0x1f`); Build also receives `CARGO_NET_OFFLINE=true` and `CARGO_BUILD_JOBS` from `intent.limits.build_jobs`. The enforcement digest binds the intent's `build_jobs`; receipts echo limits. [Goal admission](./goals.md#lifecycle-budgets-and-recovery) owns its snapshot and bounds. Other classes and runtimes get no jobs override. Flags or payload environment changes can override this compilation default within process/memory limits; jobs cap neither test threads nor CPU quota. The marker replaces lower-precedence Rust flags and enables only inventoried conditional ignores, never `arany_ci`; ordinary builds receive no marker. Overrides remain confined; offline mode and the marker prove no isolation. The [decision register](../research/next-step-decision-register.md#d-27--selected-rust-and-honest-guard-only-test-omissions) owns the peer choice.

An offline registry-backed build needs each required archive, source and index subtree selected independently, plus the selected compiler and SDK on macOS. Incomplete inputs, read-only extraction failures and unselected tools produce ordinary bounded command failures; there is no discovery, installation, extra mount, network retry or automatic host rerun. Repository toolchain selection, wrappers and configuration are computation inputs only. Guarded Cargo output retains actual passed, failed and ignored counts. IPC-dependent library tests use `cfg_attr(arany_guard, ignore = "requires local test IPC")`; pre-existing helper/release ignores retain their reasons, and affected conditional native gates also ignore under `arany_guard`. Pure and in-memory tests remain active. Forcing ignored tests to run retains socket denial. Flag changes must rebuild the test binary; a successful compile-only command can publish a cache but supplies no executed-test evidence.

Each Workspace has one archive keyed by its canonical path plus device and inode; at most 128 identities are retained. A nonblocking exclusive identity lease covers primary/editor command restore, collection, publication and clear; the retained native shared-read facility is unavailable to current editors. Competing exclusive operations return busy. Restore writes only fresh single-link regular files and executable bits into a separate quota-backed view and never creates links. Store accepts only allowlisted cache roots and rejects symlinks, special files, set-ID inputs, malformed paths, identity drift and unknown archive data. After positive descendant termination and native cleanup, Guard streams a bounded candidate to Store, which publishes it through a rollback intent, a committed marker and a successful parent-directory sync. Failure before the marker rolls back. If the marker write or its sync fails, Store returns a persistence error and keeps both archives and the records. Recovery must sync the directory before resolving the marker; a continuing failure blocks cache admission until recovery succeeds or the user runs `/cache clear`. Recovery restores the previous archive when a committed new archive is invalid and the previous one is valid; a synced marker keeps a validated new archive. Malformed or unsafe records fail closed and remain available for diagnosis. Only success or a Guard-attested primary or editor Build Command timeout with an empty Workspace changeset may publish; other failures, cancellation, resource/output limits and uncertain cleanup retain the prior cache.

For primary and editor commands, the controller records a typed `cache_update` beside the original observation, command result and Guard receipt, with six values: `published` (candidate committed); `rejected` (known size or quota rejection kept the prior archive); `failed` (candidate validation, host-side staging create, write or sync, reopen, or a known publication failure left the prior archive committed); `uncertain` (outcome cannot be confirmed and stops Run continuation); `not_attempted` (Guard error after dispatch, or a failed command that did not attempt publication); and `not_applicable` (no private cache). Published, rejected and failed updates require the eligibility above. A synthetic Limit without a Guard report requires `not_applicable`; an absent candidate cannot make it uncertain. Actual capture/publication uncertainty stops continuation. Cache updates preserve disposition and cause, including `Limit(timeout)`; success cannot commit `not_attempted`. No automatic retry occurs; a later explicit command may reuse a validated timeout cache. Cache data is never executable authority or automatic Provider context; command or MCP output that discloses it is ordinary bounded observation. Background jobs do not survive a call. This finite profile does not establish support for every large Rust, Node or Python build.

Native cache records and adapters retain bounded shared-read generation vocabulary pending native retirement. Current editor assignments neither pin a cache generation nor acquire an assignment-time shared-read lease, and each editor command takes the same exclusive identity lease as a primary command. Restore/publication/clear retains its ordinary recovery behavior. Editor command admission follows [Editor Tool steps](#editor-tool-steps).

The cache result is separate from command success. Text receipts surface rejected, failed and uncertain updates; JSONL and replay keep the full observation. The `default` or `build` class, user settings and checked headroom set each invocation's cache-view limit. The 8 GiB setting is a requested maximum, not usable capacity: committed archives, metadata, reservations, candidate and staging all count toward the 8 GiB StateRoot aggregate, and candidate and view are capped by remaining headroom. No cache is evicted automatically. Increasing the setting raises no other bound.

`/cache clear` removes only the current Workspace archive and displays `Cleared this Workspace's private build cache`; `/cache clear all` reclaims all committed caches and displays `Cleared all private build caches`. A busy clear displays `Build cache is in use; retry after its command finishes` and keeps the archive. A malformed clear displays `Error: Usage: /cache clear [all]`; other failures display `Error: private build cache could not be cleared`.

Archives capture regular files by content regardless of link count, so Cargo hard links restore as independent files. Competing operations return busy rather than wait. Publication builds the candidate beside the committed archive, syncs it, durably records rollback intent before renaming, and treats the committed marker with parent-directory sync as the commit point. A marker write or sync failure returns the error, skips Drop-time recovery and retains both archives and transaction records. Task transport carries only the checked Workspace identity and the exact read-only exclusions, never a `StateRoot` path or handle.

## Command input selection

Primary guarded commands copy pattern-selected inputs. Workspace-root and nested `.gitignore` files apply in directory order, with ordered negation, case-sensitive matching, and parent pruning; an excluded parent cannot be reopened by a descendant rule. Selection is pattern-only, including tracked-but-ignored files, and never reads the Git index. Fixed protected names, fixed dependency-directory exclusions and the pinned command grant remain dominant. No `.ignore`, `.rgignore`, parent/global ignore, Git configuration or `.git/info/exclude` discovery is performed. An ignored control still supplies rules when its directory is reached, without becoming payload-visible automatically.

Controls are bounded UTF-8 regular single-link files admitted through no-follow, no-mount-crossing directory capabilities. The shared matcher uses pinned `ignore = "=0.4.33"` through `GitignoreBuilder::new`, `add_line`, `build` and `matched`; it never invokes a filesystem walker or discovers global, parent or repository configuration. Missing controls mean no rules; unsafe or inaccessible required controls, malformed rules, replacement or resource exhaustion reject preparation before payload dispatch. The invocation freezes control bytes and selection. Replay never loads ignore controls. Ordinary entries are classified without following links through their admitted parent directory; exclusions apply before opening them. Excluded symlinks, special files and hard links are omitted, while unexcluded ones reject preparation. Required control admission and full output validation remain mandatory even for ignored paths. Safe ordinary inputs above 1 MiB are omitted without reading content; exactly 1 MiB remains admitted, and growth during a bounded read rejects rather than truncates. An omitted input is never a deletion; a replacement at an oversized omission path rejects capture, and publication independently checks absent-file preconditions and safe parents.

Parsing and walking run inside the admitted native unit, with a 512 MiB phase envelope even for Build commands. Linux uses a separate attested preparation process under the same retained FIFO reservation, stops it positively, waits within the teardown deadline for systemd to unload its service name, and then launches the payload without source access. Preparation receives the same pinned read-only runtime mounts as execution and attests their topology before selection; execution still revalidates grant identities and mounts before GO. Once unloading is confirmed, a child-reap or stderr-drain failure marks the preparation seed terminated for cleanup; an unconfirmed unload retains its reservation for recovery. During Linux capture, after positive descendant absence, the cgroup memory ceiling is the smaller of the payload allowance and 512 MiB plus its verified retained `shmem` charge. Capture cannot grow those private tmpfs files; all remaining unit memory stays within 512 MiB, and CPU/process limits return to the selection envelope. Malformed or out-of-bound accounting fails closed. Its private framed selection transfer is capped at 8 MiB and never mounted into the payload. macOS supervises the complete coalition during preparation and capture, retains control data outside the payload's Seatbelt grants, and captures before detaching images. Its controller applies selection limits only during the SELECT and capture phases; pre-GO preparation and cache or worker transfers use the pinned intent limits and ordinary CPU accounting. The inner supervisor owns payload resource outcomes. After `CAPTURE_DONE`, controller sampling stops so completed capture is not charged again against the payload CPU limit; observation and cache reporting retain their byte bounds, deadlines and cleanup requirements. After descendant absence, both macOS capture monitors pin the surviving supervisor's CPU counter before allowing capture; its 15-second CPU bound counts only work since that baseline, while other process identities retain their full CPU charge. Selection reserves five seconds separately from payload preparation; both remain inside the admitted action window. Phase deadlines are five seconds, shortened by the action deadline and transported as monotonic expiry values so private-channel delivery never restarts the budget. Capture leaves a one-second bounded report window inside the completion deadline; when necessary, its work deadline is shortened to preserve that window, and insufficient time refuses capture. Capacity waiting, including recovery and the ticket lifetime, is at most 30 seconds. Cancellation keeps ownership until cleanup. Selection transport preserves changed-input, configuration, operation, missing-path and grant-denial errors. Resource/expansion/call overflow is `Limit(resource)`; elapsed selection time is `Limit(timeout)`. No automatic unguarded fallback or retry is introduced.

Compared with Codex CLI and Claude Code's execution over real-path mounts/profiles, Arany retains disposable copies so host changes publish exclusively through validated changesets. Ignore preferences never grant access. Worker commands, MCP, typed discovery, Skills, executable admission and snapshot capacity retain their existing contracts.

## Local storage inventory

`arany storage` and idle `/storage` expose a user-local metadata report. The
[terminal contract](./terminal.md#storage-report) owns invocation and channels;
[credentials](./credentials.md#metadata-only-storage-inspection) owns account-root
admission. This operation is not a model Tool or a generic private-file read grant.
It creates no Session, Run, Event, directory, database, lock file, cache or log;
it invokes no Provider, credential helper, recovery, cleanup or telemetry export.

Coverage includes the selected Session StateRoot, the default Session StateRoot
and the fixed OS-user account root. `--state-dir` and `ARANY_STATE_DIR` select
Session storage only. Authenticate each existing root with private no-follow
component admission, independently of history/database or account payload validity.
Missing roots remain absent without creation. Report paths only for admitted
owned locations; suppress individual private-file and directory names. The main
Workspace is excluded by opened identity, including when inside a storage root;
a root inside the Workspace is unavailable. Nested roots and regular-file
identities are counted once. Private build-cache and Output spill totals are
separate from their parent's other private records and are not added twice.
Each admitted `spill` subtree has an `Output spill` row, including its directories,
output files and writer-lock metadata. Missing spill directories remain absent;
inspection never creates them. It neither reads payloads nor checks journal
references, takes writer locks, changes retention or grants Tool Read authority.

Aggregate regular-file and directory counts, logical metadata lengths and
allocated bytes (`blocks × 512`, checked for overflow). Secret-containing regular
files contribute metadata only; never read payloads. Metadata-only descriptors
use Linux `O_PATH` or macOS `O_EVTONLY`; only admitted directories open for
listing. Require private ownership, permissions and existing ACL admission;
unexpected multiple-link files, symlinks, special objects, foreign owners and
unowned mount crossings are excluded and make coverage partial. Never follow a
linked target. Linux uses `openat2` with no-cross-mount resolution; macOS uses
no-follow handles and device checks. Unsupported enforcement fails closed.
Linux `O_PATH` can admit a private mode-000 record for metadata inspection;
macOS `O_EVTONLY` may still require read authorization. A denied metadata open
excludes that record and makes its category partial, without reading content or
changing permissions.

Build-cache inventory reuses the owner's closed record-name classification. It
counts committed/previous archives, candidate/staging files, lock files and
reservation/transaction record bytes without parsing their contents, acquiring
leases or performing recovery. Pending/candidate/reservation records label the
category busy/retained and keep the report partial. A capacity reservation's
promised capacity is not allocated disk usage. An unknown/unsafe cache object is
excluded with a partial reason. Complete metadata does not prove inactivity or
safe reclamation; active shared readers need not create pending records.

Each category is complete, partial, absent, busy or unavailable. Metadata or root
identity changes during collection make the affected category partial. Only
attributed observations enter the known subtotal. Allocated bytes are not a
promise of reclaimable space, especially with sparse files, compression, clones
or snapshots. The observation is point-in-time and is not an atomic host total.

One inventory runs at a time, with no queue, retry or refresh. A shared 30-second
cooperative deadline, 16,384 scanned entries, depth 32, 4 KiB paths, 8 MiB
identity/path index and the [cache-identity limit](#persistent-workspace-build-cache)
bound work before allocation.
Exhaustion or arithmetic overflow stops the affected scan and marks a partial
known subtotal, never an exact complete zero. Cancellation publishes no complete
report, closes handles and performs no cleanup; blocking work remains owned
until it stops. A deadline cannot interrupt a stalled kernel syscall. Output is
at most 64 KiB with at most 128 detail rows; summaries and a partial/overflow
marker have reserved space.

Guard backing storage/scratch is explicitly not yet included, pending
the remaining storage work in [NEXT_STEPS](../../NEXT_STEPS.md#tool-and-engine-follow-ups). No owned
worktree registry exists in this version; this is not a zero-size worktree claim.
Coverage also excludes unregistered StateRoots, developer checkouts, external
worktrees, shared Cargo/npm caches, installed binaries and OS-keyring allocation.
No ambient host search or prefix-based attribution occurs.

Cleanup guidance names existing `/cache clear` (current Workspace) and
`/cache clear all` (selected StateRoot's caches), including their busy behavior,
and the [historical Guard maintenance procedure](../tools.md#historical-linux-seed-maintenance).
It never generates deletion/detach commands or recommends automatic removal of
history, credentials or live/uncertain Guard storage.

## Command changesets

After command completion and positive descendant termination, Guard compares the private snapshot with its admitted input and returns a sorted changeset of created, modified and deleted regular files with digest-bound before and after bytes and executable bits; binary content uses canonical base64. A nonzero exit may still return changes, since exit status and publication are separate outcomes. A failed capture, timeout, cancellation or unconfirmed cleanup publishes nothing.

Current commands select the primary Workspace publication path. The retained native WorkerImage source, target fields and framed-transfer codecs have no editor dispatch caller; live editor histories reject them. [Editor Tool steps](#editor-tool-steps) owns the foreground-only capability.

After positive descendant absence, the entire private output tree is structurally validated, including ignored directories, before publishable content is read. Baseline membership wins over frozen ignore rules; payload edits to controls affect only the next invocation. Newly generated ignored regular files are discarded without reading their content. Oversized publishable outputs or enlarged baseline files reject capture. The canonical command result requires an explicit `selection` field: new results carry `{ignored_entries, pruned_directories, oversized_inputs, discarded_outputs}`, while `null` means counts were not observed. Counts describe observed entries and pruned roots, never unseen descendants, and contain no paths or content; presentation and replay use these committed counts. An unobserved summary displays `selection counts unavailable`, never zero counts. Links (including hard links), special files, set-ID bits, excluded or invalid paths, mount crossings, unsupported type conversions and overflow reject the whole changeset. Directory creation is supported only as parents of created files; empty-directory changes are not integrated. The ceiling is 64 files, 32 KiB aggregate decoded before and after content, and 48 KiB canonical serialized changeset JSON. Engine-generated command-receipt integration has a 64 KiB argument allowance; ordinary model Tool arguments remain capped at 16 KiB. The Build class raises neither these nor other Workspace or Tool-context limits.

Engine records the command observation, then creates a separate one-use integration intent bound to that exact receipt; models cannot request integration. The Goal path scope and pinned write grant are checked before publication. An out-of-scope integration is journaled as `Denied` with no receipt or dispatch, and replay accepts only that correlated denial. In-scope integration goes through the in-process file publisher and never adopts subprocess-created host paths. Approval cannot widen the grant. Auto edits accepts in-grant integration after command approval; Request approvals shows the sanitized before and after changes and asks separately; Auto approval reviews the concrete integration and asks a human on uncertainty. Headless runs use their upfront grant. Goal plan revision cannot widen the pinned Tool grant.

Before publishing, the in-process file publisher validates the whole batch, Workspace identity, every before digest, executable bit or absent-file precondition, and parent types through no-follow handles; conflict, denial or overflow leaves every file unchanged. Publication uses fresh regular inodes and checked deletions, then synchronized directory receipts. It is not an atomic multi-file transaction: failure or drift after publication records Uncertain and stops the Run without retry. Cancellation during approval changes nothing; cancellation during publication may leave uncertain effects. Replay retains both outcomes and never repeats the command, approval or integration. Only a successful integration receipt proves publication.

Before dispatch, a command reserves Store and Event headroom for its observation, any required integration and the terminal Run and Goal receipts; if that tail cannot be admitted, the command does not dispatch. Context admission also reserves the complete command-receipt integration argument allowance and rendering overhead before command dispatch; insufficient context prevents dispatch. Integration shares the Goal's active-time accounting, uses fresh authorization and never renews the command's approval.

Command capture starts only after payload descendants are positively absent, and the changeset scan finishes before images detach. The Guard validates command capture; the in-process file publisher rechecks the integration batch before Workspace publication. The system-executable catalogue travels only through the trusted controller and supervisor channel, never Workspace or payload input, and is never persisted as an authority cache.

## Checkpoints and rewind

Store captures private pre-images for primary and editor Workspace Write, Edit, MultiEdit, Delete, Move and both ApplyChangeset sources after approval, through the Engine checkpoint gate before in-process publication. A checkpoint is the position before a Run's first effect, covering prompts, Goal start/resume and autonomous Runs; steering notes create no checkpoint. Capture saves an existing file on its first successful or Uncertain publication in that Run, and again if its before digest differs from the last successful after digest in the Run. Creates and same-Run repeats without a gap need no bytes. Deletions save their before bytes. A failed publication never advances that chain.

Typed edits read through the existing admitted directory handle with identical grant, identity, protected-name, no-follow, mount, link and file bounds, then verify the intent's expected SHA-256. Command and rewind integration use their already validated in-memory before bytes. Successful capture commits before publication; the in-process file publisher still rechecks the whole publication batch. Digest mismatch skips capture and leaves publication's own conflict check in force. Mkdir has no checkpoint capture for either actor; MCP, commands themselves, cache publication and scratch are also excluded. Integrated command changes are covered because they are Workspace publications. Unguarded commands and external effects remain outside this coverage.

`StateRoot/checkpoints.sqlite` is a Store-thread-owned schema-v1 derived store outside the Workspace, separate from the journal. It contains content-addressed `blobs(digest, bytes, len)` and attribution/quota `refs(session_id, goal_id, run_id, rewind_id, tool_sequence, path, digest, len, captured_at_ms)`. The ref sequence names the committed ToolStarted or WorkspaceRewindStarted; exactly one of run_id and rewind_id is present. Rewinds have no Goal and use the Session quota bucket for goal_id. Bytes are deduplicated; every blob read verifies SHA-256. Refs never choose a restore destination: rewind plans must come solely from journal facts and look up blobs by journal digests. Strict replay never opens this store, reads the Workspace or re-executes a publication. [Session rewind planning](./session.md#rewind-planning-and-replay) consumes only journal metadata.

Admission reuses private_fs: a private 0700 directory, owner-only 0600 regular single-link no-follow files and native ACL checks. SQLite uses defensive mode, trusted_schema=OFF, DELETE rollback journaling, synchronous=EXTRA, incremental auto-vacuum and a max_page_count derived from the physical quota. SQLite values and rows are capped at 1 MiB + 4 KiB and SQL at 64 KiB; overflow makes storage unavailable. The checkpoint migration floor and current SQLite `user_version` are both 1. `store::migrate` registers this schema alongside the journal; the version guard requires each later adjacent step and its exact source schema and fixture. A schema-v1 identity fixture pins Tool and rewind refs and their content-addressed bytes without a rewrite, backup or migration marker. Future checkpoint steps must use the [journal copy-transform, validation and recoverable swap protocol](./execution.md#journal-migration), under the same history and checkpoint locks, preserving blob digests and refs. At startup, a nonempty SQLite checkpoint file with `user_version` below the floor, including a foreign SQLite database, archives intact with the journal and sidecars through the existing history archive and notice; a file SQLite cannot read stays as malformed storage. A hot `-journal` is first recovered by SQLite under the exclusive history and checkpoint locks and eligibility is then re-read; a sidecar that survives recovery refuses as unsafe state with every file untouched. Missing or empty checkpoint storage remains lazily initialized. Newer or malformed schemas retain explicit checkpoint recovery and reject before mutable pragmas or eviction; busy or unsafe storage is never archived. Capture failures preserve that storage and do not block the effect. The Store reset API admits a private malformed/unsupported store, holds its exclusive checkpoint lock, snapshots its file identities and modification facts, and refuses a changed file. Explicit confirmation may then remove only checkpoint storage and its SQLite sidecars. Busy, non-private or unsafe storage cannot be reset. The [terminal rewind panel](./terminal.md#rewind) offers confirmed recovery; no clear command or settings toggle exists.

| Bound | Limit | Overflow |
|---|---|---|
| Pre-image | 1 MiB | skip the whole publication with `too_large` |
| Path per owning Session | 32 versions and 32 MiB logical bytes | evict oldest versions first |
| Goal | 256 MiB logical referenced bytes | evict oldest checkpoint refs, excluding the current Run |
| Session | 100 checkpoints with refs and 512 MiB logical bytes | evict the oldest checkpoint's refs, excluding the current Run |
| Store | 2 GiB SQLite pages including free pages, blobs and refs; 262,144 refs; remaining filesystem headroom | evict the least recently captured Session's oldest refs, excluding this publication; otherwise skip whole with `quota` |
| Retention | 30 days after the Session's latest capture; future-dated Sessions are eligible | sweep on Engine open and before capture |
| Publication capture | typed edit 1 MiB; [command changeset limits](#command-changesets); editor typed edits use the same per-publication bounds as primary edits | skip whole; no partial capture |
| Contention | 2 seconds shared by checkpoint-lock and SQLite contention | skip with `store_unavailable` |

Eviction is transactional and set-based: expired Sessions, then per-path, per-Goal, per-Session and total quotas, each one ordered pass that removes whole checkpoints until the quota holds, with one pass targeting twice the shortfall for the physical size and filesystem headroom; retention expiry commits in its own transaction so it makes progress even when the capture itself is skipped. Unreferenced blobs are removed and incremental vacuum reclaims free pages. A failed batch rolls back its insertions and evictions. Eviction runs before the filesystem headroom check: admission retains 4 MiB of filesystem headroom plus the incoming bytes and the file growth, which covers the rollback journal; SQLite's page ceiling remains enforced. The Store validates the whole database once per open and re-checks only the file identity and schema version afterwards. The Engine waits at most 3 seconds, and at least 1 second before the publication deadline, for a capture; a later result is discarded and the capture is `skipped` with `store_unavailable`. Orphans from a crash before publication expire with the Session's refs. Removing a ref whose digest remains available through deduplication emits no notice. The first eviction per Run that loses a blob of this Session identifies its newest affected checkpoint: `Older checkpoints pruned; code restore unavailable before Run ID`. Other Sessions' prunes are never named in this Session's journal. A startup sweep's prune of this Session is retained for its next captured publication.

[ToolFinished](./execution.md#admission-persistence-and-recovery) has required nullable `checkpoint`: null for non-publications or known non-dispatch; otherwise `{status: captured|not_needed|skipped, reason: null|quota|too_large|store_unavailable|digest_mismatch, pruned_before_run: null|RunId}`. Captured requires an overwrite and successful or Uncertain publication; not_needed requires a create, a repeat without a gap, or a dispatched publication that did not change the Workspace (failed, conflicted or denied), which never produces a rewind notice. Skipped capture still permits the publication. Tool summaries and `show` surface the reason (quota: `This change cannot be rewound (checkpoint storage full)`); JSONL retains the field, and Goal reports retain a priority unresolved fact. Checkpoint bytes never enter model context, telemetry or diagnostics automatically.

Capture executes no Git and leaves the user's `.git` untouched. Prior file contents are unencrypted private state, like the journal. The same storage and capture contract applies on Linux and macOS; existing native admission and publisher guarantees remain required, with no new native enforcement or stronger macOS filesystem durability claim. [D-21](../research/next-step-decision-register.md#d-21--checkpoint-storage) owns the peer comparison and storage rationale.

Engine::rewind_preview admits an idle Session under the Engine operation slot, Session and ancestor locks and the account-wide Workspace writer lock. It checks the pinned Workspace identity and reloads the current explicit write grant or saved folder consent, never historical permission. Current permission denies also exclude the path; confirmation supplies any required human approval. Preview computes live digests and executable bits through the admitted in-process directory capability and verifies required checkpoint blobs. Read-only or excluded paths are outside_grant; links, special files, mounts and case aliases are unsafe. Missing, pruned or tampered blobs are unavailable. A preview contains no executable text or authority from restored bytes. Its comparison data reuses the admitted before/after versions, capped at 64 MiB of decoded content in aggregate; content beyond that comparison bound is explicitly unavailable without changing restore admission. Unsafe, outside-grant and unavailable paths disclose no comparison content. Checkpoint-storage errors remain distinguishable from a missing blob so the terminal can offer checked recovery.

Any live drift, intermediate history drift, unavailable blob, unsafe path or grant exclusion refuses the entire batch by default and lists the affected paths. Two explicit selections produce a new preview for confirmation: keep listed files and restore the others, or overwrite drift/history-drift paths using their observed digest/absence as a new precondition. Unavailable, unsafe and outside-grant paths can only be kept. A live file exceeding the 1 MiB version bound is listed as an unsafe path that can be kept. Preview applies the publisher's path admission (ASCII, at most 16 components, whole-batch directory scan bound), so it never promises a restore the publisher refuses. Combined kept/overwrite selections are sorted, distinct, disjoint subsets of at most 64 explicit paths, each at most 512 UTF-8 bytes. An empty effective plan cannot restore. Open or Uncertain publications block code restore under the [Session contract](./session.md#rewind-planning-and-replay).

Engine::rewind consumes one opaque, non-cloneable preview as confirmation of that exact plan. It reacquires the locks, rechecks the head/prefix, live state, blobs, current grant and enforcement, and refuses a changed preview before Started. The preview remains confirmable while live and unchanged; it cannot be renewed or reused. Before Started the Engine reserves two maximal Session Events; capacity refusal changes nothing. The effective plan is capped at 32 MiB of restored content and 32 MiB of overwritten content; file count, per-version size and serialized transfer use the shared [changeset bounds](./execution.md#worker-journal-protocol). Overflow refuses the whole action. Workspace contention returns WorkspaceBusy; an active Engine returns Busy.

Restoration uses an internal Rewind publication source containing the canonical plan digest and transfer length/digest. It is never a model Tool or a ToolStarted source. Restore bytes are decoded and validated in process under the existing transfer bounds; the file publisher consumes the admitted Workspace capability and validated versions. After committing Started, the Engine attempts to capture overwritten content in the Store under that rewind ID for the Before rewind checkpoint. When publication proceeds, Finished records the actual capture status; skipped capture still permits ordinary restoration. An explicit drift overwrite refuses before publication if its content could not be saved. Hooks never run. The existing publisher checks the complete batch before its first write, then uses fresh inodes and checked deletions. Publication follows the shared capacity, deadline and uncertainty rules for [in-process file operations](#in-process-file-operations), with no native Guard unit. Cancellation before Started changes nothing; after Started it records cancelled when non-publication is known. A conflict lists only the paths whose live state differs from the preview, re-read after the refusal. An unconfirmed write or lost completion is Uncertain, with no automatic retry. Finished binds the intent and its in-process attestation digest to the plan, Workspace and enforcement; historical Guard receipt digests retain their original encoding. A missing Finished leaves an Uncertain prefix; [Goal recovery](./goals.md#rewind-and-goal-recovery) owns the resume block. Conversation restoration and both-mode ordering follow the [Session contract](./session.md#conversation-rewind); the [terminal](./terminal.md#rewind) and [serve](./serve.md#rewind) own their controls.

Linux and macOS use the same admitted-capability file publisher, Store, planner, Events and transfer validation, with no new native code. Existing ASCII case-alias refusal applies on both platforms; case-insensitive APFS additionally refuses filesystem aliases during exact-case admission. Case-sensitive filesystems can hold distinct names, which does not relax publisher admission. SQLite retains existing macOS durability settings with no F_FULLFSYNC claim. On WSL2, drvfs or /mnt/c executable-bit changes can appear as drift. Native support requires the separate Linux/macOS rewind evidence; compilation alone is not that evidence.

## Local MCP

Each `mcp` entry pins a server executable, immutable input files, fixed startup arguments and allowed tool names:

```json
{
  "name": "local",
  "program": {
    "name": "python-mcp",
    "executable": "/absolute/resolved/python-executable",
    "sha256": "<digest>",
    "interpreter": true,

```

The configured server has the same offline snapshot, runtime and descendant restrictions as commands, with no Provider or account credentials. This subset is intended for local data and computation tools. Servers needing external APIs, credentials, writable host state or package installation are not supported by this base.

Arany implements the **2025-11-25 stdio tools profile**: `initialize`, exact version and capability negotiation, `notifications/initialized`, bounded `tools/list` pagination, schema validation, one `tools/call`, then disconnect. It is not the newer 2026-07-28 stateless profile or an HTTP/OAuth adapter. Server-to-client ping works; sampling, roots and elicitation are unavailable and receive method-not-found responses. Notifications cannot trigger discovery, refresh permission or extend deadlines.

Discovery returns a digest of each admitted complete tool definition. A later call lists again and requires the selected digest; drift rejects before the call. Arguments must be an object encoded as a JSON string that satisfies the admitted input schema. Schemas use the supported Draft 2020-12 or Draft 7 subset, bounded linear regexes and offline compilation; references, `$id`, remote retrieval and unsupported dialects reject. Calls have no hidden retry. Output admits bounded text, inert resource links and legacy object `structuredContent`; a declared output schema is enforced for successful results. Links are not fetched. Embedded resources, images and audio are rejected. `isError` is recorded as an observed failure, not success.

## Extension and transport admission

The current MCP profile is [local stdio](#local-mcp); no generic listener, remote MCP or runtime self-update is admitted. A new listener requires a named feature and a separate reviewed protocol. The [stdio server](../../NEXT_STEPS.md#pursue-in-order) and network-capable extensions remain deferred.

Any future HTTP or MCP listener must validate exact `Host` and `Origin`, authenticate and authorize each session, admit exact content types, bound bodies and sessions, reject DNS-rebinding, CSRF and cross-site requests, and encrypt traffic leaving loopback. Loopback routing is not authentication. The sole current listener exception is the one-shot [OAuth callback](./chatgpt.md#authorization-transaction). PTY, update, package-install, approval and other high-authority operations require a narrow authenticated protocol and explicit capability rather than a generic listener.

MCP servers, plugins, Skills and updates require reviewed provenance and an immutable version or digest; no update endpoint may select arbitrary packages or installation/lifecycle scripts. Future MCP credentials must bind server, issuer, audience, scopes and session, never Provider or ambient credentials; authorization is per server, Tool, resource and operation. Manifests and results remain untrusted. Network grants retain the [Provider destination and disclosure constraints](./provider.md#configuration-and-egress).

## Typed Git reads

Install Command Line Tools to enable macOS Git reads; remaining macOS evidence is listed in [next steps](../../NEXT_STEPS.md).

1. **Availability.** Folder trust pins the platform Git when it resolves under the platform root to a root-owned, non-set-ID, non-writable executable of the platform's format (path and SHA-256 per Run): `/usr/bin/git` (ELF) on Linux, `/Library/Developer/CommandLineTools/usr/bin/git` (Mach-O) on macOS. Explicit configuration uses the `git` field (`name` `git`, executable under the platform root, SHA-256, `interpreter: false`, no inputs) and requires `workspace_paths: ["."]`. Without a pin the catalog reports `unavailable`, no Git operation is offered or admitted, and Git is never emulated. Git outside the platform root is unavailable by design: Nix, Homebrew and Guix Git, Xcode.app Git and, on macOS, the `/usr/bin/git` xcrun shim.
2. **Operations.** `git_status {path}`, `git_diff {path, base, head, staged}` and `git_log {path, revision, max_count}`. `path` is a Workspace-relative literal pathspec, and `.` is the whole repository. `git_diff` compares the working tree with the index, the staged index with `base` (or HEAD when `base` is null), the working tree with `base`, or the two endpoint trees; `head` requires `base` and excludes `staged`. Endpoint diff has Git's two-dot semantics (`diff base head`), not a merge-base comparison. A single revision is `HEAD`, a ref name or a hex commit name with at most four `~N`/`^N` steps, at most 128 bytes. `git_log.revision` also accepts exactly one `base..head` range with two nonempty independently valid revisions, each at most 128 bytes and the whole range at most 258 bytes (two endpoints plus `..`). Open endpoints, three-dot ranges, revision sets, `:`, `@{` and options reject. If a revision name matches ambiguous refs, resolution fails before dependent reads. `max_count` is 1 through 50. Compared endpoints resolve once to commit OIDs before dependent reads; at most four invocations share the existing action deadline. Comparison results include both original endpoint names and captured OIDs. Results are JSON: `git_status` returns `{"branch":{"oid","head"},"entries":[{"path","state"}],"truncated"}`, `git_diff` returns `{"files":[{"path","added","deleted"}],"patch","truncated"}` plus `comparison` for endpoint reads, and `git_log` returns `{"commits":[{"oid","parents","author","time","subject"}],"truncated"}` plus `comparison` for ranges. A failure returns `{"failed"}`; diagnostics follow the [disclosure policy](#typed-git-reads) below.
3. **Exclusions and fidelity.** The components `.git`, `.aws`, `.ssh`, `.gnupg`, `.env`, `.env.*`, `.npmrc` and `.pypirc` are excluded case-insensitively (ASCII) through `:(icase)` pathspecs and row and stderr filters, including history, so `.ENV` or `.Env` on a case-insensitive APFS volume is excluded too. Renames are not detected, submodules are ignored, and `.git/info/exclude` is not applied. Git runs with default settings, not the repository's: `core.filemode`, `core.autocrlf`, `core.eol`, `core.ignorecase`, `core.symlinks`, `core.excludesFile`, sparse checkout and `branch.*` are not applied. A WSL2 `/mnt/c` repository with `core.filemode=false` can show mode-only changes, and an `autocrlf` repository can show line-ending changes that your own `git status` hides. The fixed view config omits `core.precomposeunicode` and `core.ignorecase`, so on APFS a non-ASCII or case-variant name can appear as deleted plus untracked. These fail without running Git: a repository rooted in a parent directory, a linked worktree, a submodule checkout or other `.git` file, a symlinked `.git`, a missing `HEAD`, `objects` or `refs`, and `[extensions]`. A split index fails when Git runs.
4. **Neutralization.** Git never receives the repository's configuration, hooks or attribute-selected drivers; Arany reads repository config only to detect `[extensions]` and extract the inert upstream metadata described below. It runs against a private view on scratch tmpfs (Linux) or in the unit control root (macOS): a fixed config, copied `HEAD` and `index` files, and linked `objects`, `refs`, `packed-refs` and `shallow`. The index is read without following links, with its mtime from the same open file (Git's racy-stat check compares against it); a linked or hard-linked index is an unsupported layout, and an index over 32 MiB refuses with Limit. It runs with a closed 13-variable environment, fixed argv (`--no-optional-locks`, `--no-ext-diff`, `--no-textconv`, `--no-pager`, `--end-of-options`, `--`), read-only Workspace access (a bind on Linux, a Seatbelt read grant on macOS), no network, the rechecked pinned executable and the default resource profile. Linux stops namespace descendants before the receipt; macOS empties the unit coalition at teardown. Inert vectors include `core.fsmonitor`, hooks, `diff.external`, textconv, filter drivers, `include.path`, pagers, signing programs, credential helpers and lazy fetch.
5. **Policy and disclosure.** Git reads need the pinned grant and no approval in any mode. They are in the Goal prelude with plan-contract `path` scope, are never success criteria, and are never offered to children. Bounds follow [limits](#limits-and-failure-behavior): the `git_log` commit limit applies to returned log rows; [branch comparison](#branch-discovery) has a separate internal ancestry scan bound. On macOS these limits use the supervised default profile. A nonzero exit is Failed and the Run may continue; `git_status`, `git_diff` and `git_log` suppress stderr because arbitrary diagnostics cannot be safely filtered by path. Committed history and changes reach the Provider and the journal as untrusted data. Residual risk: secret-path exclusions are pathspec and output filters, not sandbox enforcement.

6. **Ignore selection.** Typed `git_status`, `git_diff` and `git_log` apply the shared bounded Git-ignore selector to returned paths, in addition to protected-name and Read filtering. Selection starts after Git capture and uses the shorter of the two-second discovery window and the existing action deadline. It reads only the Workspace root and nested `.gitignore` controls through no-follow admission; missing controls mean no rules at that level, while malformed, unsafe, unavailable or over-budget required controls fail the operation without partial output. Rules are retained for the operation. Ignored paths stay hidden when tracked, and an explicit Git path argument does not bypass selection. Filtering occurs before result fitting: status and numstat rows are omitted, a diff section is kept only when its recognized path is visible, and a log commit requires visible changed-path evidence. A commit subject that remains visible through another path is still untrusted data and is not a secret-redaction guarantee. Git rename detection remains disabled; unrecognized or quoted headers remain hidden. The selector uses the shared [ignore-control admission](#command-input-selection) and [discovery limits](#typed-read-discovery), within the same bounded Guard operation. Expiry returns `Limit(timeout)`, an over-budget control returns `Limit(resource)`, and invalid or unsafe controls reported as `Path` or `FilesystemDenied` return `Denied`. Any selection failure discards the complete read. Strict replay uses the committed observation and never loads current ignore controls or reruns Git.

macOS trade-offs, known and accepted for this release:

- The private view has no volume quota (`install_git` uses `unit_root`, which skips `storage::verify_storage`), so writes are bounded only by the 20-second cap and fixed argv. The pinned Git has no code-signature or entitlement verdict; its only check is a SHA-256 pin of a root-owned file, and the kernel enforces the platform signature at exec.
- A TOCTOU window exists between `verify_pin` and spawn-by-path. Linux avoids the equivalent window by executing the pinned file in place; macOS cannot, so exploiting it requires root write access to the Command Line Tools tree. Ancestor directories of the pinned executable are not checked for ownership or writability on either platform; `verify_host_executable` checks only the leaf. This is a known limit.
- A Command Line Tools update changes the digest, so Git reads fail with `ChangedInput` until folder trust is renewed. The read-only Workspace bind includes `.env`, so a Git memory-corruption bug triggered by a hostile pack could emit Workspace bytes through the bounded output channel, the only exit because there is no network. Encodings are offline-tested only; live evidence is listed in [next steps](../../NEXT_STEPS.md).

### Branch discovery

`git_branch {name:null, start_point:null, scope, base, max_count}` reads local
and remote-tracking tips through the same primary-only Git grant on Linux and
macOS, including plan mode. Null `scope` means `local`; the other choices are
`local`, `remote` and `all`. Null `max_count` means 256, otherwise 1–256.
Null `base` omits comparison; an explicit base uses the read revision grammar
and must resolve to a commit. Invalid inputs reject before execution. Creation
keeps the [write contract](#typed-git-writes) and requires these three fields null.

The JSON result has `branches`, nullable `comparison_base: {revision, oid}`,
`history_complete`, `truncated` and `timed_out`. Rows are sorted by their full
ref names before projection, with invalid UTF-8 replaced by U+FFFD and `name`
capped at 1 KiB on a UTF-8 boundary. `name_truncated` marks clipped or lossy
names; never treat either as an exact ref identity. A lossy local name has no
upstream association and reports `upstream_status:unsupported`, so its displayed
name cannot select another branch's metadata. Rows carry
`kind: local|remote|non-commit`, captured tip `oid`, `current`,
nullable `symbolic_target`, nullable `subject`,
`subject_withheld`, nullable `upstream`, `upstream_status`, nullable
`ahead`/`behind`, `counts_withheld` and `counts_capped`. Symbolic targets share
the same replacement and cap, adding `symbolic_target_truncated:true` when
clipped or lossy. Non-commit refs, including annotated tags stored in branch
namespaces, remain rows with
their captured object OID, a null subject and withheld counts; they do not fail
the listing. Remote symbolic aliases retain their target but have no independent
subject or counts. Detached or unborn HEAD does not prevent enumeration; an
empty repository without an explicit base succeeds with no rows.

The base resolves once to a commit OID. Each comparison uses that OID and the
captured commit tip OID with fixed `rev-list --left-right --max-count=1001
base_oid...tip_oid`: left is `behind`, right is `ahead`. At most 1,000 emitted
commits yield exact counts over available history. A lookahead commit withholds
both counts with `counts_capped:true`; it never reports a partial count as exact.
The output cap does not bound merge-base traversal, so subject and count work
also share a one-second per-row deadline. Reaching that deadline keeps the row
with unobserved fields null and withheld, marks requested counts capped, and
continues to other rows while the shared action deadline permits it. Any such
cap returns `truncated:true`. Counts describe whole-history ancestry, not
permitted-file changes. Null counts mean comparison was not requested, the row
is an alias or non-commit ref, or `counts_withheld` is true.

Tip subjects are at most 256 characters and require visible-path evidence from
that exact commit; an older visible commit never supplies the subject. Mandatory
secret-path exclusions always filter evidence and diagnostics, independently of
user Read rules; mandatory exclusions do not disable enrichment. Unresolved
restrictive user Read path rules populate the hidden-path set and suppress
subject and count enrichment, marking those fields withheld.
A protected-only tip has a null subject with `subject_withheld:true`. A parentless
tip in a shallow view also withholds its subject: its apparent root diff cannot
prove which paths changed. Filters run before persistence and model continuation,
with the same filtered diagnostics as other reads.

Remote-tracking refs are local observations that may be stale; no fetch or
network occurs. Shallow repositories return `history_complete:false`, so
counts describe only available history. Missing objects or an unresolved base
fail explicitly. A concurrent ref change does not change a captured OID; this
is not an atomic repository snapshot. One sorted `for-each-ref` enumerates the
selected namespaces within the [shared read limits](#limits-and-failure-behavior).
Returned rows are enriched sequentially, with at most one subject and one comparison
invocation per returned row, plus one base resolution per action. Each capture
is discarded after projection. All invocations share the action ceiling;
branch reads reserve one second for teardown and result delivery.
Reaching the remaining work deadline returns completed rows with `truncated:true`
and `timed_out:true`, preserving captured OIDs and any already resolved base.
A deadline during enumeration or base resolution returns an empty truncated
listing; `comparison_base` is null if resolution never completed, with the
requested revision still recorded in the intent. A timeout is not an empty
successful inspection of the whole repository. An overflowing tip capture keeps
only complete evidence lines; without visible evidence its subject stays withheld.
Complete rows fit the Tool result budget; overflow
or clipped or lossy names return `truncated:true`, never partial rows or invented counts.
Cancellation, teardown and unknown completion follow the existing Guard contract:
only confirmed cleanup permits another row or a partial result. A failed or
expired child reap stops the action and leaves remaining processes to Guard
teardown; a missing receipt remains Uncertain. Replay uses committed rows, flags and OIDs without running Git or
rereading configuration.

Upstream associations use only direct `branch.<name>.remote`,
`branch.<name>.merge` and the matching `remote.<name>.fetch`, parsed as inert
metadata from the existing no-follow, at-most-64-KiB config inspection. Ordinary
Git-written quoted subsection names and plain or quoted scalars in the admitted
ref alphabet are supported. Remote `.` names a local ref; another remote needs
one unambiguous positive literal or single-wildcard fetch mapping, optionally
prefixed with `+`. Resolved targets are checked through the shared no-follow
ref reader (1 KiB loose refs, at most 32 MiB packed refs); an unsupported ref
shape or over-bound lookup is reported unsupported. Requested packed targets are
read and indexed once per action, with loose refs taking precedence.
No URL, helper or executable
setting is loaded or passed as Git configuration. `upstream_status` is:

- `present`: the direct association resolves to a present target ref;
- `gone`: the supported target ref is missing, with its name retained;
- `unavailable`: direct metadata is missing; this makes no claim about user-global configuration;
- `unsupported`: duplicate/ambiguous keys, unsupported syntax or mappings, escapes,
  continuations, or any include/includeIf declaration; `upstream` is null;
- `not_applicable`: a remote row has no branch upstream.

Includes are never read; their presence prevents claiming a complete direct
association. [Decision D-25](../research/next-step-decision-register.md#d-25--branch-reads-use-git-semantics-with-inert-tracking-metadata)
records the peer behavior and neutralization rationale.

### Typed prefix rules

`permissions.json` may carry `permissions.typedPrefixes`, an optional list (default empty) of `{"prefix": [...], "decision": "allow"|"ask"|"deny", "workspace": null | {"path","device","inode"}}`; every field is required and unknown or duplicate fields reject. `prefix` is exactly one of `["git","commit"]`, `["git","branch"]`, `["git","switch"]`, `["git","push"]`, `["gh","pr","create"]`, `["gh","pr","list"]` or `["gh","pr","view"]`; partial verbs, extra tokens, flags, globs, shell strings, aliases, wrappers and executable paths reject. Matching uses the validated typed operation, never adapter argv: `git_commit`, `git_branch` with a `name` and `git_switch` map to their verbs; branch listing is a read and matches none. `push` and `pr create` match `git_push` and `gh_pr_create`; `pr list` and `pr view` match `gh_pr_list` and `gh_pr_view` and follow the separate [host-read approval exception](#human-approved-host-git). Push and PR creation remain human-only under every permitted mode, including with an `allow` rule; `/permissions` labels them `host; human approval required`. `workspace: null` is user-wide within this state directory; an object binds the exact absolute path, device and inode of the folder, so a moved or replaced folder inherits nothing. Paths are at most 4096 bytes, canonical, control-free, with a nonzero inode.

Typed rules and [host-prefix records](#remembered-host-prefixes) share the 128-rule and 64 KiB limits with the ordinary rules. Typed rules follow the same single `deny > ask > allow` order, so a typed allow cannot override an ordinary deny or ask. The folder filter applies once at Run admission; the pinned digest still covers the whole file, and settings never reload during a Run. A configuration read without a Workspace identity ignores folder-scoped allows and still applies folder-scoped deny and ask rules.

The only writer is the typed settings edit behind `/permissions` and the remember choice below. Inside the account replacement lock it rereads and validates the whole file, compares the SHA-256 the user saw (absent versus present included), revalidates the folder identity, applies one insert, decision change or removal, validates the result and replaces the private file atomically; other settings keep their values. A stale view, a busy lock or an overflow refuses with a fresh-load notice and no retry or truncation; a failure after the replacement may still have taken effect and reports `save not confirmed`. `/permissions` may create a missing file with `defaultMode: "default"` and says that doing so also activates default permission policy for other Tools; the remember choice never creates the file.

At a human approval for a primary local Git write that no rule or hook decided, the dialog offers `Yes, and allow git commit in this folder from the next Run` (or `git branch` or `git switch`). The human verdict is committed first (source `human`); only then is the rule appended to the existing file, and a failed save denies the pending call with the approved verdict already journaled; a save whose final directory sync fails after the rename may already be in effect, so it is journaled as an Uncertain `rule save not confirmed` outcome that stops the Run, dispatches nothing and is never retried. The separate [host-prefix save](#remembered-host-prefixes) uses the same atomic settings writer; settings dialogs report an unconfirmed replacement as uncertain rather than as kept. The current action is approved by that one-use reply, the Run keeps its pinned rules, so another matching call in the same Run still asks, and the saved rule applies from the next admission. Replay never saves. The choice is offered only when `permissions.json` already pinned the Run, so remembering never activates settings for other Tools, and never for children, branch listing, hook asks, explicit ask rules, serve or ACP clients, or an `exec` Run with no human. Settings edits bind the folder identity captured when `/permissions` loaded them or the Run admitted it; a replaced directory refuses. `/permissions` lists, adds, changes and removes rules when no Run is active.

## Human-approved host Git

The primary may request `git_push {remote, branch}`, `gh_pr_create {repository, base, head, title, body, draft}`, `gh_pr_list {repository, state, base, head, limit}` or `gh_pr_view {repository, number}`. These use the separate `host` execution class, authorized by the owner-approved exception in [AGENTS.md](../../AGENTS.md), and are never Guard-attested. They reuse the typed Git catalog, immutable intent, permission verdict, action reservation and committed observation. Writes retain the whole-Workspace Git/write grant and Workspace writer lock. PR operations require an explicit native `gh` Program pin in the user-owned Tool configuration's `commands` list; neither PATH nor repository files choose it. Children receive none of these operations. The primary catalog offers push only when the admission snapshot contains user Git configuration or an SSH-agent socket, and PR operations only with a captured gh authentication record and its native Program pin. Catalog generation never rereads authentication files or the environment; the snapshot indicates availability, not successful authentication or authorization to dispatch. The implementation follows peers' use of the user's existing Git credentials and gh authentication.

### Host pull request inspection

`gh_pr_view {repository, number}` is a primary-only read of one PR. The repository is an explicit admitted `host/owner/repository` under the [PR-listing repository bounds](#host-pull-request-listing); the number is 1–2,147,483,647. The user-owned gh authentication host must match. The Tool runs fixed `gh pr view NUMBER --repo HOST/OWNER/REPO --json ...` scalar fields, then one fixed `gh api graphql --hostname HOST --method POST --input -` request with adapter-generated JSON variables. The returned HTML URL and PR number must match the admitted repository and requested number: scheme, host, route and number are exact, while ASCII owner and repository names compare case-insensitively, as [GitHub documents for repository identity](https://docs.github.com/en/rest/repos/repos#get-a-repository). The request includes the latest 50 issue comments, latest 50 reviews, and at most 100 check/status contexts on the queried head; it never paginates, accepts a caller query, follows a returned URL, or mutates a PR.

A matching user-owned `gh pr view` typed prefix allow rule or human approval is required under the same mode handling and child restrictions as [`gh_pr_list`](#host-pull-request-listing). Both subprocesses share one deadline narrowed by Goal allowance, using the [PR-listing runtime and per-stream capture bounds](#host-pull-request-listing). The query body is capped at 8 KiB. At most 200 discussion/check rows are retained. For responses within the capture bounds, body, comment and review text are clipped to 8 KiB each; title and other strings follow the [PR-listing text bounds](#host-pull-request-listing). Field and connection truncation are explicit, and the pinned Tool result budget takes precedence. Budget trimming retains the newest fetched comments and reviews and the first fetched check/status contexts. If the fixed PR fields still cannot fit after trimming, the Tool reports a local result-budget failure with no PR data, retaining the exit-zero host receipt; it does not classify the response as malformed GitHub data. GraphQL errors fail even when gh exits successfully. Null or missing status remains unknown; empty checks means none reported. A changed head OID between the scalar and GraphQL observations sets `stale: true` and retains both head identities, so old description and current checks are not presented as one snapshot. The result is historical data, not instruction or authority. Confirmed auth/API/parse failures are Failed; an interrupted dispatched process without confirmed completion and cleanup is Uncertain and stops continuation. Replay uses only the committed bounded observation.

### Host pull request listing

`gh_pr_list` is a primary-only remote read. It uses the explicit admitted `host/owner/repository`, `gh pr list`, a fixed JSON field set, null-normalized `state: open` and `limit: 30`, optional exact base/head names, and a limit of 1–50. State is one of `open`, `closed`, `merged` or `all`; repository is at most 256 bytes and base/head are at most 128 bytes, control-free and validated before argv construction. The user-owned `gh` authentication host must match the repository host. No local repository discovery, arbitrary API request, browser, pagination, mutation or URL following is available.

The read asks for a human in every mode that asks. A matching user-owned `gh pr list` typed prefix allow rule may pre-approve it in any mode, including Plan, Auto and headless/ACP; the exact typed rules remain subordinate to deny and ask. Ordinary rules, repository content, hooks, AI review, upfront grants and child authority cannot approve it. Without a human channel or matching typed allow, the read is refused before dispatch. The approval surface identifies host execution, the exact repository and filters, and private PR disclosure to the current Provider. Before saving a typed rule that allows this read, including changing an existing ask or deny rule, the rule editor repeats the disclosure and requires explicit confirmation.

One fixed command runs through the pinned S3 gh copy and existing host supervisor. Stdout is capped at 256 KiB, stderr at 4 KiB and runtime at 20 seconds, narrowed by the Goal allowance. At most 50 rows are retained; title is clipped to 256 bytes and other strings to 2 KiB with truncation fields. A result at the requested limit reports `possibly_more: true`; no total count is inferred. Empty output is a successful empty list. Invalid or oversized JSON and confirmed API/auth failures are Failed; an interrupted dispatch with no captured completion is Uncertain and stops continuation, even after local cleanup is confirmed. Cleanup does not establish the remote read outcome. The committed result is replayed without another process, network request or credential read.

**Intent and approval.** Failure to pin host source data refuses before approval or dispatch with `Host source data is unavailable; no operation was dispatched`, rather than a grant-scope refusal; hook denials retain precedence. Push accepts one literal credential-free `https://host/path` or `ssh://git@host/path` URL and an existing local branch. Repository remote aliases, userinfo/passwords, ports, query strings, fragments, local/file/ext transports and ambiguous routing refuse. Its immutable intent includes the exact local source object ID and `OID:refs/heads/branch` refspec; there is no force, deletion, follow-tags or recursive submodule push. PR creation pins `host/owner/repository`, base, head, title, body and draft. Its local head object ID detects local drift before dispatch; it does not bind the remote PR commit. The approval explicitly says the PR uses the remote head branch at creation and does not display the local OID as its source. A preflight remote-ref query cannot prevent a subsequent remote branch update. Push and PR creation require separate one-use approvals showing the entire normalized destination and payload. PR body lines are escaped and indented beneath `Body:` so they cannot impersonate approval fields. For writes, the ordinary and typed rule precedence remains deny > ask > allow, but neither allow nor Auto review can authorize a host effect. Default, acceptEdits and Auto ask a human; plan and dontAsk deny. Missing, dropped, denied or cancelled human approval dispatches nothing. ACP's channel without human-only attestation refuses; a human-capable serve channel may approve. Write prompts offer once/deny only. A committed `ToolStarted` verdict with source `human` precedes process launch; replay rejects rule-only or AI-only host write approval and any Guard or unguarded receipt for that intent.

**Execution and credentials.** Authentication choices are captured at Run admission from the launching user's configuration and environment, before repository Skill discovery. HTTPS snapshots the user-owned XDG Git config and then `~/.gitconfig` (64 KiB per file). The pinned Git reads all credential entries in file order with `config --file … --no-includes --null --get-regexp`; the query also detects include/includeIf entries, whose presence refuses because omitted included files could contain credential resets. All credential keys and values are passed in order through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, never process arguments. Git itself applies every matching section, ordered helper resets and helper chains, username and useHttpPath; Arany does not select one most-specific helper. The query has a five-second deadline, 128 KiB stdout cap, 256-entry cap and 4 KiB stderr cap, with explicit private GIT_DIR and a discovery ceiling. Missing or malformed credential configuration refuses; an intentional reset remains effective. Repository helper settings never apply. Helper search uses only admitted, root- or user-owned, non-group/other-writable `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and `/bin`, after the private pinned Git directory; unsafe or unavailable directories are skipped, and no admitted directory produces a specific refusal. No ambient PATH applies. SSH requires the launching `SSH_AUTH_SOCK`, uses fixed `/usr/bin/ssh` with no SSH config, batch mode, no identity files or forwarding and strict host-key checking. Missing helpers or agents refuse; no login or interactive prompt is started. gh uses the user's existing bounded `hosts.yml` authentication record in an exclusively created 0600 file inside a 0700 temporary configuration directory, with the same home for its own credential store. Host scratch lives under the admitted State root in an owner-only, non-symlink `host-scratch` directory, independent of `TMPDIR`. There are 64 fixed scratch slots per State root; exhaustion refuses before dispatch. Each slot has a persistent private lease file outside its scratch directory, locked before the directory is created and held through removal. Engine startup examines every slot and removes stale private directories only while holding their leases, preserving active operations and concurrent creation. Normal teardown removes its directory before releasing the lease. Pinned Program verification and the gh private copy have a separate 256 MiB executable limit. The gh executable is streamed once through a 64 KiB buffer into an exclusive 0500 file while hashing; a digest mismatch or copy failure unlinks the partial file. Only after verification does that copy execute; those verified bytes are executed on Linux and macOS. The permitted host defaults to github.com; a literal `host:` in the user's gh config may select another. User config must be an admitted regular file owned by the current user and not writable by group or others. Credential values are never included in intents, catalog, Provider context, journal, diagnostics or result text.

Every host write runs from a disposable neutralized repository view with only the approved branch ref, HEAD and fixed config private. Push links the admitted object store for Git to read; it never copies or counts its objects. PR creation gets an empty object directory. PR listing and inspection use an empty private Git directory and an explicit repository; they never inspect the Workspace repository. No host Git process discovers live repository config, and no incidental tracking-ref update reaches it. Unsupported layouts and object alternates refuse for writes. Host write admission retains the HEAD 256-byte and repository config 64 KiB bounds and shared layout checks, but never reads the index; the 32 MiB index bound applies to local Git views only. Packed-ref admission and shallow metadata are bounded to 32 MiB each; the separate executable bound does not raise Guard snapshot or runtime-capture limits. A preparation limit refusal names these bounds. The object link is not an OS read-only mount: this host class relies on the fixed push command reading objects without mutation. After a dispatched push, Arany rechecks the Git directory and object-store identities and absence of alternates; a mismatch records Uncertain. A concurrent replacement restored before that check, or an alternate briefly introduced during execution, is not prevented or detected reliably. Repository includes, conditional includes, sshCommand, insteadOf, pushurl, hooks, filters, signing, aliases, pagers, editors and extensions supply no authority. Environment is cleared; Git system/global config and interactive auth are disabled. HTTPS redirects are disabled. gh receives fixed operation arguments and an explicit repository, so it cannot implicitly push, fork, paginate or select another repository. User credential helpers remain user-authorized host code, not an Arany credential adapter. Only the primary Git and gh binaries are hash-pinned: system `/usr/bin/ssh`, Git's installed `git-remote-https`, their libraries and user-selected helpers remain trusted installed host components. A user or administrator able to replace those components can change their behavior; the private gh copy does not pin those transitive dependencies, on either platform.

**Bounds and outcomes.** The Host Git row in [Limits and failure behavior](#limits-and-failure-behavior) defines payload and runtime bounds. Malformed/control-bearing write data refuses (body newlines are allowed). The existing primary scheduling and Workspace writer lock allow one Git write in flight per Workspace. After approval, one monotonic runtime deadline starts at host entry and covers scratch acquisition, preparation, credential setup and process execution; preparation timeout refuses before dispatch, and the existing cleanup allowance remains separate. The [shared approval contract](#folder-trust-and-approvals) governs human waiting without a wall-clock expiry; waiting does not consume Goal active time or the host runtime allowance, and elapsed approval time cannot invalidate the approved intent. Cancellation and the runtime deadline are rechecked immediately before spawn. Stdout and stderr use the shared Typed Git reads capture caps in [Limits and failure behavior](#limits-and-failure-behavior); host overflow terminates the process group. Raw process output is discarded, including on errors, to prevent credential disclosure. A confirmed zero exit with confirmed group teardown records a host receipt and fixed completion text, also shown in the Tool summary; a confirmed exit 1 with exactly one Git porcelain rejection for the pinned refspec, `(non-fast-forward)` or `(fetch first)`, records Failed with fixed “remote reported no ref update” text. This does not mean no dispatch or upload occurred: HTTPS can upload a pack before rejection. For PR listing or inspection, confirmed nonzero exit, invalid JSON or capture overflow is Failed with fixed bounded text; timeout, cancellation after launch, lost acknowledgement or unconfirmed teardown is Uncertain and stops continuation. Authentication errors for writes and gh's PR-already-exists diagnostics do not prove absence of a remote effect and remain Uncertain. A crash after the committed approval without an outcome remains unresolved on replay. Rewind marks host effects non-rewindable when they have a Host receipt, an Uncertain outcome, or approval without an outcome; it never claims to undo a remote push or PR. No write automatically retries, completes or rolls back. Terminal, transcript, exec/show, Provider observations and Goal reports mark the class `host`.

Host execution does not enforce Guard filesystem, network, CPU, memory or process-count isolation, bound remote transfer/storage, isolate DNS destinations, or contain descendants escaping the process group. Human approval and time/output bounds are the v1 controls. Linux/macOS use the same supervision path with the platform-pinned Git; native credentials, keychains, teardown and terminal accessibility require the owner-run evidence in [NEXT_STEPS](../../NEXT_STEPS.md).

## Typed Git writes

Typed Git writes let the primary commit, create branches and switch like [Claude Code](https://code.claude.com/docs/en/permissions#bash) and Codex CLI agents running `git` in the Workspace, while keeping per-effect isolation: Git runs inside the Guard on a neutralized private view, and only Arany's own code publishes the validated result into the real repository. [Human-approved host Git](#human-approved-host-git) owns push and PR creation. [Typed prefix rules](#typed-prefix-rules) remember and revoke approval for the three local verbs.

1. **Availability.** They need the [typed Git read](#typed-git-reads) pin, its whole-Workspace grant, `write: true` and Linux Landlock ABI 3 or later (below); otherwise the catalog lists only the reads, among them `git_branch` with a schema that fixes `name` and `start_point` to null, so branches can still be listed, for example in plan mode. **Git writes are refused on macOS**: they are not offered and a proposal is denied before dispatch, because Seatbelt cannot further restrict a child of the already sandboxed Guard worker; [next steps](../../NEXT_STEPS.md) record the planned separate Git executor. They are offered only to the primary, never to researchers or editors, are never Goal success criteria, and a plan contract admits them only with `.` scope. Unsupported layouts and formats fail as for reads.
2. **Operations.** `git_commit {message, paths, staged}` commits to the current local branch: either distinct literal Workspace-relative `paths` (`.` for every change, even beside other paths), whose working-tree contents are added (including new and deleted files) and committed with Git's `--only` semantics, or `staged: true` with empty `paths`, committing the staged index. Other staged entries stay staged. The message is non-blank UTF-8 without controls other than newline and tab; Git's default whitespace cleanup applies. In paths mode protected path components are excluded as for reads and stay uncommitted; staged mode commits the index exactly as staged. `git_branch {name, start_point, scope, base, max_count}` with `name: null` uses the [branch discovery read](#branch-discovery); creation requires `scope`, `base` and `max_count` null and creates `name` at `start_point` (a read revision, or HEAD when null) without switching or tracking, and an existing name fails. A start point naming a symbolic ref other than HEAD (any `ref:` content, as Git's files backend parses it), such as `origin/HEAD` or a bare remote name, refuses, and so does a branch while HEAD points to a ref outside `refs/heads`: name the branch it points to, since only direct refs and HEAD's referent are held. Names use the read ref-name grammar without ancestry steps, never `HEAD`, and may not differ only by ASCII case from an existing ref or ref directory. `git_switch {branch}` moves HEAD to an existing local branch; the current branch returns `switched: false` and publishes nothing. There is no amend, signing, force, delete, detach, merge, remote or raw-argument escape.
3. **Results and receipts.** A commit returns `{"commit","branch","publication"}`, a creation `{"branch","oid","publication"}` and a switch `{"branch","switched","files","publication"}`. The receipt `publication` is `{"objects","files"}` plus, as applicable, `"ref": {"name","before","after"}` (object names, `before` null for a new branch), `"index": {"before","after"}` (SHA-256 of the real index bytes, `before` null when absent) and `"head": {"before","after"}`. Failures return `{"failed"}` with filtered diagnostics, as for reads, and publish nothing; under Read-rule result filtering a failure keeps only its message and a switch refusal counts, but never names, a hidden path. Receipts carry object names and branch names, never file paths.
4. **Neutralized mutable view.** A fresh view in Guard scratch holds a fixed configuration (the read settings plus `logAllRefUpdates`, `commit.gpgSign`, `gc.auto` and `maintenance.auto` off), copies of HEAD, the index with its mtime, `packed-refs`, `shallow` and the `refs` tree (another Git's `*.lock` is skipped), and a private object directory that borrows the real store as an alternate, so every new object stays private until publication. Each Git child is spawned from a thread confined by a Landlock domain (ABI 3 or later, so truncation is mediated) that denies every write, truncation, link, rename and node creation outside Guard scratch and `/dev/null`, and by seccomp filters that deny mode, owner, time, extended-attribute and `file_setattr` changes everywhere, answer `ENOSYS` (an older kernel, to libc) for every syscall newer than the last one the policy knows, so a future metadata setter fails closed, and deny every `ioctl` (answered `ENOTTY`, since inode-flag, fsxattr and filesystem-version requests change metadata through a read-only descriptor and Git without a terminal needs none), which Landlock does not mediate. The child inherits both, so Git can read the Workspace and real `.git` but never change them, while the Guard keeps its access for validated publication. An older kernel or a missing facility fails closed before Git runs. Repository configuration, includes, conditional includes, hooks, aliases, `core.sshCommand`, filter, diff and merge drivers, signing programs and fsmonitor never apply. The closed read environment gains only `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`; commits use `--no-verify` and `--no-gpg-sign`, and timestamps are UTC. Reflog entries are not written.
5. **Identity.** Private `tools.json` may set `git_identity` (`name` and `email`, without controls, `<` or `>`, no whitespace in the email). Folder trust reads `user.name` and `user.email` from `$XDG_CONFIG_HOME/git/config` (default `~/.config/git/config`) and then `~/.gitconfig`, the later file winning per key, as data only: other keys, `include`, `includeIf`, escapes and environment overrides are ignored, so a per-directory identity from a conditional include is not applied. Without both values the commit uses `Arany <arany@localhost.invalid>`. Repository configuration never supplies the identity.
6. **Commit and branch rules.** A commit needs HEAD on a local branch, and a switch refuses from a detached HEAD because no reflog entry would keep its commits reachable; creating a branch from a detached HEAD is allowed, as in Git, and moves nothing. A repository with `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, `rebase-merge`, `rebase-apply` or `sequencer` refuses commits and switches; finish or abort that operation first. Git itself refuses an empty commit and unmerged entries. An unborn branch can receive its first commit.
7. **Switch rules.** After a private index refresh, the switch refuses when any path changed between HEAD and the target is modified in the index or working tree, when an untracked or ignored file or directory occupies an added path, when an entry is a symbolic link or submodule, when a path is protected, invalid or too deep, and when two planned paths, or any of their parent directories, differ only by ASCII case, or one aliases an existing Workspace name by case; the failure lists the first conflicting paths. A file-to-directory or directory-to-file transition refuses with a dedicated message directing the user to switch in their own terminal, even when the working tree is clean. Each preimage is captured only when its bytes and executable bit still equal HEAD's blob, so an edit racing the check refuses instead of being overwritten. It writes raw blob contents without end-of-line or attribute conversion, creates new files `0600` (`0700` when executable) as typed writes do, removes deleted files and leaves emptied directories. The new index comes from Git's two-tree `read-tree -m`, keeping unrelated staged entries.
8. **Publication.** Before the first effect the Guard creates Git-compatible exclusive locks for every target it replaces or read: the branch ref, `index` and HEAD (`HEAD.lock` is held even when a commit leaves HEAD unchanged), a switch's source and target refs, a new branch's start ref under Git's lookup order (HEAD's referent by default), and `packed-refs`. Every ref path component is admitted with exact case against its directory first; a directory a lock creates is synced into its parent, and removed again unless the lock commits. Under those locks it requires HEAD, `packed-refs`, every loose ref and the index digest to equal the snapshot the view was built from, so a commit can never replace a ref that advanced after the snapshot. A held lock, any drift or a replaced `.git` returns `Failed` with nothing published; locks that were only held are removed after publication. Before its first lock the Guard writes `.git/arany-locks-<intent>.json` and records each lock's path, device, inode and SHA-256 as it takes it; the record goes once the locks are gone. If the Guard dies, exclusion over those locks can no longer be proven, so nothing moves or deletes them: the controller (once the Guard unit is confirmed stopped) and Goal resume (once private recovery confirms the unit is gone) report every recorded lock that is still the recorded inode with the recorded bytes as the typed `StaleGitLocks` error, which names the paths and says to remove them after checking that no git process is running. The controller puts that report first in the write's journaled `Uncertain` observation, so `show`, `exec` and serve carry it whole and the terminal row wraps it, escaped, across at most eight continuation rows before an explicit remainder count. Record paths admit only the typed ref-name alphabet, and every CLI error line is escaped like other untrusted text; Goal resume returns it before refusing to resume past the unsettled write. Another inode or other bytes at a recorded path belong to someone else and are not reported. When no recorded lock remains, the record itself is removed. Publication is never retried. It then publishes switched Workspace files through the [changeset publisher](#command-changesets) (digest-checked, no-follow, fresh inodes), new loose objects (content-addressed `0444` files renamed without replacement; an existing object is kept), and renames the ref, index and HEAD locks, syncing each directory. This is not a transaction: after the first effect any failure records `Uncertain`, stops the Run and is never retried; reopen and strict replay neither complete nor roll it back. [Rewind](#checkpoints-and-rewind) does not undo Git writes.
9. **Policy.** Creating a branch, committing and switching ask like commands: Request and Auto edits ask a human, Auto approval reviews them and `plan` denies them. A matching allow rule, ordinary (naming `git_commit`, `git_branch` or `git_switch`) or typed for its verb, pre-approves them in `default` and is required for `dontAsk` to permit them; `acceptEdits` and `auto` ignore it, and the [typed-allow mode mapping](#modes-and-approval-decisions) owns the rest. Rules and hooks only narrow; the Guard and pinned grant still apply. The receipt and every refusal are journaled as for other effects. The [limits table](#limits-and-failure-behavior) owns every bound; a result budget below its minimum records `Limit` before any effect.
10. **Platforms and non-claims.** Git still reads the whole Workspace under the Guard, as reads do. Linked worktrees, submodules and signing remain unsupported, and macOS refuses Git writes as item 1 states.

## In-process file operations

Execution-site dispatch stays inside `ToolRuntime::execute` using the typed operation and safe file-type admission. A `ToolExecutor` trait with interchangeable InProcess and Guard
adapters was rejected: the sites enforce different contracts, and a fake Guard
could make Engine tests pass without exercising enforcement.

Per-dispatch queue progress, active-action and checkpoint channels are composed
with consuming `ToolRuntime` builders. Guard dispatch takes one owned runtime
copy from its borrowed baseline before adding those channels; queue accounting,
checkpoint gates and cancellation retain their existing per-dispatch lifetimes.

Exact Read, exact-file Search and Skill text reads run in the Engine process, following peer explicit-file access. List, directory Search and Glob run in the resource-owned Guard because their ignore parser consumes hostile repository data. Write, Edit, MultiEdit, Mkdir, Delete, Move and primary ApplyChangeset publication run in process on Linux and macOS, following Claude Code's CLI-owned exact replacement and Codex CLI's in-process patch application. Typed Git reads, commands, Skill loading, Skill scripts and MCP retain their Guard paths. Editor typed mutations use this same in-process path under their child identity and lease. The Engine opens the Workspace directory handle once at Tool admission, which still requires available native protection, and resolves paths beneath it with no-follow, link, mount, special-file and protected-name checks and the same `workspace_paths` scope. Before dispatch it checks the intent, policy digest and admitted directory identity. Replacing the Workspace records Failed at `pinned input` without attestation. A failed discovery operation never starts an exact read. After Workspace identity validation, the in-process reader rechecks exact-file type-probe errors and records persistent missing or unsafe paths as attested Failed or Denied observations that permit continuation. It requires an admitted regular file again before returning content.

Within a primary or researcher multi-call step, admitted exact Read, exact-file Search and Skill text calls run concurrently under the existing [process-wide file-operation capacity](#limits-and-failure-behavior). Each retains its own result and runtime bounds; capacity exhaustion records Limit without reading. [Execution](./execution.md#committed-event-stream) owns step ordering relative to other calls and Provider observation order. A path that ceases to be an exact file cannot fall back to Guard discovery during concurrent dispatch. Read completions continue to commit while a sibling waits for hooks, review or approval. Cancellation, Uncertain, Limit or a hook stop prevents further dispatch, withdraws a pending sibling approval, drains already dispatched reads and gives each remaining intent a `not_dispatched` observation. Started hooks and reviews settle under their existing bounds; further admission handlers and approval escalation do not start after a stopping completion. Late approval replies cannot dispatch the withdrawn call. This follows [Claude Code's concurrent read-only Tools](https://code.claude.com/docs/en/agent-sdk/agent-loop#parallel-tool-execution) and [Codex CLI's parallel-safe Tool dispatch](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/parallel.rs).

Results fit the intent's rendered (model-facing serialized) result budget: List and Glob drop trailing rows and set `may_be_truncated`, Search pages as [below](#limits-and-failure-behavior); a budget too small for any content is Limit. Read follows Claude Code's 1-based line paging. Its nullable integer `offset` defaults to 1; nullable `limit` defaults to and caps at [`MAX_READ_PAGE_LINES`](./limits.md#max_read_page_lines), and each line is cut at [`MAX_READ_LINE_CHARS`](./limits.md#max_read_line_chars) characters. Both fields may be omitted or null. It streams the admitted regular file and its whole-file SHA-256, returns numbered `N\t` lines, and marks a cut line with `… [line truncated to <MAX_READ_LINE_CHARS> chars]`. CRLF is a single line ending; invalid UTF-8 fails. The result is `{sha256, total_lines, start_line, end_line, next_line, truncated, text}`. The page ends at the line limit or rendered budget; `next_line` is the next unread line, or null at EOF. `truncated` marks more pages or a cut line. Empty files and offsets past EOF return empty text, the file's `total_lines`, `end_line: start_line - 1` and null `next_line`. Each page is the committed observation; replay never rereads the file. A read is bounded by its intent runtime: timeout records Limit and cancellation records Cancelled, neither attested. It waits for no Guard capacity and reserves its Goal action with zero preparation overhead, so exhausted active time refuses it and its runtime is clamped to the remaining active time.

`Read { path: "spill:<digest>", offset, limit }` uses the same paging grammar through a separate admitted private-directory capability. The digest must be exactly 64 lowercase hexadecimal characters; every other `spill:` shape rejects before opening. Only references committed in this Session’s own Runs, including the current Run, authorize access; guessed files, other Sessions and inherited fork history grant nothing. Workspace and plan path scopes do not select this capability; ordinary Read permission restrictions still apply. Missing or unknown references record attested `Failed` with `no spill for this Run`. No-follow, owner, private mode, single-link, regular-file and same-device checks apply. The Guard receives neither StateRoot paths nor handles.

A valid, in-scope, non-protected missing path (including a non-directory regular-file ancestor) records attested `Failed` with `File or directory not found; List the parent directory to check the path`, following OpenCode's not-found distinction without path suggestions. Link, mount and special-file refusals remain `Denied` with `File path is unavailable or outside the admitted regular-file boundary`; protected-name and out-of-scope paths retain their pinned-grant denial.

Each observation carries an `attestation`: `in_process` with the policy digest and Workspace device and inode, or `guard` with the Guard receipt. Validation and replay reject in-process attestations for List and Glob. Successful Workspace mutations require an additive `FileReceipt { intent_digest, before, after, executable }` inside the in-process attestation; reads omit that field. The receipt binds the immutable intent and publication result; Move preserves the content digest, Delete has no after digest, and Mkdir and batch ApplyChangeset have no single-file digests. Batch preconditions and versions remain pinned in the intent. The in-process file enforcement digest distinguishes new mutation intents from historical native Guard intents, whose receipts still replay unchanged; Guard receipts and bootstrap causes reject for the new profile. Filesystem diagnostics identify File enforcement for this profile while historical Guard labels remain unchanged. Skill reads require in-process attestations; Guard receipts and Guard-bootstrap causes are invalid for them. Live Guard dispatch admits discovery intents and refuses exact Read and Skill text intents. Discovery receipts identify the native enforcement profile; worker discovery wraps that receipt in `worker_read`. In-process file operations run with the Engine's ambient privileges: their boundary is the handle-relative checks; they never spawn or use the network.

Native file writes use digest or create preconditions, no-follow handles and a fresh inode plus atomic replacement, never in-place truncation of an aliased inode. Parent directories must already exist; a missing Write or Mkdir parent records attested `Failed` with `Parent directory not found; create it with Mkdir first`. A missing Edit or MultiEdit target uses the [in-process read not-found result](#in-process-file-operations). Symlinks, hard links, special files and stale preconditions reject. This is not a transaction against concurrent host edits, a rollback guarantee, or protection from a hostile same-user or root process.

ToolStarted commits before any mutation byte is written. A blocking task retains its file-operation capacity slot until it exits. Cancellation is checked before temporary creation and publication; after publication begins it completes and records success before the Run stops as Cancelled. Deadline expiry prevents publication if it has not begun (Limit); after publication begins it is Uncertain and stops the Run. Failed temporary writes or pre-publication renames leave the target unchanged; a failed parent-directory sync after publication is Uncertain. Process death between publication and ToolFinished leaves an Interrupted intent; resume never retries it. Checkpoint capture precedes dispatch through the Engine's existing Store owner. These operations have no Guard preparation or pre-GO stage.

### Typed read discovery

List, directory Search, Glob and [file suggestions](./terminal.md#interactive-commands-and-completion) apply the shared [ignore-control admission](#command-input-selection) before opening payloads. Only admitted root/nested `.gitignore` data supplies rules, including outside Git repositories. Nested precedence, escapes, ordered negation and ancestor pruning are shared with command selection; tracked files have no exemption. Naming a nested or ignored directory keeps all ancestor rules. Query patterns only narrow visible candidates. Fixed protected names, generated-directory exclusions, grants and restrictive Read rules remain independent and dominant, including case variants and descendants. An inaccessible required control rejects generically; confirmed absence is allowed.

List and Glob inspect metadata only, including restricted-grant List. Disappearing descendants and absent configured scope roots are omitted from discovery; an explicitly missing requested base retains the attested not-found result. Required-control changes still reject the whole selection. Directory Search opens only selected regular files after exclusion and preserves its existing matching and pagination. Filtering precedes visible sorting, pagination and fitting. Exact Read and exact-file Search of an otherwise admitted ignored file retain their permission decisions and bounds without loading controls; protected names remain refused. Explicit includes, Skills, commands and Git disclosure keep their separate contracts. There is no model-controlled ignore override. Compared with Claude's default Glob and peer listings, the consistent omission across typed discovery deliberately narrows incidental disclosure.

Typed discovery selection runs single-threaded in the default native unit, with the existing 512 MiB envelope and shared FIFO capacity. Typed discovery waits at most 250 ms for capacity, including admission locks and recovery. The [Terminal contract](./terminal.md#interactive-commands-and-completion) owns local composer suggestions and their resource admission. Full capacity or wait expiry is busy (`QueueFull`, model `Limit / ReadCapacity`) without dispatch or retry. Selection is bounded by 1,048,576 matcher calls, including ancestor checks, and two seconds, shortened by the Tool/Goal deadline. Count or expansion exhaustion is `Limit(resource)`; elapsed selection time is `Limit(timeout)`. Each walk retains the existing scan/path/content/result bounds and depth 16, including control filenames. Failure discards partial results; cancellation retains ownership until confirmed cleanup. Neither failure nor cancellation starts an exact Read or a host operation. Linux kernel ceilings and macOS supervised thresholds retain their documented differences. Strict replay projects committed observations without rereading controls, parsing patterns or rediscovering names.

### Glob file discovery

`glob` takes `{pattern, path, limit}` and returns admitted regular files whose path relative to `path` matches `pattern`, copying the call shape and 100-file default of Claude Code's Glob and OpenCode's glob. `pattern` is 1–512 UTF-8 bytes. `path` names a Workspace-relative directory and `limit` is 1–100; strict native schemas expose both as required nullable fields. Null or omitted values, and an empty `path`, normalize to `.` and 100 before the intent is hashed, so permissions, hooks and replay see one form. A zero or larger limit is refused, not clamped.

The grammar is closed and case-sensitive on both platforms. `/` separates components and the whole relative path must match. `*` matches zero or more characters and `?` one character within a component. `**` is permitted only as a whole component: `**/` crosses zero or more directories and a terminal `**` matches the rest of the path, so `*.rs` matches only files directly in `path`. One level of `{a,b}` supplies literal or wildcard alternatives inside a component, at most 16 alternatives across all groups. Bracket classes, backslash escapes, a leading `!`, absolute or `~` prefixes, controls, empty, `.` or `..` components, nested, empty, single or unclosed braces and a partial `**` are refused as invalid arguments before any traversal; no invalid syntax is reinterpreted as a literal. The pattern translates to a regular expression of at most 8 KiB, compiled with a 128 KiB size, a 32 KiB DFA cache and 32 nesting levels, and overflow refuses the call. Peer divergence: Claude Code also accepts bracket classes; Arany refuses them to keep the discovery grammar closed. Permission path patterns keep their own separate translation and semantics.

Discovery reads metadata only. It never opens file contents, so sizes beyond the 1 MiB content cap are reported, and no SHA-256 or edit precondition is implied; use Read for those. It walks with the no-follow handles, `workspace_paths` scope and protected-name exclusions of List: protected components (`.env`, `.env.*`, `.git` and the rest), symbolic links, hard-linked and special files, other mounts and non-UTF-8 names are skipped, and a whole-project grant also skips `target`, `node_modules`, `.venv` and `venv`. Other hidden names match like any name. A pattern without `**` does not descend past its component count. The walk inspects at most 8,192 directory entries and retains at most 2,048 matching files, at depth at most 16 and with paths of at most 512 bytes; exceeding any bound records Limit, never a partial success.

The result is `{entries: [{path, bytes}], limit, may_be_truncated}`: Workspace-relative paths, deduplicated across selected roots and sorted in UTF-8 byte order before the first `limit` entries are kept. `may_be_truncated` is true only when another match exists or trailing entries were dropped to fit the rendered result budget, so exactly `limit` matches is complete; matches that cannot fit at all record Limit. There is no paging: narrow `pattern` or `path` instead. Peer divergence: Claude Code orders by modification time; Arany uses path order so the committed observation does not depend on mutable timestamps. A `path` naming a regular file records Failed, a missing path the not-found result above, and a link, mount or special file is Denied. Editors discover the live Workspace through the same guarded Glob operation within their narrowed read grant; a missing leased creation root records the not-found result.

Evidence: the grammar and normalization tables in `tools::glob::tests`; `tools::tests::glob_returns_admitted_regular_files_in_path_order_with_honest_truncation` and `tools::tests::glob_never_discloses_protected_or_unadmitted_entries_and_bounds_its_walk` in the [Workspace corpus](../../crates/arany/src/tools/tests.rs); the live editor discovery journey in [the worker corpus](../../crates/arany-cli/tests/guard_runs/worker.rs); mapping and narrowing rows in `tool_mappings_cover_typed_operations_and_read_denials_cover_writes`, `hook_matchers_use_exact_alternatives_or_bounded_unanchored_regex` and `updated_input_accepts_only_provable_narrowing`; `session::reducer::tool::lifecycle::tests::discovery_replays_recorded_guard_observations_and_rejects_in_process_receipts`; and the closed-journal journey `in_process_reads_are_attested_and_replay_after_exit_or_a_crash`.

## Typed delete and move

`delete {path, expected_digest}` removes one existing regular file. `move {source, destination, expected_digest}` moves one existing regular file to an absent destination, creating missing destination parents. The digest is the exact lowercase SHA-256 of the source from Read or a file include. Move preserves the complete bytes, including binary content, and executable status. Neither operation removes directories or overwrites an existing destination; identical and ASCII case-only moves reject. Missing sources fail, stale source digests and occupied destinations conflict. Protected names, unsafe ancestors, links (including hard links), special files, set-ID files, mount crossings and filesystem aliases refuse under the existing file-publication boundary. The existing file-version, argument, result, action and checkpoint bounds apply; input or preflight overflow publishes nothing.

Both are Edit-family mutations under the existing write grant, permission modes, hooks and Goal scope. Move requires both paths within the grant, plan and any editor lease. A path allow must cover both paths in one rule; a deny or ask matching either path applies, and Read denials cover both. Hooks see the peer name `Edit` with the complete typed call; unsupported input rewrites deny. Researchers cannot invoke either operation. Editors need the corresponding `delete` or `move` capability and publish through the ordinary [Workspace mutation and checkpoint path](#editor-tool-steps). Primary effects refuse overlap with either path of an active editor lease.

One call is one immutable, journaled intent and one result. Primary and editor calls use the [in-process file publisher](#in-process-file-operations), including its receipt, deadline and cancellation rules; editor calls retain child permission/hook identity and ordinary Workspace receipts. The publisher validates the entire file changeset before publication, including source bytes/digest/executable status, absent destination and no-follow parent identities. Move publishes a fresh destination inode before deleting the source; the same checked deletion and directory synchronization used by changeset integration supplies the receipt. Move is not an atomic multi-file transaction. A failure or drift after any publication, lost completion or unconfirmed durability is Uncertain, stops continuation and never retries or claims rollback. Cancellation before publication changes nothing. A successful result retains the removed file's digest, byte length and executable status; the intent determines the source deletion and optional identical destination creation. Checkpoint capture saves the source before publication, and rewind restores it and removes the move destination. Structural parent directories follow the existing changeset policy. Strict replay validates those publication facts and receipts without reopening or mutating files.

[Codex CLI's apply-patch implementation](https://github.com/openai/codex/blob/main/codex-rs/apply-patch/src/lib.rs) supplies named-file deletion and move-as-destination-write/source-delete semantics with destination parent creation. [Claude Code's tool surface](https://code.claude.com/docs/en/tools-reference) routes file mutations through edit permissions and uses Bash for general filesystem commands. Arany exposes closed typed operations because generic command changes must pass separate changeset publication; it retains digest preconditions, an absent destination, bounded no-follow admission and journaled publication receipts to preserve its guarantees. Linux and macOS use the existing file publisher with no new native API or stronger durability claim.

## Atomic single-file MultiEdit

`multiedit` takes `{file_path, expected_digest, edits: [{old_string, new_string, replace_all}]}`. It edits one existing regular UTF-8 file, using Edit's admitted Workspace-relative path and required lowercase SHA-256 precondition. Unknown fields reject at both object levels. `replace_all` defaults to false; strict Provider schemas expose it as required nullable, with null also meaning false. Normalized intents serialize the effective boolean.

Apply 1–64 literal replacements in array order, each against the preceding result. False requires exactly one non-overlapping match; true replaces every non-overlapping match and requires at least one. Empty searches and identical old/new strings reject. A batch whose final content equals the original rejects. Replacement text stays literal, with no quote normalization, implicit newline removal or replacement-token expansion. Dependent edits such as A → B then B → C succeed. A missing or ambiguous later match leaves the original file unchanged.

Byte and size ceilings are owned by [Limits and failure behavior](#limits-and-failure-behavior): the file-operation row owns the replacement-string, MultiEdit input and file-size ceilings, and the Tool-context row owns the serialized-argument ceiling. The original, every intermediate result and the final content each stay within the file-size ceiling; sizing uses checked arithmetic before allocating a replacement. Overflow refuses the entire batch. At most 64 bounded transformation passes run, without recursive replacement or retry. Existing file-operation deadlines and result, context, Guard, checkpoint, worker and Goal bounds still apply.

The file publisher prepares the complete single-file change and publishes once through Edit's fresh-inode replacement, retaining before/after digests, byte lengths and executable bits. Readers see original or complete final content. Stale digests, invalid UTF-8, denied or unsafe paths, match failures and bounds failures publish nothing. Cancellation before publication changes nothing. Interrupted publication or failed durability confirmation remains Uncertain, stops continuation and never retries or claims rollback. One batch is one immutable intent, permission decision, Tool action and outcome, under the existing checkpoint policy; strict replay consumes its receipt and publication facts without reading or editing the current file.

MultiEdit uses the Edit permission family, including `acceptEdits`, path restrictions and read-denial protection. Hooks see `MultiEdit` and the complete bounded batch, under the existing hook-input ceiling; unsupported rewrites deny. Researchers cannot invoke it. An editor requires the explicit `multiedit` capability within the parent grant and its lease. Editors use the ordinary Workspace publisher with child lease validation and journaled checkpoints. Model results omit private checkpoint metadata. Terminal presentation shows one `MultiEdit(path, N edits)` outcome; approval presents every replacement in order.

Peer behavior: the replacement field names, false default, match-count checks, identical-string and unchanged-final-content rejection, and Edit permission family follow Claude Code 1.0.128 ([shipped-code evidence](../research/claude-code-multiedit-evidence.md)). Ordered intermediate-result semantics follow [OpenCode v1.1.13](https://github.com/anomalyco/opencode/blob/v1.1.13/packages/opencode/src/tool/multiedit.ts#L21-L35), the owner's accepted choice over Claude's original-file validation and cross-edit substring restriction. Existing-file-only scope and the 64-edit limit are owner decisions. Arany retains exact matching, digest-bound admission and one in-process Workspace publication to preserve its guarantees; it does not copy peers' implicit creation, fuzzy matching or partial/direct-write paths. Linux and macOS share the transformation and Workspace publisher, with no new native API or stronger durability claim.

Thresholds are supervised, not kernel ceilings: scheduling delays and work between samples can exceed them, and swap prohibition and kernel group-OOM enforcement are not claimed. The enforcement digest binds the native policy, class and effective values, including the command timeout and checked cache-view cap; it covers profile rules, admission algorithms and enforced constants, so changing an enforced dimension changes it. Missing or unknown profiles, mismatches between intent or receipt values and native enforcement, and receipts for another class reject. The 128-byte minimum result budget is the smallest admitted result. Mutation and failure receipts must fit it, retaining resource identity through the correlated intent rather than repeating a long path; Guard failure receipts contain only compiled stage labels. An applied mutation with a lost completion stays uncertain; receipt overflow cannot turn it into an ordinary retryable failure.

Search follows the controls of [Claude Code's Grep](https://code.claude.com/docs/en/tools-reference#grep-tool-behavior) and [OpenCode's grep](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/grep.ts#L13-L33) within one UTF-8 line of a named regular file or a directory under selected roots, inside the Guard for directory discovery, and in process for an exact file. The call is `{path, query, regex, include, case_sensitive, offset, limit}`: `path` and `query` are required, and native schemas expose the rest as required nullable fields whose null or omitted values default to `regex: false`, `include: null`, `case_sensitive: true`, `offset: 0` and `limit: 100`. Defaults are canonical before intent hashing and hook comparison, and a stored intent omits default options. `query` is 1–512 UTF-8 bytes, literal unless `regex` is true; regex mode uses Rust regex syntax without look-around or backreferences, `case_sensitive: false` uses Unicode case folding, and inline flags keep Rust semantics. `include` (1–512 bytes) filters paths relative to a directory `path`, or a named file's basename: `*` and `?` stay within a segment, `**` must be a whole segment (`**/` spans zero or more directories, a terminal `**` the rest of the path), and single-level `{a,b}` groups supply at most 16 alternatives in total; classes, escapes, negation, absolute or home prefixes, controls, empty, `.` or `..` segments and malformed or single-alternative braces reject, as [Glob](#glob-file-discovery) does through the same matcher. Unlike the peers' ripgrep globs, separator-free `*.rs` matches only the directory's own files (`**/*.rs` matches any depth), keeping one closed discovery grammar in which `*` never crosses `/`. Query and glob compile once per call with a 128 KiB compiled-size limit, 32 KiB DFA cache and nesting 32, the glob translation being at most 8 KiB; each line takes one boolean match, so matching stays linear in scanned bytes. An invalid, unsupported or over-limit pattern records attested `Failed`, in the Workspace and the WorkerView alike, with `Search pattern refused: <cause>; nothing was read` before any content is read, naming the regex syntax, regex size, glob syntax or glob limits, so the model can correct it as after a peer's Grep error; it never falls back to literal matching. A `limit` outside 1–100, an `offset` above 33,554,432 or an empty include rejects at decoding.

Authorization, protected names, ignored whole-project directories and scope apply before the filter, and an excluded file is never read. Rows are `{path, line, text}` with one-based line numbers and previews cut to 512 characters, ordered by Workspace-relative path in UTF-8 byte order and then line, independent of host locale. `offset` skips matching rows; at most `limit` rows plus one lookahead match are held, and skipped rows are never retained. The result is `{entries, limit, may_be_truncated, next_offset}`: `next_offset` is the requested offset plus the rows returned when another matching row exists, otherwise null, and `may_be_truncated` is true exactly when it is non-null. Fitting to the rendered budget drops only trailing rows and resumes at the first dropped one; matches with no fitting row record Limit, and an offset past the last match returns empty entries with null `next_offset`. Each page is a fresh bounded read, not a snapshot across calls; replay uses the committed observation. A timed-out scan stops at its next line. Whole-project trust preserves this for named files; directory enumeration never reads file contents. Search supplies no edit preconditions; use an `@` include's SHA-256 or a successful Read. No-follow checks, protected paths and scan, input and result bounds apply to both forms.

The pinned Tool catalog supplies the host clock in Unix milliseconds with an explicit UTC basis, so a current-date task does not depend on historical dates or a shell command. It grants no authority.

The [execution contract](./execution.md#accepted-outcomes) owns strict native-function and structured-text selection and rejection. Tool field descriptions explain nullable line-based Read paging and that Edit `old` must be non-empty exact text excluding Read line-number prefixes; typed validation and the Guard enforce limits. Descriptions are generation guidance, not permission or a live-model completion guarantee.

The primary completes file actions through correlated Tool continuations in planning and synthesis. A read needed for an edit is a Tool proposal in the same Run, not a request for the user to supply a result. Delegated researcher children inspect with read-only Tools; the primary performs edits and verifies its own evidence. `@` file references add bounded include snapshots labeled with their escaped relative path and the SHA-256 of the actual bytes; metadata counts toward the context budget. Trailing-slash directory references identify where to inspect without reading a directory as a file or granting access.

Native adapters present the bounded catalog and JSON outputs as structured task data, with ordered call, disposition and output observations rather than internal intents and receipts. Each observation carries a workspace-effect fact: inspection and disposable commands have none, attested successful mutations are applied, uncertain or cancelled mutations remain uncertain, and other mutations are not confirmed. Historical Tool context remains distinct untrusted data; the full intent, limits and Guard receipt remain canonical. Plain or malformed-JSON output stays an untrusted string. No result or catalog becomes instructions or authority, and inspecting a file produces no edit receipt. This representation improves model input, not a guarantee of live task completion. The primary Tool set never changes within a Run.

Except for the typed [`guard_bootstrap` continuation](#enforcement-failure-causes), Guard preparation, bootstrap or attestation failures before the GO dispatch gate record Failed without a receipt and stop the Run without another model call; strict replay rejects continuation or a successful answer after that failure, because nothing was dispatched. An attested ordinary Failed result may continue; Engine continuation and strict replay share this stopping rule. Beginning the GO write makes a subsequent missing completion conservatively uncertain, including a partial write. No unconfined fallback exists. Historical failures are previous-Run facts, not pending Tools; a fresh request may inspect current files and propose a newly authorized edit with fresh preconditions, never reusing a previous intent or approval.

The internal Guard task is one newline-delimited JSON frame of at most 1 MiB before its delimiter, enough for the largest Write, Edit or MultiEdit intent with its pinned configuration; the definition-only extension is described under [parser admission](#agent-definition-parser-admission), and Guard/rewind file-data transfers use separate bounded paths under [checkpoints and rewind](#checkpoints-and-rewind). Missing delimiters, oversized frames and malformed tasks reject before Ready or effects; the exact capacity remains admissible. Worker and supervisor reject trailing buffered input, including a valid GO coalesced with the task, before Ready. GO remains a separate one-use exchange.

The [execution contract](./execution.md#committed-event-stream) owns immutable proposal, review, approval, dispatch and observation ordering. An interrupted or uncertain effect stops the loop without automatic retry; inspect `arany show --output text SESSION_ID`, the private JSONL export and the actual files before intentionally retrying. Replay, resume, fork and compaction carry past Tool facts only as untrusted context and never execute an old intent or renew permission. JSONL is an explicit sensitive-data export.

The [execution admission contract](./execution.md#admission-persistence-and-recovery) owns complete-topology Event headroom, ancestor locking, compaction and fork quotas and pre-disclosure rejection. Logical headroom does not reserve physical disk or eliminate crash or disk-fault uncertainty after dispatch.

The worker names a failed teardown step with a closed stage (process cleanup, launcher reap, output EOF or storage cleanup) in its final line, which the controller reports as the Guard stage; no worker text reaches the model. Its only output is panic text, which its panic hook writes up to 4 KiB in total and drops beyond that; the runtime's fixed fatal-abort lines are the only other writes. Privileged OS mutation remains outside the current-user boundary.

Supervision uses kernel process identity and cumulative CPU accounting across exec. Reaped or replaced members retire after identity revalidation, including when sampling fails during exit; missing observation of a live member still rejects. Exact-incarnation signaling must not affect a reused PID.

These volumes are distinct, and enlarging one enlarges no Workspace bound. Admission reserves the exact backing sizes and rejects before GO if they do not fit shared capacity. Each unit's root is `/private/tmp/arany-u-<uuid>`; the live unit creates and locks `unit.lock` in one exclusive open, which the kernel releases when the controller exits, including on a crash. Before launching its job, the controller durably records the root's device, inode and macOS boot identity; the supervisor durably records its process and coalition identity before receiving a task, and no payload or attachment may precede this record. Normal completion, partial setup, cancellation and unwind require positively established process termination before detachment. Unexpected mount targets reject without being followed. Unfinished attachment or failed cleanup retains the control root and rejects completion rather than recursively deleting through a live or uncertain mount. Each volume is a fixed-size, case-sensitive image attached kernel-only, so a payload sees a case-sensitive filesystem even on a case-insensitive host.

Before creating a unit, admission scans at most 4096 directory entries and attempts recovery of at most eight unlocked roots owned by the effective uid, within one 30-second recovery deadline. Recovery takes an exclusive lock and validates private no-follow records and root identity before cleanup; live controllers and competing recovery owners are excluded. Within the recorded boot, recovery removes the exact one-use job and positively empties its recorded coalition by current audit-token identities. After reboot it never signals persisted identities or removes a job from the later boot. Storage cleanup requires the pinned backing image inode, the OS disk-image inventory and exact device and mount correspondence; unexpected or nested mount targets reject before detachment, and an attached but unmounted owned image must be detached. An interrupted-attachment marker clears only after positive absence following detachment of the positively identified image, or evidence that its recorded boot ended; empty inventory alone cannot settle a current-boot attachment. Recovery durably records positive observation before detachment. Root deletion also requires absence of all mounts beneath the checked root. Unlocked roots without valid ownership records, including older retained roots, stay untouched and count toward shared capacity with live and recovering roots, including roots interrupted before lock publication. Valid records are selected before the eight-attempt budget is spent. Unreadable or over-limit listings and deadline expiry reject as unavailable native protection without removal advice. A filename prefix never authorizes cleanup, and there is no stored-format migration. Cancellation or failure leaves recoverable records in place and never retries an old Tool intent.

Commands and MCP receive a fresh checked snapshot of the selected Workspace, including prior typed edits, and a separate read-only tree of pinned runtime resources. Writable project and scratch mounts prohibit set-ID behavior. Reviewed system executables must be immutable, root-owned, non-set-ID and unentitled; privileged process, credential and coalition changes stay denied after exec. When a grant enables commands or MCP, admission checks the bounded system-executable catalogue once per Run, and each process intent and receipt binds it to the compiled policy. Workers revalidate its no-follow identities, ownership, permissions, size and modification or change timestamps before Ready; changed or oversized catalogues reject before dispatch without refresh or retry. The catalogue is transient trusted-controller data within the Task byte cap; file and Skill workers carry none. An undetermined signature result excludes that program for that admission only. The runtime excludes host account and Session roots, network destinations and Mach services. Root or mismatched real and effective identities reject process dispatch. Ordinary unprivileged `fork`, `exec` and `posix_spawn` remain available. Unselected host paths have no general metadata grant; traversal ancestors such as `/private/tmp` and the unit control root grant metadata without listings, and admitted runtime directories stay readable. Commands also read the literal filesystem root because the native loader opens it, which lists top-level names without granting access beneath them. Exact runtime metadata covers native shell selection and system path aliases; it grants no subtree access to host account or temporary storage.

macOS uses private physical paths rather than a mount namespace. The command's working directory lies inside its project snapshot. Standalone argv paths rooted at `/workspace`, `/scratch`, `/cache`, `/inputs`, `/skills` or `/programs` map into private storage, and copied-program aliases apply to copied executables. Shell strings are not rewritten for Workspace aliases; scripts use `ARANY_TOOL_WORKSPACE`, `ARANY_TOOL_INPUTS`, `ARANY_TOOL_SKILLS` or project-relative paths. One narrow compatibility prefix is added only when the resolved executable is the pinned `/bin/sh` and argv begins with `-c`: it exports the fixed, quote-escaped page-size helper path before the original script and preserves the remaining argv. A missing script or an argument beginning with `-` or `+` immediately after `-c` rejects before the shell starts; the Guard never rewrites an option into script text or skips the required prefix. It does not expand Workspace aliases inside the script. `HOME` and `TMPDIR` point to private scratch. Checked system binaries execute at their original paths because native relocation is not universally supported.

The macOS command environment is cleared and adds `CURL_SSL_BACKEND=Secure-Transport` only when a Rust toolchain profile is selected, because Cargo's libcurl otherwise initializes LibreSSL, which reads `/private/etc/ssl` and fails under Seatbelt; `SDKROOT` is set only when the exact physical Apple SDK profile is selected. The Guard stages the embedded page-size compatibility dylib in its private runtime resources, reads it without following links under a 128 KiB cap, and compares it with the exact embedded bytes before dispatch. The helper is a universal library with arm64, arm64e and x86_64 slices, so guarded children of any of those architectures load it. Those bytes and their source are bound into the enforcement digest. The shim answers only libc `sysconf(_SC_PAGESIZE)` and `getpagesize()` from the public `vm_page_size` value; it forwards other `sysconf` requests. Kernel sysctl calls and other sysctl metadata remain denied, with no Seatbelt exception. Host CPU discovery stays denied; selected-Rust Build commands receive the Goal-pinned jobs environment default above, lowered through `/settings`. A nested SIP-protected shell can strip it again; page-size compatibility is not claimed inside such a nested shell.

On macOS, absolute traversal opens intermediate directories with search-only descriptors and only the selected final directory readably, because a readable ancestor would expose sibling listings.

Canonicalized selected roots reject strict descendant targets in the `getfsstat` mount table before Seatbelt and before Ready/GO. This is a point-in-time check, not a lifetime guarantee.

Non-spawning discovery, Skill loading, definition parsing and private typed file workers reset and unblock `SIGXCPU` and install hard CPU expiry before Seatbelt prohibits changes; commands and MCP rely on external CPU supervision. Denial is attested before GO, so no payload runs under a partially installed profile. The profile denies sysctl access, named socket creation, network operations and descriptor-bearing messages. Inherited bootstrap ports are cleared before payload exec, and `NOSUID` alone does not strip signed entitlements.

System executables are revalidated per catalogue entry through no-follow handles (root ownership, non-writable and non-set-ID mode, device and inode, size and timestamps) opened relative to pinned `/bin` and `/usr/bin` handles. A signature verdict is reused only for the same path and an identical metadata stamp, and is never persisted.

Unit membership is observed through bounded kernel metadata, never process arguments or environments. Cleanup terminates and positively empties the payload coalition before detaching either disk image, including during preparation unwinds. Repeated observations overwrite their stage, so the trace is a snapshot, not a log. ## Shared native capacity and settings

Linux and macOS coordinate Guard capacity across processes and Session roots through the effective user's fixed account root. The owner-only file `guard/limits.json` is created on first native admission with:

```json
{"version":1,"units":8,"queued":32}
```

Edit that private file to change capacity; preserve mode `0600` and the private directory. On macOS the fixed account root is `~/Library/Application Support/dev.Arany.arany`; on Linux it is `~/.local/state/arany`, resolved from the effective user's account rather than environment-selected Session storage. `units` accepts 1–64 and `queued` accepts 1–1024. Unknown fields or versions, unsafe files and invalid ranges reject admission. Every admission rereads settings. Lowering a limit never kills admitted units or registered waiters; no new admission exceeds the selected limit, so existing usage may temporarily exceed a lowered value.

Every Guard unit, including file-only units, reserves one slot before native launch. Live, recovering and retained units count. macOS admission also reserves the exact bounded backing-volume sizes of the immutable intent; a per-Goal maximum does not guarantee that all units can run at that maximum concurrently. Existing excess roots from a previous implementation are retained and prevent further admission. Linux's per-unit mount and cgroup limits are unchanged, and its slot owns the host seed until checked deletion. Each seed holds at most 128 MiB of selected Workspace data and 96 MiB of runtime data, bounding newly admitted retained payload at `units × 224 MiB` (1.75 GiB by default). This is a logical payload bound, not a physical filesystem quota; directory, file-count and record bounds apply separately. Historical unrecorded seeds require the maintenance procedure below.

When capacity is occupied, the approved Tool remains pending in its Run. Up to `queued` Tools register in one shared FIFO ordered by registration under the namespace lock; newcomers cannot overtake registered waiters. Cancellation, a finite capacity deadline and process death remove a participant's position. The capacity deadline starts at post-approval queue entry and is bounded by the pinned runtime allowance; it is a capacity refusal, never a human rejection. Once admitted, native preparation and GO have their own deadlines, so on both Linux and macOS a short command timeout is not refused when preparation outlasts it. Linux still reaches GO within its five-second preparation deadline, and macOS within its worker preparation bound. Overflow rejects before effects. Waiting never renews an intent, approval or Run budget, is not a durable queue, and restart never resumes old permissions. There is one pending Tool per Run. The [terminal contract](./terminal.md#conversation-progress-and-history) owns the temporary queued indication. Native recovery keeps its 30-second deadline within the post-approval capacity window; local filesystem bounds remain cooperative, not hard-real-time guarantees.

Coordination records are no-follow, owner-checked, mode-checked, ACL-checked, single-link and bounded. Coordination creates no database or history records, and admission never creates canonical Events; wait hints use the existing callback. Reaping in `Drop` never bypasses the attempt and deadline budget. Preparing without a committed identity authorizes only removal of an empty directory. macOS control roots count against capacity independently of reservations, with UUIDs deduplicated.

### Linux host seed ownership

Every new host seed retains its reservation from creation until checked deletion. Normal completion leaves no seed or stale reservation. After controller death, the next admission recovers owned storage before releasing capacity, without replaying the effect. Failed deletion, identity uncertainty and ambiguous native launch keep the charge. A new boot settles old processes but not file deletion. Recovery resets a positively identified failed unit before retirement; a missing or not-loaded unit cannot settle an interrupted launch, so that reservation can exhaust capacity until positive native evidence or a later boot permits recovery. Linux reservations use version 2; macOS remains version 1. A locked lease owns one bounded seed record and at most one publication temporary; the planned location is committed before exclusive creation and the directory identity before copying payload. A dead preparation without a committed identity permits only empty-directory removal. Launch-requested precedes launcher invocation, and positive native termination precedes recursive deletion. Deletion rejects links, mounts, foreign ownership, unsafe permissions and replacements; incomplete cleanup retains its slot and prevents completion. Historical unrecorded roots need the [one-time maintenance procedure](../tools.md#historical-linux-seed-maintenance), with Arany stopped, positive native inactivity and authorization of exact inventoried objects; reboot is the fallback for uncertain inactivity. A name prefix never authorizes removal, and normal admission neither migrates nor deletes unsupported records.

### Ubuntu namespace-entry diagnosis

Successful user-namespace creation does not establish permission to map IDs or mount inside it. On Ubuntu 24.04, [AppArmor allows unconfined executables to create user namespaces but denies subsequent capability use inside them](https://documentation.ubuntu.com/release-notes/24.04/#unprivileged-user-namespace-restrictions), which can produce `ProtectionUnavailable` with the required kernel facilities installed. A denial alone does not identify AppArmor: compare the failure stage, profile labels and capability sets. Namespace authorization and kernel/tmpfs-user-xattr enforcement are separate prerequisites.

Stock Ubuntu 24.04 has no enabled executable profile for `/usr/bin/bwrap` or plain `/usr/bin/unshare`; the [S1a0 stock-image bundle](../../planning/command-workspace-overlay/README.md#d7-native-gate-result) records no loaded attachment for either (bwrap itself was not installed). `bwrap-userns-restrict` is an [extra profile](https://gitlab.com/apparmor/apparmor/-/raw/master/profiles/apparmor/profiles/extras/bwrap-userns-restrict) there; it became enabled by default in [Ubuntu 25.04](https://documentation.ubuntu.com/release-notes/25.04/#apparmor-profile-for-bwrap). [Codex documents the same Ubuntu failure and remedy](https://learn.chatgpt.com/docs/sandboxing#prerequisites) by installing Ubuntu’s `bwrap-userns-restrict` extra profile from the `apparmor-profiles` package, with the sysctl as fallback. Arany’s current [unshare-first bootstrap](../../crates/arany/src/tools/guard/linux.rs) is also denied under stock policy; this follows from the code and the [S1a0 refusals](../../planning/command-workspace-overlay/README.md#d7-native-gate-result), not a completed Guard observation. [CI](../../.github/workflows/ci.yml) disables the restriction before Linux native lanes, so those lanes do not prove stock-policy compatibility.

The [D7′ supervisor plan](../../planning/command-workspace-overlay/README.md) selects in-process `unshare(2)` in the pinned Arany executable, followed by capability clearing before bwrap; it retires the external `unshare --keep-caps` entry. On a host that denies the required namespace, guarded commands fail closed as `ProtectionUnavailable` before GO with this diagnosis and the exact hand-run remedy below. No copy or host fallback is selected. The profile procedure targets that replacement entry; it does not repair the current unprofiled-unshare bootstrap. The diagnostic must render the actual admitted supervisor path in the profile below, never a model- or repository-supplied path. Native success with the profiles remains [pending](../../NEXT_STEPS.md#daily-use-first).

**Preferred one-time administrator step.** Install an executable-specific `userns` exception for both `/usr/bin/bwrap` and the exact pinned Arany supervisor executable. This procedure attaches one static absolute executable path: the example below uses `/opt/arany/bin/arany`. Before running it, replace that literal with the actual resolved, admitted supervisor path; do not use a symlink, version wildcard, directory grant or a profile for the terminal/shell. The binary must already be installed at that path. Review existing local profiles first; do not overwrite a local policy or load conflicting attachments for the same executable. If `aa-status` already lists a profile attached to `/usr/bin/bwrap` (Ubuntu 25.04+ enables `bwrap-userns-restrict` by default; Codex’s remedy installs it on 24.04), omit the `arany_bwrap` block and install only the `arany_supervisor` profile; compatibility of that distribution profile with Arany’s bwrap invocation is S1a1 native evidence, not assumed. [AppArmor denies exec when its longest-left-match heuristic cannot pick a winner between attachments](https://manpages.ubuntu.com/manpages/noble/man5/apparmor.d.5.html).

The following is the complete profile text (omit `arany_bwrap` when an attachment already exists) and the commands for the administrator to run by hand in their own terminal. Arany never performs these policy changes. Privilege tools are never executed by Arany, even through a host-command approval.

```sh
sudo tee /etc/apparmor.d/arany-userns >/dev/null <<'PROFILE'
abi <abi/4.0>,

profile arany_bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,
}

profile arany_supervisor /opt/arany/bin/arany flags=(unconfined) {
  userns,
}
PROFILE
sudo chmod 0644 /etc/apparmor.d/arany-userns
sudo apparmor_parser -r /etc/apparmor.d/arany-userns
```

Loading the file applies it without a reboot; `/etc/apparmor.d` retains the administrator’s policy for later boots. Keep `kernel.apparmor_restrict_unprivileged_userns=1`. Fully stop and restart Arany from the exact profiled executable, then explicitly retry the original guarded command. Verify the loaded profile labels and namespace operations; profile installation alone does not establish mount, xattr, overlay or full Guard support. These `flags=(unconfined)` profiles add namespace authorization for the named executables; they are not general AppArmor confinement. They expose namespace kernel operations to those executables, while Arany must still enforce zero payload capabilities, no-new-privileges, seccomp and the existing grants. They authorize no host command or broader filesystem access through Arany.

AppArmor’s [executable attachments](https://manpages.ubuntu.com/manpages/noble/man5/apparmor.d.5.html) match paths, not executable digests. If `cargo install`, an upgrade or relocation moves the executable, the new resolved path has no exception until the administrator updates the attachment and reloads the profile by hand; namespace entry remains fail closed meanwhile. Replacing the executable at the same path retains the AppArmor exception for the replacement, so the administrator must trust what is installed there. Arany’s separate identity/digest pin must reject a changed binary for an already pinned invocation; restart and readmit the replacement before retrying. Do not broaden the attachment to follow arbitrary future versions.

**Last resort.** If the targeted profiles are unavailable or insufficient, an administrator may explicitly choose this temporary system-wide change by hand:

```sh
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

This removes AppArmor’s unprivileged-user-namespace restriction for all otherwise unconfined applications on the host, expanding their access to the kernel’s namespace attack surface. It is broader than the two executable exceptions, does not supply other missing enforcement and is not the profile-enabled Ubuntu evidence lane. Restore it by hand with `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=1` after the experiment; the temporary setting normally resets at reboot unless separate administrator policy persists it. Arany never performs these policy changes.

For diagnosis from the checkout, in a disposable unprivileged account on the stock Ubuntu 24.04 host, the hand-run S1a0 reproduction is:

```sh
cargo run --locked --offline -p arany --example namespace_entry_probe
```

The [probe](../../crates/arany/examples/namespace_entry/probe.rs) still compares the historical in-process and external-launcher entries. It records kernel/package/profile provenance, labels, UID/GID maps, capability sets and positive process teardown; success additionally observes bounded tmpfs mount/write/read/unmount, capability removal and no-new-privileges across exec. A missing probe-entry snapshot is startup failure, not mount/capability evidence. A timed-out child is killed if still running and positively reaped; cleanup errors or host mountpoint leftovers stop comparison. It launches no command payload. Both entries refused in S1a0; the external route is no longer an implementation candidate. The probe executable has its own path and is not authorized by the Arany attachment above. S1a1+ native evidence must exercise the actual profiled supervisor on Ubuntu 24.04 with the restriction enabled and on an unrestricted distribution. It must also verify compatibility of Arany’s bwrap invocation with the distribution’s existing `bwrap-userns-restrict` attachment when present. A probe or sysctl-disabled run does not substitute for this evidence.

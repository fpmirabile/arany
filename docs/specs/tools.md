# Local coding tools

This contract owns Tool grants, guarded effects, runtime Skills and local MCP. [Terminal](./terminal.md) owns completion, settings and consent presentation; [execution](./execution.md) owns Run coordination and capacity admission. Editing constraints: [security rules](../../agents/security.md).

Arany can continue a primary AgentRun through file operations, commands, portable Skills and local stdio MCP tools. This is an explicit, offline local foundation, not unrestricted host shell access. Every attached startup asks whether you trust the opened folder before account selection or setup, including when no account is configured, unless that exact folder already has remembered trust. This consent flow is the same across operating systems and independent of Provider flags or `--tools`. `/permissions` revisits the choice. Without explicit private Tool configuration, untrusted folders remain read-only. Explicit process selections and headless Runs can opt into reviewed configuration with `--tools`; this flag adds no paid compatibility check.

Folder consent and native Tool capability are independent. On platforms without an implemented enforcer, attached chat remains available without Tools even after trust is remembered. `/permissions` uses the same consent choices; Shift+Tab reports the native restriction without enabling authority. Explicit `--tools` rejects unavailable protection. Trust alone never supplies missing OS protection: no effect runs outside the Guard, and [in-process reads](#in-process-reads) run only once native protection admits Tools.

The complete harness requires equivalent granted file operations, commands, Skills and local MCP across supported operating systems, with the same permission, isolation, cancellation and durable-result contract. Typed Git reads follow their [per-platform availability](#typed-git-reads). Resource guarantees differ explicitly by native profile as defined below. [Next steps](../../NEXT_STEPS.md#beta-2-and-broader-release) records unperformed native, platform, live and human checks; implemented code alone does not establish platform support.

Native OpenAI and the consented ChatGPT adapter advertise strict native functions, including phase-specific completion and delegation, and require exactly one function call per step; Anthropic uses strict structured outcomes. Both translate to one semantic Tool proposal at a time, and compatibility with a real selected model requires live evidence. Exact custom profiles reject `--tools` because their data-free conformance covers read-only outcomes, not this encoding.

The generated function and outcome schemas offer file reads and search and only catalog-enabled mutations, commands, Skills, MCP operations and typed Git reads. Command, Skill and MCP-server identifiers are constrained to configured names. An unparseable or oversized catalog offers only read-only file operations. This restriction guides generation; catalog text supplies no execution authority, and the pinned router and Guard independently admit every proposal.

Before a Goal plan is recorded, only bounded Workspace List/Read/Search, [typed Git reads](#typed-git-reads), an already admitted Skill read, and the configured bounded MCP catalog listing are available. MCP catalog listing is read-only discovery; an actual MCP tool invocation requires a Goal plan even when catalog metadata says `readOnlyHint`. Commands require a plan regardless of their script's intended behavior. A plan may accompany a prelude call and is always validated and journaled before dispatch. The [Goal contract](./goals.md#initial-plan-contract-and-success-receipt) owns the exact timing and replay rules.

## Authority and effect admission

Each mutation, process, Skill script and MCP call requires typed effects, deterministic restrict-only Policy, a separate Guard and effective-capability attestation. Hooks, prompts, command regexes, classifiers and approval UI are not enforcement boundaries. [In-process reads](#in-process-reads) use the same admitted scope and their own execution-site attestation.

An effect is normalized once into an immutable typed intent identifying actor, Run, Tool, resources, operations, destinations, descendant behavior, expiry, use count and limits. Policy, approval, journal and Guard share its digest; names, prefixes, hostnames, remembered approvals and summaries never define authority. Tool effects from primary and child AgentRuns pass one deterministic Policy route. [Provider egress](./provider.md#configuration-and-egress) has its own admission under the Provider contract. The [execution contract](./execution.md#collaboration) owns child grants.

Execution requires effective capabilities equal to or narrower than the authorized set. Unsupported enforcement dimensions, missing capabilities, failed attestations and authentication, authorization, signature, policy or schema failures reject. Descendants retain or lose authority; there is no automatic unsandboxed fallback. Privileged code never follows or executes filesystem objects created by a less-privileged agent or sandbox without fresh no-follow, handle-relative validation. A process starts from a trusted executable identity without ambient PATH search, with explicit validated arguments, a pinned working directory, an allowlisted cleared environment and closed inherited descriptors and sockets. Scripts require an admitted interpreter policy. Process-tree supervision, cancellation, reaping and release of permits, transactions and temporary resources follow the native profiles and [failure contract](#limits-and-failure-behavior).

## Folder trust and approvals

The consent screen shows the full folder path and vertical Read only / Trust choices, Read only focused. With explicit `--tools`, the first choice instead says Use explicit config and keeps that private configuration when trust is skipped; neither choice expands roots or capabilities. The screen lists metadata-only toolchain and host-cache candidates unchecked; checking one switches the choice to Trust. A discovery failure shows a notice and never aborts startup. Discovery runs for initial consent or when `/permissions` opens; remembered startup revalidates only saved pins, so an unrelated over-limit manager cannot block prompt-free chat. Enter confirms; Escape dismisses without a decision; Ctrl+C exits without saving one. `/permissions` rediscovers candidates, preserves unchanged selections, and permits explicit add and remove. Checking a toolchain unchecks other selections of its runtime kind; linear `trust` with two of one kind asks again, and `trust N` and `use config` also work. A selection that cannot be saved reports an error and keeps the previous permissions, so startup continues read only. Consent precedes saved-account lookup, catalog or credential access, and Session discovery or creation, for new, resumed and forked entry. Choosing read only, using explicit configuration without trust, or dismissing remembers nothing. Unavailable, malformed or unsafe trust metadata stops startup before account or Session access with a message naming the record and the failed check. An unsupported-version or malformed `workspace-permissions.json` offers Retry, Reset folder trust or Exit, mirroring [history recovery](./terminal.md#acceptance-scenarios-and-evidence-owners); a reset deletes only that record after an explicit confirmation and refuses when the record changed meanwhile. A non-private record or state directory is reported and never reset or modified. Trust is user-owned, shared by conversations, and pinned to the exact absolute path and directory identity; replacing the directory requires trust again, and replay never supplies authority. Remembered grants apply only to native Providers on platforms that admit Tools; custom Providers stay read-only. Explicit private `--tools` configuration takes precedence over remembered trust and keeps its narrower roots and capabilities.

A private version-2 `workspace-permissions.json` in the fixed OS-user account root stores at most 128 entries and 64 KiB using owner-only atomic replacement. Unsupported prior versions reject without changing the record; there is no migration, and only the consented reset above removes it. Trust generates a version-1 Tool grant for `workspace_paths: ["."]`, typed writes, discovered project Skills and a pinned resolved system `sh` on Linux and macOS, plus a pinned system Git for [typed Git reads](#typed-git-reads) when one is available. Optional runtime selections bind each exact path, profile kind and directory device/inode to that folder entry. MCP requires explicit private configuration. Standard secret, link and mount exclusions and finite snapshots still apply; `target`, `node_modules`, `.venv` and `venv` are omitted from root discovery and snapshots. Commands use the existing offline Guard, never the host terminal, the whole home directory, package-manager configuration or credentials.

Runtime discovery reads only bounded directory entries and executable metadata under `~/.rustup/toolchains`, the per-version Node roots of nvm, fnm, Volta and asdf, and `~/.pyenv/versions`. It never executes a candidate or reads manager or project configuration. Candidates need a numeric `major.minor.patch` directory label; aliases such as `stable` and `nightly` are excluded, and the label is the manager's directory name, not a verified binary version. Python candidates need a version-specific regular executable, or a `python`/`python3` alias to one in the same `bin`; other symlink traversal is rejected. A selected Rust, Node or Python directory mounts read-only as an exact subtree, and its `bin` joins the command `PATH`; folder trust never selects every installed version. The label, absolute path and device/inode are bound into Tool policy, hashed into candidate tokens, and rechecked at Run and Guard admission and before Ready/GO; drift rejects before dispatch.

Optional host caches are distinct read-only grants: Cargo's exact `registry/cache`, `registry/src` and `registry/index`; npm's exact `_cacache`; and pip's exact `http-v2` or `wheels` under `~/.cache/pip` (Linux) or `~/Library/Caches/pip` (macOS). They are never inferred from a toolchain, and no parent cache directory mounts. Cache data may include private package names, source, registry metadata or embedded credential URLs. Arany does not load it automatically, but a command or local MCP Tool can emit selected data through bounded output, which is journaled and can enter a later Provider request; consent warns of this. Configuration, credential files, environment values and parent directories stay unavailable. A selected read-only host subtree takes precedence for that Run: Arany neither reads it into its private archive nor restores private bytes over it, and it retains earlier Arany-owned entries at that exact subtree when publishing other cache changes. Disabling the opt-in restores the private writable view and those entries. Cache data supplies no authority.

Shift+Tab cycles **Auto edits → Request approvals → Auto approval → Auto edits**, preserving the draft and caret. The current mode appears beside the composer and follows the selected Provider's native capability. Selecting a supported native Provider after trusting an unconfigured conversation restores the remembered mode. Auto edits allows typed edits and asks for commands and MCP calls; Request approvals asks for every effect. Reads and Skill or catalog discovery still need the pinned grant but no per-action question. Auto approval uses the selected AI to review the exact proposed action against the current user request and resolves an Ask within the pinned grant, which can add model usage. Uncertainty, invalid output, failure or an exhausted review budget asks the user, as does switching out of Auto while review runs.

A human approval shows the exact proposed action, with vertical Deny / Allow once choices and Deny focused (an [unguarded re-run](#unguarded-re-run-after-a-guard-failure) adds a third). All pages must be reviewed before accepting. Approval is one-use, never expands the grant, and expires with the immutable intent, which expires at issue plus its action runtime (the command timeout for commands), extended by the time reserved for its PreToolUse hooks. Escape, a dropped reply or timeout denies; Run cancellation prevents dispatch. Denial stops the Run without retry or rollback of completed actions. AI reviews have a 20-second ceiling, a 256-token output cap, no Tools or project instructions, history or includes, and canonical Provider-call usage. They share the primary call budget, preserving final continuation; review text never becomes an assistant answer. Headless `--tools` uses its explicit private upfront grant without an interactive approval channel.

Workspace input resolves one component at a time beneath the pinned directory handle with no-follow semantics. Symlinks, special files, absolute paths, empty components, `.` and `..` reject. Candidates open nonblocking before the regular-file check, and the validated handle is used instead of reopening by path. Folder trust pins the exact path, device and inode in private OS-user state, never in Session facts. A saved toolchain grant for a recreated root is a new candidate.

Each accepted AI review is pinned to its pending Tool in the projection. Ownership is never inferred from adjacent review calls, so an approval-mode change cannot duplicate an integration review.

## Permission modes, rules and hooks

The shared Engine `before_dispatch` evaluates `arany::permissions::PermissionConfig` for primary and researcher Tool steps. Optional `permissions.json` is an authenticated user settings record beside `tools.json` in the admitted StateRoot, outside the Workspace. It uses the same private regular-file, ownership, no-follow and bounded-read admission as `provider-routing.json`; an unsafe or invalid present file rejects Tool admission. Missing settings preserve the existing interactive and headless approval behavior. Repository, Skill, model and hook text never select trust. Parsed settings are immutable data, not executable configuration or a grant. Hook commands run only as [Hook execution](#hook-execution) defines.

Tool admission snapshots the settings once and pins the SHA-256 of the complete settings bytes in `RunStarted.tool_policy.permissions_digest` (`null` when absent). Editing the file does not change an admitted Run. Present settings select the mode and approval path below, including in headless Runs: a required human approval without a channel denies; AI review can use the admitted review Provider. The terminal's existing mode cycle is unchanged when settings are absent.

Every configured step commits `ToolPermissionDecided` after its immutable `ToolStarted` and before dispatch or its denied observation. The verdict binds the exact intent digest, effective decision, pinned settings mode, rule/mode/grant basis, final approval and approval source (`rule`, `mode`, `pinned_grant`, `human`, `ai_review`, `unavailable_approval`, `exact_command_rule` or `hook`), the narrowest hook restriction (`hook_restriction`, `null` when none) and the number of hooks that ran (`hooks`). The reducer rejects missing, duplicate, wrong-intent or post-observation verdicts and any effect after a denied verdict. An AI preapproval requires a recorded review of that pending Tool. Strict replay consumes these facts without reading settings, rerunning a review or dispatching an effect. The [execution version table](./execution.md#admission-persistence-and-recovery) owns current payload versions; only an [unguarded re-run](#unguarded-re-run-after-a-guard-failure) may omit the settings mode.

The same settings restrict children; a child cannot select its own settings or expand its read-only spawn grant. Explicit asks go to the human adapter; auto reviews of researcher MCP discovery use the admitted review Provider with the child's exact intent and the Goal objective, within the existing delegation deadline and budget. Tool steps after primary synthesis retain their existing non-review path: required approval goes to a human or denies without a channel, preserving the delegation's reserved synthesis and continuation headroom. A human wait with no sibling call in flight is excluded from delegation active time; outstanding sibling work keeps that shared interval active. Rules never bypass the Goal plan, deterministic Policy, pinned grant or Guard. A denied call returns one short model-facing line naming the permission deny rule or mode, and terminal Tool summaries name the same cause without reproducing rule text or undisclosed paths.

### Modes and approval decisions

The [serve approval transport](./serve.md#server-requests) is another human client of the same one-use approval channel.

The peer contract is [Claude Code permission modes](https://code.claude.com/docs/en/permissions#permission-modes). The five accepted spellings are case-sensitive; aliases and bypass modes reject. The parser's omitted `defaultMode` is `default`; it does not change Arany's existing interactive default.

| Mode | Peer behavior | Arany mapping and narrowing |
|---|---|---|
| `default` | Prompt on first Tool use. | Existing `Request`: absent a matching allow, a fresh one-use human approval for each effect needing approval. Remembering Tool use cannot renew an immutable intent. |
| `acceptEdits` | Accept file edits and common filesystem commands in working directories. | Existing `AutoEdits`: typed mutations, including changeset integration; commands and MCP calls still ask because arbitrary process behavior is not a typed edit. |
| `plan` | Explore without source edits; read-only shell commands are available. | Deny mutations and generic command/MCP processes, even with allow rules. Permit admitted typed reads, Skill reads and typed Git reads. Arbitrary argv and MCP metadata cannot prove a read-only effect. |
| `auto` | Classify actions before running without routine prompts; broad execution allows are dropped. | Preserve existing `Auto` AI review for approval-needing calls. Add review for typed Git processes and MCP discovery; every `spawns_process` call and MCP operation requires review. Matching allows never skip it. Existing budgets, uncertainty-to-human fallback and cancellation remain mandatory. |
| `dontAsk` | Deny actions that would prompt; pre-approved actions remain available. | Convert an unresolved `Ask` to `Deny`; permit otherwise admitted no-question calls and matching allow rules. An explicit ask rule still denies. |

Settings and the live terminal mode are independent restrictions: a call asks if either asks, human Request takes precedence over AI review or edit preapproval, and neither can widen a settings Ask or Deny. [Claude Code treats `defaultMode` as the starting mode that Shift+Tab overrides](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in); Arany combines both to preserve its only-narrow guarantee.

`decision(call)` returns only `Allow`, `Deny` or `Ask`. These are approval dispositions within the pinned grant, never executable authority. Invalid or oversized calls deny. `approval_mode(call)` selects human `Request` for an explicit ask rule even under `auto` or `acceptEdits`; only an otherwise unresolved `auto` decision selects AI review. A caller must still journal the exact intent and verdict and obtain deterministic Policy admission and Guard attestation before dispatch. `Decision::narrow` combines independent restrictions with `Deny > Ask > Allow`; an allow from a hook or review cannot erase an earlier denial or question. A hook's `allow` is ignored because it is runtime program output, unlike a static allow rule from user configuration; only a human or the Auto review resolves an Ask. Children retain the intersection with parent authority. There is no bypass or implicit unguarded execution: `command_unguarded` is never pre-approved by an allow rule, a mode or AI review; `plan` and `dontAsk` deny it.

**Owner-accepted peer behavior — 2026-10-17:** in `default`, a matching allow rule pre-approves commands and MCP calls without a human prompt or AI review, subject to live terminal restrictions, as in [Claude Code permissions](https://code.claude.com/docs/en/permissions#permission-rule-syntax). This is an explicit user-configured approval, not a bypass of the Guard, deterministic Policy or the pinned grant. Deny and ask retain precedence. `acceptEdits` keeps human approval for commands and MCP calls even with an allow rule; its existing typed-edit approval is unchanged.

[Claude Code drops broad execution allows on entering auto mode](https://code.claude.com/docs/en/permission-modes#how-auto-mode-evaluates-actions), including blanket command rules and wildcarded interpreters. Arany enforces the stricter behavior directly during decision evaluation: `auto` ignores allow rules for processes, MCP operations and calls that already need approval, including bare `Bash`/`command`, `Bash(*)`, `Bash(python*)`, `Bash(python *)`, `:*` equivalents, bare `mcp_call` and whole-server MCP rules. Existing AI review for commands, MCP calls and typed mutations remains mandatory. With settings present, Arany also reviews typed Git processes and MCP discovery; the existing Auto mode without settings keeps its previous scope. Explicit ask rules still select a human and deny rules still block.

### Permission rules

The envelope copies [Claude Code settings](https://code.claude.com/docs/en/settings) and [rule syntax](https://code.claude.com/docs/en/permissions#permission-rule-syntax):

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(git diff *)", "Read(./crates/arany/src/**)"],
    "deny": ["Read(./private/**)"],
    "ask": ["Edit(./crates/arany/src/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "/reviewed/check", "timeout": 30}]
      }
    ]
  }
}
```

All fields shown at the envelope and permissions levels are optional with empty lists/maps as defaults. Unknown or duplicate fields, wrong types, unsupported names and malformed rules reject the entire document; no invalid rule is silently skipped. A rule is a bare Tool or `Tool(specifier)`; inner parentheses are literal. Lists are evaluated in deny, ask, allow order, regardless of specificity or input ordering. Within each list there are no exceptions that undo a match.

| Peer Tool | Typed Arany operations |
|---|---|
| `Bash` | `command`; the subject uses its admitted logical program identifier and argv, not an inferred executable basename. |
| `Read` | `list`, `read`, `search`; deny and ask also cover `git_status`, `git_diff` and `git_log` paths. A deny also covers typed mutations and changeset paths to prevent writing through a read denial. |
| `Edit` | `mkdir`, `write`, `edit`, `apply_changeset`. |
| `Write`, `Glob` | Bare `write` and `list` respectively; path specifiers reject in favor of `Edit` and `Read`. |
| `Grep`, `Skill` | `search` path and admitted `skill` name respectively. Skill wildcards match names, not authority or resource discovery. |
| `mcp__<server>__<tool>` | `mcp_call` matched against separate server and tool fields; the Tool segment supports `*`. `mcp__<server>` also covers that server's catalog listing and all calls; `mcp__*` covers all servers for deny/ask. |
| Exact Arany catalog name | That operation only, including `git_status`, `git_diff`, `git_log`, `mcp_list` and `mcp_call`. Native MCP operation names accept bare rules only. |

Bare Tool-name `*` globs are supported for deny and ask against peer and native operation names. A non-MCP glob that matches no known operation rejects, preventing silent no-op restrictions. MCP allow rules require a literal server; generic allow name-globs reject. Server patterns are at most 64 bytes and use lowercase ASCII letters, digits, `_`, `-` and `*`; Tool patterns are at most 128 bytes within the complete-rule ceiling. MCP allows compare the parsed server and Tool fields separately. Deny/ask also test the complete peer-name glob against the call or catalog subject, including `__` descendants so the rule can restrict a whole server. This conservatively covers ambiguous server names containing `__` or ending in `_`; an ambiguous spelling may restrict more calls, but never pre-approve them. Tool names supply no authority and matching discovers no servers. A changeset allow requires every path to match the same rule; deny/ask requires any path. Separate allows cannot assemble authority for an otherwise unmatched batch.

Bash patterns follow the peer's [wildcard examples](https://code.claude.com/docs/en/permissions#wildcard-patterns): `*` spans spaces; exact patterns stay exact. A sole trailing ` *` also matches the bare command but keeps its word boundary; trailing `:*` is equivalent. `Bash(*)` equals bare `Bash`. Other characters are literal.

Arany-specific command narrowing: only unambiguous argv words composed of ASCII letters/digits and `_./:@+=,%~-` are joined with spaces for specifier matching. Empty, quoted, whitespace-bearing or shell/control-bearing arguments are opaque. An opaque command cannot match a specifier allow and conservatively matches every applicable specifier deny/ask. A bare Tool rule still covers it. For deny/ask only, the pattern also checks every word-boundary suffix of the joined argv, so `timeout 30 rm x`, `nice rm x`, `xargs rm x` and `env FOO=1 rm x` cannot hide an `rm *` restriction. This is a conservative narrowing: even a word used as ordinary data may trigger a restriction. Allows match only the complete argv projection. Arany does not split shell strings, expand variables or infer commands from scripts as the peer does. This avoids shell parsing becoming an authority boundary; all execution remains under the pinned command grant and Guard. Text matching does not prove an executable's effects, filesystem disclosure or read-only behavior.

File patterns use the peer's [Read/Edit matching depths](https://code.claude.com/docs/en/permissions#read-and-edit) and [gitignore wildcards](https://git-scm.com/docs/gitignore#_pattern_format): `*` and `?` stay within a segment; whole-segment `**` crosses zero or more directories; alphanumeric classes/ranges, class negation and backslash-escaped literals are supported. Bare filenames match at any depth. `/path` and `./path` anchor at the admitted Workspace; multi-segment relative patterns anchor there too. This is an explicit peer divergence for `/path`: Claude Code anchors it at the settings source, while Arany uses its admitted directory capability to prevent settings placement from changing path authority. Unanchored `crates/arany/src/**` matches only root `src` for allow, and a `src` directory at any depth for deny/ask. An explicit `**/src/**` matches at any depth for every list. Deny/ask path patterns compile case-insensitively on Linux and macOS; allow patterns remain case-sensitive. Deny/ask reject non-ASCII pattern literals. Any non-ASCII subject path conservatively matches an applicable restrictive path rule, including changeset and Git paths, closing NFC/NFD and Unicode case aliases without normalization dependencies. This deliberately over-restricts unrelated Unicode paths. Allow literals retain exact Unicode spelling and cannot normalize into a wider match. There is no filesystem access or symlink following; actual filesystem aliases and result filtering remain outside this matcher, under the separate no-follow grant and Guard.

The admitted path vocabulary is Workspace-relative. This slice rejects `//` absolute and `~/` home anchors, traversal, empty components, trailing directory-only slashes, non-segment `**`, unsupported classes and dangling escapes rather than guessing filesystem identities or settings-source roots. Leading comments and gitignore `!` exceptions also reject: restrict-only sources cannot remove prior restrictions. The existing no-follow admission and exclusions still apply. Rules match proposed typed paths; they do not filter directory/search results, includes, interpreter I/O or subprocess filesystem access. Such disclosure remains bounded by the independent grant and Guard; this config API is not an OS path filter.

### Hook execution

The envelope and nested groups copy the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#configuration) and [command fields](https://code.claude.com/docs/en/hooks#command-hook-fields). Accepted events are exactly `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop` and `PreCompact`. Groups contain a `hooks` array of command handlers, an optional matcher, and no other fields. Handlers accept `type: "command"`, a nonempty `command`, optional `args` and an optional integer `timeout` in seconds. Omitted `args` retains shell-form text; a present array, including `[]`, retains exec form. Nothing is interpolated or resolved; all five events execute at the Engine sites below.

Matchers absent, empty or `*` select every occurrence. The peer's exact-name/`|`/`,` alternatives are copied; other patterns use an unanchored regex. Arany narrows regexes to the bounded finite-automaton syntax: JavaScript lookaround/backreferences and oversized compiled patterns reject. Tool events must use `matches_tool` so invalid or ambiguous calls cannot evade a hook; other events use `matches` on their event-specific subject. Tool matching uses canonical peer names above, including actual `mcp__<server>__<tool>` call subjects and `mcp__<server>` catalog subjects; `SubagentStop` matches agent type and `PreCompact` matches the trigger (`manual`/`auto`). `Stop` accepts only match-all: a filtering matcher rejects instead of the peer's silent ignore. An MCP server name containing `__` produces a blocking Tool-subject error rather than an ambiguous canonical name; native MCP rules still compare typed fields. A present `null` is invalid, not an omitted field. Empty handler groups, other events/types, async handlers and extra execution options reject.

**Recorded owner decision — 2026-10-17:** hook commands run inside the Guard like every process, under pinned interpreter/executable identities, an explicit environment and typed grants. Arany copies Claude Code's hook protocol: events, matchers, JSON on stdin, event-specific exit-2 blocking, `permissionDecision` `allow|deny|ask` and timeouts. The peer divergence is execution authority: [Claude Code command hooks run with full user permissions](https://code.claude.com/docs/en/hooks#security-considerations); Arany requires Guard isolation because of its [Per-effect isolation security guarantee](../../AGENTS.md#non-negotiable-guarantees). Descendants cannot gain authority, and repository or hook output cannot select trust.

If a hook fails because of Guard enforcement, the planned [NEXT_STEPS item 7 escape hatch](../../NEXT_STEPS.md) applies to that exact command. Running it outside the Guard requires a new intent and explicit user approval for that command; it is never an automatic retry. The approval and unguarded execution are journaled, and the effect and Run are marked unguarded. Journal-first durability, honest uncertainty, budgets and restrict-only verdicts still apply. A hook never approves or originates an unguarded command, and the hook origin of that escape hatch remains unimplemented.

**`PreToolUse` command hooks.** After the permission decision and the live terminal restriction, and only while the decision is not `Deny`, a primary Tool step runs its matched handlers one at a time in configuration order. Each handler is a journaled `Command` effect with the Guard's offline, private-Workspace-view, explicit-environment grant of any model command: `HookStarted` commits the immutable hook intent, the exact-stdin digest and the pending Tool's digest; the Guard runs it; `HookFinished` commits the Guard observation (receipt included) and the parsed result; then the verdict follows. Shell form runs the pinned `sh` as `sh -c <command>`; exec form runs `command` as a pinned program name with `args`. A program that is not pinned, a matcher error or more matched handlers than the limit below denies the pending Tool before any hook starts, with reason `hook program is not pinned`, `hook configuration blocks this Tool` or `hook limit`. A researcher's Tool that matches a hook is denied because delegated research reserves no hook Events (`hooks are unavailable to delegated research`). Handlers after a denial do not run. Internal Engine preparation calls over snapshot-pinned input (agent definition parsing) are never model Tools: no hook sees or narrows them, and they widen nothing.

The hook receives one JSON object on stdin (closed field set): `session_id`, `cwd` (always `/workspace`, the Guard view, never a host path), `permission_mode`, `hook_event_name`, `tool_name` (the peer name), `tool_input` (the typed call) and `tool_use_id`. Exit codes and output follow the peer: exit 0 with empty or non-JSON stdout adds nothing; exit 0 with a JSON object may carry `hookSpecificOutput` (`hookEventName` must be `PreToolUse`) with `permissionDecision` and `permissionDecisionReason`, the legacy top-level `decision: "block"` with `reason`, or `continue: false` with `stopReason` (both deny); exit 2 denies and its stderr is the reason; any other exit is a non-blocking failure. Unknown fields are ignored, and stdout is never interpreted as instructions. Hook output is evidence and a reason string only: reasons are control-stripped and truncated to the reason limit below, and the model sees only `Hook denied this Tool` with that reason.

A Guarded Command that is not a hook reads an empty stdin (immediate EOF), like the unguarded executor.

| Peer behavior | Arany |
|---|---|
| Hooks run with the user's full permissions. | Hooks run in the Guard under the pinned grant; their Workspace changes are journaled in the observation but never integrated. |
| `allow` skips the permission prompt. | `allow` is journaled (`allow_is_no_op`) and changes nothing: it never resolves an Ask or erases a Deny, unlike a configured allow rule. `ask` narrows any non-Deny decision to the human prompt, even over an Auto-review Ask; `deny` and exit 2 narrow to Deny. |
| `updatedInput` replaces the tool input. | Accepted only as a provable narrowing of the immutable intent (below); any other non-null `updatedInput` denies the Tool (`hook input update does not narrow`). |
| Matching hooks run in parallel. | Sequential, in configuration order; overflow denies. |
| A failed hook lets the action go ahead; a timeout is a non-blocking error and there is no output cap. | The same for exit codes other than 0 and 2 and for output that is not valid text, which add no restriction and are shown as a non-blocking failure. A timeout or output overflow cannot be told apart and is bounded, so it fails closed: the Tool is denied (`hook limit reached`), so a model-steered large output can never switch off a deny hook. An `Uncertain` hook stops the Run without retry and the Tool is not dispatched. |
| `transcript_path`, `async`, non-command types and path interpolation exist. | Not provided; the stdin field set is closed. |
| Settings are re-read while running. | Settings are pinned per Run; replay never reads them, never runs a hook and never re-parses its output. |

The verdict records `hook_restriction` (`null`, `ask` or `deny`) and `hooks` (handlers that ran). The reducer requires every started hook to be finished before the verdict, `hooks` to equal the journaled count, `null` only when no hook restricted or stopped, `ask` only when the fold is `Ask`, and `deny` only for a `Deny` fold, a stopped hook or a denial before any hook ran. A `Deny` hook verdict has basis and source `hook`; a hook `Ask` over an `Allow` has basis `hook` and is resolved by the human, never by AI review. Unknown outcomes stop continuation: a hook whose observation is `Uncertain`, cancelled or unattested is recorded and blocks resume like an uncertain Tool.

Hook limits: at most 8 matched handlers per occurrence; stdin at most 32 KiB, and the complete Guard task of every matched handler must encode within the Guard task ceiling before any hook starts, else the Tool is denied (`hook input exceeds the Guard task limit`) with no `HookStarted`; stdout and stderr 16 KiB each (a 32 KiB result; overflow fails closed); runtime at most the handler `timeout` and the remaining Goal active time, never less than 1 s (the Goal ledger refuses a start that does not fit); reasons at most 1 KiB; admission of a Tool step reserves two Events and one observation per matched handler, and the Tool's authorization lifetime and active-time ceiling grow by the handlers' worst case, clamped to the remaining Goal active time (unbounded Goals keep the full worst case). Hook time is Goal active time. Descendants are reaped by the Guard on timeout.

**`PostToolUse` command hooks.** After a primary Tool completes with a `Succeeded` observation, its matched `PostToolUse` handlers run one at a time with the same Guard grant, bounds and `HookStarted`/`HookFinished` pair as `PreToolUse` (`HookStarted` requires that committed observation, the Tool's digest and directly follows the Tool's latest journaled step: a Command's hooks run after its changeset integration commits, so the hook sees the published tree, and no Provider call, compaction or other Tool may sit between the Tool and its hooks). The hook cannot undo the effect, and its Workspace changes are discarded like any hook's. Failed, denied, uncertain and internal Engine calls run no `PostToolUse` hook. Stdin adds `tool_response` to the `PreToolUse` field set: the observation's model-facing projection, replaced by `{"truncated": true, "text": <prefix>}` when the input would exceed the stdin limit, with the prefix halved (down to empty) until every matched handler's Guard task fits, so on macOS a hook can receive less than 32 KiB. Exit 2 (stderr) and `decision: "block"` with `reason` become feedback; `hookSpecificOutput` (`hookEventName` must be `PostToolUse`) with `additionalContext` becomes feedback too; any other exit is a non-blocking failure, and a timeout or output overflow becomes the feedback `hook limit reached`. Feedback strings are control-stripped and at most 1 KiB each. `updatedToolOutput` and every other field are ignored: hook output never replaces an attested observation. `continue: false` is ignored too, deliberately for this slice: the peer's stop-the-agent needs a distinct Run outcome (a hook-requested stop is neither a failure nor a cancellation) that is not defined yet; it stays listed under NEXT_STEPS item 6. An `Uncertain`, cancelled or unattested hook stops the Run after the Tool effect without retry, the observation stays committed and the next Provider call does not start.

Feedback is stored only in the journaled `HookFinished` result (a `feedback` result with a `lines` list); the reducer requires the recorded result to equal the deterministic parse of the hook's observation for its event. The model-facing Tool result gains a `hook_feedback` list of lines `hook feedback: <text>` (at most 4 KiB in total, later lines dropped), derived from the live results and, after resume or in history, from the journaled ones, so the same prompt bytes result. A step that matches `PostToolUse` handlers reserves twice that room (JSON escaping) in the context budget, and `PostToolUse` handler time extends the active-time ceiling but not the Tool's authorization lifetime. Because a `PostToolUse` handler cannot be refused after the effect, a Tool whose `PostToolUse` handlers are unpinned, over the matched-handler limit, unable to encode their Guard task or stdin even with an empty truncated response, or for a researcher is denied before dispatch with the `PreToolUse` reasons.

**`updatedInput` narrowing.** `updatedInput` must be a complete, valid Tool call (the shape of `tool_input`); anything else denies. A replacement narrows only when it is: a `read` of the same path whose offset and end lie inside the original window; a `list`, `search`, `git_status`, `git_diff` or `git_log` whose path equals the original or lies beneath it by whole path segments (a root original admits any path), with `search` keeping its query and the Git reads keeping every other field. Parent paths, `..`, case or symlink variants, a larger window, a changed query and every `command`, MCP, Skill, `write`, `edit`, `mkdir`, `apply_changeset` or internal call never narrow (a changed argv or content has no provable order; the model must propose it as a new call). The replacement must also be at least as restrictive as the original under the pinned rules and be within the pinned grant. `HookFinished` journals every valid-shaped update outside an `ask` decision (which keeps the original input) as a `narrowed` result carrying the call, but only the verdict's `narrowed` flag records that the Engine accepted it. An update identical to the current call is a no-op (the call proceeds as is and the hook restricts nothing, so idempotent clamping hooks work). An update refused by `narrows`, the pinned rules or grant, or the per-step limit denies with the matching reason and a false flag. `ask` together with `updatedInput` keeps the ask on the original input (the update is dropped, the human decides). On an accepted narrowing the original Tool is `Denied` with basis `hook`, the verdict flag set and the model-facing line `Hook narrowed this Tool to: <tool_name>`; it does not answer the request, and the next Tool of that step must be exactly the replacement (a new `ToolStarted` intent), so a later step requesting the same call is an ordinary request. `PreToolUse` hooks run again for the replacement; at most one narrowing per step, so a second one denies (`hook narrowing limit`). The model receives one Tool result for the request, built from the replacement's observation; the original's denial line arrives as a separate `hook_narrowing` data block. Internal Engine calls and delegated research are never narrowed. Step admission reserves the replacement's Events and observations.

**`Stop` and `SubagentStop`.** A primary Finish runs `Stop` before `AgentFinished`. A researcher Finish runs `SubagentStop`, matched against its definition role name or `researcher`, before the child's `AgentFinished`. Both receive `stop_hook_active` and `last_assistant_message`, truncated at a UTF-8 boundary to fit the 32 KiB stdin and complete Guard task ceilings. Exit 2, `decision: "block"` or `continue: false` records `blocked` with a bounded reason. The accepted assistant turn and a user-data block labelled `stop_hook_feedback` are appended to the next request; feedback is at most 8 KiB per actor. The next primary call uses ordinary Goal Provider-call admission; exhaustion ends the turn with the existing budget outcome. A child re-prompt stays inside its original delegation deadline and turn ceiling. At most eight consecutive blocked continuations are admitted per actor; after those continuations a valid Finish completes without another Stop invocation. Internal Tool calls never trigger hooks.

**`PreCompact`.** Before an active-Run compaction reservation or an idle Session compaction, matching handlers receive `trigger` (`manual` or `auto`) and empty `custom_instructions`. A block skips the compaction and makes no compaction Provider reservation; a manual `/compact` that a hook blocked (or already attempted at that call count) fails with `CompactionBlockedByHook`, distinct from an empty input. If retained context still exceeds its limit, the existing context failure applies. Each trigger/call-index occurrence runs once, including blocked occurrences. Idle compaction re-admits the current private configured or remembered folder grant only if its digest and the permissions digest match the Run's pins; changed or unavailable admission fails closed. Between Runs of an open Goal, hook start reserves a durable active-time ceiling and completion settles elapsed time; outside an open Goal the handler keeps its finite timeout and Guard limits.

Lifecycle hooks use the same pinned programs, Guard, sequential execution, eight-handler bound, fail-closed Limit and uncertainty handling as Tool hooks. An invalid program, matched-handler overflow or unencodable stdin records the offending (else first configured) handler's own call as a denied, never-dispatched intent with the reason as output, and the result is `Blocked` with that reason, before any process runs. A SubagentStop shares its delegation, so its admission reserves a researcher step's tail rather than the primary's; a cut-off or cancelled SubagentStop ends only that child (a cancel is reported as cancelled, never as budget exhaustion) unless its outcome is unknown, which stops the Run as `Uncertain`. Replay binds Stop subjects to `(agent_run_id, provider call index)` and PreCompact subjects to `(trigger, provider call count)`. A Stop occurrence immediately follows its accepted Finished call; a blocked Stop forbids successful Agent completion until a new primary/child call is recorded. The eight-continuation cap counts every blocked Stop of the agent in the Run, so interleaved Tool calls never reset it or `stop_hook_active`; each continuation re-renders the Finish turn, which counts toward the Tool context and its compaction trigger, and a context without room for it refuses with `ContextTooLarge` before any hook journals. Open or Uncertain hooks block continuation and resume; strict replay consumes recorded facts without executing hooks.

| Peer lifecycle behavior | Arany divergence and reason |
|---|---|
| Stop handlers prevent stopping and send feedback to the model. | Feedback is bounded user data; each continuation must fit the pinned Goal budget, the eight-continuation cap and, for children, the existing delegation deadline and turn ceiling. These bounds preserve durable budgets. |
| PreCompact blocks compaction and accepts custom instructions (`null` when absent). | Blocking is preserved; `custom_instructions` is always empty, and digest-only subjects avoid host paths or fresh authority. |

Human and AI approval share the `before_dispatch` seam as resolvers of an Ask, while hooks only restrict.

## Private grants

Put an owner-only `tools.json` beside the admitted Session database, outside the Workspace. Its directory must be private (`0700`) and the file must be regular, single-link, no-follow, current-user-owned and `0600`. `--state-dir` selects this Session and configuration root; it does not move your saved account. Permissions are not encryption or protection from another process running as the same user.

A minimal file-only configuration is:

```json
{
  "version": 1,
  "workspace_paths": ["src", "Cargo.toml", "Cargo.lock"],
  "write": true,
  "commands": [],
  "skills": [],
  "mcp": []
}
```

Use exact, nonoverlapping relative files or directories. The singleton `["."]` selects the whole project under the same exclusions and bounds; mixing `"."` with other roots rejects. List, search and command working directories accept `"."` or an empty path for the project root; mutations still require a named relative path. Absolute paths, traversal, links, mount crossings and special files are not admitted. StateRoot and the fixed account root must not overlap the Workspace or configured runtime resources. `.git`, `.env`/`.env.*`, `.aws`, `.ssh`, `.gnupg`, `.npmrc` and `.pypirc` path components are excluded. Repository history is reachable only through [typed Git reads](#typed-git-reads). This is not a universal secret detector: review the files you select. Tool observations can be sent to the selected Provider and persisted in the private, unencrypted journal.

The Linux profile exposes the system `/usr` tree read-only as its runtime. Workspace, StateRoot and account roots must not overlap it, since a private file inside a runtime mount stays visible to a same-user payload. This authorizes no home or unselected cache mount.

The offline profiles deny network, named Unix socket creation, connect, bind, listen and destination-bearing sends; a network namespace alone would leave pathname sockets in visible runtime trees reachable. Anonymous pipes and anonymous socket pairs stay usable: Linux pairs cannot rebind or send to named destinations, and macOS denies pair writes, so payloads cannot depend on socket wakeups. `sendmsg`/`sendmmsg` descriptor passing is unsupported. This is not a network-capable test profile.

JSON has a closed versioned schema: all six listed top-level fields are required and the optional `git` field pins [typed Git reads](#typed-git-reads); unknown and duplicate fields reject. Private configuration has no interpolation, automatic installation or hidden executable lookup. Project Skill discovery stays within its selected Workspace roots. Where commands are supported, folder trust pins the resolved system shell rather than looking up arbitrary commands on PATH. Configuration is pinned for a Run; editing it does not cancel an admitted Run. Changed pinned executable or resource contents reject dispatch rather than being silently trusted.

## Enforcement failure causes

`ToolFinished` records an optional closed `enforcement_cause` separately from the disposition and untrusted output. The initial cause is `filesystem_denied`: command snapshot capture explicitly rejected a protected path component or set-ID entry metadata. These checks enforce the command output boundary. Shared file readers and resolvers retain their existing errors, so unsupported Git layouts, ordinary path validation, non-regular or multiply linked files, unsupported changeset type conversions and opaque filesystem errors remain unclassified. A cause requires an execution attestation and a `denied` disposition; success, resource limits, cancellation and uncertainty cannot claim one. Classification changes no grant, approval, dispatch, retry or uncertainty rule.

The cause carries no path, filename, contents or native diagnostic text. Its size is fixed by the enum, within the existing observation and context budgets; protected names discovered while scanning a command snapshot never enter the cause or its diagnostic. The model result adds one short diagnostic field only when a cause exists: `Guard enforcement: filesystem boundary denied`. Terminal Tool summaries show the same line. Results without a cause retain their model-facing projection. JSONL and strict replay retain the typed field; only the `ToolFinished` payload version advances, and its previous version rejects without rewriting stored data.

| Platform | Reliable attribution in this profile | Reports no cause |
|---|---|---|
| Linux | Protected-path and set-ID entry refusals inside command snapshot capture | Bubblewrap startup failures, namespace-hidden paths, read-only mounts and seccomp-returned errno have no trusted per-operation denial channel. The current seccomp profile returns `EPERM` (and `ENOSYS` for `clone3`), rather than notification records; Arany uses no Landlock/audit attribution channel. A blocked socket/connect, `EACCES`, `EPERM`, `EROFS`, missing file or signal alone cannot establish Guard causation. |
| macOS | Post-run command snapshot refusals in the supervisor; a pre-launch snapshot refusal is a bootstrap failure and reports no cause | Seatbelt violations are not collected through a trusted, invocation-correlated report channel. Program errno, stderr, exit status and unrelated system sandbox reports cannot establish attribution. |

`null` means no attributable cause, not permission or proof that enforcement was uninvolved. No network or process cause is claimed without a trusted evidence source. This applies equally to commands and local MCP servers; `isError`, server-provided cause fields and text remain ordinary program data. Skill loading is data-only; Skill scripts use ordinary guarded commands and the same classification.

This mirrors the separate sandbox diagnostic attached to results by Claude Code's [sandbox runtime `annotateStderrWithSandboxFailures`](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/sandbox-manager.ts), which uses invocation-correlated violations, and Codex CLI's [distinct `SandboxErr::Denied` result](https://github.com/openai/codex/blob/main/codex-rs/core/src/exec.rs). Arany does not copy Codex's `is_likely_sandbox_denied` output heuristic: hostile program output must never attest enforcement. The peers' escalation flows are the [unguarded re-run](#unguarded-re-run-after-a-guard-failure) below; a cause never decides whether it is offered, only the journal evidence does.

## Unguarded re-run after a Guard failure

This is the only exception to per-effect isolation that [AGENTS.md](../../AGENTS.md) permits: a per-command run outside the Guard that the user approves after a sandbox-caused failure, never automatic, journaled and marked unguarded. It copies [Claude Code's unsandboxed retry](https://code.claude.com/docs/en/sandboxing) (the model re-proposes the same call, a prompt titled for the lack of sandbox, an allow-rule remembered per project) and Codex CLI's `require_escalated` (a model-authored `justification` becomes the user-facing question; three choices: once, remember, deny). It diverges where a guarantee requires: the model cannot pre-empt or remember (no prefix rules), a wildcard allow rule, a mode or AI review never approves it (Claude Code's allow-rule and auto-mode classifier paths are rejected), there is no bypass mode, and the process keeps a cleared allowlisted environment, a pinned executable, explicit argv, a pinned cwd, output caps, a timeout and a process-group kill.

**Operation.** `command_unguarded` takes the `command` fields plus `justification` (1–512 UTF-8 bytes, control-free apart from tab, shown as untrusted text). Its peer name is `Bash`, so deny and ask rules match like `command`; `"deny": ["command_unguarded"]` is the Arany spelling of Claude Code's `allowUnsandboxedCommands: false`. It is offered beside `command` when `commands` is non-empty, never to researchers, and may satisfy `tool_call_succeeded` because an unguarded success is an attested, human-approved receipt that the report marks unguarded.

**Evidence gate.** One predicate, `qualifying_guard_failure`, serves the Engine and the reducer. The latest observation in the same Run of a primary `command` with byte-identical program, args and cwd must be Guard-attested `failed`. A `denied` observation (including `filesystem_denied`), `limit`, `uncertain`, `cancelled`, an unattested failure, a child's observation and any later success of that command never qualify. Because no trusted per-operation cause exists beyond `filesystem_denied`, a failure without a cause qualifies and the prompt says Arany could not verify that the Guard caused it. Argv containing a Guard path alias (`/workspace`, `/scratch`, `/cache`, `/seed`, `/programs`, `/inputs`, `/skills`, `/arany` as a root path) never qualifies: the same bytes name other paths on the host. So does argv naming a Guard-only variable (`ARANY_TOOL_INPUTS`, `ARANY_TOOL_SKILLS`, any `ARANY_TOOL_*` but `ARANY_TOOL_WORKSPACE`): the host environment does not set it. The check is lexical; shell-built paths and `..` relative to the directory are not caught. The Engine reads the live Tool context, so a failure that was compacted away, or was observed in the same model turn, does not yet qualify (the stricter side of the reducer's view). The gate runs before the approval and a refusal is journaled as a `denied` observation with an unapproved verdict.

**Prompt.** A boxed, paged panel titled `Run outside the Guard? (unguarded)` states that the command failed inside the Guard and the model asks to run it again on this machine with no sandbox, then shows the program and its pinned executable, each argument on its own line, the directory (`./` is the real project folder), the model's reason, the Guard attribution (`none. **Execution.** The host executor re-verifies the pinned executable digest and the Workspace identity, resolves the directory beneath the admitted Workspace without following links, and spawns the explicit argv with a cleared environment: `PATH` from the admitted runtime grants, real `HOME`, the system `TMPDIR`, `LANG`/`LC_ALL`/`TERM` when set, `NO_COLOR=1`, `ARANY_TOOL_WORKSPACE` (the real Workspace) and `ARANY_UNGUARDED=1`; no credential or proxy variable, no stdin. Output is capped, the run is bounded by the command timeout, and the process group is killed on timeout, overflow or cancellation. A leader or group that is not confirmed stopped makes the outcome `uncertain` and stops the Run. No changeset is produced: edits land directly, `workspace_effect` projects as `unguarded`, and only a later read is evidence of file content. The attestation is an `UnguardedReceipt` (pid, exit code, executable digest, whether descendants were confirmed stopped), issued only when the process was spawned; a Guard receipt never attests this operation and the Guard helper refuses it.

**Journal and replay.** `ToolStarted`, `ToolFinished`, `ToolPermissionDecided` and `RunStarted` (current versions in the [version table](./execution.md#admission-persistence-and-recovery)) carry the operation, the attestation, the nullable settings mode and the pinned rules digest. Matching is typed byte equality, never a wildcard, prefix or shell parse. The snapshot is pinned in `RunStarted` and immutable: a rule recorded by "Always allow" applies from the next submission, and a repeat in the same Run prompts again. Edit or delete the file to remove a rule. Children never inherit rules; a worker grant must add an explicit field that defaults to false.

**Marking.** Terminal and `/transcript` summaries append `UNGUARDED`; the answer heading reads `Answer (unguarded effects: N):`; `/goal` and `exec`'s stderr receipt add `unguarded effects: N`; the Goal report adds an unresolved fact and names `An unguarded host run` as the evidence attester; Run and Goal spans carry `arany.run.unguarded_effects` and `arany.goal.unguarded_effects`.

**Non-claims.** The host run does not bound network, filesystem beyond the Workspace, memory, CPU or process counts, descendants that leave the process group (for example by `setsid`), or changes to host state. The executor runs the pinned executable and directory by path, which can be user-writable, unlike the Guard's private copy on Linux, so a concurrent writer with the user's authority could swap them between verification and exec or between directory validation and spawn; a human approved this command with that authority, and closing the race needs a private copy or descriptor exec, which are not portable. Guard path aliases are refused rather than translated. Project rules bind path, device and inode, which can be reused after a project is deleted and recreated at the same path (folder trust shares this limit). A dropped future kills only the leader; the journal records the outcome as uncertain.

## Commands

Each `commands` entry declares a reviewed executable and its SHA-256, whether it is an interpreter, and any additional pinned input files:

```json
{
  "name": "bash",
  "executable": "/usr/bin/bash",
  "sha256": "REPLACE_WITH_THE_64_CHARACTER_LOWERCASE_SHA256",
  "interpreter": true,
  "inputs": []
}
```

The placeholder above is deliberately invalid. Resolve a system executable's real path and calculate its digest yourself, for example with `readlink -f /usr/bin/bash` and `sha256sum /usr/bin/bash` on Linux, or `shasum -a 256 /bin/sh` on macOS. Arany requires a no-follow, regular, single-link native executable: ELF on Linux or Mach-O on macOS. A symlink must be replaced with its resolved executable path. The optional `git` pin differs: it must lie under `/usr`, be root-owned, non-set-ID and not group- or world-writable, may have several hard links (distributions hard-link `git-core`), and runs in place from the read-only `/usr` mount rather than from a `/programs` copy, since its shared libraries load live from `/usr`. Updating an executable requires reviewing and changing its pin.

Additional inputs use `{"path":"/absolute/reviewed/file","destination":"relative/name","sha256":"<digest>"}`. They appear read-only under `/inputs/PROGRAM_ID/relative/name`. Executables are copied to `/programs/PROGRAM_ID`, except checked immutable macOS system programs, which retain their original paths. Paths and digests are checked again for each fresh invocation. Descriptions and the `interpreter` declaration do not prove that arbitrary arguments or a script are safe; allowing a shell or interpreter authorizes its behavior inside the same OS-enforced boundary, including descendants using the admitted native runtime.

## Persistent Workspace build cache

Commands receive an explicit argument array, a relative working directory, a cleared environment, private `HOME`, temporary and Cargo directories, no terminal input and bounded UTF-8 output. With the build cache enabled, `CARGO_HOME`, `CARGO_TARGET_DIR`, `npm_config_cache` and `PIP_CACHE_DIR` point into the admitted cache view (`/cache` on Linux, the cache volume on macOS); otherwise they point into private scratch. Toolchain subtrees are executable across their whole tree, so `bin` entries that symlink into `lib` run on both platforms; selected `bin` paths augment the fixed system `PATH` in grant order, and a selected host cache replaces only its corresponding nested cache path. Each snapshot is a fresh writable copy of selected project paths, including prior typed edits and integrated changes; empty directories and executable bits survive without set-ID bits.

Each Workspace has one archive keyed by its canonical path plus device and inode; at most 128 identities are retained. A nonblocking exclusive identity lease covers restore, collection, publication and clear, and competing operations return busy. Restore writes only fresh single-link regular files and executable bits into a separate quota-backed view and never creates links. Store accepts only allowlisted cache roots and rejects symlinks, special files, set-ID inputs, malformed paths, identity drift and unknown archive data. After positive descendant termination and native cleanup, Guard streams a bounded candidate to Store, which publishes it through a rollback intent, a committed marker and a successful parent-directory sync. Failure before the marker rolls back. If the marker write or its sync fails, Store returns a persistence error and keeps both archives and the records. Recovery must sync the directory before resolving the marker; a continuing failure blocks cache admission until recovery succeeds or the user runs `/cache clear`. Recovery restores the previous archive when a committed new archive is invalid and the previous one is valid; a synced marker keeps a validated new archive. Malformed or unsafe records fail closed and remain available for diagnosis. A failed, nonzero, cancelled, timed-out, overflowed or uncertain command never publishes, and the last committed cache survives.

The controller records a typed `cache_update` beside the original observation, command result and Guard receipt, with six values: `published` (candidate committed); `rejected` (known size or quota rejection kept the prior archive); `failed` (candidate validation, host-side staging create, write or sync, reopen, or a known publication failure left the prior archive committed); `uncertain` (outcome cannot be confirmed and stops Run continuation); `not_attempted` (Guard error after dispatch, or a failed command that did not attempt publication); and `not_applicable` (no private cache). Uncertainty never changes the command's disposition: a successful command stays `succeeded`, and a successful cache-backed command cannot commit `not_attempted`. Publication is never retried by rerunning the command. Cache data is never executable authority or automatic Provider context; command or MCP output that discloses it is ordinary bounded observation. Background jobs do not survive a call. This finite profile does not establish support for every large Rust, Node or Python build.

The cache result is separate from command success. Text receipts surface rejected, failed and uncertain updates; JSONL and replay keep the full observation. The `default` or `build` class, user settings and checked headroom set each invocation's cache-view limit. The 8 GiB setting is a requested maximum, not usable capacity: committed archives, metadata, reservations, candidate and staging all count toward the 8 GiB StateRoot aggregate, and candidate and view are capped by remaining headroom. No cache is evicted automatically. Increasing the setting raises no other bound.

`/cache clear` removes only the current Workspace archive and displays `Cleared this Workspace's private build cache`; `/cache clear all` reclaims all committed caches and displays `Cleared all private build caches`. A busy clear displays `Build cache is in use; retry after its command finishes` and keeps the archive. A malformed clear displays `Error: Usage: /cache clear [all]`; other failures display `Error: private build cache could not be cleared`.

Archives capture regular files by content regardless of link count, so Cargo hard links restore as independent files. Competing operations return busy rather than wait. Publication builds the candidate beside the committed archive, syncs it, durably records rollback intent before renaming, and treats the committed marker with parent-directory sync as the commit point. A marker write or sync failure returns the error, skips Drop-time recovery and retains both archives and transaction records. Task transport carries only the checked Workspace identity and the exact read-only exclusions, never a `StateRoot` path or handle.

## Command changesets

After command completion and positive descendant termination, Guard compares the private snapshot with its admitted input and returns a sorted changeset of created, modified and deleted regular files with digest-bound before and after bytes and executable bits; binary content uses canonical base64. A nonzero exit may still return changes, since exit status and publication are separate outcomes. A failed capture, timeout, cancellation or unconfirmed cleanup publishes nothing.

The snapshot is scanned without following links or reading excluded paths. Links (including hard links), special files, set-ID bits, excluded or invalid paths, mount crossings, unsupported type conversions and overflow reject the whole changeset. Directory creation is supported only as parents of created files; empty-directory changes are not integrated. The ceiling is 64 files and 8 KiB aggregate decoded before and after content, plus the existing serialized capacity; the Build class raises neither these nor other Workspace or Tool-context limits.

Engine records the command observation, then creates a separate one-use integration intent bound to that exact receipt; models cannot request integration. The Goal path scope and pinned write grant are checked before publication. An out-of-scope integration is journaled as `Denied` with no receipt or dispatch, and replay accepts only that correlated denial. In-scope integration goes through the typed-mutation Guard and never adopts subprocess-created host paths. Approval cannot widen the grant. Auto edits accepts in-grant integration after command approval; Request approvals shows the sanitized before and after changes and asks separately; Auto approval reviews the concrete integration and asks a human on uncertainty. Headless runs use their upfront grant. Goal plan revision cannot widen the pinned Tool grant.

Before publishing, Guard validates the whole batch, Workspace identity, every before digest, executable bit or absent-file precondition, and parent types through no-follow handles; conflict, denial or overflow leaves every file unchanged. Publication uses fresh regular inodes and checked deletions, then synchronized directory receipts. It is not an atomic multi-file transaction: failure or drift after publication records Uncertain and stops the Run without retry. Cancellation during approval changes nothing; cancellation during publication may leave uncertain effects. Replay retains both outcomes and never repeats the command, approval or integration. Only a successful integration receipt proves publication.

Before dispatch, a command reserves Store and Event headroom for its observation, any required integration and the terminal Run and Goal receipts; if that tail cannot be admitted, the command does not dispatch. Integration shares the Goal's active-time accounting, uses fresh authorization and never renews the command's approval.

Command capture starts only after payload descendants are positively absent, and the changeset scan finishes before images detach. Guard, not the worker, validates the integration batch. The system-executable catalogue travels only through the trusted controller and supervisor channel, never Workspace or payload input, and is never persisted as an authority cache.

```json
  "directory": "/absolute/reviewed/skills/review",
  "files": {"SKILL.md": "<digest>", "references/checklist.md": "<digest>"}

```

Arany discovers project Skills only from `.agents/skills/NAME/SKILL.md`, admitted by remembered whole-folder trust or by an explicit grant whose roots contain `.agents/skills`. Other harness directories, `agents/skills` and home Skills are not automatic sources. Private entries take precedence over duplicate project names. Names, resources and digests are bounded and pinned anew at Run admission; links, special files and excessive discovery reject.

The model sees admitted names and bounded previews, then requests `SKILL.md` and listed resources lazily. Project previews are literal frontmatter excerpts, not host-side YAML parsing; descriptions truncate to 96 characters, and resource digests stay in admission and receipts. `SKILL.md` needs YAML frontmatter with a matching string `name` and a nonempty string `description`. Quoted, folded and CRLF forms are supported; ambiguous, duplicate or excessive metadata and local executable YAML tags reject. Global YAML tags may be ignored inertly. `allowed-tools`, hooks, shell directives, forks and installation text are guidance, never grants. Scripts need an ordinary approved command; requesting a Skill executes none of its body. Attached completion exposes admitted names, including unsent `$NAME` insertion, per the [terminal completion contract](./terminal.md#interactive-commands-and-completion). Untrusted folder contents grant no Skill access. Startup and `/permissions` refresh names, Run admission revalidates them, at most 64 names are admitted, and installation changes during a pinned Run never renew grants.

A root `skills-lock.json` without a `.agents/skills` directory produces an attached notice to run `npx --yes skills@1.7.0 experimental_install` in the project, which restores the lock through the [Skills 1.7.0 installer](https://github.com/vercel-labs/skills/blob/v1.7.0/src/install.ts). Arany inspects installation state, never lock contents or historical command execution, and never runs the installer; an existing Skill directory, even an empty one, produces no notice.

YAML parsing occurs only inside the killable Guard, never in the credential-owning Engine; parser input caps do not prove bounded parser allocation or safe transitive code. Linux mounts Skills read-only under `/skills/SKILL_ID`; the macOS file worker opens only the requested admitted resource through checked handles and validates its pinned digest. Unlisted resources cannot load. A Goal plan names each Skill resource exactly (`resource: null` means `SKILL.md`); the list narrows the admitted names and files and never grants discovery or additional resources. A matching successful Skill receipt may satisfy a Goal's success criterion.

## Private worker targets and handover transfer

These are internal facilities; [Engine editor admission remains unavailable](./execution.md#worker-journal-protocol). An assignment owns an immutable base and an acknowledged cumulative overlay. Its target pins the assignment, base-manifest digest and revision, separately from logical Workspace device/inode, Run, policy and enforcement identity. Base capture reads only admitted directory capabilities, scans twice to reject drift in bytes, types or subtree membership, and records explicit absence for leased creation roots. Unsafe, protected, linked, special, set-ID, cross-mount and case-aliased inputs reject. An absent creation root reconstructs only its structural parent directories inside the private view; Mkdir remains a separate typed private operation. Neither repository Git nor repository configuration executes.

Read, List and Search project only the immutable base plus that assignment's acknowledged edits, using the same paging/result limits as Workspace reads and target-bound in-process attestation. They never reopen live Workspace files or observe siblings. Only typed Write, Edit and Mkdir can mutate a private view. Scope, expected digest, exact replacement, file count, content bytes and remaining serialized-data allowance are checked before native dispatch. Write/Edit preserve executable bits and cannot remove files; Mkdir is private preparation and empty directories never become published file changes. Each mutation reconstructs a fresh disposable file view inside the Guard, captures the complete resulting image, and validates the exact typed change before producing that mutation's complete before/after delta against the acknowledged revision. Final handover capture produces the cumulative delta against the assignment base. A candidate supplies no acknowledged revision until its matching data seal and ToolFinished are committed. No private receipt claims Workspace publication.

Snapshot scanning, retained data and complete candidates use the independent [execution data bounds](./execution.md#worker-journal-protocol). Immutable raw bytes are shared in memory; base64 encoding belongs only to bounded serialization and transfer. Reject the whole action at the first overflow; no splitting or truncation. Each committed record consumes the assignment's remaining data allowance. An unchanged final handover may reuse its exact previous mutation seal through a fresh guarded capture without advancing the revision or duplicating data. Engine/Store admission must reserve the complete action and terminal tail before dispatch; nominal limits do not promise available Store capacity.

The 96 KiB task carries normalized operation and transfer pins, with no inline bulk bytes. A separate bounded binary phase carries a little-endian total length and SHA-256, full-size length-prefixed chunks (only the last may be shorter), and a zero terminator, within the [chunk and transfer bounds](./execution.md#worker-journal-protocol). Length, chunk shape, canonical data, digest, target and grant are checked before Ready; buffered trailing input refuses. GO is separate and one-use, and final EOF/trailing-output checks precede accepting a candidate. Transfer shares the finite action deadline, capped at 120 seconds. Output is fully checked before sealing; bytes never enter model context, diagnostics or telemetry automatically.

An internal Workspace ApplyChangeset may carry the exact WorkerHandover sealed reference and transfer its complete canonical data through this same phase. Parent scope and exact path case are validated before GO; publication rechecks the whole batch's digest/absence/type preconditions before the first write and uses the existing fresh-inode publisher. Case scans are bounded to 8,192 entries. The command source retains its separate [changeset](#command-changesets) and argument limits and receipt correlation. Ordinary runtime dispatch still refuses worker preparation/publication, so these facilities grant no model editor or integration authority.

Linux gives private targets fresh 64 MiB project and scratch tmpfs mounts, no writable host Workspace and no selected command/runtime resources. Its file worker adds a non-spawning seccomp layer. macOS reconstructs on the existing fixed-size, case-sensitive 64 MiB project/scratch volumes under the non-spawning Seatbelt file profile, without granting the host Workspace; publication uses the ordinary guarded Workspace file profile. Neither private target uses a Build increase, cache or network grant. Materialization and file effects occur only after GO inside the Guard. Native cleanup uses existing owned seeds/volumes, positive process termination and retained capacity on both platforms; no persistent worker filesystem or new cleanup format exists.

A bad frame or snapshot/grant mismatch before GO is known non-dispatch. Missing or invalid completion after GO is private-target Uncertain: stop that actor and never retry the effect. A cleanup receipt requires positive containment/disposal; unknown cleanup cannot release native capacity or become a Workspace publication claim. Workspace publication uncertainty retains its existing whole-Run stop semantics. Persistent command-capable views remain C3.

The private Tool/fs corpus is `tools::worker::tests`; the shared native journey is `guard_runs::native_private_guard_target_keeps_edits_disposable_and_reads_assignment_local`. Linux seed retention and macOS private-volume ownership remain with their existing native cleanup owners. Native platform evidence is required separately from these implementation facilities.

## Local MCP

Each `mcp` entry pins a server executable, immutable input files, fixed startup arguments and allowed tool names:

```json
{
  "name": "local",
  "program": {
    "name": "python-mcp",
    "executable": "/absolute/resolved/python-executable",
    "sha256": "<digest>",
    "interpreter": true,

```

The configured server has the same offline snapshot, runtime and descendant restrictions as commands, with no Provider or account credentials. This subset is intended for local data and computation tools. Servers needing external APIs, credentials, writable host state or package installation are not supported by this base.

Arany implements the **2025-11-25 stdio tools profile**: `initialize`, exact version and capability negotiation, `notifications/initialized`, bounded `tools/list` pagination, schema validation, one `tools/call`, then disconnect. It is not the newer 2026-07-28 stateless profile or an HTTP/OAuth adapter. Server-to-client ping works; sampling, roots and elicitation are unavailable and receive method-not-found responses. Notifications cannot trigger discovery, refresh permission or extend deadlines.

Discovery returns a digest of each admitted complete tool definition. A later call lists again and requires the selected digest; drift rejects before the call. Arguments must be an object encoded as a JSON string that satisfies the admitted input schema. Schemas use the supported Draft 2020-12 or Draft 7 subset, bounded linear regexes and offline compilation; references, `$id`, remote retrieval and unsupported dialects reject. Calls have no hidden retry. Output admits bounded text, inert resource links and legacy object `structuredContent`; a declared output schema is enforced for successful results. Links are not fetched. Embedded resources, images and audio are rejected. `isError` is recorded as an observed failure, not success.

## Extension and transport admission

The current MCP profile is [local stdio](#local-mcp); no generic listener, remote MCP or runtime self-update is admitted. A new listener requires a named feature and a separate reviewed protocol. The [stdio server](../../NEXT_STEPS.md#pursue-in-order) and network-capable extensions remain deferred.

Any future HTTP or MCP listener must validate exact `Host` and `Origin`, authenticate and authorize each session, admit exact content types, bound bodies and sessions, reject DNS-rebinding, CSRF and cross-site requests, and encrypt traffic leaving loopback. Loopback routing is not authentication. The sole current listener exception is the one-shot [OAuth callback](./chatgpt.md#authorization-transaction). PTY, update, package-install, approval and other high-authority operations require a narrow authenticated protocol and explicit capability rather than a generic listener.

MCP servers, plugins, Skills and updates require reviewed provenance and an immutable version or digest; no update endpoint may select arbitrary packages or installation/lifecycle scripts. Future MCP credentials must bind server, issuer, audience, scopes and session, never Provider or ambient credentials; authorization is per server, Tool, resource and operation. Manifests and results remain untrusted. Network grants retain the [Provider destination and disclosure constraints](./provider.md#configuration-and-egress).

## Typed Git reads

Install Command Line Tools to enable macOS Git reads; remaining macOS evidence is listed in [next steps](../../NEXT_STEPS.md).

1. **Availability.** Folder trust pins the platform Git when it resolves under the platform root to a root-owned, non-set-ID, non-writable executable of the platform's format (path and SHA-256 per Run): `/usr/bin/git` (ELF) on Linux, `/Library/Developer/CommandLineTools/usr/bin/git` (Mach-O) on macOS. Explicit configuration uses the `git` field (`name` `git`, executable under the platform root, SHA-256, `interpreter: false`, no inputs) and requires `workspace_paths: ["."]`. Without a pin the catalog reports `unavailable`, no Git operation is offered or admitted, and Git is never emulated. Git outside the platform root is unavailable by design: Nix, Homebrew and Guix Git, Xcode.app Git and, on macOS, the `/usr/bin/git` xcrun shim.
2. **Operations.** `git_status {path}`, `git_diff {path, base, head, staged}` and `git_log {path, revision, max_count}`. `path` is a Workspace-relative literal pathspec, and `.` is the whole repository. `git_diff` compares the working tree with the index, the staged index with `base` (or HEAD when `base` is null), the working tree with `base`, or `base` with `head`; `head` requires `base` and excludes `staged`. A revision is `HEAD`, a ref name or a hex commit name with at most four `~N`/`^N` steps, at most 128 bytes; ranges, `:`, `@{` and options reject. `max_count` is 1 through 50. Results are JSON: `git_status` returns `{"branch":{"oid","head"},"entries":[{"path","state"}],"truncated"}`, `git_diff` returns `{"files":[{"path","added","deleted"}],"patch","truncated"}`, and `git_log` returns `{"commits":[{"oid","parents","author","time","subject"}],"truncated"}`. A failure returns `{"failed"}`, plus `"stderr"` only when bounded diagnostics remain.
3. **Exclusions and fidelity.** The components `.git`, `.aws`, `.ssh`, `.gnupg`, `.env`, `.env.*`, `.npmrc` and `.pypirc` are excluded case-insensitively (ASCII) through `:(icase)` pathspecs and row and stderr filters, including history, so `.ENV` or `.Env` on a case-insensitive APFS volume is excluded too. Renames are not detected, submodules are ignored, and `.git/info/exclude` is not applied. Git runs with default settings, not the repository's: `core.filemode`, `core.autocrlf`, `core.eol`, `core.ignorecase`, `core.symlinks`, `core.excludesFile`, sparse checkout and `branch.*` are not applied. A WSL2 `/mnt/c` repository with `core.filemode=false` can show mode-only changes, and an `autocrlf` repository can show line-ending changes that your own `git status` hides. The fixed view config omits `core.precomposeunicode` and `core.ignorecase`, so on APFS a non-ASCII or case-variant name can appear as deleted plus untracked. These fail without running Git: a repository rooted in a parent directory, a linked worktree, a submodule checkout or other `.git` file, a symlinked `.git`, a missing `HEAD`, `objects` or `refs`, and `[extensions]`. A split index fails when Git runs.
4. **Neutralization.** Git never receives the repository's configuration, hooks or attribute-selected drivers; Arany reads repository config only to detect `[extensions]`. It runs against a private view on scratch tmpfs (Linux) or in the unit control root (macOS): a fixed config, a copied `HEAD`, and linked `objects`, `refs`, `packed-refs`, `index` and `shallow`. It runs with a closed 13-variable environment, fixed argv (`--no-optional-locks`, `--no-ext-diff`, `--no-textconv`, `--no-pager`, `--end-of-options`, `--`), read-only Workspace access (a bind on Linux, a Seatbelt read grant on macOS), no network, the rechecked pinned executable and the default resource profile. Linux stops namespace descendants before the receipt; macOS empties the unit coalition at teardown. Inert vectors include `core.fsmonitor`, hooks, `diff.external`, textconv, filter drivers, `include.path`, pagers, signing programs, credential helpers and lazy fetch.
5. **Policy and disclosure.** Git reads need the pinned grant and no approval in any mode. They are in the Goal prelude with plan-contract `path` scope, are never success criteria, and are never offered to children. Bounds: 256 KiB stdout and 4 KiB stderr kept per Git invocation, 256 rows, 50 commits, results fitted to the Tool result budget with `truncated`, and at most 20 seconds per read. On macOS the same bounds run under the supervised default profile in [limits](#limits-and-failure-behavior). A nonzero exit is Failed with its status and at most 1 KiB of diagnostics, and the Run may continue. Committed history and changes reach the Provider and the journal as untrusted data. Residual risk: secret-path exclusions are pathspec and output filters, not sandbox enforcement.

macOS trade-offs, known and accepted for this release:

- The private view has no volume quota (`install_git` uses `unit_root`, which skips `storage::verify_storage`), so writes are bounded only by the 20-second cap and fixed argv. The pinned Git has no code-signature or entitlement verdict; its only check is a SHA-256 pin of a root-owned file, and the kernel enforces the platform signature at exec.
- A TOCTOU window exists between `verify_pin` and spawn-by-path. Linux avoids the equivalent window by executing the pinned file in place; macOS cannot, so exploiting it requires root write access to the Command Line Tools tree. Ancestor directories of the pinned executable are not checked for ownership or writability on either platform; `verify_host_executable` checks only the leaf. This is a known limit.
- A Command Line Tools update changes the digest, so Git reads fail with `ChangedInput` until folder trust is renewed. The read-only Workspace bind includes `.env`, so a Git memory-corruption bug triggered by a hostile pack could emit Workspace bytes through the bounded output channel, the only exit because there is no network. Encodings are offline-tested only; live evidence is listed in [next steps](../../NEXT_STEPS.md).

## In-process reads

Execution-site dispatch stays inside `ToolRuntime::execute` using the operation's
pinned site. A `ToolExecutor` trait with interchangeable InProcess and Guard
adapters was rejected: the sites enforce different contracts, and a fake Guard
could make Engine tests pass without exercising enforcement.

List, Read and Search run in the Engine process, as Claude Code and Codex CLI run reads outside their command sandbox. Typed Git reads, typed mutations, commands, Skills and MCP stay in the Guard, because they spawn a process or change the Workspace. The Engine opens the Workspace directory handle once at Tool admission, which still requires available native protection, and resolves every path beneath it with the Guard's no-follow, link, mount, special-file and protected-name rules (including `.env`) and the same `workspace_paths` scope, so disclosure does not widen. Before each read it rechecks the intent, its expiry and policy digest, and that both the pinned handle and the Workspace path still have the admitted device and inode; a replaced directory records Failed at `pinned input` without attestation before reading and stops the Run.

Results fit the intent's result budget before serialization: a Read page ends early with `truncated` and `next_offset`, and List and Search drop trailing rows and set `may_be_truncated`; a budget too small for any content is Limit. A read is bounded by its intent runtime: timeout records Limit and cancellation records Cancelled, neither attested. It waits for no Guard capacity and reserves its Goal action with zero preparation overhead, so exhausted active time refuses it and its runtime is clamped to the remaining active time.

Each observation carries an `attestation`: `in_process` with the policy digest and Workspace device and inode, or `guard` with the Guard receipt. Validation and replay accept an attestation only from the site the operation runs at, so a read attestation never authorizes a mutation and a Guard receipt never attests a read. The Guard refuses a read intent. In-process reads run with the Engine's ambient privileges, not the Guard's OS sandbox: their boundary is the handle-relative checks, and they never write, spawn or use the network.

## macOS enforcement and compatibility

Native Tool dispatch requires an available Background launchd user domain, a distinct kernel resource coalition, a trusted bounded supervisor and a separate attested Seatbelt worker. The private control directory lies outside the Workspace; overlap rejects before dispatch. The supervisor's launchd PID and authenticated local peer must identify the same process. The controller accepts completion only after the owned coalition is empty and the one-use job is removed or positively reported absent; automatic job retirement alone is not descendant cleanup. There is no unsandboxed fallback. Typed Git reads use a third Seatbelt profile that may spawn only the pinned Command Line Tools Git, with no command catalogue, runtime grants, network or Mach service lookup. The file and Skill worker stays non-spawning; commands and MCP keep ordinary child launches.

Before Tools are offered, admission validates the immutable `launchctl`, `env` and `hdiutil` executables through the same no-follow OS-program admission, then coalition observation and the user's launchd domain (a data-free probe with a three-second deadline and one second for kill and reap). Unit authentication, coalition ownership, storage preparation and installed enforcement remain mandatory before GO; startup availability is not dispatch attestation. Controller connection and preparation deadlines name their stage; native-manager command failures name that boundary without exposing native diagnostics. Cleanup failures retain their own stage and still prevent acceptance. After an effect, supervisor process stop, launcher reap, stderr EOF and storage-cleanup retries share one ten-second teardown bound (the MCP server reap and stderr drain share a second, equal bound inside the worker), member enumeration that fails while a process exits is retried within it, and storage cleanup makes at most eight attempts with pauses growing by 250 ms, starting and pausing only while time remains, so a transiently unlistable disk-image inventory is retried within the bound; a path-less inventory entry still rejects. A device that leaves the inventory between an attempt's listing and its detach re-check is never detached; the attempt is retried, and only a later attempt's fresh inventory and mount checks can accept. A storage-cleanup attempt already running keeps each native disk-image command's own bound, so teardown can outlast the shared bound; the controller's completion deadline then ends the call Uncertain. Only observed termination and detachment accept; exhausting the bound leaves the call Uncertain. The worker names a failed teardown step with a closed stage (process cleanup, launcher reap, output EOF or storage cleanup) in its final line, which the controller reports as the Guard stage; no worker text reaches the model. A storage-cleanup failure also names the failed check (inspection, listing unavailable, device unlisted before detach, detach failed, image still listed or mount still present), which in product builds only the debug development log records; test-support builds also keep it per Tool intent for release test assertions. A macOS execution failure after dispatch names its check the same way (worker closed before its report, worker panicked, malformed report, unattested report, report not followed by end of stream, cancelled or controller thread failed); the model-facing stage stays execution. The supervisor's stdout and stderr go to one owner-only output file in the unit root, discarded with it. Its only output is panic text, which its panic hook writes up to 4 KiB in total and drops beyond that; the runtime's fixed fatal-abort lines are the only other writes. When the worker closes early, the controller reads at most the file's last 4 KiB, classifies a panic, and keeps the printable tail for the debug development log and test recorder only. Privileged OS mutation remains outside the current-user boundary.

Supervision uses kernel process identity and cumulative CPU accounting across exec. Reaped or replaced members retire after identity revalidation, including when sampling fails during exit; missing observation of a live member still rejects. Exact-incarnation signaling must not affect a reused PID.

Private storage allocates separate owner-only, writable native filesystems sized from the immutable intent: scratch 64 MiB; the project volume 64 MiB by default, up to 1 GiB for Build; and the cache view, which has its own checked effective capacity. These volumes are distinct, and enlarging one enlarges no Workspace bound. Admission reserves the exact backing sizes and rejects before GO if they do not fit shared capacity. Each unit's root is `/private/tmp/arany-u-<uuid>`; the live unit creates and locks `unit.lock` in one exclusive open, which the kernel releases when the controller exits, including on a crash. Before launching its job, the controller durably records the root's device, inode and macOS boot identity; the supervisor durably records its process and coalition identity before receiving a task, and no payload or attachment may precede this record. Normal completion, partial setup, cancellation and unwind require positively established process termination before detachment. Unexpected mount targets reject without being followed. Unfinished attachment or failed cleanup retains the control root and rejects completion rather than recursively deleting through a live or uncertain mount. Each volume is a fixed-size, case-sensitive image attached kernel-only, so a payload sees a case-sensitive filesystem even on a case-insensitive host.

Before creating a unit, admission scans at most 4096 directory entries and attempts recovery of at most eight unlocked roots owned by the effective uid, within one 30-second recovery deadline. Recovery takes an exclusive lock and validates private no-follow records and root identity before cleanup; live controllers and competing recovery owners are excluded. Within the recorded boot, recovery removes the exact one-use job and positively empties its recorded coalition by current audit-token identities. After reboot it never signals persisted identities or removes a job from the later boot. Storage cleanup requires the pinned backing image inode, the OS disk-image inventory and exact device and mount correspondence; unexpected or nested mount targets reject before detachment, and an attached but unmounted owned image must be detached. An interrupted-attachment marker clears only after positive absence following detachment of the positively identified image, or evidence that its recorded boot ended; empty inventory alone cannot settle a current-boot attachment. Recovery durably records positive observation before detachment. Root deletion also requires absence of all mounts beneath the checked root. Unlocked roots without valid ownership records, including older retained roots, stay untouched and count toward shared capacity with live and recovering roots, including roots interrupted before lock publication. Valid records are selected before the eight-attempt budget is spent. Unreadable or over-limit listings and deadline expiry reject as unavailable native protection without removal advice. A filename prefix never authorizes cleanup, and there is no stored-format migration. Cancellation or failure leaves recoverable records in place and never retries an old Tool intent.

Commands and MCP receive a fresh checked snapshot of the selected Workspace, including prior typed edits, and a separate read-only tree of pinned runtime resources. Writable project and scratch mounts prohibit set-ID behavior. Reviewed system executables must be immutable, root-owned, non-set-ID and unentitled; privileged process, credential and coalition changes stay denied after exec. When a grant enables commands or MCP, admission checks the bounded system-executable catalogue once per Run, and each process intent and receipt binds it to the compiled policy. Workers revalidate its no-follow identities, ownership, permissions, size and modification or change timestamps before Ready; changed or oversized catalogues reject before dispatch without refresh or retry. The catalogue is transient trusted-controller data within the Task byte cap; file and Skill workers carry none. An undetermined signature result excludes that program for that admission only. The runtime excludes host account and Session roots, network destinations and Mach services. Root or mismatched real and effective identities reject process dispatch. Ordinary unprivileged `fork`, `exec` and `posix_spawn` remain available. Unselected host paths have no general metadata grant; traversal ancestors such as `/private/tmp` and the unit control root grant metadata without listings, and admitted runtime directories stay readable. Commands also read the literal filesystem root because the native loader opens it, which lists top-level names without granting access beneath them. Exact runtime metadata covers native shell selection and system path aliases; it grants no subtree access to host account or temporary storage.

macOS uses private physical paths rather than a mount namespace. The command's working directory lies inside its project snapshot. Standalone argv paths rooted at `/workspace`, `/scratch`, `/cache`, `/inputs`, `/skills` or `/programs` map into private storage, and copied-program aliases apply to copied executables. Shell strings are not rewritten; scripts use `ARANY_TOOL_WORKSPACE`, `ARANY_TOOL_INPUTS`, `ARANY_TOOL_SKILLS` or project-relative paths. `HOME` and `TMPDIR` point to private scratch. Checked system binaries execute at their original paths because native relocation is not universally supported.

On macOS, absolute traversal opens intermediate directories with search-only descriptors and only the selected final directory readably, because a readable ancestor would expose sibling listings.

Canonicalized selected roots reject strict descendant targets in the `getfsstat` mount table before Seatbelt and before Ready/GO. This is a point-in-time check, not a lifetime guarantee.

Non-spawning file and Skill workers reset and unblock `SIGXCPU` and install hard CPU expiry before Seatbelt prohibits changes; commands and MCP rely on external CPU supervision. Denial is attested before GO, so no payload runs under a partially installed profile. The profile denies sysctl access, named socket creation, network operations and descriptor-bearing messages. Inherited bootstrap ports are cleared before payload exec, and `NOSUID` alone does not strip signed entitlements.

System executables are revalidated per catalogue entry through no-follow handles (root ownership, non-writable and non-set-ID mode, device and inode, size and timestamps) opened relative to pinned `/bin` and `/usr/bin` handles. A signature verdict is reused only for the same path and an identical metadata stamp, and is never persisted.

Unit membership is observed through bounded kernel metadata, never process arguments or environments. Memory is measured as aggregate physical footprint plus live thread count; resident size omits compressed and swapped pages, so a missing live observation fails closed. Cleanup requires an exact-target `bootout` that succeeds or reports absence, then positive emptiness, even after one-use retirement.

Cleanup terminates and positively empties the payload coalition before detaching either disk image, including during preparation unwinds. It never removes a mounted or uncertain control root and never sweeps roots by filename prefix; deletion needs positive ownership and device or mount evidence. The unfinished-attachment marker is created immediately before attachment, after image creation and validation, and backing image inodes are pinned before attachment.

Debug builds with an explicit account root and `ARANY_TEST_GUARD_TRACE` may record Guard stage snapshots for fixtures: one fixed record per compiled stage, at most 128 bytes each and 8 KiB in aggregate, each `active`, `complete` or `interrupted`. Repeated observations overwrite their stage, so the trace is a snapshot, not a log. Capture failures never change Tool outcomes, and records never reach Events, Provider context, telemetry or the development log.

Linux and macOS coordinate Guard capacity across processes and Session roots through the effective user's fixed account root. The owner-only file `guard/limits.json` is created on first native admission with:

```json
{"version":1,"units":8,"queued":32}
```

Edit that private file to change capacity; preserve mode `0600` and the private directory. On macOS the fixed account root is `~/Library/Application Support/dev.Arany.arany`; on Linux it is `~/.local/state/arany`, resolved from the effective user's account rather than environment-selected Session storage. `units` accepts 1–64 and `queued` accepts 1–1024. Unknown fields or versions, unsafe files and invalid ranges reject admission. Every admission rereads settings. Lowering a limit never kills admitted units or registered waiters; no new admission exceeds the selected limit, so existing usage may temporarily exceed a lowered value.

Every Guard unit, including file-only units, reserves one slot before native launch. Live, recovering and retained units count. macOS admission also reserves the exact bounded backing-volume sizes of the immutable intent; a per-Goal maximum does not guarantee that all units can run at that maximum concurrently. Existing excess roots from a previous implementation are retained and prevent further admission. Linux's per-unit mount and cgroup limits are unchanged, and its slot owns the host seed until checked deletion. Each seed holds at most 32 MiB of selected Workspace data and 96 MiB of runtime data, bounding newly admitted retained payload at `units × 128 MiB` (1 GiB by default). This is a logical payload bound, not a physical filesystem quota; directory, file-count and record bounds apply separately. Historical unrecorded seeds require the maintenance procedure below.

When capacity is occupied, the approved Tool remains pending in its Run. Up to `queued` Tools register in one shared FIFO ordered by registration under the namespace lock; newcomers cannot overtake registered waiters. Cancellation, original intent expiry and process death remove a participant's position. For Guard Tools, intent expiry bounds approval and this capacity wait only: once admitted, native preparation and GO are bounded by the preparation and GO deadlines, so on both Linux and macOS a short command timeout is no longer refused when preparation outlasts it. Linux still reaches GO within its five-second preparation deadline, and macOS within its worker preparation bound. Overflow rejects before effects. Waiting never renews an intent, approval or Run budget, is not a durable queue, and restart never resumes old permissions. There is one pending Tool per Run. The [terminal contract](./terminal.md#conversation-progress-and-history) owns the temporary queued indication. Native recovery keeps its 30-second deadline within the original intent lifetime; local filesystem bounds remain cooperative, not hard-real-time guarantees.

Coordination records are no-follow, owner-checked, mode-checked, ACL-checked, single-link and bounded. Coordination creates no database or history records, and admission never creates canonical Events; wait hints use the existing callback. Reaping in `Drop` never bypasses the attempt and deadline budget. Preparing without a committed identity authorizes only removal of an empty directory. macOS control roots count against capacity independently of reservations, with UUIDs deduplicated.

### Linux host seed ownership

Every new host seed retains its reservation from creation until checked deletion. Normal completion leaves no seed or stale reservation. After controller death, the next admission recovers owned storage before releasing capacity, without replaying the effect. Failed deletion, identity uncertainty and ambiguous native launch keep the charge. A new boot settles old processes but not file deletion. Recovery resets a positively identified failed unit before retirement; a missing or not-loaded unit cannot settle an interrupted launch, so that reservation can exhaust capacity until positive native evidence or a later boot permits recovery. Linux reservations use version 2; macOS remains version 1. A locked lease owns one bounded seed record and at most one publication temporary; the planned location is committed before exclusive creation and the directory identity before copying payload. A dead preparation without a committed identity permits only empty-directory removal. Launch-requested precedes launcher invocation, and positive native termination precedes recursive deletion. Deletion rejects links, mounts, foreign ownership, unsafe permissions and replacements; incomplete cleanup retains its slot and prevents completion. Historical unrecorded roots need the [one-time maintenance procedure](../tools.md#historical-linux-seed-maintenance), with Arany stopped, positive native inactivity and authorization of exact inventoried objects; reboot is the fallback for uncertain inactivity. A name prefix never authorizes removal, and normal admission neither migrates nor deletes unsupported records.

## Linux enforcement and compatibility

The first enforcer requires installed non-set-ID, root-owned `/usr/bin/bwrap`, `/usr/bin/unshare`, `/usr/bin/systemd-run`, `/usr/bin/systemctl` and `/usr/bin/env`, working unprivileged user namespaces, a systemd user manager and cgroup v2 with effective memory, swap, PID and CPU limits and owned cgroup termination. `systemd-run` must support `--expand-environment=no`; installation alone does not establish compatible launch capabilities. A fixed `/usr/bin/unshare --user --map-current-user --mount --propagation private` bootstrap runs before the unchanged Bubblewrap command, without `--keep-caps`: util-linux establishes private propagation before exec, while retained capabilities make Bubblewrap reject a non-root real UID. Before Ready and again after GO, the helper parses its bounded namespace-local `/proc/self/mountinfo` and rejects ambiguous roots, stacked or missing runtime mounts, propagation metadata and any descendant mount beneath a selected runtime mount, so a later host mount cannot propagate into an admitted runtime. Read-only binds import source submounts recursively, so admitted mount sources are checked with that import in mind. This is a kernel and native-capability contract, not a GNOME or KDE dependency. Other Linux init systems need a separately enforcing adapter. Unsupported architecture or missing enforcement fails closed, with no unsandboxed fallback. macOS uses the separate native profiles described above.

The Guard verifies isolated mount, network, PID, user, IPC and UTS namespaces, dropped capabilities, no-new-privileges, inherited syscall filters and effective limits before releasing a one-use intent. It owns the exact transient unit, invocation and retained cgroup identity, including double-fork and setsid descendants, and verifies termination before accepting completion. Garbage collection of transient units relies on the retained group's empty or removed state. The compiled seccomp deny profile is defense in depth, not a universal syscall allowlist. ARM64's profile is source-supported; native runner evidence is required before claiming platform support.

Byte and entry bounds on synchronous snapshot preparation do not guarantee a finite response from stalled host storage or an uninterruptible kernel operation. Process deadlines and cleanup bound ordinary payload execution; they are not hard-real-time or kernel-failure guarantees. Native file preconditions do not make a multi-file transaction or exclude concurrent hostile host mutation.

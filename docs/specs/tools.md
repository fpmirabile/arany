# Local coding tools

This contract owns Tool grants, guarded effects, runtime Skills and local MCP. [Terminal](./terminal.md) owns completion, settings and consent presentation; [execution](./execution.md) owns Run coordination and capacity admission. Editing constraints: [security rules](../../agents/security.md).

Arany can continue a primary AgentRun through file operations, commands, portable Skills and local stdio MCP tools. This is an explicit, offline local foundation, not unrestricted host shell access. Every attached startup asks whether you trust the opened folder before account selection or setup, including when no account is configured, unless that exact folder already has remembered trust. This consent flow is the same across operating systems and independent of Provider flags or `--tools`. `/permissions` revisits the choice. Without explicit private Tool configuration, untrusted folders remain read-only. Explicit process selections and headless Runs can opt into reviewed configuration with `--tools`; this flag adds no paid compatibility check.

Folder consent and native Tool capability are independent. On platforms without an implemented enforcer, attached chat remains available without Tools even after trust is remembered. `/permissions` uses the same consent choices; Shift+Tab reports the native restriction without enabling authority. Explicit `--tools` rejects unavailable protection. Trust alone never supplies missing OS protection: no effect runs outside the Guard, and [in-process reads](#in-process-reads) run only once native protection admits Tools.

The complete harness requires equivalent granted file operations, commands, Skills and local MCP across supported operating systems, with the same permission, isolation, cancellation and durable-result contract. Typed Git reads follow their [per-platform availability](#typed-git-reads). Resource guarantees differ explicitly by native profile as defined below. [Next steps](../../NEXT_STEPS.md#beta-2-and-broader-release) records unperformed native, platform, live and human checks; implemented code alone does not establish platform support.

Native adapters use [automatic Tool selection and plain text answers](./provider.md#structured-outcomes-and-tool-encoding), translating one semantic proposal at a time. Exact custom profiles reject `--tools` because their data-free conformance covers read-only turns. Compatibility with a real selected model requires live evidence.

The generated function and outcome schemas offer file reads and search and only catalog-enabled mutations, commands, Skills, MCP operations, typed Git reads and, with `write`, [typed Git writes](#typed-git-writes). Command, Skill and MCP-server identifiers are constrained to configured names. An unparsable or oversized catalog offers only read-only file operations and the primary's optional plan function. This restriction guides generation; catalog text supplies no execution authority, and the pinned router and Guard independently admit every proposal.

The optional `arany_plan` function records Engine-owned Goal state; it is separate from guarded effect Tools. [Goals](./goals.md#initial-plan-contract-and-success-receipt) owns plan admission, scope, success and replay rules.

## Authority and effect admission

Each mutation, process, Skill script and MCP call requires typed effects, deterministic restrict-only Policy, a separate Guard and effective-capability attestation. Hooks, prompts, command regexes, classifiers and approval UI are not enforcement boundaries. [In-process reads](#in-process-reads) use the same admitted scope and their own execution-site attestation.

An effect is normalized once into an immutable typed intent identifying actor, Run, Tool, resources, operations, destinations, descendant behavior, use count and finite action limits. Policy, approval, journal and Guard share its digest; names, prefixes, hostnames, remembered approvals and summaries never define authority. Tool effects from primary and child AgentRuns pass one deterministic Policy route. [Provider egress](./provider.md#configuration-and-egress) has its own admission under the Provider contract. The [execution contract](./execution.md#collaboration) owns child grants.

Execution requires effective capabilities equal to or narrower than the authorized set. Unsupported enforcement dimensions, missing capabilities, failed attestations and authentication, authorization, signature, policy or schema failures reject. Descendants retain or lose authority; there is no automatic unsandboxed fallback. Privileged code never follows or executes filesystem objects created by a less-privileged agent or sandbox without fresh no-follow, handle-relative validation. A process starts from a trusted executable identity without ambient PATH search, with explicit validated arguments, a pinned working directory, an allowlisted cleared environment and closed inherited descriptors and sockets. Scripts require an admitted interpreter policy. Process-tree supervision, cancellation, reaping and release of permits, transactions and temporary resources follow the native profiles and [failure contract](#limits-and-failure-behavior).

## Folder trust and approvals

The consent screen shows the full folder path and vertical Read only / Trust choices, Read only focused. With explicit `--tools`, the first choice instead says Use explicit config and keeps that private configuration when trust is skipped; neither choice expands roots or capabilities. The screen lists metadata-only toolchain and host-cache candidates unchecked; checking one switches the choice to Trust. A discovery failure shows a notice and never aborts startup. Discovery runs for initial consent or when `/permissions` opens; remembered startup revalidates only saved pins, so an unrelated over-limit manager cannot block prompt-free chat. Enter confirms; Escape dismisses without a decision; Ctrl+C exits without saving one. `/permissions` first asks whether to manage folder trust or [typed Git rules](#typed-prefix-rules); folder trust rediscovers candidates, preserves unchanged selections, and permits explicit add and remove. Checking a toolchain unchecks other selections of its runtime kind; linear `trust` with two of one kind asks again, and `trust N` and `use config` also work. A selection that cannot be saved reports an error and keeps the previous permissions, so startup continues read only. Consent warns that prior versions of files changed by Arany are saved unencrypted in private StateRoot storage. Consent precedes saved-account lookup, catalog or credential access, and Session discovery or creation, for new, resumed and forked entry. Choosing read only, using explicit configuration without trust, or dismissing remembers nothing. Unavailable, malformed or unsafe trust metadata stops startup before account or Session access with a message naming the record and the failed check. An unsupported-version or malformed `workspace-permissions.json` offers Retry, Reset folder trust or Exit, mirroring [history recovery](./terminal.md#acceptance-scenarios-and-evidence-owners); a reset deletes only that record after an explicit confirmation and refuses when the record changed meanwhile. A non-private record or state directory is reported and never reset or modified. Trust is user-owned, shared by conversations, and pinned to the exact absolute path and directory identity; replacing the directory requires trust again, and replay never supplies authority. Remembered grants apply only to native Providers on platforms that admit Tools; custom Providers stay read-only. Explicit private `--tools` configuration takes precedence over remembered trust and keeps its narrower roots and capabilities.

A private `workspace-permissions.json` in the fixed OS-user account root stores at most 128 entries and 64 KiB using owner-only atomic replacement. Versions below its [migration floor](./execution.md#json-record-migration) reject without changing the record, and only the consented reset above removes it. Trust generates a version-1 Tool grant for `workspace_paths: ["."]`, typed writes, discovered project Skills and a pinned resolved system `sh` on Linux and macOS, plus a pinned system Git for [typed Git reads](#typed-git-reads) when one is available. Optional runtime selections bind each exact path, profile kind and directory device/inode to that folder entry. MCP requires explicit private configuration. Standard secret, link and mount exclusions and finite snapshots still apply; `target`, `node_modules`, `.venv` and `venv` are omitted from root discovery and snapshots. Commands use the existing offline Guard, never the host terminal, the whole home directory, package-manager configuration or credentials.

Runtime discovery reads only bounded directory entries and executable metadata under `~/.rustup/toolchains`, the per-version Node roots of nvm, fnm, Volta and asdf, and `~/.pyenv/versions`. It never executes a candidate or reads manager or project configuration. Candidates need a numeric `major.minor.patch` directory label; aliases such as `stable` and `nightly` are excluded, and the label is the manager's directory name, not a verified binary version. Python candidates need a version-specific regular executable, or a `python`/`python3` alias to one in the same `bin`; other symlink traversal is rejected. A selected Rust, Node or Python directory mounts read-only as an exact subtree, and its `bin` joins the command `PATH`; folder trust never selects every installed version. The label, absolute path and device/inode are bound into Tool policy, hashed into candidate tokens, and rechecked at Run and Guard admission and before Ready/GO; drift rejects before dispatch. Discovery and consent profile numbers use kind order (Rust, Node, Python, Cargo archive/source/index caches, npm cache, pip HTTP/wheel caches, Apple compiler, Apple SDK), then descending lexicographic version label, then ascending absolute path and token. Saved selections retain their pinned grants and are matched by token, never by display position.

macOS also offers two distinct, unchecked Command Line Tools profiles. The compiler profile is the fixed physical `/Library/Developer/CommandLineTools/usr` root; admission requires root-owned, non-group/world-writable directories, a root-owned `cc` link to `clang`, and root-owned, single-link, executable, non-set-ID and not group/world-writable `clang` and `ld` files. The native signature check must establish that both executables are unentitled; an unknown result is not checked at discovery and the Guard refuses the grant at bootstrap with `ProtectionUnavailable`. Only the selected `cc`, `clang` and `ld` executable paths receive process-exec permission. SDK profiles are exact physical directories named `MacOSX<version>.sdk` under `/Library/Developer/CommandLineTools/SDKs`; versions have two or three canonical numeric components, each in the range 0–65535 with a nonzero major component, and a total length at most 32 bytes. The selected directory and its required SDK contents must be root-owned and not group/world-writable. Compiler and SDK grants each bind their kind, manager, exact path and directory device/inode; the SDK also binds its version. Either profile requires separate explicit selection, and each counts toward the [selected runtime grant ceiling](#limits-and-failure-behavior).

Optional host caches are distinct read-only grants: Cargo's exact `registry/cache`, `registry/src` and `registry/index`; npm's exact `_cacache`; and pip's exact `http-v2` or `wheels` under `~/.cache/pip` (Linux) or `~/Library/Caches/pip` (macOS). They are never inferred from a toolchain, and no parent cache directory mounts. Cache data may include private package names, source, registry metadata or embedded credential URLs. Arany does not load it automatically, but a command or local MCP Tool can emit selected data through bounded output, which is journaled and can enter a later Provider request; consent warns of this. Configuration, credential files, environment values and parent directories stay unavailable. A selected read-only host subtree takes precedence for that Run: Arany neither reads it into its private archive nor restores private bytes over it, and it retains earlier Arany-owned entries at that exact subtree when publishing other cache changes. Disabling the opt-in restores the private writable view and those entries. Cache data supplies no authority.

Shift+Tab cycles **Auto edits → Request approvals → Auto approval → Auto edits**, preserving the draft and caret. The current mode appears beside the composer and follows the selected Provider's native capability. Selecting a supported native Provider after trusting an unconfigured conversation restores the remembered mode. Auto edits allows typed edits and asks for commands, MCP calls and Git writes; Request approvals asks for every effect. Reads and Skill or catalog discovery still need the pinned grant but no per-action question. Auto approval uses the selected AI to review the exact proposed action against the current user request and resolves an Ask within the pinned grant, which can add model usage. Uncertainty, invalid output, failure or an exhausted review budget asks the user, as does switching out of Auto while review runs.

A human approval shows the exact proposed action; [terminal approval](./terminal.md#interactive-commands-and-completion) owns layout, focus, labels and linear replies. All pages must be reviewed before accepting. Approval is one-use and never expands the grant. Primary ordinary, hook Ask and unguarded prompts have no wall-clock expiry while their human channel and Run remain live, following [Claude Code ordinary permission waits](https://code.claude.com/docs/en/remote-control#limitations) and [Codex one-shot approval waits](https://github.com/openai/codex/blob/61f34c35af77777db4d77d0ea2aeb8547a6b4523/codex-rs/core/src/session/mod.rs#L2988-L3119). Escape and Ctrl+C cancel the Run; explicit No declines the proposal. Pause, cancellation and channel loss withdraw pending work. Missing channels and failed, invalid or oversized delivery record unavailable approval, never human decline. A late allow still validates the admitted directory, any explicit file-content precondition, executable bytes, grant/enforcement digests and worker revision before dispatch; no pin is refreshed. Ordinary reads do not pin file content. Permission settings remain the Run snapshot: editing the rules file during a wait applies to later admission, not the pending decision. Child asks temporarily retain their issue-time runtime-plus-hook and delegation bounds as live Engine scheduling state until [A2](../../planning/approvals-wait/README.md#vertical-slices); a child timer withdrawal is reported as a child wait timeout, not human decline. The non-dispatched observation stores `approval_cause` as `cancelled`, `paused`, `channel_unavailable`, `declined` or `child_timeout`; other observations and migrated histories without that fact carry `null`. Presentation and replay use this typed cause, never infer it from output text. Replay never restores a live request. Denial stops the Run without retry or rollback of completed actions. AI reviews have a 20-second ceiling, a 256-token output cap, no Tools or project instructions, history or includes, and canonical Provider-call usage. They share the primary call budget, preserving final continuation; review text never becomes an assistant answer. Headless `--tools` uses its explicit private upfront grant without an interactive approval channel.

Workspace input resolves one component at a time beneath the pinned directory handle with no-follow semantics. Symlinks, special files, absolute paths, empty components, `.` and `..` reject. Candidates open nonblocking before the regular-file check, and the validated handle is used instead of reopening by path. Folder trust pins the exact path, device and inode in private OS-user state, never in Session facts. A saved toolchain grant for a recreated root is a new candidate.

Each accepted AI review is pinned to its pending Tool in the projection. Ownership is never inferred from adjacent review calls, so an approval-mode change cannot duplicate an integration review.

## Permission modes, rules and hooks

The shared Engine `before_dispatch` evaluates `arany::permissions::PermissionConfig` for primary and researcher Tool steps. Optional `permissions.json` is an authenticated user settings record beside `tools.json` in the admitted StateRoot, outside the Workspace. It uses the same private regular-file, ownership, no-follow and bounded-read admission as `provider-routing.json`; an unsafe or invalid present file rejects Tool admission. Missing settings preserve the existing interactive and headless approval behavior. Repository, Skill, model and hook text never select trust. Parsed settings are immutable data, not executable configuration or a grant. Hook commands run only as [Hook execution](#hook-execution) defines.

Tool admission snapshots the settings once and pins the SHA-256 of the complete settings bytes in `RunStarted.tool_policy.permissions_digest` (`null` when absent). Editing the file does not change an admitted Run. Present settings select the mode and approval path below, including in headless Runs: a required human approval without a channel denies; AI review can use the admitted review Provider. The terminal's existing mode cycle is unchanged when settings are absent.

Every configured step commits `ToolPermissionDecided` after its immutable `ToolStarted` and before dispatch or its denied observation. The verdict binds the exact intent digest, effective decision, pinned settings mode, rule/mode/grant basis, final approval and approval source (`rule`, `mode`, `pinned_grant`, `human`, `ai_review`, `unavailable_approval`, `exact_command_rule`, `hook` or `typed_prefix_rule`), the narrowest hook restriction (`hook_restriction`, `null` when none) and the number of hooks that ran (`hooks`). The reducer rejects missing, duplicate, wrong-intent or post-observation verdicts and any effect after a denied verdict. An AI preapproval requires a recorded review of that pending Tool. Strict replay consumes these facts without reading settings, rerunning a review or dispatching an effect. The [execution version table](./execution.md#admission-persistence-and-recovery) owns current payload versions; only an [unguarded re-run](#unguarded-re-run-after-a-guard-failure) and a primary [typed Git write](#typed-git-writes) without settings at Run start may omit the settings mode. The latter commits a verdict with `mode: null`, basis `mode` or `pinned_grant` and source `mode`, `pinned_grant`, `human`, `ai_review` or `unavailable_approval`; the reducer rejects it for any other call, for children, for a hook restriction and for rule, hook, exact-rule or typed sources, and still replays pre-existing unconfigured writes that carry no verdict.

The same settings restrict children; a child cannot select its own settings or expand its read-only spawn grant. Explicit asks go to the human adapter; auto reviews of researcher MCP discovery use the admitted review Provider with the child's exact intent and the Goal objective, within the existing delegation deadline and budget. Tool steps after primary synthesis retain their existing non-review path: required approval goes to a human or denies without a channel, preserving the delegation's reserved synthesis and continuation headroom. A human wait with no sibling call in flight is excluded from delegation active time; outstanding sibling work keeps that shared interval active. Rules never bypass the Goal plan, deterministic Policy, pinned grant or Guard. A denied call returns one short model-facing line naming the permission deny rule or mode, and terminal Tool summaries name the same cause without reproducing rule text or undisclosed paths.

### Modes and approval decisions

The [serve approval transport](./serve.md#server-requests) is another human client of the same one-use approval channel. The [ACP adapter](./acp.md#tool-updates-and-permissions) permits ordinary one-use client verdicts, including user-configured client policy. ACP v1 cannot attest a human gesture, so its approval channel disables human-only requests: unguarded commands (also when an exact project rule exists) and hook Asks dispatch nothing, send no permission request and journal source `unavailable_approval`. AI review, mode changes and client capabilities cannot resolve those requests.

The peer contract is [Claude Code permission modes](https://code.claude.com/docs/en/permissions#permission-modes). The five accepted spellings are case-sensitive; aliases and bypass modes reject. The parser's omitted `defaultMode` is `default`; it does not change Arany's existing interactive default.

| Mode | Peer behavior | Arany mapping and narrowing |
|---|---|---|
| `default` | Prompt on first Tool use. | Existing `Request`: absent a matching allow, a fresh one-use human approval for each effect needing approval. Remembering Tool use cannot renew an immutable intent. |
| `acceptEdits` | Accept file edits and common filesystem commands in working directories. | Existing `AutoEdits`: typed mutations, including changeset integration; commands, MCP calls and Git writes still ask because process behavior is not a typed edit. |
| `plan` | Explore without source edits; read-only shell commands are available. | Deny mutations and generic command/MCP processes, even with allow rules. Permit admitted typed reads, Skill reads and typed Git reads. Arbitrary argv and MCP metadata cannot prove a read-only effect. |
| `auto` | Classify actions before running without routine prompts; broad execution allows are dropped. | Preserve existing `Auto` AI review for approval-needing calls. Add review for typed Git processes and MCP discovery; every `spawns_process` call and MCP operation requires review. Matching allows never skip it. Existing budgets, uncertainty-to-human fallback and cancellation remain mandatory. |
| `dontAsk` | Deny actions that would prompt; pre-approved actions remain available. | Convert an unresolved `Ask` to `Deny`; permit otherwise admitted no-question calls and matching allow rules. An explicit ask rule still denies. |

Settings and the live terminal mode are independent restrictions: a call asks if either asks, human Request takes precedence over AI review or edit preapproval, and neither can widen a settings Ask or Deny. [Claude Code treats `defaultMode` as the starting mode that Shift+Tab overrides](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in); Arany combines both to preserve its only-narrow guarantee.

`decision(call)` returns only `Allow`, `Deny` or `Ask`. These are approval dispositions within the pinned grant, never executable authority. Invalid or oversized calls deny. `approval_mode(call)` selects human `Request` for an explicit ask rule even under `auto` or `acceptEdits`; only an otherwise unresolved `auto` decision selects AI review. A caller must still journal the exact intent and verdict and obtain deterministic Policy admission and Guard attestation before dispatch. `Decision::narrow` combines independent restrictions with `Deny > Ask > Allow`; an allow from a hook or review cannot erase an earlier denial or question. A hook's `allow` is ignored because it is runtime program output, unlike a static allow rule from user configuration; only a human or the Auto review resolves an Ask. Children retain the intersection with parent authority. There is no bypass or implicit unguarded execution: `command_unguarded` is never pre-approved by an allow rule, a mode or AI review; `plan` and `dontAsk` deny it.

**Owner-accepted peer behavior — 2026-10-17:** in `default`, a matching allow rule pre-approves commands and MCP calls without a human prompt or AI review, subject to live terminal restrictions, as in [Claude Code permissions](https://code.claude.com/docs/en/permissions#permission-rule-syntax). This is an explicit user-configured approval, not a bypass of the Guard, deterministic Policy or the pinned grant. Deny and ask retain precedence. `acceptEdits` keeps human approval for commands and MCP calls even with an allow rule; its existing typed-edit approval is unchanged.

[Claude Code drops broad execution allows on entering auto mode](https://code.claude.com/docs/en/permission-modes#how-auto-mode-evaluates-actions), including blanket command rules and wildcarded interpreters. Arany enforces the stricter behavior directly during decision evaluation: `auto` ignores allow rules for processes, MCP operations and calls that already need approval, including bare `Bash`/`command`, `Bash(*)`, `Bash(python*)`, `Bash(python *)`, `:*` equivalents, bare `mcp_call` and whole-server MCP rules. Existing AI review for commands, MCP calls and typed mutations remains mandatory. With settings present, Arany also reviews typed Git processes and MCP discovery; the existing Auto mode without settings keeps its previous scope. Explicit ask rules still select a human and deny rules still block.

**Typed Git prefix rules.** A matching typed `allow` rule skips the approval prompt in Request approvals and Auto edits, as Claude Code allow rules do; the verdict records `typed_prefix_rule`. Settings `default` and `dontAsk` honor it; `acceptEdits` and `auto` ignore local-write allows and ask, live Auto approval keeps its AI review, and `plan` denies writes. Deny and ask rules, in either list, always win over any allow, and a typed rule never overrides an ordinary Read, Edit, path or tool-name restriction. Rules are user-owned configuration: repository content never adds or widens one. See [Typed prefix rules](#typed-prefix-rules).

### Permission rules

The envelope copies [Claude Code settings](https://code.claude.com/docs/en/settings) and [rule syntax](https://code.claude.com/docs/en/permissions#permission-rule-syntax):

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": ["Bash(git diff *)", "Read(./crates/arany/src/**)"],
    "deny": ["Read(./private/**)"],
    "ask": ["Edit(./crates/arany/src/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{"type": "command", "command": "/reviewed/check", "timeout": 30}]
      }
    ]
  }
}
```

All fields shown at the envelope and permissions levels are optional with empty lists/maps as defaults. Unknown or duplicate fields, wrong types, unsupported names and malformed rules reject the entire document; no invalid rule is silently skipped. A rule is a bare Tool or `Tool(specifier)`; inner parentheses are literal. Lists are evaluated in deny, ask, allow order, regardless of specificity or input ordering. Within each list there are no exceptions that undo a match.

| Peer Tool | Typed Arany operations |
|---|---|
| `Bash` | `command`; the subject uses its admitted logical program identifier and argv, not an inferred executable basename. |
| `Read` | `list`, `read`, `search`, `glob`; deny and ask also cover `git_status`, `git_diff` and `git_log` paths, Skill files inside the Workspace, and [Git writes](#typed-git-writes): commit paths and potentially covered descendants, and every staged or whole-repository commit and every switch, whose paths are unknown before dispatch. A deny also covers typed mutations and changeset paths to prevent writing through a read denial. |
| `Edit` | `mkdir`, `write`, `edit`, `multiedit`, `apply_changeset`; deny and ask also cover the same [Git writes](#typed-git-writes) as `Read`. |
| `MultiEdit` | `multiedit`; the same Edit-family path rules and read-denial protection apply. |
| `Write`, `Glob` | Bare `write`, and bare `list` and `glob`, respectively; path specifiers reject in favor of `Edit` and `Read`. |
| `Grep`, `Skill` | `search` path and admitted `skill` name respectively. Skill wildcards match names, not authority or resource discovery. |
| `mcp__<server>__<tool>` | `mcp_call` matched against separate server and tool fields; the Tool segment supports `*`. `mcp__<server>` also covers that server's catalog listing and all calls; `mcp__*` covers all servers for deny/ask. |
| Exact Arany catalog name | That operation only, including `git_status`, `git_diff`, `git_log`, `mcp_list` and `mcp_call`. Native MCP operation names accept bare rules only. |

Bare Tool-name `*` globs are supported for deny and ask against peer and native operation names. A non-MCP glob that matches no known operation rejects, preventing silent no-op restrictions. MCP allow rules require a literal server; generic allow name-globs reject. Server patterns are at most 64 bytes and use lowercase ASCII letters, digits, `_`, `-` and `*`; Tool patterns are at most 128 bytes within the complete-rule ceiling. MCP allows compare the parsed server and Tool fields separately. Deny/ask also test the complete peer-name glob against the call or catalog subject, including `__` descendants so the rule can restrict a whole server. This conservatively covers ambiguous server names containing `__` or ending in `_`; an ambiguous spelling may restrict more calls, but never pre-approve them. Tool names supply no authority and matching discovers no servers. A changeset allow requires every path to match the same rule; deny/ask requires any path. Separate allows cannot assemble authority for an otherwise unmatched batch.

Bash patterns follow the peer's [wildcard examples](https://code.claude.com/docs/en/permissions#wildcard-patterns): `*` spans spaces; exact patterns stay exact. A sole trailing ` *` also matches the bare command but keeps its word boundary; trailing `:*` is equivalent. `Bash(*)` equals bare `Bash`. Other characters are literal.

Arany-specific command narrowing: only unambiguous argv words composed of ASCII letters/digits and `_./:@+=,%~-` are joined with spaces for specifier matching. Empty, quoted, whitespace-bearing or shell/control-bearing arguments are opaque. An opaque command cannot match a specifier allow and conservatively matches every applicable specifier deny/ask. A bare Tool rule still covers it. For deny/ask only, the pattern also checks every word-boundary suffix of the joined argv, so `timeout 30 rm x`, `nice rm x`, `xargs rm x` and `env FOO=1 rm x` cannot hide an `rm *` restriction. This is a conservative narrowing: even a word used as ordinary data may trigger a restriction. Allows match only the complete argv projection. Arany does not split shell strings, expand variables or infer commands from scripts as the peer does. This avoids shell parsing becoming an authority boundary; all execution remains under the pinned command grant and Guard. Text matching does not prove an executable's effects, filesystem disclosure or read-only behavior.

File patterns use the peer's [Read/Edit matching depths](https://code.claude.com/docs/en/permissions#read-and-edit) and [gitignore wildcards](https://git-scm.com/docs/gitignore#_pattern_format): `*` and `?` stay within a segment; whole-segment `**` crosses zero or more directories; alphanumeric classes/ranges, class negation and backslash-escaped literals are supported. Bare filenames match at any depth. `/path` and `./path` anchor at the admitted Workspace; multi-segment relative patterns anchor there too. This is an explicit peer divergence for `/path`: Claude Code anchors it at the settings source, while Arany uses its admitted directory capability to prevent settings placement from changing path authority. Unanchored `crates/arany/src/**` matches only root `src` for allow, and a `src` directory at any depth for deny/ask. An explicit `**/src/**` matches at any depth for every list. Deny/ask path patterns compile case-insensitively on Linux and macOS; allow patterns remain case-sensitive. Deny/ask reject non-ASCII pattern literals. Any non-ASCII subject path conservatively matches an applicable restrictive path rule, including changeset and Git paths, closing NFC/NFD and Unicode case aliases without normalization dependencies. This deliberately over-restricts unrelated Unicode paths. Allow literals retain exact Unicode spelling and cannot normalize into a wider match. There is no filesystem access or symlink following; actual filesystem aliases remain outside this matcher, under the separate no-follow grant and Guard, and [result filtering](#permission-rules) applies the same matcher to each result path.

The admitted path vocabulary is Workspace-relative. This slice rejects `//` absolute and `~/` home anchors, traversal, empty components, trailing directory-only slashes, non-segment `**`, unsupported classes and dangling escapes rather than guessing filesystem identities or settings-source roots. Leading comments and gitignore `!` exceptions also reject: restrict-only sources cannot remove prior restrictions. The existing no-follow admission and exclusions still apply. Rules match proposed typed paths, and they also filter results.

A commit path can publish its entire subtree. Read/Edit deny and ask rules therefore also apply when a commit path overlaps the rule's literal directory prefix in either direction. The prefix ends before the first segment containing a wildcard, class or escape; patterns that can start at any depth have an empty prefix and restrict every commit path. This deliberately over-restricts uncertain wildcard suffixes without filesystem access or expanding an allow rule. Staged and whole-repository commits conservatively match every applicable restrictive path rule.

Result filtering follows the peer's [best-effort application of `Read` rules to Grep and Glob](https://code.claude.com/docs/en/permissions#read-and-edit) and its directory listings that leave out the names a rule matches. `list`, `search` and `glob` results, `git_status` and `git_diff` rows and patch sections, and `git_log` commits omit every path for which the same operation on that path would match a deny or ask rule that the call itself did not match. A rule that matched the call either denied it or was approved for it, so an approved `search` of an asked directory shows its rows while a broader call hides them: an approver never saw paths the call did not name. The matcher is unchanged, including case folding and the conservative non-ASCII match, so while any restrictive path rule applies, a broader call's results drop every non-ASCII path. A covered directory covers its whole subtree, so Workspace walks prune it before opening it and Search never opens a covered file; a private worker filters its in-memory image the same way. Filtering precedes ordering, row and byte fitting, `limit`, `offset`, `next_offset` and `truncated`, so pages and truncation count only visible rows. The Engine sends the restrictive patterns to the Guard in its task, where Git output is filtered before fitting. Every patch section starts hidden and only a `diff --git a/P b/P` or combined `diff --cc P` header, or a staged `* Unmerged path P` line, naming a visible unquoted path reveals it, so conflict sections, unrecognized or quoted headers and a line cut by the capture limit fail closed. A collapsed untracked directory row such as `dir/` names only that directory and is hidden when a rule covers it. The view config sets `core.quotePath=false`, so Git quotes only names with control characters, `"` or `\`, and those stay hidden. A filtered `git_log` reads changed paths (`--name-only` without rename detection, so a move reports both sides, and merges against their first parent) for at most 1,000 commits, keeps only commits that change a visible path, then applies `max_count`; a commit with no path evidence is dropped, and an exhausted scan sets `truncated`. Subjects of kept commits are shown even when they also change covered paths. A filtered Git failure drops its `stderr` detail. Git's own [capture bound](#limits-and-failure-behavior) still counts covered output, so a capture overflow keeps `truncated` true. A Skill file inside the Workspace is also a file read: a `skill` call takes the stricter of its own decision and a `read` of that file's Workspace path, and a Skill whose `SKILL.md` a restriction covers is omitted from the catalog, so its description is never previewed. The verdict is journaled before dispatch, so a denied Skill file never becomes a Guard task; the Guard checks the pinned grant and file digests, not permission settings. Rules do not filter explicit includes, interpreter I/O or subprocess filesystem access; that disclosure remains bounded by the independent grant and Guard, and this config API is not an OS path filter.

### Hook execution

The envelope and nested groups copy the [Claude Code hooks reference](https://code.claude.com/docs/en/hooks#configuration) and [command fields](https://code.claude.com/docs/en/hooks#command-hook-fields). Accepted events are exactly `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop` and `PreCompact`. Groups contain a `hooks` array of command handlers, an optional matcher, and no other fields. Handlers accept `type: "command"`, a nonempty `command`, optional `args` and an optional integer `timeout` in seconds. Omitted `args` retains shell-form text; a present array, including `[]`, retains exec form. Nothing is interpolated or resolved; all five events execute at the Engine sites below.

Matchers absent, empty or `*` select every occurrence. The peer's exact-name/`|`/`,` alternatives are copied; other patterns use an unanchored regex. Arany narrows regexes to the bounded finite-automaton syntax: JavaScript lookaround/backreferences and oversized compiled patterns reject. Tool events must use `matches_tool` so invalid or ambiguous calls cannot evade a hook; other events use `matches` on their event-specific subject. Tool matching uses canonical peer names above, including actual `mcp__<server>__<tool>` call subjects and `mcp__<server>` catalog subjects; `SubagentStop` matches agent type and `PreCompact` matches the trigger (`manual`/`auto`). `Stop` accepts only match-all: a filtering matcher rejects instead of the peer's silent ignore. An MCP server name containing `__` produces a blocking Tool-subject error rather than an ambiguous canonical name; native MCP rules still compare typed fields. A present `null` is invalid, not an omitted field. Empty handler groups, other events/types, async handlers and extra execution options reject.

**Recorded owner decision — 2026-10-17:** hook commands run inside the Guard like every process, under pinned interpreter/executable identities, an explicit environment and typed grants. Arany copies Claude Code's hook protocol: events, matchers, JSON on stdin, event-specific exit-2 blocking, `permissionDecision` `allow|deny|ask` and timeouts. The peer divergence is execution authority: [Claude Code command hooks run with full user permissions](https://code.claude.com/docs/en/hooks#security-considerations); Arany requires Guard isolation because of its [Per-effect isolation security guarantee](../../AGENTS.md#non-negotiable-guarantees). Descendants cannot gain authority, and repository or hook output cannot select trust.

An enforcement-caused hook failure (`enforcement_cause` or typed Guard bootstrap failure on the hook intent) stays `Ignored`. The [unguarded execution contract](#unguarded-re-run-after-a-guard-failure) admits only a fresh, human-approved intent for that exact command. Hook output, an allow rule, a remembered exact-command rule and AI review never authorize this re-run. The original hook result is immutable; the separate Tool observation records the approved host run as unguarded, without interpreting its output as a new hook verdict. There is no automatic host retry.

**Delegated Tools and worker integration.** Like Claude Code, researcher and editor Tool calls trigger the same configured `PreToolUse` and `PostToolUse` hooks as primary Tools. Hook intents and Events carry the child's `agent_run_id`; admission adds hook Events and observations to the child's `Action::Child` tail (and worker chunk headroom), and execution stays inside the original delegation deadline and active reservation. Denial and feedback apply to that child's Tool; an unknown hook outcome stops the Run without retry. Delegated calls are never rewritten. The Engine's handover `ApplyChangeset` runs both Tool hook sets around its ordinary path rules and approval. Its `tool_input` adds `files`, the sorted sealed file paths, subject to the same stdin and Guard task ceilings; overflow denies before any hook starts. Integration is never narrowable: hooks may deny it, never rewrite it. Its post-hook feedback reaches primary synthesis, and completed publication is retained even when a post hook stops the Run.

**`PreToolUse` command hooks.** After the permission decision and the live terminal restriction, and only while the decision is not `Deny`, a Tool step runs its matched handlers one at a time in configuration order. Each handler is a journaled `Command` effect with the Guard's offline, private-Workspace-view, explicit-environment grant of any model command: `HookStarted` commits the immutable hook intent, the exact-stdin digest and the pending Tool's digest; the Guard runs it; `HookFinished` commits the Guard observation (receipt included) and the parsed result; then the verdict follows. Shell form runs the pinned `sh` as `sh -c <command>`; exec form runs `command` as a pinned program name with `args`. A program that is not pinned, a matcher error or more matched handlers than the limit below denies the pending Tool before any hook starts, with reason `hook program is not pinned`, `hook configuration blocks this Tool` or `hook limit`. Handlers after a denial do not run. Internal Engine preparation calls over snapshot-pinned input (agent definition parsing) are never model Tools: no hook sees or narrows them, and they widen nothing.

The hook receives one JSON object on stdin (closed field set): `session_id`, `cwd` (always `/workspace`, the Guard view, never a host path), `permission_mode`, `hook_event_name`, `tool_name` (the peer name), `tool_input` (the typed call) and `tool_use_id`. Exit codes and output follow the peer: exit 0 with empty or non-JSON stdout adds nothing; exit 0 with a JSON object may carry `hookSpecificOutput` (`hookEventName` must be `PreToolUse`) with `permissionDecision` and `permissionDecisionReason`, the legacy top-level `decision: "block"` with `reason`, or `continue: false` with `stopReason` (stops the Run before dispatch, taking precedence over `decision: "block"`); exit 2 denies and its stderr is the reason; any other exit is a non-blocking failure. Unknown fields are ignored, and stdout is never interpreted as instructions. Hook output is evidence and a reason string only: reasons are control-stripped and truncated to the reason limit below, and the model sees only `Hook denied this Tool` with that reason.

A Guarded Command that is not a hook reads an empty stdin (immediate EOF), like the unguarded executor.

The verdict records `hook_restriction` (`null`, `ask` or `deny`) and `hooks` (handlers that ran). The reducer requires every started hook to be finished before the verdict, `hooks` to equal the journaled count, `null` only when no hook restricted or stopped, `ask` only when the fold is `Ask`, and `deny` only for a `Deny` fold, a stopped hook or a denial before any hook ran. A `Deny` hook verdict has basis and source `hook`; a hook `Ask` over an `Allow` has basis `hook` and is resolved by the human, never by AI review. Unknown outcomes stop continuation: a hook whose observation is `Uncertain`, cancelled or unattested is recorded and blocks resume like an uncertain Tool.

Hooks have at most 64 groups and 128 handlers across all events. Matchers and match subjects are at most 1024 bytes and control-free. Subject overflow, controls or an invalid Tool call return an error, not a non-match; callers must block the pending action on this error and cannot skip the hook. Commands are at most 4096 bytes; tab/newline are permitted as inert command text, other controls reject. Exec form has at most 64 arguments of 4096 bytes each, without NUL, within the aggregate document limit. Hook timeout is 1–600 seconds, default 600; the finite maximum is an Arany narrowing. Each regex has a 128 KiB compiled-size ceiling, a 32 KiB DFA cache and 32 nesting levels. All overflow rejects, with no truncation, partial config, retry or fallback. Errors identify the list/index or hook constraint without echoing command/rule text.

Hook limits: at most 8 matched handlers per occurrence; stdin at most 32 KiB, including the complete `tool_input`: a matched `PreToolUse` or `PostToolUse` set that cannot receive the whole call, such as a valid Write, Edit or MultiEdit carrying more than about 32 KiB of content, denies the Tool before any handler or effect (`hook input exceeds its limit`, zero handlers), never truncating or hashing `tool_input`, bypassing the hook or retrying unhooked; the complete Guard task of every matched handler must encode within the Guard task ceiling before any hook starts, else the Tool is denied (`hook input exceeds the Guard task limit`) with no `HookStarted`; a 32 KiB result with each stdout/stderr capture capped at 16 KiB minus 128 bytes (overflow fails closed); runtime at most the handler `timeout` and the remaining Goal active time, never less than 1 s (the Goal ledger refuses a start that does not fit); reasons control-stripped and truncated at a UTF-8 boundary to at most 1 KiB; admission of a Tool step reserves two Events and one observation per matched handler, and the Tool's authorization lifetime and active-time ceiling grow by the handlers' worst case, clamped to the remaining Goal active time (unbounded Goals keep the full worst case). Hook time is Goal active time. Descendants are reaped by the Guard on timeout.

**`PostToolUse` command hooks.** After a primary or delegated Tool completes with a `Succeeded` observation, its matched `PostToolUse` handlers run one at a time with the same Guard grant, bounds and `HookStarted`/`HookFinished` pair as `PreToolUse` (`HookStarted` requires that committed observation, the Tool's digest and directly follows the Tool's latest journaled step: a Command's hooks run after its changeset integration commits, so the hook sees the published tree (a worker command's hook instead runs after its private seal and sees the host Workspace, never the private view), and no Provider call, compaction or other Tool may sit between the Tool and its hooks). The hook cannot undo the effect, and its Workspace changes are discarded like any hook's. Failed, denied, uncertain and internal Engine calls run no `PostToolUse` hook. Stdin adds `tool_response` to the `PreToolUse` field set: the observation's model-facing projection, replaced by `{"truncated": true, "text": <prefix>}` when the input would exceed the stdin limit, with the prefix halved (down to empty) until every matched handler's Guard task fits, so on macOS a hook can receive less than 32 KiB. Exit 2 (stderr) and `decision: "block"` with `reason` become feedback; `hookSpecificOutput` (`hookEventName` must be `PostToolUse`) with `additionalContext` becomes feedback too; any other exit is a non-blocking failure, and a timeout or output overflow becomes the feedback `hook limit reached`. Feedback strings use the reason bound below. On exit 0, `continue: false` takes precedence over feedback and records `stopped` with optional `stopReason`; remaining handlers do not run. Its terminal behavior belongs to [Run outcomes](./execution.md#accepted-outcomes). `updatedToolOutput` and other fields are ignored: hook output never replaces an attested observation. An `Uncertain`, cancelled or unattributed unattested hook stops the Run after the Tool effect without retry; the typed pre-dispatch bootstrap exception above stays `Ignored`, the observation stays committed and the next Provider call does not start.

PostToolUse feedback is stored only in the journaled `HookFinished` result (a `feedback` result with a `lines` list); the reducer requires the recorded result to equal the deterministic parse of the hook's observation for its event. The model-facing Tool result gains a `hook_feedback` list of lines `hook feedback: <text>` (at most 4 KiB in total, later lines dropped), derived from the live results and, after resume or in history, from the journaled ones, so the same prompt bytes result. A step that matches either Tool hook set reserves twice that room (JSON escaping) in the context budget, including room for the separately derived unguarded proposals, and `PostToolUse` handler time extends the active-time ceiling but not the Tool's authorization lifetime. Because a `PostToolUse` handler cannot be refused after the effect, a Tool whose `PostToolUse` handlers are unpinned, over the matched-handler limit, unable to encode their Guard task or stdin even with an empty truncated response is denied before dispatch with the `PreToolUse` reasons.

**`updatedInput` narrowing.** `updatedInput` must be a complete, valid Tool call (the shape of `tool_input`); anything else denies. A replacement narrows only when it is: a `read` of the same path whose offset and end lie inside the original window; a `glob` with the same normalized pattern, an equal or lower limit and an equal or subtree path; a `list`, `git_status`, `git_diff` or `git_log` whose path equals the original or lies beneath it by whole path segments (a root original admits any path), with the Git reads keeping every other field; or a `search` keeping its query, `regex`, `include` and `case_sensitive` after default normalization, whose page lies inside the original row window (`offset` through `offset + limit`) for the same path, or whose path lies beneath the original's with no include, both offsets zero and a limit no larger (a subtree renumbers its rows, and an include would match relative to the new path). Parent paths, `..`, case or symlink variants, a larger window or glob limit, a changed query, glob pattern, matching mode, include or case and every `command`, MCP, Skill, `write`, `edit`, `multiedit`, `mkdir`, `apply_changeset` or internal call never narrow (a changed argv or content has no provable order; the model must propose it as a new call). The replacement must also be at least as restrictive as the original under the pinned rules and be within the pinned grant. `HookFinished` journals every valid-shaped update outside an `ask` decision (which keeps the original input) as a `narrowed` result carrying the call, but only the verdict's `narrowed` flag records that the Engine accepted it. An update identical to the current call is a no-op (the call proceeds as is and the hook restricts nothing, so idempotent clamping hooks work). An update refused by `narrows`, the pinned rules or grant, or the per-step limit denies with the matching reason and a false flag. `ask` together with `updatedInput` keeps the ask on the original input (the update is dropped, the human decides). On an accepted narrowing the original Tool is `Denied` with basis `hook`, the verdict flag set and the model-facing line `Hook narrowed this Tool to: <tool_name>`; it does not answer the request, and the next Tool of that step must be exactly the replacement (a new `ToolStarted` intent), so a later step requesting the same call is an ordinary request. `PreToolUse` hooks run again for the replacement; at most one narrowing per step, so a second one denies (`hook narrowing limit`). The model receives one Tool result for the request, built from the replacement's observation; the original's denial line arrives as a separate `hook_narrowing` data block. Internal Engine calls and delegated research are never narrowed. Step admission reserves the replacement's Events and observations.

**`Stop` and `SubagentStop`.** A primary answer runs `Stop` before `AgentFinished`. A researcher or editor answer runs `SubagentStop`, matched against its definition name (or the explicit role fallback `researcher` / `editor` if no definition is loaded), before the child's `AgentFinished`. Both receive `stop_hook_active` and `last_assistant_message`, truncated at a UTF-8 boundary to fit the stdin and Guard task ceilings of the Hook limits. Exit 2 or `decision: "block"` records `blocked` with a bounded reason. On exit 0, `continue: false` takes precedence over `decision: "block"`, journals `stopped` with optional `stopReason` and skips remaining handlers; [Run outcomes](./execution.md#accepted-outcomes) owns terminal settlement. On a block, the accepted assistant turn and a user-data block labelled `stop_hook_feedback` are appended to the next request; the next primary call uses ordinary Goal Provider-call admission; exhaustion ends the turn with the existing budget outcome. A child re-prompt stays inside its original delegation deadline and turn ceiling; a stopped editor is cleaned up and its private handover is never integrated. **Continuation cap:** at most eight blocked continuations are admitted per actor in a Run, counting every blocked Stop whatever Tool calls sit between them (they never reset the cap or `stop_hook_active`), so their feedback stays within 8 KiB (eight reasons at the Hook limits' reason bound); after the cap a valid answer completes without another Stop invocation. An enforcement-caused primary Stop counts toward the cap even when no re-run proposal is offered: counting only offered proposals would let a later unguarded attempt lower the count and unbound the cap. Internal Tool calls never trigger hooks.

**`PreCompact`.** Before an active-Run compaction reservation or an idle Session compaction, matching handlers receive `trigger` (`manual` or `auto`) and empty `custom_instructions`. A block skips the compaction and makes no compaction Provider reservation; `continue: false` stops an active Run before the compaction reservation, or stops only the compaction when idle. A manual `/compact` that a hook blocked fails with `CompactionBlockedByHook`, distinct from an empty input. If retained context still exceeds its limit, the existing context failure applies. Each trigger/call-index occurrence runs once; a retry at the same call count reuses the recorded outcome (a recorded block still blocks, a recorded pass proceeds) and never reruns the hook. Idle compaction re-admits the current private configured or remembered folder grant only if its digest and the permissions digest match the Run's pins; changed or unavailable admission fails closed. Between Runs of an open Goal, hook start reserves a durable active-time ceiling and completion settles elapsed time; outside an open Goal the handler keeps its finite timeout and Guard limits.

Lifecycle hooks use the same pinned programs, Guard, sequential execution, Hook limits, fail-closed Limit and uncertainty handling as Tool hooks. An invalid program records the offending handler's own call as a denied intent that was never dispatched; matched-handler overflow uses the first handler configured for the event and stdin that cannot fit the Guard task uses the first matched handler. Each selected call carries the reason as output and the result is `Blocked` with that reason, before any process runs. A SubagentStop shares its delegation, so admission reserves the actor's researcher or editor settlement tail rather than the primary's; a cut-off or cancelled SubagentStop ends that child (cancelled when the user cancelled, otherwise failed under that child's C1-fatal or C2-local failure policy) without declaring the Goal budget exhausted; the editor's closed failure cause follows the [worker outcome contract](./execution.md#worker-journal-protocol). An unknown outcome stops the Run as `Uncertain`. Replay binds Stop subjects to `(agent_run_id, provider call index)` and PreCompact subjects to `(trigger, provider call count)`. A Stop occurrence immediately follows its accepted Finished call; a blocked Stop forbids successful Agent completion until a new primary/child call is recorded. Each continuation re-renders the answer turn, which counts toward the Tool context and its compaction trigger, and a context without room for it refuses with `ContextTooLarge` before any hook journals. Open or Uncertain hooks block continuation and resume; strict replay consumes recorded facts without executing hooks.

### Supervisor adapter

The Engine coordinator calls one pure, deterministic evaluator over committed reducer facts. Tool-enabled Runs pin `config.supervisor = {evaluator: 1, window: 32, floors, candidates, digest}` in `RunStarted`; Runs without Tools pin null. The field is required. The SHA-256 digest binds the domain `arany.supervisor.policy.v1`, evaluator, window and both closed threshold structs. There is no configuration file, model call, clock, I/O, network, Guard task or journal subscriber. Repository text, model output and hooks cannot select thresholds. Shadow mode is always on in production and never changes permissions, catalogs, approvals, continuation, integration, Run outcomes or model input.

A boundary follows every model `ToolFinished`, including Denied, Failed, Conflict, Limit, Uncertain and Cancelled; a primary command carrying a nonempty validated changeset uses `command_capture` for that same boundary. `worker_capture` follows a mutation seal, `handover` follows `WorkerHandoverRecorded`, and `stall` follows an invalid/deferred Provider result or a blocked Stop/SubagentStop. Deferred worker-team outcomes are already recorded as invalid Provider outcomes. Internal definition parsing, worker preparation and changeset integration are excluded. C3 command seals and in-view gate rejections are not available until the C3 slices implement them. Capture-only boundaries do not duplicate a Tool call in call patterns.

Each actor has an independent last-32-boundary window in its Run (at most nine actors). The oldest step is evicted whole on the 33rd boundary; a new Run starts empty. All feature counts saturate at 65,535; ratios use saturating integer arithmetic, floor division and a denominator of at least one. Keys are SHA-256 over domain `arany.supervisor.call.v1` and canonical typed calls; Write/Edit content fields are replaced by SHA-256. Intent, actor and Run IDs, expiry and target revision are excluded. Outcome equality binds disposition, closed enforcement cause, exit class (zero/nonzero/unknown) and SHA-256 of the model-facing result without its call or target. No prose is parsed to invent denial classes. Policy/plan/grant/lease/permission/hook denials count as refusals; closed `filesystem_denied` enforcement counts as a path-admission rejection. Ordinary nonzero exits do not count as probing.

| Loop | Identical `(call, outcome)` suffix; same-call non-success suffix; greatest whole suffix cycle repetitions for lengths 2, 3 and 4 (shortest length wins ties); maximum per-path returns to a prior after-digest following a different digest; stall boundaries since the last succeeded observation | identical 3; failing 2; cycle 3; oscillation 1; stalled 2 | identical 4; failing 3; length-2 cycle 3, other cycles 5; oscillation 2; stalled 3 |
| Probing | Refusal suffix; refusals in window; distinct refused call keys; closed path-admission rejections | streak 2 or alias 1 | streak 3, or distinct 3 with window 4, or alias 2 |
| Disproportion | Files, deleted files, ceil(decoded before+after bytes / 1024), declared roots (minimum 1), worker base KiB (primary null), files/root, deleted/files permille, changed/base permille (primary null) | files 16, or deletion 250 permille with files/root 4 | files/root 8 with files 32; deletion 500 permille with deleted 8; growth 4000 permille with changed 64 KiB |

Loop and probing signals are evaluated at `tool_outcome`, `command_capture` and `stall` boundaries only, and are journaled only when the subject is itself in the signal's evidence, so one crossing yields one verdict rather than a notice at each later boundary; disproportion is evaluated at every capture. A candidate hit has level `would_narrow`, otherwise a floor hit has level `notice`; both meet the minimum journaled notice level. Candidate responses are loop `pause`, probing `revoke`, disproportion `require_approval`; notices have null response. These are calibration candidates only. Disproportion uses sealed capture/handover facts, the worker's leased base and roots or the primary's Goal plan paths. Each signal retains at most eight increasing subject sequences as evidence. Edit equality retains only hashed path/after-digest pairs, at most the existing 2,048-file capture bound per step and 589,824 pairs per Run (36 MiB of pair data), never contents. Eviction removes the oldest step and its pairs together. Per-boundary work is bounded by the 32-step window and those existing finite capture bounds; no work or allocation grows with Session history. The evaluator has no fallible external operation; an implementation panic fails the coordinator through its existing failure boundary.

The coordinator commits a nonempty `SupervisorVerdictRecorded` immediately after its subject, before hooks, integration or stop facts. Its closed payload carries `subject_sequence`, `site`, `evaluator: 1`, `mode: shadow`, one to three signal entries (`signal`, `level`, nullable `would_response`, fixed feature struct and evidence) and `capped`. It contains only integers, booleans, enums and sequences. The [execution contract](./execution.md#persistence-bounds) owns the 2 KiB payload and 256-verdict Run cap. Evaluation continues after the cap without journaling. No verdict enters compiled context, compaction input, Provider input or diagnostics. [Serve](./serve.md#notifications-and-items) forwards this canonical, privacy-reduced verdict, including features and evidence that contain counts, sequences and closed enums, never paths or content. [Terminal](./terminal.md#conversation-progress-and-history) and [telemetry](./telemetry.md#spans) own their further-reduced fixed-vocabulary projections; the calibration corpus below owns its separate privacy contract.

Replay recomputes the same evaluator from pinned data without executing any historical Provider, Tool, hook or Guard action or reading configuration. A missing, forged, changed, duplicate or misplaced verdict is an invalid transition. An interrupted prefix ending immediately after a subject remains valid; later recovery starts fresh windows in a new Run. A different feature definition requires a new evaluator version and rejects old history under the current-format rule. Threshold changes are pinned data and do not alter replay of an existing Run.

`arany show --output supervisor-corpus SESSION_ID` exports a local calibration corpus after strict read-only replay. It takes the existing Session lock nonblockingly for the entire read, refuses an active operation or an absent/unsafe lock, and neither creates lock files nor changes journal bytes. It opens no Workspace, reads no credentials or runtime configuration, and performs no Provider, Tool, hook or Guard call. Fork references and inherited history undergo the same strict validation as ordinary replay; records describe the selected Session's direct evaluation boundaries. Interrupted closed prefixes are valid. Invalid history emits no corpus.

The stdout format is JSONL, one header followed by one record for every evaluation boundary, including negatives and boundaries after the journal's verdict cap. The header has `format: "arany.supervisor.corpus.v1"`, `evaluator: 1`, `session_ordinal: 1`, `runs` and `goals`. Each Run entry contains its one-based `run_ordinal`, closed `outcome` and nullable `policy` with its pinned evaluator, window, floors and candidates; the policy digest is omitted. Run outcomes are `completed|failed|cancelled|stopped_by_hook|interrupted`; unfinished prefixes use `interrupted`. Goal entries contain a one-based `goal_ordinal`, `run_ordinals` and `outcome: completed|failed|interrupted|budget_exhausted`. A budget-exhausted Goal remains distinguishable from another failure.

Each record contains `run_ordinal`, the journal's zero-based `actor_ordinal`, closed `role`, `site`, nullable catalog `operation`, nullable `disposition_class` and closed enforcement `cause_class`, `features: {loop, probing, disproportion}`, nullable `journaled_level`, `salted_call_key`, `salted_outcome_key`, one-based `relative_step`, and `labels`. The feature structs are exactly those defined above, recomputed over the same actor window; disproportion is null outside capture sites. Operation, disposition and cause describe Tool observations and are null at other sites. `relative_step` counts all boundaries in that Run in journal order. `journaled_level` is the greatest level in the matching committed verdict, or null when no verdict was committed (negative, capped or interrupted prefix); it is not a fabricated verdict. Labels are booleans `pause_or_cancel`, `steering` and `goal_failed`, set when the corresponding committed cancellation, steering note or failed Goal follows within three subsequent evaluation boundaries of the same Run (including immediately after the subject). The journal does not distinguish a user pause from Ctrl+C, so the combined cancellation label makes no such inference; crash interruption is not a cancellation label.

Corpus privacy is an allowlist: only the fields above are serialized, with no objectives, paths, argv, file content, model text, UUIDs, timestamps, account data, raw hashes or policy digests. Call and outcome equality keys are HMAC-SHA-256 of the evaluator's normalized keys, with separate corpus domains and a fresh cryptographically random 32-byte secret salt per export. The salt is never exported or persisted. Equal keys remain equal within one export, but a new export changes every key while keeping other fields stable. Row ordering, ordinals and feature patterns stay observable across exports; only equality keys are unlinkable. Feature patterns and outcomes can still identify similar trajectories; the corpus is privacy-reduced, not an anonymity guarantee. No export is uploaded; owner labels are added offline to a copy, and threshold sweeps use the feature columns without re-execution.

An export holds at most 10,000 records and emits at most 8 MiB, including its header and newlines. The [lineage replay cap](./execution.md#persistence-bounds) also applies before corpus collection. Record or byte overflow refuses the whole export with record and serialized-byte counts, never truncation or partial stdout; replay-limit refusal uses the existing history-limit error. Corpus buffers, ordinal metadata and label tracking are bounded by those Event/record limits, the fixed record schema and a four-boundary label window. Random-source failure fails closed. The corpus grants no enforcement authority; calibrated enforcement and owner overrides remain separate work.

Peer mechanisms: [OpenHands](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/stuck_detector.py) supplies ID-free action/observation equality, four identical steps, failure streaks and alternating cycles; [Gemini CLI](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts) supplies hashed calls and short cycles; [Goose](https://github.com/aaif-goose/goose/blob/main/crates/goose/src/agents/agent.rs) places repetition checks in the pre-dispatch inspector seam; [Claude Code hooks](https://code.claude.com/docs/en/hooks) supply the restrict-only adapter shape. Arany diverges by journaling shadow candidates before enforcement, recomputing them on replay, using bounded per-actor windows and excluding LLM judges. Enforcement, durable pause/revoke and human-only overrides require later calibrated owner approval; this adapter applies none of them.

Evidence owners: [pure signal corpus](../../crates/arany/src/supervisor/tests.rs), [reducer corpus](../../crates/arany/src/session/reducer/tests.rs), [Event corpus](../../crates/arany/src/session/events/tests.rs), [Engine Goal corpus](../../crates/arany/tests/engine_run/goals.rs), [corpus show journey](../../crates/arany-cli/tests/session_run/supervisor.rs), [export-bound corpus](../../crates/arany/src/supervisor/corpus.rs) and shared `assert_action_bounds`. They cover signal thresholds/cycles/oscillation/saturation, required/absent/forged/misplaced/capped/interrupted verdicts, closed decoding and unchanged model observations and accepted output with an all-off test pin. The evaluator is platform-independent; native journeys establish platform support separately.

## Private grants

Put an owner-only `tools.json` beside the admitted Session database, outside the Workspace. Its directory must be private (`0700`) and the file must be regular, single-link, no-follow, current-user-owned and `0600`. `--state-dir` selects this Session and configuration root; it does not move your saved account. Permissions are not encryption or protection from another process running as the same user.

A minimal file-only configuration is:

```json
{
  "version": 1,
  "workspace_paths": ["src", "Cargo.toml", "Cargo.lock"],
  "write": true,
  "commands": [],
  "skills": [],
  "mcp": []
}
```

Use exact, nonoverlapping relative files or directories. The singleton `["."]` selects the whole project under the same exclusions and bounds; mixing `"."` with other roots rejects. List, search and command working directories accept `"."` or an empty path for the project root; mutations still require a named relative path. Absolute paths, traversal, links, mount crossings and special files are not admitted. StateRoot and the fixed account root must not overlap the Workspace or configured runtime resources. `.git`, `.env`/`.env.*`, `.aws`, `.ssh`, `.gnupg`, `.npmrc` and `.pypirc` path components are excluded. Repository history is reachable only through [typed Git reads](#typed-git-reads). This is not a universal secret detector: review the files you select. Tool observations can be sent to the selected Provider and persisted in the private, unencrypted journal.

The Linux profile exposes the system `/usr` tree read-only as its runtime. Workspace, StateRoot and account roots must not overlap it, since a private file inside a runtime mount stays visible to a same-user payload. This authorizes no home or unselected cache mount.

The offline profiles deny network, named Unix socket creation, connect, bind, listen and destination-bearing sends; a network namespace alone would leave pathname sockets in visible runtime trees reachable. Anonymous pipes and anonymous socket pairs stay usable: Linux pairs cannot rebind or send to named destinations, and macOS denies pair writes, so payloads cannot depend on socket wakeups. `sendmsg`/`sendmmsg` descriptor passing is unsupported. This is not a network-capable test profile.

JSON has a closed versioned schema: all six listed top-level fields are required, the optional `git` field pins [typed Git reads](#typed-git-reads), the optional `git_identity` `{name, email}` is the [commit identity](#typed-git-writes), and optional `child_unguarded` selects the explicit [child escape-hatch restriction](#unguarded-re-run-after-a-guard-failure); unknown and duplicate fields reject. Private configuration has no interpolation, automatic installation or hidden executable lookup. Project Skill discovery stays within its selected Workspace roots. Where commands are supported, folder trust pins the resolved system shell rather than looking up arbitrary commands on PATH. Configuration is pinned for a Run; editing it does not cancel an admitted Run. Changed pinned executable or resource contents reject dispatch rather than being silently trusted.

## Enforcement failure causes

`ToolFinished` and `HookFinished` record an optional closed `enforcement_cause` separately from the disposition and untrusted output. `filesystem_denied` means command snapshot capture explicitly rejected a protected path component or set-ID entry metadata. These checks enforce the command output boundary. It requires an execution attestation and a `denied` disposition. `guard_bootstrap` means the trusted controller observed a typed Guard bootstrap error at the RuntimeMounts, Capabilities or Handshake sandbox-setup stage before GO dispatch: it requires `failed`, no execution attestation and a Guard-site intent. This known pre-dispatch failure permits continuation; it never converts an unknown dispatched outcome into a retryable failure. Ordinary errno, diagnostics and program output cannot set either cause. Resource limits, cancellation, uncertainty and successes cannot claim a cause.

A runtime mount-topology refusal reported as a typed bootstrap failure before Ready and GO on Linux or macOS is `guard_bootstrap`: the next model request may receive that failed, unattested observation. This continuation grants no authority and dispatches no retry; an ordinary command's unattested failure still cannot qualify an unguarded re-run. Once GO begins, a missing completion remains uncertain and cannot use this exception.

Shared file readers and resolvers retain their existing errors, so unsupported Git layouts, ordinary path validation, non-regular or multiply linked files, unsupported changeset type conversions and opaque filesystem errors remain unclassified. Classification changes no grant or approval, and never retries anything.
The cause carries no path, filename, contents or native diagnostic text. Its size is fixed by the enum, within the existing observation and context budgets; protected names discovered while scanning a command snapshot never enter the cause or its diagnostic. The model result adds one short diagnostic field only when a cause exists: `Guard enforcement: protected path or set-ID entry refused`. Terminal Tool summaries show the same diagnostic. Bootstrap failures instead show `Guard enforcement: bootstrap failed before dispatch`. Results without a cause retain their model-facing projection. JSONL and strict replay retain the typed field under the [current payload versions](./execution.md#admission-persistence-and-recovery); previous versions reject without rewriting stored data.

| Platform | Reliable attribution in this profile | Reports no cause |
|---|---|---|
| Linux | Protected-path and set-ID entry refusals inside command snapshot capture; typed pre-dispatch controller bootstrap failures | Unclassified Bubblewrap startup failures, namespace-hidden paths, read-only mounts and seccomp-returned errno have no trusted per-operation denial channel. The current seccomp profile returns `EPERM` (and `ENOSYS` for `clone3`), rather than notification records; Arany uses no Landlock/audit attribution channel. A blocked socket/connect, `EACCES`, `EPERM`, `EROFS`, missing file or signal alone cannot establish Guard causation. |
| macOS | Post-run command snapshot refusals in the supervisor; a typed pre-launch controller bootstrap failure reports `guard_bootstrap` | Seatbelt violations are not collected through a trusted, invocation-correlated report channel. Program errno, stderr, exit status and unrelated system sandbox reports cannot establish attribution. |

`null` means no attributable cause, not permission or proof that enforcement was uninvolved. No network or process cause is claimed without a trusted evidence source. This applies equally to commands and local MCP servers; `isError`, server-provided cause fields and text remain ordinary program data. Skill loading is data-only; Skill scripts use ordinary guarded commands and the same classification.

This mirrors the separate sandbox diagnostic attached to results by Claude Code's [sandbox runtime `annotateStderrWithSandboxFailures`](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/sandbox-manager.ts), which uses invocation-correlated violations, and Codex CLI's [distinct `SandboxErr::Denied` result](https://github.com/openai/codex/blob/main/codex-rs/core/src/exec.rs). Arany does not copy Codex's `is_likely_sandbox_denied` output heuristic: hostile program output must never attest enforcement. The peers' escalation flows are the [unguarded re-run](#unguarded-re-run-after-a-guard-failure) below; a cause never decides whether it is offered, only the journal evidence does.

## Unguarded re-run after a Guard failure

This is the only exception to per-effect isolation that [AGENTS.md](../../AGENTS.md) permits: a per-command run outside the Guard that the user approves after a sandbox-caused failure, never automatic, journaled and marked unguarded. It copies [Claude Code's unsandboxed retry](https://code.claude.com/docs/en/sandboxing) (the model re-proposes the same call, a prompt titled for the lack of sandbox, an allow-rule remembered per project) and Codex CLI's `require_escalated` (a model-authored `justification` becomes the user-facing question; three choices: once, remember, deny). It diverges where a guarantee requires: the model cannot pre-empt or remember, and the user-owned [typed prefix rules](#typed-prefix-rules) cover only closed Git and `gh` verbs, never this operation or an arbitrary command; a wildcard allow rule, a mode or AI review never approves it (Claude Code's allow-rule and auto-mode classifier paths are rejected), there is no bypass mode, and the process keeps a cleared allowlisted environment, a pinned executable, explicit argv, a pinned cwd, output caps, a timeout and a process-group kill.

**Operation.** `command_unguarded` takes the `command` fields plus `justification` (1–512 UTF-8 bytes, control-free apart from tab, shown as untrusted text). Its peer name is `Bash`, so deny and ask rules match like `command`; `"deny": ["command_unguarded"]` is the Arany spelling of Claude Code's `allowUnsandboxedCommands: false`. It is offered beside `command` when `commands` is non-empty, never added to researcher or editor catalogs by an escape-hatch restriction alone, and may satisfy `tool_call_succeeded` because an unguarded success is an attested, human-approved receipt that the report marks unguarded.

**Evidence gate.** Shared predicates `qualifying_guard_failure` and `qualifying_hook_failure` serve the Engine and reducer through the pinned Run view. The latest observation in the same Run of a primary `command` with byte-identical program, args and cwd must be Guard-attested `failed`. A `denied` observation (including `filesystem_denied`), `limit`, `uncertain`, `cancelled`, an unattested failure, a child's observation and any later success of that command never qualify. For ordinary commands, because no trusted per-operation cause exists beyond `filesystem_denied`, a failure without a cause qualifies and the prompt says Arany could not verify that the Guard caused it. Argv containing a Guard path alias (`/workspace`, `/scratch`, `/cache`, `/seed`, `/programs`, `/inputs`, `/skills`, `/arany` as a root path) never qualifies: the same bytes name other paths on the host. So does argv naming a Guard-only variable (`ARANY_TOOL_INPUTS`, `ARANY_TOOL_SKILLS`, any `ARANY_TOOL_*` but `ARANY_TOOL_WORKSPACE`): the host environment does not set it. The check is lexical; shell-built paths and `..` relative to the directory are not caught. The Engine reads the live Tool context, so a failure that was compacted away, or was observed in the same model turn, does not yet qualify (the stricter side of the reducer's view). The gate runs before the approval and a refusal is journaled as a `denied` observation with an unapproved verdict.

**Hook-origin interlock.** The latest matching hook observation in journal order can qualify instead: the exact byte-identical program, argv and cwd must have `filesystem_denied` with a valid Guard receipt, or typed `guard_bootstrap` on the hook intent. A later matching hook success or unclassified failure invalidates that evidence. Only completed Tool steps and recorded lifecycle outcomes qualify; hooks of the pending unguarded request cannot qualify that request. The Engine offers a complete exact-command proposal in existing feedback, bounded to 4 KiB per step; it omits proposals that cannot fit, never truncates or changes the command. A primary Stop failure can offer it through the existing bounded Stop continuation; a PreCompact offer blocks that compaction. Eligible child-hook proposals reach primary coordination under the same catalog bound. A completed unguarded attempt suppresses repeated automatic offers of that command in the Run.

The model must submit a fresh `command_unguarded` request. Every hook-origin re-run requires a fresh human Ask, including under Auto and with a remembered exact-command rule. Remembering a hook approval would silently pre-approve unrelated ordinary-path host runs. Denial, unavailable approval or a dropped reply dispatches nothing and leaves the hook `Ignored`. The approved operation uses the ordinary unguarded executor and empty stdin; it is a separate command receipt, never a replacement hook invocation or a source of permission. Strict replay uses only committed evidence and never executes either command.

**Child inheritance.** The pinned Tool policy carries typed `unguarded` and `child_unguarded` restrictions (`denied` or `human_only`); child permission must narrow parent permission. Private `tools.json` may explicitly set `child_unguarded: "human_only"` only when commands are admitted; omission means `denied`. Each researcher and editor `ChildGrant` records its own required `unguarded` field, which may only narrow that pinned child restriction. A NoTools child always has `denied`. Replay rejects a missing field or widened grant. This permission grants no additional process, filesystem or Tool scope: current researcher and editor catalogs still refuse direct host-command requests. The primary may propose a child's exact failed hook command only with that child's explicitly inherited `human_only` permission. Definitions, hook text and children cannot set or widen it. Child-origin re-runs never inherit remembered exact-command approvals.

**Execution.** The host executor re-verifies the pinned executable digest and the Workspace identity, resolves the directory beneath the admitted Workspace without following links, and spawns the explicit argv with a cleared environment: `PATH` from the admitted runtime grants, real `HOME`, the system `TMPDIR`, `LANG`/`LC_ALL`/`TERM` when set, `NO_COLOR=1`, `ARANY_TOOL_WORKSPACE` (the real Workspace) and `ARANY_UNGUARDED=1`; no credential or proxy variable, no stdin. Output is capped, the run is bounded by the command timeout, and the process group is killed on timeout, overflow or cancellation. A leader or group that is not confirmed stopped makes the outcome `uncertain` and stops the Run. No changeset is produced: edits land directly, `workspace_effect` projects as `unguarded`, and only a later read is evidence of file content. The attestation is an `UnguardedReceipt` (pid, exit code, executable digest, whether descendants were confirmed stopped), issued only when the process was spawned; a Guard receipt never attests this operation and the Guard helper refuses it.

**Journal and replay.** `ToolStarted`, `ToolFinished`, `ToolPermissionDecided` and `RunStarted` (current versions in the [version table](./execution.md#admission-persistence-and-recovery)) carry the operation, the attestation, the nullable settings mode and the pinned rules digest. A verdict is committed for every unguarded intent, with or without `permissions.json`. Replay rejects an approved verdict unless the actor is the primary, the source is `human` or `exact_command_rule`, the decision is not deny, `exact_command_rule` has a pinned rules digest and the journal holds a qualifying failure; it rejects an `ai_review`, `rule` or `mode` approval, a Guard receipt, a cache update and an integration sourced from an unguarded intent, and any finish without a verdict. An unqualified proposal still replays as a denial.

**Project rules.** `unguarded-commands.json` in the admitted StateRoot holds at most 128 exact entries in 64 KiB (program, args, cwd, creation time, and the Workspace path, device and inode), under the same private-record admission as `permissions.json`; an unsafe or invalid file rejects Tool admission. Matching is typed byte equality, never a wildcard, prefix or shell parse. The snapshot is pinned in `RunStarted` and immutable: a rule recorded by "Always allow" applies from the next submission, and a repeat in the same Run prompts again. Edit or delete the file to remove a rule. Children never inherit rules; the explicit typed ChildGrant restriction above defaults to `denied`.

**Marking.** Terminal and `/transcript` summaries append `UNGUARDED`; the answer heading reads `Answer (unguarded effects: N):`; `/goal` and `exec`'s stderr receipt add `unguarded effects: N`; the Goal report adds an unresolved fact and names `An unguarded host run` as the evidence attester; Run and Goal spans carry `arany.run.unguarded_effects` and `arany.goal.unguarded_effects`.

**Non-claims.** The host run does not bound network, filesystem beyond the Workspace, memory, CPU or process counts, descendants that leave the process group (for example by `setsid`), or changes to host state. The executor runs the pinned executable and directory by path, which can be user-writable, unlike the Guard's private copy on Linux, so a concurrent writer with the user's authority could swap them between verification and exec or between directory validation and spawn; a human approved this command with that authority, and closing the race needs a private copy or descriptor exec, which are not portable. Guard path aliases are refused rather than translated. Project rules bind path, device and inode, which can be reused after a project is deleted and recreated at the same path (folder trust shares this limit). A dropped future kills only the leader; the journal records the outcome as uncertain.

## Commands

Command project copies exclude `.git`; the command description points to typed Git reads when they are cataloged. Following the Run's pinned catalog, a nonzero command exit whose kept stderr contains `not a git repository` receives a fixed hint in the model result's `hint` field when `git_status`, `git_diff` and `git_log` are available; the hint is derived deterministically from the recorded observation and omitted if adding it would put the complete model result above the [per-call result ceiling](#limits-and-failure-behavior).

Each `commands` entry declares a reviewed executable and its SHA-256, whether it is an interpreter, and any additional pinned input files:

```json
{
  "name": "bash",
  "executable": "/usr/bin/bash",
  "sha256": "REPLACE_WITH_THE_64_CHARACTER_LOWERCASE_SHA256",
  "interpreter": true,
  "inputs": []
}
```

The placeholder above is deliberately invalid. Resolve a system executable's real path and calculate its digest yourself, for example with `readlink -f /usr/bin/bash` and `sha256sum /usr/bin/bash` on Linux, or `shasum -a 256 /bin/sh` on macOS. Arany requires a no-follow, regular, single-link native executable: ELF on Linux or Mach-O on macOS. A symlink must be replaced with its resolved executable path. The optional `git` pin differs: it must lie under `/usr`, be root-owned, non-set-ID and not group- or world-writable, may have several hard links (distributions hard-link `git-core`), and runs in place from the read-only `/usr` mount rather than from a `/programs` copy, since its shared libraries load live from `/usr`. Updating an executable requires reviewing and changing its pin.

Additional inputs use `{"path":"/absolute/reviewed/file","destination":"relative/name","sha256":"<digest>"}`. They appear read-only under `/inputs/PROGRAM_ID/relative/name`. Executables are copied to `/programs/PROGRAM_ID`, except checked immutable macOS system programs, which retain their original paths. Paths and digests are checked again for each fresh invocation. Descriptions and the `interpreter` declaration do not prove that arbitrary arguments or a script are safe; allowing a shell or interpreter authorizes its behavior inside the same OS-enforced boundary, including descendants using the admitted native runtime.

## Persistent Workspace build cache

Commands receive an explicit argument array, a relative working directory, a cleared environment, private `HOME`, temporary and Cargo directories, no terminal input and bounded lossy UTF-8 output. With the build cache enabled, `CARGO_HOME`, `CARGO_TARGET_DIR`, `npm_config_cache` and `PIP_CACHE_DIR` point into the admitted cache view (`/cache` on Linux, the cache volume on macOS); otherwise they point into private scratch. Toolchain subtrees are executable across their whole tree, so `bin` entries that symlink into `lib` run on both platforms; selected `bin` paths augment the fixed system `PATH` in grant order, and a selected host cache replaces only its corresponding nested cache path. Each snapshot is a fresh writable copy of selected project paths, including prior typed edits and integrated changes; empty directories and executable bits survive without set-ID bits.

Each Workspace has one archive keyed by its canonical path plus device and inode; at most 128 identities are retained. A nonblocking exclusive identity lease covers primary restore, collection, publication and clear; worker restores use the shared-read lease below. Competing exclusive operations return busy. Restore writes only fresh single-link regular files and executable bits into a separate quota-backed view and never creates links. Store accepts only allowlisted cache roots and rejects symlinks, special files, set-ID inputs, malformed paths, identity drift and unknown archive data. After positive descendant termination and native cleanup, Guard streams a bounded candidate to Store, which publishes it through a rollback intent, a committed marker and a successful parent-directory sync. Failure before the marker rolls back. If the marker write or its sync fails, Store returns a persistence error and keeps both archives and the records. Recovery must sync the directory before resolving the marker; a continuing failure blocks cache admission until recovery succeeds or the user runs `/cache clear`. Recovery restores the previous archive when a committed new archive is invalid and the previous one is valid; a synced marker keeps a validated new archive. Malformed or unsafe records fail closed and remain available for diagnosis. A failed, nonzero, cancelled, timed-out, drain-ceiling-killed or uncertain command never publishes, and the last committed cache survives.

For primary commands, the controller records a typed `cache_update` beside the original observation, command result and Guard receipt, with six values: `published` (candidate committed); `rejected` (known size or quota rejection kept the prior archive); `failed` (candidate validation, host-side staging create, write or sync, reopen, or a known publication failure left the prior archive committed); `uncertain` (outcome cannot be confirmed and stops Run continuation); `not_attempted` (Guard error after dispatch, or a failed command that did not attempt publication); and `not_applicable` (no private cache). Uncertainty never changes the command's disposition: a successful command stays `succeeded`, and a successful cache-backed command cannot commit `not_attempted`. Publication is never retried by rerunning the command. Cache data is never executable authority or automatic Provider context; command or MCP output that discloses it is ordinary bounded observation. Background jobs do not survive a call. This finite profile does not establish support for every large Rust, Node or Python build.

Internal worker assignments can pin a shared-read lease before their first intent. The nullable generation is a domain-separated SHA-256 of the committed archive's device, inode, length and nanosecond modification/change timestamps, or null when absent. The lease keeps that immutable archive generation stable until assignment disposal, including absence; it creates no reservation or candidate and never runs transaction recovery. Pending transaction markers refuse as busy until an exclusive owner recovers them. Each worker command takes a separate nonblocking shared-read restore lease and checks its generation against the intent before Ready; mismatch is known non-dispatch, with no wait or retry. Every command restores a fresh quota-backed writable copy and discards it after positive native cleanup. Workers never collect, stage or publish cache bytes, and a worker receipt records `cache_update: discarded`, including an absent archive. `/cache clear` and primary command admission remain busy while any reader holds the identity. The existing Engine additionally holds primary processes until worker lease quiescence.

The cache result is separate from command success. Text receipts surface rejected, failed and uncertain updates; JSONL and replay keep the full observation. The `default` or `build` class, user settings and checked headroom set each invocation's cache-view limit. The 8 GiB setting is a requested maximum, not usable capacity: committed archives, metadata, reservations, candidate and staging all count toward the 8 GiB StateRoot aggregate, and candidate and view are capped by remaining headroom. No cache is evicted automatically. Increasing the setting raises no other bound.

`/cache clear` removes only the current Workspace archive and displays `Cleared this Workspace's private build cache`; `/cache clear all` reclaims all committed caches and displays `Cleared all private build caches`. A busy clear displays `Build cache is in use; retry after its command finishes` and keeps the archive. A malformed clear displays `Error: Usage: /cache clear [all]`; other failures display `Error: private build cache could not be cleared`.

Archives capture regular files by content regardless of link count, so Cargo hard links restore as independent files. Competing operations return busy rather than wait. Publication builds the candidate beside the committed archive, syncs it, durably records rollback intent before renaming, and treats the committed marker with parent-directory sync as the commit point. A marker write or sync failure returns the error, skips Drop-time recovery and retains both archives and transaction records. Task transport carries only the checked Workspace identity and the exact read-only exclusions, never a `StateRoot` path or handle.

## Command changesets

After command completion and positive descendant termination, Guard compares the private snapshot with its admitted input and returns a sorted changeset of created, modified and deleted regular files with digest-bound before and after bytes and executable bits; binary content uses canonical base64. A nonzero exit may still return changes, since exit status and publication are separate outcomes. A failed capture, timeout, cancellation or unconfirmed cleanup publishes nothing.

The command snapshot source is either the Workspace or `WorkerImage { assignment_id, base_digest, revision }`, selected by the immutable intent target and validated framed transfer. A worker source reconstructs only its acknowledged private image after GO, never a host Workspace snapshot. Its successful capture uses the [private worker bounds](#private-worker-targets-and-handover-transfer) and yields a private overlay candidate; it never produces a Workspace CommandChangeset or ApplyChangeset. The Workspace limits and correlation rules below are unchanged.

The snapshot is scanned without following links or reading excluded paths. Links (including hard links), special files, set-ID bits, excluded or invalid paths, mount crossings, unsupported type conversions and overflow reject the whole changeset. Directory creation is supported only as parents of created files; empty-directory changes are not integrated. The ceiling is 64 files and 8 KiB aggregate decoded before and after content, plus the existing serialized capacity; the Build class raises neither these nor other Workspace or Tool-context limits.

Engine records the command observation, then creates a separate one-use integration intent bound to that exact receipt; models cannot request integration. The Goal path scope and pinned write grant are checked before publication. An out-of-scope integration is journaled as `Denied` with no receipt or dispatch, and replay accepts only that correlated denial. In-scope integration goes through the typed-mutation Guard and never adopts subprocess-created host paths. Approval cannot widen the grant. Auto edits accepts in-grant integration after command approval; Request approvals shows the sanitized before and after changes and asks separately; Auto approval reviews the concrete integration and asks a human on uncertainty. Headless runs use their upfront grant. Goal plan revision cannot widen the pinned Tool grant.

Before publishing, Guard validates the whole batch, Workspace identity, every before digest, executable bit or absent-file precondition, and parent types through no-follow handles; conflict, denial or overflow leaves every file unchanged. Publication uses fresh regular inodes and checked deletions, then synchronized directory receipts. It is not an atomic multi-file transaction: failure or drift after publication records Uncertain and stops the Run without retry. Cancellation during approval changes nothing; cancellation during publication may leave uncertain effects. Replay retains both outcomes and never repeats the command, approval or integration. Only a successful integration receipt proves publication.

Before dispatch, a command reserves Store and Event headroom for its observation, any required integration and the terminal Run and Goal receipts; if that tail cannot be admitted, the command does not dispatch. Integration shares the Goal's active-time accounting, uses fresh authorization and never renews the command's approval.

Command capture starts only after payload descendants are positively absent, and the changeset scan finishes before images detach. Guard, not the worker, validates the integration batch. The system-executable catalogue travels only through the trusted controller and supervisor channel, never Workspace or payload input, and is never persisted as an authority cache.

## Checkpoints and rewind

Store captures private pre-images for primary Workspace Write, Edit, MultiEdit and both ApplyChangeset sources after approval, immediately before Guard GO. A checkpoint is the position before a Run's first effect, covering prompts, Goal start/resume and autonomous Runs; steering notes create no checkpoint. Capture saves an existing file on its first successful publication in that Run, and again if its before digest differs from the last successful after digest in the Run. Creates and same-Run repeats without a gap need no bytes. Deletions save their before bytes. A failed publication never advances that chain.

Typed edits read through the existing admitted directory handle with identical grant, identity, protected-name, no-follow, mount, link and file bounds, then verify the intent's expected SHA-256. Command and worker integration use their already validated in-memory before bytes. Capture commits before GO; Guard still rechecks the whole publication batch. Digest mismatch skips capture and leaves publication's own conflict check in force. Mkdir, MCP, commands themselves, private worker edits, cache publication and scratch have no checkpoint capture. Integrated command and worker changes are covered because they are Workspace publications. Unguarded commands and external effects remain outside this coverage.

`StateRoot/checkpoints.sqlite` is a Store-thread-owned schema-v1 derived store outside the Workspace, separate from the journal. It contains content-addressed `blobs(digest, bytes, len)` and attribution/quota `refs(session_id, goal_id, run_id, rewind_id, tool_sequence, path, digest, len, captured_at_ms)`. The ref sequence names the committed ToolStarted or WorkspaceRewindStarted; exactly one of run_id and rewind_id is present. Rewinds have no Goal and use the Session quota bucket for goal_id. Bytes are deduplicated; every blob read verifies SHA-256. Refs never choose a restore destination: rewind plans must come solely from journal facts and look up blobs by journal digests. Strict replay never opens this store, reads the Workspace or re-executes a publication. [Session rewind planning](./session.md#rewind-planning-and-replay) consumes only journal metadata.

Admission reuses private_fs: a private 0700 directory, owner-only 0600 regular single-link no-follow files and native ACL checks. SQLite uses defensive mode, trusted_schema=OFF, DELETE rollback journaling, synchronous=EXTRA, incremental auto-vacuum and a max_page_count derived from the physical quota. SQLite values and rows are capped at 1 MiB + 4 KiB and SQL at 64 KiB; overflow makes storage unavailable. The checkpoint migration floor and current SQLite `user_version` are both 1. `store::migrate` registers this schema alongside the journal; the version guard requires each later adjacent step and its exact source schema and fixture. A schema-v1 identity fixture pins Tool and rewind refs and their content-addressed bytes without a rewrite, backup or migration marker. Future checkpoint steps must use the [journal copy-transform, validation and recoverable swap protocol](./execution.md#journal-migration), under the same history and checkpoint locks, preserving blob digests and refs. At startup, a nonempty SQLite checkpoint file with `user_version` below the floor, including a foreign SQLite database, archives intact with the journal and sidecars through the existing history archive and notice; a file SQLite cannot read stays as malformed storage. A hot `-journal` is first recovered by SQLite under the exclusive history and checkpoint locks and eligibility is then re-read; a sidecar that survives recovery refuses as unsafe state with every file untouched. Missing or empty checkpoint storage remains lazily initialized. Newer or malformed schemas retain explicit checkpoint recovery and reject before mutable pragmas or eviction; busy or unsafe storage is never archived. Capture failures preserve that storage and do not block the effect. The Store reset API admits a private malformed/unsupported store, holds its exclusive checkpoint lock, snapshots its file identities and modification facts, and refuses a changed file. Explicit confirmation may then remove only checkpoint storage and its SQLite sidecars. Busy, non-private or unsafe storage cannot be reset. The [terminal rewind panel](./terminal.md#rewind) offers confirmed recovery; no clear command or settings toggle exists.

| Bound | Limit | Overflow |
|---|---|---|
| Pre-image | 1 MiB | skip the whole publication with `too_large` |
| Path per owning Session | 32 versions and 32 MiB logical bytes | evict oldest versions first |
| Goal | 256 MiB logical referenced bytes | evict oldest checkpoint refs, excluding the current Run |
| Session | 100 checkpoints with refs and 512 MiB logical bytes | evict the oldest checkpoint's refs, excluding the current Run |
| Store | 2 GiB SQLite pages including free pages, blobs and refs; 262,144 refs; remaining filesystem headroom | evict the least recently captured Session's oldest refs, excluding this publication; otherwise skip whole with `quota` |
| Retention | 30 days after the Session's latest capture; future-dated Sessions are eligible | sweep on Engine open and before capture |
| Publication capture | typed edit 1 MiB; command changeset 8 KiB; worker handover 32 MiB and 2,048 files | skip whole; no partial capture |
| Contention | 2 seconds shared by checkpoint-lock and SQLite contention | skip with `store_unavailable` |

Eviction is transactional and set-based: expired Sessions, then per-path, per-Goal, per-Session and total quotas, each one ordered pass that removes whole checkpoints until the quota holds, with one pass targeting twice the shortfall for the physical size and filesystem headroom; retention expiry commits in its own transaction so it makes progress even when the capture itself is skipped. Unreferenced blobs are removed and incremental vacuum reclaims free pages. A failed batch rolls back its insertions and evictions. Eviction runs before the filesystem headroom check: admission retains 4 MiB of filesystem headroom plus the incoming bytes and the file growth, which covers the rollback journal; SQLite's page ceiling remains enforced. The Store validates the whole database once per open and re-checks only the file identity and schema version afterwards. The Engine waits at most 3 seconds, and at least 1 second before the Guard's GO deadline, for a capture; a later result is discarded and the capture is `skipped` with `store_unavailable`. Orphans from a crash before GO expire with the Session's refs. Removing a ref whose digest remains available through deduplication emits no notice. The first eviction per Run that loses a blob of this Session identifies its newest affected checkpoint: `Older checkpoints pruned; code restore unavailable before Run ID`. Other Sessions' prunes are never named in this Session's journal. A startup sweep's prune of this Session is retained for its next captured publication.

[ToolFinished](./execution.md#admission-persistence-and-recovery) has required nullable `checkpoint`: null for non-publications or known non-dispatch; otherwise `{status: captured|not_needed|skipped, reason: null|quota|too_large|store_unavailable|digest_mismatch, pruned_before_run: null|RunId}`. Captured requires an overwrite and successful or Uncertain publication; not_needed requires a create, a repeat without a gap, or a publication that reached GO without changing the Workspace (failed, conflicted or denied), which never produces a rewind notice. Skipped capture still permits the publication. Tool summaries and `show` surface the reason (quota: `This change cannot be rewound (checkpoint storage full)`); JSONL retains the field, and Goal reports retain a priority unresolved fact. Checkpoint bytes never enter model context, telemetry or diagnostics automatically.

Capture executes no Git and leaves the user's `.git` untouched. Prior file contents are unencrypted private state, like the journal. The same storage and capture contract applies on Linux and macOS; existing native admission and publisher guarantees remain required, with no new native enforcement or stronger macOS filesystem durability claim. [D-21](../research/next-step-decision-register.md#d-21--checkpoint-storage) owns the peer comparison and storage rationale.

Engine::rewind_preview admits an idle Session under the Engine operation slot, Session and ancestor locks and the account-wide Workspace writer lock. It checks the pinned Workspace identity and reloads the current explicit write grant or saved folder consent, never historical permission. Current permission denies also exclude the path; confirmation supplies any required human approval. Preview computes live digests and executable bits through the admitted in-process directory capability and verifies required checkpoint blobs. Read-only or excluded paths are outside_grant; links, special files, mounts and case aliases are unsafe. Missing, pruned or tampered blobs are unavailable. A preview contains no executable text or authority from restored bytes. Its comparison data reuses the admitted before/after versions, capped at 64 MiB of decoded content in aggregate; content beyond that comparison bound is explicitly unavailable without changing restore admission. Unsafe, outside-grant and unavailable paths disclose no comparison content. Checkpoint-storage errors remain distinguishable from a missing blob so the terminal can offer checked recovery.

Any live drift, intermediate history drift, unavailable blob, unsafe path or grant exclusion refuses the entire batch by default and lists the affected paths. Two explicit selections produce a new preview for confirmation: keep listed files and restore the others, or overwrite drift/history-drift paths using their observed digest/absence as a new precondition. Unavailable, unsafe and outside-grant paths can only be kept. A live file exceeding the 1 MiB version bound is listed as an unsafe path that can be kept. Preview applies the Guard's path admission (ASCII, at most 16 components, whole-batch directory scan bound), so it never promises a restore the Guard refuses. Combined kept/overwrite selections are sorted, distinct, disjoint subsets of at most 64 explicit paths, each at most 512 UTF-8 bytes. An empty effective plan cannot restore. Open or Uncertain publications block code restore under the [Session contract](./session.md#rewind-planning-and-replay).

Engine::rewind consumes one opaque, non-cloneable preview as confirmation of that exact plan. It reacquires the locks, rechecks the head/prefix, live state, blobs, current grant and enforcement, and refuses a changed or expired preview before Started. Confirmation expires after 60 seconds. Before Started it reserves two maximal Session Events; capacity refusal changes nothing. The effective plan is capped at 32 MiB of restored content and 32 MiB of overwritten content; file count, per-version size and serialized transfer use the shared [changeset bounds](./execution.md#worker-journal-protocol). Overflow refuses the whole action. Workspace contention returns WorkspaceBusy; an active Engine returns Busy.

Restoration uses an internal Rewind publication source containing the canonical plan digest and transfer length/digest. It is never a model Tool or a ToolStarted source. Restore bytes cross the existing bounded binary transfer phase; Guard receives no StateRoot path or checkpoint handle. After committing Started, the Engine durably captures all overwritten content in the Store under that rewind ID, creating the Before rewind checkpoint. When publication proceeds, Finished reports capture status; an explicit drift overwrite refuses before GO if its content could not be saved. Hooks never run. The existing publisher checks the complete batch before its first write, then uses fresh inodes and checked deletions. Guard capacity waits at most 30 seconds; transfer and publication each use the existing 60-second action limit, with native setup/cleanup deadlines unchanged. Cancellation before Started changes nothing; after Started it records cancelled when non-publication is known. ## Typed Git reads

Install Command Line Tools to enable macOS Git reads; remaining macOS evidence is listed in [next steps](../../NEXT_STEPS.md).

1. **Availability.** Folder trust pins the platform Git when it resolves under the platform root to a root-owned, non-set-ID, non-writable executable of the platform's format (path and SHA-256 per Run): `/usr/bin/git` (ELF) on Linux, `/Library/Developer/CommandLineTools/usr/bin/git` (Mach-O) on macOS. Explicit configuration uses the `git` field (`name` `git`, executable under the platform root, SHA-256, `interpreter: false`, no inputs) and requires `workspace_paths: ["."]`. Without a pin the catalog reports `unavailable`, no Git operation is offered or admitted, and Git is never emulated. Git outside the platform root is unavailable by design: Nix, Homebrew and Guix Git, Xcode.app Git and, on macOS, the `/usr/bin/git` xcrun shim.
2. **Operations.** `git_status {path}`, `git_diff {path, base, head, staged}` and `git_log {path, revision, max_count}`. `path` is a Workspace-relative literal pathspec, and `.` is the whole repository. `git_diff` compares the working tree with the index, the staged index with `base` (or HEAD when `base` is null), the working tree with `base`, or `base` with `head`; `head` requires `base` and excludes `staged`. A revision is `HEAD`, a ref name or a hex commit name with at most four `~N`/`^N` steps, at most 128 bytes; ranges, `:`, `@{` and options reject. `max_count` is 1 through 50. Results are JSON: `git_status` returns `{"branch":{"oid","head"},"entries":[{"path","state"}],"truncated"}`, `git_diff` returns `{"files":[{"path","added","deleted"}],"patch","truncated"}`, and `git_log` returns `{"commits":[{"oid","parents","author","time","subject"}],"truncated"}`. A failure returns `{"failed"}`, plus `"stderr"` only when bounded diagnostics remain.
3. **Exclusions and fidelity.** The components `.git`, `.aws`, `.ssh`, `.gnupg`, `.env`, `.env.*`, `.npmrc` and `.pypirc` are excluded case-insensitively (ASCII) through `:(icase)` pathspecs and row and stderr filters, including history, so `.ENV` or `.Env` on a case-insensitive APFS volume is excluded too. Renames are not detected, submodules are ignored, and `.git/info/exclude` is not applied. Git runs with default settings, not the repository's: `core.filemode`, `core.autocrlf`, `core.eol`, `core.ignorecase`, `core.symlinks`, `core.excludesFile`, sparse checkout and `branch.*` are not applied. A WSL2 `/mnt/c` repository with `core.filemode=false` can show mode-only changes, and an `autocrlf` repository can show line-ending changes that your own `git status` hides. The fixed view config omits `core.precomposeunicode` and `core.ignorecase`, so on APFS a non-ASCII or case-variant name can appear as deleted plus untracked. These fail without running Git: a repository rooted in a parent directory, a linked worktree, a submodule checkout or other `.git` file, a symlinked `.git`, a missing `HEAD`, `objects` or `refs`, and `[extensions]`. A split index fails when Git runs.
4. **Neutralization.** Git never receives the repository's configuration, hooks or attribute-selected drivers; Arany reads repository config only to detect `[extensions]`. It runs against a private view on scratch tmpfs (Linux) or in the unit control root (macOS): a fixed config, copied `HEAD` and `index` files, and linked `objects`, `refs`, `packed-refs` and `shallow`. The index is read without following links, with its mtime from the same open file (Git's racy-stat check compares against it); a linked or hard-linked index is an unsupported layout, and an index over 32 MiB refuses with Limit. It runs with a closed 13-variable environment, fixed argv (`--no-optional-locks`, `--no-ext-diff`, `--no-textconv`, `--no-pager`, `--end-of-options`, `--`), read-only Workspace access (a bind on Linux, a Seatbelt read grant on macOS), no network, the rechecked pinned executable and the default resource profile. Linux stops namespace descendants before the receipt; macOS empties the unit coalition at teardown. Inert vectors include `core.fsmonitor`, hooks, `diff.external`, textconv, filter drivers, `include.path`, pagers, signing programs, credential helpers and lazy fetch.
5. **Policy and disclosure.** Git reads need the pinned grant and no approval in any mode. They are in the Goal prelude with plan-contract `path` scope, are never success criteria, and are never offered to children. Bounds: 256 KiB stdout and 4 KiB stderr kept per Git invocation, 256 rows, 50 commits, results fitted to the Tool result budget with `truncated`, and at most 20 seconds per read. On macOS the same bounds run under the supervised default profile in [limits](#limits-and-failure-behavior). A nonzero exit is Failed with its status and at most 1 KiB of diagnostics, and the Run may continue. Committed history and changes reach the Provider and the journal as untrusted data. Residual risk: secret-path exclusions are pathspec and output filters, not sandbox enforcement.

macOS trade-offs, known and accepted for this release:

- The private view has no volume quota (`install_git` uses `unit_root`, which skips `storage::verify_storage`), so writes are bounded only by the 20-second cap and fixed argv. The pinned Git has no code-signature or entitlement verdict; its only check is a SHA-256 pin of a root-owned file, and the kernel enforces the platform signature at exec.
- A TOCTOU window exists between `verify_pin` and spawn-by-path. Linux avoids the equivalent window by executing the pinned file in place; macOS cannot, so exploiting it requires root write access to the Command Line Tools tree. Ancestor directories of the pinned executable are not checked for ownership or writability on either platform; `verify_host_executable` checks only the leaf. This is a known limit.
- A Command Line Tools update changes the digest, so Git reads fail with `ChangedInput` until folder trust is renewed. The read-only Workspace bind includes `.env`, so a Git memory-corruption bug triggered by a hostile pack could emit Workspace bytes through the bounded output channel, the only exit because there is no network. Encodings are offline-tested only; live evidence is listed in [next steps](../../NEXT_STEPS.md).

### Typed prefix rules

`permissions.json` may carry `permissions.typedPrefixes`, an optional list (default empty) of `{"prefix": [...], "decision": "allow"|"ask"|"deny", "workspace": null | {"path","device","inode"}}`; every field is required and unknown or duplicate fields reject. `prefix` is exactly one of `["git","commit"]`, `["git","branch"]`, `["git","switch"]`, `["git","push"]` or `["gh","pr","create"]`; partial verbs, extra tokens, flags, globs, shell strings, aliases, wrappers and executable paths reject. Matching uses the validated typed operation, never adapter argv: `git_commit`, `git_branch` with a `name` and `git_switch` map to their verbs; branch listing is a read and matches none. `push` and `pr create` are accepted for editing but match no operation until host publication ships: they grant nothing, and every future execution will need human approval, even under `allow`. `workspace: null` is user-wide within this state directory; an object binds the exact absolute path, device and inode of the folder, so a moved or replaced folder inherits nothing. Paths are at most 4096 bytes, canonical, control-free, with a nonzero inode.

Typed rules share the 128-rule and 64 KiB limits with the ordinary rules and follow the same single `deny > ask > allow` order, so a typed allow cannot override an ordinary deny or ask. The folder filter applies once at Run admission; the pinned digest still covers the whole file, and settings never reload during a Run. A configuration read without a Workspace identity ignores folder-scoped allows and still applies folder-scoped deny and ask rules.

The only writer is the typed settings edit behind `/permissions` and the remember choice below. Inside the account replacement lock it rereads and validates the whole file, compares the SHA-256 the user saw (absent versus present included), revalidates the folder identity, applies one insert, decision change or removal, validates the result and replaces the private file atomically; other settings keep their values. A stale view, a busy lock or an overflow refuses with a fresh-load notice and no retry or truncation; a failure after the replacement may still have taken effect and reports `save not confirmed`. `/permissions` may create a missing file with `defaultMode: "default"` and says that doing so also activates default permission policy for other Tools; the remember choice never creates the file.

At a human approval for a primary local Git write that no rule or hook decided, the dialog offers `Yes, and allow git commit in this folder from the next Run` (or `git branch` or `git switch`). The human verdict is committed first (source `human`); only then is the rule appended to the existing file, and a failed save denies the pending call with the approved verdict already journaled; a save whose final directory sync fails after the rename may already be in effect, so it is journaled as an Uncertain `rule save not confirmed` outcome that stops the Run, dispatches nothing and is never retried. The remembered exact unguarded-command rule saves the same way, after its human verdict, and settings dialogs report an unconfirmed replacement as `settings change not confirmed` rather than as kept. The current action is approved by that one-use reply, the Run keeps its pinned rules, so another matching call in the same Run still asks, and the saved rule applies from the next admission. Replay never saves. The choice is offered only when `permissions.json` already pinned the Run, so remembering never activates settings for other Tools, and never for children, branch listing, hook asks, explicit ask rules, serve or ACP clients, or an `exec` Run with no human. Settings edits bind the folder identity captured when `/permissions` loaded them or the Run admitted it; a replaced directory refuses. `/permissions` lists, adds, changes and removes rules when no Run is active.

## Typed Git writes

Typed Git writes let the primary commit, create branches and switch like [Claude Code](https://code.claude.com/docs/en/permissions#bash) and Codex CLI agents running `git` in the Workspace, while keeping per-effect isolation: Git runs inside the Guard on a neutralized private view, and only Arany's own code publishes the validated result into the real repository. The [Git write workflow plan](../../planning/git-write-workflow/README.md) owns the later host push. [Typed prefix rules](#typed-prefix-rules) remember and revoke approval for the three local verbs.

1. **Availability.** They need the [typed Git read](#typed-git-reads) pin, its whole-Workspace grant, `write: true` and Linux Landlock ABI 3 or later (below); otherwise the catalog lists only the reads, among them `git_branch` with a schema that fixes `name` and `start_point` to null, so branches can still be listed, for example in plan mode. **Git writes are refused on macOS**: they are not offered and a proposal is denied before dispatch, because Seatbelt cannot further restrict a child of the already sandboxed Guard worker; [next steps](../../NEXT_STEPS.md) record the planned separate Git executor. They are offered only to the primary, never to researchers or editors, are never Goal success criteria, and a plan contract admits them only with `.` scope. Unsupported layouts and formats fail as for reads.
2. **Operations.** `git_commit {message, paths, staged}` commits to the current local branch: either distinct literal Workspace-relative `paths` (`.` for every change, even beside other paths), whose working-tree contents are added (including new and deleted files) and committed with Git's `--only` semantics, or `staged: true` with empty `paths`, committing the staged index. Other staged entries stay staged. The message is non-blank UTF-8 without controls other than newline and tab; Git's default whitespace cleanup applies. In paths mode protected path components are excluded as for reads and stay uncommitted; staged mode commits the index exactly as staged. `git_branch {name, start_point}` with `name: null` lists local branches as `{"branches":[{"name","oid","current"}],"truncated"}`, read-only and without approval; otherwise it creates `name` at `start_point` (a read revision, or HEAD when null) without switching or tracking, and an existing name fails. A start point naming a symbolic ref other than HEAD (any `ref:` content, as Git's files backend parses it), such as `origin/HEAD` or a bare remote name, refuses, and so does a branch while HEAD points to a ref outside `refs/heads`: name the branch it points to, since only direct refs and HEAD's referent are held. Names use the read ref-name grammar without ancestry steps, never `HEAD`, and may not differ only by ASCII case from an existing ref or ref directory. `git_switch {branch}` moves HEAD to an existing local branch; the current branch returns `switched: false` and publishes nothing. There is no amend, signing, force, delete, detach, merge, remote or raw-argument escape.
3. **Results and receipts.** A commit returns `{"commit","branch","publication"}`, a creation `{"branch","oid","publication"}` and a switch `{"branch","switched","files","publication"}`. The receipt `publication` is `{"objects","files"}` plus, as applicable, `"ref": {"name","before","after"}` (object names, `before` null for a new branch), `"index": {"before","after"}` (SHA-256 of the real index bytes, `before` null when absent) and `"head": {"before","after"}`. Failures return `{"failed"}` with filtered diagnostics, as for reads, and publish nothing; under Read-rule result filtering a failure keeps only its message and a switch refusal counts, but never names, a hidden path. Receipts carry object names and branch names, never file paths.
4. **Neutralized mutable view.** A fresh view in Guard scratch holds a fixed configuration (the read settings plus `logAllRefUpdates`, `commit.gpgSign`, `gc.auto` and `maintenance.auto` off), copies of HEAD, the index with its mtime, `packed-refs`, `shallow` and the `refs` tree (another Git's `*.lock` is skipped), and a private object directory that borrows the real store as an alternate, so every new object stays private until publication. Each Git child is spawned from a thread confined by a Landlock domain (ABI 3 or later, so truncation is mediated) that denies every write, truncation, link, rename and node creation outside Guard scratch and `/dev/null`, and by seccomp filters that deny mode, owner, time, extended-attribute and `file_setattr` changes everywhere, answer `ENOSYS` (an older kernel, to libc) for every syscall newer than the last one the policy knows, so a future metadata setter fails closed, and deny every `ioctl` (answered `ENOTTY`, since inode-flag, fsxattr and filesystem-version requests change metadata through a read-only descriptor and Git without a terminal needs none), which Landlock does not mediate. The child inherits both, so Git can read the Workspace and real `.git` but never change them, while the Guard keeps its access for validated publication. An older kernel or a missing facility fails closed before Git runs. Repository configuration, includes, conditional includes, hooks, aliases, `core.sshCommand`, filter, diff and merge drivers, signing programs and fsmonitor never apply. The closed read environment gains only `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`; commits use `--no-verify` and `--no-gpg-sign`, and timestamps are UTC. Reflog entries are not written.
5. **Identity.** Private `tools.json` may set `git_identity` (`name` and `email`, without controls, `<` or `>`, no whitespace in the email). Folder trust reads `user.name` and `user.email` from `$XDG_CONFIG_HOME/git/config` (default `~/.config/git/config`) and then `~/.gitconfig`, the later file winning per key, as data only: other keys, `include`, `includeIf`, escapes and environment overrides are ignored, so a per-directory identity from a conditional include is not applied. Without both values the commit uses `Arany <arany@localhost.invalid>`. Repository configuration never supplies the identity.
6. **Commit and branch rules.** A commit needs HEAD on a local branch, and a switch refuses from a detached HEAD because no reflog entry would keep its commits reachable; creating a branch from a detached HEAD is allowed, as in Git, and moves nothing. A repository with `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `BISECT_LOG`, `rebase-merge`, `rebase-apply` or `sequencer` refuses commits and switches; finish or abort that operation first. Git itself refuses an empty commit and unmerged entries. An unborn branch can receive its first commit.
7. **Switch rules.** After a private index refresh, the switch refuses when any path changed between HEAD and the target is modified in the index or working tree, when an untracked or ignored file or directory occupies an added path, when an entry is a symbolic link or submodule, when a path is protected, invalid or too deep, and when two planned paths, or any of their parent directories, differ only by ASCII case, or one aliases an existing Workspace name by case; the failure lists the first conflicting paths. A file-to-directory or directory-to-file transition refuses with a dedicated message directing the user to switch in their own terminal, even when the working tree is clean. Each preimage is captured only when its bytes and executable bit still equal HEAD's blob, so an edit racing the check refuses instead of being overwritten. It writes raw blob contents without end-of-line or attribute conversion, creates new files `0600` (`0700` when executable) as typed writes do, removes deleted files and leaves emptied directories. The new index comes from Git's two-tree `read-tree -m`, keeping unrelated staged entries.
8. **Publication.** Before the first effect the Guard creates Git-compatible exclusive locks for every target it replaces or read: the branch ref, `index` and HEAD (`HEAD.lock` is held even when a commit leaves HEAD unchanged), a switch's source and target refs, a new branch's start ref under Git's lookup order (HEAD's referent by default), and `packed-refs`. Every ref path component is admitted with exact case against its directory first; a directory a lock creates is synced into its parent, and removed again unless the lock commits. Under those locks it requires HEAD, `packed-refs`, every loose ref and the index digest to equal the snapshot the view was built from, so a commit can never replace a ref that advanced after the snapshot. A held lock, any drift or a replaced `.git` returns `Failed` with nothing published; locks that were only held are removed after publication. Before its first lock the Guard writes `.git/arany-locks-<intent>.json` and records each lock's path, device, inode and SHA-256 as it takes it; the record goes once the locks are gone. If the Guard dies, exclusion over those locks can no longer be proven, so nothing moves or deletes them: the controller (once the Guard unit is confirmed stopped) and Goal resume (once private recovery confirms the unit is gone) report every recorded lock that is still the recorded inode with the recorded bytes as the typed `StaleGitLocks` error, which names the paths and says to remove them after checking that no git process is running. The controller puts that report first in the write's journaled `Uncertain` observation, so `show`, `exec` and serve carry it whole and the terminal row wraps it, escaped, across at most eight continuation rows before an explicit remainder count. Record paths admit only the typed ref-name alphabet, and every CLI error line is escaped like other untrusted text; Goal resume returns it before refusing to resume past the unsettled write. Another inode or other bytes at a recorded path belong to someone else and are not reported. When no recorded lock remains, the record itself is removed. Publication is never retried. It then publishes switched Workspace files through the [changeset publisher](#command-changesets) (digest-checked, no-follow, fresh inodes), new loose objects (content-addressed `0444` files renamed without replacement; an existing object is kept), and renames the ref, index and HEAD locks, syncing each directory. This is not a transaction: after the first effect any failure records `Uncertain`, stops the Run and is never retried; reopen and strict replay neither complete nor roll it back. [Rewind](#checkpoints-and-rewind) does not undo Git writes.
9. **Policy.** Creating a branch, committing and switching ask like commands: Request and Auto edits ask a human, Auto approval reviews them and `plan` denies them. A matching allow rule, ordinary (naming `git_commit`, `git_branch` or `git_switch`) or typed for its verb, pre-approves them in `default` and is required for `dontAsk` to permit them; `acceptEdits` and `auto` ignore it, and the [typed-allow mode mapping](#modes-and-approval-decisions) owns the rest. Rules and hooks only narrow; the Guard and pinned grant still apply. The receipt and every refusal are journaled as for other effects. The [limits table](#limits-and-failure-behavior) owns every bound; a result budget below its minimum records `Limit` before any effect.
10. **Platforms and non-claims.** Git still reads the whole Workspace under the Guard, as reads do. Linked worktrees, submodules and signing remain unsupported, and macOS refuses Git writes as item 1 states.

## In-process reads

Execution-site dispatch stays inside `ToolRuntime::execute` using the operation's
pinned site. A `ToolExecutor` trait with interchangeable InProcess and Guard
adapters was rejected: the sites enforce different contracts, and a fake Guard
could make Engine tests pass without exercising enforcement.

List, Read, Search and Glob run in the Engine process, as Claude Code and Codex CLI run reads outside their command sandbox. Typed Git reads, typed mutations, commands, Skills and MCP stay in the Guard, because they spawn a process or change the Workspace. The Engine opens the Workspace directory handle once at Tool admission, which still requires available native protection, and resolves every path beneath it with the Guard's no-follow, link, mount, special-file and protected-name rules (including `.env`) and the same `workspace_paths` scope, so disclosure does not widen. Before each read it rechecks the intent, its expiry and policy digest, and that both the pinned handle and the Workspace path still have the admitted device and inode; a replaced directory records Failed at `pinned input` without attestation before reading and stops the Run.

Results fit the intent's rendered (model-facing serialized) result budget: List and Glob drop trailing rows and set `may_be_truncated`, Search pages as [below](#limits-and-failure-behavior); a budget too small for any content is Limit. Read follows Claude Code's 1-based line paging and 2,000-line default. Its required nullable integer `offset` defaults to 1 and `limit` defaults to and caps at 2,000. It streams the admitted regular file and its whole-file SHA-256, returns numbered `N\t` lines, and cuts lines after 2,000 characters with `… [line truncated to 2000 chars]`. CRLF is a single line ending; invalid UTF-8 fails. The result is `{sha256, total_lines, start_line, end_line, next_line, truncated, text}`. The page ends at the line limit or rendered budget; `next_line` is the next unread line, or null at EOF. `truncated` marks more pages or a cut line. Empty files and offsets past EOF return empty text, the file's `total_lines`, `end_line: start_line - 1` and null `next_line`. Each page is the committed observation; replay never rereads the file. A read is bounded by its intent runtime: timeout records Limit and cancellation records Cancelled, neither attested. It waits for no Guard capacity and reserves its Goal action with zero preparation overhead, so exhausted active time refuses it and its runtime is clamped to the remaining active time.

A valid, in-scope, non-protected missing path (including a non-directory regular-file ancestor) records attested `Failed` with `File or directory not found; List the parent directory to check the path`, following OpenCode's not-found distinction without path suggestions. Link, mount and special-file refusals remain `Denied` with `File path is unavailable or outside the admitted regular-file boundary`; protected-name and out-of-scope paths retain their pinned-grant denial.

Each observation carries an `attestation`: `in_process` with the policy digest and Workspace device and inode, or `guard` with the Guard receipt. Validation and replay accept an attestation only from the site the operation runs at, so a read attestation never authorizes a mutation and a Guard receipt never attests a read. The Guard refuses a read intent. In-process reads run with the Engine's ambient privileges, not the Guard's OS sandbox: their boundary is the handle-relative checks, and they never write, spawn or use the network.

### Glob file discovery

`glob` takes `{pattern, path, limit}` and returns admitted regular files whose path relative to `path` matches `pattern`, copying the call shape and 100-file default of Claude Code's Glob and OpenCode's glob. `pattern` is 1–512 UTF-8 bytes. `path` names a Workspace-relative directory and `limit` is 1–100; strict native schemas expose both as required nullable fields. Null or omitted values, and an empty `path`, normalize to `.` and 100 before the intent is hashed, so permissions, hooks and replay see one form. A zero or larger limit is refused, not clamped.

The grammar is closed and case-sensitive on both platforms. `/` separates components and the whole relative path must match. `*` matches zero or more characters and `?` one character within a component. `**` is permitted only as a whole component: `**/` crosses zero or more directories and a terminal `**` matches the rest of the path, so `*.rs` matches only files directly in `path`. One level of `{a,b}` supplies literal or wildcard alternatives inside a component, at most 16 alternatives across all groups. Bracket classes, backslash escapes, a leading `!`, absolute or `~` prefixes, controls, empty, `.` or `..` components, nested, empty, single or unclosed braces and a partial `**` are refused as invalid arguments before any traversal; no invalid syntax is reinterpreted as a literal. The pattern translates to a regular expression of at most 8 KiB, compiled with a 128 KiB size, a 32 KiB DFA cache and 32 nesting levels, and overflow refuses the call. Peer divergence: Claude Code also accepts bracket classes; Arany refuses them to keep the discovery grammar closed. Permission path patterns keep their own separate translation and semantics.

Discovery reads metadata only. It never opens file contents, so sizes beyond the 1 MiB content cap are reported, and no SHA-256 or edit precondition is implied; use Read for those. It walks with the no-follow handles, `workspace_paths` scope and protected-name exclusions of List: protected components (`.env`, `.env.*`, `.git` and the rest), symbolic links, hard-linked and special files, other mounts and non-UTF-8 names are skipped, and a whole-project grant also skips `target`, `node_modules`, `.venv` and `venv`. Other hidden names match like any name. A pattern without `**` does not descend past its component count. The walk inspects at most 8,192 directory entries and retains at most 2,048 matching files, at depth at most 16 and with paths of at most 512 bytes; exceeding any bound records Limit, never a partial success.

The result is `{entries: [{path, bytes}], limit, may_be_truncated}`: Workspace-relative paths, deduplicated across selected roots and sorted in UTF-8 byte order before the first `limit` entries are kept. `may_be_truncated` is true only when another match exists or trailing entries were dropped to fit the rendered result budget, so exactly `limit` matches is complete; matches that cannot fit at all record Limit. There is no paging: narrow `pattern` or `path` instead. Peer divergence: Claude Code orders by modification time; Arany uses path order so the committed observation does not depend on mutable timestamps. A `path` naming a regular file records Failed, a missing path the not-found result above, and a link, mount or special file is Denied. A private worker globs only its assignment's base plus acknowledged edits, under its WorkerRead attestation; it skips the same ignored directory names below `path`, and a leased creation root that does not exist yet records the not-found result.

Evidence: the grammar and normalization tables in `tools::glob::tests`; `tools::tests::glob_returns_admitted_regular_files_in_path_order_with_honest_truncation` and `tools::tests::glob_never_discloses_protected_or_unadmitted_entries_and_bounds_its_walk` in the [Workspace corpus](../../crates/arany/src/tools/tests.rs); the private-image case in `tools::worker::tests::private_target_reads_own_acknowledged_edits_and_keeps_siblings_and_workspace_isolated`; mapping and narrowing rows in `tool_mappings_cover_typed_operations_and_read_denials_cover_writes`, `hook_matchers_use_exact_alternatives_or_bounded_unanchored_regex` and `updated_input_accepts_only_provable_narrowing`; `session::reducer::tests::goal_replay_tests::a_glob_replays_only_its_recorded_in_process_observation`; and the closed-journal journey `in_process_reads_are_attested_and_replay_after_exit_or_a_crash`.

## Atomic single-file MultiEdit

`multiedit` takes `{file_path, expected_digest, edits: [{old_string, new_string, replace_all}]}`. It edits one existing regular UTF-8 file, using Edit's admitted Workspace-relative path and required lowercase SHA-256 precondition. Unknown fields reject at both object levels. `replace_all` defaults to false; strict Provider schemas expose it as required nullable, with null also meaning false. Normalized intents serialize the effective boolean.

Apply 1–64 literal replacements in array order, each against the preceding result. False requires exactly one non-overlapping match; true replaces every non-overlapping match and requires at least one. Empty searches and identical old/new strings reject. A batch whose final content equals the original rejects. Replacement text stays literal, with no quote normalization, implicit newline removal or replacement-token expansion. Dependent edits such as A → B then B → C succeed. A missing or ambiguous later match leaves the original file unchanged.

Byte and size ceilings are owned by [Limits and failure behavior](#limits-and-failure-behavior): the file-operation row owns the replacement-string, MultiEdit input and file-size ceilings, and the Tool-context row owns the serialized-argument ceiling. The original, every intermediate result and the final content each stay within the file-size ceiling; sizing uses checked arithmetic before allocating a replacement. Overflow refuses the entire batch. At most 64 bounded transformation passes run, without recursive replacement or retry. Existing file-operation deadlines and result, context, Guard, checkpoint, worker and Goal bounds still apply.

Guard prepares the complete single-file change and publishes once through Edit's fresh-inode publisher, retaining before/after digests, byte lengths and executable bits. Readers see original or complete final content. Stale digests, invalid UTF-8, denied or unsafe paths, match failures and bounds failures publish nothing. Cancellation before publication changes nothing. Interrupted publication or failed durability confirmation remains Uncertain, stops continuation and never retries or claims rollback. One batch is one immutable intent, permission decision, Tool action and outcome, under the existing checkpoint policy; strict replay consumes its receipt and publication facts without reading or editing the current file.

MultiEdit uses the Edit permission family, including `acceptEdits`, path restrictions and read-denial protection. Hooks see `MultiEdit` and the complete bounded batch, under the existing hook-input ceiling; unsupported rewrites deny. Researchers cannot invoke it. An editor requires the explicit `multiedit` capability within the parent grant and its lease. Workspace execution and private-worker prediction share the same transformation; private success stays private until sealed handover integration. Model results omit private checkpoint metadata. Terminal presentation shows one `MultiEdit(path, N edits)` outcome; approval presents every replacement in order.

Peer behavior: the replacement field names, false default, match-count checks, identical-string and unchanged-final-content rejection, and Edit permission family follow Claude Code 1.0.128 ([shipped-code evidence](../research/claude-code-multiedit-evidence.md)). Ordered intermediate-result semantics follow [OpenCode v1.1.13](https://github.com/anomalyco/opencode/blob/v1.1.13/packages/opencode/src/tool/multiedit.ts#L21-L35), the owner's accepted choice over Claude's original-file validation and cross-edit substring restriction. Existing-file-only scope and the 64-edit limit are owner decisions. Arany retains exact matching, digest-bound admission, Guard isolation and one publication to preserve its guarantees; it does not copy peers' implicit creation, fuzzy matching or partial/direct-write paths. Linux and macOS share the transformation and existing typed-file profiles, with no new native API or stronger durability claim.

The macOS default and Build profiles terminate their entire owned unit when an observation exceeds a threshold or the resource observer fails. Thresholds are supervised, not kernel ceilings: scheduling delays and work between samples can exceed them, and swap prohibition and kernel group-OOM enforcement are not claimed. Normalized intents and receipts identify `linux_kernel` or `macos_supervised` resource semantics and the `default` or `build` class. The enforcement digest binds the native policy, class and effective values, including the command timeout and checked cache-view cap; it covers profile rules, admission algorithms and enforced constants, so changing an enforced dimension changes it. Selected grants and configured pins are bound by the intent's policy digest and resource identities; file and Skill intents carry no runtime grants. Missing or unknown profiles, mismatches between intent or receipt values and native enforcement, and receipts for another class reject. The 128-byte minimum result budget is the smallest admitted result. Mutation and failure receipts must fit it, retaining resource identity through the correlated intent rather than repeating a long path; Guard failure receipts contain only compiled stage labels. An applied mutation with a lost completion stays uncertain; receipt overflow cannot turn it into an ordinary retryable failure.

Search follows the controls of [Claude Code's Grep](https://code.claude.com/docs/en/tools-reference#grep-tool-behavior) and [OpenCode's grep](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/grep.ts#L13-L33) within one UTF-8 line of a named regular file or a directory under selected roots, in process and without a subprocess. The call is `{path, query, regex, include, case_sensitive, offset, limit}`: `path` and `query` are required, and native schemas expose the rest as required nullable fields whose null or omitted values default to `regex: false`, `include: null`, `case_sensitive: true`, `offset: 0` and `limit: 100`. Defaults are canonical before intent hashing and hook comparison, and a stored intent omits default options. `query` is 1–512 UTF-8 bytes, literal unless `regex` is true; regex mode uses Rust regex syntax without look-around or backreferences, `case_sensitive: false` uses Unicode case folding, and inline flags keep Rust semantics. `include` (1–512 bytes) filters paths relative to a directory `path`, or a named file's basename: `*` and `?` stay within a segment, `**` must be a whole segment (`**/` spans zero or more directories, a terminal `**` the rest of the path), and single-level `{a,b}` groups supply at most 16 alternatives in total; classes, escapes, negation, absolute or home prefixes, controls, empty, `.` or `..` segments and malformed or single-alternative braces reject, as [Glob](#glob-file-discovery) does through the same matcher. Unlike the peers' ripgrep globs, separator-free `*.rs` matches only the directory's own files (`**/*.rs` matches any depth), keeping one closed discovery grammar in which `*` never crosses `/`. Query and glob compile once per call with a 128 KiB compiled-size limit, 32 KiB DFA cache and nesting 32, the glob translation being at most 8 KiB; each line takes one boolean match, so matching stays linear in scanned bytes. An invalid, unsupported or over-limit pattern records attested `Failed`, in the Workspace and the WorkerView alike, with `Search pattern refused: <cause>; nothing was read` before any content is read, naming the regex syntax, regex size, glob syntax or glob limits, so the model can correct it as after a peer's Grep error; it never falls back to literal matching. A `limit` outside 1–100, an `offset` above 33,554,432 or an empty include rejects at decoding.

Authorization, protected names, ignored whole-project directories and scope apply before the filter, and an excluded file is never read. Rows are `{path, line, text}` with one-based line numbers and previews cut to 512 characters, ordered by Workspace-relative path in UTF-8 byte order and then line, independent of host locale. `offset` skips matching rows; at most `limit` rows plus one lookahead match are held, and skipped rows are never retained. The result is `{entries, limit, may_be_truncated, next_offset}`: `next_offset` is the requested offset plus the rows returned when another matching row exists, otherwise null, and `may_be_truncated` is true exactly when it is non-null. Fitting to the rendered budget drops only trailing rows and resumes at the first dropped one; matches with no fitting row record Limit, and an offset past the last match returns empty entries with null `next_offset`. Each page is a fresh bounded read, not a snapshot across calls; replay uses the committed observation. A timed-out scan stops at its next line. The WorkerView applies the same matcher and paging to its private image. Whole-project trust preserves this for named files; directory enumeration never reads file contents. Search supplies no edit preconditions; use an `@` include's SHA-256 or a successful Read. No-follow checks, protected paths and scan, input and result bounds apply to both forms.

The pinned Tool catalog supplies the host clock in Unix milliseconds with an explicit UTC basis, so a current-date task does not depend on historical dates or a shell command. It grants no authority.

The [execution contract](./execution.md#accepted-outcomes) owns strict native-function and structured-text selection and rejection. Tool field descriptions explain nullable line-based Read paging and that Edit `old` must be non-empty exact text excluding Read line-number prefixes; typed validation and the Guard enforce limits. Descriptions are generation guidance, not permission or a live-model completion guarantee.

The primary completes file actions through correlated Tool continuations in planning and synthesis. A read needed for an edit is a Tool proposal in the same Run, not a request for the user to supply a result. Delegated researcher children inspect with read-only Tools; the primary performs edits and verifies its own evidence. `@` file references add bounded include snapshots labeled with their escaped relative path and the SHA-256 of the actual bytes; metadata counts toward the context budget. Trailing-slash directory references identify where to inspect without reading a directory as a file or granting access.

Native adapters present the bounded catalog and JSON outputs as structured task data, with ordered call, disposition and output observations rather than internal intents and receipts. Each observation carries a workspace-effect fact: inspection and disposable commands have none, attested successful mutations are applied, uncertain or cancelled mutations remain uncertain, and other mutations are not confirmed. Historical Tool context remains distinct untrusted data; the full intent, limits and Guard receipt remain canonical. Plain or malformed-JSON output stays an untrusted string. No result or catalog becomes instructions or authority, and inspecting a file produces no edit receipt. This representation improves model input, not a guarantee of live task completion. The primary Tool set never changes within a Run.

Native file writes use digest or create preconditions, no-follow handles and a fresh inode plus atomic replacement, never in-place truncation of an aliased inode. Parent directories must already exist; a missing Write or Mkdir parent records attested `Failed` with `Parent directory not found; create it with Mkdir first`. A missing Edit or MultiEdit target uses the [in-process read not-found result](#in-process-reads). Symlinks, hard links, special files and stale preconditions reject. This is not a transaction against concurrent host edits, a rollback guarantee, or protection from a hostile same-user or root process.

Except for the typed [`guard_bootstrap` continuation](#enforcement-failure-causes), Guard preparation, bootstrap or attestation failures before the GO dispatch gate record Failed without a receipt and stop the Run without another model call; strict replay rejects continuation or a successful answer after that failure, because nothing was dispatched. An attested ordinary Failed result may continue; Engine continuation and strict replay share this stopping rule. Beginning the GO write makes a subsequent missing completion conservatively uncertain, including a partial write. No unconfined fallback exists. Historical failures are previous-Run facts, not pending Tools; a fresh request may inspect current files and propose a newly authorized edit with fresh preconditions, never reusing a previous intent or approval.

The internal Guard task is one newline-delimited JSON frame of at most 1 MiB before its delimiter, enough for the largest Write, Edit or MultiEdit intent with its pinned configuration; the definition-only extension is described under [parser admission](#agent-definition-parser-admission), and [worker bulk bytes](#private-worker-targets-and-handover-transfer) use a separate bounded phase. Missing delimiters, oversized frames and malformed tasks reject before Ready or effects; the exact capacity remains admissible. Worker and supervisor reject trailing buffered input, including a valid GO coalesced with the task, before Ready. GO remains a separate one-use exchange.

Before review or dispatch the Engine commits an immutable `ToolStarted` intent. Before inferring again it commits the correlated bounded `ToolFinished` observation. An interrupted or uncertain effect stops the loop without automatic retry; inspect `arany show --output text SESSION_ID`, the private JSONL export and the actual files before intentionally retrying. Replay, resume, fork and compaction carry past Tool facts only as untrusted context and never execute an old intent or renew permission. JSONL is an explicit sensitive-data export.

The [execution admission contract](./execution.md#admission-persistence-and-recovery) owns complete-topology Event headroom, ancestor locking, compaction and fork quotas and pre-disclosure rejection. Logical headroom does not reserve physical disk or eliminate crash or disk-fault uncertainty after dispatch.

## macOS enforcement and compatibility

Ambient Seatbelt traversal metadata grants name only required roots and exact
ancestors; ancestors grant no directory data. Selected resources retain their
scoped read grants. The spawning command profile retains a
literal `/` directory read for the native loader, exposing top-level names
without access beneath them. Search-only ancestor handles preserve no-follow
path admission without granting ancestor listings. The file-profile and native
unit corpora own unselected-metadata and ancestor/control-root listing refusal.

Private worker commands use this spawning profile and capture the reconstructed tree only after coalition cleanup, before volume detachment. Native Tool dispatch requires an available Background launchd user domain, a distinct kernel resource coalition, a trusted bounded supervisor and a separate attested Seatbelt worker. The private control directory lies outside the Workspace; overlap rejects before dispatch. The supervisor's launchd PID and authenticated local peer must identify the same process. The controller accepts completion only after the owned coalition is empty and the one-use job is removed or positively reported absent; automatic job retirement alone is not descendant cleanup. There is no unsandboxed fallback. Typed Git reads use a third Seatbelt profile that may spawn only the pinned Command Line Tools Git, with no command catalogue, runtime grants, network or Mach service lookup. The file and Skill worker stays non-spawning; commands and MCP keep ordinary child launches.

Before Tools are offered, admission validates the immutable `launchctl`, `env` and `hdiutil` executables through the same no-follow OS-program admission, then coalition observation and the user's launchd domain (a data-free probe with a three-second deadline and one second for kill and reap). Unit authentication, coalition ownership, storage preparation and installed enforcement remain mandatory before GO; startup availability is not dispatch attestation. Controller connection and preparation deadlines name their stage; native-manager command failures name that boundary without exposing native diagnostics. Cleanup failures retain their own stage and still prevent acceptance. After an effect, supervisor process stop, launcher reap, stderr EOF and storage-cleanup retries share one ten-second teardown bound (the MCP server reap and stderr drain share a second, equal bound inside the worker), member enumeration that fails while a process exits is retried within it, and storage cleanup makes at most eight attempts with pauses growing by 250 ms, starting and pausing only while time remains, so a transiently unlistable disk-image inventory is retried within the bound; a path-less inventory entry still rejects. A device that leaves the inventory between an attempt's listing and its detach re-check is never detached; the attempt is retried, and only a later attempt's fresh inventory and mount checks can accept. A storage-cleanup attempt already running keeps each native disk-image command's own bound, so teardown can outlast the shared bound; the controller's completion deadline then ends the call Uncertain. Only observed termination and detachment accept; exhausting the bound leaves the call Uncertain. The worker names a failed teardown step with a closed stage (process cleanup, launcher reap, output EOF or storage cleanup) in its final line, which the controller reports as the Guard stage; no worker text reaches the model. A storage-cleanup failure also names the failed check (inspection, listing unavailable, device unlisted before detach, detach failed, image still listed or mount still present), which in product builds only the debug development log records; test-support builds also keep it per Tool intent for release test assertions. A macOS execution failure after dispatch names its check the same way (worker closed before its report, worker panicked, malformed report, unattested report, report not followed by end of stream, cancelled or controller thread failed); the model-facing stage stays execution. The supervisor's stdout and stderr go to one owner-only output file in the unit root, discarded with it. Its only output is panic text, which its panic hook writes up to 4 KiB in total and drops beyond that; the runtime's fixed fatal-abort lines are the only other writes. When the worker closes early, the controller reads at most the file's last 4 KiB, classifies a panic, and keeps the printable tail for the debug development log and test recorder only. Privileged OS mutation remains outside the current-user boundary.

Supervision uses kernel process identity and cumulative CPU accounting across exec. Reaped or replaced members retire after identity revalidation, including when sampling fails during exit; missing observation of a live member still rejects. Exact-incarnation signaling must not affect a reused PID.

Private storage allocates separate owner-only, writable native filesystems sized from the immutable intent: scratch 64 MiB; the project volume 64 MiB by default, up to 1 GiB for Build; and the cache view, which has its own checked effective capacity. These volumes are distinct, and enlarging one enlarges no Workspace bound. Admission reserves the exact backing sizes and rejects before GO if they do not fit shared capacity. Each unit's root is `/private/tmp/arany-u-<uuid>`; the live unit creates and locks `unit.lock` in one exclusive open, which the kernel releases when the controller exits, including on a crash. Before launching its job, the controller durably records the root's device, inode and macOS boot identity; the supervisor durably records its process and coalition identity before receiving a task, and no payload or attachment may precede this record. Normal completion, partial setup, cancellation and unwind require positively established process termination before detachment. Unexpected mount targets reject without being followed. Unfinished attachment or failed cleanup retains the control root and rejects completion rather than recursively deleting through a live or uncertain mount. Each volume is a fixed-size, case-sensitive image attached kernel-only, so a payload sees a case-sensitive filesystem even on a case-insensitive host.

Before creating a unit, admission scans at most 4096 directory entries and attempts recovery of at most eight unlocked roots owned by the effective uid, within one 30-second recovery deadline. Recovery takes an exclusive lock and validates private no-follow records and root identity before cleanup; live controllers and competing recovery owners are excluded. Within the recorded boot, recovery removes the exact one-use job and positively empties its recorded coalition by current audit-token identities. After reboot it never signals persisted identities or removes a job from the later boot. Storage cleanup requires the pinned backing image inode, the OS disk-image inventory and exact device and mount correspondence; unexpected or nested mount targets reject before detachment, and an attached but unmounted owned image must be detached. An interrupted-attachment marker clears only after positive absence following detachment of the positively identified image, or evidence that its recorded boot ended; empty inventory alone cannot settle a current-boot attachment. Recovery durably records positive observation before detachment. Root deletion also requires absence of all mounts beneath the checked root. Unlocked roots without valid ownership records, including older retained roots, stay untouched and count toward shared capacity with live and recovering roots, including roots interrupted before lock publication. Valid records are selected before the eight-attempt budget is spent. Unreadable or over-limit listings and deadline expiry reject as unavailable native protection without removal advice. A filename prefix never authorizes cleanup, and there is no stored-format migration. Cancellation or failure leaves recoverable records in place and never retries an old Tool intent.

Commands and MCP receive a fresh checked snapshot of the selected Workspace, including prior typed edits, and a separate read-only tree of pinned runtime resources. Writable project and scratch mounts prohibit set-ID behavior. Reviewed system executables must be immutable, root-owned, non-set-ID and unentitled; privileged process, credential and coalition changes stay denied after exec. When a grant enables commands or MCP, admission checks the bounded system-executable catalogue once per Run, and each process intent and receipt binds it to the compiled policy. Workers revalidate its no-follow identities, ownership, permissions, size and modification or change timestamps before Ready; changed or oversized catalogues reject before dispatch without refresh or retry. The catalogue is transient trusted-controller data within the Task byte cap; file and Skill workers carry none. An undetermined signature result excludes that program for that admission only. The runtime excludes host account and Session roots, network destinations and Mach services. Root or mismatched real and effective identities reject process dispatch. Ordinary unprivileged `fork`, `exec` and `posix_spawn` remain available. Unselected host paths have no general metadata grant; traversal ancestors such as `/private/tmp` and the unit control root grant metadata without listings, and admitted runtime directories stay readable. Commands also read the literal filesystem root because the native loader opens it, which lists top-level names without granting access beneath them. Exact runtime metadata covers native shell selection and system path aliases; it grants no subtree access to host account or temporary storage.

macOS uses private physical paths rather than a mount namespace. The command's working directory lies inside its project snapshot. Standalone argv paths rooted at `/workspace`, `/scratch`, `/cache`, `/inputs`, `/skills` or `/programs` map into private storage, and copied-program aliases apply to copied executables. Shell strings are not rewritten for Workspace aliases; scripts use `ARANY_TOOL_WORKSPACE`, `ARANY_TOOL_INPUTS`, `ARANY_TOOL_SKILLS` or project-relative paths. One narrow compatibility prefix is added only when the resolved executable is the pinned `/bin/sh` and argv begins with `-c`: it exports the fixed, quote-escaped page-size helper path before the original script and preserves the remaining argv. A missing script or an argument beginning with `-` or `+` immediately after `-c` rejects before the shell starts; the Guard never rewrites an option into script text or skips the required prefix. It does not expand Workspace aliases inside the script. `HOME` and `TMPDIR` point to private scratch. Checked system binaries execute at their original paths because native relocation is not universally supported.

The macOS command environment is cleared and adds `CURL_SSL_BACKEND=Secure-Transport` only when a Rust toolchain profile is selected, because Cargo's libcurl otherwise initializes LibreSSL, which reads `/private/etc/ssl` and fails under Seatbelt; `SDKROOT` is set only when the exact physical Apple SDK profile is selected. The Guard stages the embedded page-size compatibility dylib in its private runtime resources, reads it without following links under a 128 KiB cap, and compares it with the exact embedded bytes before dispatch. The helper is a universal library with arm64, arm64e and x86_64 slices, so guarded children of any of those architectures load it. Those bytes and their source are bound into the enforcement digest. The shim answers only libc `sysconf(_SC_PAGESIZE)` and `getpagesize()` from the public `vm_page_size` value; it forwards other `sysconf` requests. Kernel sysctl calls and other sysctl metadata remain denied, with no Seatbelt exception. Host CPU discovery also stays denied; use an explicit positive `--jobs` value for guarded Cargo builds to avoid that discovery. SIP can strip `DYLD_INSERT_LIBRARIES` when the pinned system shell starts, so its fixed `-c` prefix re-exports the value for child tools. A nested SIP-protected shell can strip it again; page-size compatibility is not claimed inside such a nested shell.

On macOS, absolute traversal opens intermediate directories with search-only descriptors and only the selected final directory readably, because a readable ancestor would expose sibling listings.

Canonicalized selected roots reject strict descendant targets in the `getfsstat` mount table before Seatbelt and before Ready/GO. This is a point-in-time check, not a lifetime guarantee.

Non-spawning file and Skill workers reset and unblock `SIGXCPU` and install hard CPU expiry before Seatbelt prohibits changes; commands and MCP rely on external CPU supervision. Denial is attested before GO, so no payload runs under a partially installed profile. The profile denies sysctl access, named socket creation, network operations and descriptor-bearing messages. Inherited bootstrap ports are cleared before payload exec, and `NOSUID` alone does not strip signed entitlements.

System executables are revalidated per catalogue entry through no-follow handles (root ownership, non-writable and non-set-ID mode, device and inode, size and timestamps) opened relative to pinned `/bin` and `/usr/bin` handles. A signature verdict is reused only for the same path and an identical metadata stamp, and is never persisted.

Unit membership is observed through bounded kernel metadata, never process arguments or environments. Memory is measured as aggregate physical footprint plus live thread count; resident size omits compressed and swapped pages, so a missing live observation fails closed. Cleanup requires an exact-target `bootout` that succeeds or reports absence, then positive emptiness, even after one-use retirement.

Cleanup terminates and positively empties the payload coalition before detaching either disk image, including during preparation unwinds. It never removes a mounted or uncertain control root and never sweeps roots by filename prefix; deletion needs positive ownership and device or mount evidence. The unfinished-attachment marker is created immediately before attachment, after image creation and validation, and backing image inodes are pinned before attachment.

Debug builds with an explicit account root and `ARANY_TEST_GUARD_TRACE` may record Guard stage snapshots for fixtures: one fixed record per compiled stage, at most 128 bytes each and 8 KiB in aggregate, each `active`, `complete` or `interrupted`. Repeated observations overwrite their stage, so the trace is a snapshot, not a log. Capture failures never change Tool outcomes, and records never reach Events, Provider context, telemetry or the development log.

## Shared native capacity and settings

Linux and macOS coordinate Guard capacity across processes and Session roots through the effective user's fixed account root. The owner-only file `guard/limits.json` is created on first native admission with:

```json
{"version":1,"units":8,"queued":32}
```

Edit that private file to change capacity; preserve mode `0600` and the private directory. On macOS the fixed account root is `~/Library/Application Support/dev.Arany.arany`; on Linux it is `~/.local/state/arany`, resolved from the effective user's account rather than environment-selected Session storage. `units` accepts 1–64 and `queued` accepts 1–1024. Unknown fields or versions, unsafe files and invalid ranges reject admission. Every admission rereads settings. Lowering a limit never kills admitted units or registered waiters; no new admission exceeds the selected limit, so existing usage may temporarily exceed a lowered value.

Every Guard unit, including file-only units, reserves one slot before native launch. Live, recovering and retained units count. macOS admission also reserves the exact bounded backing-volume sizes of the immutable intent; a per-Goal maximum does not guarantee that all units can run at that maximum concurrently. Existing excess roots from a previous implementation are retained and prevent further admission. Linux's per-unit mount and cgroup limits are unchanged, and its slot owns the host seed until checked deletion. Each seed holds at most 32 MiB of selected Workspace data and 96 MiB of runtime data, bounding newly admitted retained payload at `units × 128 MiB` (1 GiB by default). This is a logical payload bound, not a physical filesystem quota; directory, file-count and record bounds apply separately. Historical unrecorded seeds require the maintenance procedure below.

When capacity is occupied, the approved Tool remains pending in its Run. Up to `queued` Tools register in one shared FIFO ordered by registration under the namespace lock; newcomers cannot overtake registered waiters. Cancellation, a finite capacity deadline and process death remove a participant's position. The capacity deadline starts at post-approval queue entry and is bounded by the pinned runtime allowance; it is a capacity refusal, never a human rejection. Once admitted, native preparation and GO have their own deadlines, so on both Linux and macOS a short command timeout is not refused when preparation outlasts it. Linux still reaches GO within its five-second preparation deadline, and macOS within its worker preparation bound. Overflow rejects before effects. Waiting never renews an intent, approval or Run budget, is not a durable queue, and restart never resumes old permissions. There is one pending Tool per Run. The [terminal contract](./terminal.md#conversation-progress-and-history) owns the temporary queued indication. Native recovery keeps its 30-second deadline within the post-approval capacity window; local filesystem bounds remain cooperative, not hard-real-time guarantees.

Coordination records are no-follow, owner-checked, mode-checked, ACL-checked, single-link and bounded. Coordination creates no database or history records, and admission never creates canonical Events; wait hints use the existing callback. Reaping in `Drop` never bypasses the attempt and deadline budget. Preparing without a committed identity authorizes only removal of an empty directory. macOS control roots count against capacity independently of reservations, with UUIDs deduplicated.

### Linux host seed ownership

Every new host seed retains its reservation from creation until checked deletion. Normal completion leaves no seed or stale reservation. After controller death, the next admission recovers owned storage before releasing capacity, without replaying the effect. Failed deletion, identity uncertainty and ambiguous native launch keep the charge. A new boot settles old processes but not file deletion. Recovery resets a positively identified failed unit before retirement; a missing or not-loaded unit cannot settle an interrupted launch, so that reservation can exhaust capacity until positive native evidence or a later boot permits recovery. Linux reservations use version 2; macOS remains version 1. A locked lease owns one bounded seed record and at most one publication temporary; the planned location is committed before exclusive creation and the directory identity before copying payload. A dead preparation without a committed identity permits only empty-directory removal. Launch-requested precedes launcher invocation, and positive native termination precedes recursive deletion. Deletion rejects links, mounts, foreign ownership, unsafe permissions and replacements; incomplete cleanup retains its slot and prevents completion. Historical unrecorded roots need the [one-time maintenance procedure](../tools.md#historical-linux-seed-maintenance), with Arany stopped, positive native inactivity and authorization of exact inventoried objects; reboot is the fallback for uncertain inactivity. A name prefix never authorizes removal, and normal admission neither migrates nor deletes unsupported records.

## Linux enforcement and compatibility

The first enforcer requires installed non-set-ID, root-owned `/usr/bin/bwrap`, `/usr/bin/unshare`, `/usr/bin/systemd-run`, `/usr/bin/systemctl` and `/usr/bin/env`, working unprivileged user namespaces, a systemd user manager and cgroup v2 with effective memory, swap, PID and CPU limits and owned cgroup termination. `systemd-run` must support `--expand-environment=no`; installation alone does not establish compatible launch capabilities. A fixed `/usr/bin/unshare --user --map-current-user --mount --propagation private` bootstrap runs before the unchanged Bubblewrap command, without `--keep-caps`: util-linux establishes private propagation before exec, while retained capabilities make Bubblewrap reject a non-root real UID. Before Ready and again after GO, the helper parses its bounded namespace-local `/proc/self/mountinfo` and rejects ambiguous roots, stacked or missing runtime mounts, propagation metadata and any descendant mount beneath a selected runtime mount, so a later host mount cannot propagate into an admitted runtime. Read-only binds import source submounts recursively, so admitted mount sources are checked with that import in mind. This is a kernel and native-capability contract, not a GNOME or KDE dependency. Other Linux init systems need a separately enforcing adapter. Unsupported architecture or missing enforcement fails closed, with no unsandboxed fallback. macOS uses the separate native profiles described above.

Private worker commands reconstruct their image on the fresh project tmpfs after GO and reap payload descendants before private capture. The Guard verifies isolated mount, network, PID, user, IPC and UTS namespaces, dropped capabilities, no-new-privileges, inherited syscall filters and effective limits before releasing a one-use intent. It owns the exact transient unit, invocation and retained cgroup identity, including double-fork and setsid descendants, and verifies termination before accepting completion. Garbage collection of transient units relies on the retained group's empty or removed state. The compiled seccomp deny profile is defense in depth, not a universal syscall allowlist. ARM64's profile is source-supported; native runner evidence is required before claiming platform support.

Byte and entry bounds on synchronous snapshot preparation do not guarantee a finite response from stalled host storage or an uninterruptible kernel operation. Process deadlines and cleanup bound ordinary payload execution; they are not hard-real-time or kernel-failure guarantees. Native file preconditions do not make a multi-file transaction or exclude concurrent hostile host mutation.

# Beta procedural-macro source review

Status: **current selected-entrypoint source review; release gate open**. The [locked normal-plus-build target inventory](./beta-dependency-inventory.md) selects 24 procedural-macro packages on Linux and 18 on each macOS target. Intersecting `cargo tree`'s selected identities with `cargo metadata`'s proc-macro targets reconciles the prior 23/17 review: `paste 1.0.15` left, while `derive_more-impl 2.1.1` and `document-features 0.2.12` entered. The latter two entrypoints and their selected invocations were inspected in cached published sources; this is not expanded-code or artifact clearance. Both macOS architecture selections match. Versions are fixed by [Cargo.lock](../../Cargo.lock); the linked upstream source revisions are those recorded in each cached published package's `.cargo_vcs_info.json`, not substitutes for the lockfile's registry checksums. Cargo's [Rust Reference](https://doc.rust-lang.org/reference/procedural-macros.html) explains why these macros execute with compiler-host file and I/O access during compilation.

## Build-host authority observed

Of the 24 selected macro packages, `rustversion` declares a custom-build target; neither newly selected macro package nor the six Linux-only credential additions has a `build.rs`. [`rustversion/build/build.rs`](https://github.com/dtolnay/rustversion/blob/3a7c76605450b9a7299c6502a421909de9126a59/build/build.rs#L19-L107) reads `RUSTC`, `RUSTC_WRAPPER`, `OUT_DIR`, and `HOST`; runs the compiler or wrapper with `--version`; writes `version.expr` under `OUT_DIR`; and emits `cfg` lines. The latter makes compiler/wrapper provenance and the generated version expression part of the build input. Cargo documents build scripts as host executables whose stdout can [control compilation](https://doc.rust-lang.org/cargo/reference/build-scripts.html#outputs-of-the-build-script).

Four macro crates read the build environment directly. [`clap_derive`](https://github.com/clap-rs/clap/blob/13f2db5072d600c11d8d6298e4e9ba53ffc6c1ab/clap_derive/src/item.rs#L1269-L1306) reads `CARGO_PKG_DESCRIPTION`, `CARGO_PKG_AUTHORS`, and `CARGO_PKG_VERSION` when those derive attributes are requested; its [`Parser` derive](https://github.com/clap-rs/clap/blob/13f2db5072d600c11d8d6298e4e9ba53ffc6c1ab/clap_derive/src/derives/parser.rs#L27-L42) also reads `CARGO_PKG_NAME`. The newly selected [`document-features`](https://docs.rs/crate/document-features/0.2.12/source/lib.rs) macro reads `CARGO_MANIFEST_DIR` and the invoked package's `Cargo.toml`, with a `Cargo.toml.orig` fallback; the selected invocation is in Crossterm's crate documentation, not Arany's source. [`strum_macros`](https://docs.rs/crate/strum_macros/0.28.0/source/src/lib.rs) reads `STRUM_DEBUG` and can print generated tokens into build output. [`rustversion`](https://github.com/dtolnay/rustversion/blob/3a7c76605450b9a7299c6502a421909de9126a59/src/time.rs#L15-L34) also reads `CARGO_PKG_NAME` and wall-clock time; the observed callers use the date in [parse diagnostics](https://github.com/dtolnay/rustversion/blob/3a7c76605450b9a7299c6502a421909de9126a59/src/bound.rs#L27-L29), not in emitted code.

The two Zbus-family macro crates can call `proc-macro-crate::crate_name` to choose generated crate paths. [`zbus_macros::zbus_path`](https://github.com/z-galaxy/zbus/blob/7518d73db4dbf830ec1c9c43865bf8aeae9a8ffd/zbus_macros/src/utils.rs#L17-L26) does so when no explicit crate path is supplied; [`zvariant_derive::config`](https://github.com/z-galaxy/zbus/blob/0f4db6980bc1566278618a46c9ffa7f5f025c18a/zvariant_derive/src/utils.rs#L8-L25) builds its default path by trying `zvariant`, then `zbus`. The locked [`proc-macro-crate 3.5.0` helper](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L173-L216) reads `CARGO_MANIFEST_DIR/Cargo.toml` and, on its initial cache entry, seeks a workspace manifest. If `CARGO` is set, that lookup [launches `Command::new(cargo)`](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L241-L264) with `locate-project --workspace --message-format=plain --manifest-path=...`; it consumes stdout without testing the child's exit status. It then [reads and parses the selected manifests](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L280-L307), and also reads [`CARGO_TARGET_TMPDIR`](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L343-L355) when resolving the generated crate path. Rust's [`Command::new` contract](https://doc.rust-lang.org/std/process/struct.Command.html#method.new) inherits the host environment and working directory and searches `PATH` for a non-absolute program. This is conditional compiler-host file/process authority in a transitive helper, not runtime D-Bus communication or proof that an ambient `CARGO` override reaches a normal Cargo build.

A clean offline Linux `cargo check --locked -p zbus` with an inherited `CARGO` pointing at a test-owned executable completed after compiling `zbus_macros` and `zvariant_derive`; the executable's unique stderr marker did not appear. This bounded probe neither records the effective `CARGO` value inside expansion nor proves an override can execute through normal Cargo. Cargo's [environment reference](https://doc.rust-lang.org/cargo/reference/environment-variables.html) says that an incoming `CARGO` value is forwarded to crate builds and build scripts instead of Cargo's detected path, and lists `CARGO` among variables supplied during crate compilation; that documented contract does not by itself attest this build's proc-macro environment. The current [release script](../../scripts/release-build.sh) guards selected native-data overrides but does not pin or record the effective compiler, wrapper, `CARGO` executable, `PATH`, manifest digests, or compiler-host child processes. Exact release-build identities and child launches remain to be observed.

A further controlled Linux dev-profile build used a test-owned `RUSTC_WRAPPER` that reported only the `CARGO` value passed to compiler invocations for `zvariant_derive`, `zvariant`, `zbus_macros`, and `zbus`. All observed `/usr/bin/cargo`. Recompiling `zbus` with the parent `CARGO` set to a nonexistent test path still passed `/usr/bin/cargo` to those compiler invocations and completed successfully. This narrows the ambient-override concern for these observed Cargo builds: the macro-expanding compiler did not inherit that parent value. It does not trace whether `proc-macro-crate` actually launched `locate-project`, attest `/usr/bin/cargo` or the compiler binary, reproduce Arany's guarded release features, or prove native macOS behavior.

A subsequent controlled Linux dev-profile build injected a test-owned `CARGO` shim through `RUSTC_WRAPPER` into the macro-expanding compiler and recompiled locked `secret-service 5.2.0` offline. The shim delegated to absolute `/usr/bin/cargo` and recorded two child invocations, each with `locate-project --workspace --message-format=plain --manifest-path=<secret-service 5.2.0 Cargo.toml>`; compilation succeeded. This proves that the selected Zbus-family expansion can exercise the child-process path for this package build. The shim's stderr marker was not visible because the helper uses `Command::output`, which captures child stderr; the earlier missing marker was not negative evidence. This probe does not attest the unwrapped executable, the release-feature build, any other selected expansion, or macOS.

The exact [helper cache path](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L173-L307) narrows that process question: after statting `CARGO_MANIFEST_DIR/Cargo.toml`, the first `crate_name` lookup for that directory attempts the child only if `CARGO` is present as UTF-8; a cache hit reuses the workspace path, even when changed manifest timestamps trigger a reparse. A failed workspace lookup can retry because it never populates the cache. The arguments are exactly `locate-project --workspace --message-format=plain --manifest-path=<package Cargo.toml>`; [Cargo defines](https://doc.rust-lang.org/cargo/commands/cargo-locate-project.html) `--workspace` as selecting the workspace-root manifest. The helper accepts trimmed UTF-8 stdout as that path without checking exit status, falls back to the package manifest on empty stdout, and [parses](https://github.com/bkchr/proc-macro-crate/blob/8f3d8b04539f732e09c07907f138a248c8d0eed9/src/lib.rs#L303-L405) package name, ordinary and target-specific dependencies and dev-dependencies, and workspace dependencies from those manifests. The [Zbus helper](https://github.com/z-galaxy/zbus/blob/7518d73db4dbf830ec1c9c43865bf8aeae9a8ffd/zbus_macros/src/utils.rs#L17-L26) skips this lookup for an explicit crate path; [Zvariant's configuration](https://github.com/z-galaxy/zbus/blob/0f4db6980bc1566278618a46c9ffa7f5f025c18a/zvariant_derive/src/utils.rs#L8-L25) tries `zvariant` and then `zbus`. A wrapper observing `CARGO` only proves the compiler input; a test-owned child shim recording those arguments would prove this path executed in that build, but not the identities or behavior of an unobserved release build.

The six Linux-only credential macro sources showed no explicit network client, dynamic-library loader, or arbitrary file read/write call beyond static documentation includes; `rustversion`'s build script has the `OUT_DIR` write described above. This is **not** a claim that compiler-host execution is sandboxed or that all transitive macro dependencies are inert. Source review also found generated `unsafe` in [`enumflags2_derive`](https://github.com/meithecatte/enumflags2/blob/332c37f47577e5f6b7104419da7e761963032086/enumflags_derive/src/lib.rs#L334-L350), [`futures-macro`](https://github.com/rust-lang/futures-rs/blob/705e6b5c0f06535b1aac1cb1989a172b3d45be8c/futures-macro/src/join.rs#L41), [`yoke-derive`](https://github.com/unicode-org/icu4x/blob/a59ab860d4bda548e94dfbf992d87fe1f761bc55/utils/yoke/derive/src/lib.rs#L218-L240), and [`zerovec-derive`](https://github.com/unicode-org/icu4x/blob/898d79c69f37da7b45a15a5714663c9b59b3d928/utils/zerovec/derive/src/ule.rs#L58-L65). These are generated-code invariant review targets, not evidence of build-host I/O or a demonstrated exploit.

The pinned Linux graph routes `enumflags2_derive` through `enumflags2` into `zbus` and `zvariant`; a search of those two selected source trees found three `#[bitflags]` invocations, all in `zbus 5.19.0`: [`message::Flags`](https://github.com/z-galaxy/zbus/blob/7518d73db4dbf830ec1c9c43865bf8aeae9a8ffd/zbus/src/message/header.rs#L88-L107), [`proxy::MethodFlags`](https://github.com/z-galaxy/zbus/blob/7518d73db4dbf830ec1c9c43865bf8aeae9a8ffd/zbus/src/proxy/mod.rs#L1032-L1061), and [`fdo::RequestNameFlags`](https://github.com/z-galaxy/zbus/blob/7518d73db4dbf830ec1c9c43865bf8aeae9a8ffd/zbus/src/fdo/dbus.rs#L24-L48). Each has an unsigned `repr` and explicit, distinct `1`, `2`, and `4` discriminants; the last names only those three flags in its default. The pinned macro [checks literal one-bit values and representation range](https://github.com/meithecatte/enumflags2/blob/332c37f47577e5f6b7104419da7e761963032086/enumflags_derive/src/lib.rs#L211-L239), then [emits `DEFAULT`/`ALL_BITS` as ORs and `bits` as a representation cast](https://github.com/meithecatte/enumflags2/blob/332c37f47577e5f6b7104419da7e761963032086/enumflags_derive/src/lib.rs#L334-L350). This source-only comparison supports the one-bit and declared-mask portions of [`RawBitFlags`' safety contract](https://github.com/meithecatte/enumflags2/blob/332c37f47577e5f6b7104419da7e761963032086/src/lib.rs#L304-L333) for these inputs. It does not independently prove the contract's `bits == transmute_copy` representation requirement, the exact expanded tokens, compiler behavior, or the release artifact; the other generated `unsafe` paths remain open.

One bounded expansion check was run on Linux with the installed Rust 1.98.1 host: `RUSTC_BOOTSTRAP=1 cargo rustc --locked --offline -p zbus --lib -- -Zunpretty=expanded`, filtering stdout with `rg -n -A 24 -B 2 'unsafe impl .*RawBitFlags for'`. It found exactly those three generated `unsafe impl`s. Their `Numeric` types were `u8`, `u8`, and `u32`; `DEFAULT` was zero, zero, and the OR of the three named flags; each `ALL_BITS` ORed those three flags; and each `bits(self)` cast to its matching numeric type. This is observed expanded-token evidence for a diagnostic `zbus` dev-profile package build, stronger than source-only inference. It is **not** the declared Rust 1.88 minimum-version build, Arany's unified-feature release build, an audited full expansion, a `transmute_copy` runtime check, or an artifact/host-executable attestation. `RUSTC_BOOTSTRAP` was used only to request diagnostic output and must not be a release-build input.

The selected `tracing-attributes` expansion is not an input to Arany's current OTLP exporter. The product's private [`Telemetry`](../../src/telemetry.rs) constructs spans directly through its own `SdkTracerProvider`; it installs no `tracing` subscriber or OpenTelemetry bridge, and the selected Linux normal/build graph contains neither `tracing-subscriber` nor `tracing-opentelemetry`. Thus dependency `#[instrument]` argument fields cannot enter Arany's current OTLP payload through a tracing bridge. This is only a route-specific source and dependency-graph conclusion, not a claim that arbitrary future subscribers, other logs, or expanded macro code are safe. Adding such a bridge would reopen the credential-field review before release.

## Decision and limits

No independent exploit was established among the reviewed selected entrypoints, so this pass does not create a new finding. Keep the supply-chain release gate open: the bounded diagnostic expansion does not attest the compiler/wrapper/`CARGO` executable identities, ambient build environment, manifest inputs, other expanded code, transitive dependency behavior, binary artifacts, or native macOS behavior. The GitHub revisions were not fetched separately; the inspected bytes were the locally cached published crate sources. A controlled release build must record the effective compiler-host executables and child launches, verify manifest inputs, inspect the exact release-feature expansions against their unsafe contracts, and inspect artifact provenance. Reopen generated tracing-field review if a subscriber or bridge is added. Re-run this review after a lockfile, feature, or target change.

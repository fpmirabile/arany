# ChatGPT-plan identity source review

Status: **first-party source and synthetic-fixture review; account activation remains blocked**. Reviewed on 2026-10-01 against the current [OpenAI registration guide](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) and [host-ID guidance](https://developers.openai.com/siwc/token-sharing-open-source). A bypass of signature, issuer, client, nonce, or selected-subject binding would be critical and release-blocking; none was demonstrated in this review. The activation gaps below block the subscription route, not the existing API-key route. This is not a live sign-in, an independent AWS-LC cryptographic audit, or evidence that a saved token is private from other same-user processes.

## Boundary reviewed

The protected assets are the issued client registration, verified account identity, and OAuth tokens. The browser callback, token response, and JWKS bytes are untrusted. [The callback owner](../../src/cli/chatgpt/callback.rs) admits one bounded loopback response only after exact Host, target, state, and callback-shape checks. [Code redemption](../../src/cli/chatgpt/exchange.rs) sends the original PKCE verifier, issued client ID, callback URI, and resource to the compiled HTTPS token endpoint with proxy, redirects, automatic decompression, and retry disabled. It fetches a bounded JWKS from the compiled issuer endpoint before publishing credentials.

[The identity validator](../../src/cli/chatgpt/identity.rs) accepts only a canonical, bounded three-segment token with an `RS256` header and one matching `kid` in a bounded JWKS. It verifies the signature with the selected RSA key before trusting claims, then requires the exact issuer, issued-client audience, attempt nonce, nonempty subject, expiration within five seconds of validity, and issuance/not-before times not in the future beyond five seconds. Returning authorization also compares the newly signed subject with the selected account; [the token response](../../src/cli/chatgpt/exchange.rs) must separately grant direct plan-use permission. This matches the guide's distinction between authenticated identity and permission to use a ChatGPT plan. The deliberately narrow algorithm set fails closed if OpenAI serves a different signing algorithm; the guide does not promise that `RS256` will remain the only one.

The synthetic RSA/JWKS and loopback corpus covers an accepted signed identity, altered signature/issuer/audience/nonce/time/subject, duplicate matching keys, a wrong key, excessive keys, wrong headers, returning-subject drift, missing permission, hostile token/JWKS transport, and the exact machine-readable spent-code response. The focused offline ChatGPT corpus passes with one explicitly ignored native connection-deadline gate. These cases establish local rejection behavior, not live issuer compatibility or all possible JSON/cryptographic parser states.

## Activation gaps found

1. The [OpenAI guide](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) says to retain the newly issued `client_id` before exchanging the authorization code, so a failed `invalid_grant` can restart authorization under the same registration. The private transaction now exposes that ID before consuming the code, recognizes only a bounded machine-readable `invalid_grant` response as an unusable code, and can construct a fresh retry attempt with the issued client and host ID. The future account owner must still durably retain this non-secret registration identity before redemption and connect the retry; otherwise a failed or interrupted exchange can lose it. Never retry the spent code or treat the callback client ID as verified account identity. This remains a recovery gap in the dormant path, not an active account-bypass finding.
2. [OpenAI's host guidance](https://developers.openai.com/siwc/token-sharing-open-source) requires a stable, opaque per-host ID before first sign-in and recommends UUIDv4 for the `urn:uuid:` form. `AuthorizationAttempt` currently receives a non-nil UUID from its caller; no product host-ID generator or durable owner is wired. A Session UUID must not silently stand in for the installation's host identity.
3. Account-scoped protected storage, refresh-token rotation under the approved cross-process lock, browser launch, model/effort conformance, live issuer-signature compatibility, and native macOS behavior are still absent. Do not enable setup or inference from this source review. A passing synthetic signature test does not establish the user's requested exclusive token access; the Linux Secret Service limitation remains [separately recorded](findings/linux-secret-service-client-isolation.md).

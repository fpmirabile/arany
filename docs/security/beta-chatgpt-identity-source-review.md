# ChatGPT-plan identity source review

Status: **source and signed-synthetic review; a user-reported live identity rejection remains undiagnosed**. Updated on 2026-10-03 against the [OpenAI registration guide](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [OpenID Connect validation rules](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) and current implementation. Account registration, storage, renewal, catalog and checked Runs are implemented; this review does not certify live compatibility. A bypass of signature, issuer, client, nonce or selected-subject binding would be critical; none is introduced by the consent controls, diagnostic categories or singleton-audience normalization. This is not an independent AWS-LC cryptographic audit or evidence of isolation from other same-user processes.

## Boundary reviewed

The protected assets are the issued client registration, verified account identity, and OAuth tokens. The browser callback, token response, and JWKS bytes are untrusted. [The callback owner](../../src/cli/chatgpt/callback.rs) admits one bounded loopback response only after exact Host, target, state, and callback-shape checks. [Code redemption](../../src/cli/chatgpt/exchange.rs) sends the original PKCE verifier, issued client ID, callback URI, and resource to the compiled HTTPS token endpoint with proxy, redirects, automatic decompression, and retry disabled. It fetches a bounded JWKS from the compiled issuer endpoint before publishing credentials.

[The identity validator](../../src/cli/chatgpt/identity.rs) accepts only a canonical, bounded three-segment token with an `RS256` header and one matching `kid` in a bounded JWKS. It verifies the signature with the selected RSA key before trusting claims, then requires the exact issuer, issued-client audience, attempt nonce, nonempty subject, expiration within five seconds of validity, and issuance/not-before times not in the future beyond five seconds. Returning authorization also compares the newly signed subject with the selected account; [the token response](../../src/cli/chatgpt/exchange.rs) must separately grant direct plan-use permission. This matches the guide's distinction between authenticated identity and permission to use a ChatGPT plan. The deliberately narrow algorithm set fails closed if OpenAI serves a different signing algorithm; the guide does not promise that `RS256` will remain the only one.

The audience is either a string or a one-element string array containing only the exact issued client. OpenID Connect permits array serialization but requires rejecting untrusted additional audiences; Arany trusts no extra audience, including a repeated client entry. A private streaming deserializer stores one string under the existing 8 KiB decoded-claims ceiling and rejects empty, non-string, nested or additional entries. A present `azp` must be a non-null string equal to the same client. Its absence is accepted. Both fields are parsed only after signature verification and their values never enter diagnostic output.

The existing synthetic RSA/JWKS and loopback corpus covers an accepted signed identity, altered signature/issuer/audience/nonce/time/subject, duplicate matching keys, a wrong key, excessive keys, wrong headers, returning-subject drift, missing permission, hostile token/JWKS transport, and the exact machine-readable spent-code response. The signed-identity owner additionally covers string/singleton acceptance, extra and malformed audience rejection, and present authorized-party binding; the code-redemption owner sends the exact grant and returns verified credentials for a signed singleton audience with matching authorized party. These cases establish local rejection behavior, not live issuer compatibility or all possible JSON/cryptographic parser states. Native credential-store and connection-deadline gates retain their separate scope.

## Current evidence and remaining checks

1. The private registration owner persists an OS-backed UUIDv4 host identity and the callback's issued client before redemption, with fresh PKCE/state/nonce on a spent-code restart. The account owner binds verified subject, issued client, host, backend and exact current consent receipt under its user-scoped lock. Existing synthetic owners cover those boundaries; callback metadata alone remains unauthenticated.
2. The user saw browser authorization and a permission email, followed by Arany's generic identity rejection. No user token or account was inspected. A credential-free read of the compiled issuer's public JWKS returned four RSA/RS256 keys with locally admissible sizes, ruling out only a globally unsupported published algorithm in that response. A signed synthetic singleton audience reproduced a local `ClaimsFormat` rejection before normalization; the corrected owner accepts that representation while retaining exact client binding and rejecting untrusted extra audiences. That defect is established, but neither the fixture nor public keys identify the user's failed token. Fixed typed rejection categories distinguish format, key selection/parameters, signature, claims and identity/time bindings without printing sensitive inputs. Final user retry must identify the remaining live category if rejection persists; it is not needed to implement the demonstrated local correction.
3. Back/Accept controls replace typed consent only after complete warning display. Back is the default, resize/resume resets review, insufficient inline geometry fails before OAuth, and linear mode announces the full text before named choices. Warning version 4 invalidates prior receipts for use until fresh consent/reconnect; it does not silently migrate a backend or preserve stale model evidence. Synthetic receipt and frame checks are distinct from real browser/OS-store usability.
4. Complete selected-backend lifecycle, live model/effort checks and a real Run remain final user-owned beta checks; native macOS belongs to the later host. Their absence does not pause implementation or count as a pass. The [Linux Secret Service same-user limitation](findings/linux-secret-service-client-isolation.md) remains explicit.

# Finding: interactive PTY loss can strand Arany's input reader

Status: **open; release-blocking for attached terminal availability**. Severity: **high for local availability**. This is not a claim of remote code execution or credential disclosure.

## Evidence and boundary

The selected `crossterm 0.29.0` Unix event backend is `event/source/unix/mio.rs` while the `use-dev-tty` feature is absent. Inside its TTY readiness loop, `Ok(0)` makes no progress and non-`WouldBlock`, non-`Interrupted` read errors are ignored. After a PTY master closes, the selected reader can therefore stay inside `event::poll` instead of returning an input error. [Upstream issue #1110](https://github.com/crossterm-rs/crossterm/issues/1110) independently identifies the ignored-error busy loop. Arany's sole interactive reader in [`src/terminal/input.rs`](../../../src/terminal/input.rs) cannot report the loss or join while that call remains stuck.

The Linux product-process regression in [`tests/session_run/active_terminal/acquisition.rs`](../../../tests/session_run/active_terminal/acquisition.rs) opens a real inline setup PTY, observes the live prompt, closes only its test-owned master, and requires the exact product to exit within five seconds. It fails with the selected default dependency features. Its matching screen-reader case, which uses Arany's separate canonical-line reader, passes. A second case in [`tests/session_run/active_terminal.rs`](../../../tests/session_run/active_terminal.rs) waits for an active synthetic Provider request before closing the PTY; the current backend leaves that request's socket open past a separate three-second observation deadline. An earlier abandoned product process had stdin/stdout/stderr linked to a deleted `/dev/pts/4`; its named terminal thread was runnable and accounted for about 85% lifetime CPU while its main thread slept. This process observation supports the failure mode but does not identify how every older orphan was created.

Loss of an SSH, tmux, IDE, or test-owned PTY is outside the Provider and Workspace trust boundaries but should not keep the attached process consuming CPU. The active test proves that the current product does not promptly cancel its local Provider socket after PTY loss; it does not prove how long a remote Provider would continue generating or billing. No credential or omitted Workspace input was observed in the terminal transcript. No pre-existing orphan has been terminated without the user's approval.

## Candidate and required verification

Cargo can temporarily enable `crossterm/use-dev-tty` without editing the manifest. With that feature, Crossterm's alternate Unix source uses the same stdin when it is a TTY and propagates read failures through its `filedescriptor` polling path. The idle lost-PTY regression passes in about 0.2 seconds; the active case exits in under a second, closes the synthetic Provider socket, and strictly replays one cancelled Run with no answer. All three focused lost-PTY tests pass in an optimized offline build. The two explicit Linux tmux release gates also pass at 20, 24, 40, 50, and 80 columns with color, `--no-color`, and `NO_COLOR`, including pane/client restoration and a retained multiline draft. The complete optimized offline workspace suite, earlier debug offline suite, and strict all-target Clippy pass with the temporary feature. The candidate has **not** been saved in `Cargo.toml`; ordinary test runs still include both failing regressions.

Enabling the feature would move locked `filedescriptor 0.8.3` into the runtime graph on Linux and macOS. It has an MIT declaration and no build script, but uses native FFI; its macOS polling path wraps `select` and rejects descriptors outside `FD_SETSIZE`. More importantly, Crossterm's alternate `tty.rs` source maps both a zero-byte read and `WouldBlock` to `Ok(0)`, then breaks only its inner read loop. If a lost macOS PTY presents readable EOF rather than an I/O error, the outer poll loop can keep returning without an input failure and Arany's reader can remain alive. Linux's passing PTY test observed the error path, so the feature alone is **not** an established cross-platform fix. Source and artifact review, an approved shared-dependency resolution, and native macOS terminal tests are still required.

The narrower source-level candidate is to keep the selected Mio backend and make its TTY loop return a typed input error on `Ok(0)` and on errors other than `WouldBlock` or `Interrupted`. This addresses both failure branches without adding `filedescriptor` to runtime. In a disposable copy of the pinned crate, a direct PTY probe hung for three seconds before the change and exited on input error after it. A separate disposable copy of Arany with a local Cargo override passed all three product-process lost-PTY cases, the full offline workspace suite, and strict all-target Clippy; the unmodified repository's focused run still fails its two inline cases. This is Linux evidence for the proposed source change, not an integrated or cross-platform fix.

A local override would enlarge the reviewed source and release-distribution surface. `cargo package --list` for the disposable Arany copy omits the patched dependency source even though its local test build selects it; a green package check would not by itself establish the patched release artifact. [The latest published Crossterm is still 0.29.0](https://docs.rs/crate/crossterm/latest) as checked on 2026-10-01, so no published upstream fix can be selected yet. The repository manifest and lockfile have not been changed. Approval, a verified distribution path, and native macOS PTY-loss proof remain mandatory.

Before closing this finding, keep both regressions active under the normal manifest, select a fix that distinguishes EOF from temporary absence of input on every supported backend, incorporate and review it, then rerun formatting, strict lint, the offline suite, package/release guards, and native idle and in-flight terminal-loss gates on both supported macOS architectures. Do not replace a stuck join with a detached spinning thread or silently treat lost terminal input as a submitted Message.

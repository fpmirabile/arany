# Finding: an opt-in OTLP response can outlive its declared request deadline

Status: **mitigated in source and verified by the Linux trickling-Collector gate; native macOS behavior remains a release gate**. Severity: **medium** (availability and telemetry loss, not a demonstrated secret leak). This audit defines a blocker as a selected reachable HTTP path that can send sensitive data or a credential to an unintended endpoint, or bypass a declared finite bound. A dormant-only path must be corrected before activation. The review makes no macOS runtime or live-Provider claim.

## Selected-path map

## Source-derived bound failure and correction

The former [`src/telemetry.rs`](../../../src/telemetry.rs) path gave `EXPORT_TIMEOUT = 500 ms` to a blocking Reqwest client and the OTLP exporter. In pinned `reqwest-0.13.5/src/blocking/client.rs:388-394,1497-1524`, this timeout is passed to the response; `src/blocking/response.rs:439-440` starts a fresh timeout around **each** `Read`. Pinned `opentelemetry-http-0.33.0/src/lib.rs:219-235` calls `read_to_end` on the response, capped at 4 MiB. Pinned `opentelemetry-otlp-0.33.0/src/retry.rs:103-130` awaits the whole HTTP operation and only then tests its exporter deadline. A local Collector sending a valid response a few bytes at a time, each interval shorter than 500 ms, could therefore occupy the sole export worker well past 500 ms without exceeding 4 MiB. The existing [stalled-Collector test](../../../src/telemetry/tests.rs) bounds the caller's shutdown wait, but does not exercise a continuing response trickle or establish a per-export deadline; SDK `opentelemetry_sdk-0.33.0/src/trace/span_processor.rs:929-962` can return from shutdown on timeout while the worker remains busy.

An explicitly activated, ignored Linux [trickle-response gate](../../../src/telemetry/tests.rs) sends a `200` response with one byte every 150 ms for up to three seconds, then requires a second queued trace request within two seconds. On the former blocking client it failed with `trickling response held the export worker`; with the private async adapter it passed in 1.05 seconds. The first attempt at that adapter panicked because the Reqwest future was created before entering Tokio; moving future creation inside the runtime fixed the observed regression. This gate observes the actual OTLP worker with a synthetic local Collector, without a real credential or Provider call. It does not establish an exact scheduler-independent maximum or macOS behavior.

The selected correction keeps the default bounded `BatchSpanProcessor`, whose dedicated thread uses `futures_executor::block_on`, and supplies a private adapter with an owned current-thread Tokio runtime. Inside that runtime, `tokio::time::timeout` wraps the complete async Reqwest `send_bytes` future, including body collection; timeout drops that future before the next batch. The adapter explicitly disables decompression as well as proxy, redirect, and retry behavior. Linux trickle, existing stalled-Collector/redirect/privacy, and product-process trace tests pass. Recheck the selected feature graph after dependency changes and repeat the product-process traffic/shutdown evidence natively on macOS. A loopback Collector's routing and TLS behavior beyond Arany are not covered here.

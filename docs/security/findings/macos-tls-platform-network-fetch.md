# Finding: macOS TLS trust evaluation may fetch certificates outside the selected destination

Status: **open; release-blocking for the macOS selected-Provider-egress claim**. Severity: **medium**. The selected TLS verifier delegates certificate-chain evaluation to macOS Security Framework without disabling its default network fetch of missing intermediates. A TLS peer whose chain lacks an intermediate can therefore induce a trust-service fetch to a certificate-specified location outside Arany's admitted Provider endpoint. This is a source-supported egress possibility, not a native observation of an Arany binary and not evidence that Workspace bytes or credentials are sent to that secondary location.

## Evidence and trust boundary

The locked macOS graph selects `reqwest 0.13.5`, `rustls-platform-verifier 0.7.1`, and `security-framework 3.7.0`; [the dependency inventory](../beta-dependency-inventory.md) records the target selection. [Arany's manifest](../../../Cargo.toml) enables `reqwest/rustls`. Its native Provider, catalog, custom-profile, and OAuth HTTPS clients use `Client::builder()` without `tls_certs_only` or a custom verifier in `src/provider/` and `src/cli/chatgpt/`. The pinned `reqwest` client source (`async_impl/client.rs`, Rustls branch) selects `rustls_platform_verifier::Verifier::new` when no explicit roots are supplied and `tls_certs_only` is false; those are its builder defaults.

The pinned Apple verifier source (`rustls-platform-verifier-0.7.1/src/verification/apple.rs`, `verify_certificate`) creates an SSL policy, creates a `SecTrust`, and calls `evaluate_with_error()`. It does not call `SecTrustSetNetworkFetchAllowed(..., false)`. [Apple's Security Framework documentation](https://developer.apple.com/documentation/security/sectrustsetnetworkfetchallowed%28_%3A_%3A%29) says SSL-policy trust evaluations permit fetching missing intermediate certificates by default and identifies the explicit disable control. The verifier's own test-root comment also states that its special anchor setting does not prevent network fetch for revocation information or root CA download; this finding only relies on Apple's documented missing-intermediate behavior. No native macOS traffic trace has yet confirmed the conditions under which the selected build actually fetches.

The selected HTTPS origin and credential are authorized by the user/profile; a certificate's issuer-download location is not. Arany's no-proxy, no-redirect, address, and endpoint checks govern its `reqwest` HTTP requests, but not an OS trust-service request made during TLS validation. The protected boundary is the release claim that provider operations contact only the admitted destination. An attacker able to influence the peer certificate chain or its network environment may influence this secondary destination. The possible disclosure is at least a connection and certificate-related metadata; there is no evidence that Arany's HTTP body, Workspace content, or API key accompanies the trust fetch. OS caching, revocation behavior, and whether the service runs in another process remain unverified.

## Resolution and verification

The user selected preservation of macOS system trust with a verifier that blocks missing-intermediate network fetch. The pinned `security-framework 3.7.0` wrapper exposes `SecTrust::set_network_fetch_allowed(false)`, but `rustls-platform-verifier 0.7.1` does not call it or expose that policy choice. A reviewed verifier integration is still required; the selection is not an implemented fix. The alternative below is retained to make the compatibility trade-off explicit:

1. **Selected:** keep platform trust but use a macOS verifier path that explicitly disables missing-intermediate network fetch, then assess any separate trust-service network behavior. This retains system trust anchors but adds a native TLS/FFI maintenance surface.
2. Use an explicit reviewed certificate-root set with a Rustls verifier that makes no platform trust evaluation. This narrows the egress path but changes enterprise/custom-root compatibility and root-update responsibility.

Do not silently disable certificate validation or accept a secondary certificate location as a Provider destination. The chosen policy must fail closed when a peer omits required chain material, unless a separately authorized and bounded retrieval design is approved. Confirm the source path for both macOS architectures, then run the shipped Arany process against a test-owned HTTPS peer with a missing intermediate and a distinct test-owned issuer-download listener. Observe outbound traffic at the OS boundary, accepted complete chains, rejected incomplete chains under the chosen policy, exact Provider request destinations, and terminal/error recovery. A minimal verifier test alone cannot prove the product's effective egress. Native macOS runners are not yet available; Linux tests and cross-compilation do not close this finding.

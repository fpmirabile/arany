# Finding: macOS TLS trust evaluation may fetch certificates outside the selected destination

Status: **open; release-blocking for the macOS selected-Provider-egress claim**. Severity: **medium**. The published TLS verifier delegates certificate-chain evaluation to macOS Security Framework without disabling its default network fetch of missing intermediates. Arany now selects a local checksum-matched patch that calls `SecTrust::set_network_fetch_allowed(false)` before evaluation, preserving the platform trust decision. This narrows the source-supported missing-intermediate path, but native traffic and revocation behavior have not been verified. It is not evidence that Workspace bytes or credentials are sent to a secondary location.

## Evidence and trust boundary

The locked macOS graph selects `reqwest 0.13.5`, `rustls-platform-verifier 0.7.1`, and `security-framework 3.7.0`; [the dependency inventory](../beta-dependency-inventory.md) records the target selection. [Arany's manifest](../../../Cargo.toml) enables `reqwest/rustls`. Its native Provider, catalog, custom-profile, and OAuth HTTPS clients use `Client::builder()` without `tls_certs_only` or a custom verifier in `src/provider/` and `src/cli/chatgpt/`. The pinned `reqwest` client source (`async_impl/client.rs`, Rustls branch) selects `rustls_platform_verifier::Verifier::new` when no explicit roots are supplied and `tls_certs_only` is false; those are its builder defaults.

The published Apple verifier source (`rustls-platform-verifier-0.7.1/src/verification/apple.rs`, `verify_certificate`) creates an SSL policy, creates a `SecTrust`, and calls `evaluate_with_error()` without disabling network fetch. [Apple's Security Framework documentation](https://developer.apple.com/documentation/security/sectrustsetnetworkfetchallowed%28_%3A_%3A%29) says SSL-policy trust evaluations permit fetching missing intermediate certificates by default and identifies the explicit disable control. The [local patched source](../../../vendor/rustls-platform-verifier-0.7.1/src/verification/apple.rs) now sets that policy on the same trust object, fails if setting it fails, and retains the original server-name-bound SSL policy. Its diff from the published, checksum-matched crate is one three-line source addition; the original MIT/Apache-2.0 licenses remain. The verifier's own test-root comment also identifies possible revocation and root-certificate fetches; no native macOS traffic trace has established the effective behavior of Arany's patched build.

The selected HTTPS origin and credential are authorized by the user/profile; a certificate's issuer-download location is not. Arany's no-proxy, no-redirect, address, and endpoint checks govern its `reqwest` HTTP requests, but not an OS trust-service request made during TLS validation. The protected boundary is the release claim that provider operations contact only the admitted destination. An attacker able to influence the peer certificate chain or its network environment may influence this secondary destination. The possible disclosure is at least a connection and certificate-related metadata; there is no evidence that Arany's HTTP body, Workspace content, or API key accompanies the trust fetch. OS caching, revocation behavior, and whether the service runs in another process remain unverified.

## Resolution and verification

The user selected preservation of macOS system trust with a verifier that blocks missing-intermediate network fetch. The pinned `security-framework 3.7.0` wrapper exposes `SecTrust::set_network_fetch_allowed(false)`, and Arany's relative `[patch.crates-io]` selects a local verifier copy that calls it. The alternative below is retained to make the compatibility trade-off explicit:

The short `reqwest::ClientBuilder::tls_certs_only(...)` route is **not** equivalent to the selected policy. In pinned `reqwest 0.13.5`, it bypasses `rustls-platform-verifier` and builds a Rustls verifier from only caller-supplied roots. Loading those roots through `rustls-native-certs` would retain many local CAs but lose macOS's per-certificate trust and distrust decisions: [the verifier project's deployment comparison](https://github.com/rustls/rustls-platform-verifier#deployment-considerations) distinguishes that behavior explicitly. A precheck of the presented chain is also insufficient because the platform trust evaluation can independently fetch certificate material. The selected fix must set the fetch policy on the same `SecTrust` instance before evaluation, then use that evaluation for the TLS decision. The existing upstream verifier creates that instance privately, so this requires a reviewed verifier change or a separately maintained macOS verifier, not a one-line Reqwest option. No untested macOS route has been activated.

The selected source-level patch is in the locked `rustls-platform-verifier 0.7.1` Apple `verify_certificate`: it calls `SecTrust::set_network_fetch_allowed(false)` on the newly created trust object and fails verification if setting the policy fails. Reqwest's default Rustls branch constructs this verifier for Arany's HTTPS clients, and no Arany client sets `tls_certs_only` or a preconfigured backend. This retains platform trust while rejecting chains that require the disabled intermediate fetch; vendoring and overriding a dependency enlarges the reviewed source/release surface. This patch alone does **not** close the selected-destination egress finding: [Apple defines a separate revocation-policy flag](https://developer.apple.com/documentation/security/revocation-policy-constants) that restricts OCSP/CRL checks to locally cached replies, and the pinned `security-framework 3.7.0` wrapper exposes it as `RevocationPolicy::NETWORK_ACCESS_DISABLED`. Adding that policy may change revocation freshness and failure behavior, so it needs a separately reviewed compatibility decision and native traffic evidence. Neither setting proves that other platform components make no secondary requests.

If a cached-only revocation policy is selected, pass it **alongside** the existing server-name-bound SSL policy when creating the same `SecTrust`; do not replace the SSL policy. The pinned verifier constructs its trust object with `SecPolicy::create_ssl(..., Some(server_name))`, while [Apple specifies that `SecTrustSetPolicies` replaces all prior policies](https://developer.apple.com/documentation/security/sectrustsetpolicies%28_%3A_%3A%29). Preserve hostname and server-role validation, and test complete-chain acceptance, revoked-chain rejection, and unavailable-revocation behavior natively before claiming equivalent trust semantics.

A local `[patch.crates-io]` changes the release provenance contract. [Cargo removes `[patch]` when packaging](https://doc.rust-lang.org/cargo/commands/cargo-package.html), and [always excludes nested packages](https://doc.rust-lang.org/cargo/reference/manifest.html#the-include-and-exclude-fields); Arany's current [`include` list](../../../Cargo.toml) has no patched dependency source. Therefore a passing `cargo package --verify` cannot prove that a distributed `.crate` builds with the patched verifier. The separate [source archive](../../../scripts/source-archive.sh) retains the exact patched source and lock resolution, and verifies Cargo selection and an offline check after extraction at a new path. It is the source-install path for both local patches; the ordinary `.crate` remains unsuitable. Native macOS binary/source pairing is still a release gate.

As of 2026-10-01, [docs.rs lists 0.7.1 as the latest published release](https://docs.rs/crate/rustls-platform-verifier/latest), and [upstream `main` still calls `evaluate_with_error()` without disabling network fetch on its `SecTrust`](https://github.com/rustls/rustls-platform-verifier/blob/main/rustls-platform-verifier/src/verification/apple.rs). Upgrading to a published release or tracking the current upstream branch does not remove this finding; recheck upstream before maintaining a patch long-term.

1. **Selected and implemented in source:** keep platform trust but use a macOS verifier path that explicitly disables missing-intermediate network fetch, then assess any separate trust-service network behavior. This retains system trust anchors but adds a native TLS/FFI maintenance surface.
2. Use an explicit reviewed certificate-root set with a Rustls verifier that makes no platform trust evaluation. This narrows the egress path but changes enterprise/custom-root compatibility and root-update responsibility.

Do not silently disable certificate validation or accept a secondary certificate location as a Provider destination. The chosen policy must fail closed when a peer omits required chain material, unless a separately authorized and bounded retrieval design is approved. Confirm the source path for both macOS architectures, then run the shipped Arany process against a test-owned HTTPS peer with a missing intermediate and a distinct test-owned issuer-download listener. Also test a complete chain with test-owned OCSP/CRL locations, including cold and warm cache states. Observe outbound traffic at the OS boundary, accepted complete chains, rejected incomplete chains under the chosen policy, exact Provider request destinations, revocation behavior, and terminal/error recovery. A minimal verifier test alone cannot prove the product's effective egress. Native macOS runners are not yet available; Linux tests and cross-compilation do not close this finding.

# macOS system TLS validation and auxiliary certificate traffic

Status: **resolved by policy clarification and selection of the published verifier; native macOS verification pending**. This is not a certificate-validation bug or a Provider-data destination grant. The earlier release-blocking finding assumed that every connection made during a Provider call had to target the selected Provider. The current policy instead distinguishes Arany's own requests and data disclosure from operating-system trust evaluation.

## Boundary and decision

Arany authorizes its HTTP request destination before Workspace input or credentials are used. Native routes are compiled; exact custom routes require trusted configuration, address admission, and current conformance evidence. Clients disable ambient proxies, redirects, and retries; credentials are selected per profile; request and response bounds remain in force. A certificate-related URL is never an authorized Arany endpoint for sending prompts, Workspace files, session content, or credentials.

The published `rustls-platform-verifier 0.7.1` is selected through Reqwest's `rustls` feature. On macOS it delegates certificate-chain and server-name validation to the Security Framework, including the system's trust and distrust decisions. Its Apple implementation creates an SSL policy bound to the requested server name and evaluates `SecTrust` without an Arany-specific network-fetch override. [Apple documents](https://developer.apple.com/documentation/security/sectrustsetnetworkfetchallowed%28_%3A_%3A%29) that an SSL-policy trust evaluation may fetch missing intermediate certificates by default. Revocation checks may also involve certificate-related network activity. These are auxiliary OS validation operations, not additional destinations authorized for Arany's HTTP body or credentials. Arany does not claim to prevent all secondary OS connections or to know every macOS trust-service destination.

The user chose standard OS validation and accepted its auxiliary behavior. The former local `SecTrust::set_network_fetch_allowed(false)` patch has been removed; it could change chain-building behavior and could not prove the absence of other OS traffic. Arany retains the system verifier and does not set `tls_certs_only`, disable certificate or hostname checks, accept invalid certificates, or substitute a bundled root set. An invalid chain or wrong server name must still fail the TLS handshake. The [source archive](../../../scripts/source-archive.sh) verifies the published crate selection for both macOS target graphs, and now verifies unmodified published Crossterm selection.

## Evidence limits

The locked dependency and source inspection establish the intended verifier path. The [explicit Linux HTTPS gate](../../../tests/platform_tls.rs) uses the default Reqwest platform verifier with a test-owned root and three local peers: a valid chain/name succeeds, while a wrong server name and a separately signed chain fail with certificate-specific errors. It uses no Provider key or paid call and proves Linux transport behavior, not native Arany/macOS behavior. A native macOS runner must still test the shipped Arany client against valid, invalid-chain, and wrong-name peers on both release architectures, including an incomplete chain whose intermediate is available through a test-owned issuer URL and test-owned revocation endpoints. Observe Arany-issued destinations and outbound payloads separately from OS certificate traffic, and confirm no Workspace bytes or credential values reach those auxiliary listeners. Test cold and warm trust caches and document the observed acceptance/rejection behavior without treating normal OS fetches as defects. Until then, native macOS TLS behavior and final release evidence remain open; no Provider-only *machine-wide connection* claim is made.

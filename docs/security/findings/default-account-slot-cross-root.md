# Finding: different StateRoots share one API-account keyring slot

Status: **partially repaired; optimized Linux private-file setup/reuse, one synthetic direct Run, and cross-user account exclusion passed through the shipped product, while isolated keyring setup and cross-user keyring proof remain open for beta 1**. Severity: **medium (local account-scope confusion and replacement race if migration or backend coordination fails)**. The user chose one account scope per OS user across that user's Sessions and StateRoots, not one account per StateRoot or the whole machine. No real account or fixed keyring slot was touched by the repair.

## Evidence and boundary

The Session [default StateRoot](../../../src/store/state.rs) still follows `directories::ProjectDirs`, but its new Linux `account_path` derives the effective UID's passwd home and a fixed `.local/state/arany` suffix. [Credential save and inspection](../../../src/cli/credentials.rs) and the dormant [ChatGPT registration](../../../src/cli/chatgpt/registration.rs) use that path for their marker and [replacement lock](../../../src/store/state/lock.rs). A separate test process changed `HOME` and `XDG_STATE_HOME` without changing the resulting account path. The fixed keyring slot remains `default-native-api-account`, selected only after account-root selection and legacy migration.

A validated old record under the current environment-selected root is copied while holding its old lock and the stable root lock. After the new copy is durable, the old record becomes a version-zero tombstone; equal partial copies can finish on retry, and a different destination record fails without replacing either account. Synthetic file-account and registration cases prove those transitions. A tombstone is not secure erasure of disk remnants. Old Arany versions still use the old root and are not coordinated by the new lock. Other same-UID access to an unlocked Secret Service item is a separate [finding](./linux-secret-service-client-isolation.md).

The Linux code and synthetic tests support the stable-root and conflict behavior. An ignored native test on this host used two self-spawned test processes with distinct `XDG_STATE_HOME` values, one debug-only private account root, and one random `native-test-` Secret Service slot. A concurrent replacement returned `AccountBusy` without changing the original keyring item or token-free marker; after lock release, replacement succeeded, the old UUID failed exact selection, and the new record was read back before explicit slot deletion and absence confirmation. The selected KDE-backed service was unlocked. This test uses the test binary's direct non-default-slot keyring path, not a complete shipped `/setup` or the fixed account slot. No cross-user isolation check or full saved-account setup journey has passed against an isolated Secret Service. A debug-assertions-only test-root override protects existing product-process tests from consulting the real account root; optimized builds reject that override. This test facility is not a production account-scope option. None of this proves OS keyring write atomicity or rollback after timeout.

On 2026-10-02, the optimized `arany` executable ran inside a private Bubblewrap home and network namespace with the real passwd-derived account path, no test-root override, and no reachable credential bus. Manual screen-reader setup reached access-method selection, the explicit private-file fallback warning, Provider selection, and the API-key prompt without entering a key. A new ignored release-only product PTY repeats the access-method and fallback choices, cancels by name, then checks a successful exit, unchanged terminal settings, no escape sequences or cursor query, and no account or Session State; it passed twice on this Linux host. This proves pre-save setup and cancellation under the production account-root rule, not secret-input echo suppression, account save/reuse, keyring isolation, cross-user scope, or a Provider turn.

Another ignored release-only product PTY preseeded one synthetic private-file API account in that passwd-derived path, then started the optimized executable twice with distinct Session StateRoots and distinct `HOME` and `XDG_STATE_HOME` values inside the same private OS-user home. Both bare starts reached the composer without reopening setup, exited cleanly through `/quit`, restored terminal settings, and strictly replayed one empty Session each with the same account UUID, Provider, and model. The synthetic key was absent from terminal output and both SQLite journals. The namespace had no network or credential bus, and neither start submitted a Run. This proves cross-StateRoot reuse of a preexisting private-file account, not account creation through the shipped wizard, native keyring reuse, or live Provider access.

The same optimized product-process harness also passed with only a preseeded synthetic ChatGPT account index, selected by UUID and marked as keyring-backed, across two distinct Session StateRoots and environment homes. Both bare starts reached the composer without a reachable credential bus, pinned `chatgpt` and the same account UUID, and left model and effort unset. The synthetic account subject was absent from output and both SQLite journals; terminal settings and strict empty-Session replay passed. This supports token-free account-ID selection at Session startup, but the fixture contains no token or current consent receipt and cannot prove keyring token loading, live sign-in, model conformance, or a Provider turn. A separate [billing-route selection finding](./ambiguous-saved-access-selection.md) now records optimized startup evidence when both account types are saved; that evidence likewise does not prove token use or a live turn.

## Resolution and verification

On 2026-10-02, an ignored Linux Store test used subordinate UID mappings and private mount, PID, and network namespaces. Effective UID 0 resolved its passwd-derived account root, wrote and reread synthetic bytes in the saved-account slot, and effective UID 1 resolved a different root and received `PermissionDenied` reading the first user's record. The owner reread the unchanged bytes afterward. This proves the private-file Store boundary across two real kernel UIDs in that namespace, not full CLI selection, Secret Service isolation, or account setup.

An ignored optimized product-process PTY repeated bare startup in one private namespace with those two effective UIDs and a preseeded synthetic private-file API account. The owner selected its exact account UUID; the second user, even with `HOME` pointed at the owner's home, reached an unconfigured composer with no account or Provider selected. Both Sessions strictly replayed with no Run, and the synthetic key was absent from output and SQLite journals. This proves cross-user exclusion for the saved private-file startup route, not isolated keyring behavior, creation through `/setup`, or a live Provider turn. An inaccessible foreign `XDG_STATE_HOME` deliberately fails legacy migration before startup, so that fixture used the second user's own legacy State path while retaining the adversarial `HOME`.

A separate ignored optimized product-process PTY now completes the private-file `/setup` write path. It runs in a private Linux network and mount namespace with a synthetic passwd home, hosts-only name resolution, and a test CA that validates a local certificate for the unchanged compiled `api.openai.com` endpoint. An OpenSSL HTTPS peer serves one synthetic account-visible model catalog; the user-visible wizard selects API key, explicitly accepts the unencrypted private file, enters a synthetic key with terminal echo disabled, selects `gpt-5.4` and Provider-default effort, then saves the account. A second bare start in a different Session StateRoot reuses the exact account UUID after that peer is stopped. Both Sessions strictly replay with no Run. A third start submits one objective over the compiled Responses HTTPS endpoint and strictly replays one finished direct Run with that same account UUID, selected model, answer, usage, and wire provenance. The peer checks the bounded request and returns synthetic strict output; terminal settings restore, the account file is mode `0600`, and the key is absent from output, request body, and SQLite journals. This proves offline private-file setup/reuse and synthetic Provider inference with ordinary TLS chain and server-name validation, not live model availability, keyring setup, same-UID secrecy, or a paid Provider turn.

Keep the stable Linux account marker and replacement lock independent of environment-selected Session StateRoots, matching the OS user's keyring slot. Preserve the failure-closed migration and explicitly resolve any conflicting old accounts before use. The private file mode does not isolate same-UID processes, and the effective user's passwd home must itself pass StateRoot path/owner checks. Native macOS path and ACL proof follows in the later cross-platform milestone, not this Linux personal goal.

Still prove keyring-backed shipped setup/reuse with two Session StateRoots under one OS user, including concurrent replacement and holder death, old-marker migration and interrupted writes, exact UUID/Provider resolution before Workspace input, and absence of keys from output, Events, traces, arguments, and environment. Verify separately that another OS user cannot select a keyring-backed account. Use random synthetic keyring slots and an isolated native service for product-process tests; never overwrite the live fixed default slot. Native Linux product proof belongs to beta 1; macOS behavior remains a later native gate.

An isolated Secret Service alone cannot complete native first-run setup offline: the shipped wizard reads the selected Provider's compiled HTTPS model catalog before saving the account. The network-namespace fixture supplies that catalog and one synthetic direct-turn response without a product endpoint override, so the private-file journey passes while the keyring journey still needs a safely writable isolated Secret Service. The fixture changes only namespace DNS and trust inputs; it is not live Provider compatibility evidence or permission to weaken production endpoint admission.

# Finding: Linux Secret Service does not establish Arany-only credential access

Status: **accepted same-user access risk for personal ChatGPT-plan storage; Arany-only stored-token claims remain blocked**. Severity: **medium**. This is a source-, specification-, and native-test-supported confidentiality boundary gap. A synthetic record was retrieved by another client on this host; no real credential was used, and this does not prove that every Secret Service backend shares unlocked items. The user's 2026-10-02 decision permits a keyring-backed subscription account only after an explicit same-user-access warning and account consent; it does not by itself activate storage or inference.

## Evidence and boundary

The locked Linux graph selects `keyring 4.2.0` with `v1`, `zbus-secret-service-keyring-store 1.0.1`, and `secret-service 5.2.0`. Arany's [credential owner](../../../src/cli/credentials.rs) writes its entire versioned API-account record under a fixed service and account name in the default OS collection. The pinned `zbus-secret-service-keyring-store/src/cred.rs` searches by the `service` and `username` attributes, and its `service.rs` opens `SecretService::connect(EncryptionType::Dh)`. The pinned `secret-service/src/session.rs` requires a Diffie–Hellman session for that choice rather than falling back to a plaintext session. Encrypted transfer is not an authorization rule for a different client that opens its own session.

The [Secret Service API](https://specifications.freedesktop.org/secret-service/latest/description.html) provides searchable attributes and `GetSecret`; its [locking rules](https://specifications.freedesktop.org/secret-service/latest/unlocking.html) allow a service either to unlock for one client or to let other client applications access already unlocked items. Arany cannot enforce the former through this API. A different process in the same user's login session could search for Arany's fixed attributes and, if the installed service allows shared access or presents an accepted unlock prompt, request the item through its own encrypted session. The pinned `secret-service 5.2.0` source even includes a cross-connection encrypted-secret retrieval test; that test is not a cross-application or native-backend observation. Root or a process able to inspect Arany's memory is outside this OS-store boundary regardless.

The ignored [native cross-client test](../../../src/cli/credentials.rs) saved a test-owned API-account record under a random slot, then invoked the separate `/usr/bin/secret-tool` client with only the current D-Bus address and runtime-directory environment. On this Linux host, `secret-tool lookup service ... username ...` returned the exact serialized record from the unlocked collection. The test deleted the item and confirmed it was absent before failing its Arany-only access assertion. This is direct same-user, cross-process retrieval evidence for this host's current backend, not a locked-item, isolated-bus, macOS, or every-backend result. The record contained only a synthetic key; the test never printed its bytes.

Test: [`src/cli/credentials.rs::native_store_denies_another_same_user_client`](../../../src/cli/credentials.rs); the observed unlocked backend was `/usr/bin/ksecretd`. That backend allowed cross-client synthetic retrieval; this does not establish every KWallet version, configuration or locked-collection behavior.

The existing API-key account path is active with a documented current-user OS-store boundary. The user accepted a current-user keyring-first API-key setup with a warned private-file fallback; this does not imply Arany-only protection against other same-UID processes. ChatGPT-plan account save, selected-token load, and serialized rotating refresh are now wired behind explicit consent and exact model/effort checks, but no real account or live Run has been verified. The user accepts the observed same-user keyring risk for ChatGPT-plan storage with an explicit warning. Arany must still protect against cross-user access and avoid token disclosure through its own output and State. No absolute or app-exclusive token secrecy is claimed.

## Resolution and verification

Keep API-key and subscription persistence explicitly scoped to the current OS user, with a subscription-specific warning and no app-exclusive claim. Account verification, consent, protected record validation, serialized rotation, and tested failure behavior gate each selected use. A compromised host or same-user process with access to an unlocked Secret Service item remains outside Arany's confidentiality guarantee. Do not relabel the current backend as app-exclusive or silently fall back to a plaintext subscription-token file.

On native Linux with test-owned Secret Service accounts and synthetic records, test locked and unlocked states, save/load/replacement, and retrieval attempts from a distinct same-user client. The product targets the Secret Service interface rather than one desktop's wallet; backend differences must produce accurate errors and warnings, not a false uniform confidentiality claim. Verify terminal redaction and State replay separately.

A private KDE service exposed Secret Service but lacked an unlocked writable collection; collection creation required prompting, and a bounded offscreen/Xwayland attempt did not complete a wallet dialog. This proves an unavailable-store path, not a KDE defect or successful setup/reuse; completing that particular fixture is not a milestone.

Test: [`src/cli/chatgpt/account/tests.rs::native_keyring_round_trips_and_replaces_a_synthetic_chatgpt_account`](../../../src/cli/chatgpt/account/tests.rs). Synthetic backend/account/helper roundtrips do not prove parent-supervisor deadlines, locked collections, full OAuth-to-Run flow or app-exclusive storage. **Isolated Linux keyring lifecycle** in [next steps](../../../NEXT_STEPS.md#beta-2-and-broader-release) owns remaining native verification.

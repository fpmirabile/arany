# Finding: Linux Secret Service does not establish Arany-only credential access

Status: **open; blocks any Arany-only stored-token claim and ChatGPT-plan token activation on Linux**. Severity: **medium**. This is a source-, specification-, and native-test-supported confidentiality boundary gap. A synthetic record was retrieved by another client on this host; no real credential was used, and this does not prove that every Secret Service backend shares unlocked items.

## Evidence and boundary

The locked Linux graph selects `keyring 4.2.0` with `v1`, `zbus-secret-service-keyring-store 1.0.1`, and `secret-service 5.2.0`. Arany's [credential owner](../../../src/cli/credentials.rs) writes its entire versioned API-account record under a fixed service and account name in the default OS collection. The pinned `zbus-secret-service-keyring-store/src/cred.rs` searches by the `service` and `username` attributes, and its `service.rs` opens `SecretService::connect(EncryptionType::Dh)`. The pinned `secret-service/src/session.rs` requires a Diffie–Hellman session for that choice rather than falling back to a plaintext session. Encrypted transfer is not an authorization rule for a different client that opens its own session.

The [Secret Service API](https://specifications.freedesktop.org/secret-service/latest/description.html) provides searchable attributes and `GetSecret`; its [locking rules](https://specifications.freedesktop.org/secret-service/latest/unlocking.html) allow a service either to unlock for one client or to let other client applications access already unlocked items. Arany cannot enforce the former through this API. A different process in the same user's login session could search for Arany's fixed attributes and, if the installed service allows shared access or presents an accepted unlock prompt, request the item through its own encrypted session. The pinned `secret-service 5.2.0` source even includes a cross-connection encrypted-secret retrieval test; that test is not a cross-application or native-backend observation. Root or a process able to inspect Arany's memory is outside this OS-store boundary regardless.

The ignored [native cross-client test](../../../src/cli/credentials.rs) saved a test-owned API-account record under a random slot, then invoked the separate `/usr/bin/secret-tool` client with only the current D-Bus address and runtime-directory environment. On this Linux host, `secret-tool lookup service ... username ...` returned the exact serialized record from the unlocked collection. The test deleted the item and confirmed it was absent before failing its Arany-only access assertion. This is direct same-user, cross-process retrieval evidence for this host's current backend, not a locked-item, isolated-bus, macOS, or every-backend result. The record contained only a synthetic key; the test never printed its bytes.

The existing API-key account path is active with a documented current-user OS-store boundary. The user accepted a current-user keyring-first API-key setup with a warned private-file fallback; this does not imply Arany-only protection against other same-UID processes. ChatGPT-plan refresh tokens remain unwired and have not been saved. The requested stronger token secrecy cannot be claimed from the selected Linux backend, so this finding still blocks stored subscription-token activation.

## Resolution and verification

Keep API-key persistence explicitly scoped to the current OS user, with the setup warning and no app-exclusive claim. Subscription credentials stay session-only or disabled until a separate storage and consent design has effective-platform proof; no mechanism can promise absolute secrecy against a compromised host or same-user process-memory access. Do not activate saved subscription tokens or relabel the current backend as app-exclusive.

On a native isolated Linux login/session bus with a test-owned Secret Service and synthetic record, test locked and unlocked states, save/load/replacement, and retrieval attempts from a distinct same-user client. Repeat against each backend Arany claims to support, because the specification permits different access policy. Verify terminal redaction and State replay separately.

On 2026-10-01, manually starting the installed KDE `ksecretd` inside a no-network `bwrap` namespace with a temporary in-memory home and private D-Bus session exposed `org.freedesktop.Secret.Service`. Its `Collections` property was empty. A `CreateCollection` request for the `default` alias returned `/` for the collection and a prompt object; the [Secret Service method contract](https://specifications.freedesktop.org/secret-service/latest/org.freedesktop.Secret.Service.html) identifies this as a creation requiring prompting. The existing synthetic-key roundtrip then failed at save with Arany's redacted `Unavailable` result under an offscreen Qt platform. This proves the unavailable-store failure path in that private environment, not successful save/reuse, locked-item behavior, or same-user exclusion. The host has no activatable private Secret Service or private graphical prompt runner, so this release gate still needs an isolated unlockable backend. The developer's live default account slot was not used.

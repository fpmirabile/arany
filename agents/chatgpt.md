# ChatGPT-plan access

Load for `src/cli/chatgpt.rs`, official subscription authentication, account consent, OAuth credentials, or the local-only output bound. [security.md](./security.md) owns shared secret and listener rules; [provider.md](./provider.md) owns inference admission.

- The private CLI module owns one offline-tested authorization transaction for first registration or a previously verified account. Every attempt binds fresh `state`, nonce, and PKCE verifier to a canonical `127.0.0.1` callback URI. First registration requires a bounded issued client ID in the callback. Returning authorization uses the selected registration's issued client and retained ID-token hint, omits `agent_name_hint`, accepts an omitted callback client ID, and rejects a different one. Callback acceptance consumes the attempt and requires exact origin/path/port and one bounded code and state. Hints are sent only to the compiled authorization endpoint and never logged.
- Redeem the code once with the exact issued client, redirect, verifier, and resource at the compiled token endpoint. Only a bounded identity-encoded JWKS from the compiled issuer endpoint may verify its ID token. The current validator accepts RS256 only; an algorithm change requires an explicit source, fixture, and live-conformance review. Bind verified signature, issuer, audience, nonce, lifetime, and nonempty subject to the token response's direct-use, resource-invocation, and offline-access scopes before returning credentials. A returning attempt also requires that signed subject to match its selected account before replacement. The callback client ID and token response alone are never account authority.
- The private, unwired refresh exchange uses that registration's issued client ID and rotating refresh token with `grant_type=refresh_token` and the fixed resource; it omits scope, requires renewed direct-use permission and a distinct replacement token pair, and returns a whole new in-memory credential value without mutating the old one. A validated code or refresh response records absolute access expiry from the local request-start time plus bounded `expires_in`, conservatively accounting for network delay; a relative lifetime alone cannot survive restart. This local timestamp does not prove remote validity under clock skew, so future active use must refresh ahead of it and handle authorization failure. It has no active caller. Only a recognized machine-readable terminal refresh error marks the token unusable; preserve credentials on transport, rate-limit, server, malformed, and unknown failures. An invalid client requires registration repair, not token deletion. Before wiring refresh to catalog or inference, serialize it across processes under a private state-root lock and atomically replace the protected account record; a successful remote rotation followed by a failed local save may require reauthorization. Preserve the originally verified subject and retained ID-token hint; the refresh response alone does not establish a new identity.
- The private, unwired sign-out primitive reads only the compiled issuer's bounded OpenID configuration, requires an exact issuer and same-origin HTTPS revocation endpoint without query or fragment, and sends the selected registration's refresh token with its issued client ID. Only an empty HTTP `200` confirms remote revocation. It never changes local credentials; every other outcome is unconfirmed. The future account owner must decide bounded retry or local clear with an explicit remote-uncertainty warning. Official documentation lists `earliest_refresh_at` in token replies but does not define its units or scheduling semantics; do not infer them for active refresh.
- Keep authorization entropy on the reviewed OS-backed `getrandom` path. Release compiler flags or backend cfgs that can substitute a different entropy source require separate provenance review; direct dependency feature flags alone do not prove the final backend.
- A private, unwired listener requires an acknowledgment produced by the current `RiskPrompt` before binding one ephemeral `127.0.0.1` port. The prompt owns the exact warning text and explicit `I ACCEPT` choice. The one accepted HTTP/1.1 GET must use the exact callback path and `Host`, have no `Origin` or body headers, and pass the state-bound callback parser. The listener has an aggregate two-minute deadline and an 8-KiB request cap; its inert response never reflects a code or token. Its acceptance value can become a consent receipt only after signed identity verifies the issued client, subject, and host. The receipt binds both warning version and exact text digest, so a different registration or warning text never inherits acceptance. Local tests may bind it; setup still must display that exact warning and collect a real choice before opening a browser.
- The private subscription catalog reads only a verified, consent-matched account token at the compiled `/v1/models` route. It returns every `visibility: "list"` model in server order with bounded slug and display name, but visibility grants no Run or effort capability. No Workspace input enters the request. Reject token reflection, duplicate/oversized rows, compressed or redirected replies, and responses above 1 MiB; one 20-second read has no retry.
- Neither redemption nor the listener or subscription catalog is reachable from setup. A separate private Provider transport can parse a bounded strict subscription stream, but no browser launch, saved subscription token, or subscription Run exists. Keep the choice unavailable until a real account-bound UI decision, protected multi-account token lifecycle, model/effort conformance, and local-only Run guarantee pass their gates.

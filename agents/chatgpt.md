# ChatGPT-plan access

Load for `src/cli/chatgpt.rs`, official subscription authentication, account consent, OAuth credentials, or the local-only output bound. [security.md](./security.md) owns shared secret and listener rules; [provider.md](./provider.md) owns inference admission.

- The private CLI module owns one offline-tested authorization transaction for first registration or a previously verified account. Every attempt binds fresh `state`, nonce, and PKCE verifier to a canonical `127.0.0.1` callback URI. First registration requires a bounded issued client ID in the callback. Returning authorization uses the selected registration's issued client and stable host ID, omits both `agent_name_hint` and the optional ID-token hint, accepts an omitted callback client ID, and rejects a different one. The browser's account selector may offer another identity, but signed-subject verification must reject it before save. Callback acceptance consumes the attempt and requires exact origin/path/port and one bounded code and state. No credential enters browser process arguments.
- Redeem the code once with the exact issued client, redirect, verifier, and resource at the compiled token endpoint. Only a bounded identity-encoded JWKS from the compiled issuer endpoint may verify its ID token. The current validator accepts RS256 only; an algorithm change requires an explicit source, fixture, and live-conformance review. Bind verified signature, issuer, audience, nonce, lifetime, and nonempty subject to the token response's direct-use, resource-invocation, and offline-access scopes before returning credentials. A returning attempt also requires that signed subject to match its selected account before replacement. The callback client ID and token response alone are never account authority.
- A bounded JSON `invalid_grant` response to code redemption marks that one code unusable; do not retry it. A first registration can restart with the callback's issued client ID, the same host ID, and fresh state/nonce/PKCE, without another `dynamic_agent_client` registration. Returning accounts instead restart from their selected verified registration so the signed-subject check remains. The private registration owner persists the issued ID under the default-user account lock before `CodeExchange::redeem` sends the code; attached ChatGPT setup invokes this first-registration path after consent.
- The refresh exchange uses that registration's issued client ID and rotating refresh token with `grant_type=refresh_token` and the fixed resource; it omits scope, requires renewed direct-use permission and a distinct replacement token pair, and returns a whole new in-memory credential value without mutating the old one. A validated code or refresh response records absolute access expiry from the local request-start time plus bounded `expires_in`, conservatively accounting for network delay; a relative lifetime alone cannot survive restart. [Official account guidance](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) directs standard OAuth renewal near that expiry, while the [token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference) gives no units or scheduling semantics for `earliest_refresh_at`; treat that field as opaque and do not use it to schedule refresh. Local expiry does not prove remote validity under clock skew, so active catalog and check use refresh ahead of it and handle authorization failure. The private account owner serializes refresh across processes under the user account-root lock and replaces the protected account record. Only a recognized machine-readable terminal refresh error marks the token unusable; preserve credentials on transport, rate-limit, server, malformed, and unknown failures. An invalid client requires registration repair, not token deletion. A successful remote rotation followed by a failed local save may require reauthorization. Preserve the originally verified subject and signed ID token for evidence binding; the refresh response alone does not establish a new identity.
- The private account owner accepts only verified credentials and an exact backend/identity-bound risk receipt. It caps account count at eight and keeps each issued client ID distinct. A keyring token uses a SHA-256-derived slot, separate from native API-account slots; its private index stores no keyring token. A user-accepted private-file token stays in the checked atomic index, never SQLite. Save holds the OS-user account lock across keyring write and index publication; replacement of an existing keyring token first persists a pending marker so an uncertain write cannot authorize a Run. The index parses structurally valid old receipts so a user can reauthorize after warning text changes, but token load and use require the current exact consent. Reopen checks UUID/host/client/subject/backend again and requires all accounts to share the same stable host ID. The single client ID in the registration record is only the pending first-registration retry: a verified account save clears it, and a later open reconciles an interrupted clear against the protected account index. A returning account does not claim that pending slot; a second new registration may use `dynamic_agent_client` after the first account is saved. Attached setup can publish a verified new account, choose among saved account UUIDs, or reauthorize the selected one. Switching selection validates the target's current consented token under the OS-user account lock and pins account-only Session defaults until an exact model check; cancelling the picker leaves the old selection unchanged. Reauthorization requires the original selected UUID and issued client under the lock before token replacement, preserves its UUID and pinned backend, clears its pending marker and model evidence, and rejects host, subject, or backend drift. Cancellation after verified save pins the account alone until an explicit model check. The private renewal owner holds that lock through near-expiry remote exchange and whole-token replacement in a supervised blocking task; dropping its async waiter does not release the lock. It writes a durable renewal-pending marker before egress. An `Unavailable` exchange clears the marker while preserving old credentials; a lost response after server-side rotation can still make the next refresh unusable. A recognized terminal refresh-token error instead disconnects the account, clears model evidence and the private-file token, and asks the supervised helper to delete a pinned keyring token; uncertain keyring deletion keeps use blocked with an explicit warning. Other failed outcomes, process death, or failed post-rotation storage leave the marker and block later loads until verified reauthorization. A synthetic owner-driven keyring rotation passed against this Linux host's Secret Service and same-binary helper; it does not prove live OAuth, an isolated full setup, macOS, or a paid turn.
- `provider logout chatgpt` signs out only the selected OS-user account under the account-replacement lock. The owner durably marks sign-out pending and removes model evidence before reading the token or attempting remote egress, blocking new catalog/check/Run token loads. The private revocation primitive reads only the compiled issuer's bounded OpenID configuration, requires an exact issuer and same-origin HTTPS revocation endpoint without query or fragment, and sends that registration's refresh token with its issued client ID. Only an empty HTTP `200` confirms revocation; transport and 5xx failures receive at most two bounded backoff/jitter retries within one 30-second deadline. The owner then atomically disconnects the account and removes its private-file token, or asks the supervised helper to delete its pinned keyring item. An unreadable token or failed remote attempt still disconnects locally and requires a ChatGPT Settings warning; uncertain keyring deletion keeps use blocked and reports local cleanup uncertainty. An interrupted operation leaves either a pending or disconnected account; both block use until cleanup or verified reauthorization. Retain the account UUID/client/subject/backend mapping for reconnect. Neither this local action nor file modes promise secure erasure of backups, isolation from same-user processes, or cancellation of requests already in flight.
- Opening an attached Session or choosing `/provider chatgpt` reads only the validated selected account ID from the local account index. It must not load a token, contact the keyring, or start a refresh merely to draw a Session. A disconnected or sign-out-pending selection is unconfigured for Run purposes but retains its registration for setup. Catalog, conformance, and Run paths still reopen the consent-matched token, serialize near-expiry refresh, and reject pending, disconnected, or invalid renewal before any Provider request or Workspace disclosure.
- Attached catalog, setup/check consent and Run admission pass their pinned account UUID into the private account owner. Under the account lock, reject a different selection before keyring-token retrieval, private-file-token use or near-expiry renewal, not only after an operation returns. Reading the protected index can still parse its private-file entries. Explicit headless catalog/check commands can resolve the current selected account instead. Exact check publication still revalidates its account/registration/consent snapshot; no lock is claimed across the entire inference sequence.
- With a connected selected ChatGPT account, `/setup` and `--setup` offer `Use saved`, `Reconnect`, and `Connect new`; `Use saved` can select another connected account by validated local UUID under the account lock, without listener or browser. A disconnected selection instead offers `Reconnect` or `Connect new`, plus `Use saved` when another connected account exists. Reconnect reads only validated selected-account metadata, pins the existing backend, repeats its warning and typed consent, and starts a fresh returning OAuth attempt without reading the old token or contacting the Provider. The verified signed subject, original UUID/client/backend, and selected account must still match under the account lock before replacement. Cancelling before save changes neither credentials nor defaults; cancellation or catalog/check failure after a new, switched, or replacement save leaves account-only defaults and an actionable error notice where applicable. Failed current-account reuse preserves existing Session defaults. An account-identity mismatch or terminal shutdown fails closed, a missing selection enters first registration, and a malformed index never becomes a missing account.
- Keep authorization entropy on the reviewed OS-backed `getrandom` path. Release compiler flags or backend cfgs that can substitute a different entropy source require separate provenance review; direct dependency feature flags alone do not prove the final backend.
- For the [official UUID host-ID format](https://developers.openai.com/siwc/token-sharing-open-source), the private registration owner persists one UUIDv4 under the user account root before first sign-in and renders it as `urn:uuid:` in authorization requests. On Linux, that root is stable across Session roots and ordinary environment changes; a validated prior registration is copied under both account locks and tombstoned at its old location after the durable copy. A distinct existing registration fails closed. Reuse the host ID across restarts; it is an identifier, not a credential or a Session UUIDv7. The record holds one optional issued client ID as unverified callback state until signed identity is admitted; a competing registration cannot replace it silently. Verified accounts live in the separate bounded account index, and registration open rejects a host mismatch with that index before a browser attempt. Neither registration field is a token or account authorization.
- The one-shot listener requires an acknowledgment produced by the current `RiskPrompt` before binding one ephemeral `127.0.0.1` port. Attached setup pages the complete warning in inline mode or announces it in linear mode, and requires typed `I ACCEPT` before the listener or browser; an inline resize restarts pagination and clears any acceptance draft so reflow cannot skip text. The prompt owns the exact plan-usage and selected-storage warnings. Its keyring warning states the Linux same-user-client limit; its file warning states that owner-only modes do not encrypt tokens or exclude same-user processes. The acknowledgment pins the chosen backend, and the receipt binds that backend, warning version and exact text digest to the verified client, subject, and host; changing any one requires fresh consent. It accepts at most eight local connections under a two-minute aggregate deadline and a five-second per-connection deadline; invalid requests receive an inert rejection and do not consume the pending authorization. A matching denial ends it; the one accepted HTTP/1.1 GET must use the exact callback path and `Host`, have no `Origin` or body headers, and pass the state-bound callback parser. Each request is capped at 8 KiB and 32 headers, and responses never reflect a code or token. The system-browser launcher accepts only the compiled authorization origin and refuses a token hint in process arguments; it cannot authorize any other egress. A native Linux loopback test covers one stalled connection's five-second rejection followed by a valid callback. Optimized, networkless product-process PTYs prove first sign-in with a test-owned browser stub, signed synthetic identity, compiled TLS endpoints, explicit private-file consent, and selected-token catalog access. One declines model-check cost and strictly replays only the account; the other explicitly accepts three synthetic checks, persists exact model/effort evidence, completes two consecutive account-bound direct Engine Runs, then one single-child team Run under the same local-only output cap. The second direct request carries the first accepted user/assistant turn as local history; the team's child receives isolated context and synthesis receives its accepted result. Both reuse the account UUID on bare restart. They do not prove a real browser, live account, native keyring, or paid Run.
- The subscription catalog reads only a selected, verified, consent-matched account token at the compiled `/v1/models` route. The account owner returns one in-memory UUID/credential/receipt/backend snapshot after serialized near-expiry refresh; the catalog checks the matching receipt again before egress. The command returns every `visibility: "list"` model in server order with bounded slug and display name, but visibility grants no Run or effort capability. No Workspace input enters the request. Reject token reflection, duplicate/oversized rows, compressed or redirected replies, and responses above 1 MiB; one 20-second read has no retry. A non-success HTTP response reports only its numeric status and fixed recovery advice, without reading or reflecting its body; malformed success and redirects still fail as an invalid catalog. An account replacement after the snapshot can stale this display but cannot authorize a Run.
- Attached setup reaches first-registration redemption and verified account save after explicit consent; `provider models chatgpt` can use that selected account without inference. The explicit `provider check chatgpt` command uses the same selected account, requires `--accept-cost`, checks visibility, then calls the bounded synthetic transport and publishes exact evidence only after success. It clears old exact evidence before the catalog request, revalidates the account before publication, and never uses an API key as fallback. Evidence is keyed by the retained verified ID token and exact consent receipt, not rotating access/refresh tokens; a new sign-in clears that account's checks. Dropping the async waiter during already-started atomic publication need not roll it back. An attached or explicit `exec` ChatGPT Run reopens the selected account, checks a pinned Session account ID when present, and requires fresh exact model/effort evidence before Workspace input. Run and compaction Events pin an opaque evidence fingerprint and account UUID, and mark that the output cap is local-only. A Session does not gain authority from replayed evidence alone. On Linux, the user accepts keyring storage with an explicit warning that another same-user application may read an unlocked Secret Service item; this [documented risk](../docs/security/findings/linux-secret-service-client-isolation.md) does not permit an Arany-only secrecy claim or a silent plaintext-file fallback. Live sign-in, selected-backend token lifecycle, paid model check, and a real subscription Run still need proof before a beta release claim.
- A pre-stream non-200 synthetic-check failure reports only its numeric HTTP status and compiled recovery advice to the user; no response body is read or reflected. The documented 401/403/503 admission cases receive distinct advice, while 429, other 5xx, and unknown statuses remain cautious and do not infer a plan limit from status alone. For a `response.failed` or `error` event, the check may report a validated, bounded machine-readable code with fixed recovery advice; malformed, token-reflecting, or absent codes, transport failures, and malformed outcomes remain generic. No failure saves model evidence, retries automatically, switches to API-key billing, or erases a stored token based on one 401. The Engine persists only its coarse failure category, not the code. This is not full upstream error-body or request-ID preservation.

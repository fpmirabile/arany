# Provider

Load when changing Provider selection, model configuration, endpoint profiles, credentials, request/response mapping, structured outcomes, routing, usage, privacy provenance, or provider conformance.

The capability/routing evidence lives in `docs/research/beta-multi-provider-routing-and-adapters.md`; the current ChatGPT-plan decision and its weaker output-bound trade-off live in `docs/research/next-step-decision-register.md` (D-18). Keep this file as the working Provider contract.

## Beta contract

- One explicitly selected ProviderProfile, model, reasoning profile, privacy profile, and outcome encoding is pinned before Workspace input and `RunStarted`; every call in that Run uses the resolution. A Session may change its default only between Runs.
- Pin the Provider-declared concurrency ceiling with the selected profile before Workspace input; `RunStarted` records it. Legacy `RunStarted` payloads without the field replay conservatively with a ceiling of one.
- `Provider` remains the only Engine behavior seam. Engine requests and responses contain Arany semantics, never provider wire objects or a generic parameter bag.
- `Provider::compact` is a separate semantic call, not a synthetic AgentRun. It receives bounded accepted conversation outcomes (including unanswered objectives) and optional prior derived summary, excludes Workspace instructions/includes, and must enforce the requested output cap remotely. The resulting summary is untrusted data, portable across Providers only with its recorded provenance.
- Product rollout is staged: native OpenAI and Anthropic first; exact custom endpoint/model profiles join only after data-free conformance; a built-in constrained OpenRouter profile remains deferred behind its route/privacy gate; Z.AI remains unadmitted until an exact profile passes a documented strict outcome contract. The scripted Provider is test-only.
- Provider switching is deterministic selection, not automatic routing. There is no cross-provider/model fallback or hidden discovery call inside a Run.
- Native effort is model-specific, resolved before Workspace input, sent explicitly on every Run and compaction request, and pinned in `RunStarted`. An omitted next-Run choice resolves to the reviewed native model default; unsupported combinations fail before a credential is read. Custom v1 conformance authorizes only provider-default effort; custom v2 declares an ordered set of selectable efforts, probes each one with synthetic input, and pins the selected choice on Run and compaction calls.

## Strict outcome rule

- Prefer provider-enforced JSON Schema for `Delegate | Finish`.
- A synthetic `submit_agent_outcome` call is an allowed private encoding only when the exact provider/model officially supports strict tool arguments and forced tool selection. It is decoded and validated, never executed.
- JSON mode, prompt-only formatting, automatic tool selection, local repair, or schema validation after unconstrained generation cannot satisfy the beta contract.
- Select the encoding from reviewed capability evidence before `RunStarted`. Refusal, truncation, duplicate/missing call, or schema mismatch fails that Provider call without retrying another encoding.

## Configuration and egress

- Resolve an explicit CLI profile/model over trusted Session or user-config defaults. There is no compiled model default, Workspace-defined profile, or implicit discovery.
- Read only the selected provider's credential. Credentials never enter CLI arguments, Events, output, fixtures, telemetry, or error bodies.
- `exec` and explicit native CLI selections use only their named API-key environment variable. Bare new attached mode can instead use one OS-credential-store API account chosen through first-run setup; its Session defaults pin an account UUID, and Run/catalog admission must match that UUID and Provider before retrieving the key. A replaced account never silently becomes the credential for an older Session. Native adapters carry the validated saved-account UUID to the Engine's `RunStarted` provenance; environment-backed and custom adapters carry no saved-account UUID. Native adapters and catalog discovery accept the selected key in-process without changing global environment. Official ChatGPT-plan OAuth is a distinct approved target with private unwired authorization and signed-identity code, but the account route remains unavailable; it requires a clear warning and affirmative account-level acceptance of local bounds without a remote output-token guarantee. Never import another harness's tokens or use a private ChatGPT route. Anthropic remains API-key only unless it grants Arany prior approval.
- The Linux Secret Service backend reads the process D-Bus session address and its D-Bus client supports executable transports. Before invoking keyring, admit only one bounded `unix:path=` or `unix:abstract=` address with an optional exact GUID, or a bounded absolute `XDG_RUNTIME_DIR` fallback. Reject `unixexec`, autolaunch, TCP, address lists, and extra parameters without launching a process or falling back to plaintext.
- Native endpoints come from compiled reviewed profiles. A custom profile lives in trusted user configuration outside the Workspace and names a closed protocol family, exact normalized endpoint/base path, exact model, credential reference, outcome encoding, and capability-evidence version. It never accepts arbitrary headers, shell credential commands, redirects, ambient proxies, or cross-profile credential reuse.
- The loader reads only `provider-profiles.json` from the private state root. Document version 1 is a closed `profiles` array (maximum 32) with unique lowercase-hyphen names, `openai-responses`, exact canonical `/responses` endpoint, model, `ARANY_PROVIDER_*` credential-environment reference, `json_schema`, `user_authorized` privacy classification, and a 4,096-token cap. Capability-evidence version 1 forbids an `efforts` field; version 2 requires a nonempty, unique, canonically ordered `efforts` array from `none|low|medium|high|xhigh|max`. Numeric loopback may use HTTP; domain hosts require HTTPS. A loaded profile is still unverified and cannot be selected for a Run until current conformance evidence exists.
- Before a custom profile receives Workspace data, `arany provider check PROFILE` runs a bounded synthetic conformance sequence and records expiring evidence keyed by Arany/adapter/test versions, exact origin, model, encoding, and output cap. A catalog or model list is not evidence. Unverified profiles are usable only by `provider check`.
- The checker uses three data-free strict Responses probes (direct finish, one child, compaction), plus one strict finish per declared v2 effort, a pinned no-proxy/no-redirect/no-retry destination, and a 24-hour SQLite evidence row. The bound effort list changes the v2 fingerprint; v1 fingerprints remain compatible. After profile admission it clears stale evidence before probes and reads only the selected credential after destination admission. `CustomProvider::admit` re-reads the exact profile, re-resolves every address, compares fresh evidence, and only then reads the selected key; `custom:NAME` Runs use that constructor before Workspace input. A check result alone is not a Run authorization.
- The custom checker and Run adapter share bounded transport and strict Responses decoding. Custom calls require positive labeled usage within the requested output cap; the unproven concurrency ceiling is one.
- Every Provider HTTP client requests identity encoding, disables automatic decompression even if another dependency enables reqwest compression features, rejects any non-identity `Content-Encoding` value before reading the body, and bounds both declared length and accumulated chunks to 1 MiB per response. Compressed Provider replies are deliberately unsupported.
- Require HTTPS outside explicit numeric loopback. Pin destination and reject redirect, route/model drift, changed addresses, metadata/link-local/multicast destinations, and credential reflection. Receipts say `custom verified`; they never relabel a service as native OpenAI/Anthropic.
- For domain DNS answers, IPv6 admission uses reviewed allocated ranges rather than all `2000::/3`; unallocated and reserved ranges fail closed. Refresh the allowlist against the [IANA global-unicast allocations](https://www.iana.org/assignments/ipv6-unicast-address-assignments) and [special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry) when a new range is needed. Numeric loopback remains a separate explicit exception.
- A future built-in OpenRouter profile treats it as a broker: pin one reviewed upstream endpoint; require parameter support; disable fallback; deny data collection; require ZDR; disable response caching; and record broker plus upstream provenance.
- Similar HTTP mechanics may use private concrete helpers. Each adapter owns authentication, request documents, strict encoding, error mapping, usage, privacy, and response parsing. Do not create a transport trait or a universal OpenAI-compatible adapter.

## Reliability and evidence

- Keep zero automatic retries. Provider calls, tokens, bytes, time, concurrency, and admitted children share one immutable aggregate Run budget sized from the resolved collaboration policy. A lost response may already have consumed tokens; broker fallback is also a retry and stays disabled.
- API-key adapters reject exact selected-key reflection in bounded raw response bytes and decoded outcome, response-ID, or compaction fields before any result can become a canonical Event. This includes JSON-escaped echoes but is not general secret detection.
- Persist bounded adapter, endpoint profile, requested/resolved model, request ID, broker/upstream identity, finish reason, usage provenance, privacy controls, and capability-evidence version. Never persist raw response bodies or uncontrolled headers.
- The scripted Provider owns Engine tests. Each product adapter owns hand-reviewed offline wire fixtures and ignored, explicitly activated, credential-and-model-gated live direct/team Runs.
- The native OpenAI Responses adapter admits the exact `gpt-5.4`, `gpt-6-astra`, `gpt-6.1-sol`, and `gpt-6-luna` IDs with `OPENAI_API_KEY`. The [GPT-5.4](https://developers.openai.com/api/docs/models/gpt-5.4), [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), and [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) pages supply the reviewed effort sets; Arany sends the resolved value as `reasoning.effort`. Arany chooses `medium` as the explicit Astra default; the other defaults match their model pages. Its HTTP client must keep redirects, ambient proxies, cookies, and automatic protocol retries disabled; reqwest retries some protocol failures by default unless explicitly overridden. Offline fixtures do not establish live support.
- The native Anthropic Messages adapter admits the exact `claude-sonnet-5`, `claude-fable-5-1`, `claude-opus-5-5`, and `claude-sonnet-5-5` IDs with `ANTHROPIC_API_KEY`. The [official effort guide](https://platform.claude.com/docs/en/build-with-claude/effort) lists each supported level; Opus 5.5 defaults to `medium`, and the other admitted models default to `high`. Arany sends the resolved value as `output_config.effort`. It uses the compiled `/v1/messages` route, `anthropic-version: 2023-06-01`, schema-constrained `output_config.format`, remote `max_tokens`, and the same no-proxy/no-redirect/no-retry bounds. Thinking blocks are ignored as private data; only one complete text outcome is accepted. Normalize Anthropic input usage as uncached + cache-creation + cache-read tokens with checked arithmetic, because `input_tokens` alone excludes cached tokens. Offline fixtures do not establish live support or an account-level ZDR claim.
- A catalog lists availability, not compatibility. Only reviewed manifests, adapter fixtures, and opt-in live probes support capability claims.
- `arany provider models PROFILE` reads only the selected native Models API credential and no Workspace data. It returns the complete account-visible result or fails closed at 1 MiB per page, 16 pages, or 4,096 unique models. The catalog uses no proxy, redirect, retry, or decompression; model IDs are bounded printable ASCII. Native entries outside Arany's reviewed model/effort table are shown as unsupported. A custom exact profile lists only its configured model and declared effort choices without reading its credential; current conformance is still checked at Run admission.
- ChatGPT-plan model discovery has a distinct, currently unwired `models[]` catalog behind a verified OAuth account and matching warning receipt. A visible subscription model is not automatically compatible with Arany's strict outcome or an effort choice; both require separate model-scoped evidence before Run selection.
- The dormant ChatGPT-plan Responses transport uses the native OpenAI strict outcome decoder but a distinct streaming request: `store: false`, `stream: true`, array `input`, and no remote `max_output_tokens`. It accepts only `response.completed`, with positive labeled final usage no greater than the requested local output cap, under a 120-second and 1-MiB stream-read bound. `response.failed`, `response.incomplete`, malformed/encoded/interrupted streams, missing usage, and local overflow fail without publishing partial text. A local abort cannot guarantee a remote generation or plan-usage cap. The transport remains unavailable until account, consent, provenance, model/effort conformance, and Run admission are wired.
- The attached `/models` browser may select only entries from this reviewed table or the one exact custom model. The browser changes idle defaults, not Run admission or capability evidence.

# Testing

Load when continuing beta 1, adding or changing behavior, fixing a defect, editing tests or fixtures, changing user-visible output, or making a correctness, security, durability, provider, performance, or platform-support claim. The detailed rationale and beta evidence register live in `docs/research/testing-strategy-for-rust-cli-harness.md`; keep this file as the concise working contract.

## Evidence budget

- Optimize for evidence per test, not test count or coverage percentage.
- Add a test only when it protects a user-visible contract, durable or security invariant, protocol boundary, concurrency or failure mode, or demonstrated regression; no existing test may already catch the same defect with equally useful diagnostics.
- State the owned claim and the defect the test would catch. If the test cannot be shown to fail for that defect, strengthen an existing test, type, or parser instead.
- Prefer adding a row to an existing scenario, table, corpus, or failpoint harness over adding another test function or file.
- Keep one authoritative test owner per claim. Duplicate a claim at another layer only when real process, platform, durability, or security evidence is materially different.
- Refactors with unchanged observable behavior normally rely on existing tests. Do not test private helpers, getters, type-enforced facts, third-party behavior, mock call order outside the protocol, or abstractions created only for testing.
- Delete or merge tests and fixtures when a stronger owner subsumes them, the contract disappears, or the failure becomes structurally impossible. Keep durable and security regressions in the narrowest stable corpus.

## User-visible proof

- Noninteractive acceptance scenarios produce an `ObservationBundle`: exit class, exact stdout bytes, exact stderr bytes, Events reopened from a closed SQLite store, and the SessionView/RunView reduced from those Events. Interactive scenarios add a separate PTY observation rather than weakening exact `exec` evidence.
- A successful assertion is incomplete when it checks only an Engine return, a Provider call, stdout, or live in-memory state.
- Compare `exec` text, screen-reader output, final receipts, and `show` as exact bytes. Canonicalize only parsed UUIDs, timestamps, and temporary paths explicitly declared volatile; preserve identity relationships, ordering, counts, and every user-controlled byte. Raw interactive escape bytes are not public golden output.
- Parse JSONL one line at a time, compare it semantically with persisted Events, and verify its exact newline and channel contract.
- Use a fresh product process for argument parsing, exit codes, stdout/stderr separation, signal wiring, and `show`. Use Cargo's absolute binary path, an explicit working directory, a cleared allowlisted environment, isolated temporary Session and user-account roots, a parent deadline, and guaranteed kill/reap cleanup. Drain piped channels while waiting, cap each capture, and include EOF collection in the deadline; waiting for exit before draining can deadlock on a valid large export. Existing PTY pumps and descendant guards retain their separate ownership. Unconfigured resume fixtures must isolate the effective UID passwd home in both profiles; clearing HOME or Session state alone cannot exclude host preferences. The shared Linux script fixture uses Bubblewrap user/network namespaces with a private home while preserving host PIDs for lifecycle observers.
- The deterministic successful `exec` exercises the real CLI adapter, Engine, SQLite file, reducer, and renderers in-process with the strict scripted Provider. Bare interactive `arany` reuses the same semantic scenario through the PTY lane. Do not expose a fake-provider CLI mode or add a second product binary for tests.
- The central deterministic Session journey covers process exit/resume, multiple ordered Runs, one single-agent Run, one bounded `N`-child Run with controlled completion order, fork lineage, compaction failure safety, replay, cancellation, and task/thread cleanup. Boundary tables own other collaboration capacities and invalid snapshots.
- Keep a few manually reviewed goldens only for public human/JSONL output. CI never rewrites them, and an agent updates them only with an intentional contract change and a summarized diff.

## Test doubles and fixtures

- Provider is the only Engine behavior double. Its scripted fake matches semantic expectations, controls concurrency with gates, fails on missing/duplicate/extra calls, and proves cancellation with drop guards. Check complete observed request semantics and exact counts outside Engine task panic handling, including failure/cancellation owners; an accidental fake panic must not satisfy an expected failed Run. A held subprocess publishes readiness only after its request matches the fixture.
- A refusal peer must return a valid success if a forbidden request arrives, so the owner's rejection assertion fails; a peer assertion/crash followed by generic product failure is not refusal proof. A native OOM owner must prove its actual payload reached execution, a kernel OOM-kill counter advanced, and cleanup was positively observed. Observer timeout, malformed output or command failure is not disappearance.
- Use real temporary filesystem objects and real file-backed SQLite for state, reopen, permission, journaling, replay, and recovery evidence. `:memory:` is not durability evidence.
- Preserve the host dynamic-loader layout and its complete symlink chain inside Linux mount fixtures; a missing loader can produce an empty PTY transcript before Arany starts.
- Use explicit gates and paused Tokio time for schedules and deadlines. Never coordinate with wall sleeps, randomness, repeated attempts, or assumed task order.
- Keep provider response fixtures minimal and hand-reviewed from the official wire contract. Never capture production responses, credentials, prompts, or user data.
- Use one bounded canary assertion across Provider observations, Events, database bytes, stdout, stderr, controlled panic/error text, and runtime-opt-in telemetry without echoing the canary on failure.

## Evidence lanes

- Beta 1 delivery order is functional implementation, consolidated local verification, then final user-owned testing. At each continuation, select the next implementable functional item before reviewing verification debt. While functionality remains, run only focused local/synthetic checks needed for a changed invariant or known failure; collect remaining checks for implementation closeout rather than starting another verification-only cycle.
- Deferred beta 1 checks: when a check needs manual interaction, real credentials, paid usage, an unavailable OS service, another machine or an unavailable toolchain, record its unverified claim and user-owned procedure once in `NEXT_STEPS.md`. Continue the next implementable task in the same turn with the goal active; this is deferred verification, not an implementation blocker. Leave these checks for the final beta 1 handoff, or beta 2 where already assigned. Never pause or block the goal, request the same prerequisites or test approval again, or wait for the user to test during implementation. When only user-owned checks remain, deliver the consolidated checklist with its unverified status; do not mark the full goal complete without its required evidence.
- Keep verification debt distinct from actual implementation defects or missing authority for an action. Record a user-deferred integration as pending and continue unaffected authorized work without repeatedly revisiting its unchanged authority gate. Fix demonstrated local defects. Pending checks or integrations are not passing evidence; preserve security and resource bounds rather than bypassing them to obtain evidence.
- Default `cargo test` is offline, deterministic, isolated, retry-free, free of wall sleeps and hardware-sensitive timing assertions, and quiet on success.
- Keep beta integration scenarios in one `tests/session_run.rs` target. Focused owning-module tests use compact transition, boundary, hostile-input, or parser tables only where the central journey cannot prove the claim.
- Use pure presentation tables and Ratatui `TestBackend` for Session/composer/status/activity-shelf frames, including single/team/overflow states. Use native Linux/macOS PTY process tests for terminal acquisition/restoration, Session and agent pickers, transient mouse reporting, signals, resize, suspend/resume, cancellation, fallback, tmux, and broken stderr. Do not duplicate Engine scenarios per width or key.
- Exact linear accessibility fixtures prove the absence of CSI/OSC and carriage-return rewriting; manual VoiceOver and Orca checks are release evidence, not silent CI skips.
- One closed-registry contract test owns slash help, aliases, availability, exact parsing, completion, and handlers. A compact corpus owns unknown commands, `//` escape, hostile Unicode/control text, lifecycle availability, and the invariant that interactive commands never enter Provider input while `exec` treats them literally.
- Ignored, explicitly activated and paid live runs cover each native claimed adapter separately. They launch the shipped executable and assert structural bounds, provenance, persistence, channels, and replay—not prose, latency, or model quality. The separate ChatGPT-plan direct-turn gate requires both `ARANY_LIVE_CONFORMANCE=1` and `ARANY_LIVE_CHATGPT=1`, an explicit account-visible model and effort, and an already selected consented account; it runs one synthetic three-call check plus one direct Run, never by default. Its parent reads no token and forwards only OS account/keyring transport variables to the product. Custom profiles own a data-free exact endpoint/model conformance lane before any Workspace-bearing smoke. A built-in OpenRouter profile remains deferred behind its route/privacy gate; Z.AI remains unadmitted until its strict-outcome gate passes.
- Cross-platform claims require native behavior tests for filesystem, ACL, signal, process, SQLite reopen, and terminal semantics. A compile-only target or silent skip is not evidence.
- Process-death, disk-fault, fuzz, repeated-flake, and named-host performance work may run as scheduled or release gates when too expensive for the default loop.
- Record host load and CPU pressure with named-host latency gates. A process-spawn-to-Provider-accept upper bound includes scheduling and transport time; a miss under contention remains a red gate until a quiet-host rerun or direct product-boundary timing isolates the cause. Do not raise the threshold or claim a product regression from that upper bound alone.
- The journal's wall-clock `RunStarted` creation timestamp precedes its append acknowledgement, while the primary `AgentSpawned` creation timestamp follows it. Their interval can diagnose the startup path but cannot replace a monotonic release gate when it straddles the threshold; reject the diagnostic if runner and listener wall-clock spans materially disagree with their monotonic span.
- Stochastic model quality belongs to evaluations; latency and resource distributions belong to benchmarks. Neither can override a failed deterministic invariant.
- Add property, fuzz, model-checking, snapshot, process-test, or concurrency frameworks only when their named boundary has outgrown readable tables or a tool replaces material repeated machinery.

## Failure and maintenance discipline

- In a Bubblewrap cross-user fixture that binds only `/etc/passwd`, make the namespace's generated `/etc` traversable before switching UID; otherwise passwd lookup fails before the account boundary is exercised. Keep the owner home and account record private. Give the second UID an accessible legacy `XDG_STATE_HOME`; pointing it at the owner's private home deliberately fails legacy migration before account selection can be tested.
- A shipped native API-key setup and direct-turn gate can serve the compiled HTTPS endpoints offline from a private Linux network namespace: use hosts-only resolution, a test CA and matching server-name certificate with ordinary TLS validation, and no production endpoint override. In this fixture, OpenSSL `s_server -HTTP` did not answer the Responses POST; use `-quiet` with a bounded request parser and static reply for that turn. This proves synthetic setup and Run flow, not live account-visible models or Provider compatibility.
- A shipped ChatGPT first-sign-in gate can reuse that networkless TLS fixture, with a test-owned browser launcher bound only inside the private mount namespace. Sign the synthetic ID token for the authorization URL's actual nonce and issued client, serve the compiled token/JWKS/catalog paths with bounded peers, and assert account-only replay when the user declines model-check cost. The companion checked-turn path requires a second catalog read, three distinct synthetic SSE completions, two consecutive direct Runs, and one single-child team Run; the second direct request carries only the prior accepted user/assistant turn, while the team child has isolated history and synthesis receives the accepted child result. Inspect selected-token placement, local-only output bounds, terminal restoration, and strict account/evidence-bound replay. The account-only owner also covers a token-free permission-disabled login, fresh-process blocking and explicit same-account enablement. A returning browser-stub gate must wait for the new complete PKCE URL, not reuse the previous file contents. A matching mock URL or unsigned token is not OAuth evidence; either synthetic journey is not live account or keyring proof.
- Run Unix state-owner tests through `cargo test`; with the required RTK prefix, use `rtk proxy cargo test`, not the `rtk cargo test` shortcut. The shortcut denies loopback binds and maps `/tmp` ownership to UID 65534 in this environment, producing false test failures.
- Run `cargo deny check` through `rtk proxy` here; the direct RTK wrapper maps the advisory database lock read-only and can report a false dependency-policy failure.
- For local PTY probes, use `script` rather than a child launched by `python3`: the latter reports root-owned path ancestors as UID 65534 and falsely fails private-state admission here.
- When a GNU `timeout` supervisor wraps an interactive `script` child, use `--foreground`; its default child process group cannot read from that PTY. Keep a separate bounded parent wait and descendant cleanup, since foreground mode does not time out grandchildren.
- A full first-run setup PTY must not write the product's fixed default OS credential slot against the user's live Secret Service or Keychain. Isolate the native credential service/account first; a private State directory alone does not isolate that slot.
- Linux account tests using `ARANY_TEST_ACCOUNT_ROOT` are debug-only: optimized Arany intentionally rejects that override. Test optimized account behavior with a private passwd home and no-network mount namespace, and first prove the no-leaf control reaches the intended boundary; otherwise an early account-root rejection can make a failure test pass without exercising its fixture.
- Focused Cargo and test-binary invocations must report their intended nonzero test count. A self-spawned helper filtered with `--exact` must assert exactly one completed test and have a bounded parent wait/output plus kill/reap cleanup. Helper-only tests are explicitly ignored by default and require their parent's private fixture when activated; returning early without assertions is not a default passing test. Zero-test or ignored-child success provides no evidence.
- To prove the no-account composer without a live keyring lookup, use a private default user StateRoot and an admitted test-owned unavailable local credential-bus address. This can prove local rejection and setup cancellation, not saved-account write/reuse or native keyring behavior.
- An attached PTY that is not testing setup must select an explicit Provider/model with a synthetic, cleared-environment credential; bare startup can read the fixed default OS account slot even under a private State directory.
- `script` is not a terminal emulator: inline PTY tests must answer bounded cursor-position queries, including final restoration before waiting for process exit. A wrapper exercising Ctrl+C must handle its own SIGINT while leaving the product's signal handling intact.
- In raw-mode PTY tests, send carriage return for Enter; line feed is a distinct newline event and can leave a draft unsubmitted. Canonical-line tests still use their physical line boundary.
- A Linux PTY test that kills its `script` wrapper to close the master must separately guard the product PID. Verify the exact executable (including only its exact Linux ` (deleted)` path after replacement) and private State argument before killing only that test-owned survivor; the wrapper's `ChildGuard` cannot reap an orphaned Arany process.
- `script` forwards stdin to its PTY asynchronously. Before signaling during hidden canonical input, wait for product output confirming that a synthetic segment was consumed; an immediate write-then-signal can echo later bytes from the restored shell and does not isolate Arany's secret handling.
- To prove a signal during restored output, bound the parent `script` stdout pipe, pause its reader on the answer prefix, verify restored terminal settings, then signal and drain. A signal after the final receipt does not cover that window.
- For broken-stderr proof, keep the input PTY controlling the product and put stderr on a second PTY; close only that second master after the Provider-start gate, then trigger a redraw. During inline acquisition, Crossterm's cursor query can use the controlling PTY even when Ratatui renders to the separate stderr PTY; observe both streams, close stderr after the query, and answer through the controlling PTY. Cursor queries can prefix shell markers on the input PTY, so locate post-fault markers within its bounded transcript rather than requiring a line start.
- Start the held peer's cancellation deadline only after the renderer fault is actually triggered. A bare SIGWINCH with unchanged geometry does not trigger the bounded Unix reader's resize event; use an admitted draft edit for a redraw-only fault or actually resize the PTY when proving resize behavior.
- For terminal-owner panic proof, run the exported owner in a supervised test helper under a PTY, answer the observed cursor query, and hold the owner at a private gate. Compare the shell's exact terminal settings before acquisition, during raw ownership, and after a deliberate unwind. This verifies RAII cleanup, not an arbitrary shipped-CLI panic site.
- For a Linux broken-stderr acquisition fault, closing the PTY master is not immediate proof that slave writes fail. Keep a test-owned slave handle, probe it nonblocking until `EIO` under a bound, then answer the cursor query; otherwise terminal acquisition may finish and create State before the fault takes effect.
- For the capped Provider-response RSS gate, a server-side half-write marker proves bytes were sent, not that Arany consumed them. Pair the mid-response sample with the product's timed peak, accepted exact-cap response, and strict replay; one custom call does not prove concurrent native response RSS.
- For picker mouse proof, send SGR hover, wheel, and left-click bytes only after observing the inline picker’s bounded `EnableMouseCapture` sequence; assert one matching disable sequence before selection returns to the composer, then verify the chosen Session through exact-ID replay. Pointer coordinates outside visible rows remain inert.
- SGR mouse coordinates are absolute screen positions. Ratatui inline frames can begin below screen row zero, so PTY picker coordinates must follow the rendered frame position rather than TestBackend's zero-origin rows.
- In canonical-line PTY tests, wait for the complete current choice prompt or labeled feedback line before sending more echoed input. A header or diagnostic substring can arrive while the line is still being written; early echo can split an exact-output assertion. After submitting an objective, gate on its expected answer and subsequent prompt before quitting; a leftover or active-Run input prompt is not completion evidence.
- In inline panel PTYs, wait for the finished menu/footer frame before navigating or closing. Scope repeated opening and closure markers to bytes emitted after the current input; an earlier matching notice is not a fresh gate. Wait for the restored composer before sending input after Escape. A header can arrive before Ratatui's cursor-position query and redraw complete; early keys can race the test's cursor reply, causing a false rendering failure or feeding response bytes into the composer. Ratatui can put cursor controls between footer words, so a contiguous raw-text search is not a reliable completion gate.
- Inline completion rows are cell-diff output, not full-line announcements. Gate a known-geometry draft edit on cursor-show followed by its fresh final caret position; the same bare coordinate can occur while painting draft text. Scope fresh-process gates after the restart marker, since prior cleanup may emit the same coordinates; use frame evidence for the full visible label. Send Escape separately and wait for the restored input frame before typing a suffix, since adjacent bytes can otherwise encode an Alt key.
- In a 16-column model-browser PTY, the model ID and close notice are clipped. Wait for the complete `Up/Dn Enter Esc` footer before controlling the browser, and use the post-cancel abbreviated notice rather than the full-width model ID or `closed` word as a readiness marker.
- For native tmux proof, use an exact test-owned `-S` socket beneath a private temporary root. A detached fixed-size pane provides a bounded screen-capture gate; attach a supervised outer PTY and send keys through that client. After a resize, wait for Arany's completed frame at the new geometry before sending history keys; tmux can report the new pane size while the old input geometry is still active. Verify both pane and outer terminal settings. A lingering socket pathname alone does not prove a live server; query the exact socket after shutdown. When the ignored release gate selects an extracted binary, use that same exact executable for data-free Provider conformance, the pane, and guarded process cleanup; still require the private State argument before signaling it.
- For Linux Store file-growth faults, open the file-backed journal before applying `RLIMIT_FSIZE` inside an isolated helper process with ignored `SIGXFSZ`; otherwise the limit can terminate the whole test process or fail setup instead of the intended append. Compare the accepted Event prefix and absent failed Event after a read-only reopen, then remove the limit by exiting that helper before proving recovery.
- For the Linux Store transaction-death gate, hold the test-build Store owner after its terminal Event insert but before commit, or hold the child after append acknowledgement; kill/reap the exact child at each completed stage marker, then reopen the actual SQLite file and compare strict replay, sequence, integrity, and recovery. A marker filename can appear before its bytes are written, so wait for the complete bounded stage value rather than mere existence. This proves the application transaction/acknowledgement boundary, not arbitrary power-loss timing.
- For shipped `exec` file-growth faults, finish data-free custom Provider conformance and create a committed Session before launching the limited product child. Ignore `SIGXFSZ` only there; compare exact failure channels, absence of a runtime Provider request, strict read-only replay, and post-fault append. The Store-only helper does not prove product reporting.
- For real Linux `ENOSPC`, mount a bounded `tmpfs` only inside a supervised child user/mount namespace and fail visibly if namespace or mount admission is unavailable. Chroot that child to the private mount before opening State: host-owned ancestors have unmapped UIDs inside the user namespace and must not be excused by weakening StateRoot admission. Require the filler write to receive `StorageFull`, SQLite to report `DiskFull`, strict read-only prefix replay and integrity after capacity returns, and a successful recovery append. This is tmpfs exhaustion, not block-device failure or power-loss evidence.
- For a shipped `exec` inside that private root, bind the already-built binary, its dynamic loader/libraries, and the host CA bundle read-only, plus `/dev/null` for standard streams. Reqwest initializes the system trust store even for a numeric-loopback HTTP profile, so a missing bundle can fail conformance before the storage fault. Keep a PID namespace around descendants, prove Store open still succeeds at zero free blocks, and compare exact product channels, absent runtime Provider egress, canonical replay, integrity, and recovery.
- For a nonblocking Workspace-input gate, use a real FIFO with no writer inside a supervised child process and a parent deadline; a Unix socket's rejection alone does not prove the open cannot hang. Confirm no Provider call or canonical Event. [Linux `fifo(7)`](https://man7.org/linux/man-pages/man7/fifo.7.html) defines the blocking-versus-nonblocking open behavior.
- For the Linux Workspace replacement gate, atomically exchange each selected path component with an outside-pointing symlink. First prove the safe and rejected stable states, then require actual swap/load overlap and no outside bytes across finite attempts; keep the gate ignored and explicitly timed. [Linux `renameat2(2)`](https://man7.org/linux/man-pages/man2/renameat2.2.html) permits exchanging a directory and symlink.
- For paused Tokio deadline tests involving the SQLite owner thread, pause time after the Provider-start gate and resume before awaiting durable shutdown; otherwise virtual-time auto-advance can outrun the real store thread.

- Failure output names the scenario and case, expected and observed exit, bounded escaped stdout/stderr, semantic Event difference, and safe fixture identifier. It never dumps secrets, raw hostile controls, provider bodies, or database payloads.
- Every test runs independently and owns its directories, files, ports, runtime, database, and processes. Do not mutate shared process environment from parallel tests.
- A flaky deterministic test is a product-or-test synchronization bug. Fix it; do not retry until green or weaken the assertion. Temporary quarantine names an owner, the missing claim, and a removal condition and does not count as passing evidence.
- For behavior changes, identify the current owner, demonstrate the failure, update the smallest scenario or corpus row, review exact output changes, and remove superseded evidence.
- Report verification by claims proved and lanes run, not by the number of tests added. State explicitly when live, platform, release, or performance gates were not run.

# Persistent Workspace build cache

Load when changing `src/store/state/build_cache.rs`, Guard cache transfer, or `/cache` clear behavior. The [Tools spec](../docs/specs/tools.md#persistent-workspace-build-cache) owns observable behavior; Store and Guard rules own their surrounding boundaries.

- Store archives live only beneath the admitted StateRoot handle. Key each archive by the exact canonical Workspace path plus checked device/inode; cap identities at 128 and committed, staged, reserved, and bounded metadata at 8 GiB total. Each archive and native scratch-backed writable view is capped at 64 MiB. Never expose a StateRoot path or handle to a payload.
- Keep one current versioned archive format. Stream through fixed-size buffers and enforce the allowlisted cache roots, 64 MiB archive size, 16,384 entries, 4 KiB path, depth 32, and 8 MiB path index bounds. Store regular single-link files and directories only; reject symlinks, special files, malformed paths, set-ID inputs, identity drift and unknown archive data. Restore files without following links and preserve executable bits only.
- Hold a nonblocking exclusive identity lease across restore, candidate collection, publication and clear. Reserve candidate plus staging capacity under a nonblocking aggregate lock before dispatch. Competing cache operations return busy rather than wait; this keeps synchronous Store lock waits out of the Tool deadline. Recovery and mutation use the same identity/aggregate lock order; never evict another identity to make room. `/cache clear` removes only the current Workspace identity and `/cache clear all` is the explicit recovery for stale identities.
- Task transport carries only the checked Workspace identity and exact selected read-only host-cache exclusions, never StateRoot locations. Revalidate the identity in Store. Host cache grants authorize only their exact read-only subtrees: exclude those roots before private traversal and restore, never import host bytes, and preserve prior Arany-owned entries below an excluded root while publishing other paths. Do not read package-manager configuration or credential files.
- Reject an existing-cache admission overflow before Ready/GO. Candidate size or aggregate overflow can occur after a command; reject that publication and retain the previous archive. Guard may request Store publication only after a successful command and positive platform cleanup. Any command failure, cancellation, timeout, transfer error, or uncertain seed/unit/storage cleanup preserves the previous cache.
- Build a complete candidate beside the committed archive, sync it, and durably record rollback intent before swapping names. The commit point is the committed marker plus a successful parent-directory sync; only then is publication acknowledged and backup cleanup allowed. Before that point, an error rolls back using the durable rollback intent. If writing or syncing the committed marker fails, return the persistence error, skip Drop-time recovery, and retain the previous archive, candidate archive and transaction records. Later recovery must first sync the directory successfully before resolving a committed marker; a continuing sync failure blocks cache admission and leaves explicit clear as recovery. A positively synced commit marker keeps a validated new archive and finishes backup cleanup. If a committed new archive is invalid but its previous archive is valid, recovery restores the previous one. Malformed or unsafe records fail closed and remain available for diagnosis.
- Store-side archive I/O has fixed byte, path and entry bounds, but local filesystem stalls are not a hard-real-time guarantee. Linux and macOS Guard transfers remain within their existing startup, command and cleanup deadlines.

Native cache evidence belongs in the existing Linux Guard and macOS owned-unit command journeys. Do not claim general build support from the bounded cache fixture; real native build admission and measured host support remain separate evidence gates.

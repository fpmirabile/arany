# Protected API accounts

Load for changes to `src/cli/credentials.rs`, saved-account selection, OS keyring integration, or Linux D-Bus transport admission. [security.md](./security.md) still owns the repository-wide secret and supply-chain rules; [provider.md](./provider.md) owns Provider admission.

A saved Provider Account is scoped to one OS user across that user's Sessions and StateRoots, never machine-wide. On Linux, its marker and lock now use the effective OS user's passwd home under `.local/state/arany`, independent of `HOME`, `XDG_STATE_HOME`, and Session `--state-dir`; the fixed keyring slot remains in that user's OS credential store. Private-file migration, optimized private-file setup/reuse, one synthetic saved-account direct turn, and cross-user startup have recorded evidence. Earlier native-keyring owner results used direct test-only access and do not establish the supervisor path; rerun the corrected isolated owners before claiming it. The [cross-root finding](../docs/security/findings/default-account-slot-cross-root.md) stays open for isolated keyring-backed product setup and cross-user proof. macOS still uses its environment-derived default root and requires a later native scope review. Linux targets Secret Service, not KDE Wallet specifically.

- The private CLI credential module owns one versioned, at-most-1-KiB default native API account. Setup prefers the OS keyring when available; an unavailable unpinned keyring may lead to a separately warned, explicitly selected private-file choice. [Terminal rules](./terminal.md#terminal-behavior) own its safe default and input modes. A versioned file under the account StateRoot pins either the keyring backend (without a key) or the file backend (with the account); a pinned keyring never silently downgrades on read or write failure. A locked keyring reports a locked error, not a fallback. The record validates the exact native Provider, UUIDv7 account identity, bounded printable key, and either a reviewed model/effort or a bounded model ID with explicit effort on both write and read. A saved tuple is not compatibility evidence; Run admission revalidates its selected account/source and model/effort without a mandatory synthetic check, while strict request/outcome validation remains enforced. Errors are redacted; never format a platform error or derive `Debug` for the record.
- Key-only accounts keep schema 1 and omit workspace scope. Schema 2 requires a validated explicit Anthropic API workspace; mismatched versions, absent/invalid scope and cross-Provider scope fail closed. Keep the outer backend marker and 1-KiB aggregate limit unchanged. Older binaries must reject a scoped account rather than silently discard its billing scope. The selected-account loader returns the whole typed credential after UUID/Provider validation; no saved path reconstructs workspace scope from the environment.
- A Session stores only the account UUID. Before native Run or catalog use, resolve that UUID and Provider against the current protected record; a replaced account is unavailable to an older Session. Explicit environment-backed paths never fall through to the protected record, and the protected path never falls through to an environment variable.
- A bare start probes checked protected-record presence before choosing between saved API and ChatGPT access, without loading either payload. When both records exist, the user explicitly chooses the billing route on every new attached start; cancellation reads neither payload and creates no Session. An invalid selected record fails without falling back to the other route. [Terminal rules](./terminal.md#terminal-behavior) own the safe choice default. An old unpinned keyring item is discovered only through the explicit native inspection/setup path when a ChatGPT index is already present.
- Keyring access runs in a short-lived same-binary helper with a five-second parent deadline, bounded private pipes, a fixed service, an admitted local transport, an empty environment except required OS account/bus variables, and a fixed safe working directory. The parent kills and reaps a stalled helper; account replacement holds its lock until then. Pass a key only through the bounded pipe, never through arguments, Events, logs, telemetry, terminal drawing calls, or process-global environment. A timed-out write reports an explicitly uncertain OS-store outcome, distinct from a timed-out read; keep the backend pinned and never claim rollback. The ignored synthetic write-supervisor gate proves the helper's connection closes after timeout, not that a real OS service rolls back an accepted write. The [native credential finding](../docs/security/findings/stalled-credential-store.md) remains a release gate.
- Native credential-owner tests use that same supervisor for reads, writes and ChatGPT deletion, never direct `cfg(test)` keyring calls. Their test build selects the explicitly supplied absolute `ARANY_TEST_EXE` because a Rust test executable cannot run the product's internal helper command; the shipped binary still uses its own executable and ignores that fixture variable. Activate native owners only against an isolated service with synthetic slots. Read back the owner's actual save/replacement before any independent write that could mask its failure. Native observation processes need their own bounded parent wait/output and kill/reap cleanup in addition to a descendant timeout; filtered unit children must complete exactly one test. Synthetic input uses a bounded private file rather than a potentially blocking parent pipe write.
- The same helper also admits a separate `chatgpt-` slot derived from the verified issued client ID. It validates a versioned, consent-bound token record before write and allows at most 64 KiB for that slot; native API-account slots retain their 1 KiB bound. A zero-byte probe checks availability without returning an existing secret to the parent. Input writing and bounded output draining run concurrently under the same deadline so a larger token pipe cannot block the supervisor. Consented ChatGPT setup can save a verified token through this helper, and checked Provider Run admission can load and refresh the selected token. ChatGPT logout may delete only a validated `chatgpt-` slot, not a native API-account item; the five-second supervised deadline can leave deletion uncertain, so account use stays blocked and the user receives a warning. A locked keyring is not treated as missing for setup file fallback; native Secret Service behavior still needs its isolated product-process gate.
- The same validated `chatgpt-` deletion path is also used after a recognized terminal refresh-token error. The account index disconnects and clears model evidence before the helper runs; failure to confirm deletion never re-enables credential use and must remain visible to the user.
- A successful read-only Secret Service probe does not prove a later write will succeed. In a private headless Linux D-Bus/KWallet compatibility session, explicit service activation made the probe pass but a synthetic helper write still failed. That service reported zero collections; independent `secret-tool store` did not finish under a 15-second guard. This narrows the missing prerequisite to native writable/unlocked service behavior, without proving its exact cause or a product regression. Keep the isolated write/setup gate open without making KDE a required product backend or touching the user's real wallet.
- The approved file fallback is plaintext at rest under a checked `0700` user-owned StateRoot: each fixed, bounded record and pending replacement is a no-follow, single-link, owner-checked `0600` file. Atomic rename and file/directory sync prevent a partial final record; a crash can leave one bounded pending file. These modes do not encrypt the key or prevent another same-UID or privileged process from reading it. On Linux, a validated record in the previous environment-selected root is copied under its old lock and the stable account-root lock; the old record becomes a version-zero tombstone only after the new copy is durable. A partial copy can finish on retry, while a different existing account fails with a redacted conflict instead of overwriting either one. The tombstone is not secure erasure of disk remnants. A debug-assertions-only `ARANY_TEST_ACCOUNT_ROOT` override isolates product-process tests; optimized builds reject it, and no release account-root override is supported.
- On Linux, admit only a single bounded `unix:path=` or `unix:abstract=` D-Bus address with an optional exact GUID, or a bounded absolute `XDG_RUNTIME_DIR`, before invoking keyring. With both variables absent, pinned `zbus 5.19.0` connects directly to `/run/user/<effective UID>/bus`; this fixed fallback does not autolaunch. Reject hostile explicit transports and address lists without command execution. Re-check all three paths whenever the keyring or D-Bus dependency changes.
- The system-store availability, replacement, unlock/failure behavior, and key-at-rest properties require native Linux and macOS release checks. Arany claims OS-store protection, not that every Linux Secret Service backend encrypts at rest or restricts an unlocked item to Arany. The Secret Service API permits cross-client access depending on the installed backend; its encrypted transport is not app-level authorization.

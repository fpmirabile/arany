# Protected API accounts

Load for changes to `src/cli/credentials.rs`, saved-account selection, OS keyring integration, or Linux D-Bus transport admission. [security.md](./security.md) still owns the repository-wide secret and supply-chain rules; [provider.md](./provider.md) owns Provider admission.

- The private CLI credential module owns one versioned, at-most-1-KiB default native API account. Setup prefers the OS keyring when available; an unavailable unpinned keyring may lead to a user-confirmed private-file choice. A versioned file under the default user StateRoot pins either the keyring backend (without a key) or the file backend (with the account); a pinned keyring never silently downgrades on read or write failure. A locked keyring reports a locked error, not a fallback. The record validates the exact native Provider, UUIDv7 account identity, bounded printable key, and either a reviewed model/effort or a bounded model ID with explicit effort on both write and read. A saved unreviewed tuple is not permanent capability evidence; Run admission rechecks its exact current evidence. Errors are redacted; never format a platform error or derive `Debug` for the record.
- A Session stores only the account UUID. Before native Run or `/models` use, resolve that UUID and Provider against the current protected record; a replaced account is unavailable to an older Session. Explicit environment-backed paths never fall through to the protected record, and the protected path never falls through to an environment variable.
- Keyring access runs in a short-lived same-binary helper with a five-second parent deadline, bounded private pipes, a fixed service, an admitted local transport, an empty environment except required OS account/bus variables, and a fixed safe working directory. The parent kills and reaps a stalled helper; account replacement holds its lock until then. Pass a key only through the bounded pipe, never through arguments, Events, logs, telemetry, terminal drawing calls, or process-global environment. A timed-out write has an uncertain OS-store outcome even after the helper dies; keep the backend pinned and report failure without a rollback claim. The [native credential finding](../docs/security/findings/stalled-credential-store.md) remains a release gate.
- The approved file fallback is plaintext at rest under a checked `0700` user-owned StateRoot: each fixed, bounded record and pending replacement is a no-follow, single-link, owner-checked `0600` file. Atomic rename and file/directory sync prevent a partial final record; a crash can leave one bounded pending file. These modes do not encrypt the key or prevent another same-UID or privileged process from reading it. Account replacement takes its lock under the default user StateRoot rather than the Session's optional `--state-dir`; a different process environment can still select a different default root.
- On Linux, admit only a single bounded `unix:path=` or `unix:abstract=` D-Bus address with an optional exact GUID, or a bounded absolute `XDG_RUNTIME_DIR`, before invoking keyring. With both variables absent, pinned `zbus 5.19.0` connects directly to `/run/user/<effective UID>/bus`; this fixed fallback does not autolaunch. Reject hostile explicit transports and address lists without command execution. Re-check all three paths whenever the keyring or D-Bus dependency changes.
- The system-store availability, replacement, unlock/failure behavior, and key-at-rest properties require native Linux and macOS release checks. Arany claims OS-store protection, not that every Linux Secret Service backend encrypts at rest or restricts an unlocked item to Arany. The Secret Service API permits cross-client access depending on the installed backend; its encrypted transport is not app-level authorization.

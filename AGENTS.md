# Arany

Arany is a Rust-first, CLI-only harness for multi-agent coding teams that can be trusted to work autonomously. The product and executable are named Arany and `arany`; the repository directory name is not part of the contract. This file guides agents developing Arany; the [documentation map](./docs/README.md) locates contracts and owners.

This file is already in your context; do not re-read it. Linked files are references, not preloads: open one only when you reach the action that triggers it, and read only the section you need (`rg -n '^#' FILE`, then a bounded read). Specs are large; never read a spec whole.

## Non-negotiable guarantees

Multi-agent coordination builds on five guarantees. Never weaken them for speed, convenience or parity with another harness; a guarantee costing more than a peer's unguarded path is a defect to fix, not a price to accept:

- **Journal-first durability.** Every Provider call, Tool intent, effect, approval verdict and team transition (spawn, lease, handover, integration) is a committed Event before the next step; the reducer validates each transition; strict replay never re-executes.
- **Honest uncertainty.** An effect with an unknown outcome is Uncertain: it stops its continuation, is reported unknown and never retries itself.
- **Per-effect isolation.** With the Guard active, processes, Skill scripts and MCP calls run in it under pinned, typed grants, need no approval beyond the user's deny and ask rules, hooks and plan, and publish only through validated changesets with receipts. With the Guard `off`, or `auto` without a sandbox, commands run on the host only under a human approval, an admitted user-owned rule or the auto-mode review, marked host and never retried; `required` fails closed. Extra read grants for guarded commands come only from a human approval or the user-owned Guard list. Exact reads, typed discovery (List, Glob, Search), Skill text reads and typed file mutations run [in process](./docs/specs/tools/file-operations.md#in-process-file-operations) under the same capabilities, preconditions and receipts, and never widen disclosure. Each editor works in its own private workspace and publishes into the Workspace only through one integration-time changeset with receipts and checkpoints. Typed Git runs natively on the host: reads with fixed arguments and no approval; writes, push and PR under the same approval as other host actions, where auto mode's review covers push and PR only to the folder's user-pinned repository; all journal-first and never retried. [Host execution](./docs/specs/tools/host-commands.md#primary-host-commands) (with [remembered prefixes](./docs/specs/tools/host-commands.md#remembered-host-prefixes) and [typed `gh` reads](./docs/specs/tools/git.md#human-approved-host-git)) is authorized only by a human approval, an admitted user-owned rule or the auto-mode review, journal-first, bounded, marked host, and never retried, rewound or used as an approval-free Guard fallback. Privilege-escalation commands never run; the user runs them by hand. Children may run host commands only per call under the same authority, and never inherit host approvals. Unsupported required enforcement fails closed.
- **Durable, budgeted Goals.** Budgets, pause, steering, cancellation and recovery survive exit and crashes; exhaustion closes the Goal, not the guarantee.
- **Safe AI cage (hostile-input neutralization).** Workspace `AGENTS.md` instructions are scoped behavior rules below user and system instructions, never authority. Other repository content, Tool output, MCP metadata/output, Skill text and child reports are untrusted data for instruction, trust and approval decisions, never executable harness configuration; they, model text, hooks and ACP client policy never authorize host execution or extra read grants. AI review authorizes host execution only in auto mode, for actions no user rule covers, judging only the user's own prompts in the Session and the exact action, never model text, Tool output, repository content or child reports; ask-rule matches still need a human, and the review never approves a push or PR to any destination other than the folder's user-pinned repository. Git runs natively with the user's configuration, through typed operations only; hooks run only if the user accepted them for this folder, and configuration that would execute a Workspace file refuses. With accepted hooks, a Git write needs a human approval, an admitted user-owned allow rule or, in auto mode, the review. Within intact state, children stay within the parent's grant, and hooks only narrow. An approved host command runs with the user's full authority, including over Arany's own state; approval does not make it isolated, and the journal is not tamper evidence.

If a guarantee blocks work, record it and raise it with the owner; never weaken it silently.

Everything else (agent loop, wire formats, defaults, permission modes, hooks, agent definitions, context strategy, UX, embedding surfaces) follows proven harness designs (priority 4); diverge only when a guarantee requires it.

## Product and implementation priorities

1. **Build the harness.** Arany owns agent execution, context, Tools, permissions and durable Sessions. Keep product policy in the Engine and platform, Provider and presentation details at their boundaries; judge changes across the whole task lifecycle, including failure, cancellation and recovery.
2. **Linux and macOS parity.** Equivalent behavior on both; native Windows is out of scope (use WSL2). Prefer standard/library OS facilities, then narrow native adapters; assume no shell, path layout, desktop, distribution or service manager. Document unavoidable differences in the owning contract; unsupported security enforcement fails closed. Linux-first is delivery order, not the boundary; native support needs native evidence.
3. **Ponytail on every implementation.** Make the smallest change that works: reuse existing code, std, OS facilities and installed dependencies; add only complexity the task or a demonstrated constraint requires, never speculative abstraction. Never cut scope, correctness, security, accessibility, error handling, resource bounds or verification to save lines; repository rules win over the skill's shortcuts. For a new module, a cross-module refactor or a code review, load the `ponytail`, `rust-clean-code` and `clean-architecture-review` skills by name ([setup](./agents/skills/README.md#install-for-a-harness) if missing); local fixes and UI tweaks need only these lines and rule 8.
4. **Prefer proven harness designs.** When proven harness designs share a working answer for a behavior, default or wire format, replicate it; diverge only for a documented Arany constraint (security, durability, strict replay), stating the reason in the owning contract.

## Global rules

1. **English only**: all repository content, including code, comments, documentation, configuration, user-facing copy, commit messages and public API names.
2. **Minimal comments**: default to none; add short `//` lines only for a non-obvious reason beside its code. No `//!` or multi-line doc blocks in internal code: behavior belongs in specs, implementation invariants in tests. Architectural reasoning belongs in design documents or ADRs.
3. **Deep modules**: keep interfaces small and hide complexity inside the implementation. Prefer in-process calls. Add a seam only with two adapters or when privilege, process, release or ownership isolation requires it. No speculative frameworks, traits or configuration.
4. **Explicit resource bounds**: queues, buffers, caches, request bodies, decompression, stdout/stderr, tool output, artifacts, concurrency, and retry counts have declared limits and overflow behavior. Goal usage follows its pinned settings ([defaults](./docs/specs/goals.md#lifecycle-budgets-and-recovery)) without removing finite per-action, request, Tool and platform bounds. Disk is bounded by free space: guarded commands and the build cache have no size cap unless the user sets one, caches are evicted first when free space nears the reserve the journal needs, and a command stops at that reserve.
5. **No historical residue**: remove superseded code cleanly. Keep one current internal format at runtime without compatibility readers. SQLite stores keep one format version; JSON records carry none ([record rules](./docs/specs/execution/persistence.md#incompatible-records)): a change of meaning renames the field, tolerant preference and cache records only add optional fields with defaults, and strict authority records change shape. Pre-beta, state another binary wrote that the current decoder refuses is archived intact and replaced with a fresh store plus a notice, and there are no migration steps or fixtures until the owner declares a beta migration floor. Never silently alter what cannot be read. External protocol support stays with its owning contract. Documentation describes the current system; git history records the old one.
6. **Never inspect or print `.env`**: read `.env.example` only. Commands may load secrets without echoing them or dumping the process environment.
7. **Unsafe Rust is exceptional**: keep `unsafe` isolated behind a safe interface, document its invariants, and require a dedicated review and test strategy.
8. **Clean code shape**: name every limit, size, timeout, ratio and retry count once, beside its owner, and derive every other use from that constant, including user- and model-facing text. Extract shared logic into its owner instead of copying it across modules. Use domain types and enums for identities and states (Provider names, phases, dispositions) instead of raw strings or flag booleans. Keep functions single-purpose: a function past 80 lines, nesting past 4 levels or 5 parameters is a split signal to resolve or justify in review. A new flow, type or function that would put a function past those signals, or a file's production lines (excluding `#[cfg(test)]` modules and test files) past 2,000, goes into a new phase or family child in the same PR; a fix inside existing code does not trigger the split. Justify any exception in review. The [library](./agents/arany.md#growth) and [binary](./agents/arany-cli.md#growth) practice name where each kind of new code goes. [rust-clean-code](./agents/skills/rust-clean-code/SKILL.md) owns the detail.

## Workflow

1. **Read the code you will change first; open a rule or spec section when your edit touches its trigger.** Plan first only for multi-module or public-interface changes: scope, Ponytail choice, OS impact or none, triggered [security pass](./agents/security.md#security-pass-triggers), and verification of success and meaningful failure paths through existing evidence owners. Ask before deleting files, renaming public APIs, restructuring modules or changing CI/shared infrastructure unless the request authorizes it; preserve user work ([Git](./agents/git.md)).
2. **Verify by target locally, fully in CI.** Run formatting, Clippy and the tests covering what you touched ([verification](./docs/development.md#verification)); CI runs the full suite on code PRs (after pushing, follow [Git](./agents/git.md#pull-requests)). Red CI blocks handoff; if a failure is demonstrably unrelated or infrastructural, say so with the run link and ask the user. Until a stable pre-beta, synthetic tests plus green CI suffice; live, native and manual checklists stay in [NEXT_STEPS.md](./NEXT_STEPS.md), never block day-to-day work, and are the only basis for native or live support claims.
3. **Touch documentation once, only when behavior changed.** Update the owning spec when observable behavior, a limit or a recovery path changed; a refactor, a fix restoring specified behavior or an adequate contract needs no edit. Record each found invariant, failure or ownership decision once at its owner ([auto-learning](./docs/specs/README.md#auto-learning)). Review the final diff with Ponytail, keep local visual artifacts in gitignored `.lavish/`, and report changes, checks run, limitations, platform evidence and, from a plan, the [slice IDs](./planning/PLANNING.md#slice-delivery) completed or left open.
